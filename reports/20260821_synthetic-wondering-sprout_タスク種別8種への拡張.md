# タスク種別を6種から8種へ拡張した作業結果

対象issue: #110（個別計画のタスク種別を6種から8種へ拡張する）

関連: `plans/synthetic-wondering-sprout.md`（全体作業計画）、
`plans/【設計】タスク種別8種への拡張.md`（個別作業計画）

## 何をしたか

個別計画のタスク種別を6種から8種へ拡張し、`【AIアセット作成】`（フェーズ3〈作業〉）・
`【実装反映】`（フェーズ4〈反映〉）を新設した。この種別を重複記載していた4ファイルすべてを
更新した。

| ファイル | 変更内容 |
|---|---|
| `.claude/skills/issue-mr-flow/SKILL.md` | 種別6種の列挙を8種へ拡張し、各種別が属するフェーズの一覧表を新設。併記/分割の指針（`【設計反映】`/`【AIアセット反映】`は併記しない）を`【実装反映】`まで含めて拡張し、`【AIアセット作成】`の併記/分割基準も明記 |
| `.claude/docs/spec/issue-mr-workflow.md` | 「計画の2階層構造」節の「6種」記述を8種へ更新し、詳細をSKILL.md側へ委譲 |
| `.claude/rules/docs-workflow.md` | ライフサイクル表の`plans/【種別】タスク内容.md`行の種別列挙を8種へ更新 |
| `plans/REVIEW-POINTS.md` | 「種別」節を8種へ更新し、新種別の使い分け（`【AIアセット作成】`/`【AIアセット反映】`が成果物か副産物か、`【実装反映】`がフェーズ3のループと役割重複していないか）をレビュー観点として追加 |

## 新種別の定義（確定内容）

Planレビューで`【実装反映】`の使いどころについて2段階の議論があった（詳細:
`plans/synthetic-wondering-sprout.md`「『実装反映』の使いどころ」節）。最終的にissue本文どおり、
次の定義に確定した。

- **`【AIアセット作成】`（フェーズ3〈作業〉）**: そのissueの主たる成果物としてAIアセット
  （スキル・ルール・エージェント・スクリプト）を作る作業。副産物としての改善を反映する
  `【AIアセット反映】`（フェーズ4）とは、成果物か副産物かで使い分ける。
- **`【実装反映】`（フェーズ4〈反映〉）**: フェーズ3（とくに`【テスト】`）で失敗・不具合が
  判明した場合に、フェーズ4でその内容を記録へ書き戻しつつ、実装コード・テストコードの修正も
  あわせて行う種別。`【設計反映】`（spec/ddrへの書き戻しのみ）と対になる。フェーズ3の
  レビュー往復ループ（3-6〜3-9）で解消できる不具合はそちらで対応し、フェーズ4へは持ち越さない。

## なぜそうしたか

- **`【AIアセット作成】`が無かった理由**: `【実装】`は実装コードを指すため、AIアセット
  （非コードの運用資産）の作成には合わない。
- **`【実装反映】`が無かった理由**: `【設計反映】`はspec/ddr、`【AIアセット反映】`は
  `.claude/rules/`等が対象で、実装コードの更新を扱う種別が無かった。
- **却下した代替案**（DDRへ記録予定。flow-id 4-6）:
  - 既存種別（`【実装】`・`【AIアセット反映】`）を流用する案 → 対象・成果物か副産物かの
    区別が曖昧になるため却下。
  - 種別を増やさずfree-textで書く案 → 機械的な列挙（`plans/【*.md`）・レビュー観点表との
    整合が取れなくなるため却下。
  - `【実装反映】`を「フェーズ4の設計反映作業中にAIが気づいた実装との差分」に限定する案 →
    「反映計画では立てられない役割で、起きたら別issueで書く内容」としてPlanレビューで
    却下（詳細は全体作業計画を参照）。

## 敵対的レビュー対応（フェーズ3・1回目）

`.claude/skills/adversarial-review/SKILL.md`に基づき実施した敵対的レビューで major 10件・
minor/nit 6件の指摘を受けた。majorの10件はすべて修正した内訳は以下のとおり。

- `【実装反映】`の除外条件（フェーズ3ループで解消できる不具合はフェーズ4へ持ち越さない）が
  適用範囲をほぼ全て飲み込んでいた点 → 「ループ合意後に判明した／持ち越すと合意したもの」に
  限定する形へSKILL.md本文を修正。
- `【設計反映】`と`【実装反映】`の対象重複（spec/ddrへの書き戻し）が「対象が異なるから分ける」
  という根拠と矛盾していた点 → 対象の重なりを認め、評価軸（実装・テストの修正を伴うか）で
  使い分ける説明へ修正。
- flow-id 4-1/4-6（反映対象の洗い出し・スキップ判定・作業内訳）に`【実装反映】`が未反映
  だった点 → 3箇所とも追記。
- `【AIアセット作成】`が新規作成のみに限定され、既存アセットの改訂（本issue自身がその実例）を
  扱えなかった点 → 「新規作成・改訂」の両方を対象とする定義へ修正。
- AIアセットの定義に「スクリプト」を含めており`【実装】`/`【実装反映】`との境界が消えていた点
  → スクリプトを対象から除外（`.claude/scripts/`配下は`【実装】`側で扱う）。
- reportsに貼った検証出力が実際の実行結果と食い違っていた点 → 実際に実行し直した出力へ
  差し替えた（本ファイル上記「検証結果」）。
- 個別作業計画の検証コマンドが「経緯注記」を理由に常に失敗しない仕様になっていた点 →
  経緯注記を除外する形へ修正。
- HANDOFF.mdのflow-id 3-2が実施していないのに`[x]`になっていた点 → `[]`へ戻し、
  実施内容を文章で補足。
- specに本issueの「影響範囲」エントリが無かった点 → エントリを追加（上記）。

minor/nitの6件（確度・重大度の組み合わせにより投稿対象外だったもの）は本ラウンドで次のように
対応した。

- reports冒頭の文が途中で切れていた → 修正済み（本ファイル冒頭）。
- 2つ目の検証（新種別への言及確認）が出力を貼らずに結論していた → 件数付きの実行出力へ
  差し替え済み（本ファイル上記）。
- HANDOFF.mdでflow-id 3-5（MR description更新）を飛ばした判断が記録されていなかった →
  HANDOFF.mdへ追記。
- issue-mr-workflow.mdでフェーズ帰属の説明がSKILL.mdと重複していた → 軽微なため今回は
  据え置き（「正はSKILL.md」という参照自体は既に明記されているため実害は小さいと判断）。
- `plans/REVIEW-POINTS.md`のインラインコードが改行で分断されていた → 1行へ修正。
- `plans/synthetic-wondering-sprout.md`の「计画」の誤字（簡体字混入） → 「計画」へ修正。
