構成する純粋関数（テストから直接呼べる）:

  • is_excluded_target_path: .claude/scripts/test/ plans/ reports/ worklog/配下の判定
  • is_placeholder_candidate: 省略記法（.../…）を 含むかの判定

  • split_concatenated_candidates_to_reply: 終端文字集合で区切れず連結 された候補を、.claude/docs/ddr/という接頭辞の再出現位置で分割する

mainはif [ "${BASH_SOURCE[0]}" = "${0}" ]; then main; fiで ガードし、単体テストからのsource時に実行されないようにした。走査対象が0件の ときは非0で終了する（空振りで緑になることを防ぐ）。

想定と異なった点

実装直後（v1）に対する敵対的レビュー（2回目、12件のfindings）で、実機再現を伴う指摘を 多数受けた。全件を検証のうえ、以下の重大な欠陥を修正した。

恒久ファイルのコメントがplans/を参照していた .claude/scripts/src/配下は永続コードだが、v1のコメントは plans/【実装】【テスト】〜.mdという短命ファイルを指しており、 .claude/rules/docs-workflow.md「恒久的な参照先」に反していた（本issue自身が 直そうとしている欠陥類型と同種で、皮肉にも本スクリプト自身のDDRパス限定の正規表現では 検出できない対象だった）。issue番号のみの参照へ修正した。
フェンス除外後の行番号がずれていた（v1のバグ） v1は行を削除する2パス方式（フェンス内の行を文字列から取り除いてから改めて行数を数える） だったため、フェンスの後ろにある参照切れの報告行番号が実ファイルの行番号とずれていた （実測: 6行目にある参照がdoc.md:3と誤って報告された）。対応: フェンス 除外の方式を、行を削除する方式から「フェンス範囲の行番号の集合を求め、grepが返す元 ファイルの行番号と突き合わせて除外するか判定する」方式へ変更した。行の削除・再構成を 行わないため、報告される行番号は常に実ファイルの行番号と一致する。
フェンスの単純トグル判定によるfalse negative（v1のバグ） 種別・長さの異なるフェンス風の行で偶数回トグルになり、安全側フォールバックが働かないまま 本文行を無言でフェンス内と誤認する欠陥があった。実際に```text / ~~~ / ``` / 参照行 / ~~~ という5行構成で、 参照切れが完全に見逃されることを実機確認した。対応: フェンスの開始・終了判定を、 開始時のマーカー種別（`/~）と長さを記憶し、同種・同じ長さ以上の 閉じ記号でのみ閉じたとみなす方式へ変更した（CommonMarkのフェンス規則を簡略化して 踏襲）。単体テストへ再現ケースを追加した。
全角句読点の終端文字追加によるロケール依存の致命的回帰 全角句読点で連結された2つのDDRパスが1本の架空パスへ誤って結合される問題（v1でも既知の 限界としてコメント済みだったが未対処）に対し、正規表現の文字クラスへ全角文字を追加する 方法で対処しようとしたところ、この環境（LANG未設定・POSIXロケール）では POSIX ERE のブラケット式に多バイト文字を含めるとgrep・bashの[[ =~ ]]の どちらも該当行に一切マッチしなくなり、リポジトリ全体の候補数が0件に落ちる致命的な回帰を 引き起こした。実機でLC_ALL=C.UTF-8を明示すれば動くことを確認したが、 git bash実機を含む配布先のロケールを制御できない前提のため採用を見送った。対応: 正規表現自体は全角文字を含めないASCII限定のままとし、抽出後の候補文字列に対して .claude/docs/ddr/という接頭辞がASCII構造として候補中に再出現するかだけを 見て連結を検知・分割する後処理（split_concatenated_candidates_to_reply）を 追加した。区切り文字が全角句読点か否かに依存せず、ロケールにも依存しない。
性能: bash単独方式は5.2秒、grep一括方式は0.96秒 候補抽出をbash単独方式（1ファイル1回のwhile read＋[[ =~ ]]）で 実装したv1は、リポジトリ全体（151ファイル・37,411行）に対し5.2秒かかった。同じ正規表現を git ls-files -z | xargs -0 grep -nHoEで一括抽出する方式に変更したところ 0.96秒に短縮した（個別作業計画の「外部コマンドはgit ls-filesの1回のみ」という設計方針は、 避けたかったforkコスト（1回あたり約0.1秒）より、37,411行に対するbash側の正規表現 マッチングの累積コストの方が大きいという実測に反していたため見直した）。grep一括方式は 元ファイルの行番号をそのまま返すため、上記の行番号ずれの問題も同時に解消される。 外部コマンドの起動回数はgit rev-parse（リポジトリルート特定）・ git ls-files・grep（xargs経由で1〜数回）の3種類であり、 当初v1レポートに書いていた「外部コマンドはgit ls-filesの1回のみ」は誤りであった。
  • git ls-filesが返す削除済み未ステージのファイルを、件数を出さずに無言で スキップしていた（v1）。skipped_missingカウンタを追加し、標準エラーの サマリへ出すようにした。
  • 除外ディレクトリは実装当初から4つ（.claude/scripts/test/ plans/ reports/ worklog/）だったが、v1レポートは 誤って「3ディレクトリ」と書いていた。本レポートで正しい件数（4つ）に修正した。

対応を見送った指摘

  • 相対パス形式のDDR参照（.claude/docs/ddr/で始まらない、 ddr/…や../docs/ddr/…等の表記）は本スクリプトの対象外の ままとした。本リポジトリには相対形式の参照が約79件存在し（ .claude/docs/README.mdのDDR一覧、.claude/rules/*.mdの リンク等）、これらは検査されない。個別作業計画「やらないこと」で見送りと決定済みの 範囲であり、フェーズ3では対応しない。ただし「参照切れ0件」という結論の主語が 「絶対パス形式に限る」ことは、この報告と個別作業計画の両方に明記して誤解を避ける。
  • 本スクリプトをhook・CI等の実行契機へ組み込むことは行わない。全体作業計画で 「毎回自動実行する仕組みは作らない」と決定済みであり、手動実行のみの運用とする。誰も 実行しなければ再発を検知できないという指摘自体は妥当であり、フェーズ4のDDRで実行 タイミングの意思決定として記録する。
