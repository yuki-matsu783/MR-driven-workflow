# 調査結果: OTelリスナー機構の設計論点調査

対象: issue #103。個別調査計画 `plans/【調査】OTelリスナー機構の設計論点調査.md` に基づく。
実施日: 2026-08-23。実行環境: Windows / git bash（MSYS bash, perl 5.36.0）＋ WSL2 Ubuntu（perl 5.30.0）。

## 概要

7つの未決定論点と追加調査3点のすべてについて、実機検証・既存リポジトリ内資料の確認・参考実装
（`参考ディレクトリ/otel/`）の読解により結論を得た。**フェーズ3の個別作業計画（設計・実装）を
書ける状態になっている。** 唯一、フェーズ3側で追加の判断が必要な点（配置場所とマシン全体共有の
両立に伴う「機構バージョンの不整合」懸念）を「持ち越し事項」として最後にまとめる。

## 1. 配置場所の決定

**結論: `.claude/hooks/otel/` を新設し、リスナー本体・共有ライブラリをそこへ置く。**
SessionStartフックへの追記分は既存 `.claude/hooks/session-start.sh` とは別の新規フックとして
`hooks.SessionStart` 配列へ追加する。

- `.claude/rules/directory-structure.md`「配置の指針」節を確認した。`.claude/scripts/src/` は
  「AIエージェントが`.claude/skills/*`経由で能動的に実行するスクリプト」の置き場と定義されている。
  リスナー本体はClaude Codeが自動起動するSessionStartフックから起動される常駐プロセスであり、
  AIが能動的に実行するものではないため、この定義に当てはまらない。
- 同節は「複数hookスクリプトで使い回すロジックは`.claude/hooks/lib/`に切り出す」とだけ定めており、
  hook本体を機能ごとにサブディレクトリへ分けることは禁止していない。既存の`.claude/hooks/`直下は
  5ファイルの平置きだが、OTel機構はリスナー本体・対応表操作・HTTPパーサ等、複数ファイルにまたがる
  まとまった機能単位であるため、新設サブディレクトリ案を採用する。
- 既存`.claude/hooks/session-start.sh`は既に「現在の作業ブランチ情報のコンテキスト注入」という
  別の責務を持っている（本セッション冒頭の`## 現在の作業ブランチ情報`の出力元）。OTel用の処理
  （対応表への追記・リスナー起動判定）をここへ追記で混在させると責務が広がりすぎるため、
  `hooks.SessionStart`配列に新しいエントリ（`matcher: "startup|resume"`、
  `command: bash ${CLAUDE_PROJECT_DIR}/.claude/hooks/otel/session-start.sh`）を追加する形にする。
  参考実装が`matcher`を`startup|resume`に絞っている理由（`clear`/`compact`では対応表の再追記が
  無駄になる）もそのまま踏襲できる。

## 2. 状態の置き場所の範囲

**結論: 参考実装と同じく「マシン全体で1つのリスナーが複数ワークスペースを横断して振り分ける」
設計を採用する。対応表（`sessions.jsonl`相当）・リスナーのPID/ログはワークスペース外の共有位置に
置かざるを得ないが、実データ（振り分け後の`claude-otel.jsonl`）は各ワークスペースの`usage/`配下に
書き込まれる。**

- 受け入れ条件「別ワークスペースのセッションが混ざらない」「複数ワークスペースが同時に動く」は、
  この設計がまさに解決しようとしている問題そのものである。`session.id`から`cwd`を引いて振り分ける
  仕組み自体が、複数ワークスペースの混在を前提にしている。
- 対抗案（ワークスペースごとに個別リスナー・個別ポートを持つ案）を検討したが、3.のポート決定方式の
  結論（固定ポートの奪い合いを避けるにはワークスペースごとに異なるポートが必要で、かつそれを
  Claude Code起動前に決定する手段が無い）により実現できず、却下した。
- 「可能な限りリポジトリ内で完結」という受け入れ条件との整合性は、**「実データはリポジトリ内の
  `usage/`に閉じる。配送用の一時メタデータ（対応表）だけがリポジトリ外の共有位置に出る」**という
  形で妥協する。対応表自体には機微情報が乗らない設計（`session_id`と`cwd`のみ。ペイロード本体は
  含まない）にすることで、リポジトリ外に置く情報を最小化できる。
- `.claude/rules/directory-structure.md`の`usage/`節（ブランチ横断のローカル作業状態という既存の
  性質）と、今回追加する対応表の性質は一致しない（対応表はブランチではなくマシン全体で共有する
  ため）。**対応表は`usage/`配下には置かない。** 共有位置の具体名（Windows:
  `%USERPROFILE%\.claude-otel\`、WSL/Linux: `~/.claude-otel/`）は、フェーズ3の設計時に確定する。

## 3. ポート決定方式

**結論: 参考実装どおり、Windows/WSLで固定2ポート（例: 4318/4319）を踏襲する。**

- OTLPエクスポート先（`OTEL_EXPORTER_OTLP_ENDPOINT`）はClaude Code起動時に`.claude/settings.json`
  から静的に読まれる。SessionStartフックが発火する時点では既にエクスポート先が確定済みのため、
  「起動時に空きポートを見つけてワークスペース内の既知ファイルへ記録する」という動的割り当て方式は
  実現できない（フックがポートを決めても、そのポートを設定ファイルへ反映するタイミングが無い）。
- 複数リポジトリ・複数ワークスペースを同時に開く運用でも、2.の結論（1リスナーがマシン全体を
  横断して振り分ける設計）のもとでは、ポートは衝突しない（そもそも1つしか無いため）。「複数
  ワークスペースが同時に動く」という受け入れ条件は、ポートを分けることではなく、対応表による
  振り分けで満たす。
- 固定ポート案の弱点（他プロセスがそのポートを既に使っている場合に起動できない）は、5.で検証した
  多重起動防止ロジック（`/dev/tcp/...`疑似デバイスでの接続試行）と同じ仕組みで検知でき、
  「既に何かが立っている＝リスナー起動済みとみなしてスキップ」という参考実装のベストエフォート
  方針をそのまま踏襲できる。

## 4. 設定の適用範囲（プロジェクトスコープ vs ユーザーホーム）

**結論: `env`・`hooks.SessionStart`ともに、プロジェクトスコープの`.claude/settings.json`
（このリポジトリ内、既にGit管理下）へ追記する形で完結できる。** 実機確認した現在の
`.claude/settings.json`は`hooks`セクションに既存のSessionStart/PreToolUse/PostToolUseフックが
定義されており、`env`セクションは現在`null`（未設定）である。同じ`hooks.SessionStart`配列へ
新規エントリを追加し、`env`セクションを新設するだけでよく、構文上の制約は無い。

- リスナー本体・共有ライブラリのパスは、hookの`args`に`${CLAUDE_PROJECT_DIR}`変数を使えば
  （既存の4つのhookエントリと同じ書き方で）絶対パスに解決される。
- **ただし持ち越し事項がある**: このリポジトリは複数プロジェクトへ配布されるテンプレートである。
  対応表・リスナーは「マシン全体で1つ」（2.の結論）である一方、リスナー本体のスクリプトは
  各リポジトリの`.claude/hooks/otel/`に置かれる。複数のリポジトリ（それぞれ別バージョンの
  OTel機構を持つ）を同時に開いた場合、**実際に起動されるリスナーは「最初にセッションを開始した
  リポジトリのフックが起動したもの」に固定される**。バージョン違いのリスナーが後から開いた別
  リポジトリの対応表フォーマットと食い違う可能性がある。この懸念はフェーズ3の個別作業計画で
  「対応表フォーマットを機構のバージョン間で後方互換に保つ」方針として引き継ぐ。

## 5. perlでのHTTPサーバー実装方式の実現可能性

**結論: 実現可能。`IO::Socket::INET`でリッスンし、リクエスト行・ヘッダ・`Content-Length`分の
bodyを読む自前HTTP/1.1最小パーサを実装し、実機で疎通確認した。**

検証コード（scratchpad配下、コミット対象外）で、ポート14319で待ち受けるリスナーを起動し、
`curl`で3種類のリクエスト（正常なOTLP JSON、空JSON、不正なJSON）をPOSTした。

| リクエスト | Content-Length | JSONパース結果 | HTTPステータス |
|---|---|---|---|
| `session.id`属性を含むOTLP JSON | 123 | ok | 200 |
| 空JSON `{}` | 2 | ok | 200 |
| 不正な文字列 `not-json` | 8 | ng（`eval`で捕捉） | 200 |

いずれも200 OKを正しく返し、不正なJSONでもリスナーがクラッシュしないことを確認した
（`eval { decode_json($body) }`でエラーを捕捉し、パース失敗時も処理を継続する設計が機能する）。
排他制御は、Claude Codeの1セッションが短時間に大量のOTLPリクエストを送る想定が薄いことと、
perlの`threads`モジュールは重い（プロセス全体をコピーする実装）ことを踏まえ、
**シングルスレッドの逐次`accept`ループで十分**と判断する（参考実装のPython版は
`ThreadingHTTPServer`だが、これはPythonのGILを前提にした実装であり、perlでそのまま真似る
必要は無い）。

## 6. WSL側の実機検証可否

**結論: 実機検証可能。** 本セッションの実行環境（Windows）でWSL2（Ubuntu, running）が利用可能で
あることを`wsl.exe -l -v`で確認した。WSL側で以下を確認した。

| モジュール/コマンド | Windows(git bash) | WSL(Ubuntu) |
|---|---|---|
| perlバージョン | 5.36.0 (MSYS) | 5.30.0 (linux-gnu) |
| `IO::Socket::INET` | 利用可 | 利用可 |
| `JSON::PP` | 利用可 | 利用可 |
| `Test::More` | 利用可 | 利用可 |
| `POSIX` | 利用可 | 利用可 |
| `setsid` | **無し**（`command -v setsid`が失敗） | 利用可 |
| `nohup` | 利用可 | 利用可 |
| `/dev/tcp/...`疑似デバイス | 利用可（bash組み込み） | 利用可（未検証だが同じbash実装のため同様と推定） |

**重要な発見**: 参考実装の`session-start.sh`が使うデタッチ起動 `setsid nohup … & disown` は、
**Windows側のgit bash（MSYS）には`setsid`が存在しない**ため、そのままは移植できない。
WSL側は`setsid`が使えるため参考実装どおりでよいが、Windows側は`nohup … & disown`のみ
（`setsid`を省く）か、別の手段を使う必要がある。この差分は追加調査3（ベストエフォート方針）で
扱う。

## 7. perlスクリプトの単体テスト方法の確立

**結論: `Test::More`が標準添付でそのまま使える。** ただし出力形式が既存bash規約
（`passed=N failures=N`、失敗時終了コード1）とは異なるTAP形式（`ok N - <説明>`、`1..N`、
失敗時は自動的に非0終了）である。

`session.id`全走査ロジック（`find_session_ids`相当）を`SessionIdFinder.pm`として純粋関数に
切り出し、`Test::More`の`is_deeply`でテストを書いて実行した。

```
ok 1 - ネストの異なる2箇所からsession.idを収集できる
ok 2 - session.idが無ければ空
1..2
```

正しく動作した。フェーズ3では、**bash版と同じ`passed=N failures=N`形式に合わせるか、
`Test::More`のTAP形式のまま採用するか**を選ぶ必要がある。TAP形式は`prove`コマンドや多くのCIが
標準対応する一般的な形式であるため、無理にbash版へ合わせず**TAP形式のまま採用し、
`.claude/rules/shell-script-style.md`（またはperl版の対応する規約ファイル）に
「perlの単体テストは`Test::More`を使いTAP形式で出力する」という一文を追記する案**を推奨する
（bash版の`assert_eq`をperlで再実装するのは車輪の再発明であり、`Test::More`は標準添付のため
追加インストールが不要という利点を活かせないため）。最終判断はフェーズ3の個別作業計画で行う。

## 追加調査1: 出力ファイルのローテーション方針・エクスポート間隔の既定値

参考実装の`README.md`は「既知の制限」として`claude-otel.jsonl`が無限に伸びることを明記している。

- **ローテーション方針の候補**: (a) 行数上限での切り詰め（参考実装の`sessions.jsonl`が採用する
  「500行超で直近300行へ切り詰め」と同じ方式。ただし出力ファイルは対応表と異なり全量を保持する
  意味があるため、切り詰めは不適切）、(b) 日次ローテーション（`claude-otel-YYYYMMDD.jsonl`のように
  日付をファイル名に含め、リスナー起動時・書き込み時に日付が変わっていたらファイルを切り替える）、
  (c) ローテーションせず利用者に手動削除を委ねる（参考実装はこちら）。
  **(b) 日次ローテーションを推奨案とする**（対応工数レポート等、後続の分析用途で「日付ごとに
  ファイルが分かれている」方が扱いやすいため）。最終判断はフェーズ3で行う。
- `OTEL_METRIC_EXPORT_INTERVAL`の既定値はOpenTelemetry SDK共通で60000ms（60秒）。参考実装は
  10000ms（10秒）を明示的に指定している。ローカルファイルへの追記のみで外部送信コストが無いため、
  短い間隔（10秒程度）を採用しても問題は無いと考えられる。

## 追加調査2: 機微情報の扱いと`.gitignore`対象範囲

OTLPペイロードに含まれうる機微情報を洗い出した。

- `user.email`相当のリソース属性（Claude Codeのアカウントに紐づくメールアドレス）
- アカウントUUID
- `session.id`
- `OTEL_LOG_USER_PROMPTS=1`を明示的に有効化した場合のプロンプト本文

出力先を`usage/`配下（例: `usage/claude-otel.jsonl`、`usage/unrouted.jsonl`）に置く前提で、
実際に空ファイルを作成し`git check-ignore -v`で確認した。

```
.gitignore:20:/usage/	usage/claude-otel.jsonl
.gitignore:20:/usage/	usage/unrouted.jsonl
```

既存の`/usage/`パターン（対応工数レポート機能が既に使っている）でそのまま除外されることを
確認した。**`.gitignore`への追記は不要。** 一方、2.の結論で「マシン全体で共有する対応表」は
このリポジトリの外（ユーザーホーム相当）に置くため、そもそも`.gitignore`の対象外である。
ただしテンプレートとして配布する以上、`DEVELOPERS.md`等の導入手順に「共有位置に置く対応表
（`session_id`と`cwd`のみで、ペイロード本体は含まないが、`cwd`はワークスペースの絶対パスを
含む）にも一定の注意を要する」旨を明記する必要がある。

## 追加調査3: ベストエフォート方針の実現方法

- **リスナー起動の非同期デタッチ方式**: 6.で判明したとおり、Windows側（git bash/MSYS）には
  `setsid`が無い。**Windows側は`nohup <listener> >listener.log 2>&1 </dev/null & disown`
  （`setsid`を省く）、WSL側は参考実装どおり`setsid nohup … & disown`とする。** 環境ごとに
  起動コマンドを分岐させる設計が必要（両者とも`.claude/hooks/otel/`配下のスクリプトから
  呼ぶが、実行環境（Windows/WSL）の判定はフェーズ3で確定する）。
- **多重起動防止**: `/dev/tcp/127.0.0.1/${PORT}`への接続試行はgit bash（MSYS）でも動作することを
  実機確認した（存在しないポートへの接続で`Connection refused`が返り、構文自体は正しく解釈
  されている）。外部コマンド不要のこの方式を踏襲できる。
- **フックのタイムアウト設計**: 既存hook（`.claude/settings.json`）のtimeout値は
  `SessionStart`（既存の`session-start.sh`）が30秒、`PreToolUse`が10秒、`PostToolUse`の2本が
  20秒。参考実装のSessionStartフックは10秒を指定している。OTel用フックは「対応表への追記＋
  リスナー起動判定＋デタッチ起動」のみで実処理は一瞬のため、**参考実装と同じ10秒**を踏襲する
  想定で問題ない。
- **受け口（リスナー）の失敗がセッションを妨げないこと**: リスナー自体はSessionStartフックの
  外側で非同期起動されるプロセスであり、フックの応答（成功/失敗）とは独立して動く。フック側は
  「対応表への追記」「起動判定」「デタッチ起動の実行」のいずれが失敗してもフック自体の終了コードを
  0で返す設計（参考実装の`session-start.sh`が`set -u`のみで`set -e`を使わず、各コマンドを
  `2>/dev/null`や`|| true`相当で握りつぶしている）を踏襲する。

## フェーズ3への持ち越し事項

1. **機構バージョンの不整合懸念**（4.の結論内）: 複数リポジトリ（それぞれ別バージョンのOTel機構）
   を同時に開いた場合、実際に起動されるリスナーが「最初に開いたリポジトリのもの」に固定される。
   対応表フォーマットの後方互換性維持を設計方針として明記する必要がある。
2. **ローテーション方式の最終決定**（追加調査1）: 日次ローテーション案を推奨するが、フェーズ3の
   個別作業計画で確定する。
3. **単体テストの出力形式**（7.）: `Test::More`のTAP形式のまま採用するか、bash版の
   `passed=N failures=N`に合わせるかをフェーズ3で確定する。
4. **共有位置（対応表・リスナーログの置き場所）の具体パス**（2.）: Windows/WSLそれぞれの
   具体的なディレクトリ名をフェーズ3の設計で確定する。
