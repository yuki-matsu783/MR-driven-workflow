### Q1. 現行ルールの射程と、一般化後に既存記述と矛盾しないか

対象は `.claude/rules/docs-workflow.md` の104〜114行目。1文ずつ切り分けると次のとおり。

| 位置 | 文 | 「見出しの挿入」への依存 |
|---|---|---|
| 104-105 | 「既存ドキュメントへ**新しい見出しを差し込むとき**は、**挿入位置の直前の節**が『その節全体にかかる地の文』で終わっていないかを必ず確認する」 | **二重に依存**。(i) 発動条件が「見出しを差し込むとき」、(ii) 見る範囲が「挿入位置の直前」 |
| 105-106 | 「終わっている場合、**間に別の節を挟む**と、その地の文が**新しい節**にかかっているように読めてしまう」 | 依存する（壊れ方の説明が「節を挟む」に限定されている） |
| 106-107 | 「**挿入位置**を節の末尾（次の見出しの直前）へ回すなど、**係り先が変わらない位置を選ぶ**」 | 前半は依存、**後半は一般**。「係り先が変わらない位置を選ぶ」が一般化の核になる |
| 109-111 | 実例1: `issue-mr-flow/SKILL.md` の `計画の2階層構造` の位置 | **依存しない**（見出し挿入の事例だが、一般ルールの1事例としてそのまま成立する） |
| 112-114 | 実例2: 「同じ節名でもファイルごとに結論が変わる」 | **依存しない**（ファイルごとに確認せよ、という一般則） |

**結論**: 書き換えが要るのは**本文3文**だけで、**実例2件はそのまま残せる**。実例2は一般化後の
文言のもとでも意味が変わらないどころか、「操作の種類ではなく個々の文脈を見よ」という一般化の
方向と整合する。受け入れ条件「拡張後の記述が issue #64 由来の既存の記述と矛盾していない」は、
本文3文の書き換えだけで満たせる。

**この節を書き換えるとき自身が同じ罠を踏みうる。** 該当段落は見出しを持たない段落の連なりの
中にあり、直後には `HANDOFF.md` の進捗記号を扱う無関係な段落が続く。**新しい見出しを立てると、
その段落が新見出しの配下に入る**（PR #139 とまったく同じ形）。フェーズ3では、見出しを立てない
か、立てるなら直後の段落にも見出しを与える。

### Q2. 同趣旨のルールが他ファイルに重複していないか

```bash

grep -rn '地の文' --include='*.md' . | grep -v '^\./\(plans\|reports\|worklog\|\.gemini\)/' | wc -l
```

「地の文」の43件は主題がばらばらなので、**「見出し」と「地の文」を同一行に持つ行**へ絞って
1件ずつ主題を判定した（7件ヒット）。

| ファイル:行 | 主題 | 今回のルールと同趣旨か |
|---|---|---|
| `.claude/rules/docs-workflow.md:104,106` | **本件の規約そのもの** | **正（規約側）** |
| `REVIEW-POINTS.md:47` | 「新しい見出しの挿入位置が、直前の節の地の文の係り先を壊していないか」 | **同趣旨（観点表側）** |
| `.claude/docs/spec/issue-mr-workflow.md:2547` | issue #64 の作業記録（当初の挿入位置を変えた経緯） | 違う（**point-in-time記録**。書き換えない） |

#### 暫定案5項目の逐条判定

上位計画「フェーズ3〈作業〉」の5項目を**原文のまま**引用し、項目ごとに何を担うか・4件を拾えるかを
判定した（項目を1文へ融合すると、どの項目の穴なのかが分からなくなるため融合しない）。

| 項目（原文） | 何を担うか | 4件への効き方 |
|---|---|---|
| 1. 適用対象を「見出しの差し込み」から**構造変更全般**へ広げる。ただし**操作の種類を列挙する形にしない** | **発動条件**（いつ確認するか） | #64・#109・PR #139 は入る。**#155 は入るか読み手に委ねられる**（下記） |
| 2. 確認の観点を「**残置した地の文・箇条書きが、変更前と同じものに係っているか**」という形で書く | **観点**（何を見るか） | 4件すべてに当てはまる。ただし**いつ見るかは定めない**ので、単独では発動条件にならない |
| 3. 「**前後どちらの残置テキストも見る**」ことを明示する | **探索範囲** | PR #139（後ろが壊れた唯一の件）を拾うのに必須 |
| 4. issue #64 の既存の実例は**消さない** | 受け入れ条件の遵守 | 検出可否には効かない |
| 5. 「分割前は正しかった行が、分割によって誤りになる」形を明示した実例を足す | 気づきやすさ | #109 の形を具体で支える |

**穴は項目1にある。** 発動条件を担うのは項目1だけであり、そこに置かれた「構造変更全般」は
**それ自体が操作の分類**である。issue #155 のコメントが明示しているとおり、この事例では
**見出しを1つも動かしておらず、節を分割しておらず、箇条書きの階層も変えていない**（同じ深さの
項を1つ増やしただけ）。「項を1つ足す」を構造変更と読むかどうかは読み手に委ねられる。
issue #142 が「操作の種類を列挙しない」と求めた理由がそのまま効いており、**上位カテゴリへ
言い換えただけでは、列挙をやめたことにならない**。

項目2の観点は #155 にも当てはまるが、**観点は「何を見るか」であって「いつ見るか」ではない**ため、
項目1が発動しなければ読まれない。したがって「項目2があるから #155 も拾える」とは言えない。

**フェーズ3への含意**: 発動条件（項目1）を**操作の側**（何をしたか）ではなく**リスクの側**
（残置テキストの周囲が変わったか）で書き直す。「既存の記述を残したまま、その**周囲**を編集した
とき」のように、操作の名前を出さずに条件を書ければ、4件すべてが自然に入る。

**載せる実例**: 既存2件（#64 由来）を残したうえで、**#109 と PR #139 の2件を足す**（合計4件）。
この2件は壊れた位置が前後で逆であり、並べると「前後どちらも見る」という観点が具体で支えられる。
**#155 は5件目の実例としては足さず**、発動条件の書き方の根拠として1行で触れるに留める
（実例を5件並べると、ルール本文より事例集のほうが長くなり、読み手が要点を取り出せなくなる）。

### Q4. 係り先・見出し挿入のルールを扱ったDDRがあるか

個別調査計画が定めた3語すべてで探索した。

```bash
bash .claude/scripts/src/search-frontmatter.sh --type ddr --text '見出し'   # matched=0
bash .claude/scripts/src/search-frontmatter.sh --type ddr --text '係り先'   # matched=0
bash .claude/scripts/src/search-frontmatter.sh --type ddr --text '構造'     # matched=5
grep -rln '係り先\|地の文' .claude/docs/ddr/                                 # 6件
```

`--text '構造'` の5件と、本文検索の6件を、1件ずつ `description` を読んで判定した。

| DDR | 主題 | 追記先になりうるか |
|---|---|---|
| `i0009-01` | planツール利用を全体作業計画に限定し個別計画をファイル分離する | ならない |
| `i0014-01` | GitHub/GitLab情報取得は `gh`/`glab` CLIを使う | ならない |
| `i0020-01` | HANDOFF進捗更新はMarkdownテーブル直接書き換えで行う | ならない |
| `i0064-01` | 大きすぎるissueの分割判定（並列列挙構造がトリガー） | ならない（「構造」は列挙構造の意） |
| `i0110-01` | 個別計画のタスク種別を6種から8種へ拡張する | ならない |
| `i0053-01` | hookのコマンド文字列検知をコマンド位置判定へ移した経緯 | ならない（「地の文」は誤検知の文脈） |
| `i0023-01` | push断面の全文コピーをやめ行番号インデックスにした経緯 | ならない |
| `i0086-01` | マージ前の関連issue通知の位置と人間承認 | ならない |
| `i0127-01` | 差分アンカーの土台をプロバイダごとに分けた経緯 | ならない |
| `i0135-01` | DDR一覧を生成物にした経緯（「見出し」はマーカー区間の話） | ならない |
| `i0067-01` | ベースブランチ追従確認を専用スクリプトにした経緯 | ならない |

**`i0064-01` も追記先にならない。** 識別子は issue #64 由来だが、主題は「大きすぎるissueの分割
判定」であり係り先ルールとは無関係である。**識別子の接頭辞だけで判定すると「issue #64 由来の
DDRがある→追記で足りる」という誤った結論になる**ため、内容で判定した。

**結論: 追記先になりうる既存DDRは0件。** したがって「既存への追記で足りる」という選択肢は成立せず、
残るのは (i) 新規DDRを作る、(ii) DDRを作らず規約への記述だけで足りると判断する、の2択である。
どちらを採るかは**却下案を伴う意思決定かどうか**で決まる。今回は「操作の列挙で書く案」を明確に
却下しており（issue #155 の3例目が列挙を外れたという実証がある）、**却下案を伴う**。
**フェーズ4で新規DDRを作る**方針を推す。

**探索の範囲**: frontmatter は計画が定めた3語すべてで、本文は「係り先」「地の文」で探した。
**本文に「見出し」を含むDDRは13件あり、そのうち内容を確認したのは `i0135-01` の1件だけ**である
（「見出し」は目次・節構造の説明で頻出する構造語のため、本文検索の絞り込みには使っていない）。
残る12件を確認していないことは下記「確かめられなかったこと」に含める。

### Q5. ルールを実際に守らせる場所はどこか

`collect-review-points.sh` の実装を読むと、祖先方向へ遡って集めるのは
`REVIEW-POINTS.md` と `REVIEW-POINTS.local.md` の2つだけである（`for base in "REVIEW-POINTS.md"
"REVIEW-POINTS.local.md"`）。

実測でも、`.claude/rules/docs-workflow.md` を対象に収集した結果に含まれたのはルート
`REVIEW-POINTS.md` と `.claude/REVIEW-POINTS.md` の中身だけで、**`.claude/rules/` 配下の規約は
1行も含まれない**。

加えて `adversarial-review` スキルは、サブエージェントへ渡すものを「レビュー対象・マージ済みの
観点表・フェーズ番号」の3つに限り、**サブエージェント側から観点表を探しに行かせない**と定めて
いる。したがって、

> **`.claude/rules/` にだけ書いたルールは、敵対的レビューには渡らない。**

#### 「4件とも敵対的レビューが検出した」は成り立たない

初版のレポートはここで「4件とも自己確認では見つからず敵対的レビューが検出した」を前提に
していたが、**これは事実ではない**。敵対的レビュー機構は **issue #77 で新設**されたもので、
`.claude/docs/spec/adversarial-review.md`「背景・目的」に「本issue以前、このリポジトリには
レビューを担うスキルもサブエージェントも存在しなかった」と明記されている。**#64 は #77 より前**
なので、#64 を敵対的レビューが検出することは原理的に不可能である（上記 Q3 の出典表のとおり、
#64 は着手時の自己確認で気づいた形として読める）。

**正しくは「4件のうち3件（#109・PR #139・#155）を敵対的レビューが検出した」である。**

#### 前提を正しても結論 (b) は保つ

前提が「4件とも」から「3件」へ弱まっても、Q5 の結論は変わらない。理由は2つ。

1. **敵対的レビュー機構が存在して以降に起きた3件は、3件とも敵対的レビューが検出している。**
   機構が無かった時代の1件を除けば、実績は3/3 である。
2. **#64 が自己確認で見つかったことは、むしろ現行ルールの限界を示す。** #64 は現行ルールが
   直接扱う形（見出しの挿入・直前が壊れる）であり、**ルールの射程内だったから気づけた**と読める。
   射程外の3件は自己確認をすり抜けており、射程を広げるだけでは足りず、**広げた射程が実際に
   検出してきた経路（観点表）へ届く必要がある**という結論を補強する。

**結論**: (b) が必要。`.claude/rules/docs-workflow.md`（規約＝書くときの手引き）を正とし、
ルート `REVIEW-POINTS.md`「ドキュメントの構造」の観点も一般化後の文言へ揃える。
(c)（サブエージェント定義の改修）は不要である——観点表は既に確実に渡る経路であり、
`adversarial-review` スキルが「観点の中身をSKILL.mdへ書かず `REVIEW-POINTS.md` へ書く」と
明示しているため、(b) がその設計どおりの反映先になる。

### 全体作業計画の検証コマンドの空振り確認

**初版の検証コマンドは空振りしていた。** `grep -F '計画の2階層構造'` の1語しか見ておらず、
(a) 実例1は3行にまたがるのにトークンを含むのは1行目だけ、(b) `計画の2階層構造` は `.claude/`
配下の**27行**に現れるため無関係な編集でも `1` が出る、(c) 対象パスが `.claude/` だけで、
本レポートが確定した書き換え先のもう一方である**ルート `REVIEW-POINTS.md` を見ない**、
という3つの穴があった。

改稿したコマンドは、実例2件の**全6行それぞれに固有の語**（いずれも `.claude/` ＋ルート
`REVIEW-POINTS.md` の中で**出現1行**であることを実測で確認）を使い、対象パスを2つへ広げている。

```bash
base=4be448af553c82c0fcf731705b0cd1d08bf23f29   # 分岐点SHAを直接渡す（origin/main は動く）
git diff "$base" -- .claude/ REVIEW-POINTS.md | grep '^-' | grep -cF \
  -e '末尾に節全体へかかる地の文' \
  -e 'での機械的列挙・flow-id 1-4の判定' \
  -e 'の直前へ新節を入れた' \
  -e '同じ節名でもファイルごとに結論が変わる' \
  -e '直後に地の文が無く' \
  -e '入れられたから安全' || true
```

合格条件: **`0` を出すこと**。

| ツリーの状態 | 出力 |
|---|---|
| 変更前（現状） | `0` |
| 109行目だけ削除（実例1の1行目） | `1` |
| 110行目だけ削除（実例1の2行目） | `1` |
| 111行目だけ削除（実例1の3行目） | `1` |
| 112行目だけ削除（実例2の1行目） | `1` |
| 113行目だけ削除（実例2の2行目） | `1` |
| 114行目だけ削除（実例2の3行目） | `1` |
| 復元後 | `0` |

**空振りしない。** 6行のどれを消しても検出できる。確認後、ファイルはバックアップから復元し、
`git status` が変更なしであることを確かめた。

## 確かめられなかったこと

- **Q3 の判定は机上である。** 暫定案の実文がまだ無いため、上位計画の5項目を逐条で当てた。
  フェーズ3で実際に書いた文言に対しては、**同じ4件をもう一度当て直す**必要がある（とくに #155）。
- **issue #64 の事例を「誰が見つけたか」は確定できていない。** specの記録から「着手時の自己確認」と
  読めるが、明示の記述は無い（#77 より前なので敵対的レビューでないことだけは確定している）。
- **Q4 で、本文に「見出し」を含むDDR13件のうち12件は内容を確認していない。** frontmatter 検索は
  3語すべてで行ったが、本文検索の絞り込みには「見出し」を使っていない（構造語のため）。
- **`.claude/rules/` が敵対的レビュー以外の経路（人間のレビュー、組み込みの `/code-review`）で
  どれだけ読まれるかは測っていない。** Q5 の結論は「敵対的レビューには渡らない」という一点で
  あり、規約が無価値だという意味ではない。
- **過去のドキュメントに同型の破損が残っているかは調べていない**（全体作業計画のスコープ外）。
- Q2 の絞り込みは「『見出し』と『地の文』を同一行に持つ」という条件で行った。**2行にまたがって
  同じことを述べている箇所は拾えていない**。ただし「係り先」での検索が返す4件のうち、
  タスク自身の自己参照2件を除いた実質2件がいずれも既知の箇所であるため、取りこぼしがあっても
  「係り先」という語を使わずに同じ規約を述べた記述に限られる。

## 設計への反映（フェーズ3で決めること）

1. **発動条件を操作の分類で書かない。** 暫定案の項目1「構造変更全般」への言い換えでは #155 を
   取りこぼす。「既存の記述を残したまま、その周囲を編集したとき」のように、**残置テキストの側**から
   条件を書く。
2. **「前後どちらも見る」を明示する。** PR #139 は挿入位置の後ろが壊れており、「直前を見よ」では
   射程内の操作ですら検出できなかった。
3. **実例は既存2件＋#109・PR #139 の計4件**とする（#155 は5件目として足さず、発動条件の書き方の
   根拠として1行で触れる）。#109 は「**分割前は正しかった行が、分割によって誤りになる**」形を
   明示する。
4. **書き換え先は2箇所。** `.claude/rules/docs-workflow.md`（正）と ルート `REVIEW-POINTS.md`。
5. **この段落を書き換えるとき、自分が PR #139 と同じ罠を踏まないこと。** 直後の `HANDOFF.md` の
   進捗記号を扱う段落は無関係であり、新しい見出しを立てるならその段落にも見出しが要る。
6. **DDRはフェーズ4で新規に作る。** 追記先になりうる既存DDRは0件で、却下案（操作の列挙で書く案）を
   伴う意思決定であるため。
7. **観点表側には「何を疑うか」が単独で伝わるだけの中身を残す。** Q2 は「観点表は規約を指す短い
   観点に留める」としたが、Q5 のとおり**規約は敵対的レビューへ渡らない**。ポインタだけを置くと、
   実際にレビューする側には「疑うべきこと」が届かない（対象ファイルを Read できるので辿れる、
   という反論は成り立つが、**何を疑うかが観点表に無いと辿る動機が生まれない**）。
   最低限、**(i) 発動条件（残置テキストの周囲を編集したとき）と (ii) 前後どちらも見ること**の
   2点は観点表側にも書く。
8. **検証コマンドの対象パスは `.claude/` と ルート `REVIEW-POINTS.md` の両方**にする。上記4で
   書き換え先を2箇所と決めた以上、片方だけを見る検証は巻き添えを検出できない。

## 想定と異なった点

- **計画では「正を1箇所に決めるか」を問うていたが、答えは「2箇所とも要る」だった。** Q5 で
  `.claude/rules/` が敵対的レビューへ渡らないと分かったため。重複を潰す方向へ進んでいたら、
  3件を検出してきた経路からルールを消すところだった。
- **Q4 は「issue #64 由来のDDRが1件ある」で終わりかけた。** 敵対的レビューの指摘で内容判定へ
  切り替えた結果、実際には追記先が0件だと分かった。**識別子は「そのissueで作られた」ことしか
  示さない。**
- **初版のレポート自身が、このissueが扱っている失敗を3つ犯していた。** (i) 「4件とも敵対的
  レビューが検出」という**確かめていない一般化**、(ii) 除外後の件数を**コマンドの出力欄**へ書いた
  ための再現不能、(iii) **1語・1ファイル**しか見ない検証。いずれも敵対的レビュー（2回目）が
  検出した。
