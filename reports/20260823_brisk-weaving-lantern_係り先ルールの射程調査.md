## 実施した内容と結果

### Q1. 現行ルールの射程と、一般化後に既存記述と矛盾しないか

対象は `.claude/rules/docs-workflow.md` の104〜114行目。1文ずつ切り分けると次のとおり。

| 位置 | 文 | 「見出しの挿入」への依存 |
|---|---|---|
| 104-105 | 「既存ドキュメントへ**新しい見出しを差し込むとき**は、**挿入位置の直前の節**が『その節全体にかかる地の文』で終わっていないかを必ず確認する」 | **二重に依存**。(i) 発動条件が「見出しを差し込むとき」、(ii) 見る範囲が「挿入位置の直前」 |
| 105-106 | 「終わっている場合、**間に別の節を挟む**と、その地の文が**新しい節**にかかっているように読めてしまう」 | 依存する（壊れ方の説明が「節を挟む」に限定されている） |
| 106-107 | 「**挿入位置**を節の末尾（次の見出しの直前）へ回すなど、**係り先が変わらない位置を選ぶ**」 | 前半は依存、**後半は一般**。「係り先が変わらない位置を選ぶ」が一般化の核になる |
| 109-111 | 実例1: `issue-mr-flow/SKILL.md` の `### 計画の2階層構造` の位置 | **依存しない**（見出し挿入の事例だが、一般ルールの1事例としてそのまま成立する） |
| 112-114 | 実例2: 「同じ節名でもファイルごとに結論が変わる」 | **依存しない**（ファイルごとに確認せよ、という一般則） |

**結論**: 書き換えが要るのは**本文3文**だけで、**実例2件はそのまま残せる**。実例2は一般化後の
文言のもとでも意味が変わらないどころか、「操作の種類ではなく個々の文脈を見よ」という一般化の
方向と整合する。受け入れ条件「拡張後の記述が issue #64 由来の既存の記述と矛盾していない」は、
本文3文の書き換えだけで満たせる。

**この節を書き換えるとき自身が同じ罠を踏みうる。** 該当段落は見出しを持たない段落の連なりの
中にあり、直後には `HANDOFF.md` の進捗記号を扱う無関係な段落が続く。**新しい見出しを立てると、
その段落が新見出しの配下に入る**（PR #139 とまったく同じ形）。フェーズ3では、見出しを立てない
か、立てるなら直後の段落にも見出しを与える。

### Q2. 同趣旨のルールが他ファイルに重複していないか

```

grep -rn '地の文' --include='*.md' . | grep -v '^\./\(plans\|reports\|worklog\|\.gemini\)/' | wc -l
```

「地の文」の43件は主題がばらばらなので、**「見出し」と「地の文」を同一行に持つ行**へ絞って

| ファイル:行 | 主題 | 今回のルールと同趣旨か |
|---|---|---|
| `.claude/rules/docs-workflow.md:104,106` | **本件の規約そのもの** | **正（規約側）** |
| `REVIEW-POINTS.md:47` | 「新しい見出しの挿入位置が、直前の節の地の文の係り先を壊していないか」 | **同趣旨（観点表側）** |
| `.claude/docs/spec/issue-mr-workflow.md:2547` | issue #64 の作業記録（当初の挿入位置を変えた経緯） | 違う（**point-in-time記録**。書き換えない） |
| `.claude/docs/spec/issue-mr-workflow.md:3568` | flow-id の裸の番号の見つけ方 | 違う |
| `.claude/docs/spec/generate-ddr-list.md:88` | DDR一覧のマーカー区間を推測しない話 | 違う |
| `.claude/docs/ddr/i0135-01-…:54` | 同上（specと対の記述） | 違う |

**結論**: 同趣旨の記述は**2箇所**。ただし Q5 の結果から、この2箇所は**役割が違うため両方必要**で

**規約側を正とし、観点表側は規約を指す短い観点に留める**のが妥当。

`.gemini/rules/docs-workflow.md` にも同じ文があるが、これは `sync-gemini-assets.sh` が生成する
写しであり重複ではない（直接編集しない。flow-id 5-3 で再生成する）。

### Q3. ルール本文へ載せる実例は何件か

4件それぞれについて、上位計画「フェーズ3〈作業〉」の5項目（**暫定案**）だけを読んで検出できるかを
机上で突き合わせた。暫定案の核になる文は次の形と想定した。

> 既存の文書の**構造へ手を入れた**ら、残置した地の文・箇条書きが、変更前と同じものに係っているかを、
> 変更箇所の**前後どちらについても**確認する。

| # | 何を変えたか | 壊れた位置（新しく書いた部分から見て） | 現行ルールで拾えるか | **暫定案**で検出できるか |
|---|---|---|---|---|
| issue #64 | 新しい見出しを差し込んだ | **前**（挿入位置の直前の節の末尾） | 拾える | **できる** |
| issue #109 | 既存の節を (1)(2) に分割した | **前**（新設した (2) の手前に残した、(1) 直下の結論行） | 拾えない | **できる** |
| PR #139（issue #135） | 新しい見出しを差し込んだ | **後ろ**（新設した見出しの配下に入った、見出しを持たない段落群） | 拾えない | **できる**（「前後どちら」が効く） |
| issue #155 | 既存の箇条書きへ項を1つ足した | **前**（直前の項の末尾にあった補足） | 拾えない | **できない可能性が高い** |

**#155 が暫定案の穴である。** issue #155 のコメントが明示しているとおり、この事例では
**見出しを1つも動かしておらず、節を分割しておらず、箇条書きの階層も変えていない**（同じ深さの項を
1つ増やしただけ）。「**構造へ手を入れた**」という発動条件は、それ自体が操作の分類であり、
「項を1つ足す」を構造変更と読むかどうかが読み手に委ねられる。issue #142 が「操作の種類を列挙しない」
と求めた理由がそのまま効いており、**「構造変更」という上位カテゴリへ言い換えただけでは、
列挙をやめたことにならない**。

**フェーズ3への含意**: 発動条件を**操作の側**（何をしたか）ではなく**リスクの側**（残置テキストの
周囲が変わったか）で書く。「既存の記述を残したまま、その**周囲**を編集したとき」のように、
操作の名前を出さずに条件を書ければ、4件すべてが自然に入る。

**載せる実例**: 既存2件（#64 由来）を残したうえで、**#109 と PR #139 の2件を足す**。この2件は
壊れた位置が前後で逆であり、並べると「前後どちらも見る」という観点が具体で支えられる。#155 は
本文の実例としては足さず、**発動条件の書き方の根拠**として1行で触れるに留める（実例を4件並べると、
ルール本文より事例集のほうが長くなり、読み手が要点を取り出せなくなる）。

### Q4. 係り先・見出し挿入のルールを扱ったDDRがあるか

```
bash .claude/scripts/src/search-frontmatter.sh --type ddr --text '見出し'
# → matched=0 total=158 indexes=25
grep -rln '係り先\|地の文' .claude/docs/ddr/
```

本文検索は6件ヒットしたので、1件ずつ `description` を読んで主題を判定した。

| DDR | 主題 | 追記先になりうるか |
|---|---|---|
| `i0053-01` | hookのコマンド文字列検知をコマンド位置判定へ移した経緯 | ならない（「地の文」は誤検知の文脈） |
| `i0023-01` | push断面の全文コピーをやめ行番号インデックスにした経緯 | ならない |
| `i0086-01` | マージ前の関連issue通知の位置と人間承認 | ならない |
| `i0127-01` | 差分アンカーの土台をプロバイダごとに分けた経緯 | ならない |
| `i0135-01` | DDR一覧を生成物にした経緯（「見出し」はマーカー区間の話） | ならない |
| `i0067-01` | ベースブランチ追従確認を専用スクリプトにした経緯 | ならない |

**`i0064-01` も追記先にならない。** 実在はするが（`i0064-01-issueの分割は並列列挙構造を主トリガーに
AIが提案し人間が決定する.md`）、主題は「大きすぎるissueの分割判定」であり、係り先ルールとは無関係で
ある。**識別子の接頭辞だけで判定すると「issue #64 由来のDDRがある→追記で足りる」という誤った結論に
なる**ため、内容で判定した。

**結論: 追記先になりうる既存DDRは0件。** したがって「既存への追記で足りる」という選択肢は成立せず、
残るのは (i) 新規DDRを作る、(ii) DDRを作らず規約への記述だけで足りると判断する、の2択である。
どちらを採るかは**却下案を伴う意思決定かどうか**で決まる。今回は「操作の列挙で書く案」を明確に
却下しており（issue #155 の3例目が列挙を外れたという実証がある）、**却下案を伴う**。
**フェーズ4で新規DDRを作る**方針を推す。

### Q5. ルールを実際に守らせる場所はどこか

`collect-review-points.sh` の実装を読むと、祖先方向へ遡って集めるのは
`REVIEW-POINTS.md` と `REVIEW-POINTS.local.md` の2つだけである（`for base in "REVIEW-POINTS.md"
"REVIEW-POINTS.local.md"`）。

実測でも、`.claude/rules/docs-workflow.md` を対象に収集した結果に含まれたのはルート
`REVIEW-POINTS.md` と `.claude/REVIEW-POINTS.md` の中身だけで、**`.claude/rules/` 配下の規約は
1行も含まれない**。

加えて `adversarial-review` スキルは、サブエージェントへ渡すものを「レビュー対象・マージ済みの
観点表・フェーズ番号」の3つに限り、**サブエージェント側から観点表を探しに行かせない**と定めて
いる。したがって、

> **`.claude/rules/` にだけ書いたルールは、敵対的レビューには渡らない。**

4件とも自己確認では見つからず敵対的レビューが検出したという事実と合わせると、**規約だけに書く
(a) は、実際に検出してきた唯一の経路へ届かない**ことになる。

**結論**: (b) が必要。`.claude/rules/docs-workflow.md`（規約＝書くときの手引き）を正とし、
ルート `REVIEW-POINTS.md`「ドキュメントの構造」の観点も一般化後の文言へ揃える。
(c)（サブエージェント定義の改修）は不要である——観点表は既に確実に渡る経路であり、
`adversarial-review` スキルが「観点の中身をSKILL.mdへ書かず `REVIEW-POINTS.md` へ書く」と
明示しているため、(b) がその設計どおりの反映先になる。

## 確かめられなかったこと

- **Q3 の判定は机上である。** 暫定案の実文がまだ無いため、「暫定案の核になる文」として想定した
  1文に対して当てはめた。フェーズ3で実際に書いた文言に対しては、**同じ4件をもう一度当て直す**
  必要がある（とくに #155）。
- **`.claude/rules/` が敵対的レビュー以外の経路（人間のレビュー、組み込みの `/code-review`）で
  どれだけ読まれるかは測っていない。** Q5 の結論は「敵対的レビューには渡らない」という一点で
  あり、規約が無価値だという意味ではない。
- **過去のドキュメントに同型の破損が残っているかは調べていない**（全体作業計画のスコープ外）。
- Q2 の絞り込みは「『見出し』と『地の文』を同一行に持つ」という条件で行った。**2行にまたがって
  同じことを述べている箇所は拾えていない**。ただし `係り先` での検索が2件しか返していないため、
  取りこぼしがあっても「係り先」という語を使わずに同じ規約を述べた記述に限られる。

## 設計への反映（フェーズ3で決めること）

1. **発動条件を操作の分類で書かない。** 「構造変更全般」への言い換えでは #155 を取りこぼす。
   「既存の記述を残したまま、その周囲を編集したとき」のように、**残置テキストの側**から条件を書く。
2. **「前後どちらも見る」を明示する。** PR #139 は挿入位置の後ろが壊れており、「直前を見よ」では
   射程内の操作ですら検出できなかった。
3. **実例は4件並べず、既存2件＋#109・PR #139 の計4件**とする（#155 は発動条件の書き方の根拠として
   1行で触れる）。#109 は「**分割前は正しかった行が、分割によって誤りになる**」形を明示する。
4. **書き換え先は2箇所。** `.claude/rules/docs-workflow.md`（正）と ルート `REVIEW-POINTS.md`
   （観点。規約を指す短い形へ揃える）。
5. **この段落を書き換えるとき、自分が PR #139 と同じ罠を踏まないこと。** 直後の `HANDOFF.md` の
   進捗記号を扱う段落は無関係であり、新しい見出しを立てるならその段落にも見出しが要る。
6. **DDRはフェーズ4で新規に作る。** 追記先になりうる既存DDRは0件で、却下案（操作の列挙で書く案）を
   伴う意思決定であるため。

## 想定と異なった点

- **計画では「正を1箇所に決めるか」を問うていたが、答えは「2箇所とも要る」だった。** Q5 で
  `.claude/rules/` が敵対的レビューへ渡らないと分かったため。重複を潰す方向へ進んでいたら、
  4件を検出してきた唯一の経路からルールを消すところだった。
- **Q4 は「issue #64 由来のDDRが1件ある」で終わりかけた。** 敵対的レビューの指摘で内容判定へ
  切り替えた結果、実際には追記先が0件だと分かった。**識別子は「そのissueで作られた」ことしか
  示さない。**
