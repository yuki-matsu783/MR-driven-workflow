## なぜそうしたか

### 手順3を「再現性」と「痕跡」に分けた（項目H）

**この手順を自分自身へ適用したことで見つかった穴である。** 当初、痕跡の確認は (a) 限定だった。
そこへ (b) の「該当するアセット」をファイル単位で読む解釈が重なると、近いファイルが必ず1つは
見つかるため **(a) が原理的に発生しなくなり、手順3が恒久的に迂回される**。

訂正は2点。(1) 「該当するアセット」は**記述単位**で見る。(2) 痕跡の確認は **(a) と (c) の両方**に
要求する（(c) と判定するには「その罠を扱った記述が本当に無いこと」の確認が要り、それは (a) の
痕跡探索と同じ作業だから）。

### 計画を種別ごとに2本へ分けた

`plans/REVIEW-POINTS.md` が「`【設計反映】` `【AIアセット反映】` `【実装反映】` を併記して
いないか（**対象・評価軸が異なるため原則分ける**）」を定めている。当初の理由「合意を1回で取れる」は
**一般則**であり、この観点は**その一般則に対する個別の上書き**だった。**一般則で個別則を上書き
する前例を作ると、以後どの併記も通ってしまう**——しかも観点を新設した当のissueが最初の違反例に
なるところだった。

### `.claude/scripts/` `.claude/hooks/` の種別

**ユーザー判断で `【AIアセット反映】` に揃えた**（AIの当初案は `【実装反映】`）。`【実装反映】`
との判別は、**反映先ではなく「どこから来た項目か」**で行う。DDR `i0110-01` の除外規定は
**フェーズ3の `【AIアセット作成】` については現役**なので、`note:` で射程を明示した。

### `.claude/VERSION` を据え置いた

AIの提案は `MINOR`（`0.2.0` → `0.3.0`）だったが、**`0.2.0` のまま据え置いた。**

決め手は flow-id 5-1 で取り込んだ main が持っていた **issue #26 の前例**である。あちらは配布の
仕組みごと入れ替える変更で、AIが `1.0.0`（`MAJOR`）を提案したのに `0.2.0` 据え置きと決まっていた。
**本issueは #26 より小さいので、#26 を据え置いて本issueだけ上げると版の意味が保てない。**

実害（配布先が版から資産の差を判別できない）は承知している。ただし本issueは**追記のみで改名・
削除を含まない**ため配布先に旧パスは残らず、機械可読な同一性は `.claude/.asset-manifest.json` が
持つ。据え置いた事実と根拠は spec の changelog に書いた。
