検出方式の設計

  1. 対象ファイル: git ls-filesの.md / .sh / .gitignore。
  2. .claude/scripts/test/配下は除外。トレードオフ（偽陰性）: ディレクトリ単位の除外のため、テストファイル内の本物の参照（設計根拠として実在DDRを引用するコメント。上記2件）も同時に除外される。除外の根拠を「フィクスチャであるという性質」に寄せる設計も検討したが、リストの形骸化リスクと実装コストを勘案し、今回はディレクトリ単位除外を採用する（設計判断として残存する既知の限界）。
  3. Markdownコードフェンス内を除外。トレードオフ（偽陰性）: markdown-frontmatter.md:36のように、フェンス内に実在する正しいDDRパスを書式例として掲載している箇所も除外される。今回は実害無しだが、厳密にするなら言語指定付きフェンスに限定する案がある。
  4. 正規表現でDDRパス候補を抽出（終端は空白・) ] " ' ` (のいずれか、.mdで終わることを要求）。bashの[[ =~ ]]は既定で貪欲マッチのため、ファイル名自体が.mdを含むケース（i0032-01-...Default.mdを正とし...md）でも正しく最後まで一致することを実測で確認済み。既知の限界（未修正）: 終端文字集合にタブと全角読点（、）が無く、タブ区切りで2パスが並ぶ行（test_check_base_conflicts.sh:192等）を1本の存在しないパスとして誤検出する。今回はテスト除外フィルタで回避されているが、フェーズ3の実装では終端文字集合へタブを追加する。
  5. ...または…を含む候補は除外（省略記法のため）。
  6. 残った候補について実在確認する。

対象範囲の限定理由（v2で追記）

  • .htmlを対象外とする理由: plans/ reports/のHTMLはタスク単位で削除される寿命の短いファイルであり、恒久的な参照切れ検出の対象として意味が薄いため除外。
  • 旧形式（4桁連番、i接頭辞なし）を対象外とする理由: 本リポジトリに現存しない（issue #133で全件改番済み）。ただし配布先で旧形式DDRが残っている場合、この検出器は検出できない。既存のddr_identifier_to_replyは旧形式も受け付けており対称性を欠く。本issueでは新形式のみ対応とし、配布先での必要性が生じた時点で追加を検討する（今後の課題）。
  • 相対パス表記を対象外とする理由: 下記「確かめられなかったこと」参照。

既存スクリプトとの整合確認（個別調査計画の未実施項目への対応）

ddr_identifier_to_reply（check-base-conflicts.sh）はDDRファイル名から識別子を抽出する関数（^(i[0-9]{4,}-[0-9]{2})-と旧形式^([0-9]{4})-の2パターン）。今回必要なのは逆方向（本文中の参照文字列から候補パスを抽出する）で直接流用できないが、識別子部分の正規表現は参考にした。桁数を{4,}ではなく+（桁数不問）にする点が意図的な差異（ゼロ埋め漏れ自体を検出したいため）。list_ddr_pathsはgit ls-treeでDDR一覧を.md$フィルタで取得しており、対象の絞り込み方法として参考にした。

shell-script-style.md規約への適合確認（個別調査計画の未実施項目への対応）

  • 外部プロセス起動のコスト: git ls-files -z | xargs -0 grep -noE '...'で、ファイル数に関わらずgrep起動を1〜数回に抑える。コードフェンス除外は行単位の状態追跡が必要なため、1ファイルにつき1回のみ< "$file"でforkなしに読み込む。
  • NULバイトの扱い: git ls-files -zとxargs -0で日本語パスのクォート化を回避。
  • 削除済み追跡ファイルの混入: [[ -f "$path" ]]のガードを実装時に挟む。

確かめられなかったこと

相対パス形式の参照は個別確認のみで、検出設計には含まれていない。 リポジトリ全体を \.\./[^ )"'`]*docs/ddr/[^]) "'`(]*\.mdで走査したところ5件ヒットし （すべて.claude/rules/配下のmarkdownリンク先）、5件とも実在を確認した。 今回は結果として参照切れは無かったが、この形式は検出ロジックの対象外であり、将来相対パス 表記でゼロ埋めを間違えても検出できない。フェーズ3で対応を含めるかは別途判断が必要 （「やらないこと」節に見送りとして明記済み）。

想定と異なった点

全体作業計画の時点では「パス形式に限定すれば誤検知を避けられる」と見込んでいたが、 実際にはパス形式に限定してもなお、テストフィクスチャとコード例という2種類の誤検知源が 残ることが分かった。これに対処する2フィルタは計画時点では想定していなかった追加要件である。

v1レポート自体の件数集計にも誤りがあった（下記「v1からの訂正点」）。「0件を期待する 検索は当たらないパターンでは常に成功する」という規約上の注意は認識していたが、件数を 報告する側にも同種の落とし穴（内訳の合計を検算しない）があることを、今回の敵対的レビューで 学んだ。
