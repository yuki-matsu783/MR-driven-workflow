Q1. 現行ルールの射程と、一般化後に既存記述と矛盾しないか

対象は .claude/rules/docs-workflow.md の104〜114行目。1文ずつ切り分けると次のとおり。

位置文「見出しの挿入」への依存

Q3. ルール本文へ載せる実例は何件か

4件それぞれについて、上位計画「フェーズ3〈作業〉」の5項目（暫定案）だけを読んで検出できるかを 机上で突き合わせた。暫定案の核になる文は次の形と想定した。

既存の文書の構造へ手を入れたら、残置した地の文・箇条書きが、変更前と同じものに係っているかを、 変更箇所の前後どちらについても確認する。
#何を変えたか壊れた位置（新しく書いた部分から見て）現行ルールで拾えるか暫定案で検出できるか
issue #64新しい見出しを差し込んだ前（挿入位置の直前の節の末尾）拾えるできる
issue #109既存の節を (1)(2) に分割した前（新設した (2) の手前に残した、(1) 直下の結論行）拾えないできる
PR #139（issue #135）新しい見出しを差し込んだ後ろ（新設した見出しの配下に入った、見出しを持たない段落群）拾えないできる（「前後どちら」が効く）
issue #155既存の箇条書きへ項を1つ足した前（直前の項の末尾にあった補足）拾えないできない可能性が高い
#155 が暫定案の穴である issue #155 のコメントが明示しているとおり、この事例では見出しを1つも動かしておらず、節を分割しておらず、 箇条書きの階層も変えていない（同じ深さの項を1つ増やしただけ）。「構造へ手を入れた」という発動条件は、 それ自体が操作の分類であり、「項を1つ足す」を構造変更と読むかどうかが読み手に委ねられる。 issue #142 が「操作の種類を列挙しない」と求めた理由がそのまま効いており、 「構造変更」という上位カテゴリへ言い換えただけでは、列挙をやめたことにならない。

フェーズ3への含意: 発動条件を操作の側（何をしたか）ではなくリスクの側 （残置テキストの周囲が変わったか）で書く。「既存の記述を残したまま、その周囲を編集したとき」のように、 操作の名前を出さずに条件を書ければ、4件すべてが自然に入る。

載せる実例: 既存2件（#64 由来）を残したうえで、#109 と PR #139 の2件を足す。この2件は 壊れた位置が前後で逆であり、並べると「前後どちらも見る」という観点が具体で支えられる。#155 は本文の実例としては 足さず、発動条件の書き方の根拠として1行で触れるに留める（実例を4件並べると、ルール本文より事例集のほうが 長くなり、読み手が要点を取り出せなくなる）。

Q5. ルールを実際に守らせる場所はどこか

collect-review-points.sh の実装を読むと、祖先方向へ遡って集めるのは REVIEW-POINTS.md と REVIEW-POINTS.local.md の2つだけである （for base in "REVIEW-POINTS.md" "REVIEW-POINTS.local.md"）。

実測でも、.claude/rules/docs-workflow.md を対象に収集した結果に含まれたのはルート REVIEW-POINTS.md と .claude/REVIEW-POINTS.md の中身だけで、 .claude/rules/ 配下の規約は1行も含まれない。

加えて adversarial-review スキルは、サブエージェントへ渡すものを「レビュー対象・マージ済みの 観点表・フェーズ番号」の3つに限り、サブエージェント側から観点表を探しに行かせないと定めている。

帰結 .claude/rules/ にだけ書いたルールは、敵対的レビューには渡らない。 4件とも自己確認では見つからず敵対的レビューが検出したという事実と合わせると、規約だけに書く (a) は、 実際に検出してきた唯一の経路へ届かないことになる。

結論: (b) が必要。.claude/rules/docs-workflow.md（規約＝書くときの手引き）を正とし、 ルート REVIEW-POINTS.md「ドキュメントの構造」の観点も一般化後の文言へ揃える。 (c)（サブエージェント定義の改修）は不要である——観点表は既に確実に渡る経路であり、 adversarial-review スキルが「観点の中身をSKILL.mdへ書かず REVIEW-POINTS.md へ書く」と 明示しているため、(b) がその設計どおりの反映先になる。

確かめられなかったこと

  • Q3 の判定は机上である。 暫定案の実文がまだ無いため、「暫定案の核になる文」として想定した1文に対して 当てはめた。フェーズ3で実際に書いた文言に対しては、同じ4件をもう一度当て直す必要がある（とくに #155）。
  • .claude/rules/ が敵対的レビュー以外の経路（人間のレビュー、組み込みの /code-review）でどれだけ読まれるかは測っていない。 Q5 の結論は「敵対的レビューには渡らない」 という一点であり、規約が無価値だという意味ではない。
  • 過去のドキュメントに同型の破損が残っているかは調べていない（全体作業計画のスコープ外）。
  • Q2 の絞り込みは「『見出し』と『地の文』を同一行に持つ」という条件で行った。2行にまたがって同じことを 述べている箇所は拾えていない。ただし「係り先」での検索が2件しか返していないため、取りこぼしがあっても 「係り先」という語を使わずに同じ規約を述べた記述に限られる。

設計への反映（フェーズ3で決めること）

  1. 発動条件を操作の分類で書かない。「構造変更全般」への言い換えでは #155 を取りこぼす。 「既存の記述を残したまま、その周囲を編集したとき」のように、残置テキストの側から条件を書く。
  2. 「前後どちらも見る」を明示する。 PR #139 は挿入位置の後ろが壊れており、「直前を見よ」では 射程内の操作ですら検出できなかった。
  3. 実例は既存2件＋#109・PR #139 の計4件とする（#155 は発動条件の書き方の根拠として1行で触れる）。 #109 は「分割前は正しかった行が、分割によって誤りになる」形を明示する。
  4. 書き換え先は2箇所。 .claude/rules/docs-workflow.md（正）と ルート REVIEW-POINTS.md（観点。規約を指す短い形へ揃える）。
  5. この段落を書き換えるとき、自分が PR #139 と同じ罠を踏まないこと。 直後の HANDOFF.md の 進捗記号を扱う段落は無関係であり、新しい見出しを立てるならその段落にも見出しが要る。
  6. DDRはフェーズ4で新規に作る。 追記先になりうる既存DDRは0件で、却下案（操作の列挙で書く案）を 伴う意思決定であるため。
