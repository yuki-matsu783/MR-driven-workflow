対象は .claude/rules/docs-workflow.md の104〜114行目。1文ずつ切り分けると次のとおり。

暫定案5項目の逐条判定

上位計画「フェーズ3〈作業〉」の5項目を原文のまま引用し、項目ごとに何を担うか・4件を拾えるかを 判定した（項目を1文へ融合すると、どの項目の穴なのかが分からなくなるため融合しない）。

項目（原文）何を担うか4件への効き方
1. 適用対象を「見出しの差し込み」から構造変更全般へ広げる。ただし操作の種類を列挙する形にしない発動条件（いつ確認するか）#64・#109・PR #139 は入る。#155 は入るか読み手に委ねられる
2. 確認の観点を「残置した地の文・箇条書きが、変更前と同じものに係っているか」という形で書く観点（何を見るか）4件すべてに当てはまる。ただしいつ見るかは定めないので、単独では発動条件にならない
3. 「前後どちらの残置テキストも見る」ことを明示する探索範囲PR #139（後ろが壊れた唯一の件）を拾うのに必須
4. issue #64 の既存の実例は消さない受け入れ条件の遵守検出可否には効かない
5. 「分割前は正しかった行が、分割によって誤りになる」形を明示した実例を足す気づきやすさ#109 の形を具体で支える
穴は項目1にある 発動条件を担うのは項目1だけであり、そこに置かれた「構造変更全般」はそれ自体が操作の分類である。 issue #155 のコメントが明示しているとおり、この事例では見出しを1つも動かしておらず、節を分割しておらず、 箇条書きの階層も変えていない（同じ深さの項を1つ増やしただけ）。「項を1つ足す」を構造変更と読むかどうかは 読み手に委ねられる。issue #142 が「操作の種類を列挙しない」と求めた理由がそのまま効いており、 上位カテゴリへ言い換えただけでは、列挙をやめたことにならない。

項目2の観点は #155 にも当てはまるが、観点は「何を見るか」であって「いつ見るか」ではないため、 項目1が発動しなければ読まれない。したがって「項目2があるから #155 も拾える」とは言えない。

フェーズ3への含意: 発動条件（項目1）を操作の側（何をしたか）ではなくリスクの側 （残置テキストの周囲が変わったか）で書き直す。「既存の記述を残したまま、その周囲を編集したとき」のように、 操作の名前を出さずに条件を書ければ、4件すべてが自然に入る。

載せる実例: 既存2件（#64 由来）を残したうえで、#109 と PR #139 の2件を足す（合計4件）。 この2件は壊れた位置が前後で逆であり、並べると「前後どちらも見る」という観点が具体で支えられる。 #155 は5件目の実例としては足さず、発動条件の書き方の根拠として1行で触れるに留める （実例を5件並べると、ルール本文より事例集のほうが長くなり、読み手が要点を取り出せなくなる）。

Q5. ルールを実際に守らせる場所はどこか

collect-review-points.sh の実装を読むと、祖先方向へ遡って集めるのは REVIEW-POINTS.md と REVIEW-POINTS.local.md の2つだけである （for base in "REVIEW-POINTS.md" "REVIEW-POINTS.local.md"）。

実測でも、.claude/rules/docs-workflow.md を対象に収集した結果に含まれたのはルート REVIEW-POINTS.md と .claude/REVIEW-POINTS.md の中身だけで、 .claude/rules/ 配下の規約は1行も含まれない。

加えて adversarial-review スキルは、サブエージェントへ渡すものを「レビュー対象・マージ済みの 観点表・フェーズ番号」の3つに限り、サブエージェント側から観点表を探しに行かせないと定めている。

帰結 .claude/rules/ にだけ書いたルールは、敵対的レビューには渡らない。

「4件とも敵対的レビューが検出した」は成り立たない

初版のレポートはここで「4件とも自己確認では見つからず敵対的レビューが検出した」を前提にしていたが、 これは事実ではない。敵対的レビュー機構は issue #77 で新設されたもので、 .claude/docs/spec/adversarial-review.md「背景・目的」に「本issue以前、このリポジトリには レビューを担うスキルもサブエージェントも存在しなかった」と明記されている。#64 は #77 より前なので、 #64 を敵対的レビューが検出することは原理的に不可能である（上記 Q3 の出典表のとおり、#64 は着手時の 自己確認で気づいた形として読める）。

正しくは「4件のうち3件（#109・PR #139・#155）を敵対的レビューが検出した」である。

前提を正しても結論 (b) は保つ

前提が「4件とも」から「3件」へ弱まっても、Q5 の結論は変わらない。理由は2つ。

  1. 敵対的レビュー機構が存在して以降に起きた3件は、3件とも敵対的レビューが検出している。 機構が無かった時代の1件を除けば、実績は 3/3 である。
  2. #64 が自己確認で見つかったことは、むしろ現行ルールの限界を示す。 #64 は現行ルールが 直接扱う形（見出しの挿入・直前が壊れる）であり、ルールの射程内だったから気づけたと読める。 射程外の3件は自己確認をすり抜けており、射程を広げるだけでは足りず、広げた射程が実際に検出してきた 経路（観点表）へ届く必要があるという結論を補強する。

結論: (b) が必要。.claude/rules/docs-workflow.md（規約＝書くときの手引き）を正とし、 ルート REVIEW-POINTS.md「ドキュメントの構造」の観点も一般化後の文言へ揃える。 (c)（サブエージェント定義の改修）は不要である——観点表は既に確実に渡る経路であり、 adversarial-review スキルが「観点の中身をSKILL.mdへ書かず REVIEW-POINTS.md へ書く」と 明示しているため、(b) がその設計どおりの反映先になる。
