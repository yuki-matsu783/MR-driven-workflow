## 実施した内容と結果

### 1〜2. CR の入口と出口

**当初は出口だけを想定していたが、入口も同じ根の問題だった。**

| 箇所 | 何が起きるか | 対処 |
|---|---|---|
| 入口: `agents/*.md` の読み込み | `mapfile` は改行だけを区切りにするため、CRLF では1行目が `$'---\r'` になり「frontmatter がありません」で落ちる | `mapfile` 直後に `${lines[i]%$'\r'}` |
| 出口: `settings.json` の書き出し | Windows native `jq` が標準出力へ CR を付ける。`.gemini/settings.json` だけが CRLF になり `--check` が環境で食い違う | `convert_settings … \| tr -d '\r' > …` |

`.gitattributes` の配布行が `eol=lf` を保証するのは `.sh` だけで、`.md` は配布先の
`core.autocrlf` 次第で CRLF になりうる。**配布行は増やさず**スクリプト側で吸収した
（配布先の `.gitattributes` へ追記される行なので、影響がこのリポジトリに閉じないため）。

検証は**スタブ `jq`**（`sed '$!s/$/\r/'` を通す）を `PATH` 先頭へ置いて行った。
スタブ自身が実際に CR を付けることも同じテストで表明している（付けないスタブなら、
CR 検査は無条件に通ってしまう）。CR の有無はバイト数の比較で見ている
（`grep -c $'\r'` は環境により全行にマッチするため使わない）。

### 3. ローカル設定の除外

**計画は「`.gitignore` へ追加する」と書いていたが、実際には既に入っていた**
（main の PR #158 が OTel 対応で `/.claude/settings.local.json` を追加済み）。
残っていたのは配布先側で、次の2つを行った。

- `install-to-project.sh` の `ignore_rules` へ `/.claude/settings.local.json` を追加。
  配布先の `.gitignore` にこの行が無いと `--exclude-standard` が落とせず、各開発者の
  ローカル設定が `.gemini/` へ焼き込まれてコミットされる。
- `commit` スキルのファイルフィルタへ `settings.local.json` を追加（`.claude/` ごと配布
  されるため、`.gitignore` 側だけでは配布先を守れない）。

`COPY_EXCLUDED_PREFIXES` へは**足していない**（計画どおり）。`.gitignore` に入れば
`--exclude-standard` が落とすので二重になり、除外の定義が2箇所へ分かれるほうが危うい。
**3案目（未追跡ファイルのコピー件数を標準エラーへ出す）も採っていない**——正常時に毎回
出力が増えるだけで、判断材料にならないため。

テストでは「除外できている」だけでなく、**ignore されていない未追跡ファイルは載る**ことも
併せて表明した（前者だけだと、未追跡が全部落ちていても通ってしまう）。

### 4. `build_into` の0件判定

**メッセージを直すつもりで見たら、失敗条件そのものが広すぎた。**
`agents/*.md` と `settings.json` は変換で作るので、その2つしか無い `.claude/` でも生成物と
しては成立するのに、「コピー対象0件」を失敗にしていた。契約の変更として扱い、判定を
「列挙0件」へ狭めたうえでテストを置き換えた（T17）。

| 原因 | 判定 | メッセージ |
|---|---|---|
| `.claude/` が無い | `[ ! -d .claude ]` | ワークフローが導入されていないリポジトリと思われる旨 |
| 追跡ファイルが全件、作業ツリーに無い | `skipped > 0` | 削除をステージしていない旨（`git status` を案内） |
| すべて ignore されている | 上記以外 | `git check-ignore -v .claude/settings.json` を案内 |

**旧メッセージの「リポジトリルートで実行していますか」は、そもそも成り立たない案内だった。**
`main` は判定より前に `git rev-parse --show-toplevel` へ `cd` しており、リポジトリ外なら
その時点で失敗する。原因を切り分けようとして初めてこの誤りが見えた。

### 5. `read -d ''` の実機計測

**main が先に片付けていた。** PR #162（issue #159）が
`.claude/rules/shell-script-style.md` へ「1バイトずつ read(2) する／この特性自体は未計測」
という注意を既に入れており、計画がここで書くはずだった内容と重複していた。

**残っていたのは「ではどう測るのか」だけ**なので、同じ節へ計測手順を足した
（ペイロード3種／空hookをベースラインに取る／同一セッション内で `read -d ''` 版と
`$(cat)` 版を連続で測る／判断は絶対値でなく差で行う）。**置き場所は計画が言っていた
`.claude/docs/spec/` ではなく `.claude/rules/`** にした——注意そのものが既にそちらにあり、
手順だけを別ファイルへ置くと、読む人が両方を突き合わせないと判断できなくなるため。

**コードは変えていない。** この実行環境（Linux）では判断できないためで、
**「測れないから現状維持」であって「測ったうえで現状維持」ではない**ことを本文へ明示した。

### 6.（新規）前置フィルタが超集合でなかった

**上の5の注記を書いている最中に、自分で踏んだ。**
「push系2本は判定本体がコマンド位置ベースなのでバックスラッシュ除去は要らない」と
書こうとして根拠を確かめたところ、偽だった。

```
cmd=git push       精密=1 前置=1
cmd=git pu\sh      精密=1 前置=0   ← 取りこぼし
cmd=git pus\h      精密=1 前置=0   ← 取りこぼし
```

`git pu\sh` は精密判定（`command_invokes_git_subcommand`）では push と読まれるが、
hook が受け取る生JSONには `pu\\sh` としか現れないため `*push*` に一致しない。
さらに `git pu\<改行>sh` は JSON 化すると `pu\\\nsh` になり、**バックスラッシュ1文字だけの
除去では `punsh` になって**やはり取りこぼす。

**issue #159 が `commit` 側で塞いだのとまったく同じ穴を、`push` 側へ開けたまま出していた。**
対処は `block-direct-git-commit.sh` と同型で、判定を純粋関数 `raw_hints_at_git_push` へ
切り出し、JSON 文字列エスケープの2文字シーケンスをまとめて除去してからブラケット式で
比較する（`${var,,}` は使わない）。2本の実装は**同一**であることをテストで固定した。

**T11 のテストは「超集合であること」を主張していたのに、ケース一覧にバックスラッシュが
1件も無かったため通っていた。** 主張とケースが噛み合っていないテストは、通っていても
根拠にならない。ケースを4件（`git pu\sh` / `git pus\h` / `git \push` / 行継続）足し、
併せて `prefilter_passes` の**写経をやめて実装を `source` して呼ぶ**形へ変えた。

## 確かめられなかったこと

- **CR の挙動は Windows 実機で確かめていない。** スタブ `jq` は native jq と MSYS の
  コマンド置換を合わせた実測に一致する形（最終行以外へ CR を付ける）だが、**スタブは
  スタブである**。後段に `head`/`sed` が挟まる経路では実 jq と結果がずれる
  （`.claude/rules/shell-script-style.md`「テスト」のスタブの限界）。
- **`read -d ''` の read(2) コストは依然として未計測である。** 手順だけを残した。
- 配布経路（`install-to-project.sh` が配布先の `.gitignore` へ行を足す）は、
  結合テストで配布先を作って確認しているが、**実際の他プロジェクトへ入れてはいない**。
