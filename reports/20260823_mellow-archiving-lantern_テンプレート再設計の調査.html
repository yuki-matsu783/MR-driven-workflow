1. 二重管理の解消方式 → 案B（テンプレートファイルを正とする）

判断 .github/pull_request_template.md を唯一の正とし、describe 節は見出し構成を列挙せず「テンプレートファイルを読んで、その見出し構成に従う」と指示するだけにする。.gitlab/merge_request_templates/Default.md は GitHub 版と本文が一致していることをテストで機械的に保証する。

根拠:

  • 同じ判断の先例がある。 references/deliverables.md「計画・レポートのHTMLビュー」は「記述の型（見出し構成）の正はテンプレート側にあり、SKILL.md（フロー定義）は列挙しない」と、issue #54 で既に同型の判断を下している。本issueはこの原則をPR/MRテンプレートへ広げるだけであり、新しい方針を持ち込まない。

  • MCP経路でも動く。 describe が行うのはローカルファイルの読み込みであり、経路に依存しない。どちらのテンプレートを読むかは get_provider で足りる（references/mcp-fallback.md の対応表でも「MCP不要」に分類）。
  • 人間がWeb UIで作るPRでも見出しが得られる（案Cが失う性質）。

採らなかった案:

案内容却下の理由

既存テストの扱い: .claude/scripts/test/test_install_to_project.sh は現在、review-loop.md の describe 節から見出し行を awk で抜き出し（抽出行数が 3 であることも表明）、テンプレート2本と3者一致を検査している。案Bでは describe 節が雛形を失うため、この抽出は空振りする。置き換え方針は次のとおり。

  1. 抽出元を review-loop.md からやめる。
  2. 代わりに、期待値の10節をテスト内へ書き下す。テンプレート2本の見出しが、この期待値と順序込みで一致することを表明する。
  3. テストの期待値は「二重管理」に数えない。 期待値は正ではなく検査であり、これが無いと「2本を比べるだけでは足りない（両方が同時にずれると通ってしまう）」という既存テストのコメントが守れなくなる。ただし更新が必要な場所であることに変わりはないため、その旨をテスト側のコメントへ明記する。
  4. 抽出行数の固定値 3 は残さない。「期待値が非空であること」の表明で空振り防止の目的は満たされる。

3. plans/ worklog/ reports/ 参照禁止の書き場所

判断 (1) .claude/rules/docs-workflow.md の既存段落「コード・スクリプト内のコメントから plans/ worklog/ reports/ のファイルを参照しない」の直後へ、MR/PR本文についての段落を足す。(2) テンプレート2本のHTMLコメント（## 反映先・関連 節の記入ガイド）にも同じ禁止と「代わりに何を書くか」を書く。例外は設けない。
  • 既存段落は「恒久的に参照してよいのは、issue番号と .claude/docs/spec/ .claude/docs/ddr/ .claude/docs/usecase/ 配下のファイルである」という一般則で終わっており、直後に足しても係り先が壊れない。docs-workflow.md 自身の「新しい見出しを差し込むとき」の注意は見出しの差し込みを対象にしており、同じ節の中の段落追加はその対象にもならない。
  • 「参照しない」だけでは足りない。 何を書くかまで示す。
    • reports/ の結論は、## 検証 ## 設計判断・採らなかった案 へ転記する（リンクしない）。
    • spec/DDRへ昇格したものは、そのパスで指す。
    • issue番号・PR番号・レビューコメントのpermalinkは恒久なので、これらで代替する。
  • 例外を認めない。 「レビュー中はまだ存在するので参照が有効に見える」という状況こそが罠で、レビュー時に踏めた参照がマージ後に必ず切れる。issue #145 が集計した「64件中52件」がまさにこの経路で生まれている。

4. 10節構成と describe の6回の全文置換

噛み合う。ただし次の3点を規約として決める。

  1. 「特になし」と「未実施」を書き分ける。 特になし ＝ 検討した結果、書くことが無かった。未実施 / このフェーズではまだ確定していない ＝ まだその段階に達していない。issue #145 は「該当が無ければ『特になし』と1行書いて残す」と定めているが、まだ書けない節に『特になし』と書くと、検討済みと誤読される。両者を区別する語をテンプレートのHTMLコメントで定義する。
  2. 各節の「計画段階では何を書くか」をHTMLコメントで定める（issue #145 の受け入れ条件）。
  3. descriptionの最終形は flow-id 4-10 で完成させる。 describe の最後の実行は 4-10 であり、plans/ worklog/ reports/ の削除（flow-id 5-5）はその後である。つまり最後の describe の時点では材料がまだ全部そろっている。この順序を仕様へ明記しないと、「材料が消えた後に書こうとして書けない」という読み違いが起きうる。
確認した事実 全文置換で前回の内容が失われる問題は、現行の2節構成にも同じようにある。 describe は毎回 get_branch_work_files で plans/ worklog/ を読み直して本文を作り直す設計で、前回のdescriptionを読み込む手順は無い。10節にしても性質は変わらない。節が増えるぶん再生成のコストは上がるが、材料（HANDOFF.md・worklog/・PRのレビュースレッド）はすべてブランチ上にあり、追加の情報源は要らない。
