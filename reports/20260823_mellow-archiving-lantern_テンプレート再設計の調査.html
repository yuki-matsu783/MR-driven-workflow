1. 二重管理の解消方式 → 案B（テンプレートファイルを正とする）

判断

.github/pull_request_template.md を唯一の正とし、describe 節は見出し構成を列挙せず「テンプレートファイルを読んで、その見出し構成に従う」と指示するだけにする。.gitlab/merge_request_templates/Default.md は GitHub 版の複製とし、先頭のHTMLコメントを除いた本文が一致していることをテストで機械的に保証する（正の実体は1つ、プロバイダ向けの複製が1つ、という関係にする）。

保証範囲を「見出し行だけ」に留めない。 現行テストは ^(Closes|## ) で見出し行しか比べておらず、それだけでは各節のHTMLコメント（＝記入ガイド。10節構成の実質的な中身）が片方だけずれても検出できない。先頭のHTMLコメントブロックだけを除外した全文差分を検査する。

先頭のHTMLコメントはプロバイダ固有で、一致させない。 GitLab版だけが Default.md という予約名の説明（DDR i0032-01 への参照）を持つ。除外するのはこのブロックだけである。

根拠

  • 同じ判断の先例がある。 references/deliverables.md「計画・レポートのHTMLビュー」は「記述の型（見出し構成）の正はテンプレート側にあり、SKILL.md（フロー定義）は列挙しない（二重管理を避けるため。型を変えたいときは、フロー定義である SKILL.md ではなくテンプレートの中身を差し替える）」と、issue #54 で既に同型の判断を下している。本issueはこの原則をPR/MRテンプレートへ広げるだけであり、新しい方針を持ち込まない。
  • テンプレート2本は core 層である。 .claude/dist-layers.json は .github / .gitlab を core（配布元所有・常に上書き）とし、note に「issue/PRテンプレート。見出しが start・describe と機能的に結合」と書いている。配布先が改変しても再適用時に .bak へ退避して上書きされる（.claude/docs/spec/asset-distribution.md の層の表）。
    • ただし core が保証するのは「再適用を実行した時点で本家の内容へ戻る」ことだけである。 再適用と再適用の間に配布先がテンプレートを書き換えれば、案Bの describe（ローカルのテンプレートを読んで見出しを決める）は書き換え後の内容を読む。「配布先でも中身は常に本家と一致する」とは言えない（ドリフトは次の再適用まで残る）。
    • それでも案Bを採れるのは、ドリフトした場合に読まれるのが「配布先自身が書いた見出し」であって、無関係な別物ではないからである。配布先が意図してテンプレートを変えたなら describe がそれに従うのはむしろ正しい挙動であり、意図していないなら再適用で戻る。
  • MCP経路でも動く。 describe が行うのはローカルファイルの読み込みであり、経路に依存しない。どちらのテンプレートを読むかの判定は get_provider で足りる。出典は Provider.sh の実装である（git remote get-url origin の結果を provider_from_remote_url へ渡すだけで、CLIを一切呼ばない）。references/mcp-fallback.md の対応表に get_provider の行は無いため、対応表を根拠に挙げない（同表で「MCP不要」に分類されているのは get_repo_url 等の別関数で、「git remote get-url origin の正規化だけで決まるプロバイダ非依存の関数」という説明文はそちらのものである）。
  • 人間がWeb UIで作るPRでも見出しが得られる（案Cが失う性質）。

3. plans/ worklog/ reports/ 参照禁止の書き場所

判断

次の2箇所へ書く。例外は設けない。

  1. .claude/rules/docs-workflow.md: 既存段落「コード・スクリプト内のコメントから plans/ worklog/ reports/ のファイルを参照しない」（64〜69行目）と、その例示であるコードブロック（71〜76行目の「悪い例／良い例」）の後、つまり76行目の直後へMR/PR本文についての段落を足す。

4. 10節構成と describe の6回の全文置換

判断

噛み合う。ただし次の3点を規約として決める。

  1. 「特になし」と「未実施」を書き分ける。
    • 特になし = 検討した結果、書くことが無かった。
    • 未実施 / このフェーズではまだ確定していない = まだその段階に達していない。

    issue #145 は「該当が無ければ『特になし』と1行書いて残す」と定めているが、まだ書けない節に『特になし』と書くと、検討済みと誤読される。両者を区別する語をテンプレートのHTMLコメントで定義する。

  2. 各節の「計画段階では何を書くか」をHTMLコメントで定める（issue #145 の受け入れ条件）。たとえば ## 検証 は計画段階では「未実施（フェーズ3で実施予定の検証を列挙）」、## レビューの結果 は「未実施（まだレビューを受けていない）」と書く。
  3. descriptionの最終形は flow-id 4-10 で完成させる。ただし「常に最新」ではない。 describe の最後の実行は 4-10 であり、plans/ worklog/ reports/ の削除（flow-id 5-5）はその後である。つまり最後の describe の時点では材料がまだ全部そろっている。この順序を仕様へ明記しておかないと、「材料が消えた後に書こうとして書けない」という読み違いが起きうる。
    • その代わり、4-10 より後のステップの変更はdescriptionへ載らない。 flow-id 5-3（.gemini/ 変換同期）・5-4（統括レポートの作成・commit・push）・5-5（plans/ 等の削除）はいずれも成果物を変更するステップであり、マージ時点のdescriptionはこれらを含まない。影響を受けるのは ## 変更内容 ## 検証 ## レビューの結果 の3節である。
    • この差は許容し、5-4 の後に describe を追加しない。 理由は2つ。(a) 5-3〜5-5 の変更はいずれも機械的で、レビューの判断材料にならない（変換生成物の同期・統括レポートの追加・作業ファイルの削除）。(b) 5-4 のサマリコメントがまさにその時点のスナップショットを担っており、二重に持つ必要が無い。「常に最新」という言い方をやめ、「flow-id 4-10 時点の全体像」と書くことで、読み手が差の存在に気づけるようにする。

確認した事実

  • 全文置換で前回の内容が失われる問題は、現行の3節構成にも同じようにある。 describe は毎回 get_branch_work_files でブランチ固有の作業ファイルを読み直して本文を作り直す設計で、前回のdescriptionを読み込む手順は無い。10節にしても性質は変わらない。
  • get_branch_work_files は plans/ worklog/ に加えて reports/ も列挙する（Provider.sh の実装が plansDir / worklogDir / reportsDir の3つを git diff と git status -z へ渡している）。ところが references/review-loop.md の describe 手順1は「全体作業計画・個別計画・worklogの要点を読む」としか書いておらず、reports/ に触れていない。関数の出力と手順文言が既にずれている。
    • これは10節構成にとって致命的である。## 検証 ## 設計判断・採らなかった案 は上記§3のとおり reports/ の結論を転記する節であり、手順1が reports/ を読まないままだと材料が手に入らない。
    • フェーズ3の作業として「describe 手順1の読み取り対象へ reports/ を明示的に加える」を行う（下記「設計への反映」の項目3-b）。
  • 節が増えるぶん再生成のコストは上がるが、材料（HANDOFF.md・worklog/・PRのレビュースレッド）はすべてブランチ上にあり、追加の情報源は要らない。
