### 2. 検出スクリプトの実装

`.claude/scripts/src/check-doc-references.sh`を作成した。**v1（実装直後）の設計から、
2回目の敵対的レビュー（12件のfindings）を受けて大幅に改訂した**（詳細は「想定と異なった点」）。

構成する純粋関数（テストから直接呼べる）:

- `is_excluded_target_path`: `.claude/scripts/test/` `plans/` `reports/` `worklog/`配下の判定
- `is_placeholder_candidate`: 省略記法（`...`/`…`）を含むかの判定
- `is_fence_delimiter_line`: 行がコードフェンス区切り（`` ``` ``/`~~~`、3個以上・インデント
  可）かの判定。マーカー種別・長さを返す
- `compute_fenced_linenos_to_reply`: 複数行テキストからフェンスで囲まれた行番号の集合を返す。
  開始と同じ種別・同じ長さ以上の閉じ記号でのみ閉じたとみなす。未閉鎖なら空集合を返す（安全側）
- `split_concatenated_candidates_to_reply`: 終端文字集合で区切れず連結された候補を、
  `.claude/docs/ddr/`という接頭辞の再出現位置で分割する
- `extract_ddr_candidates_to_reply`: 1行からDDRパス候補を貪欲マッチですべて抽出する
  （`main`の実走査はgrepで行うため直接は使われないが、`CHECK_DOC_REFERENCES_REGEX`という
  同じ正規表現変数を参照するため、単体テストがgrep側の挙動も間接的に裏付ける）

`main`は`if [ "${BASH_SOURCE[0]}" = "${0}" ]; then main; fi`でガードし、単体テストからの
`source`時に実行されないようにした。走査対象が0件のときは非0で終了する（空振りで緑になる
ことを防ぐ）。

## 想定と異なった点

実装直後（v1）に対する敵対的レビュー（2回目、12件のfindings）で、実機再現を伴う指摘を多数
受けた。全件を検証のうえ、以下の重大な欠陥を修正した。

- **恒久ファイルのコメントが`plans/`を参照していた**。`.claude/scripts/src/`配下は永続コード
  だが、v1のコメントは`plans/【実装】【テスト】〜.md`という短命ファイルを指しており、
  `.claude/rules/docs-workflow.md`「恒久的な参照先」に反していた（本issue自身が直そうとして
  いる欠陥類型と同種で、皮肉にも本スクリプト自身のDDRパス限定の正規表現では検出できない
  対象だった）。issue番号のみの参照へ修正した。
- **フェンス除外後の行番号がずれていた**（v1のバグ）。v1は行を削除する2パス方式（フェンス内の
  行を文字列から取り除いてから改めて行数を数える）だったため、フェンスの後ろにある参照切れの
  報告行番号が実ファイルの行番号とずれていた（実測: 6行目にある参照が`doc.md:3`と誤って
  報告された）。**対応: フェンス除外の方式を、行を削除する方式から「フェンス範囲の行番号の
  集合を求め、grepが返す元ファイルの行番号と突き合わせて除外するか判定する」方式へ変更した。**
  行の削除・再構成を行わないため、報告される行番号は常に実ファイルの行番号と一致する。
- **フェンスの単純トグル判定が、種別・長さの異なるフェンス風の行で偶数回トグルになり、
  安全側フォールバックが働かないまま本文行を無言でフェンス内と誤認する false negative が
  あった**（v1のバグ）。実際に``` text / ~~~ / ``` / 参照行 / ~~~ という5行構成で、参照切れが
  完全に見逃されることを実機確認した。**対応: フェンスの開始・終了判定を、開始時のマーカー
  種別（`` ` ``/`~`）と長さを記憶し、同種・同じ長さ以上の閉じ記号でのみ閉じたとみなす方式へ
  変更した**（CommonMarkのフェンス規則を簡略化して踏襲）。単体テストへ再現ケースを追加した。
- **全角句読点で連結された2つのDDRパスが1本の架空パスへ誤って結合される問題（v1でも既知の
  限界としてコメント済みだったが未対処）に対し、正規表現の文字クラスへ全角文字を追加する
  方法で対処しようとしたところ、この環境（`LANG`未設定・POSIXロケール）ではPOSIX ERE の
  ブラケット式に多バイト文字を含めるとgrep・bashの`[[ =~ ]]`のどちらも該当行に一切マッチ
  しなくなり、リポジトリ全体の候補数が0件に落ちる致命的な回帰を引き起こした。** 実機で
  `LC_ALL=C.UTF-8`を明示すれば動くことを確認したが、git bash実機を含む配布先のロケールを
  制御できない前提のため採用を見送った。**対応: 正規表現自体は全角文字を含めないASCII限定の
  ままとし、抽出後の候補文字列に対して`.claude/docs/ddr/`という接頭辞がASCII構造として
  候補中に再出現するかだけを見て連結を検知・分割する後処理
  （`split_concatenated_candidates_to_reply`）を追加した。** 区切り文字が全角句読点か否かに
  依存せず、ロケールにも依存しない。
- **候補抽出をbash単独方式（1ファイル1回の`while read`＋`[[ =~ ]]`）で実装したv1は、
  リポジトリ全体（151ファイル・37,411行）に対し5.2秒かかった。** 同じ正規表現を
  `git ls-files -z | xargs -0 grep -nHoE`で一括抽出する方式に変更したところ0.96秒に短縮した
  （個別作業計画の「外部コマンドはgit ls-filesの1回のみ」という設計方針は、避けたかった
  forkコスト（1回あたり約0.1秒）より、37,411行に対するbash側の正規表現マッチングの累積コスト
  の方が大きいという実測に反していたため見直した）。grep一括方式は元ファイルの行番号を
  そのまま返すため、上記の行番号ずれの問題も同時に解消される。**外部コマンドの起動回数は
  `git rev-parse`（リポジトリルート特定）・`git ls-files`・`grep`（xargs経由で1〜数回）の
  3種類**であり、当初v1レポートに書いていた「外部コマンドはgit ls-filesの1回のみ」は誤りで
  あった。
- **`git ls-files`が返す削除済み未ステージのファイルを、件数を出さずに無言でスキップして
  いた**（v1）。`skipped_missing`カウンタを追加し、標準エラーのサマリへ出すようにした。
- **除外ディレクトリは実装当初から4つ（`.claude/scripts/test/` `plans/` `reports/`
  `worklog/`）だったが、v1レポートは誤って「3ディレクトリ」と書いていた。** 本レポートで
  正しい件数（4つ）に修正した。

### 対応を見送った指摘

- **相対パス形式のDDR参照（`.claude/docs/ddr/`で始まらない、`ddr/…`や`../docs/ddr/…`等の
  表記）は本スクリプトの対象外のままとした。** 本リポジトリには相対形式の参照が約79件
  存在し（`.claude/docs/README.md`のDDR一覧、`.claude/rules/*.md`のリンク等）、これらは
  検査されない。個別作業計画「やらないこと」で見送りと決定済みの範囲であり、フェーズ3では
  対応しない。ただし「参照切れ0件」という結論の主語が「絶対パス形式に限る」ことは、
  この報告と個別作業計画の両方に明記して誤解を避ける。
- **本スクリプトをhook・CI等の実行契機へ組み込むことは行わない。** 全体作業計画で「毎回自動
  実行する仕組みは作らない」と決定済みであり、手動実行のみの運用とする。誰も実行しなければ
  再発を検知できないという指摘自体は妥当であり、フェーズ4のDDRで実行タイミングの意思決定
  として記録する。
