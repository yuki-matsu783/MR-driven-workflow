ベースブランチ追従確認の差し込み地点と検知方法

結論

1. 前提は崩れていない

「コンフリクトは無いが遅れている」状態を検知する機構は、このリポジトリに1つも無い。

2. 判定は1コマンドで足りる

git rev-list --left-right --count origin/<base>...HEAD で behind・ahead 両方。変更ファイルは3点リーダ必須。

3. merge-base 無しで落ちる

3点diff は fatal・終了コード128。set -euo pipefail 配下ではスクリプトごと停止するため事前判定が必須。

4. resume は fetch しない

そのまま behind を足すと古い参照を見て「遅れていない」と報告する。fetch は新スクリプト側の責務にする。

設計への反映（フェーズ3への申し送り）

  1. .claude/scripts/src/check-base-sync.sh を新設し --base / --head / --no-fetch を受ける。fetch は既定でこのスクリプトが行う。
  2. behind・ahead は rev-list --left-right --count 1回で取る。
  3. 変更ファイルは3点リーダ。その前に merge-base の有無を必ず判定する。
  4. origin/<base> 不在は終了コード1＋復旧コマンド入りメッセージ。
  5. 変更ファイルは50件で切り詰め、全件数と切り詰めフラグを併記（silent truncationにしない）。
  6. isShallow / hasCommonHistory を出力へ含める。
  7. 純粋関数を BASH_SOURCE ガードで分離し .claude/scripts/test/test_check_base_sync.sh から単体テストする。

確かめられなかったこと

  • git bash（MSYS）実機での挙動。本調査は Linux 上。
  • 巨大リポジトリでの所要時間。rev-list --count は履歴長に比例するが未実測。
  • --no-fetch の有無による実測差。git の仕様から述べているだけ。
  • merge-base が shallow 境界の外にある場合の値。このリポジトリでは再現できなかったため、isShallow の出力で設計側から吸収する。
