# 調査結果 — set-headerの無言成功とHANDOFF.mdヘッダ表記の実態

対象issue: [#66](https://github.com/yuki-matsu783/MR-driven-workflow/issues/66)（flow-id 2-6）
個別調査計画: `plans/【調査】set-headerの無言成功とヘッダ表記の実態.md`

## 結論（先に3行）

1. issueの報告どおり、`set-header --pr` は**1件も書き換えずに終了コード0を返す**。原因は
   `cmd_set_header` が一致件数を数えていないことで、`- Draft PR:` 表記はその引き金にすぎない。
2. **同じ「ヘッダ行の位置を決めていない」ことに起因する2件目の欠陥を見つけた**。`- 現在のループ:`
   行の挿入位置判定が、実物のHANDOFF.md（見出しの**下**にヘッダを置く形）と噛み合っておらず、
   `## フロー進捗状況` 見出しの**上**へ離れて挿入される。既存テストのフィクスチャがこの配置を
   持たないため、一度も検出されていなかった。
3. issue #140 は**別issueのまま残す**のが妥当。両者は症状こそ似ているが、#66 は「実装がエラーを
   返し損ねている」不具合、#140 は「インターフェースの意味をどうするか」の設計判断である。

## 調査1: 無言成功の再現

### 再現手順と結果

実物と同じ形のHANDOFF.md（`## フロー進捗状況` 見出しの下にヘッダ行、PR行は `- Draft PR:` 表記）を
作り、`set-header --pr` を実行した。

```bash
bash .claude/scripts/src/update-handoff-progress.sh set-header --pr '#999' --file "$SP/t1.md"
# exit=0
diff "$SP/real-handoff.md" "$SP/t1.md"   # → 差分なし
```

**終了コード0・ファイルは1バイトも変わらない。** issueの報告と一致する。

### 原因（コードの構造）

`cmd_set_header` は全行を走査して該当パターンにマッチした行を置き換えるだけで、**一致件数を
持たない**。ループを抜けた後は無条件に `write_lines_from_array` を呼ぶため、0件でも「書き戻した」
という結果になる。

```bash
for ((i = 0; i < ${#LINES[@]}; i++)); do
  ...
  elif [[ $has_pr -eq 1 && "$line" =~ ^-[[:space:]]PR: ]]; then
    LINES[$i]="- PR: ${pr}"
  ...
done
write_lines_from_array "$file"   # ← 0件でもここへ来る
```

対照的に `cmd_mark_done` / `cmd_mark_skip` / `cmd_add_round` は `matched` を数え、想定数と
食い違えばエラーを出して**書き戻さずに** `return 1` する。`set-header` だけがこの形になっていない。

**したがって `- Draft PR:` 表記は引き金であって原因ではない。** 表記を統一しても、ヘッダ行を
消してしまった・見出しを書き換えた・`--file` で別のファイルを指した、といった場合には同じ無言の
成功が起きる。

## 調査2: ヘッダ行の表記・並び順・位置の実態

`HANDOFF.md` の全履歴断面（このクローンで辿れる50断面）を集計した。squash mergeにより、
マージ済みブランチの途中経過は残っていない点に注意する（issueが挙げたPR #52の
`- Draft PR:` 表記も、この集計には現れない）。

| 観点 | 実態 |
|---|---|
| PR行の表記 | 集計できた32断面はすべて `- PR:`。ただし**値の書式は揃っていない**（`#82 (Draft) https://…` / `#124（https://… ）` / `[#29](https://…)（…`） |
| ヘッダブロックの位置 | **見出しの後: 23断面 / 見出しの前: 9断面 / ヘッダ行なし: 18断面** |
| 並び順 | ヘッダ行を持つ24断面すべてで、先頭は `- issue:` |

**位置が2通りある**ことがこの調査の主な収穫である。

- 見出しの**前**（例: `5973caf`、2026-08-19）: `# HANDOFF` の直後にヘッダ行が並び、その後に
  `## フロー進捗状況` が来る。
- 見出しの**後**（例: `d48b698^`、直近の運用）: `## フロー進捗状況` の直下にヘッダ行が並ぶ。

### 2件目の欠陥: `- 現在のループ:` 行の挿入位置

`set_loop_header_in_lines` は、挿入位置の基準となるヘッダ項目を
**`## フロー進捗状況` 見出しより前にあるものだけ**から探す（`$heading -lt 0` のガード）。
これは「本文中の引用を基準にしない」ための配慮だが、**実物が採っている「見出しの後」配置では
ヘッダ項目が1件も見つからない**ことになり、フォールバックの「見出しの直前へ挿入」が働く。

実物と同じ形のフィクスチャに `mark-done 2-3` を実行した結果:

```
# HANDOFF

- 現在のループ: 2-3〜2-4 の1周目（完了）   ← ここへ入る

## フロー進捗状況

- issue: #117
- ブランチ: `claude/foo`
- Draft PR: #124 https://github.com/o/r/pull/124
- push回数: 3
```

`- 現在のループ:` だけが他のヘッダ項目から切り離される。**終了コードは0で、警告も出ない。**

既存テストがこれを検出できなかったのは、フィクスチャの作りによる。

| フィクスチャ | 見出し | ヘッダ項目 | 通る経路 |
|---|---|---|---|
| `write_fixture`（handoff1〜15） | **無し** | 有り | 「最後のヘッダ項目の直後」 |
| handoff16 | 有り | **無し** | 「見出しの直前」 |
| handoff17 | 無し | 無し | 挿入位置なし（警告） |

**「見出しが有り、かつヘッダ項目も有る」という実物の組み合わせだけが抜けている。**

### ヘッダ項目の正しい表記（本調査が提案する定義）

```
## フロー進捗状況

- issue: #66
- ブランチ: `claude/set-header-silent-failure-p3izl0`
```

- 行頭は `- <項目名>: `（半角ハイフン・半角スペース・項目名・半角コロン・半角スペース）。
- **項目名は上記6つで固定**。`- Draft PR:` のような別名は使わない（Draftかどうかは値の側で書く）。
- **1項目1行**。ヘッダブロックは `## フロー進捗状況` 見出しの直下に置く。
- `- 現在のループ:` / `- 追従監視:` は `- push回数:` の後（この2つは後から増える項目のため）。

## 調査4: issue #140 との関係

### 両者は同じ形か

「呼び出しは成功したように見えるが、ファイルは期待した状態になっていない」という**症状**は同じ
だが、**欠陥の性質は異なる**。

| | #66（`set-header`） | #140（`mark-skip`） |
|---|---|---|
| 何が起きるか | **何も書き換えられていない**のに成功する | **指示どおりに書き換えた**が、結果が表のルールに反する |
| 正しい挙動が決まっているか | **決まっている**（`mark-done` と同じ形にすればよい） | **決まっていない**（issue本文が案A/B/Cを提示して比較検討を求めている） |
| インターフェースへの影響 | 無い（成功していた呼び出しが失敗するようになるだけ） | **有りうる**（案Aは「列挙したものだけを書き換える」という意味を変える） |
| 仕様書の現在の記述 | 触れていない | 「意図した挙動である」と**明記されている**（変更には記述の書き換えが要る） |

### 結論: 別issueのまま残す

理由は3つ。

1. **#140 は設計判断を含み、レビューの単位が違う。** 3案の比較検討と「ループ範囲の一部だけを
   `[-]` にする正当なユースケースがあるか」の確認を要求している。#66（実装がエラーを返し損ねて
   いる不具合）と1つのPRへ混ぜると、レビューで評価軸が混ざる。
   `.claude/skills/issue-mr-flow/SKILL.md`「種別を複数併記する場合／分ける場合」の
   「迷ったら分ける」に沿う。
2. **#140 は仕様書の既存記述の書き換えを伴う。** 「意図した挙動である」という記述をどう改めるかは
   #140 の成果物であり、#66 側で先に触ると #140 の検討材料を消してしまう。
3. **まとめなくても #66 の成果は #140 へ効く。** 下記の方針を仕様書へ1本立てておけば、#140 は
   「`mark-skip` がこの方針をどう満たすか」という形で検討を始められる。

### #66 側で残すもの（#140 への引き渡し）

`.claude/docs/spec/update-handoff-progress.md` へ、スクリプト全体の方針として次を明記する。

> **書き換えを求められた対象が見つからなかった場合、このスクリプトは書き戻さずに非0で終了する。**
> 「呼び出しは成功したが、ファイルは期待した状態になっていない」状態を作らない。

`mark-skip` が作りうる**不整合**（範囲の一部だけが `[-]`）はこの方針の射程外であることも
明記し、#140 で扱うと書く。「無言の失敗を全部まとめて直した」と読めてしまうと、#140 が
対応済みに見えてしまうため。

## 実装方針（フェーズ3への引き渡し）

1. `cmd_set_header`: 指定された項目ごとに一致件数を数え、**0件の項目が1つでもあれば書き戻さずに
   エラー終了**する。エラーメッセージには項目名と期待する行の書式を出す。
   **2件以上一致した項目もエラー**にする（ヘッダ項目は1行という前提が崩れている）。
2. ヘッダ行の探索範囲を「**ヘッダブロック**」へ限定する。ヘッダブロックは
   「ファイル先頭から `## フロー進捗状況` 節の終わり（次の `## ` 見出しの直前）まで」とし、
   見出しが無ければファイル全体とする。見出しの前・後どちらの配置でも拾え、「やったこと」以降の
   引用行は拾わない。
3. `set_loop_header_in_lines`: 同じヘッダブロックの中から最後のヘッダ項目を探し、その直後へ挿入
   する。ヘッダ項目が無ければ**見出しの直後**（空行を挟む）へ挿入する（現状の「見出しの直前」から
   変更する）。どちらの基準も無ければ従来どおり終了コード1を返す。
4. `cleanup-task.sh` の `HANDOFF_TEMPLATE` へヘッダ行の雛形6行を追加する。
5. テストへ「見出しが有り、かつヘッダ項目も有る」実物どおりのフィクスチャを追加する。
