実施した内容と結果

1. Q1: 参照箇所の全列挙と仕分け（14行の仕分け表）

パス言及は20ファイル（.claude/ 10・.gemini/ 10・ルート0）、節名言及は5箇所・4ファイル。重複を統合した仕分け表14行の全行が「直す／直さない／書き換えない（point-in-time）」のいずれかに分類できた（表の全体は正文mdを参照）。

結論 フェーズ3で変更するのは reports.template.html 1本。.gemini/ はflow-id 5-3の再生成で追随（手編集しない）。spec・DDRのpoint-in-time記録は書き換えず、specへの反映はフェーズ4の新規changelogエントリで行う。

2. Q2: 節ごとの維持／移動／改修／新設

節名を参照する3系統（planning.md 280行目・reports/REVIEW-POINTS.md 15-16行目・spec 3101行目）が全て現節名を前提とするため、節名は全維持し、並び順と内部構造だけを変える。新しい節順: ヘッダ帯（結論件数チップ追加）→ 目次 → 重点レビュー依頼（新設） → サマリ（色分け結論カードへ改修）→ 確かめられなかったこと（前半へ移動・一覧化） → 実施条件 → 実施した内容と結果（章ID f1〜・性質チップ・未確認詳細callout）→ 設計への反映 → 想定と異なった点 → 残課題。

結論 受け入れ条件のうち「各行から該当節へリンク」は現行でもコメント指示として存在するが実マークアップの規則が無かった。新テンプレートは結論カードに href="#f1" 形式の実例を持たせ、指示との二重化を防ぐ。

3. Q3: 色トークン設計

性質トークンライトダーク記号・ラベル

結論 --good をアクセント色から分離して新設。緑（--ok）は「決めたこと」box専用として残し、結論の性質には使わない（issueの指定は青。緑青併用は「良かった」の表現が2系統に割れる）。色・記号・ラベル・並び順（問題→注意→良）の4重で判別可能にする。

4. Q4: フェーズごとの読み替え

「重点レビュー依頼」はレビュー往復を前提とする本フローの全フェーズで意味が通る。統括（5-4）のみ「マージ判断で最後に見てほしい点」への読み替えコメントを添える。「確かめられなかったこと」の統括での運用（残存分のみ・水増ししない）は従来どおり。

結論 「フェーズごとの読み替え」コメントは更新のみで維持できる。新設節のためにフローの読み替え構造を壊す必要は無い。
