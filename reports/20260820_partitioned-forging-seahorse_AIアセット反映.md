## 反映した内容

### `.claude/rules/shell-script-style.md`（4件）

| 追加した内容 | 入れた場所 | 実例 |
|---|---|---|
| **数値の桁区切りのような整形は、行全体ではなく「数値と分かっている場所」へ適用する** | `## 文字コード` 節の中、`awk`/`sed` の置換文字列の項の直後 | markdownの表をjqで組み立てたあと行全体へ `sed` をかけ、`claude-3-5-sonnet-20241022` を `claude-3-5-sonnet-20,241,022` へ壊しかけた |
| **`perl -0pi -e "..."` / `sed "..."` をダブルクォートで囲まない** | 既存の「バックスラッシュが1つに潰れることがある」の項へ**1文追加**（独立した項は作らなかった） | 置換文字列の `$(printf ...)` をシェルが先に展開し、意図しないコマンドが走った |
| **`grep` へ `-` で始まるパターンを渡すときは `--` を置く** | `## JSON操作` 節の `jq --args` の `--` の項の直後 | `grep -cF '- 使用モデル:'` が `grep: unknown option --` で失敗した |
| **Windowsネイティブの `jq` へプロセス置換 `<(...)` のパスを渡せない** | `## git bashのパス変換の落とし穴` 節の中、`MSYS_NO_PATHCONV` と `jq` の項の直後 | `jq -s -c '...' <(jq -c . session2.jsonl)` が `Could not open file /proc/48730/fd/63` で失敗した（フェーズ2。worklog push3に「フェーズ4で検討」と明記していた項目） |

`grep` の項を `## JSON操作` へ置いたのは節名と噛み合わないが、**原因も対処も `jq --args` と
同じ（`--` を置く）**ため隣接させた。節をまたいだ相互参照より、両方を一度に思い出せる形を採った。

プロセス置換の項には、**「標準入力へ繋ぐ `jq ... < <(...)` は問題なく動く」**という但し書きを
添えた。パス名を渡す場合だけの制約なので、これを書かないと過剰に避けることになる。

### `.claude/skills/resolve-conflict/SKILL.md`（2件）

いずれも Step 5（検証）へ小見出しとして追加した。**類型に依存せず必ず通る位置**を選んでいる。

1. **「1つでも落ちたらコミットしない」の例外: defaultブランチ側に既存の失敗がある場合。**
   Step 5 の原則をそのまま適用するとマージを永久にコミットできない状況が実在した
   （`main` 上で `test_post_issue_create_notice.sh` が `failures=1`）。切り分け（`origin/<base>`
   単体で再現するか）・続行可否・**報告義務**の3点を書いた。「黙って通さない」ことを明記した
   のは、次に見る人がその失敗をマージが持ち込んだものだと誤解するため。
2. **自動マージされて入った行も確認する。** `main` マージで、競合しなかったHTMLコメント
   （別タスクの記述）が `HANDOFF.md` へ入り込んだ。gitが競合と見なさない変更は `git status`
   にも `git diff --check` にも出ないため、`git diff HEAD -- <path>` で通しで読む必要がある。

### `REVIEW-POINTS.md`（ルート直下・1件）

**`.claude/` 配下ではなくルート直下へ置いた。** 計画では置き場所を「実施時に判断」としていたが、
内容がリポジトリ全体に効くため（`.claude/rules/directory-structure.md`「一般的な観点ほど上位へ
置き、下位で重複して書かない」）。

「## 変えないはずのものが変わっていないか」として2項目を追加した。

- 既存の出力・挙動を変えないはずのリファクタで、**変えていないことを機械的に確かめているか**。
  「テストを足した」だけでは切り出し時点の劣化を検出できない（新しいテストは変更後の実装に
  対して書かれるため）。
- **検証コマンドが、異常があるときに本当に検出できるか。** 「異常が無ければ何も出ない」形の
  検証は、パターンが実データに合っていないと常に成功する。

2つ目は、フェーズ4の敵対的レビューで最も多かった指摘の型であり、**さらに設計反映の実施中に
2件（採番チェック・`--query`）が実際に見つかった**。観点表へ入れるだけの再現性がある。

## 別issueの起票を提案する項目（**AIからは起票しない**）

**`get_branch_work_files` の出力が、ブランチ上で改名されたファイルについて
`"旧パス" -> "新パス"` という1行を返す。** このため出力をパス一覧として機械的に扱う処理は壊れる
（issue #97 の作業中に2回踏み、2回とも目視で回避した）。

- これは**注意書きで回避させるべきものではなく、`Provider.sh` 側の出力仕様の粗さ**である。
  ルールへ「気をつける」と書いても、次にこの関数を使う人が同じ場所で止まる。
- 本MRのスコープ外のため、**ユーザーへ別issueの起票を提案するに留める**
  （`.claude/skills/issue-create/SKILL.md`「してはいけないこと」: どのissueにいつ着手するかを
  決めるのは人間である）。
