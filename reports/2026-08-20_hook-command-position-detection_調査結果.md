# 調査結果: hook検知の誤検知類型と判定方式

- issue: [#53](https://github.com/yuki-matsu783/MR-driven-workflow/issues/53)
- 個別調査計画: `plans/【調査】hook検知の誤検知類型と判定方式.md`
- **測定環境: Claude Code on the web のリモート実行環境（Linux 6.18.5 / bash 5.x）／2026-08-20。**
  このリポジトリが常用環境として前提とする Windows / git bash では測っていない
  （`.claude/rules/shell-script-style.md`「前提・保存形式」）。fork回数に依存する結論は、
  git bashでは**絶対値が大きく変わる**（同ファイル「外部プロセス起動のコスト」が
  約95ms/回と記録している）。

## 1. 現行の検知の実態

### 検知箇所

| hook | 検知 | `.claude/settings.json` の `if` |
|---|---|---|
| `block-direct-git-commit.sh` | `grep -qiE 'git[[:space:]]+commit'` | **無し**（`matcher: "Bash\|PowerShell"` のみ） |
| `post-push-usage-report.sh` | `grep -qiE 'git[[:space:]]+push'` | `Bash(git push*)` / `PowerShell(git push*)` |
| `post-push-compact-prompt.sh` | 同上 | 同上 |
| `post-issue-create-notice.sh` | `[[ "$command" == *create-issue.sh* ]]` | 無し |

**コミット側だけ `if` を経由しない**という非対称が、コード上の事実として確認できた
（issue #53 のコメントで申し送られていたとおり）。したがってコミット側は、どんな文章が
コマンド文字列に含まれていても必ずスクリプトまで届き、そこで部分一致に当たれば発火する。
push側は `if` が1段目のフィルタとして効くため、スクリプト内の再チェックまで届く入力が
そもそも少ない。

### 実測: 20ケースの内訳（変更前）

hookへ直接JSONを標準入力から流し、終了コード（2=ブロック / 0=素通り）を見た。

| 期待 | ケース数 | 期待どおり | 外れ |
|---|---|---|---|
| ブロックすべき（B01〜B07） | 7 | 6 | **1**（B06） |
| ブロックすべきでない（A01〜A08） | 8 | 2 | **6**（A01〜A06） |
| 素通りさせたくない（N01〜N05） | 5 | 5 | 0 |

外れた7件の内訳:

| id | 入力 | 変更前 |
|---|---|---|
| B06 | `git -C /repo commit -m "fix"` | **素通り**（`git` と `commit` の間にオプションが挟まると部分一致に当たらない） |
| A01 | ヒアドキュメント本文に該当語 | ブロック |
| A02 | `--message "…git commit…"` | ブロック |
| A03 | `echo "…git commit…"`（日本語の地の文） | ブロック |
| A04 | `grep -rn 'git commit' .claude/` | ブロック |
| A05 | 行頭コメントに該当語 | ブロック |
| A06 | 行末コメントに該当語 | ブロック |

**この調査の最中にも2回、実際にブロックを踏んだ。** どちらも、この機構を日本語で説明する
文章（1回目はデバッグ用スクリプトのコメント、2回目は修正パッチの説明コメント）に該当語が
含まれていただけである。issue本文の「ルールを知っていても、hookの仕組み自体を説明する
文章を書く場面では踏みやすい」が、調査中にそのまま再現した形になる。

### fork回数

`block-direct-git-commit.sh` は1回の起動あたり、おおよそ次のプロセスを起こす。

- `raw="$(cat)"` — コマンド置換 + `cat`
- `jq -c '.'` / `jq -r '.tool_name'` / `jq -r '.tool_input.command'` — 3回、各々コマンド置換とパイプを伴う
- `printf '%s' "$command" | grep -qiE …` — パイプ

Linuxでの実測は50回で865ms（17.3ms/回。うちbash起動そのものが2.4ms/回）。
**このhookは `if` を持たないため、Bash/PowerShellツールの呼び出しごとに必ずこのコストがかかる。**

## 2. 誤検知・検知漏れの類型

### 誤検知（ブロックされるべきでないのにブロックされる）

いずれも「該当語が**データ**として現れている」類型である。

1. ヒアドキュメント本文（`<<'EOF' … EOF`）
2. クォートされた文字列リテラル（`"…"` / `'…'`）
3. コメント（行頭・行末とも）
4. 単語の一部（`git commit` ではなく `git_commit` / `git-commit` は現行でも素通りする）

### 検知漏れ（実行されるのに検知されない）

1. `git` とサブコマンドの間にグローバルオプションが挟まる（`git -C dir commit` / `git -c k=v commit`）
2. コマンドをラップしたスクリプト（`bash deploy.sh`）— コマンド文字列に語が現れないため
   **原理的に検知できない**（既存の仕様で受け入れ済み。`.claude/docs/spec/issue-mr-workflow.md`）

### 新方式で**新たに**素通りしうる構造（実装前に洗い出した）

「文字列リテラルの中身がコードとして実行される」構造。クォート内を判定対象から外すと、
ここがそのまま抜け道になる。

| 構造 | 例 |
|---|---|
| シェルへコードを文字列で渡す | `bash -c "…"` / `sh -c "…"` / `eval "…"` |
| ダブルクォート内のコマンド置換 | `echo "$(…)"` / ``echo "`…`"`` |
| 引数をコマンドとして実行する | `xargs …` / `find … -exec … \;` |

**この洗い出しが本調査でいちばん効いた部分である。** 「クォートとヒアドキュメントを除外する」
だけを実装していたら、上の3類型はすべて素通りしていた（実測でも変更前は5件すべてブロック
されていたため、素通りは純粋な機能後退になる）。

## 3. 判定方式の候補比較

| | (a) 行分割→行頭のみ | (b) セパレータ分割→各部分の先頭 | (c) クォート追跡＋正規化 |
|---|---|---|---|
| 実装量 | 小 | 小 | 中（約280行） |
| B02（`cd src && …`） | **外す**（行頭ではない） | 通る | 通る |
| A02（クォート内） | 通る | 通る | 通る |
| A03（`echo "a; git commit"` 型） | 通る | **外す**（クォート内の `;` で割れる） | 通る |
| N03（`"$( … )"`） | 外す | 外す | 通る |
| 判定の説明しやすさ | 高 | 中 | 中 |

**(c) を採用した。** (a) は受け入れ条件が名指しする B02 を落とすため候補にならない。(b) は
実装が軽いが、クォート内にシェルのセパレータが現れた瞬間に誤検知へ戻る（「日本語の地の文」は
自由文なので、`;` や `&&` が混ざらない保証が無い）。(c) だけが、受け入れ条件の3グループを
同時に満たせる。

### (c) の設計

1. **正規化**: クォート・コメント・ヒアドキュメント本文を、コマンド位置になりえない
   プレースホルダ `_` へ潰す。**ダブルクォート内の `$( )` と `` ` `` だけはコードとして
   展開し直す**（上の N03 対策）。
2. **走査**: 正規化後の文字列をトークンへ割り、コマンド位置にある `git` の直後の
   **非オプショントークン**が目的のサブコマンドかを見る（`-c` / `-C` は値を1つ取るので2つ飛ばす）。
   これで B06 の検知漏れも同時に埋まる。
3. **保守的なフォールバック**: 位置判定で一致しなかった場合でも、コード文字列を受け取りうる
   実行系がコマンド位置にあり、かつ**従来の部分一致が成立する**なら、ブロック側へ倒す。

フォールバックの対象語は2段に分けた。

| 区分 | 語 | 理由 |
|---|---|---|
| 無条件 | `eval` `xargs` `find` `ssh` `watch` `flock` `parallel` | 引数そのものがコードとして実行される |
| コード指定オプション（`-c` `-e` `-E` `--command` 等）と併用時のみ | `bash` `sh` `zsh` `python` `perl` `ruby` `node` `pwsh` 等 | **`bash` を無条件に含めると A02 が壊れる。** このリポジトリの通常の呼び出し（`bash .claude/scripts/src/create-commit.sh --message "…"`）が全部フォールバック対象になってしまう |

**この2段分けは、実装中に A02 が落ちて初めて気づいた。** 当初は `bash` を無条件のフォールバック対象
リストに入れており、受け入れ条件のケースがそのまま失敗した。

## 4. CRの影響（issue #94 からの申し送りへの回答）

**結論: `tr -d '\r'` は不要。ただし理由は issue #94 のときとは違う。**

- issue #94 の理由は「`grep -qiE 'git[[:space:]]+commit'` は `[[:space:]]` がCRにもマッチする
  ので判定が変わらない」だった。位置ベースではこの理由は成り立たない。
- 新方式では、**判定側でCRを空白として扱う**ことで同じ結論に至る。具体的には
  (1) トークン分割の `IFS` に `\r` を含める、(2) ヒアドキュメントの区切り行を比較する前に
  末尾の `\r` を落とす、の2点。**どちらもbash組み込みで、forkは増えない。**
- 検証: `.claude/rules/shell-script-style.md`「テスト」節のスタブ `jq`（最終行以外の行末へ
  CRを付ける）をPATHの先頭へ置いて20ケースを再実測し、**CRなしのときと1件も結果が
  変わらないこと**を確認した。

CRを扱わないと具体的に何が壊れるかも確認した。`cd src && git commit -m x\r\nls` の場合、
CRを空白として扱わないとトークンが `commit\r` になり、サブコマンド名の一致が外れて
**素通りする**（最も避けたい方向の失敗）。単体テストにこのケースを入れてある。

## 5. 性能

判定部分だけを取り出し、**同一セッション内で**空関数をベースラインに旧実装と新実装を比較した
（`.claude/rules/shell-script-style.md`「テスト」の計測手順）。200回あたり。

| 入力 | 空関数 | 旧（`printf \| grep`） | 新（純粋bash） |
|---|---|---|---|
| 短い1行（31バイト） | 4ms | 432ms | **98ms** |
| ヒアドキュメント（18225バイト） | 23ms | 480ms | 1450ms |

- **常用ケース（短いコマンド）では新実装が約4.5倍速い**（2.14ms/回 → 0.47ms/回）。
  hookが起動する大半はこちらである。
- **大きなヒアドキュメントでは新実装が約3倍遅い**（2.4ms/回 → 7.1ms/回）。
  ただし絶対値は7ms、かつ**Linuxでの比較**である。git bashでは旧実装が2プロセス
  （約190ms）を必ず起こすのに対し、新実装は0プロセスなので、この環境では大きな入力でも
  新実装のほうが速い見込みである（未実測）。
- 入力サイズに対する伸びは線形の範囲に収まる（9KB=4ms / 18KB=7ms / 36KB=14ms /
  73KB=13ms。最後の1点は計測ノイズ）。**二乗にならないこと**が要点で、これは
  1文字ずつの `${s:i:1}` を避け、(1) 行配列へ一度で分割し、(2) 行内は「次の関心文字まで
  一気に読み飛ばす」形にしたことによる。

### 1文字ずつの走査を避けた理由（実測）

`${s:i:1}` による走査は、**ロケールに関係なく**文字列長の二乗で伸びた。

| 入力 | マルチバイトロケール | `LC_ALL=C` |
|---|---|---|
| 1800バイト | 15ms | 16ms |
| 5400バイト | 78ms | 76ms |
| 10800バイト | 258ms | 261ms |

当初は「マルチバイトロケールだから遅いのだろう、`LC_ALL=C` にすれば直る」と見込んでいたが、
**実測では効果が無かった**。バイト単位にしても `${s:i:1}` は先頭からの走査を伴うためである。
この見込み違いを実装前に潰せたことが、この調査の実利のひとつである。

## 6. hook全体の所要（変更前後）

`block-direct-git-commit.sh` を、該当語を含まない通常のコマンドで50回起動した実測。

| | 50回 | 1回あたり |
|---|---|---|
| 空スクリプト（bash起動のみ） | 118ms | 2.4ms |
| 変更前 | 865ms | 17.3ms |
| 変更後 | 833ms | 16.7ms |

差が小さいのは、**残りのコストがjqの3回呼び出しに支配されている**ためである。判定部分の
改善（fork 2つの削減）はこの中に埋もれている。

**jq呼び出しを1回へまとめる余地があるが、本issueでは行わない。** 誤検知の解消とは別の
関心事（性能）であり、`jq -r` の出力を1回で受けて `tool_name` と `command` に割る処理には
「commandが空のとき1行しか返らない」という境界があって、レビュー面を混ぜたくないため。
**別issueとして起票するのが妥当である**（git bashでは 3回×約95ms＝約285ms/回の削減になる
見込みで、効果は本issueの改善より大きい）。

## 7. 設計への反映

| 調査結果 | 設計への反映 |
|---|---|
| 誤検知は「該当語がデータとして現れる」4類型 | 正規化でクォート・コメント・ヒアドキュメント本文を潰す |
| クォートを外すと `bash -c` / `eval` / `$( )` / `xargs` / `find` が素通りする | ダブルクォート内の `$( )` `` ` `` はコードとして残す。それ以外は保守的フォールバックで従来どおりブロック |
| `bash` を無条件のフォールバック対象にすると A02 が壊れる | コード指定オプションと併用時のみ対象にする |
| `git -C dir commit` が現行では素通り | `git` の直後の非オプショントークンで判定する |
| 位置ベースではCRが判定を変える | トークン分割の `IFS` と区切り行の比較でCRを吸収する（forkを増やさない） |
| `${s:i:1}` は二乗、`LC_ALL=C` でも直らない | 行配列＋チャンク読み飛ばしで線形にする |
| コミット側hookは `if` を経由せず必ず走る | 判定を純粋bash化してforkを2つ減らす |
| push側hookは `if` が1段目のフィルタ | 同じ判定を適用するが、**`if` 自体は緩めない**（発火が増える方向の変更で、本issueとは向きが逆） |

## 8. 確かめられなかったこと

- **Windows / git bash 実機での性能**。fork回数に依存する結論（「常用ケースで速くなる」
  「大きな入力でも git bash では速い見込み」）は、この環境では検証できていない。
  fork回数そのもの（旧2 → 新0）はコードから確定するが、**所要時間の比は未実測である**。
- **`.claude/settings.json` の `if` フィルタの照合規則**。issue #47 が「前方一致か部分一致か」で
  両論併記のまま残しており、本調査でも切り分けていない（本issueの対象はhookスクリプト内の
  判定であり、`if` の挙動ではない）。
- **`post-issue-create-notice.sh` の部分一致**（`*create-issue.sh*`）。同じclassの誤検知を
  持つが、issue #53 が名指ししていないため対象外とした。`create-issue.sh` という語が
  地の文に現れる場面は「この機構を説明する文章」に限られ、頻度はコミット側より低い。
