結論

コピーの失敗が成功として報告される経路を3つ塞いだ。計画では2つ （place_real_copy と呼び出し側）を想定していたが、実装中に同じ類型がもう1つ 見つかった（sync_real_copy の pwd -P 失敗が「リンクとみなします」という 成功で終わる）。

回帰テスト 5つの表明を追加し、5つすべてが修正前の実装で実際に落ちることを確認してから書いた。 単体テストは 18ファイル / passed=1147 failures=0。

直した3箇所

1. place_real_copy（受け入れ条件7のフォールバック経路）

# 前

  mkdir -p "$link_path"
  cp -R "${target_path}/." "${link_path}/"     # 失敗しても止まらない
  cat <<MSG

run_or_fail <説明> <コマンド...> を新設し（install-to-project.sh の 同名関数と同じ形）、mkdir と cp の終了コードを検査して非0で戻すようにした。 成功メッセージより先に、失敗しうる操作を済ませて検査する順序へ変えている。

3. sync_real_copy のパス解決（計画に無かった。実装中に見つけた）

if [ "$src_real" = "$dst_real" ]; then
  printf 'skip（.claude/ と同じ実体を指しています。リンクとみなします）: %s\n' "$dst"

より悪い形 cd が失敗すると両方が空文字列になり、空同士は等しいので 「リンクとみなします」と表示して成功で戻る。同じ「失敗が成功として報告される」類型で、 しかも「安全のための二重の確認」として置かれた行が誤動作する。 どちらかが空なら明示的に失敗させるようにした。

なぜ set -e では止まらないのか

main は各対象を setup_target "$t" || fail=1 という条件式の中で 呼ぶ（1つ失敗しても残りを試すため）。bashはこの評価中、set -e の 「失敗したら即座に終了する」動作を呼ばれた関数の内部にまで及んで一時停止させる （.claude/rules/shell-script-style.md「bashでのtry/catch相当の書き方」）。

したがって cp / mkdir / 代入の失敗は、明示的に終了コードを検査しない 限り伝わらない。|| fail=1 という呼び方自体は意図どおりなので変えず、内部の検査で 対処した（この理由を run_or_fail の直上のコメントへ残した）。

テストを書く過程で踏んだ落とし穴

表明ごとに新しい木を使う必要があった。 最初は1つの木を使い回していたが、1回実行すると .gemini/<name> が（中身は空のまま）出来上がるため、2回目以降は absent ではなく real 経路に入る。その結果、

  • 表明2（「作成しました を出さない」）が修正前でも通ってしまっていた。 2回目は「作成しました」ではなく「更新します」を出すためである。
気づけた理由 「修正前で落ちること」を確認していなければ、この空振りに気づけなかった。 フェーズ3の敵対的レビュー2回目で「自分の書いた回帰テストが blocker を検出できていなかった」 という失敗を踏んでおり、その手順（直す前の実装へ当てて落ちることを見る）がここで効いた。
