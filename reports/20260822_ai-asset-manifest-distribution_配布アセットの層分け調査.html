調査2: REVIEW-POINTS.md の層

現状の実測（重大な発見）

4件のうち配布されているのは1件だけ .claude/REVIEW-POINTS.md しか配られておらず、ルート・plans/・reports/ の3件は未配布。 つまり配布先で敵対的レビューを回すと、4件中1件の観点表しか適用されない。

結論

ファイル層所有者
<dir>/REVIEW-POINTS.mdcore本家。更新は再適用で配布先へ届く
<dir>/REVIEW-POINTS.local.mdseed配布先。空の雛形を1回だけ配置し、本家は二度と触らない
  • 却下案「seed 単独」: 本家が観点を追加しても配布先へ永久に届かない。
  • 却下案「core 単独」: 配布先が育てた観点が再適用で消える。
  • 却下案「merge で散文をマージ」: 行の重複・見出しの重複を機械的に解けない。

波及先（1箇所ではない）

成立条件 cleanup-task.sh の KEEP_BASENAMES はベース名の完全一致で残す対象を決めており、 test_cleanup_task.sh がその完全一致を明示的に表明している。このまま plans/REVIEW-POINTS.local.md を置くと flow-id 5-4 で毎タスク削除される。

波及先は cleanup-task.sh / collect-review-points.sh とその単体テスト2本、 markdown-frontmatter.md / adversarial-review.md / docs-workflow.md / directory-structure.md の記述。

調査3: 層分け定義の置き場所と形式

案判定理由
A: 定義ファイル1枚採用全パスを1箇所で見渡せ、網羅性を機械的に検査できる
B: 各ファイルがマーカーで持つ却下JSON（.mrworkflow.json settings.json）にコメントを書けない。空ファイル・将来の画像にも書けない
C: ディレクトリ単位の規約却下例外（worklog/TEMPLATE.md だけ core、skills/ のうち1つだけ exclude）を表現できない
案Aの弱点は検査で塞ぐ どの層にも exclude にも該当しないパスを列挙して終了コード1を返す。 exclude を暗黙の既定値にしない——「定義に無い＝配らない」にすると、 この検査が常に成功する（＝異常が無ければ何も出ない検証になる）。

.claude/settings.json を merge にする際の分割線

キー所有者根拠
hooks本家配布したhookスクリプトの登録そのもの
permissions.deny の2行本家コミットをスキル経由へ強制する多重防御の一部（DDR i0000-09）
それ以外 / plansDirectory / autoCompactWindow配布先権限モード・compact窓は配布先の好み

したがって merge の粒度は「トップレベルのキー単位」では足りず、「キーのパス単位」が要る。

調査4: manifestの記録項目

記録するもの

配布先の .claude/.asset-manifest.json へ、本家のコミットSHA・版・URLと、 ファイルごとの層・sha256（merge は行／キーの指紋）を記録する。local は記録しない （記録すると「配布した」と誤読される）。

sha256 の算出（改行コード）

LFへ正規化してから取る Windows で core.autocrlf=true の配布先では作業ツリーがCRLFになり、正規化しないと 全テキストファイルが「配布先が変更した」と誤検知される。 Windows実機での確認はこの環境（Linuxコンテナ）ではできないため、未確認事項として残す。

dirty の定義（受け入れ条件6）

候補判定理由
追跡ファイルの変更・ステージ済み変更含めるコミットSHAとワークツリーが食い違うと manifest のSHAが嘘になる
未追跡ファイル含める（配布対象パス配下のみ）未追跡の新規スクリプトは「配るつもりのファイル」でありうる
無視ファイル含めないindex.jsonl usage/ は常に存在し、含めると永久に適用できない
plans/ worklog/ reports/含めないlocal 層で配布対象外

--allow-dirty を持たせる（結合テストが実プロセスとして起動するため逃げ道が要る）。ただし manifest の source.commit へ -dirty の接尾辞を付け、通常の配布手順には書かない。

調査6: AGENTS.md の分割線

判定（「ルール」節の9項目）

9項目すべてが本家所有である。項目9（ドキュメント探索は frontmatterインデックスの横断検索を第一手段にする）は 「ルール」節で最も長い項目で、doc-search スキルの入口そのものなので、 切り出しから落とすと配布先で全文探索が既定に戻る。

切り出し後の形

  • 切り出し先: .claude/rules/agent-common.md（type: rule）。
  • AGENTS.md は「共通ルールのimport＋プロジェクト概要＋開発・実行」の3節だけになり、seed 層に置ける。
  • CLAUDE.md / GEMINI.md は @./AGENTS.md を保つ（層は core）。

seed の雛形にする際の注意

プロジェクト概要は本家固有の本文を持つ seed は「配置後は配布先が所有する初期値」なので、このままだと どの配布先の AGENTS.md も本家を名乗った状態から始まる。汎用の文言へ差し替える。

@import の解決（実測と未確認）

  • 実測: .claude/rules/*.md の7件すべてが project instructions として読み込まれた。 alwaysApply: true を持つのは3件だけなので、読み込みは alwaysApply の有無に依存していない。
  • 未確認: Gemini CLI 側の挙動と、相対パスで書いた @ import の解決基準。 安全側に倒し、AGENTS.md からの @ import も併せて張る。
