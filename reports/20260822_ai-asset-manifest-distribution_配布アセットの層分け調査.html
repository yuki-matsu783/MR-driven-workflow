受け入れ条件2と8の衝突を、層を増やさずに解消する

.gemini/{docs,…} は local（インストーラは触らない）のままにし、受け入れ条件8は setup-gemini-links.sh が満たす。インストーラは適用の最後にそれを呼び出すだけ。同スクリプトには (1) 実体コピーへのフォールバック（条件7）、(2) 実体ディレクトリなら中身を最新へ入れ替える（条件8）の2点を足す。リンクと実体の判別は [ -L ] では足りない（NTFSジャンクションはディレクトリに見える）。Windows実機でしか確認できない。

local 層は .gitignore のパターンから導く（実測で必要性を確認）

調査3: 層分け定義の置き場所と形式

案判定理由
A: 定義ファイル1枚採用全パスを1箇所で見渡せ、網羅性を機械的に検査できる
B: 各ファイルがマーカーで持つ却下JSON（.mrworkflow.json・settings.json）にコメントを書けない。空ファイル・将来の画像にも書けない
C: ディレクトリ単位の規約却下例外（worklog/TEMPLATE.md だけ core、skills のうち1つだけ exclude）を表現できない

案Aの弱点（足し忘れが無言で漏れる）は検査で塞ぐ

check-dist-coverage.sh（仮）が分母168と同じ範囲を定義ファイルへ突き合わせ、どの層にも exclude にも該当しないパスを列挙して終了コード1を返す。exclude を暗黙の既定値にしない——「定義に無い＝配らない」にすると、この検査が常に成功する。

.claude/settings.json の分割線

hooks と permissions.deny の2行（コミット強制の多重防御・DDR i0000-09）は本家所有、permissions のそれ以外・plansDirectory・autoCompactWindow は配布先所有。merge の粒度は「トップレベルのキー単位」では足りず「キーのパス単位」が要る。

調査4: manifest の記録項目

層 記録するか 内容と理由
coreするsha256。再適用時に配布先の変更を検出して警告（条件4）
seedするsha256 ＋ placed（配置したか／既に在ったので触らなかったか）。placed:false は以後 sha256 を比較しない
mergeするファイル全体ではなく配った行の指紋。配布後は「本家の行＋配布先の行」になり全体の sha256 は必ず食い違う
local / excludeしない配布していない。書くと「配布した」と誤読される

sha256 は LF 正規化してから取る

Windows で core.autocrlf=true の配布先は作業ツリーが CRLF になり、正規化しないと全テキストファイルが「配布先が変更した」と誤検知される。Windows 実機での確認はこの環境ではできず、未確認事項として新方式の spec へ記載する。

dirty は「配布対象パスに限定」＋ --allow-dirty

追跡ファイルの変更と配布対象配下の未追跡ファイルは含める。無視ファイル（usage/ .claude/state/ index.jsonl は常に存在する）と plans/ worklog/ reports/ のタスク単位ファイルは含めない。フェーズ3の実装中は本家が常に dirty で結合テストが流せなくなるため逃げ道を持たせ、source.commit に -dirty 接尾辞を付けて痕跡を残す。

調査6: AGENTS.md の分割線

「ルール」節は9項目（awk で実測）。9項目すべてが本家所有で、.claude/rules/agent-common.md へ切り出す。9項目目は「ドキュメント探索は frontmatterインデックスの横断検索を第一手段にする」（doc-search スキル、issue #38）で、節で最も長い項目のため落とすと配布先で全文探索が既定に戻る。

seed の雛形にする際の注意

## 開発・実行 は TODO コメントのみだが、## プロジェクト概要 には本家固有の本文が3行ある（「このリポジトリは……のテンプレートです」）。そのまま seed にするとどの配布先も本家を名乗った状態から始まる。汎用の文言へ差し替えることがフェーズ3の作業項目。

@import の解決（実測と未確認）

実測: .claude/rules/*.md の7件すべてが project instructions として読み込まれた。frontmatter に alwaysApply: true を持つのは3件だけなので、読み込みは alwaysApply に依存していない。
未確認: Gemini CLI 側の挙動と、AGENTS.md からの相対 @ import の解決基準。安全側に倒して import も併せて張る。

build/ をどうするか決めて書く

build/ は .skill のビルド成果物の置き場としてのみ存在している。ビルド工程が無くなるので、削除するのか将来の別用途のために残すのかを決める（決めずに放置すると、次の作業者には漏れと区別できない）。とくに directory-structure.md はセッションごとに読み込まれるルールなので、存在しない工程の記述が残り続ける。

.gitattributes の読み出し元の移設は仕様変更を伴う

現行は ${ASSETS_DIR}/.gitattributes（install-to-project.sh 294行目）。新方式では本家のワークツリーを直接読む。あわせてマーカーが1行も見つからない場合を「警告」から「失敗」へ変えるが、現行 spec（distribution-assets.md 111〜112行目）は「件数付きの警告を出す」と明文化しているため、フェーズ4でその明文も更新する。
.gitignore も同じマーカー方式へ揃えると、欠陥3（配る行が実状態と不一致）が構造的に解消する。

  1. 1. exclude カテゴリの新設 — 承認
