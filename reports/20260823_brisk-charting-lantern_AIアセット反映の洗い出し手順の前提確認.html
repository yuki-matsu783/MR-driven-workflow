Q2. スキップ条件は洗い出し手順のどの段階か

現行の条件文は「反映するものが無いと確認できた場合」で、何をもって「確認できた」とするかが 書かれていない。これが issue #155 が「要求だけがあり、それに応える手順が無い」と述べている状態で ある。

新設する手順を「手順1: 起点の列挙 → 手順2: 4類型への分類 → 手順3: 証拠集め（(a) のみ）→ 手順4: 反映先の形態の決定」と置くと、AIアセット部分の判定は次のように言い直せる。

手順1と手順2まで実施し、4類型のいずれにも分類される項目が0件だったとき。
  • 手順3（証拠集め）まで進む必要はない。 証拠が要るのは (a) だけで、しかも「反映するか否か」 ではなく「(a) として反映してよいか」を決めるためのものだからである。手順2で0件なら手順3の 入力自体が無い。
  • 手順4も同様。 反映先を選ぶ対象が無い。

この言い直しが効くのはAIアセットの1系統だけである

現行のスキップ条件は「spec/ddr・AIアセット・実装コード/テストコードのいずれにも反映する ものが無い」という3系統の連言であり、新設する手順が扱うのはそのうち1系統（AIアセット）に すぎない。 節名も「AIアセット反映の対象の洗い出し」であり、4類型もAIアセットの不備の 分類である。

したがって、スキップ条件全体を「手順1〜2で分類結果が0件」へ置き換えてはいけない。置き換えると 「spec/ddrへ反映すべきDDRが1件あるのに、AIアセットの4類型が0件だからフェーズ4をスキップして よい」と読める状態になり、フェーズ4の必須通過という設計そのものが後退する。

結論: 接続の文言は、3系統の連言を保ったままAIアセットの項だけを手順の番号で言い直す。

spec/ddr・実装コード/テストコードに反映するものが無く、かつAIアセット側は洗い出し手順の 手順1〜2まで実施して分類結果が0件だったとき。

「無いと確認できた」という主観的な表現が消えるのはAIアセットの項だけである。残る2系統 （spec/ddr・実装コード/テストコード）の判定手順は、この issue の範囲外として据え置く （issue #155 が対象にしているのは flow-id 4-1・4-6 のAIアセット反映である）。

matched=0 だけを打ち切り条件にすると、本文には罠が明記されているのにfrontmatterに語が無い DDR/specを「存在しない」と判定する。 その結果 (a)「アセットが無かった」として重複したアセットを 新設し、この手順が減らそうとしている (d)「あったのに辿り着けない」を手順自身が生む。AGENTS.md も「本文中の特定の文字列を探すときは grep/rg」と切り分けている。

その他

  • 絞り込みは --type / --tag / --keyword / --path / --text / --since / --until の 7つ（--help の「絞り込み」節）。証拠集めでは --text <罠の語> と --type ddr の 組み合わせが実用的で、--since は「その罠に触れた作業がいつのものか」を絞るのに使える。
  • --format json をパイプの途中で切ってはいけない。 整形済みJSON配列なので先頭3行は [ / { / concept_id の行だけになり、確かめたい項目が1つも出ない。スクリプト側も SIGPIPEで終了コード141になる。

結論: 打ち切り条件として書けるが、doc-search 単独では足りない。

doc-search で matched=0、かつ grep -rn <語> .claude/docs .claude/rules も0件なら 痕跡なしと判断して次の段階へ進む。DDRを証拠に使うときは、--format detail に出ない status を --format jsonl かファイル本体で確認する。

Q8. 削除・統合したときに配布経路で何が起きるか

.claude/docs/spec/distribution-assets.md 89-92行目:

据え置きには実害があることを承知して選ぶ。（…）とくに改名・削除を伴う回は、 install-to-project.sh が上流で消えたファイルを配布先から削除しない（コピーのみ）ため、 配布先に旧パスが残ったことに気づく手掛かりが版にも無くなる。

実装でも確認した。 資産の配布は cp -f のみである。

$ grep -n 'cp \|rm \|--delete' .claude/skills/apply-mr-workflow-to-project/scripts/install-to-project.sh
105:      cp -f "${src}" "${dest}"
108:      cp -f "${src}" "${dest}"
113:      cp -f "${dest}" "${backup}"
116:      cp -f "${src}" "${dest}"
121:      cp -f "${src}" "${dest}"
199:  rm -f "${DEST_DIR}/.claude/rules/go-applications.md" \

唯一の rm -f（199行目）は非Goプロジェクトへ配布するときにGo用ルールを消す特例であり、「上流で消えたファイルを追随して消す」処理ではない。

壊れ方: アセットAをアセットBへ統合してAを削除したMRを配布先へ適用すると、配布先には AとBが両方残る。読み手（次のセッションのAI）は矛盾する2つの記述を読むことになり、本手順が減らそうとしている (d)「あったのに辿り着けない」を、配布先で自ら増やす。

版を上げても実害は打ち消せない

当初「打ち消しの手段は版を上げること」と結論しかけたが、これは誤りである。install-to-project.sh は .claude/VERSION を always-overwrite の対象として単に上書きコピー するだけで（実測）、版の差分に応じて配布先のファイルを消す処理も、差分を通知する処理も持たない。

$ sed -n '69,71p' .claude/skills/apply-mr-workflow-to-project/scripts/install-to-project.sh
declare -a ALWAYS_OVERWRITE_RELPATHS=(
  ".claude/VERSION"
)

版を上げても、配布先にはAとBが残り続ける。 得られるのは「配布先が差に気づく手掛かり （追跡可能性）」だけである。

これは外部の制約ではなく、このリポジトリの配布スクリプトの仕様である （reports/REVIEW-POINTS.md「制約が外部APIの制約なのか、このリポジトリの実装の欠陥なのかを 取り違えていないか。後者なら修正対象であり、制約として受け入れてはいけない」）。実害の解消は 本issueの範囲外として、下記「残課題」へ送る。

手順側に書くこと（フェーズ3で節へ入れる1〜2行）:

削除・統合を反映内容に含めた回は、.claude/VERSION の扱いを .claude/docs/spec/distribution-assets.md に従って判断する（上流の削除は配布先へ伝播しない ため、版が配布先にとって唯一の手掛かりになる）。

規定そのものは再掲しない。 「増分はAIが提案し人間が決める」「据え置く場合はspecのchangelogへ 残す」は distribution-assets.md 74-88行目が既に持っており、新節へ書き写すと「正が2つ」になる （Q3・Q6で自ら立てた原則）。しかも既存規定は「配布対象アセットに変更があった回」を対象に しているのに、削除・統合に限った書き方をすると条件の広狭が食い違ったまま残る。

結論: 新節が持つのは「削除・統合の回は配布経路に実害がある」という注意喚起と、既存規定への 参照だけである。版を上げること自体は実害を打ち消さない（追跡可能性が上がるだけ）。
