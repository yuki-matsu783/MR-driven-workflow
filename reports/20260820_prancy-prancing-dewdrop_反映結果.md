## 設計反映: push検知hookの環境差をspecへ併記した

### 何をしたか

`.claude/docs/spec/issue-mr-workflow.md` の「誤検知（pushしていないのに発火する）」項の**末尾へ**、
issue #47 の観測を環境差として併記する段落を足した。あわせて `## 影響範囲` の末尾へ
`### issue #47（push検知hookの誤検知に関する環境差の併記）` を追加した。

併記した内容は次の3点である。

1. issue #47 の調査（Claude Code on the web / Linux、2026-08-20）で計4ケースを実測した。
   **発火しなかったのは「地の文に該当語が含まれるだけ」の2ケース**（`echo` の引数／
   コマンド置換＋heredocの地の文）で、**対象コマンドそのものを含む2ケースは発火した**。
   内訳を表で載せている。
2. issue #23 の計3回のうち、`cd /c/Users/... && ...` のケースは**食い違わない**
   （`&&` の右辺が対象コマンドになるため、部分コマンド分解モデルでも説明できる）。
   **逆になっているのは heredocの地の文の類型についてのみ**である。
   issue #23 の観測はこのリポジトリが前提とする常用環境（Windows / git bash）でのものである。
3. **どちらが現行かを決める材料は無い。** バージョン差かプラットフォーム差かの切り分けも
   できていない。**したがって回避策（長文をファイル経由で渡す）は変えない。**

**当初は「同じ構成で発火しなかった（計4ケース）」とだけ書いており、根拠の重みを約2倍に
膨らませていた**（4ケースのうち支持証拠は2ケースだけ）。敵対的レビュー（フェーズ4・1回目）の
指摘を受けて内訳が読める形へ書き直した。specは正史であり、Windows実機で再測する人がこの記述を
出発点にするため、内訳を落とすと再測設計そのものが歪む。

### issue #23 の記録を訂正しなかった理由

実測4ケースは**1環境・1バージョンの観測**にすぎず、別環境で計3回観測された記録を上書きできる
根拠にならない。フェーズ3の敵対的レビューが「同じ事象について逆のことを書いた2つのルールが
`.claude/rules/` に同時に存在することになる」と指摘した際の判断（両論併記）を、正史側でも維持した。

### 差し込み位置

既存の「誤検知」項は、末尾が**節全体にかかる地の文**（回避策の提示と
`.claude/rules/git-workflow.md` への誘導）で終わっている。この地の文より前へ差し込むと係り先が
壊れるため、**項の末尾（次の段落 `より厳密な検知…` の直前）へ置いた**
（`.claude/rules/docs-workflow.md`「既存ドキュメントへ新しい見出しを差し込むとき」）。

### 検証コマンドの実行結果

**検証の基準は「ブランチ分岐点との差分」に固定している。** 引数なしの `git diff` は作業ツリー
比較であり、後から再現できないうえ、**後続のコミットが同じファイルへ入った瞬間に保証が無効になる**
（下記「検証がすり抜けた事故」）。

| # | 検証 | 期待値 | 結果 |
|---|---|---|---|
| 1 | `git diff ad18795 -- .claude/docs/spec/issue-mr-workflow.md \| grep '^-' \| grep -v '^---'` | 削除行なし | **削除行なし** |
| 1' | `git diff --stat ad18795 -- .claude/` | 追加のみ | **`336 insertions(+)`、削除0**（5ファイル） |

## mainとのコンフリクト解消（DDR番号 0059 → 0061）

`hasTextualConflict`（`.claude/docs/README.md`）と `hasDuplicateDdrNumber`（0059）の両方を
真で返した。類型A・C・Dのみで類型Eを含まないため、監視モードの規則どおり承認を待たず解消した。

改番に追随させた箇所: ファイル名／frontmatterの `title`／本文冒頭の見出し／
`.claude/docs/README.md` のリンク（**ファイル名とテキストの両方**）／
`.claude/rules/ai-command-style.md` の参照リンク／specのchangelogの新規ファイル列挙／
`plans/` `reports/` `worklog/` の言及。

検証（`resolve-conflict` Step 5）はすべて通過した（コンフリクトマーカー・unmergedパスなし、

### 検証がすり抜けた事故（敵対的レビューが検出）

**改番の一括置換が、`main` 由来の `### issue #113` changelogエントリまで書き換えていた。**
`- .claude/docs/README.md（DDR一覧へ0059を追加）` を `0061を追加` にしてしまい、issue #113 が
追加したDDR（現在も0059）とは無関係な内容にすり替わっていた。

`.claude/rules/docs-workflow.md` は「ファイル移動に伴うパス参照の一括置換は、specの過去issueごとの
changelogを対象に含めない」と明記しており、それを正面から踏んでいる。

**より重いのは、この事故を自前の検証が検出できなかったこと**である。当時の検証1は
`git diff`（引数なし＝作業ツリー比較）をコミット `4b6a601` の時点で1回実行しただけで、
その後のマージのコミット `000142d` が同じファイルへ入れた改変は**射程の外**だった。
レポートには「既存記述を1文字も変更していない」と機械的な裏付けつきで書かれていたが、
ブランチ先端では成立していなかった。

対処は次の3つ。

1. 該当行を `0059を追加` へ戻した。
2. **検証の基準をコミット単位からブランチ分岐点（`ad18795`）へ固定した。** 後続のコミットが
   何回入っても、分岐点との比較なら常に全体を見る。
3. 検証対象を1ファイルから `.claude/` 配下全体へ広げた（改番の波及先を先回りで限定しない）。

同じ轍を踏まないための一般化は、AIアセット反映のラウンドで扱う。

## AIアセット反映: 3件

### 反映1: DDR一覧への追記を手順として明文化した

`.claude/rules/docs-workflow.md` の運用表のDDRの行へ一文を足し、続く本文へ段落を追加した。

**明文化した内容**: DDRを新規作成したら `.claude/docs/README.md` のDDR一覧へ番号順に1行追記する／
**`extract-frontmatter.sh` も `index.jsonl` も目次の欠落を検出しない**（frontmatterの
インデックスには載るため、件数の確認では代替できない）／改番時はリンクの**ファイル名とテキストの
両方**を追随させる（手順は `resolve-conflict/SKILL.md` 類型Aが正）／**改番の一括置換を過去
changelogへ当てない**。

**反映先が確認によって変わった。** 当初は `issue-mr-flow/SKILL.md` の全体フローへステップを
新設するつもりだったが、確認すると `spec/issue-mr-workflow.md` のchangelogに
`- .claude/docs/README.md（DDR一覧へ00NN を追加）` が繰り返し現れており、**慣習としては確立して
いるのに明文化だけが無い**と分かった。不足しているのは手順の新設ではなく明文化なので、
ドキュメントのライフサイクルを持つ `docs-workflow.md` へ書いた。flow-idは増やしていない。

**このファイルは見出しを持たない地の文構成**のため、`##` 見出しは新設せず、既存と同じ
「太字で始まる段落」の形に揃えた（表からの参照も「下記」に留めた）。

### 反映2: 結論の主語・件数の内訳・測定環境を観点にした

`reports/REVIEW-POINTS.md`「内容の妥当性」へ3つ足した。

| 観点 | 防ぎたい失敗 |
|---|---|
| 結論の主語が、実際に測った対象と一致しているか | `hooks[].if` を測って `permissions` の結論を書く／`deny` を測って `allow` を含む結論を書く |
| 測った件数の内訳が、結論を支える件数と一致しているか | 「4ケース測って発火しなかった」の支持証拠が実は2件 |
| 測った環境が結論に添えられているか | 1環境・1バージョンの観測を全環境の事実として書く |

既存の「確かめられなかったことが、確かめたことと**区別して**書かれているか」では**今回の失敗は
防げない**。本人は区別したつもりで書いているためである。必要なのは「**確かめたことの射程**」を
問う観点だった。

**2つ目（件数の内訳）は計画に無く、フェーズ4の敵対的レビューの指摘3・4を受けて足した。**
射程の逸脱には「主語がずれる」以外に「件数が水増しされる」形もあると、実際に踏んで分かったため。

### 反映3: 検証の基準をブランチ分岐点に置くことを観点にした（計画外の追加）

ルート `REVIEW-POINTS.md`「変えないはずのものが変わっていないか」へ2つ足した。

- **「変えていない」ことの検証を、ブランチ分岐点との差分で取っているか。** 引数なしの
  `git diff` や特定コミットの差分は、その1回の実行以降に入るコミットを見ない。**保証は失効するが、
  失効したことは誰にも通知されない。**
- **検証の対象範囲を、変更したファイル1つに絞っていないか。** 一括置換は意図しないファイルへ
  波及する。ディレクトリ単位で見る。

**計画に無い追加のため、チャットでユーザーの承認を得てから足した**（個別反映計画の
「反映3」節にも経緯を記録済み）。

**ルート側へ置いた理由**: 対象は `reports/` に限らない（spec本文・DDR・rules いずれの変更でも
同じ失敗が起きる）。既存の「検証コマンドが、異常があるときに本当に検出できるか」と対になる観点で
ある。既存観点は**パターンが実データに合っているか**を問うもので、**基準（比較対象のリビジョン）が
動くこと**は射程外だった。今回の失敗は、パターンは正しいのに基準が古かったために素通りしている。
