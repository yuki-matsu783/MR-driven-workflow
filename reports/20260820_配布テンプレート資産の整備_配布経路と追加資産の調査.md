# 調査結果: 配布経路と追加資産の設計判断（issue #33）

個別調査計画: `plans/【調査】配布経路と追加資産の設計判断.md`
全体作業計画: `plans/配布テンプレート資産の整備.md`

## 実機確認の方法（この結果の根拠）

机上の読解だけでなく、**使い捨ての空リポジトリへ実際に配布して観測した**。手順は次のとおり。

```bash
# 1. 配布先を作り、「配布先が元から持っている資産」を置く
mkdir destrepo && cd destrepo && git init -q .
printf '%s\n' '# 配布先が元から持っている設定' '*.png binary' '*.md text eol=lf diff=markdown' > .gitattributes
printf '%s\n' 'node_modules/' > .gitignore
printf '%s\n' '1.2.3' > VERSION

# 2. 本家で assets/ を作り直し、配布先へ適用する
bash .claude/skills/apply-mr-workflow-to-project/scripts/sync-assets.sh
bash .claude/skills/apply-mr-workflow-to-project/scripts/install-to-project.sh <destrepoの絶対パス>
```

観測結果（適用後の配布先）:

- `.gitattributes`: **1バイトも変わらなかった**（3行そのまま）。
- `VERSION`: **`1.2.3` のまま変わらなかった**。
- `.gitignore`: 末尾に `# mr-driven-develop workflow ignores` 以下5行が**追記**された（既存の
  `node_modules/` は残った）。
- `.github/ISSUE_TEMPLATE/task.md`・`.gitlab/issue_templates/Default.md` は新規配置された。

つまり現状、**`.gitattributes` と ルートの `VERSION` は配布経路にまったく載っていない**。

## Q1. `describe` が生成するMR descriptionの構成

`.claude/skills/issue-mr-flow/SKILL.md` の `### describe` 節が持つテンプレートは次の3要素のみ。

```markdown
Closes #<issue番号>

## Plan

<全体作業計画の要約＋各個別計画の要点>

## 実装状況

<worklogの「うまくいったこと」等から、現時点までの実装内容の要約。plan段階では「未着手」>
```

**結論**: PR/MRテンプレートの見出しは `## Plan` → `## 実装状況` の2つだけにし、先頭に
`Closes #` を置く。**これ以外の見出し（レビュー観点・チェックリスト等）を足さない。**
`describe` は description を**全文置換**するため（`set_mr_description <n> <file>`）、テンプレート
側にしか無い見出しは flow-id 2-5 の初回 `describe` で消える。消えても困らない記入ガイドは
**HTMLコメント**で置く（HTMLコメントはGitHub/GitLabの表示上は見えず、`describe` に置換されても
情報を失わない）。

### 設計への反映

- テンプレートの本体は「見出しの骨格＋HTMLコメントのガイド」だけにする。
- GitLab側も同じ構成にする。`describe` はプロバイダを問わず同じ本文を作るため、
  2ファイルの内容が食い違うと、どちらかが必ず `describe` の生成物と矛盾する。

## Q2. 現行の配布経路と、追加資産ごとに必要な変更

`sync-assets.sh`（本家 → `assets/`）と `install-to-project.sh`（`assets/` → 配布先）の2段構成。

| 追加資産 | `sync-assets.sh` | `install-to-project.sh` | 必要な変更 |
|---|---|---|---|
| `.github/pull_request_template.md` | `.github/` を丸ごと `cp -R` | `safe_copy_dir ${ASSETS_DIR}/.github` | **不要**（既存のディレクトリ単位コピーに乗る） |
| `.gitlab/merge_request_templates/Default.md` | `.gitlab/` を丸ごと `cp -R` | `safe_copy_dir ${ASSETS_DIR}/.gitlab` | **不要**（同上） |
| `.gitattributes` | 対象外（ルートは列挙式で `.mrworkflow.json`・`AGENTS.md`・`GEMINI.md`・`CLAUDE.md`・`HANDOFF.md`・`index.md` の6つだけ） | 対象外 | **両方に必要** |
| VERSION（`.claude/VERSION` に置く場合） | `.claude/*` のループに載る | `safe_copy_dir ${ASSETS_DIR}/.claude`（`find -type f` なので配下の全ファイルが対象） | **不要** |
| VERSION（ルート `VERSION` に置く場合） | 列挙へ追加が必要 | `safe_copy_file` の追加が必要 | 両方に必要（かつQ4の衝突リスクあり） |

**結論**: 「集める側」と「配る側」の両方に手が要るのは `.gitattributes` だけ。VERSIONは配置場所の
選び方でスクリプト変更の要否が変わる。

## Q3. `.gitattributes` を配布先へどう配置するか

| 案 | 挙動 | 判定 |
|---|---|---|
| (a) ファイル丸ごとコピー（他資産と同じ `safe_copy_file`） | 配布先の既存 `.gitattributes` を `.bak` へ退避して**全文置換**する | **不採用**。実機で確認したとおり配布先は `*.png binary` や `diff=markdown` のような自前の設定を持ちうる。改行正規化・diff/merge driverの指定が消えると、配布先の作業ツリーが壊れる（テキスト化されたバイナリの破損はGitの履歴に残る形で起きる） |
| (b) 行追記（`.gitignore` と同じ扱い） | 必要な行が無ければ末尾へ足す | **採用**。`.gitattributes` は**後に書いた行が勝つ**仕様なので、末尾追記は「配布先の既定を尊重しつつ、配布したスクリプトに必要な指定だけを上書きする」形になり、意味論としても正しい |
| (c) 配らない | 本家だけがLFを保証する | 不採用。配布先へ配るのは `.sh` を含む資産一式であり、CRLFで取り出されると `bash: $'\r': command not found` で動かない。配布先でこそ必要 |

**配布する行は `*.sh text eol=lf` の1行だけにする。** 本家の `.gitattributes` には
`* text=auto`（リポジトリ全体の正規化方針）も置くが、**これは配らない**。全体方針は配布先が
自分で決めるべきもので、`* text=auto` を勝手に足すと配布先の既存ファイルが次のコミットで
一斉に正規化されうる。「配布したスクリプトが動くのに必要な最小限」＝ `.sh` のLF保証だけを配る。

### 確かめられなかったこと

- **Windows実機（git bash / `core.autocrlf=true` の環境）での挙動は確認していない。** この実行環境は
  Linuxコンテナであり、`.gitattributes` が無い状態でCRLFが混入する事象そのものを再現できない。
  確認できたのは「配布経路が `.gitattributes` を運ばない」ことと「行追記で既存設定が保たれる」
  ことまでである。

## Q4. VERSIONファイルをどこへ置くか

| 案 | 判定 |
|---|---|
| (a) ルート `VERSION` | **不採用**。実機の配布先は自分の版として `VERSION` に `1.2.3` を持っていた。ここへ配布物の版を配ると、配布先のアプリの版を `.bak` 退避のうえ上書きする。「テンプレートを入れたらアプリの版が書き換わった」は事故として重い |
| (b) `.claude/VERSION` | **採用**。`.claude/` はワークフロー機構が所有するディレクトリであり、配布先の資産と名前が衝突しない。さらにQ2のとおり**スクリプト変更なしで配布経路に載る** |
| (c) `.mrworkflow.json` のキー | 不採用。`.mrworkflow.json` は「配布先が編集する設定ファイル」（ブランチ命名規則等をプロジェクトごとに書き換える前提）であり、配布元が上書きしたい版番号と、配布先が書き換えたい設定が同じファイルに同居する。上書き方針が定まらない |

## Q5. VERSIONの更新規則

版番号は更新規則が無いと必ず腐るため、規則までを本issueで決める。

- **形式**: SemVer（`MAJOR.MINOR.PATCH`）の1行のみ。初期値は **`0.1.0`**。
  1.0.0 にしないのは、issue #26 が配布方式そのもの（manifest化・層分け・`sync-assets.sh` 廃止）を
  作り直す予定であり、配布インターフェースがまだ安定していないため。
- **更新するタイミング**: flow-id 4-6（AIアセット反映）。配布対象アセットに変更があった回だけ行う。
- **増分の決め方**: AIエージェントが増分を**提案**し、**人間が決める**（AIが独断で上げない）。
  - `MAJOR`: 配布先に手作業を要求する非互換変更（配置場所の変更・必須スクリプトの引数変更など）
  - `MINOR`: 資産の追加・フローの拡張
  - `PATCH`: 文言修正・バグ修正
- **CHANGELOGは持たない**（ユーザー判断）。何が変わったかはコミット履歴／PR一覧で辿る。

## Q6. issue #26 との整合

issue #26 は配布を manifest 方式へ作り直し、資産を4層（`core` 常に上書き／`seed` 無ければ配置／
`merge` 構造マージ／`local` 触らない）へ分ける予定。今回の追加を層へ当てはめると次のとおり。

| 追加資産 | 該当する層 | 根拠 |
|---|---|---|
| PR/MRテンプレート | `seed` | #26 が `.github/ISSUE_TEMPLATE/` `.gitlab/issue_templates/` を `seed` に置いており、PR/MRテンプレートも同じ性質（配布先が自分の文言に育てる） |
| `.gitattributes` | `merge` | #26 が `.gitignore` を「行追記」として `merge` に置いている。Q3で採用した行追記はこの規則の先取りであり、方針が一致する |
| `.claude/VERSION` | `core` | 配布元が所有し、常に上書きされるべき値 |

**`sync-assets.sh` 廃止（#26）との両立**: 本issueでは現行の `sync-assets.sh` にも対応を入れる
（受け入れ条件5）。廃止後は `install-to-project.sh` 側だけが残るため、**両方へ同じ対応を入れて
おけば、#26 で `sync-assets.sh` を消したときに取りこぼしが出ない**。

**`.claude/VERSION` と `.claude/.asset-manifest.json` の役割は重複しない**。manifestが持つのは
「適用元コミットSHA＋ファイルごとのsha256」という機械可読で正確な同一性であり、VERSIONは
人間が口頭・issue上で示せる粗い識別子である。#26 の manifest には両方を記録すればよい
（本issueでは manifest 自体を作らない）。

## 調査中に見つかった、本issueの範囲外の問題

いずれも issue #26 の受け入れ条件が既に扱っている（＝本issueで直すと二重対応になる）ため、
**記録だけ残して直さない**。flow-id 5-2 で #26 へ通知する。

1. **`.gitignore` 対象のローカル生成物が配布先へ混入する。** 実機で確認したところ、配布先に
   `.claude/index.jsonl`・`.github/ISSUE_TEMPLATE/index.jsonl` 等の `index.jsonl` が10件以上と、
   `.claude/state/`（`post-push-compact-prompt.sh` のローカル状態）が配置された。#26 の `local`
   層の定義がそのままこの問題を指している。
2. **`install-to-project.sh` が追記する `.gitignore` の行が、現在の状態ディレクトリと一致していない。**
   追記されるのは `/.claude/usage-state/` `/.claude/session-logs/` `/.gemini/usage-state/`
   `/.gemini/session-logs/` の4つだが、本家が実際に使うのは `/usage/` と `/.claude/state/` である
   （issue #23 で `logs/` を廃止し `usage/` へ一本化した際に、配布側が追従していない）。配布先では
   ワークフローの生成物がGit管理から外れない。

## 設計への反映（フェーズ3で作るもの）

1. `.github/pull_request_template.md`: `Closes #` ＋ `## Plan` ＋ `## 実装状況`。ガイドはHTMLコメント。
2. `.gitlab/merge_request_templates/Default.md`: 1と同一構成。
3. `.gitattributes`: 本家用に `* text=auto` ＋ `*.sh text eol=lf`。
4. `.claude/VERSION`: `0.1.0`。
5. `sync-assets.sh`: ルート列挙へ `.gitattributes` を追加。
6. `install-to-project.sh`: `.gitattributes` へ `*.sh text eol=lf` を**行追記**する処理を追加
   （`.gitignore` の追記処理と同じ形）。
