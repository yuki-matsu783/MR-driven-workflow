### C. SessionStart hook で現在地flow-idを解決できるか

#### C-0. DDR i0113-01 が同じ材料を却下した理由は、本件にも当てはまるか

i0113-01 の却下文（原文）:

> **判定を `HANDOFF.md` の進捗表の有無で行う**。…`HANDOFF.md` はリセット直後（flow-id 5-3 の
> 直後）やブランチ作成直後には空であり、**フローの最初と最後で取りこぼす**。また表の書式の
> 変更に判定が引きずられる。

| 却下理由 | 本件に当てはまるか | 理由 |
|---|---|---|
| (1) フローの最初と最後で取りこぼす | **当てはまらない** | **失敗時の損失が非対称である。** i0113-01 の判定対象は「SKILL.md を読み直させるか」で、取りこぼすと**再読み込み指示そのものが出ず、手順が丸ごと失われる**。本件の判定対象は「どの参照ファイルを名指しするか」で、取りこぼしても**1行が出ないだけ**。SKILL.md 本文（入口＋全体フロー表＋不変条件）は i0113-01 の仕組みで従来どおり読み直され、**参照ファイルは全体フロー表に明記されているので表から自力で辿れる**。加えて、取りこぼす時期（進捗表が空＝flow-id 1-1〜1-3 と 5-4 以降）は、そもそも参照ファイルの名指しが要らない時期と重なる |
| (2) 表の書式の変更に引きずられる | **当てはまる。ただし解消できる** | 書式の正は既に `update-handoff-progress.sh` の `parse_table_row_to_reply` が持っている（`^\|[[:space:]]*(\[[^\|]*\])[[:space:]]*\|[[:space:]]*([0-9]+-[0-9]+)[[:space:]]*\|`）。**同じ正規表現を共有すれば二重管理にならない。** 書式が変わってパースできなければ空を返す（fail-open） |

**結論: 採用してよい。** ただし本件は i0113-01 の判定（対象ブランチか）を**置き換えるものではなく、
その上に足す**という位置づけにする。この非対称の議論は DDR へ残す。

#### C-1. 現在地flow-idの解決方式

**個別調査計画が当初書いていた「awkで最初の `[]` 行を採る」方式は誤りだった。**
本ブランチの `HANDOFF.md` は 1-5（人間の合意）が `[]` のまま 1-6 が `[x]` であり、
実際に `1-5` を返した。

```
単純な最初の[] : 1-5   ← 誤り
最後の完了の次  : 2-1   ← 正しい
```

採用する方式は **「最後の `[x]` または `[-]` の行より後に現れる、最初の `[]` の行」**。
これは進捗表に穴が空いていても正しく動く。**穴あきは例外ではなく既定である**
（非対話セッションでは人間担当のステップが `[]` のまま残り、ループ範囲も1周完了まで `[]` のまま）。

#### C-2. 縮退ケース（4件・すべて実測）

| ケース | 入力 | 返り値 | 扱い |
|---|---|---|---|
| (i) 進捗表そのものが無い | `cleanup-task.sh` のテンプレート | **空** | 行を注入しない（fail-open） |
| (ii) 全行が `[]` | 着手直後 | `1-1` | 先頭から始める |
| (iii) 穴あき・`[-]` 混在 | `[x] 1-6` / `[-] 2-1` / `[-] 2-2` / `[] 3-1` | `3-1` | 正しい |
| (iv) 書式が想定と違う | パースできない行 | **空** | 行を注入しない（fail-open） |

#### C-3. flow-id → 参照ファイルの対応をどこに持つか

**SKILL.md の全体フロー表に「参照」列を足し、hookはそこから抽出する。**
hook内に対応表を持つと二重管理になり、受け入れ条件「全体フロー表の各行に参照ファイルを明記する」
と食い違う。ヘッダ行から `参照` を含む列の位置を求めるawkで実現できることを試作で確認した。

```
1-4 => [ `references/planning.md` / `references/deliverables.md` ]
2-2 => [ `references/review-loop.md` ]
5-6 => [ — ]
9-9 => []          ← 存在しないflow-idは空（fail-open）
```

**制約**: この抽出は「表のセルが `|` を含まない」ことに依存する。現在のフロー表は満たしている。
ヘッダ行から列位置を求めているため、列の順序変更には強い。

#### C-4. 注入サイズ

追加するのは1行（例: `- 現在地 flow-id 2-1 の参照: .claude/skills/issue-mr-flow/references/planning.md`）で
約150バイト。`CONTEXT_SIZE_WARN_BYTES`（既定8000バイト）に対して 2% 未満であり、
i0113-01 が守った「指示文の長さは有界で入力サイズに依存しない」という条件も満たす。

#### C-5. `references/*.md` の frontmatter

`extract-frontmatter.sh` の走査対象は次のとおりで、**`.md` であれば配下ディレクトリを問わず載る**。

```
git ls-files --cached --others --exclude-standard -z -- "$target_rel" | grep -z '\.md$'
```

`plans/*.html` `reports/*.html` が対象外なのは「HTMLだから」であって（issue #54）、
`references/*.md` はこの例外に当たらない。したがって **frontmatter が必要**であり、
`.claude/rules/markdown-frontmatter.md` の `type` の値の表へ追記する必要がある。

**この追記はフェーズ4ではなくフェーズ3で行う。** フェーズ4へ回すと、フェーズ3のコミット時点で
「表に無い `type` を持つmarkdown」がリポジトリと `index.jsonl` へ入る。

### D. 壊れるテストと配布経路

#### D-1. `test_install_to_project.sh` は壊れる（ただし無言ではない）

`describe_headings()` は `### \`describe\`` 節から `Closes` / `## ` で始まる行をawkで抜き出し、
PR/MRテンプレートの見出しと3者で突き合わせている。`describe` 節を `references/` へ移した写しで
実行すると、抽出が **3行 → 0行** になった。

```
現行SKILL.md: 3行
Closes #<issue番号>
## Plan
## 実装状況
describe節を除いたコピー: 0行
```

テストには「期待値そのものが空になっていないか」のガード
（`assert_eq "describeの見出しを3行抽出できている" "3" …`）があるため、**空同士の一致で通ってしまう
ことはない**。フェーズ3では抽出元のパスを `references/` の該当ファイルへ変える。

#### D-2. `references/` は配布先へ渡る

`sync-assets.sh` はスキルごとに `cp -R "${skill_item}" "${ASSETS_DIR}/.claude/skills/"` を行う。
**スキルディレクトリを丸ごとコピーするため、サブディレクトリは自動で含まれる。**

## 確かめられなかったこと

- **git bash（MSYS）上での C・D の再現。** 本調査はLinux上のリモート実行環境で行った。
  C-1/C-2 の試作スクリプトと D の実測は bash の挙動に依存するため、ユーザーの常用環境
  （Windows / git bash）では確認していない。とくに `awk` の実装差（`gawk` vs `mawk` vs
  `busybox awk`）は C-3 の列抽出に影響しうる。
- **`references/` を実際に作ったうえでの D-2 の確認。** 今回確認したのは「既存の `assets/`
  サブディレクトリが配布先へ渡ること」であり、`references/` そのものではない。同じ `cp -R` の
  経路を通るので渡ると判断したが、**これは実測ではなく実装の読解による推論である。**
  フェーズ3で実物を作ってから再確認する。
- **(d) パスのみの参照154箇所を1件ずつは読んでいない。** 「SKILL.md 自体は同じパスに残るので
  リンクは切れない」という性質から機械的に対応不要と判断した。ただし
  `.claude/docs/spec/issue-mr-workflow.md:53` のディレクトリツリー図のように、**パスは切れないが
  記述としては古くなる**ものが混ざりうる。フェーズ3では、少なくとも「ディレクトリ構成を説明して
  いる箇所」を別途洗い出す。
- **`.gemini/` 側。** `.claude/` 配下へのローカルリンクであり実体を編集すれば足りるが、
  この環境にリンクが張られていないため動作は確認していない。

## 設計への反映

1. **分割は案1（「いつ読むか」で切る）を採用する。** A-3 の「ファイルまたぎ件数」では案を選べず
   （どちらも39件）、E-2/E-3 の「flow-idごとの読み込みバイト数」が決め手になる。この経緯は
   DDR へ「サイズだけで機械的に割る案を却下した根拠」として残す。
2. **全体フロー表へ「参照」列を追加する。** hookの対応表はここから抽出し、二重管理しない（C-3）。
3. **SessionStart hook の現在地解決は「最後の `[x]`/`[-]` の次の `[]`」**とし、
   解決できないときは行を出さない（C-1/C-2）。書式の正規表現は
   `update-handoff-progress.sh` の `parse_table_row_to_reply` と揃える（C-0 の (2) への対処）。
4. **DDR i0113-01 との整合**を DDR へ書く。同じ材料を再採用する根拠は「失敗時の損失が非対称で
   あること」であり、i0113-01 を否定するものではない（C-0）。
5. **`.claude/rules/markdown-frontmatter.md` の type 表への追記はフェーズ3へ前倒す**（C-5）。
   `type` の値を新設するか既存を流用するかは、フェーズ3の個別作業計画で決める。
6. **参照追従の対象は (c) の47件＋折り返し2件に限定する。** (a) DDR本文8件は書き換えず、
   旧節名→新パスの対応表から辿れるようにする。(b) は0件、(d) 154箇所は対応不要（B-3）。
7. **参照元を数えるときは `git grep` を使う**（配布用 `assets/` の複製が母集団を倍にする。B-1）。
   この落とし穴は spec か rules へ残す価値がある。
8. **フェーズ3で追従させる実装は3箇所＋テスト2本**（D-1/D-3）。検証は
   `.claude/scripts/test/` 配下の全テストを回して合計 `failures=0` を条件にする。
