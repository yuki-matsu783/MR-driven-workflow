### C. SessionStart hook で現在地flow-idを解決できるか

#### C-0. DDR i0113-01 が同じ材料を却下した理由は、本件にも当てはまるか

i0113-01 の却下文（原文）:

> **判定を `HANDOFF.md` の進捗表の有無で行う**。…`HANDOFF.md` はリセット直後（flow-id 5-3 の
> 直後）やブランチ作成直後には空であり、**フローの最初と最後で取りこぼす**。また表の書式の
> 変更に判定が引きずられる。

| 却下理由 | 本件に当てはまるか | 理由 |
|---|---|---|
| (1) フローの最初と最後で取りこぼす | **当てはまらない** | **失敗時の損失が非対称である。** i0113-01 の判定対象は「SKILL.md を読み直させるか」で、取りこぼすと**再読み込み指示そのものが出ず、手順が丸ごと失われる**。本件の判定対象は「どの参照ファイルを名指しするか」で、取りこぼしても**1行が出ないだけ**。SKILL.md 本文（入口＋全体フロー表＋不変条件）は i0113-01 の仕組みで従来どおり読み直され、**参照ファイルは全体フロー表に明記されているので表から自力で辿れる**。取りこぼす時期は具体的には **flow-id 1-1〜1-5**（進捗表は 1-6 で書かれる）と **5-4 のリセット後（5-5 / 5-6）**で、E-1 のとおり **1-2 / 1-3 は `start-resume.md`、5-5 は `review-loop.md` を要する時期**である。**「名指しが要らない時期と重なる」わけではない**。それでも採用してよいのは、上の非対称——出ないのは1行だけで、表から自力で辿れる——が成り立つからである |
| (2) 表の書式の変更に引きずられる | **当てはまる。ただし解消できる** | 書式の正は既に `update-handoff-progress.sh` の `parse_table_row_to_reply` が持っている（`^\|[[:space:]]*(\[[^\|]*\])[[:space:]]*\|[[:space:]]*([0-9]+-[0-9]+)[[:space:]]*\|`）。**同じ正規表現を共有すれば二重管理にならない。** 書式が変わってパースできなければ空を返す（fail-open） |

その上に足す**という位置づけにする。この非対称の議論は DDR へ残す。

#### C-1. 現在地flow-idの解決方式

**個別調査計画が当初書いていた「awkで最初の `[]` 行を採る」方式は誤りだった。**
本ブランチの `HANDOFF.md` は 1-5（人間の合意）が `[]` のまま 1-6 が `[x]` であり、
実際に `1-5` を返した。

```
単純な最初の[] : 1-5   ← 誤り
最後の完了の次  : 2-1   ← 正しい
```

採用する方式は **「最後の `[x]` または `[-]` の行より後に現れる、最初の `[]` の行」**。
これは進捗表に穴が空いていても正しく動く。**穴あきは例外ではなく既定である**
（非対話セッションでは人間担当のステップが `[]` のまま残り、ループ範囲も1周完了まで `[]` のまま）。

試作した関数（フェーズ3で `session-start.sh` へ入れる形。正規表現は
`update-handoff-progress.sh` の `parse_table_row_to_reply` と同じもの）:

```bash
ROW_RE='^(\|[[:space:]]*)(\[[^|]*\])([[:space:]]*\|[[:space:]]*([0-9]+-[0-9]+)[[:space:]]*\|.*)$'

current_flow_id_to_reply() {
  local file="$1" line mark fid last_done=0 n=0
  REPLY=''
  [ -f "$file" ] || return 0
  local -a marks=() fids=()
  while IFS= read -r line; do
    [[ "$line" =~ $ROW_RE ]] || continue
    marks+=("${BASH_REMATCH[2]}"); fids+=("${BASH_REMATCH[4]}")
  done < "$file"
  n=${#fids[@]}; [ "$n" -gt 0 ] || return 0
  local i
  for ((i = 0; i < n; i++)); do
    case "${marks[i]}" in *x*|*-*) last_done=$((i + 1)) ;; esac
  done
  for ((i = last_done; i < n; i++)); do
    case "${marks[i]}" in *x*|*-*) continue ;; esac
    REPLY="${fids[i]}"; return 0
  done
  return 0
}
```

#### C-2. 縮退ケース（4件・すべて実測）

| ケース | 入力 | 返り値 | 扱い |
|---|---|---|---|
| (i) 進捗表そのものが無い | `cleanup-task.sh` のテンプレート | **空** | 行を注入しない（fail-open） |
| (ii) 全行が `[]` | 着手直後 | `1-1` | 先頭から始める |

#### C-3. flow-id → 参照ファイルの対応をどこに持つか

**SKILL.md の全体フロー表に「参照」列を足し、hookはそこから抽出する。**
hook内に対応表を持つと二重管理になり、受け入れ条件「全体フロー表の各行に参照ファイルを明記する」
と食い違う。ヘッダ行から `参照` を含む列の位置を求めるawkで実現できることを試作で確認した。

```
1-4 => [ `references/planning.md` / `references/deliverables.md` ]
2-2 => [ `references/review-loop.md` ]
5-6 => [ — ]
9-9 => []          ← 存在しないflow-idは空（fail-open）
```

**試作の入力は、`参照` 列を足したフロー表のサンプルである**（その列は現時点の SKILL.md には
まだ無いため、本物では試せない）。フェーズ3で実物へ列を足したあと、同じ関数で再確認する。

```bash
refs_for_flow_id_to_reply() {
  local skill="$1" fid="$2"
  REPLY=''
  [ -f "$skill" ] || return 0
  REPLY="$(awk -v want="$fid" '
    /^\|[[:space:]]*進捗[[:space:]]*\|/ || /^\|[[:space:]]*flow-id[[:space:]]*\|/ {
      n = split($0, h, "|")
      for (i = 1; i <= n; i++) {
        gsub(/^[[:space:]]+|[[:space:]]+$/, "", h[i])
        if (h[i] == "参照")   col = i
        if (h[i] == "flow-id") idcol = i
      }
      next
    }
    col && idcol && /^\|/ {
      n = split($0, c, "|"); if (n < col) next
      v = c[idcol]; gsub(/^[[:space:]]+|[[:space:]]+$/, "", v); if (v != want) next
      r = c[col];   gsub(/^[[:space:]]+|[[:space:]]+$/, "", r); print r; exit
    }
  ' "$skill")"
}
```

**制約**: この抽出は「表のセルが `|` を含まない」ことに依存する。現在のフロー表は満たしている。
ヘッダ行から列位置を求めているため、列の順序変更には強い。使った `awk` は `mawk 1.3.4 20240123`
であり、**`gawk`（git bashの既定）では未確認**である。

## 確かめられなかったこと

- **git bash（MSYS）上での C・D の再現。** 本調査はLinux上のリモート実行環境で行った。
  C-1/C-2 の試作スクリプトと D の実測は bash の挙動に依存するため、ユーザーの常用環境
  （Windows / git bash）では確認していない。とくに `awk` の実装差（`gawk` vs `mawk` vs
  `busybox awk`）は C-3 の列抽出に影響しうる。
- **`references/` を実際に作ったうえでの D-2 の確認。** 今回確認したのは「既存の `assets/`
  サブディレクトリが配布先へ渡ること」であり、`references/` そのものではない。同じ `cp -R` の
  経路を通るので渡ると判断したが、**これは実測ではなく実装の読解による推論である。**
  フェーズ3で実物を作ってから再確認する。
- **(d) 節名を伴わない83件を1件ずつは読んでいない。** 「SKILL.md 自体は同じパスに残るので
  リンクは切れない」という性質から機械的に対応不要と判断した。ただし**パスは切れないが記述としては
  古くなる**ものが混ざりうるため、フェーズ3では少なくとも「ディレクトリ構成を説明している箇所」を
  別途洗い出す（ディレクトリツリー図 `.claude/docs/spec/issue-mr-workflow.md:53` は (c) として

## 設計への反映

1. **分割は案1（「いつ読むか」で切る）を採用する。** A-3 の「ファイルまたぎ件数」では案を選べず
   （どちらも39件）、E-3 の「flow-idごとの読み込みバイト数」が決め手になる。この経緯は
   DDR へ「サイズだけで機械的に割る案を却下した根拠」として残す。**そのとき、却下した案2の定義
   （E-2 の4チャンク表）も DDR へ写す**（`reports/` は flow-id 5-4 で消えるため、数値だけを
   写すと後から検算できなくなる）。
2. **全体フロー表へ「参照」列を追加する。** hookの対応表はここから抽出し、二重管理しない（C-3）。
3. **SessionStart hook の現在地解決は「最後の `[x]`/`[-]` の次の `[]`」**とし、
   解決できないときは行を出さない（C-1/C-2）。書式の正規表現は
   `update-handoff-progress.sh` の `parse_table_row_to_reply` と揃える（C-0 の (2) への対処）。
4. **DDR i0113-01 との整合**を DDR へ書く。同じ材料を再採用する根拠は「失敗時の損失が非対称で
   あること」であり、i0113-01 を否定するものではない（C-0）。**「取りこぼす時期は名指しが
   要らない時期と重なる」とは書かない**——実際には 1-2/1-3 と 5-5 が取りこぼす時期に当たる。
   書くのは「出ないのは1行だけで、SKILL.md 本文の全体フロー表から自力で辿れる」という非対称のみ。
5. **`.claude/rules/markdown-frontmatter.md` の type 表への追記はフェーズ3へ前倒す**（C-5）。
   `type` の値を新設するか既存を流用するかは、フェーズ3の個別作業計画で決める。
6. **参照追従の対象は (c) の64件。** (a) DDR本文26件と **(b) specのpoint-in-time節33件**は
   書き換えず、旧節名→新パスの対応表から辿れるようにする。(d) 83件は対応不要（B-3）。
   **(b) は0件ではないので、旧節名の機械置換を一括で当ててはならない**（`## 影響範囲` の中に
   現在の状態を説明する小節が混ざるため、行番号による線引きも使えない）。1件ずつ判断する。
7. **参照元を数えるときは `git grep` を使う**（配布用 `assets/` の複製が母集団を倍にする。B-1）。
   この落とし穴は spec か rules へ残す価値がある。
8. **フェーズ3で追従させる実装は3箇所＋テスト2本**（D-1/D-3）。検証は
