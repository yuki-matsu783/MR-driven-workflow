### Q2. スキップ条件は洗い出し手順のどの段階か

現行の条件文は「反映するものが**無いと確認できた**場合」で、**何をもって「確認できた」とするかが
書かれていない**。これが issue #155 が「要求だけがあり、それに応える手順が無い」と述べている状態で
ある。

新設する手順を「手順1: 起点の列挙 → 手順2: 4類型への分類 → 手順3: 証拠集め（(a) のみ）→
手順4: 反映先の形態の決定」と置くと、スキップ条件は次のように言い直せる。

> **手順1と手順2まで実施し、4類型のいずれにも分類される項目が0件だったとき。**

- **手順3（証拠集め）まで進む必要はない。** 証拠が要るのは (a) だけで、しかも「反映するか否か」
  ではなく「(a) として反映してよいか」を決めるためのものだからである。手順2で0件なら手順3の
  入力自体が無い。
- **手順4も同様。** 反映先を選ぶ対象が無い。

**結論**: 接続の文言は「洗い出し手順の手順1〜2まで実施し、分類結果が0件だったとき」で書ける。
「無いと確認できた」という主観的な表現を、実施した手順の番号で置き換えられる。

```
$ bash .claude/scripts/src/search-frontmatter.sh --type ddr --path i0110 --format detail
- .claude/docs/ddr/i0110-01-個別計画のタスク種別を6種から8種へ拡張する
  type       : ddr

  description: 個別計画のタスク種別に【AIアセット作成】（フェーズ3）・【実装反映】（フェーズ4）を新設し6種から8種へ拡張する意思決定
  tags       : issue-mr-flow, plans, タスク種別
  keywords   : タスク種別, AIアセット作成, 実装反映, 設計反映, AIアセット反映, SKILL.md, 併記, 分割
  mtime      : 2026-08-23T04:28:51
matched=1 total=129 indexes=23
```

返るのは **`type` / `title` / `description` / `tags` / `keywords` / パス / `mtime`** と、
末尾のサマリ `matched=N total=N indexes=N`。

- **`matched=N` がそのまま打ち切り条件に使える。** 「`doc-search` で `matched=0` なら痕跡なしと
  判断して次の段階へ進む」と書ける。
- 検索は `--type` / `--tag` / `--keyword` / `--path` / `--text` の5つで絞れる（`--help` で確認）。
  証拠集めでは `--text <罠の語>` と `--type ddr` の組み合わせが実用的である。
- **`--format json` をパイプの途中で切ってはいけない。** 整形済みJSON配列なので先頭3行は
  `[` / `{` / `concept_id` の行だけになり、確かめたい項目が1つも出ない。

**結論**: 打ち切り条件として書ける形である。`--format detail` と `matched=N` を使う。

### Q5. `【AIアセット作成】` との使い分けと矛盾しないか

既存の規定（SKILL.md 162-166行目）:

> **`【AIアセット作成】`**: そのissueの**主たる成果物**としてAIアセット（スキル・ルール・
> エージェント）を**新規作成・改訂**する作業。（…）作業の**副産物**として気づいた改善を反映する
> `【AIアセット反映】`（フェーズ4）とは、**成果物か副産物かで使い分ける**。

新設する洗い出し手順の**起点**は「今回のMRで行った作業のうち、既存アセットで対応できなかったもの」
であり、これは定義上すべて**副産物**である（そのissueの主たる成果物としてアセットを作る場合、
その作業はフェーズ3で `【AIアセット作成】` として計画される）。

**結論**: 矛盾しない。むしろ洗い出し手順は「副産物側だけを対象にする」ことを起点の定義で明示する
ため、既存の使い分けを補強する。**新節には「主たる成果物としてのアセット作成は対象外
（`【AIアセット作成】` で扱う）」と1行書いておく**と、境界が読み手に伝わる。

### Q7. `scripts` / `hooks` を反映先に含めるか

issue #155 は反映先の形態として6つ（`rules` / `skills` / `scripts` / `hooks` /
`REVIEW-POINTS.md` / `agents`）を挙げるが、現行のSKILL.mdは次の2点でこれと食い違う。

```
$ grep -n '対象に含めない' .claude/skills/issue-mr-flow/SKILL.md
164:  同じ性質（単体テストを持つ等）を持つため対象に含めない（`【実装】`/`【実装反映】`側で扱う）。
```

1. `【AIアセット作成】` は `.claude/scripts/` 配下を**明示的に対象外**にしている（164行目）。
2. flow-id 4-6 のAIアセット反映の反映先は**4つに限定**されている
   （`.claude/rules/` `.claude/skills/` `CLAUDE.md` `AGENTS.md`）。`.claude/agents/` と
   `REVIEW-POINTS.md` は、AIアセットでありながら**列挙から漏れている**。

**結論: 含める。ただし「反映先に選べること」と「どの種別で作業するか」を分ける。**

- **反映先の形態としては6つすべて選べる。** 2軸の「守らせ方の強さ」で `hooks`（検証で落とす）を
  選べないと、軸そのものが機能しない。実際 `.claude/hooks/block-direct-git-commit.sh` は
  「commitスキル経由を強制する」というルールを hook で守らせた実例である（DDR i0000-09）。
- **`scripts` / `hooks` を選んだ場合、その作業の種別は `【実装反映】` になる**（単体テストを伴う
  ため。164行目の除外規定はそのまま生きる）。新節にはこの1行を書く。
- **flow-id 4-6 の反映先の列挙へ `.claude/agents/` と `**/REVIEW-POINTS.md` を補う。** これは
  Q7とは独立に、現行の列挙が `【AIアセット作成】` の定義（「スキル・ルール・**エージェント**」）と
  食い違っている漏れである。

この形なら issue #110 の切り分け（成果物か副産物か／実装・テストの修正を伴うか）を1つも壊さない。

### Q8. 削除・統合したときに配布経路で何が起きるか

`.claude/docs/spec/distribution-assets.md` 89-91行目:

> **据え置きには実害がある**ことを承知して選ぶ。（…）とくに改名・削除を伴う回は、
> `install-to-project.sh` が上流で消えたファイルを配布先から削除しない（コピーのみ）ため、
> 配布先に旧パスが残ったことに気づく手掛かりが版にも無くなる。

**実装でも確認した。** 資産の配布は `cp -f` のみである。

```
$ grep -n 'cp \|rm \|--delete' .claude/skills/apply-mr-workflow-to-project/scripts/install-to-project.sh
105:      cp -f "${src}" "${dest}"
108:      cp -f "${src}" "${dest}"
113:      cp -f "${dest}" "${backup}"
116:      cp -f "${src}" "${dest}"
121:      cp -f "${src}" "${dest}"
199:  rm -f "${DEST_DIR}/.claude/rules/go-applications.md" \
```

唯一の `rm -f`（199行目）は**非Goプロジェクトへ配布するときにGo用ルールを消す特例**であり、
「上流で消えたファイルを追随して消す」処理ではない。

**壊れ方**: アセットAをアセットBへ統合してAを削除したMRを配布先へ適用すると、配布先には
**AとBが両方残る**。読み手（次のセッションのAI）は矛盾する2つの記述を読むことになり、
本手順が減らそうとしている (d)「あったのに辿り着けない」を、配布先で自ら増やす。

**手順側に書くこと（フェーズ3で節へ入れる1〜2行）**:

> **削除・統合を反映内容に含めた回は、`.claude/VERSION` の増分をAIから提案する。**
> `install-to-project.sh` は上流の削除を配布先へ伝播しない（コピーのみ）ため、版を上げないと
> 配布先は旧アセットが残ったことに気づけない（`.claude/docs/spec/distribution-assets.md`）。
> 据え置く判断をした場合は、その事実をspecのchangelogへ残す。

**結論**: 打ち消しの手段は「版を上げる（またはは据え置きを記録する）」であり、既存の規定の
