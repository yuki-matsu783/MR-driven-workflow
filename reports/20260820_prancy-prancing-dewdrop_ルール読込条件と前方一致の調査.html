調査2: permissions の照合単位

無害なパターンを .claude/settings.local.json へ一時的に置いて実測した（実験後に削除済み・未コミット）。 設定はセッション途中でも即座に反映された。 

{ "permissions": { "deny": ["Bash(echo arv-probe*)"] } }

渡したコマンド文字列をそのまま載せる（行位置がそのまま結論の根拠になるため）。

A 拒否された 
echo arv-probe-case-a

基準ケース。

B 拒否された 
# 実験: 1行目をコメントにして deny の前方一致が外れるか
echo arv-probe-case-b

本命。1行目がコメントでも外れない。

C 拒否された 
set -euo pipefail

# 対象コマンドを3行目に置く（先頭は無関係なコマンド）
ls /tmp >/dev/null
echo arv-probe-case-c

対象は5行目。何行目にあっても効く。

D 実行された 
set -euo pipefail
# 対象語を引数の中に含むだけ（コマンドとしては実行しない）
printf '%s\n' "echo arv-probe-case-d は引数の中の文字列"

引数の中の文字列では効かない。

導かれるモデル

  • B・Cから: 「コマンド文字列全体の先頭で前方一致する」モデルではない。
  • Dから: 「コマンド文字列全体に対する部分一致」モデルでもない。
  • 4ケースすべてを説明するのは 「コマンドを部分コマンドへ分解し、各部分コマンドの先頭で照合する」 というモデル。

確かめられなかったこと: allow へは外挿できない

意味論
denyいずれかの部分コマンドが一致したら拒否（ANY）
allowすべての部分コマンドが許可規則に一致して初めて自動承認（ALL）

この非対称性のもとでは、先頭のコメント行が「無視される」のか 「どの許可規則にも一致しない部分コマンドとして数えられる」のかを、 deny の実験では原理的に区別できない（後者でも deny の結果は変わらないため）。

issue #47 の付帯制約が問題にしているのは、まさに後者による「許可済みのはずの操作で承認プロンプトが出る」ケースである。 したがって本調査は、issueの主張のうち allow 側を反証していない。

  • 実測を見送った理由: 観測には権限モードをプロンプトが出る形へ変える必要があり、 そうすると以降のあらゆるコマンドが承認待ちになってセッションが止まる（削除コマンドすら実行できず復旧できない）。
  • 実験時の権限モードを記録していなかった。 allow 由来の挙動は権限モード依存のため、追試するならまず記録すること。

参考: hookの if フィールドも同じ挙動だった

permissions とは別物であり、この観測を permissions の根拠には使っていない。

既存記述との食い違い: git-workflow.md・spec/issue-mr-workflow.md・DDR 0022 は、 issue #23 の実機観測3回をもとに「前方一致ではなく部分一致」と記録し、 「heredocで渡す地の文で発火した」と書いている。 ケース4はその構成そのものを再現したが、発火しなかった。 一方「cd … && … で発火した」は部分コマンド分解モデルでも説明できる。 食い違うのは地の文の1点だけで、バージョン差かプラットフォーム差かは切り分けられなかった。

調査3: hook誤検知の発火範囲

hookスクリプトは tool_input.command 全体を検査し、コメント行を除外しない。 jq -r '.tool_input.command' の結果をそのまま grep へ渡している（間にコメント除去を挟んでいない）。 

# 検索した構文: sed / awk / ${var//#*/} / 行頭 # の除去
grep -cE 'sed|awk|//#|\^#' .claude/hooks/block-direct-git-commit.sh   # → 0
# 対照（grep 自体が機能していることの確認）
grep -c 'command' .claude/hooks/block-direct-git-commit.sh            # → 5

0件だけでは「除外処理が無い」と「パターンが誤っている」を区別できないため、対照を併記している。

hooks[].if スクリプト内部の grep
誰が判定するかClaude Code本体hookスクリプト自身
判定単位部分コマンドコマンド文字列全体の部分一致
コミットブロックhook持たない（matcherはツール名のみ）これだけで判定する
push検知hook×2持つ通過後に再チェック
コミットブロックhookは if を経由しないため、地の文の該当語で必ず発火する。 push検知の2つは if で絞られるため、この環境では地の文だけでは発火しない（調査2の参考表・ケース2と4）。 「コメント本文で誤検知する」という注意が最も強く当てはまるのはコミット側。

既存ルールとの重複: git-workflow.md には既にコミット側・push側の2箇所に同趣旨の注意がある。 新ルールが足すのは「コマンド内コメントを書くときの注意」という文脈だけで、仕組みの説明は参照で済ませる。

提案: .claude/rules/ai-command-style.md（新規）

既存の命名は kebab-case の主題名。shell-script-style と対になる形にすると、 「保存するスクリプト」対「ツールへ渡すコマンド」の対比が名前から読める。

frontmatter の方針: alwaysApply は付けない

  1. 規約にキー定義が無い。 markdown-frontmatter.md のキー定義表に alwaysApply は無く、 「既にそれを持つファイルでは値・位置を変更しない」と定めるだけで、新規付与を求めていない。受け入れ条件6は「規約に沿った frontmatter」を求めている。
  2. 読み込みの条件ではない（調査1の実測）。
  3. 同種のルールが持っていない。 コーディング規約系の3ファイルはいずれも持たず、持っているのはワークフロー運用系の3ファイル。今回の内容は前者に属する。

ただしこの判断は調査1の観測に依存する。 新規ファイルでの実測で「読み込まれない」と分かった場合は再検討する。

理由をissueの記述のまま書くと、半分は事実に反し、半分は未確認の根拠に立つことになる。

案A

制約自体を撤回する

推奨しない。 allow 側は反証できておらず、承認プロンプトの帰結は依然として起こりうる。 加えて測れたのは1環境・1バージョンだけで、常用環境では未確認。既存記録（issue #23）とも食い違っている。

案B

理由を「リスク回避」へ書き換える

推奨。「deny 側はこの環境では外れなかったが、allow 側は未確認であり、 照合の実挙動が環境・バージョンで異なる観測もあるため、先頭は避ける」とする。 結論は変えずに根拠を実測へ合わせられ、受け入れ条件4の「理由とともに明記」も満たす。 本文には実測表A〜Dと、allow を確かめられなかった理由（ANY／ALLの非対称性、セッションが止まるリスク）を載せる。

案C

issueの記述どおり「前方一致が外れる」と書く

不可。 少なくとも deny 側は実測と食い違う記述をルールとして残すことになる。

受け入れ条件2の扱い

「description はコンソール上1行しか表示されない」という根拠は本環境では再現できない（コンソール表示が無いため）。 issue #47 起票時の実機確認を出典として引用する形で書く。 確度は「未確認（issue起票時の観測を引用）」であり、実測で覆した受け入れ条件4とは扱いが違う （条件2は出典を添えて断定、条件4はリスク回避として記述）。

その他の反映

  • 受け入れ条件1: 新規ファイルでの実測が済むまで「満たした」と書かない。
  • 受け入れ条件5: 仕組みの説明は git-workflow.md を参照し、コマンド内コメントの文脈での注意だけを書く。 コミット側と push 側で当てはまり方が違うことにも触れ、「コメントに2語を並べると常に誤発火する」とは書かない。
  • 切り出し先: scratchpad か .claude/scripts/src/ かの判断基準を表に含める （後者は「skills経由で能動的に実行するスクリプト」の置き場で、使い捨てを置くと配置ルールと衝突し、片付けの削除対象でもないため残り続ける）。
