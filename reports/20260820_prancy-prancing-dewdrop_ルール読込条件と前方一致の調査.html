調査2: permissions の照合単位

無害なパターンを .claude/settings.local.json へ一時的に置いて実測した（実験後に削除済み・未コミット）。 設定はセッション途中でも即座に反映された。 

{ "permissions": { "deny": ["Bash(echo arv-probe*)"] } }
A 拒否された 
echo arv-probe-case-a

基準ケース。

B 拒否された 
# 1行目をコメントにする
echo arv-probe-case-b

本命。先頭コメントでも外れない。

C 拒否された 
set -euo pipefail

# 対象は3行目より後
ls /tmp >/dev/null
echo arv-probe-case-c

何行目にあっても効く。

D 実行された 
printf '%s\n' "echo arv-probe-case-d は引数の中の文字列"

引数の中の文字列では効かない。

導かれるモデル

  • B・Cから: 「コマンド文字列全体の先頭で前方一致する」モデルではない。
  • Dから: 「コマンド文字列全体に対する部分一致」モデルでもない。
  • 4ケースすべてを説明するのは 「コマンドを部分コマンドへ分解し、各部分コマンドの先頭で照合する」 というモデル。
既存記述との食い違い: .claude/rules/git-workflow.md・spec/issue-mr-workflow.md・DDR 0022 は、 issue #23 の実機観測3回をもとに「前方一致ではなく部分一致」と記録している。 食い違うのは「heredocの地の文で発火する」という一点で、 バージョン差かプラットフォーム差かは本調査では切り分けられなかった。

調査1: 自動読込の条件

経路1

settings.json

読み込み対象を指すキーは1つも無い（permissions / plansDirectory / autoCompactWindow / hooks のみ）

経路2

@import

CLAUDE.md / GEMINI.md が ./AGENTS.md を読むだけ。AGENTS.md は rules を文章で参照するのみ

経路3

SessionStart hook

session-start.sh は rules という語を1度も含まない

ファイル alwaysApply: true 読み込まれたか
directory-structure.mdありされた
docs-workflow.mdありされた
git-workflow.mdありされた
markdown-frontmatter.mdなしされた
powershell-encoding.mdなしされた
shell-script-style.mdなしされた

経路が3つとも無いのに全ファイルが読み込まれている。Claude Code本体が .claude/rules/*.md をディレクトリ単位でプロジェクト指示として読んでいると考えるのが素直 （開始時コンテキストでも project instructions, checked into the codebase として提示された）。

確かめられなかったこと: これは既存ファイルの観測であり、新規ファイルの証拠にはならない。 受け入れ条件1を満たすには、フェーズ3でルールファイルを作った後に新しいセッションで実測する必要がある。 他の実行経路（ローカルのgit bash・Gemini CLI）も未確認。

調査3: hook誤検知の発火範囲

hookスクリプトは tool_input.command 全体を検査し、コメント行を除外しない （除外処理の grep は0件）。本セッションでも実際に踏んだ。

hooks[].if スクリプト内部の grep
誰が判定するかClaude Code本体hookスクリプト自身
判定単位部分コマンドコマンド文字列全体の部分一致
コミットブロックhook持たない（matcherはツール名のみ）これだけで判定する
push検知hook×2持つ通過後に再チェック
コミットブロックhookは if を経由しないため、地の文の該当語で必ず発火する。 push検知の2つは if で絞られるため、この環境では地の文だけでは発火しない。 「コメント本文で誤検知する」という注意が最も強く当てはまるのはコミット側。

設計への反映

受け入れ条件4の扱い（要判断）

受け入れ条件4は「1行目にコメントを書かないことが、前方一致が外れる理由とともに明記されている」ことを求める。 しかし実測では外れない。理由をそのまま書くと、ルールが事実でない根拠に立つ。

案A

制約自体を撤回する

推奨しない。 測れたのは1環境・1バージョンだけで、常用環境では未確認。 既存記録（issue #23）とも食い違っており、照合の実装が変わりうることを示している。

案B

理由を「リスク回避」へ書き換える

推奨。 「照合の実挙動が環境・バージョンで異なる観測があるため、先頭は避ける」とする。 結論は変えずに根拠を実測へ合わせられ、受け入れ条件4の「理由とともに明記」も満たす（理由の中身が変わるだけ）。 ルール本文には実測表A〜Dを載せ、「この環境では外れなかった」事実も隠さず書く。

案C

issueの記述どおり「前方一致が外れる」と書く

不可。 実測と食い違う記述をルールとして残すことになる。
