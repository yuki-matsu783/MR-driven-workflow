issue #7 調査結果

post-push hook群のGemini CLI対応状況

post-push-usage-report.sh / post-push-compact-prompt.sh を post-push-save-logs.sh と同様に Gemini CLI/Claude Code 両対応にするための調査記録

結論

post-push-usage-report.sh と post-push-compact-prompt.sh は、 Claude Code専用のガード条件（CLAUDE_PROJECT_DIR必須・ tool_nameがBash/PowerShell限定）を持つため、 Gemini CLI実行時は処理冒頭で必ずexit 0となり動作しない。

一方 post-push-save-logs.sh は tool_nameによるエンジン判定と ${GEMINI_PROJECT_DIR:-${CLAUDE_PROJECT_DIR:-}} によるフォールバック取得を実装済みで、これを手本に他2スクリプトへ同パターンを移植する。

1. 参考実装: post-push-save-logs.sh

エンジン判定（41〜49行目）

case "$tool_name" in
  run_shell_command) engine="gemini"; engine_label="Gemini CLI" ;;
  Bash|PowerShell) engine="claude"; engine_label="Claude Code" ;;
  *) exit 0 ;;
esac

プロジェクトルート取得（59〜60行目）

local project_dir="${GEMINI_PROJECT_DIR:-${CLAUDE_PROJECT_DIR:-}}"
[ -n "$project_dir" ] || exit 0

判定結果 engine / engine_label は 74・108・136行目で後段処理（サブエージェントログ探索方式、完了メッセージ表示）に使われる。 .claude/docs/spec/session-log-hooks.md「エンジン判定」節に同パターンが文書化済み。

2. 対応が必要な2ファイルの現状

post-push-usage-report.sh

66  [ -n "${CLAUDE_PROJECT_DIR:-}" ] || exit 0
68  local tool_name
69  tool_name="$(printf '%s' "$hook_input" \
      | jq -r '.tool_name // empty')"
70  if [ "$tool_name" != "Bash" ] \
      && [ "$tool_name" != "PowerShell" ]; then
71    exit 0
72  fi

80行目 cd "$CLAUDE_PROJECT_DIR"、 82行目 UsageTracking.shのsourceパスも CLAUDE_PROJECT_DIR固定。 89〜91行目のsession_id/transcript_path取得は tool_name分岐と無関係にhook入力から直接取得しているため、Gemini CLI側も同名フィールドが 提供される前提であれば変更不要と考えられる（save-logs側と同じ暗黙の前提）。

post-push-compact-prompt.sh

47  agent_id="$(... | jq -r '.agent_id // empty')"
50  [ -z "$agent_id" ] || exit 0
52  [ -n "${CLAUDE_PROJECT_DIR:-}" ] || exit 0

      && [ "$tool_name" != "PowerShell" ]; then

usage-report.shと完全に同一パターンのガード（11行目コメントで同一と明記）。 UsageTracking.shはsourceせず、 MRコメントではなくhookSpecificOutput.additionalContext 形式のJSONを出力してコンテキストへ注入する方式。状態ファイルの読み書きは無い。

3. hook登録設定の差分

項目 Claude Code（.claude/settings.json） Gemini CLI（.gemini/settings.json）
hookイベント名PostToolUseAfterTool
matcherBash|PowerShellrun_shell_command|Bash|PowerShell

timeout単位秒（20）ミリ秒（20000）
3スクリプトの登録usage-report / compact-prompt / save-logs いずれも登録済み（設定側は両対応の体裁済み）

設定ファイル側は3スクリプトとも既に登録済みで、未対応なのはスクリプト本体側のみ （save-logs以外）という「設定と実装の不整合」状態。

4. 未検証事項・対象外

  • GitLab側の動作検証は今回の受け入れ条件で明示的に対象外（GitHub remote環境での確認に限定）。
  • Gemini CLIのhook入力JSONがsession_id/transcript_path/agent_idを Claude Codeと同名・同形式で提供するかは本リポジトリ内に明記が無い暗黙の前提。save-logs側が 既にこの前提で動作している実績があるため、本issueでも同じ前提を踏襲し新たな検証は行わない。
  • Stop/SessionEnd等、他のhookイベントへの対応拡張は対象外。

5. 対応方針（作業計画の元）

  1. post-push-usage-report.shにpost-push-save-logs.shと同じ tool_name分岐を追加し、66行目のガードを ${GEMINI_PROJECT_DIR:-${CLAUDE_PROJECT_DIR:-}}によるフォールバックへ置換。 80行目cd・82行目sourceパスも修正。
  2. post-push-compact-prompt.shに同様の修正を適用（47〜64行目のガード部分）。
  3. .claude/docs/spec/session-log-hooks.mdに、この2スクリプトも同じエンジン判定パターンへ 対応した旨を追記。
  4. 可能であればGitHub remote環境でGemini CLIからgit pushをトリガーし、 工数レポート・コンパクトプロンプトの動作を確認する。
