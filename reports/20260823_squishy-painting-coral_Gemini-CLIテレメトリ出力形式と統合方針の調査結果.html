調査手法についての注記

WebFetchはページ内容を小さく速いモデルが要約して返す仕組みであり、ソースコードを直接目視したものではない。本reportで「引用」と書いている箇所は、WebFetchが返した引用（要約段階での言い換え・省略のリスクがある）であって、リポジトリをgit cloneして直接読んだ逐語引用ではない。

確度を上げた方法 重要な判断（出力形式のシリアライズ方式・スキーマ配置・環境変数の存在）は、同一ファイル・同一質問で2回以上WebFetchを実行し、結果が一致することを確認したうえで採用している。それでも一次資料そのものではないため、フェーズ3で実装に落とし込む際は可能であればgit clone等での再確認を推奨する。

実施した内容と結果

1. 出力ファイル形式

command -v gemini で実機の有無を確認したところ存在しなかった（exit=1）ため、 公式ソースコードを直接確認した。

$ command -v gemini; echo "exit=$?"
exit=1

packages/core/src/telemetry/sdk.tsで、FileSpanExporter / FileLogExporter / FileMetricExporterの3つがすべて同一のtelemetryOutfile値で初期化される ことを確認した。packages/core/src/telemetry/file-exporters.tsのコンストラクタは fs.createWriteStream(filePath, { flags: 'a' })（追記モード）、シリアライズは safeJsonStringify(data, 2) + '\n'（インデント2のpretty-print JSON＋末尾改行）。 gemini_cli.api_responseはlogger.emit()によるLogRecordとして記録される （Spanイベントではない。packages/core/src/telemetry/loggers.ts）。

追加確認（敵対的レビュー2回目で発見）

同一イベントが常に2回LogRecordとしてemitされる。 logApiResponse()は 条件分岐を挟まずlogger.emit(event.toLogRecord(config))と logger.emit(event.toSemanticLogRecord(config))の両方を無条件に呼ぶ （レガシー形式＋semantic conventions形式）。素朴に名前だけで数えるとトークン数が2倍になる。

metricsは10秒間隔で周期的にexportされる。 FileMetricExporterは PeriodicExportingMetricReader（exportIntervalMillis: 10000）と 組み合わせて登録される。cumulative temporalityのため、同じ累計値が繰り返し出力されうる。

結論 単一ファイル・追記型・spans/logs/metrics混在。「1行1JSON」ではなく、複数行にわたる pretty-print JSONが改行区切りで連続する形式。ローテーション実装は確認した1ファイル （file-exporters.ts）の範囲では見当たらないが、他ファイルまでは追えていない。

2. settings.jsonのスキーマ確認

packages/cli/src/config/settingsSchema.tsでtelemetryキーが type: 'object', ref: 'TelemetrySettings'としてトップレベルに 定義されていることを確認した（2回のWebFetchで同一内容を再確認）。

telemetry: {
  type: 'object',
  category: 'Advanced',
  ref: 'TelemetrySettings',
  ...
}
結論 telemetryはgeneral配下ではなくトップレベルキー。現行の .gemini/settings.json（general.plan.directory, hooks） と衝突しない。

3. 出力先配置の比較

issue #103は常駐perlリスナー自身が日付ベースでファイルを切り替えて usage/claude-otel-YYYYMMDD.jsonlを実現している。Gemini CLI側の outfileは.gemini/settings.jsonでは単一固定パスだが、 公式ドキュメントに「Environment variables can override these settings」とあり、 対応するGEMINI_TELEMETRY_OUTFILE環境変数の存在を確認した。

結論（当初の判断を修正）

環境変数GEMINI_TELEMETRY_OUTFILEによりGemini CLI起動時に動的パスを渡すこと 自体は技術的に可能（当初の「settings.jsonが静的だから動的パスを渡せない」という 判断は誤りだった）。ただし本機構にGemini CLI起動を仲介するラッパーが無いため、 当面は.gemini/settings.jsonによる固定ファイル名 （usage/gemini-otel.log）を採用し、issue #103との整合はさせない。 起動ラッパーの新設は将来の拡張としてDDRの未決定事項に残す。

残課題: outfileの相対パス解決基準（cwd／プロジェクトルート）は未確認。

4. 差分カーソル単位の判定

単一ファイル・追記型・複数行JSON混在という性質から、Claude Code経路の行カーソル方式、 Gemini CLIセッションログ経路の畳み込み方式（DDR i0097-01）のいずれも適さない。

結論

バイトオフセットカーソル（前回処理した末尾バイト位置を記録し、以降を新規として集計）を 推奨する。ただし次の3点をフェーズ3の必須要件とする。

  • metricsを集計対象から除外し、gemini_cli.api_response由来のLogRecord のみを対象にする（metricsは10秒ごとの周期exportで二重計上の原因になるため）。
  • 同一イベントの2重emit（toLogRecord/toSemanticLogRecord）を重複排除する （どちらか一方の形式のみ採用、またはイベント一意キーでの重複排除）。
  • 耐障害性: 途中書き込み（不完全な末尾JSON）・ファイル縮小（DDR i0097-01の needsResetと同じ考え方でカーソルを0へ戻す）・状態ファイルの破損への 自己回復ロジックを実装する。複数プロセス同時追記の原子性は実機未検証。

5. 二重計上回避方針

セッションログ由来（issue #97）とテレメトリ由来は入力データソースが完全に別物。

結論

別の状態ファイルを持たせ、レポート上も既存のtokensByModelへ合算せず、 別セクション（参考値）として表示する方針を推奨する。既存の安定稼働（issue #97）への 影響を避けるため。

状態ファイルのスコープ: DDR i0097-01はセッションログの前回累計をブランチ非依存の gemini-totals/<sessionId>.jsonへ置いた。テレメトリのoutfileは それ以上に「単一の固定ファイルへ複数ブランチ・複数セッションが書き込む」ため、 状態ファイルはブランチにもセッションにも紐づかない単一のグローバルなバイトオフセット カーソルとする（例: usage/state/gemini-otel-cursor.json）。複数ブランチが 同時並行で作業している場合の貢献の帰属（どのpushへ計上するか）はフェーズ3で確定する。

6. logPromptsの扱い

既定値はtrue（docs/cli/telemetry.mdのキー一覧表で確認。 ソースコードでの既定値確認は未実施）。プロンプト本文がログレコードへ含まれる設計と見られる。

結論（範囲を明確化） logPrompts: falseを明示指定する。ただしlogPromptsが制御するのは 「プロンプト本文」のみであり、tool_callイベントの引数（ファイルパス・シェルコマンド等）や エラーメッセージ本文が抑制されるかは未確認。「安全だから既定ONにしてよい」の根拠には ならない（7.参照）。

7. 既定有効化の可否

issue #103はClaude Code側を配布先全体で既定ONにしている。

結論を保留に修正（敵対的レビュー2回目で発見）

既定ONの前提「出力先はリポジトリへコミットされない」は、本リポジトリの.gitignore だけでは成り立たない。.gitignoreは配布対象ではなく（配布マーカーを 持つのは.gitattributesのみ）、一方.gemini/settings.jsonは install-to-project.shにより配布される。既定ONだけが配布され、それを 安全にする前提は配布されないという非対称があり、配布先で出力ファイルがコミット されうる（Gemini CLI側の制約ではなく本機構側の配布漏れ）。

推奨: 次の2条件が満たされるまで既定ONにしない。(1) install-to-project.sh へ出力先の.gitignore追記を追加する、(2) tool_call等の機微情報残存の有無を 実機確認する。条件が整うまでは任意設定として案内するに留める。

8. ローテーション方針

確認した範囲（file-exporters.ts）にローテーション機構は見当たらず、 実行中プロセスの追記先を安全に切り替える手段も本機構側からは無い（同一inodeへの書き込み継続）。 一方GEMINI_TELEMETRY_OUTFILE環境変数により、起動をラップすれば動的パスの注入は 技術的に可能なことを3.で確認した。

結論 当面ローテーションを実装しない。4.のバイトオフセットカーソルにより集計の正しさは保たれる。 起動ラッパーの新設はDDRの未決定事項として残す。
