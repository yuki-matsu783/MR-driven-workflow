実施した内容と結果

1. 出力ファイル形式

command -v gemini で実機の有無を確認したところ存在しなかった（exit=1）ため、 公式ソースコードを直接確認した。

$ command -v gemini; echo "exit=$?"
exit=1

packages/core/src/telemetry/sdk.tsで、FileSpanExporter / FileLogExporter / FileMetricExporterの3つが**すべて同一のtelemetryOutfile値**で初期化される ことを確認した。packages/core/src/telemetry/file-exporters.tsのコンストラクタは fs.createWriteStream(filePath, { flags: 'a' })（追記モード）、シリアライズは safeJsonStringify(data, 2) + '\n'（インデント2のpretty-print JSON＋末尾改行）。 gemini_cli.api_responseはlogger.emit()によるLogRecordとして記録される （Spanイベントではない。packages/core/src/telemetry/loggers.ts）。

結論 単一ファイル・追記型・spans/logs/metrics混在。「1行1JSON」ではなく、複数行にわたる pretty-print JSONが改行区切りで連続する形式。ローテーション実装は無い。

2. settings.jsonのスキーマ確認

packages/cli/src/config/settingsSchema.tsでtelemetryキーが type: 'object', ref: 'TelemetrySettings'としてトップレベルに 定義されていることを確認した。

telemetry: {
  type: 'object',
  category: 'Advanced',
  ref: 'TelemetrySettings',
  ...
}
結論 telemetryはgeneral配下ではなくトップレベルキー。現行の .gemini/settings.json（general.plan.directory, hooks） と衝突しない。

3. 出力先配置の比較

issue #103は常駐perlリスナー自身が日付ベースでファイルを切り替えて usage/claude-otel-YYYYMMDD.jsonlを実現している。Gemini CLI側の outfileは静的設定の単一固定パスであり、同等の仕組みを持たない。

結論 完全な整合は取れない。出力先は固定ファイル名（例: usage/gemini-otel.log）とし、 整合しない理由をDDRへ記録する。

4. 差分カーソル単位の判定

単一ファイル・追記型・複数行JSON混在という性質から、Claude Code経路の行カーソル方式、 Gemini CLIセッションログ経路の畳み込み方式（DDR i0097-01）のいずれも適さない。

結論 バイトオフセットカーソル（前回処理した末尾バイト位置を記録し、以降を新規として集計）を推奨する。 各エントリは一度しか出力されないため二重計上は起きない。

5. 二重計上回避方針

セッションログ由来（issue #97）とテレメトリ由来は入力データソースが完全に別物。

結論 別の状態ファイルを持たせ、レポート上も既存のtokensByModelへ合算せず、 別セクション（参考値）として表示する方針を推奨する。既存の安定稼働（issue #97）への 影響を避けるため。

6. logPromptsの扱い

既定値はtrue。プロンプト本文がログレコードへ含まれる設計と見られる。

結論 logPrompts: falseを明示指定する。

7. 既定有効化の可否

issue #103はClaude Code側を配布先全体で既定ONにしている。

結論 logPrompts: false前提であれば、telemetry.enabled: trueを既定ONに してissue #103の判断に揃える。

8. ローテーション方針

Gemini CLI本体にローテーション機構は無く、実行中プロセスの追記先を安全に切り替える手段も 本機構側からは無い（同一inodeへの書き込み継続）。

結論 当面ローテーションを実装しない。4.のバイトオフセットカーソルにより集計の正しさは保たれる。
