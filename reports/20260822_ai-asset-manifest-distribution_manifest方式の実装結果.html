設計の要点

層分け定義（.claude/dist-layers.json）

  • パスは git pathspec として git に評価させる（globの意味論を再実装しない）。
  • 例外は .gitignore と同じ 後に書いたエントリが勝つ規約で表す。
  • exclude（配らない）は明示指定を必須とする。暗黙の既定値にすると網羅性チェックが常に通ってしまう。
  • 任意キー requiredLine（seed 専用）で、配布先の既存ファイルが古い形式のままでないかを再適用時に知らせる。

網羅性チェック（4種）

検査見るもの
検査1追跡ファイル全件が分類されているか（分母は git ls-files）
検査2.gitignore の全行が local エントリに載っているか
検査31件も一致しない空振りエントリが無いか
検査4layer / strategy / gitignorePattern / requiredLine の妥当性

配布先（upstream の印が無い定義）では、件数を出したうえでスキップする。

インストーラ（2パス構成）

走査 → 提示 → 配置の順で進む。受け入れ条件4が「上書きの前に警告と対象一覧を出す」ことを 求めており、配置しながら警告を出す1パスの形では満たせない。

  • merge の2方式: lines-marker（.gitignore / .gitattributes）と json-keys（settings.json）。
  • manifest（.claude/.asset-manifest.json）は、本家のコミットSHA＋LF正規化した sha256 で 「適用後に配布先で変更されたか」を判定する。

コマンドライン長の上限（major）

dirty判定が git status へ187パス・28,319バイトを渡していた。Windows の CreateProcess の上限は32,767文字で、数十ファイル増えれば配布が始まる前に止まる。 本家全体の status を1回だけ取り、配布対象かは bash 側の連想配列で突き合わせる形へ変えた。

レビューの提案どおりには直せなかった git status は --pathspec-from-file を持たない（git 2.43 で実測）。 pathspec を渡すのをやめる方向で解いている。

bashの罠を1つ踏んだ（記録）

${!assoc[@]+…} は連想配列のキーの空配列ガードにならない bashが !group[@]+… を間接展開として解釈し、キーではなく値を変数名として扱おうとして invalid variable name で落ちる（最小再現で確認）。インデックス配列の ${a[@]+"${a[@]}"} は問題なく、連想配列のキーだけが別物である。 件数を先に見る形へ直した。
