実施した内容と結果（Q1〜Q8）

Q1. manifest の形式と merge 層の指紋

層レコード形
core{path, layer:"core", sha256}
seed{path, layer:"seed", sha256, placed}
merge（lines-marker）{path, layer:"merge", strategy:"lines-marker", lines:"<sha256>"}（マージ後ファイル全体のハッシュ）
merge（json-keys）{path, layer:"merge", strategy:"json-keys", keys:{"<キー>":"<sha256>"}}
  • sha256 は LF正規化（tr -d '\r'）後の内容に対する値。収穫側も同じ正規化が必須。
  • source.commit は本家dirty時に -dirty サフィックスが付く。
  • local / exclude は manifest に載らない（層判定は manifest の layer キーで足りる）。
結論merge層の指紋は記録のみで読む側が無い（実装コメントで明言）。収穫スキルが最初の読み手になる。

Q2. 置き場所

スクリプトはスキル配下 scripts/、単体テストは .claude/scripts/test/test_install_to_project.sh が前例（passed=N failures=N 規約）。収穫スキルは本家でしか意味を持たないため、apply-mr-workflow-to-project と同じく exclude 層。dist-layers.json へのエントリ追加を忘れると .claude の core エントリに一致して配布されてしまい、網羅性チェックでは気づけない。

Q3. 3-way突き合わせ

$ git merge-file -p merged.txt base.txt theirs.txt   # 終了コード=衝突数、-pで入力を変更しない
<<<<<<< merged.txt
line2-ours
=======
line2-theirs
>>>>>>> theirs.txt
  • base は git show <記録SHA>:<path>。取得不可時は (1) -dirty を落とす → (2) git cat-file -e で存在確認 → 失敗なら 2-way（本家HEAD vs 配布先）へ縮退し「base取得不可（理由）」を明示。-dirty 付き記録は配布内容がどのコミットにも無いため、-dirty を落として解決できても base が配布物と一致しない可能性を出力に明示する。
  • 隣接行の変更（3行ファイルでoursが2行目・theirsが3行目）も衝突扱いになることを実測で確認。ハンクが離れていれば自動マージされ「衝突なし」。
  • 3-way の3入力（base/ours/theirs）には manifest と同じLF正規化を掛ける。実測で、theirs をCRLF化しただけ（内容同一）で衝突マーカー1件が出た（git merge-file -p ours base theirs_crlf | grep -c '^<<<<<<<' → 1）。正規化しないと sha256 比較「変更なし」と 3-way「全行衝突」が矛盾する。
結論git merge-file の終了コードで「衝突なし／衝突あり」を仕分けられる。縮退経路（2-way）と3入力へのLF正規化は必須。

Q4. 縮退モード（manifest無し）の対象列挙

build_plan と同じ方式（dist-layers.json の entries を jq 1回で読み、git ls-files -z -- <pathspec> を本家で評価、「後に書いたエントリが勝つ」）で core/merge の集合を得る。縮退時の比較は2-way（LF正規化）で、added / deleted の確定分類は成立しないため「差分一覧の提示」に留める（分類の確定は Q8）。

Q8. added / deleted の判定と local / exclude 層の除外

manifest（write_manifest）は local / exclude 層を記録しない（「書くと『配布した』と誤読される」と実装コメントで明言）。素朴な差集合は配布先所有物を誤検出する。

分類判定
modifiedmanifest に載っていて（core/merge）、現在のLF正規化 sha256 が記録と異なる
deletedmanifest に載っていて、配布先に実体が無い
added配布対象ディレクトリ配下に在り、manifest に載っておらず、層解決（後勝ち規則）で core に解決されるパス
  • 層解決の適用で local（plans/ 等・gitignoreパターン群）・exclude・seed（manifest に載るため差集合に現れない）が候補から除外される。
  • added 候補のうち本家HEADに同パスが無いものは、「配布先の新規追加」か「本家の削除漏れ（SCAN_CORE_REMOVED は一覧提示のみで削除しない）」かの区別材料（本家の git log --diff-filter=D -- <path> の有無）を添えて提示し、最終判断は人間に委ねる。
  • 探索範囲は配布対象ディレクトリ（core/merge エントリの pathspec 配下）に限る（配布先のアプリ本体を走査しない）。

Q5. 出口レベルの接続点

.claude/rules/markdown-frontmatter.md の「DDRの識別子」節配下。DDR採番規約が集約されており、core 層で配布されるため「配布物のルールに含める」を満たす。常時読込の agent-common.md へ置くほどの知識ではない。

Q7. 判断材料3種

材料取得方法限界・縮退
ai-asset: prefixコミットgit log --format=%s -- <path> の先頭一致非gitリポジトリ・未追跡なら「取得不可」明示。浅い履歴は過小評価
