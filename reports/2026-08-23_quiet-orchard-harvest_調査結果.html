実施した内容と結果（Q1〜Q8）

Q1. manifest の形式と merge 層の指紋

層レコード形
core{path, layer:"core", sha256}
seed{path, layer:"seed", sha256, placed}
merge（lines-marker）{path, layer:"merge", strategy:"lines-marker", lines:"<sha256>"}（マージ後ファイル全体のハッシュ）
merge（json-keys）{path, layer:"merge", strategy:"json-keys", keys:{"<キー>":"<sha256>"}}
  • sha256 は LF正規化（tr -d '\r'）後の内容に対する値。収穫側も同じ正規化が必須。ただし merge/json-keys の指紋はキーごとの jq -c 'getpath(...)' 出力に対する値で、ファイル全体でもLF正規化後でもない。
  • source.commit は本家dirty時に -dirty サフィックスが付く。
  • local / exclude は manifest に載らない（層判定は manifest の layer キーで足りる）。
結論merge層の指紋は記録のみで読む側が無い（実装コメントで明言。scan_pass が manifest を読むのは select(.sha256) と select(.layer=="core")（SCAN_CORE_REMOVED）の2箇所で、いずれも merge エントリには一致しない）。収穫スキルが最初の読み手になる。

Q2. 置き場所

スクリプトはスキル配下 scripts/、単体テストは .claude/scripts/test/test_install_to_project.sh が前例（passed=N failures=N 規約。directory-structure.md の字義とは食い違うが前例に合わせ、文言の更新はフェーズ4で扱う）。収穫スキルは本家でしか意味を持たないため、apply-mr-workflow-to-project と同じく exclude 層。dist-layers.json へのエントリ追加を忘れると .claude の core エントリに一致して配布されてしまい、網羅性チェックでは気づけない。

非対称に注意テスト（.claude/scripts/test/＝core配下）は全配布先へ配られるが、テスト対象のスクリプトは exclude で配られない。前例と同型のスキップガード（対象不在なら skipped:＋passed=0 failures=0・終了コード0）が必須。無いと配布先で恒常的に落ちるテストが1本増える。

Q3. 3-way突き合わせ

実測（mdの「実行検証の記録」1の転写）:

$ printf 'l1\nl2\nl3\n' > base; printf 'l1\nL2\nl3\n' > ours; printf 'l1\nl2x\nl3\n' > theirs
$ git merge-file -p ours base theirs; echo "exit=$?"
l1
<<<<<<< ours
L2
=======
l2x
>>>>>>> theirs
l3
exit=1
$ git merge-file -p ours base nofile; echo "exit_missing=$?"
error: Could not stat nofile: No such file or directory
exit_missing=255
  • 終了コードは 0（衝突なし）／1〜127（衝突数）／≧128（エラー=判定不能）の3分岐で仕分ける。「0以外は衝突あり」と実装すると、エラー（実測255）が「255件の衝突」に誤分類される。-p は入力3ファイルを変更しない（実行前後の sha256 不変を実測）。
  • base は git show <記録SHA>:<path>——成立するのは core 層のみ。merge層は配布直後の内容が本家のどのコミットにも無いため3-wayの対象外（指紋比較まで）。dist-layers.json は del(.upstream) を掛けた内容を base にする。
  • 取得不可時は (1) -dirty を落とす → (2) git cat-file -e で存在確認 → 失敗なら 2-way（本家HEAD vs 配布先）へ縮退し「base取得不可（理由）」を明示。-dirty 付き記録は配布内容がどのコミットにも無いため、-dirty を落として解決できても base が配布物と一致しない可能性を出力に明示する。
  • 隣接行の変更（3行ファイルでoursが2行目・theirsが3行目）も衝突扱いになることを実測で確認。ハンクが離れていれば自動マージされ「衝突なし」。
  • 3-way の3入力（base/ours/theirs）には manifest と同じLF正規化を掛ける。実測で、theirs をCRLF化しただけ（内容同一）で衝突マーカー1件が出た（git merge-file -p ours base theirs_crlf | grep -c '^<<<<<<<' → 1）。正規化しないと sha256 比較「変更なし」と 3-way「全行衝突」が矛盾する。
結論git merge-file の終了コード3分岐で「衝突なし／衝突あり／判定不能」を仕分ける。base の例外（merge層・dist-layers.json）、縮退経路（2-way）、3入力へのLF正規化は必須。

Q4. 縮退モード（manifest無し）の対象列挙

build_plan と同じ方式（dist-layers.json の entries を jq 1回で読み、git ls-files -z -- <pathspec> を本家で評価、「後に書いたエントリが勝つ」）で core/merge の集合を得る。縮退時の比較は2-way（LF正規化）で、added / deleted の確定分類は成立しないため「差分一覧の提示」に留める（分類の確定は Q8）。

Q8. added / deleted の判定と local / exclude 層の除外

manifest（write_manifest）は local / exclude 層を記録しない（「書くと『配布した』と誤読される」と実装コメントで明言）。素朴な差集合は配布先所有物を誤検出する。

分類判定
modifiedmanifest に載っていて（core/merge）、記録済み指紋と異なる。比較は層・strategy 別: core=LF正規化sha256、merge/lines-marker=全体sha256（キー lines）、merge/json-keys=キーごとの jq -c getpath 出力のsha256（キー keys）。merge レコードに sha256 キーは無い
deletedmanifest に core/merge として載っていて、配布先に実体が無い（seed＝配布先所有物の削除は含めない）
added配布対象ディレクトリ配下に在り、manifest に載っておらず、自前のpathspec照合で core に解決され、gitignoreパターン照合でも除外されないパス
  • build_plan の層解決は added へ流用できない（本家の git ls-files で pathspec を展開する方式のため、本家に無いパスは1件も展開されない）。「pathspec 文字列と任意のパス文字列の直接照合」（完全一致＋ディレクトリ前方一致・後勝ち）を自前実装する。
  • path を持たない local エントリ9件（gitignoreパターン群）は path の層解決では除外できない。.claude/state/・settings.local.json・index.jsonl 等が added に誤って混ざるため、gitignorePattern との照合（自前のサブセット実装、git リポジトリなら git check-ignore）を併用する。
  • seed（*.local.md 等）は manifest に載るため差集合に現れない。
  • added 候補のうち本家HEADに同パスが無いものは、「配布先の新規追加」か「本家の削除漏れ（SCAN_CORE_REMOVED は一覧提示のみで削除しない）」かの区別材料（本家の git log --diff-filter=D -- <path> の有無）を添えて提示し、最終判断は人間に委ねる。
  • 探索範囲は配布対象ディレクトリ（core/merge エントリの pathspec 配下）に限る（配布先のアプリ本体を走査しない）。

Q6. DDR運用規約の明文化先

.claude/rules/markdown-frontmatter.md の「DDRの識別子」節配下。DDR採番規約が集約されており、core 層で配布されるため「配布物のルールに含める」を満たす。常時読込の agent-common.md へ置くほどの知識ではない。理由は現行のissue番号ベース識別子に合わせて書く（配布先のissue番号は本家と独立採番のため、配布先で機構DDRを作ると本家の同番号issue由来の識別子と衝突しうる。プロジェクト固有のDDRは従来どおり配布先で書いてよい）。

Q7. 判断材料3種

材料取得方法限界・縮退
ai-asset: prefixコミットgit log --format=%s -- <path> の先頭一致非gitリポジトリ・未追跡なら「取得不可」明示。浅い履歴は過小評価。commitスキルは .claude/scripts/ を ai-asset の対象外にしているため、スクリプト類は規約どおりでも常に0件。規約未準拠の配布先も0件になる——0件を「改善なし」と読ませない提示にする
