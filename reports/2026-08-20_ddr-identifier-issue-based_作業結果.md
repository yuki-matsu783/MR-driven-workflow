## 予定になかった修正

**`check-base-conflicts.sh` の `--help` が行番号直書きだった。** `sed -n '2,30p'` で先頭コメントを
出していたため、今回コメントを増やした時点でヘルプが説明の途中で切れた。行番号を書かず、
「2行目から最初の非コメント行の直前まで」を `awk` で取る形へ変えた。**コメントの増減で範囲が
黙ってずれる作りをそのままにすると、次に同じ壊れ方をする**ため、範囲指定ごと直した。

```bash
# 変更前（コメントを増減させると黙ってずれる）
sed -n '2,30p' "${BASH_SOURCE[0]}"
# 変更後
awk 'NR > 1 { if ($0 !~ /^#/) exit; print }' "${BASH_SOURCE[0]}"
```

### 対応issueの特定（ここが本作業の山だった）

**本文が名乗るissue番号を機械的に信用すると誤る。** このリポジトリはワークフロー機構の
テンプレートとして別プロジェクトから切り出されたもので、古いDDRは**移植元プロジェクトの
issue番号**を書いている。番号だけは本リポジトリのissueとも一致してしまうため、素朴な抽出では
無関係なissueへ紐づく。

| 旧番号 | 本文が名乗るissue | 本リポジトリの同番号issue | 判定 |
|---|---|---|---|
| `0014` | #48「調査結果をHTMLでも残す」 | 「Gitlab.shに実機検証で判明した3件の不具合がある」 | **別物** → `i0000-11` |

git履歴も使えなかった（shallow cloneであり、かつ移植は単一の一括コミット `3f30159` として
入っている）。最終的に、**本リポジトリのissue 78件をすべて取得し、DDRのタイトルと突き合わせて
1件ずつ判定**した。結果は根拠つきの一覧としてユーザーへ提示し、承認を得ている。

- **43件**は本リポジトリのissueへ対応づけできた（例: `0021` → `i0011-01`、`0045`〜`0047` → `i0077-01`〜`i0077-03`）。
- **13件**は対応するissueを特定できなかった。

なお、この特定作業では**一度「3件」と誤って報告し、その後13件へ訂正**している。最初は本文の
issue記載をそのまま信じたためで、上表のような突き合わせを行って初めて誤りが分かった。

### 対応issueを持たない13件（`i00`）

ユーザーの指示により、**`i00` を「対応するissueが無い」ことを表す予約番号**とし、
`i0000-01`〜`i0000-13` を振った。**`i00` の枝番だけは、issueごとではなくリポジトリ全体の通し番号**
である（`i00` は特定のissueを指さないため「同一issue内で01から」という原則が働かない）。

内訳は、移植元のPRから生まれてissueが存在しないもの2件、本文が移植元のissue番号を名乗っていて
本リポジトリでは特定できないもの10件、issue・PRのどちらも記載が無いもの1件。
**新しく `i00-*` を作ることはない**（今後のDDRは必ずissueを起点とするため）。

**一括置換が単体テストのフィクスチャを壊した。** `test_check_base_conflicts.sh` には
`0027-gh_glab-CLI不在時…` と `0027-プロバイダ判定…` という2つのパスがあり、これは

`git checkout -- <file>` で差し戻し、以降このファイルを一括置換の対象から丸ごと除外した。

## 追加対応: issue番号のゼロ埋め（main の issue #135 との統合）

レビュー待ちの間に `main` が **issue #135「`.claude/docs/README.md` のDDR一覧を生成スクリプト化する」**
（PR #139）をマージした。これは本ブランチと**同じ対象を別々に作り変えた**もので、
`resolve-conflict` スキルの**類型E**にあたるため、いったん解消せずに止めてユーザーへ確認した。

### 何が噛み合わなかったか

`generate-ddr-list.sh` は**ファイル名の昇順（`LC_ALL=C` のglob順）**で一覧を出力する。
ゼロ埋めしない識別子では、この順序が数値順にならない。

```
ゼロ埋めなし: i106-01, i109-01, i11-01, i112-01, …, i133-01, i14-01, …, i3-01
ゼロ埋めあり: i0003-01, i0011-01, i0014-01, …, i0106-01, i0109-01, i0112-01, i0133-01
```

本ブランチのREADMEは「issue番号の数値順に並べる」と明記していたので、そのまま取り込むと
**ドキュメントの記述と生成結果が食い違う**。

### 採った解決（ユーザーの判断）

**識別子のissue番号を4桁ゼロ埋めする**（`i133-01` → `i0133-01`）。ファイル名の辞書順が数値順と
一致するため、**`generate-ddr-list.sh` を1行も変えずにそのまま使える**。

| 案 | 評価 |
|---|---|
| 生成スクリプトへ数値ソートを実装する | 453行のスクリプトと366行のテストへ手が入り、issue #133 のスコープを大きく超える |
| 一覧の並びをファイル名順と認め、記述を変える | 一覧の読みやすさを恒久的に捨てる |

### 実装中に踏んだ問題

**`git ls-files` の出力で走査すると、日本語ファイル名のDDRが丸ごと処理から漏れた。**
gitは既定（`core.quotePath=true`）で非ASCIIパスを `"\343\203..."` とクォートして返すため、
そのパスが実ファイルとして開けず**無言でスキップ**される。1回目のゼロ埋めパスで「42ファイル変更」
と出たのにDDR本文が1件も含まれておらず、`superseded_by: "i9-01"` が残っているのを見て気づいた。
`rglob` による直接走査へ切り替えて解決した（**リポジトリの規約
`.claude/rules/shell-script-style.md` が警告している落とし穴そのもの**を踏んだ）。

**一括置換が、直前に書いた単体テストのフィクスチャを書き換えた。** 「ゼロ埋め漏れは弾く」ことを
確かめる `i133-01-ゼロ埋め漏れ.md` が、後から流したゼロ埋めパスで `i0133-01-…` になり、
**弾かれるはずのケースが弾かれず**テストが落ちた。`0027-…` フィクスチャのときと同じ形の事故で、
**「意図的に不正な値」を持つフィクスチャは一括置換と相性が悪い**という同じ教訓である。
