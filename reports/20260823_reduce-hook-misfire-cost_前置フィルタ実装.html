最終的な前置フィルタ（純粋関数、2回目の改訂を反映）:

raw_hints_at_git_commit() {
  local raw="$1"
  local probe="$raw"
  probe="${probe//\\\\/}"   # \\ （エスケープされたバックスラッシュ）を最初に処理する
  probe="${probe//\\\"/}"
  probe="${probe//\\n/}"
  probe="${probe//\\t/}"
  probe="${probe//\\r/}"
  probe="${probe//\\\//}"
  probe="${probe//\\b/}"
  probe="${probe//\\f/}"
  probe="${probe//\\/}"     # 残った単独のバックスラッシュ（\uXXXX 等）
  case "$probe" in
    *[Cc][Oo][Mm][Mm][Ii][Tt]*) return 0 ;;
    *) return 1 ;;
  esac
}

2. 超集合性の確認（改訂後）

結論 git -C /x commit（非連続）・git COMMIT（大文字）・ git com\mit（バックスラッシュ分割——1回目の敵対的レビューで見つかった反例に対する 回帰テスト）・git com\<改行>mit（バックスラッシュ+改行の行継続——2回目 （作業結果）の敵対的レビューで見つかった反例に対する回帰テスト）・\git commit （エイリアス迂回）のいずれも前置フィルタを通過し、精密判定まで到達して実際にブロックされる （exit 2）ことを確認した。逆にgit -C /x pushは正しく足切りされる （jqが呼ばれない）ことも明示的にテストした。

3. jqが1回も呼ばれないことの確認

結論 「呼ばれたら失敗するスタブjq」をPATH先頭へ置き、対象外ペイロード（git -C /x pushを含む）で実際にhookプロセスを起動して確認した。マーカーファイルは空のまま （jqが1度も呼ばれない）でexit 0。時間計測には頼っていない。

確かめられなかったこと

この結果が言っていないこと
  • git bash（Windows）実機でのexecve/clone実測は行っていない（strace非対応）。
  • IFS= read -r -d '' rawは、パイプ入力に対して1バイトずつread(2)する （bashが区切り文字を越えて読み過ぎないための仕様）。60バイト程度の小さいペイロードでは 無視できるが、大きなtool_input.command（ヒアドキュメント等）ではread(2)の 回数が入力バイト数に比例して増える。今回のexecve/clone実測はいずれも小さいペイロード 1件のみで、この特性（大きな入力でのread(2)回数増加）を測っていない （2回目の敵対的レビューで指摘）。git bash（MSYS）はLinuxよりシステムコールのコストが 高いため、大きな入力での実際の遅速はgit bash実機でしか確認できない。実装は変更せず、 shell-script-style.md「hookの前置フィルタ」節へ注記した。
  • 大規模な実運用での体感速度改善は計測していない。
  • bash 3.2実機での動作確認は行っていない（手元に無いため。ブラケット式は仕様上動作するはずだが未確認）。
  • クォート断片の連結による意図的な文字列分割への対応は、精密判定自体が対象外としているため本実装も対応しない（スコープ外）。
