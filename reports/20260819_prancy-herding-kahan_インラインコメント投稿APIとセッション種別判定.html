インラインコメント投稿APIとセッション種別判定

敵対的レビュースキルの設計に入る前に、GitHub・GitLab・MCPの各経路でのインラインコメント投稿と、非対話セッションの機械的な判定方法を実機で確かめた。

調査1 GitHub — 最重要

1件でも不正な行があるとレビュー全体が失敗する

複数指摘を1レビューにまとめられる代わりに、投稿は原子的。有効な指摘まで巻き添えで落ちるため、投稿前の行検証が必須。

調査1 GitHub — 承認モデルへの制約

提出済みレビューは取り消せない

インラインコメント個別は削除できるが、レビュー本体は削除不可（サマリ本文の書き換えのみ）。「投稿は元に戻せない」前提で承認モデルを設計する。

調査3 実行モード判定

AUTOMATION は自動設定されない

対話・非対話のどちらでも未設定だった。ただし明示すれば子セッションのBashまで伝播するため、「AUTOMATION=1 なら非対話」という片方向の運用契約として成立する。

調査2 GitLab

diff_refs だけで position を組める

新規行・削除行・コンテキスト行の3ケースとも投稿できた。ただし glab api --input はContent-Typeを自動で付けない（明示しないと415）。

経路ごとの比較

観点 GitHub（gh api） GitLab（glab api） MCP（mcp__github__*）
呼び出し単位 全指摘を1リクエスト
POST pulls/<n>/reviews		 指摘ごとに1リクエスト
POST .../discussions		 3段階（create → 指摘ごとに追加 → submit）
不正な行があったとき 全件が失敗（巻き添え） その1件のみ失敗 その1件のみ失敗
エラーの識別 Path could not be resolved / Line could not be resolved で区別できる 区別できない（どちらも同じ400 line_code） 理由候補を並べたメッセージが返る
レビュアーへの通知 1回にまとまる 指摘ごとに飛ぶ submit時に1回
ファイル単位コメント レビュー経由は不可（subject_type 非対応） 今回は未検証 subjectType="FILE" で可能
ペイロードの渡し方 --input <file> --input <file> ＋ -H "Content-Type: application/json"（必須） ツール引数
comments からの見え方 unresolved として拾える（path:line 付き） unresolved として拾えるが位置情報が出ない スレッド単位で isResolved を持つ

調査1: 投稿できる行の範囲（GitHub）

✓ 投稿できた

  • 追加行（新規ファイルを含む）
  • hunk内のコンテキスト行（変更されていない行）
  • start_line〜line の複数行指定
  • 日本語を含むパス

✗ 422になった

  • PRで変更していないファイル
    Path could not be resolved
  • 変更ファイル内でもhunkの外の行
    Line could not be resolved

→ 事前検証できる

pulls/<n>/files の patch のhunkヘッダから有効行を算出。HANDOFF.md では 14〜107 の94行と算出され、line=5 の422・line=15 の成功という実機結果と一致した。

注意: patch はファイルが大きい場合にAPIから省略される。その場合は有効行を算出できないため、当該ファイルの指摘はレビュー本文（サマリ）へ回す。

調査3: 実行モードの判定材料

材料 対話（VSCode拡張） 非対話（claude -p） 判定に使うか
AUTOMATION unset unset（明示すれば伝播する） 使う（唯一の材料）
CLAUDE_CODE_ENTRYPOINT claude-vscode sdk-cli 使わない（値の網羅性を保証できない）
TTYの有無 非TTY 非TTY 使えない（差が出ない）

結論

AUTOMATION=1 のときだけ非対話モードとして扱う。「非対話なら必ず AUTOMATION=1」は成立しないが、判定を誤ったときに「勝手に動く」側ではなく「動かない」側へ倒れるため、この非対称性は許容する。未設定・他の値はすべて対話モード（＝AIからの自律起動を禁止）。

フェーズ3の設計へ引き渡すこと

1

投稿前の行検証を純粋関数として実装し、単体テストの対象にする。 GitHubの巻き添え失敗を防ぐため必須。GitLabもエラーの原因を切り分けられないため同じ検証を通す。

2

共通インターフェースの戻り値を「投稿できた件数／できなかった指摘の一覧」に揃える。 GitHub（全件巻き添え）とGitLab（1件のみ失敗）という失敗の粒度の差を、呼び出し側に意識させない。

3

行が特定できない指摘はレビュー本文（サマリ）へ集約する。 ファイル単位コメントの別経路は通知が分散し、経路も二重になるため採らない。

4

gitlab_format_discussion_notes に position の出力を足す改修を作業計画へ含める。 GitHub版は path:line を出すのに対しGitLab版は位置情報を出しておらず、インライン投稿を入れるとこの差が実害になる。

5

MCP経路は「create → 全件追加 → 必ず submit_pending」を手順として明記する。 pending reviewを提出せずに終えると中途半端な状態が残る。失敗時は delete_pending で片付ける。

6

スキルの手順1は AUTOMATION の判定に確定。 未設定は対話モード扱いとし、AIからの自律起動を禁止する。
