最重要の結論

C — 差分の取り方

全体をid単位で畳んで、前回累計との差分を取る

Claude Code式の「新規行のみ加算」は二重計上する。 同一idが複数行に現れ、$set が全メッセージを再送するため。

S — 切り詰め

対応は不要だった

ファイル書き直しで10行→6行に減っても、畳み込み後の累計は完全に一致。 行番号ではなく内容を基準にするため、問題自体が消えている。

K — 変更範囲

Claude Code側は無改造

sync_usage_state に分岐を1つ足し、Gemini専用関数を2つ新設するだけ。 「既存の集計結果が変わらない」ことを構造で担保する。

issue本文・参考実装の前提が覆った点

観点 当初の前提 確定した事実
形式 単一のJSONオブジェクト（issue本文） 追記型JSONL（v0.39.0〜）
トークン 相当フィールドが無い（issue本文） input / output / cached / thoughts? / tool? / total が実在
ツールの status success / error|failed / pending|running（Rustパーサ） validating / scheduled / executing / awaiting_approval / success / error / cancelled
failed・pending・running は存在しない。cancelled が存在する。
ブランチ帰属 1行目の directories が使えるかも（flow-id 1-4の見込み） 使えない。 directories は /dir add で追加されたワークスペースであり cwd ではない

調査項目ごとの結論

# 項目 結論
A形式の裏取り確定。status の値集合が参考実装の想定と違っていた。再書き出し経路は2つあり、いずれもメッセージを失わない
Bhookペイロード確定。transcript_path は実ファイルのフルパス。代替探索は不要
C差分の取り方(a) 全体をid単位で畳んで前回累計との差分
D$rewindTo集計から外さない（課金・ツール実行は起きているため）
Eブランチ帰属push時点の git branch --show-current。限界を明示する（セッション内でブランチを切り替えると混ざる）
Fトークン列Gemini専用の列構成（Cache Write を出さず、Thoughts・Tool を出す）
G投稿要否ガードトークン・ツール実行回数・応答回数のいずれかが0より大きければ投稿
Hツールエラーerror のみ。cancelled は実行回数に含めるがエラーにしない
Iサブエージェント今回は保存のみ。specの既存の懸念（親と同じセッションIDでは？）は解消できる
K既存経路の分岐点sync_usage_state に分岐1つ＋Gemini専用関数2つ。Claude Code側は無改造
L・M・P（欠番）テレメトリのスコープ除外に伴い削除（決-5。issue #105 へ切り出し）
N既存テストの型source ＋一時ディレクトリ＋assert_eq＋passed=N failures=N
O行カーソル / push-index差分計算には使わない。早期リターンは畳み込み後の差分が0かで判定
Q稼働時間timestampで並べ直してからgapを積む。閾値定数は流用
R応答回数・使用モデル畳み込み後のユニークid数 / model の集合
S消失・切り詰め切り詰めは対応不要（(a)が本質的に耐性を持つ）。消失は負値で検知しリセット

確かめられなかったこと（未検証）

Gemini CLI実機でのエンドツーエンド動作

この開発機に ~/.gemini が存在しない。確定させるには、Gemini CLIをインストールしてfeatureブランチ上で実際にリモートへ反映し、レポートが投稿されることを確認する。

hookが実際にこのペイロードで発火するか

型定義・組み立てコードでは確定したが、実行時の値は未確認。AfterTool hookで受け取ったJSONをそのまま保存して突き合わせる。

$set.messages が実際に出る条件

型と読み込み側の存在は確認したが、書き出し側で messages を含む $set を出す箇所は特定できていない。ただし出ても出なくても畳み込みは正しく動く（検証1で確認済み）ため、設計上のリスクは無い。

別バージョンでの形式の安定性

0.56.0-nightly の1点のみで確認。形式変更に備え、パースに失敗しても集計が0になるだけで壊れないこと（検証5）を保証しておく。

これらはフェーズ4で .claude/docs/spec/issue-mr-workflow.md の「未決定事項・懸念点」へ反映する。

フェーズ3への申し送り

  • ▸新設する関数は _usage_gemini_fold と _usage_gemini_merge_state の2つ。既存関数は sync_usage_state の分岐追加以外は触らない。
  • ▸_usage_gemini_merge_state は既存の [0, (cur - prev)] | max パターンを全指標へ拡張しつつ、負値が出たことを needsReset として上位へ返す点が異なる。
  • ▸レポート組み立てはエンジンごとにトークンテーブルの列構成を切り替える必要がある。
  • ▸ディレクトリをグロブする場合は session-*.jsonl で絞り、*.unreadable-* *.tmp-* を拾わないこと。
  • ▸DDRに残す判断: C（差分の取り方）・D（$rewindTo）・E（ブランチ帰属と限界）・F（トークン列）・I（サブエージェントの非対称）・S（切り詰めが問題にならない理由）。
