判定方式の候補比較

(a) 行分割 → 行頭のみ

不採用

受け入れ条件が名指しする cd src && … を落とす。

(b) セパレータ分割 → 各部分の先頭

不採用

クォート内に ; や && が現れた瞬間に誤検知へ戻る。地の文は自由文なので保証が無い。

(c) クォート追跡 + 正規化

採用

受け入れ条件の3グループを同時に満たせる唯一の案。約280行。

(c) の処理の流れ

  1. 1 正規化 — クォート・コメント・ヒアドキュメント本文をプレースホルダ _ へ潰す。ダブルクォート内の $( ) と `　` だけはコードとして展開し直す。
  2. 2 走査 — トークンへ割り、コマンド位置にある git の直後の非オプショントークンが目的のサブコマンドかを見る（-c/-C は値を1つ取るので2つ飛ばす）。
  3. 3 保守的フォールバック — 位置判定で外れても、コード文字列を受け取りうる実行系がコマンド位置にあり、かつ従来の部分一致が成立するならブロックする。

${s:i:1} による走査はロケールに関係なく二乗で伸びた。 「マルチバイトロケールだから遅い、LC_ALL=C にすれば直る」という当初の見込みは、実測では効果が無かった。

CRの影響（issue #94 からの申し送りへの回答）

結論: tr -d '\r' は不要。ただし理由は issue #94 のときとは違う。

issue #94 の理由は「[[:space:]] がCRにもマッチするので判定が変わらない」だった。位置ベースではこの理由は成り立たない。 新方式では判定側でCRを空白として扱うことで同じ結論に至る （トークン分割の IFS に \r を含める／ヒアドキュメントの区切り行を比較する前に末尾の \r を落とす）。どちらもbash組み込みでforkは増えない。

扱わないと何が壊れるか

cd src && git commit -m x\r\nls でトークンが commit\r になり、サブコマンド名の一致が外れて素通りする（最も避けたい方向の失敗）。単体テストにこのケースを入れてある。

検証は、スタブ jq（最終行以外の行末へCRを付ける）をPATHの先頭へ置いて20ケースを再実測し、CRなしのときと1件も結果が変わらないことで行った。
