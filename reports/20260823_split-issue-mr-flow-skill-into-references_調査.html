C-0. DDR i0113-01 が同じ材料を却下した理由は、本件にも当てはまるか

i0113-01 の却下文（原文）:

判定を HANDOFF.md の進捗表の有無で行う。…HANDOFF.md はリセット直後（flow-id 5-3 の直後）や ブランチ作成直後には空であり、フローの最初と最後で取りこぼす。また表の書式の変更に判定が引きずられる。
却下理由本件に当てはまるか理由
(1) フローの最初と最後で取りこぼす当てはまらない 失敗時の損失が非対称である。 i0113-01 の判定対象は「SKILL.md を読み直させるか」で、取りこぼすと手順が丸ごと失われる。 本件は「どの参照ファイルを名指しするか」で、取りこぼしても1行が出ないだけ。SKILL.md 本文は従来どおり読み直され、 参照ファイルは全体フロー表に明記されているので表から自力で辿れる。加えて取りこぼす時期（進捗表が空）は、 そもそも名指しが要らない時期と重なる
(2) 表の書式の変更に引きずられる当てはまる。ただし解消できる 書式の正は既に update-handoff-progress.sh の parse_table_row_to_reply が持っている。 同じ正規表現を共有すれば二重管理にならない。 パースできなければ空を返す（fail-open）
結論 採用してよい。 ただし本件は i0113-01 の判定（対象ブランチか）を置き換えるものではなく、その上に足す。 この非対称の議論は DDR へ残す。

C-1 / C-2. 現在地flow-idの解決方式と縮退

個別調査計画が当初書いていた「awkで最初の [] 行を採る」方式は誤りだった。 本ブランチの HANDOFF.md は 1-5（人間の合意）が [] のまま 1-6 が [x] である。

単純な最初の[] : 1-5   ← 誤り
最後の完了の次  : 2-1   ← 正しい
縮退ケース入力返り値扱い
(i) 進捗表そのものが無いcleanup-task.sh のテンプレート空行を注入しない（fail-open）
(ii) 全行が []着手直後1-1先頭から始める
(iii) 穴あき・[-] 混在[x] 1-6 / [-] 2-1 / [-] 2-2 / [] 3-13-1正しい
(iv) 書式が想定と違うパースできない行空行を注入しない（fail-open）
結論 採用する方式は「最後の [x] または [-] の行より後に現れる、最初の [] の行」。 穴あきは例外ではなく既定である（非対話セッションでは人間担当のステップが [] のまま残り、ループ範囲も1周完了まで [] のまま）。

  • git bash（MSYS）上での C・D の再現。 本調査はLinux上のリモート実行環境で行った。 とくに awk の実装差（gawk vs mawk vs busybox awk）は C-3 の列抽出に影響しうる。

  • (d) パスのみの参照154箇所を1件ずつは読んでいない。 「SKILL.md 自体は同じパスに残るのでリンクは切れない」という性質から機械的に対応不要と判断した。 ただし spec/issue-mr-workflow.md:53 のディレクトリツリー図のように、パスは切れないが記述としては古くなるものが混ざりうる。
  • .gemini/ 側。 .claude/ 配下へのローカルリンクであり実体を編集すれば足りるが、この環境にリンクが張られていないため動作は確認していない。

設計への反映

  1. 分割は案1（「いつ読むか」で切る）を採用する。 A-3 では案を選べず（どちらも39件）、E-2/E-3 が決め手になる。この経緯は DDR へ「サイズだけで機械的に割る案を却下した根拠」として残す。
  2. 全体フロー表へ「参照」列を追加する。 hookの対応表はここから抽出し、二重管理しない（C-3）。
  3. SessionStart hook の現在地解決は「最後の [x]/[-] の次の []」とし、解決できないときは行を出さない。書式の正規表現は update-handoff-progress.sh と揃える（C-0 の (2) への対処）。
  4. DDR i0113-01 との整合を DDR へ書く。根拠は「失敗時の損失が非対称であること」であり、i0113-01 を否定するものではない（C-0）。
  5. markdown-frontmatter.md の type 表への追記はフェーズ3へ前倒す（C-5）。値を新設するか流用するかはフェーズ3の個別作業計画で決める。
  6. 参照追従の対象は (c) の47件＋折り返し2件に限定する。 (a) DDR本文8件は書き換えず、旧節名→新パスの対応表から辿れるようにする（B-3）。
  7. 参照元を数えるときは git grep を使う（配布用 assets/ の複製が母集団を倍にする。B-1）。この落とし穴は spec か rules へ残す価値がある。
  8. フェーズ3で追従させる実装は3箇所＋テスト2本（D-1/D-3）。検証は .claude/scripts/test/ 配下の全テストを回して合計 failures=0 を条件にする。
