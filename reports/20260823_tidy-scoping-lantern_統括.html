3. 作業中に判明して直したもの（issueの要求外）

いずれも既存の検査・記述が誤っていたもので、issue #54 の作業に取りかからなければ 表面化しなかった。

  1. 自己完結の検査が、正しい成果物を不合格にしていた。 grep -c 'https\?://' が0という形は、本文で <code> にURLを引用しただけの レポート（実測3件）と http://www.w3.org/2000/svg（createElementNS の 名前空間。実測4件）を必ず誤検知する。属性・CSSからの外部読み込みだけを見る2本立てへ改め、 シングルクォート・プロトコル相対・@import まで拾う形にしたうえで、 拾えないもの2つ（相対パスのローカル参照・<code> 内でHTML属性ごとURLを 引用した箇所）を限界として明記した。
  2. 埋め忘れの検査が、テンプレート自身を説明する成果物を誤検知していた。 grep -c '<!-- ここに書く' へ揃えた（<!-- を含めないと地の文の 「ここに書く」に当たる）。
  3. 既存の成果物1件が、その検査に当たっていた。 reports/…HTMLビュー前提調査.html が <code> 内で &lt;script src="https://…"&gt; を引用しており、新旧どちらの検査でも ヒットしていた——つまり reports/REVIEW-POINTS.md の「0件であること」を、 自分たちの成果物が満たしていない状態で通していた。URLのスラッシュを &#47;&#47; と書く（表示は変わらない）形へ直して0件へ戻した。
  4. create-commit.sh の挙動が仕様書のどこにも無かった。 「渡したパスに加えて、既にステージ済みの変更も同じコミットへ入る」。フェーズ3で git mv によりステージ済みだったディレクトリ改名が別のコミットへ混ざって気づいた （同一ブランチかつsquash mergeのため実害は無かったが、コミットメッセージと中身が食い違った）。 スクリプトの挙動は変更していない。

設計への反映

反映しきれず次のissueへ回したものを書く（テンプレートの「フェーズごとの読み替え」に従う）。

  1. install-to-project.sh に「上流で消えたファイルの削除」を持たせるかは、 issue #26 の判断へ委ねた。 事実は spec/issue-mr-workflow.md のchangelogと spec/distribution-assets.md の両方へ記録し、#26 へマージ前通知として コメント済み。新規issueは起票しない（ユーザーの判断）。
  2. assets という語が二義的になっている点も #26 へ通知した。 恒久の バンドルリソース（Git管理下）と、sync-assets.sh が生成するビルド用一時 ディレクトリ（.gitignore 対象）が同じ名前を持つ。現状の .gitignore は 先頭スラッシュでパスを固定しているため衝突しないが、相対パターンへ広げると恒久の テンプレートが無言でGit管理から外れる。
  3. 報告HTMLの方式変更を issue #114 へ通知した。 同issueは対象を「TailwindCSS CDN方式の 自己完結HTML」と書いており、前提が変わった。ホスティング設計はむしろ単純になる（外部依存ゼロ） 一方、canvas形式で mermaid を使う場合だけ CDN の <script src> が1本残る。
  4. .claude/VERSION は 0.1.2 のまま据え置いた。 配布対象アセットは 増えたが、ユーザーの判断。規定の例外にあたるため spec/distribution-assets.md 側にも 据え置きの扱いと実害を記録した。次に配布物を触るissueで、まとめて増分を検討することになる。
  5. create-commit.sh の挙動の是非（パス指定コミットにすべきか）は独立した 意思決定である。 変えるなら別issueを起票する。この判断が読解によるもので実測して いないことは spec/create-commit.md の ### なぜパス指定でコミットしないのか へ書いた。
