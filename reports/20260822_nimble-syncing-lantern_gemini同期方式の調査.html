Q1. agents frontmatter — 本issueの本題

結論: 原因は tools だけではない。現行ファイルは3系統の理由で必ず弾かれる。

理由 1 （S）
ツール名が Gemini の語彙でない
Read, Grep, Glob, Bash

issue #70 が把握していたのはこれだけ

理由 2 （S+M）
tools が配列でない
tools: Read, Grep, …

YAMLではスカラー文字列。z.array() を満たさない

理由 3 （S）
.strict() が未知キーを拒否
title / type / tags / keywords

本issueが見落としていた欠陥

ツール名だけを変換しても、title 等が残っている限りロードは失敗し続ける。 変換規則は「置換」ではなく「許可キーだけを通すホワイトリスト」でなければならない。 ブラックリストにすると、.claude/rules/markdown-frontmatter.md にキーが1つ増えるたびに Gemini 側が壊れる。

バリデーション実装（packages/core/src/agents/agentLoader.ts L91–L116）

const localAgentSchema = z
  .object({
    name: nameSchema,                       // /^[a-z0-9-_]+$/
    description: z.string().min(1),
    tools: z
      .array(                               // ← 配列であることが必須
        z.string().refine(
          (val) => isValidToolName(val, { allowWildcards: true }),
          { message: 'Invalid tool name' }, // ← issueのエラー文言はここ
        ),
      ).optional(),
    model: z.string().optional(),
    temperature / max_turns / timeout_mins / mcp_servers / display_name / kind
  })
  .strict();                                // ← 未知キーを拒否する

黄色の4行が現行2ファイルで実際に使われているもの（M）。

  • 対応表に無いClaudeツール名が現れたら、変換スクリプトは黙って落とさずエラーにする。黙って落とすと、Gemini 側のエージェントが必要な権限を失ったまま静かに動く。
  • model はスキーマ上 z.string() なので sonnet/opus は通ってしまう。弾かれないぶん、かえって危ない。変換ではなく除去して inherit（既定）に委ねるのが安全。

エラー添字 tools.0 との食い違い（U）

issueのエラーは tools.0＝配列として解釈されたうえで0番目が不正を示すが、現行ファイルの tools は文字列である。報告時の環境では YAML の配列記法で書かれていた可能性が高い。実機が無いため確定できないが、どちらでも上記3系統の変換は必要で方針は変わらない。

Q2. skills は読まれるか

結論: 読む。かつ変換は不要（そのままコピーでよい）。

agents — 厳しい
  • スキーマ: zod + .strict()
  • 未知キー: 拒否
  • 変換: 必要
skills — 寛容
  • スキーマ: 手書き（name/descriptionのみ抽出）
  • 未知キー: 無視
  • 変換: 不要（コピーのみ）

この非対称は覚えておく価値がある。「Gemini は Claude の記法を受け付けない」と一括りにするのは誤りで、厳しいのは agents だけ。skills まで変換対象に含めると、情報を落とすだけで得るものが無い。現行 .claude/skills/*/SKILL.md 全9件が name を持つことを確認済み（M）。

Q3. settings.json の写像

結論: 現行の手書き .gemini/settings.json は10項目すべて正しい → ゴールデンファイルとして単体テストに固定できる。

if の畳み込みで落ちるもの — 機能等価ではない

.claude 側は post-push-* の2本を if: "Bash(git push*)" が真のときだけ起動する。 Gemini には if が無いため、シェル呼び出しのたびに毎回この2本が起動する。

ただし実害は限定的（M）。両スクリプトは自身でも tool_input.command を再チェックし（command_invokes_git_subcommand）、pushでなければ即 exit 0 する。

落ちるのは正しさではなく性能。git bash の外部プロセス起動 約95ms/回 を当てると、シェル1回あたり約190msの上乗せ。 「等価な変換」と書くと、将来スクリプト側の自己チェックを外した人が Gemini 側だけ静かに壊す。specとコメントへ必ず書く。

Q5. 同期の実行位置（flow-id の採番）

issueの前提が古い。 issue #70 は「現行 flow-id 5-3（片付け）の直前へ新設」と書くが、issue #111（最終統括レポート）が 5-3 を占めたため、現在の片付けは 5-4。見積もりの「29ファイル・161箇所」も変わっている。

94箇所は下限である。HANDOFF.md の進捗表・update-handoff-progress.sh の LOOP_RANGES 定数・cleanup-task.sh のコメントなど、flow-id 接頭辞を伴わない参照が別にある（217との差がそれを示す）。うちDDR内18箇所は本文不変のため更新対象外。

案A. 新規 flow-id を挿入
繰り下げ: 94〜217箇所

表に明示され飛ばしにくい。だが1箇所の漏れでHANDOFF.mdの進捗表と噛み合わなくなる。過去2回（#112 / #111）の繰り下げは既に負債（DDR i0028-01 は当時の番号のまま note で補足）。

案B. 片付け（5-4）へ統合
繰り下げ: 無し

追加コスト最小。だが責務が違う——片付けは「タスク固有のファイルを消す」、同期は「.claude→.gemini を再生成する」。--dry-run の意味・失敗時の扱いが混ざる。

案C. 並行手順（推奨）
繰り下げ: 無し

既に4つの先例（REVIEW-POINTS収集・PR追従監視・ベース追従確認・敵対的レビュー）。表に出ないぶん忘れうるが、--check をpush直後に走らせて非0で落とすことで補う。

案C を推す3つの理由

  1. 確立した前例がある。SKILL.md は追従監視の節で「flow-idは増やさない」と明示し、DDR i0088-01 がその判断を記録している。同じ性質（タスクの進行と直交する、状態を揃える作業）を別扱いにする理由が無い。
  2. 繰り下げのコストが得るものに見合わない。issue #70 自身も代案を用意している。
  3. 忘れる問題は番号でなく --check で解く。案Aでもステップは飛ばされうる（記号を付けるのは人間／AI）。

ただしこれは推奨であって決定ではない。フローの見え方に関わるので、フェーズ3の個別作業計画のレビューで人間の合意を取る。
