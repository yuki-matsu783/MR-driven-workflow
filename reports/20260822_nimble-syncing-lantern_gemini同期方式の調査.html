Q1. agents frontmatter — 本issueの本題

結論: 原因は tools だけではない。現行ファイルは3系統の理由で必ず弾かれる。

理由 1 （S）
ツール名が Gemini の語彙でない
Read, Grep, Glob, Bash

issue #70 が把握していたのはこれだけ

理由 2 （S+M）
tools が配列でない
tools: Read, Grep, …

YAMLではスカラー文字列。z.array() を満たさない

理由 3 （S）
.strict() が未知キーを拒否
title / type / tags / keywords

本issueが見落としていた欠陥

ツール名だけを変換しても、title 等が残っている限りロードは失敗し続ける。 変換規則は「置換」ではなく「許可キーだけを通すホワイトリスト」でなければならない。 ブラックリストにすると、.claude/rules/markdown-frontmatter.md にキーが1つ増えるたびに Gemini 側が壊れる。

バリデーション実装（packages/core/src/agents/agentLoader.ts L91–L116）

issueのエラーは tools.0＝配列として解釈されたうえで0番目が不正を示すが、現行ファイルの tools は文字列である。報告時の環境では YAML の配列記法で書かれていた可能性が高い。実機が無いため確定できないが、どちらでも上記3系統の変換は必要で方針は変わらない。

Q2. skills は読まれるか

結論: 読む。かつ変換は不要（そのままコピーでよい）。

agents — 厳しい
  • スキーマ: zod + .strict()
  • 未知キー: 拒否
  • 変換: 必要
skills — 寛容
  • スキーマ: 手書き（name/descriptionのみ抽出）
  • 未知キー: 無視
  • 変換: 不要（コピーのみ）

この非対称は覚えておく価値がある。「Gemini は Claude の記法を受け付けない」と一括りにするのは誤りで、厳しいのは agents だけ。skills まで変換対象に含めると、情報を落とすだけで得るものが無い。現行 .claude/skills/*/SKILL.md 全9件が name と description の両方を持つことを確認済み（M）。ローダは両方が揃って初めてスキルとして成立させ、片方でも欠けると簡易パーサへ落ち、そこでも取れなければそのスキルは丸ごと捨てられる。

Q3. settings.json の写像

結論: issue #70 の10観点のうち8つで正しい。permissions は誤り、SessionStart matcher の縦棒つなぎは未確認。そのままではゴールデンファイルにできない。

「10観点で正しい」と「ゴールデンファイルにできる」は別の主張である。前者は issue #70 が列挙した観点の網羅、後者は変換元の全キーが写像先に説明できていることを要求する。次の3つは10観点の外にあり未判定のまま残っている:
  • autoCompactWindow: 600000 — 表のどこにも現れず .gemini 側にも無い
  • PostToolUse のグループ構造（2グループ→1グループ）と mcp__github__issue_write の脱落
  • .gemini 側 AfterTool のエントリ数（3）と、if 行の「2エントリへ集約」という記述の食い違い

未判定を抱えたまま固定すると、変換スクリプトが情報を落としていることを単体テストが永久に緑で通す。

落ちるのは正しさではなく性能。ただし当初の「シェル1回あたり約190ms」は hook 1本＝プロセス1つと数えた誤りで、撤回する。 早期returnの経路でも各hookはコマンド置換とjqを回す（.claude/rules/shell-script-style.md「コマンド置換・パイプもサブシェルをforkする」）。

上乗せは「2プロセス」ではなく「10プロセス超」の桁。95ms/回（Windows git bash の値。この調査環境の値ではない）を当てるとシェル1回あたり1秒近くになりうる。 正確な値はフェーズ3で実測する（見積もりのまま spec へ転記しない）。「等価な変換」と書くと、将来スクリプト側の自己チェックを外した人が Gemini 側だけ静かに壊す。

Q5. 同期の実行位置（flow-id の採番）

結論: 案A（新規 flow-id を新設し繰り下げる）。挿入位置は最終統括レポートの直前 → 新設 5-3。

チャットでのレビューで決着した（2026-08-22）。 ユーザーの指示は「flow-id は issue #111 に合わせて」、続けて「最終統括レポートの前が良いな」。 すなわち issue #111（統括レポートの追加）とまったく同じやり方で繰り下げる。当初の推奨だった案Cは取り下げる。 issue #70 本文の「5-3（片付け）の直前」は、#111 以降の番号へ読み替えたうえでさらに1つ手前になる。

① 生成の直後に確定が来る

旧 5-3（統括レポート）は自前で commit・push するステップなので、同期で生えた .gemini/** はその commit に載る。同期ステップ自体は commit を持たない（片付け → commit と同じ既存パターン）。片付けの直前へ挿す案では、生成と commit の間に片付けが挟まっていた。

② 統括レポートが最終形を書ける

.gemini/ を再生成してからレポートを書くので、「このブランチで何が変わったか」に同期結果が含まれる。

③ mainからの取り込みを拾える

5-1 のコンフリクト解消で main から入った .claude/ の変更を、確実に再変換できる。

issue #112 の制約を壊さない。 SKILL.md は片付けについて「このステップを commit の直前へ置くのは、生成と確定の間に他のステップを挟まないため」と定めているが、新設ステップは片付けより前にあるため、片付けと commit は隣接したままである。

依存関係: 同期を片付け（cleanup-task.sh）より前に置く以上、Q4-B の「extract-frontmatter.sh に .gemini 除外を足す」は必須の前提条件になる。片付けは index.jsonl を再生成するため、除外が無いとその最中に .gemini/**/index.jsonl が生える。
