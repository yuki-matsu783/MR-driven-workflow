get_branch_work_files の改名対応

issue #115 — 改名されたファイルが "旧パス" -> "新パス" の1行で返り、 パス一覧として扱えない問題の修正結果

受け入れ条件 5/5 充足 passed=140 failures=0 単体テスト 131 → 140 ケース DDRは起こさない

結論

未コミット分の取得を git status --porcelain（行単位）から --porcelain -z（NUL区切り）へ移し、その分解を純粋関数 porcelain_z_to_paths へ切り出した。出力は常に 「1行＝1つの実在するパス」になり、改名されたファイルは新パスのみが返る。 改名が無い場合の出力は従来と同一。

なぜ -z なのか（行単位形式は原理的に曖昧）

パス自体が  ->  を含む改名を実機で作ると、行単位形式は次のようになる。 

$ git -c core.quotepath=false status --porcelain -- plans | sed -E 's/^...//'
"plans/arrow -> old.md" -> "plans/arrow -> new.md"   ← ` -> ` が3回。さらにクォートされる

$ git -c core.quotepath=false status --porcelain -z -- plans | porcelain_z_to_paths
plans/arrow -> new.md
  • 「最後の -> で分割」「最初の -> で分割」のどちらの自作パーサも壊れる。
  • 空白を含むパスはダブルクォートで囲まれるため、アンクォート処理まで必要になる。
  • -z なら改名エントリは XY <新パス>\0<旧パス>\0 の2フィールド。 行単位形式とは順序が逆で新パスが先、クォートも無い（od -c で実機確認）。

この「クォートされる」「-> はパスにも現れうる」はissue本文に無かった追加の発見で、 -z へ移す判断の決め手になった。
