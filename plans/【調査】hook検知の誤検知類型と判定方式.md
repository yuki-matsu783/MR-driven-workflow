# 【調査】hook検知の誤検知類型と判定方式

- issue: [#53](https://github.com/yuki-matsu783/MR-driven-workflow/issues/53)
- 全体作業計画: `plans/hook-command-position-detection.md`
- フェーズ: 2〈調査〉（flow-id 2-1）

## 目的

「コマンド位置での判定」へ置き換えるにあたり、**どこまでシェル構文を解釈するか**の線引きを
決めるための材料を揃える。線引きを誤ると、issue #53 の受け入れ条件5が言う「素通りリスクが
改善効果を上回る」状態になり、対応しないほうがよいという結論になりうる。

## 調べること

### 1. 現行の検知の実態

- 4つのhook（`block-direct-git-commit.sh` / `post-push-usage-report.sh` /
  `post-push-compact-prompt.sh` / `post-issue-create-notice.sh`）が、それぞれ
  `tool_input.command` をどう検査しているか。
- `.claude/settings.json` の `hooks` エントリの `matcher` / `if` との二段構えがどうなっているか。
  **コミット側に `if` が無く push側にはある**という非対称（issue #53 のコメントで指摘済み）を
  コードで確認する。
- 現行の判定が消費するfork回数。

### 2. 誤検知・検知漏れの類型

「該当語がコマンド文字列に現れるが、実際には実行されない」ケースと、その逆を列挙する。
最低限、受け入れ条件が名指ししている次を含める。

- 誤検知（ブロックされるべきでない）: ヒアドキュメント本文／クォート内の文字列リテラル／
  日本語の地の文（コメント含む）／該当文字列を検索する `grep` 等。
- 正検知（ブロックされるべき）: 単体実行／`cd src && ...` の複合／改行区切りの2行目。
- **検知漏れになりうる構造**（新方式で新たに素通りしうるもの）を、実装前に洗い出す。
  `bash -c "..."`・`eval "..."`・`$( )` によるコマンド置換・`xargs`・`find -exec` など、
  **文字列リテラルの中身がコードとして実行される**構造が該当する。

### 3. 判定方式の候補比較

少なくとも次の3案を、実装コスト・素通りリスク・誤検知残存の観点で比較する。

- (a) 行分割 → 各行の先頭だけを見る
- (b) セパレータ（`;` `&&` `||` `|` 改行）で分割 → 各部分コマンドの先頭を見る
- (c) クォート・ヒアドキュメント・コメントを追跡して正規化 → 正規化後にコマンド位置を判定

### 4. CRの影響（issue #94 からの申し送り）

issue #94 では「4hookには `tr -d '\r'` を足さない」と判断した。根拠は
「`grep -qiE 'git[[:space:]]+commit'` は `[[:space:]]` がCRにもマッチするため判定が変わらない」
だった。**位置ベースの判定ではこの前提が崩れうる**ので、次を確かめる。

- 新方式でCRが判定結果を変えるか（変えるなら、どの入力で）。
- 対処を `tr -d '\r'`（fork1回）で行うか、判定側でCRを空白扱いすることで行うか。
- Windows実機なしで検証する方法（`.claude/rules/shell-script-style.md`「テスト」節のスタブ `jq`）
  が今回にも使えるか。

### 5. 性能

- hookは毎ツール呼び出しで走る（コミット側は `if` が無いので**必ず**走る）。
- 新方式のfork回数を現行と比較する。増えるなら、増分に見合うかを判断する。

## 調べないこと

- 悪意ある回避（意図的な文字列分割等）への耐性。DDR `i0000-09` のとおり、これは敵対的な
  安全境界ではないため。
- `.claude/settings.json` の `permissions.deny` 側の挙動。`.claude/rules/ai-command-style.md`
  が「`allow` 側は未確認」と記録しているが、本issueの対象はhookスクリプトの判定であり、
  権限設定の照合規則ではない。
- push検知hookの `if` フィルタ自体の緩和。**現行より発火が増える方向の変更**であり、
  本issue（誤検知を減らす）とは向きが逆なので扱わない。
