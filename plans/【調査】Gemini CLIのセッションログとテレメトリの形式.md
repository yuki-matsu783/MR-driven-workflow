## 目的

`.claude/hooks/lib/UsageTracking.sh` をGemini CLIへ対応させる**実装方針を、フェーズ3の個別作業計画
（flow-id 3-1）が書ける粒度まで確定させる**こと。

このissueは着手時点で**issue本文の前提が2点覆っている**（全体作業計画「着手時点で判明した、
issue本文の前提のズレ」節。flow-id 1-4で記録・1-5で承認済み）。

1. セッションログは単一JSONではなく、Gemini CLI v0.39.0以降は**追記型JSONL**である。
2. **トークン相当のフィールドは実在する**（`tokens: {input, output, cached, thoughts, tool, total}`）。

したがって本調査は「形式が何か」を一から調べるのではなく、**上記の裏取り**と、**それを踏まえた
設計上の分岐点の決定**が主眼である。

**ただし前提1には例外がありうる。** Gemini CLI本体には、ファイル全体を書き直す経路
（`rewriteConversationFile`）と、レガシー `.json` から `.jsonl` へ移行する経路が存在する。
どちらも**行数が減る／対象ファイルのパスが変わる**ため、「追記型だから行番号は単調に増える」と
決め打ちしない（調査項目A・O）。

**issue #97 の本文は修正しない**（決-6）。ただし期待する動作3の「トークン数は……レポートから
省略する」には従わず、本文の但し書き「取得できるフィールドが実在すれば計上する」に従って
**トークンを計上する**方向で調査・設計する（調査項目F）。

対応先を割り付ける。**

| H | **ツールエラーの計上方法**: `status == "error"\|"failed"` を計上。`pending`/`running` の扱い（未完了として計上しないか） | 期待する動作2（**ツール実行回数・ツールエラー回数**） |

| I | **サブエージェントの扱い**: 本体側は `chats/<親sessionId>/<完全なsessionId>.jsonl` へネストする。集計対象に含めるか、保存のみに留めるか | 期待する動作6 |

### 実行面（**結論そのものを検証する**）

このフェーズではコードを変更しないため、既存テストは何を調査しても通る。したがってそれだけでは
調査の妥当性を確かめたことにならない。**C・D・O・S の結論は、合成フィクスチャとjqのプロトタイプで
実際に確かめる**（フェーズ3のフィクスチャの原型にもなる）。

```bash
# 1. 合成フィクスチャを作る（スクラッチパッド配下）。最低限、次を1本のJSONLへ含める:
#    - 1行目のメタデータ
#    - 同一idのリビジョン再送（tokens の後埋め・toolCalls の status 遷移）
#    - $set によるスナップショット再送
#    - $rewindTo
# 2. Cで選んだ方式のjqフィルタをプロトタイプとして書き、同じファイルを2回流して
#    「2回目の差分が0であること」（＝同じ範囲を二重計上しないこと）を確認する
# 3. 切り詰め（行数が減る）を模したファイルを用意し、S・Oの結論どおりに振る舞うことを確認する

# 4. 既存の状態を壊していないことの確認（この調査では変更しないので必ず通る＝下限の確認）
bash .claude/scripts/test/test_usage_tracking.sh
bash -n .claude/hooks/lib/UsageTracking.sh
```

- 実機（Gemini CLI）でのエンドツーエンド確認は**行えない**（この開発機に `~/.gemini` が存在しない
  ことを flow-id 1-4 で確認済み）。上記の合成フィクスチャと、決-4の一次情報の突き合わせで代替する。
