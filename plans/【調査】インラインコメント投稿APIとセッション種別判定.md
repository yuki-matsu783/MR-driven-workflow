# 【調査】インラインコメント投稿APIとセッション種別判定

全体作業計画: `plans/prancy-herding-kahan.md`（issue #77 / PR #80）

## 目的

敵対的レビュースキルの設計に入る前に、**このリポジトリで前例の無い3点**を実機で確定させる。
いずれも「公式ドキュメントの記述と実機の挙動がずれると、後段の設計がまるごと崩れる」性質の
ものであり、フェーズ3で作る `Provider.sh` の関数シグネチャ・スキルの手順1・縮退方針が
この結果に直接依存する。

1. インラインコメントを**どの単位で**投稿できるか（GitHub / GitLab）
2. 非対話セッションを**機械的に**判定できるか（`AUTOMATION` 環境変数）
3. `gh`/`glab` 不在（MCP経路）で**どこまで縮退させるか**

## 調査項目

### 調査1: GitHubのインラインコメント投稿（PR #80 上で実機確認）

`gh api repos/{owner}/{repo}/pulls/<n>/reviews` に `event=COMMENT` と `comments[]`
（`path` / `line` / `side` / `body`）を渡す形を実際に投稿して確かめる。

- **1回のレビューに複数の指摘をまとめられるか**（レビュアーへの通知が1回で済むか）。
  まとめられない場合、指摘ごとに `pulls/<n>/comments` を叩く形になり通知が指摘数だけ飛ぶため、
  投稿上限（既定10件）の設計を見直す必要がある。
- **diffに含まれない行を `line` に指定したときの失敗の仕方**（HTTPステータス・エラーメッセージ・
  一部だけ不正なときに他の指摘も巻き添えで失敗するか）。敵対的レビューは「diffの外にある
  既存コードの問題」を指摘しがちなため、この失敗はほぼ確実に起きる。巻き添えになるなら、
  投稿前に対象行がdiffに含まれるかを検証する処理が必要になる。
- 投稿したスレッドが `get_mr_unresolved_comments`（GraphQLの `reviewThreads`）に
  **`unresolved` として現れるか**。現れれば、既存の `comments` サブコマンドがそのまま
  「敵対的レビューの指摘一覧」としても機能する。
- **投稿ペイロードの渡し方**: `--input <ファイル>` でJSONを渡せることを確認する
  （コマンドライン引数へ埋め込む形は、引数長・hook誤検知の両面で採らない）。

確認後、投稿したレビュー・コメントは削除して元の状態へ戻す。

### 調査2: GitLabのインラインコメント投稿（docker上のGitLab CEで実機確認）

`projects/:id/merge_requests/<iid>/discussions` へ `position` 付きでPOSTする形を確かめる。

- `position` の必須項目（`base_sha` / `start_sha` / `head_sha` / `old_path` / `new_path` /
  `new_line` / `position_type`）を**どこから取得するか**を確定させる
  （MR JSONの `diff_refs` で足りるか、`versions` APIが要るか）。
- **`glab api` でネストしたフォームパラメータ（`position[new_line]` 等）を渡せるか**。
  渡せない場合は `--input` でのJSON送信、それも不可なら `-X POST --raw-field` 等の代替を探す。
- 新規行（`new_line` のみ）・削除行（`old_line` のみ）・文脈行（両方）の3ケースで投稿できるか。
- 手順・所要時間を記録する（コンテナの起動、root トークン発行、テスト用プロジェクト・MRの作成、
  `glab auth login --hostname` でのローカルホスト向け認証）。作業後はコンテナを停止・削除する。

### 調査3: 非対話セッションの判定（`AUTOMATION` 環境変数）

- 対話セッションである**このセッション**で `echo "AUTOMATION=${AUTOMATION:-unset}"` が
  `unset` になることを確認する。
- Claude Code の非対話実行経路（`claude -p` 等）で `AUTOMATION=1` が実際に設定されるかを確認する。
  設定されない場合、**何が設定されるのか**（プロセスに渡る環境変数の差分）を洗い出す。
- 代替材料として `get_vcs_access_mode`（`mcp` はCLI不在のリモート環境と相関する）と、
  hookへ渡るJSONに実行モードを示すフィールドがあるかも調べる。ただし
  **`mcp` は「CLIが無い」ことしか意味しないため、単独の判定材料には採らない**。
- **結論の出し方**: `AUTOMATION=1` を非対話の唯一の判定材料とし、未設定・他の値はすべて
  対話モード（＝AIからの自律起動を禁止）へ倒す。この既定は、判定を誤ったときに
  「勝手に動く」側ではなく「動かない」側へ倒れることを狙ったものである。

### 調査4: MCP経路でのインライン投稿

- `mcp__github__*` にインラインレビューを作成できるツール（pending review の作成 →
  コメント追加 → 提出、の3段構成が典型）が存在するかを確認する。
- 存在すれば `issue-mr-flow/SKILL.md` の「Provider関数 → MCPツール対応表」へ追記できる形
  （ツール名・引数・CLI版との差分）にまとめる。
- 存在しなければ、**MCP経路ではインライン投稿を行わず、全指摘を通常コメント1件へ集約する**
  という縮退を定める（`add_mr_comment` → `mcp__github__add_issue_comment` は既に対応表にある）。
- GitLabは対象外（既存方針どおり。`glab` 不在時は `require_vcs_cli` が明示して失敗する）。

## 進め方・成果物

1. 調査1・3・4（外部依存が軽いもの）を先に行い、最後に調査2（docker）を行う。
   調査2で時間を使い切っても、他の3つの結果だけでフェーズ3の設計に入れる状態にしておく。
2. **調査結果は本ファイルへ書かない。**
   `reports/20260819_prancy-herding-kahan_インラインコメント投稿APIとセッション種別判定.md` に記録する
   （計画と結果を同じファイルへ混ぜると、計画として何を合意したのかが読み取りにくくなるため）。
   詳細な試行錯誤は worklog に書く。
3. あわせて `reports/20260819_prancy-herding-kahan_インラインコメント投稿APIとセッション種別判定.html` に
   視覚的にまとめる。**要素間の関連が主題ではなく「項目ごとの確認結果」が主題**のため、
   canvas形式ではなくTailwindCSS CDNの通常版で作る。

## この調査で決めないこと

- 確度・重大度による投稿／報告の振り分け基準（フェーズ3の設計で決める）。
- レビュー観点の具体的な中身（同上）。
- 実施回数カウンタの状態ファイル形式（同上。ただし調査3の結論に依存する部分があれば記録する）。
