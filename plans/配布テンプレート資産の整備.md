# 全体作業計画: 配布テンプレート資産の整備（issue #33）

対象issue: [#33](https://github.com/yuki-matsu783/MR-driven-workflow/issues/33)
ブランチ: `claude/distribution-template-assets-oi4uai`（ハーネス指定。`.mrworkflow.json` の
`feature-{issue}-{slug}` 規則とは異なるが、実行環境側の指定が優先される）

## このissueで達成すること

他プロジェクトへ配布する「ワークフローテンプレート」として不足している基本資産を揃える。
issueの受け入れ条件は5つで、それぞれの対応方針は次のとおり。

| # | 受け入れ条件 | 方針 | 決定状況 |
|---|---|---|---|
| 1 | PR/MRテンプレートの追加（`describe` の生成物と矛盾しない） | `.github/pull_request_template.md` と `.gitlab/merge_request_templates/Default.md` を追加し、`describe` サブコマンドのテンプレート（`Closes #N` / `## Plan` / `## 実装状況`）と同じ構成にする | 本計画で確定 |
| 2 | LICENSEの追加（種別はユーザー決定） | **追加しない**。ユーザーが種別として「なし」を選択したため、受け入れ条件1件を意図的に満たさない形で完了させ、判断と影響をDDRへ残す | ユーザー判断（flow-id 1-4 時点） |
| 3 | `.gitattributes` に `*.sh text eol=lf` 相当を追加し、`shell-script-style.md` の「未導入」記述を更新 | 本リポジトリへ `.gitattributes` を追加し、配布時は**行追記**（`.gitignore` と同じ扱い）で配布先へ反映する | 本計画で確定 |
| 4 | 版管理方針をspecまたはDDRへ記録（採用時は配布物にも版を含める） | **VERSIONファイルのみ採用（CHANGELOGなし）**。配布先の本体アプリが持つ版と衝突しない位置へ置く | ユーザー判断（flow-id 1-4 時点） |
| 5 | 追加資産が `sync-assets.sh` の同期対象に含まれ、#26 と衝突しない | `sync-assets.sh` / `install-to-project.sh` を追加資産に対応させる。#26 が予定する層分け（core/seed/merge/local）と矛盾しない配置・上書き方針にする | フェーズ2で確認 |

## フェーズ2〈調査〉

**実施する。** 実装より先に、次を確定させないと受け入れ条件5を満たせない。

- 現行の配布経路（`sync-assets.sh` が何を `assets/` へ集め、`install-to-project.sh` が何をどう
  配置するか）と、そこへ追加資産を載せる際の変更点。
- `describe` サブコマンドが生成するMR description の構成（PR/MRテンプレートが「矛盾しない」と
  言える形を、推測ではなくSKILL.mdの記述から確定させる）。
- issue #26 が予定する層分け・manifest方式との整合（今回の追加が #26 の設計を先取りして
  壊さないか。特に「配布先の既存ファイルを上書きしてよいか」の線引き）。
- `.gitattributes` を配布先へ**丸ごとコピー**した場合の副作用（配布先が自前の
  `.gitattributes` を持つケース）。

成果物: `reports/日付_配布テンプレート資産の整備_配布経路と追加資産の調査.md`（正文）と同名の
`.html`（視覚化）。

## フェーズ3〈作業〉

調査結果をもとに、次を実装する（詳細な手順は個別作業計画で定める）。

1. `.github/pull_request_template.md`
2. `.gitlab/merge_request_templates/Default.md`
3. `.gitattributes`
4. VERSIONファイル（配置先は調査結果で確定する）
5. `sync-assets.sh` / `install-to-project.sh` の対応

## フェーズ4〈反映〉

**必ず通る。** 反映対象は flow-id 4-1 で洗い出す。現時点で見込んでいる候補は次のとおり
（確定した反映内容ではない）。

- spec: 配布テンプレート資産（PR/MRテンプレート・`.gitattributes`・VERSION）の仕様。
- DDR: 版管理方針（VERSIONのみ・CHANGELOG不採用）／LICENSEを同梱しない判断。
- AIアセット: `.claude/rules/shell-script-style.md` の「未導入」記述、
  `.claude/rules/directory-structure.md` のツリー、`index.md`（Repository Map）、
  `README.md` / `DEVELOPERS.md`。

## この計画で決めないこと（スコープ外）

- **issue #26 の配布方式再設計そのもの**（manifest方式・層分け定義ファイル・`.skill` パッケージの
  廃止）。本issueは現行方式の上へ資産を足すところまでを担当し、層の定義は #26 側で行う。
- **配布先プロジェクトのライセンス**。本リポジトリがLICENSEを持たない判断は、配布先が自分の
  ライセンスを選ぶことを妨げない。
- **リリースタグの運用**（いつ誰がタグを打つか）。VERSIONの更新規則までを本issueで決め、
  タグ運用は必要になった時点で別issueとする。

## 検証

- `bash -n` による構文チェック（変更したすべての `.sh`）。
- `bash .claude/scripts/test/test_*.sh` の全件実行（`passed=N failures=N` 規約。既存テストを
  壊していないことの確認）。
- `install-to-project.sh` を**使い捨ての空リポジトリ**へ実際に適用し、追加資産が配置されること・
  配布先の既存 `.gitattributes` を壊さないことを実機で確認する（机上確認で済ませない）。
- `bash .claude/scripts/src/extract-frontmatter.sh .` が新規markdownを取り込めること。

## issue分割の判定

受け入れ条件は5件あるが、**同型の成果物の並列列挙ではない**（PR/MRテンプレート・
`.gitattributes`・版管理・配布スクリプト対応はそれぞれ性質が異なり、かつ「配布物として一式が
揃っていること」がこのissueの価値）。個別にマージしても壊れはしないが、分割すると
`sync-assets.sh` への変更が3つのissueに分散する。**分割しない**と判断した。
