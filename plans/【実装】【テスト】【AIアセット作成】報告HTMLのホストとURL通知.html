方針

作業1: Provider.sh に4つの関数を足す

純粋関数2つ（単体テストの対象）

関数役割戻り値
report_site_prefix_to_reply <provider> <番号>サブディレクトリ名を決めるREPLY に pr-<番号>（github）／mr-<番号>（gitlab）
join_url_to_reply <base> <path>ベースURLとパスを連結するREPLY に連結結果
  • どちらも外部コマンド・コマンド置換を含めない （.claude/rules/shell-script-style.md「ホットパスの小さなヘルパー関数は REPLY へ返す」）。
  • join_url_to_reply は、base の末尾スラッシュの有無・path の 先頭スラッシュの有無を吸収してスラッシュが重複しないようにする。空の path を 渡した場合は base をそのまま返す。
  • report_site_prefix_to_reply は、番号が空・非数値なら非0で終える （呼び出し側が「URLを組み立てられない」として扱えるようにする）。

公開関数2つ

get_report_site_url [<MR番号>]
  成功: URL（末尾スラッシュ付き）をstdoutへ / 終了コード0
  失敗: 理由をstderrへ / 終了コード非0

wait_for_report_site <url> [<上限秒=90>] [<間隔秒=5>]
  到達: 終了コード0
  未到達: 理由をstderrへ / 終了コード非0（上限に達した場合も含む）
失敗は正常系のひとつ

upload_attachment と同じ扱いにする。呼び出し側（flow-id 5-6）は非0を受け取ったら 注記だけ出してフローを続ける。関数の直上コメントにもその旨を書く（既存の upload_attachment の書き方に揃える）。

  • MR番号を省略したときは get_mr_for_branch の結果から取る。 番号の導出はこの1経路に一本化する（調査結果「設計への反映」1）。この関数はJSONを返すので jq -r '.number' で取り出す（値は1行なので tr -d は挟まない）。
  • wait_for_report_site は curl -sS -o /dev/null -w '%{http_code}' で 200 を待つ。curl が無い環境では即座に非0で終える（待ち続けない）。

作業2: プロバイダ固有のURL取得

プロバイダ一次経路フォールバック
GitHubgh api repos/{owner}/{repo}/pages --jq .html_urlhttps://<owner>.github.io/<repo> を組み立てる
GitLabglab api projects/:id/pages --jq .urlenvironments API から external_url を引く
  • 取得したベースURLへ report_site_prefix_to_reply の結果を join_url_to_reply で足す。
  • CLI不在（MCP経路）では require_vcs_cli で非0にする。 MCPにはPages情報を 引くツールが無いため、フォールバックの組み立てだけを行う経路は用意しない （URLが正しいと確認できないまま提示するほうが害が大きいため）。この判断は mcp_tool_hint にも1行として載せる。

作業3: GitHub Actions ワークフロー

.github/workflows/publish-report-site.yml を新規作成する。要点だけを示す（全文は実装時）。

on:
  push:
    branches: ['feature-*']     # paths フィルタは付けない（削除の変更も拾う必要がある）
concurrency:
  group: gh-pages-deploy
  cancel-in-progress: false     # 直列化する。取り消すと片方のデプロイが失われる
permissions:
  contents: write
  pull-requests: read

ジョブは次の順で判定する。どちらかで外れたら何もせず正常終了する（exit 0）。

  1. openなPRがちょうど1件か。 gh pr list --head "$GITHUB_REF_NAME" --state open --json number の件数が1でなければ スキップ（0件＝PR作成前、複数件＝どれへ載せるか決まらない）。
  2. 対象HTMLが1件以上あるか。 reports/*.html ＋ plans/*.html の 件数が0ならスキップ。これが flow-id 5-6 の削除で送られる変更を無害化する仕掛けである （gh-pages 側の pr-<n>/ は触られないので残る）。

デプロイは gh-pages ブランチを checkout し、 pr-<n>/reports/ pr-<n>/plans/ を置き換えて （rm -rf してから cp）リモートへ反映する。反映は3回までリトライし、 各回の前に git pull --rebase する（concurrency は同一リポジトリ内の 直列化しか担保せず、手動実行等と競合しうるため）。

作業4: GitLab CI

.gitlab-ci.yml を新規作成する。

pages:
  stage: deploy
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  pages:
    path_prefix: "mr-$CI_MERGE_REQUEST_IID"
    expire_in: never
  artifacts:
    paths: [public]
  • script で reports/*.html plans/*.html を public/ へ集め、0件なら exit 0 でジョブを終える （GitHub側と同じガード）。
  • path_prefix が空文字列に展開されると本番サイトを上書きするため、 $CI_MERGE_REQUEST_IID が空なら rules で弾かれることを、 コメントで明記する。

作業5: 配布からの除外

sync-assets.sh の .github 同期を、workflows/ を除いたコピーへ変える。

置き換え前

if [ -d "${PROJECT_ROOT}/.github" ]; then
  echo "Syncing .github templates..."
  mkdir -p "${ASSETS_DIR}/.github"
  cp -R "${PROJECT_ROOT}/.github/"* "${ASSETS_DIR}/.github/"
fi

置き換え後

if [ -d "${PROJECT_ROOT}/.github" ]; then
  echo "Syncing .github templates..."
  mkdir -p "${ASSETS_DIR}/.github"
  # workflows/ は配布しない（issue #114）。配布先のCI設定を上書きしうるうえ、
  # Pages の有効化・ブランチ運用は配布先ごとに異なる。雛形は
  # .claude/skills/issue-mr-flow/assets/publish-report-site.*.yml として配る。
  for entry in "${PROJECT_ROOT}/.github/"*; do
    [ -e "$entry" ] || continue
    [ "${entry##*/}" = "workflows" ] && continue
    cp -R "$entry" "${ASSETS_DIR}/.github/"
  done
fi
  • ISSUE_TEMPLATE/ と pull_request_template.md は従来どおり 配布される（この2つが .github/ 配下の既存の中身であり、除外してはいけない）。
  • [ … ] && continue を set -e 配下で使わない。 最後の要素が workflows だった場合にループ全体の終了コードが1になり、 スクリプトが落ちる。実装では if … then continue; fi にする。
  • install-to-project.sh 側は変更しない（assets/ に無いものは 配布されないため、除外は sync-assets.sh の1箇所で完結する）。
