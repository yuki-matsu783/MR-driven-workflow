# 【AIアセット作成】【テスト】10節テンプレートと `describe` 節の一本化

issue #145 / PR #187 / 全体作業計画 `plans/mellow-archiving-lantern.md`
調査結果 `reports/20260823_mellow-archiving-lantern_テンプレート再設計の調査.md`

**種別を2つ併記している理由**: テンプレート・スキル定義（AIアセット作成）と、それを固定するテスト
（テスト）は**同じコミットで揃っていないと意味が無い**。テンプレートだけ変えるとテストが落ち、
テストだけ変えると何も検査していない状態になる。合意も1回で取る。

## この計画で何をするか

フェーズ2の調査で決めた**案B**（`.github/pull_request_template.md` を唯一の正とし、`describe` 節は
雛形を持たない）を実装する。作業は7項目で、**うち3項目（1・2・4）は互いに依存する**ため
まとめて行う。

### 案B採用の合意状況

**案Bは人間の合意をまだ得ていない。** このセッションは非対話（人間のレビュー往復を待てない）で
実行されており、フェーズ2のレビュー往復は**敵対的レビューによる自動レビューで代替**している
（ユーザーからの明示指示による）。したがって案Bは、現時点では**AI側の結論**である。

- 判断の根拠と却下案（案A・案C）は `reports/20260823_…調査.md` §1 にある。ただし
  **`reports/` は flow-id 5-5 で削除される**ため、マージ後に辿れる場所へ残す必要がある。
- **恒久的な記録先はフェーズ4のDDR `i0145-01` である**（flow-id 4-6）。この計画・レポートは
  そこへ昇格させるための材料であり、それ自体は合意の記録ではない。
- 人間のレビューで案Bが否認された場合、この計画の作業項目1〜5はすべて作り直しになる。

## 各項目の設計

### 1・2. テンプレート2本

**構造**: 先頭のHTMLコメント（プロバイダ固有）→ `Closes #<issue番号>` → 10節。各節の直下に
記入ガイドのHTMLコメントを置く。

**先頭のHTMLコメントへ書くこと**（現行から差し替える内容）。

- このファイルが**見出し構成の唯一の正**であること。`describe` は**このファイルを読んで**
  見出しを決めるので、ここを変えれば `describe` の出力も変わる（逆は無い）。
- flow-id 2-5/2-10/3-5/3-10/4-5/4-10 で `describe` が本文を**全文置換**すること。
- **Draft PR/MRの初期本文（`new_draft_merge_request` のハードコード）はこの10節に合わせない。**
  初回の `describe` で全文置換されるため実害が無く、合わせると「まだ何も無い状態の10節」が
  一時的に残るだけで読みにくいため。**この判断そのものを1行残す**（後から見た人が「初期本文が
  古いテンプレートのままだ」と誤解しないため）。
- GitLab版のみ: `Default.md` が予約名であること（DDR `i0032-01`）。**この差分がGitHub版との
  唯一の相違**である。

**「見出しを増やさない」という現行の制約をどう書き換えるか。** 現行の先頭コメントは「**見出しを増やさないこと**（増やしても最初の `describe` で消える）」と
書いている。案Bでは `describe` がこのファイルを読むため、**増やした見出しは消えない**——
理由が成り立たなくなる。しかし「増やしてよい」と単純に書き換えると、**配布先に対して守れない
約束になる**。

| | 配布元（このリポジトリ） | 配布先 |
|---|---|---|
| テンプレートの扱い | 見出し構成の正。ここを変えれば `describe` の出力も変わる | `core` 層＝**再適用のたびに上流の内容で上書きされる**（改変は `.bak` へ退避のうえ一覧で通知） |
| 見出しを増やせるか | **増やせる**（消えない） | 増やせるが、次の `install-to-project.sh` 適用で**上流の内容へ戻る** |

**採る方針**: テンプレートを `core` 層のまま据え置き、**コメントの文言を配布元に限定する**。
「このリポジトリでは見出しを増やしてよい。**配布先では `core` 層として再適用のたびに上書き
されるため、増やした見出しは次の再適用で失われる**」と両方を書く。

**`seed` へ層を変える案は採らない。** `dist-layers.json` の note が「見出しが `start`・`describe` と
**機能的に結合**」と書いているとおり、テンプレートの見出しは `describe` の出力そのものであり、
配布先ごとに分岐すると `describe` の挙動も分岐する。層の変更は `dist-layers.json`・
`check-dist-coverage.sh`・`distribution-assets.md` の3箇所に波及し、本issueの目的
（正を1つにする）と逆方向でもある。

**各節のHTMLコメントへ書くこと**（3点セット）。

1. **何を書くか**（節の趣旨）。
2. **計画段階では何を書くか**（issue #145 の受け入れ条件）。
3. 該当が無いときの書き方。

**「特になし」と「未実施」の書き分け**（調査の結論4）。この定義は**`## 概要` の記入ガイドへ
まとめて1回だけ書き**、各節は参照しない（10箇所へ同じ定義を複製すると二重管理になる）。

| 語 | 意味 |
|---|---|
| `特になし` | 検討した結果、書くことが無かった |
| `未実施` / `このフェーズではまだ確定していない` | まだその段階に達していない |

**`## 反映先・関連` の記入ガイドには、参照禁止を書く**（作業項目6と対になる）。
`plans/` `worklog/` `reports/` のパスを書かず、結論は転記し、spec/DDRのパス・issue番号・
PR番号・レビューコメントのpermalinkで指す。

### 3-a・3-b. `describe` 節

**3-a**: 現在の手順2は「以下のテンプレートでMR description本文を組み立て、**一時ファイルへ
書き出す**。」であり、**雛形の提示と一時ファイル生成の指示を兼ねている**。続く手順3が
`set_mr_description <n> <一時ファイル>` を呼ぶため、雛形だけを消すと引数の出どころが失われる。
**置き換え後の手順2は次の全文にする**（雛形は消し、残りの2つの役割は保つ）。

> 2. `get_provider` で判定したプロバイダに対応するテンプレートファイルを**リポジトリルートからの
>    相対パス**で読み、その見出し構成に従ってMR description本文を組み立て、**一時ファイルへ
>    書き出す**。
>    - `github` → `.github/pull_request_template.md`
>    - `gitlab` → `.gitlab/merge_request_templates/Default.md`
>    - **各節のHTMLコメント（記入ガイド）は指示であり、descriptionへは書き出さない。**
>      書き出すのは `Closes` 行と見出し、および各節の中身だけである。
>    - **テンプレートファイルが読めない場合は、本文を組み立てずにその旨を提示して止まる。**
>      見出しを推測して埋めない（推測すると、案Bが無くそうとした「正が2つ」の状態が実行時に
>      再発する）。`get_provider` 自体が失敗する場合（origin未設定等）も同じ。

**この節に見出しを列挙しない理由を1行残す**（次に触る人が親切心で復活させないため）。

**3-b**: 手順1の読み取り対象へ `reports/` を加える。現在の文言は「全体作業計画・個別計画・
worklogの要点を読む」だが、`get_branch_work_files` は `plansDir` / `worklogDir` / `reportsDir` の
3つを列挙しており、**関数の出力と手順文言が既にずれている**。10節の `## 検証`
`## 設計判断・採らなかった案` は `reports/` の結論を転記する節なので、これが無いと材料が手に入らない。

### 4. テスト

現在の `describe_headings()`（`review-loop.md` から `awk` で抽出）は、案Bで `describe` 節が
雛形を失うため**抽出が0行になり、`assert_eq "3"` が失敗する**（「空振りして通る」のではなく
「落ちる」。既存ガードは正しく機能している）。次の**3種類**へ差し替える。

| 検査 | 内容 |
|---|---|
| (a) 見出し | 期待値の10節を**テスト内へ書き下し**、テンプレート2本の `^(Closes|## )` が順序込みで一致すること |
| (b) 全文 | **先頭のHTMLコメントブロックだけを除外**した2本の全文差分が空であること |
| (c) 参照 | **`review-loop.md` の `describe` 節が、テンプレート2本のパスを両方とも参照していること**（各1件以上） |

**(c) を足す理由**: 現行テストは「`describe` 節 ⇔ GitHub版 ⇔ GitLab版」の**3者**を突き合わせて
おり、テストのコメント自身が「2つのテンプレート同士を比べるだけでは足りない」と書いている。
(a)(b) だけにすると**テンプレート側しか見なくなり**、案Bの成立条件である
「`describe` 節がテンプレートファイルを読むと書いてあること」が誰かの編集で無言で失われても
**どのテストも落ちない**。一本化の効果はこの1点に全面的に依存しているので、そこだけ無検査には
できない。

**空振り防止の表明を「期待値が非空」にしない。** 期待値はテスト内のリテラルなので、非空は
編集ミスでない限り常に真であり、**落ちる入力が存在しない**表明になる（ルート
`REVIEW-POINTS.md`「異常が無ければ何も出ない形の検証は…常に成功する」）。代わりに次の2つを行う。

1. **実データ側**（テンプレートから抽出した見出し行・除外後の全文の行数）が非空であることを表明する。
   とくに (b) は、除外後の行数が **0でも1でもないこと**を併せて表明する（下記の空振り経路への対策）。
2. 着手時に**意図的に片方だけ1文字変えて (a)(b)(c) が落ちる**ことを確かめ、worklog へ記録する。

- 抽出行数の固定値 `3` は残さない。
- **期待値を持つことは「二重管理」に数えない。** 期待値は正ではなく**検査**であり、これが無いと
  「2本を比べるだけでは足りない（両方が同時にずれると通ってしまう）」という既存コメントの趣旨が
  守れない。**その旨をテスト側のコメントへ明記する**（次に読む人が「二重管理では」と消しに来ないため）。

### 検証3は、それ単独では完了判定に使えない

**検証3は変更前から成功する不変条件である。** 「2本が食い違っていないこと」は今も真であり、
この作業の成否を判定しない。**判定に効くのは検証2・3'・4の3つ**で、検証3はそれらと組にして
「10節へ移したあとも2本が食い違っていない」ことを守る役割にとどまる。

### 除外の実装（`strip_lead`）が空振りする2つの経路

素朴な `sed '1{/^<!--$/!q}; 1,/^-->$/d'` は、次の2つの入力で**本文が食い違っているのに差分なし**に
なる（いずれも実測で確認済み）。

| 経路 | 何が起きるか |
|---|---|
| 先頭コメントの終端が行末に付く（`  説明 -->` のように `-->` が単独行でない） | `^-->$` に一致せず、削除範囲が**最初の節の記入ガイドの `-->` まで伸びる**。`Closes` 行・`## 概要`・その記入ガイドが両ファイルで丸ごと消える。**「特になし／未実施」の定義を置く唯一の場所**が検査の穴になる |
| 先頭に `<!--` が無い | `1{/^<!--$/!q}` の `q` はパターン空間を出力して終了するため、**出力が1行目だけ**になる。1行目が同じなら本文がどれだけ違っても差分なし |

**対策**: (1) 除外を「1行目が `<!--` で始まり、その後最初に現れる `-->` を**含む行**まで」へ広げる。
ただし **`sed` の範囲指定（`1,/-->/d`）では両方とも塞げない**——範囲は1行目で開始してしまうと
`-->` が現れるまで伸び続け、先頭にコメントが無い場合はEOFまで削る（実測で確認）。**状態を持つ
`awk` で書く**（下記の実装）。(2) **除外後の行数が0でも1でもないこと**を併せて表明する（検証3'）。
(3) 意図的に片方だけ1文字変えて `diff` が落ちることを着手時に確認する。

**実測（2026-08-23、変更前のツリー）**: 下記の `awk` 版は4ケースすべてで期待どおりだった。

| 入力 | 期待 | 実測 |
|---|---|---|
| 先頭にコメント無し・本文が違う | 差分あり | 差分あり |
| 終端が行末（`<!-- 説明 -->`）・本文が違う | 差分あり | 差分あり |
| 通常形・先頭コメントだけ違う | 差分なし | 差分なし |
| 未終端コメント（`-->` が無い） | 除外後0行 → 検証3'が落ちる | 0行 |

### 検証2・3・3' の実行コマンド

**期待値のヒアドキュメントは各行を `| ` で始めて `sed` で剥がす**（行頭に `## ` を持つ行を
この計画ファイル自身へ増やすと、計画のmd/HTML見出し突き合わせとテンプレートの見出しを数える
検査の両方がコードブロックの中身を拾うため）。

```bash
expected="$(sed 's/^| //' <<'EXPECTED'
| Closes #<issue番号>
| ## 概要
| ## 変更内容
| ## 設計判断・採らなかった案
| ## 検証
| ## レビューの結果
| ## 意図的にやらなかったこと・スコープ外
| ## 未解決・限界・確かめられなかったこと
| ## 受け入れ条件との対応
| ## 反映先・関連
| ## 備考
EXPECTED
)"
gh_t=.github/pull_request_template.md
gl_t=.gitlab/merge_request_templates/Default.md

# 検証2: 見出しが期待値と順序込みで一致する
for f in "$gh_t" "$gl_t"; do
  diff <(printf '%s\n' "$expected") <(grep -E '^(Closes|## )' "$f") || echo "NG(見出し): $f"
done

# 先頭のHTMLコメントブロックだけを除く（終端が行末に付く形・先頭にコメントが無い形の両方へ対応）。
# sedの範囲指定（`1,/-->/d`）では両方とも塞げないことを実測したため awk で状態を持つ。
strip_lead() {
  awk 'NR==1 && /^[[:space:]]*<!--/ { lead = 1 }
       lead { if (/-->/) lead = 0; next }
       { print }' "$1"
}

# 検証3': 除外後が 0行でも1行でもない（除外が伸びすぎ／効かなすぎを検出する）
for f in "$gh_t" "$gl_t"; do
  n="$(strip_lead "$f" | grep -c '')"
  [ "$n" -gt 1 ] || echo "NG(除外後が${n}行): $f"
done

# 検証3: 先頭のHTMLコメントブロックだけを除いた全文が一致する
diff <(strip_lead "$gh_t") <(strip_lead "$gl_t") || echo 'NG(全文差分)'
```
