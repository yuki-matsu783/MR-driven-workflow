この作業で何をするか

.claude/rules/docs-workflow.md にある「既存ドキュメントへ新しい見出しを差し込むときは、 挿入位置の直前の節が『その節全体にかかる地の文』で終わっていないかを必ず確認する」というルール （issue #64 で追加）を、見出しの挿入に限定された書き方から、「残置したテキストの係り先が変わって いないか」という観点の書き方へ一般化する。

同型の事故が既に4件確認されている（issue #64 / #109 / PR #139 / issue #155）。現行の文言は そのうち #64 の形しか拾えない。

背景（確定している事実）

#何を変えたか壊れたテキストの位置現行ルールで拾えるか
issue #64新しい見出しを差し込んだ挿入位置の直前拾える このルールの元ネタ
issue #109既存の節を (1)(2) に分割した(1) の直後（分割前は正しかった行）拾えない 見出しの挿入ではない
PR #139（issue #135）新しい見出しを差し込んだ挿入位置の直後（見出しを持たない段落群）拾えない 射程内の操作なのに「直前を見よ」では検出できない
issue #155既存の箇条書きへ項を1つ足した直前の項の末尾にあった補足拾えない 見出しも節も階層も動いていない
共通点 4件とも自己確認では見つからず、敵対的レビューが検出している。書いた本人は「新しく書いた部分が 正しいか」を見ており、「既にあった行の係り先が変わったか」を見ていない。

ファイル群・領域操作何をするか
.claude/rules/（規約）変更該当ルールの文言を一般化する。フェーズ3の主たる成果物

フェーズ2〈調査〉

実施する。次の問いに答える。

  1. 現行ルール（該当段落と実例2件）は、どの範囲を射程にしているか。一般化したとき、既存の実例2件は そのまま残せるか。
  2. 同じ趣旨のルールが他のファイルにも重複していないか（ルート REVIEW-POINTS.md 「ドキュメントの構造」に同型の観点がある）。正を1箇所にするのか、観点表と規約で役割を分けるのかを決める。
  3. 4件の実例のうち、ルール本文へ載せるのはどれか。#109（分割で前が壊れる）と PR #139（挿入で 後ろが壊れる）は方向が逆で、2つ並べると観点が立体的になる。何件までなら読み手の負担にならないか。
  4. 受け入れ条件が求める「DDRを新規に残すか既存への追記で足りるか」の材料。issue #64 由来のDDRが 存在するかを .claude/docs/ddr/ の検索で確定する。
  5. このルールを実際に守らせる場所はどこか（規約だけでよいか、観点表・敵対的レビューにも要るか）。

フェーズ3〈作業〉の方針

調査結果をもとに .claude/rules/docs-workflow.md の該当ルールを書き換える。想定する形は 次のとおりで、確定はフェーズ3の個別計画で行う。

  • 適用対象を「見出しの差し込み」から構造変更全般へ広げる。ただし操作の種類を列挙する形に しない（issue #155 の3例目が、列挙した4操作のどれにも入らなかったため）。
  • 確認の観点を「残置した地の文・箇条書きが、変更前と同じものに係っているか」という形で書く。
  • 「前後どちらの残置テキストも見る」ことを明示する（PR #139 のコメントの指摘）。
  • issue #64 の既存の実例（計画の2階層構造 の位置、ファイルごとに結論が変わる話）は消さない。
  • 「分割前は正しかった行が、分割によって誤りになる」形を明示した実例を足す。

種別は 【AIアセット作成】 を想定する（ルール文書そのものが今回の主たる成果物であるため）。

フェーズ4〈反映〉

flow-id 4-1 で反映対象を洗い出す。現時点の見込みは次のとおりで、確定した反映内容ではない。

  • DDR: 「なぜ操作の列挙ではなく観点で書くのか」の判断を残すか、既存DDRへの追記で足りるか。 issue #142 の受け入れ条件が明示的に求めているため、結論の記録は必須。
  • REVIEW-POINTS.md: ルートの「ドキュメントの構造」の同型の観点を、 一般化後の記述と揃えるか。
  • .claude/docs/usecase/: 影響の有無を確認する。

やらないこと（スコープ外）

この計画では決めない・触らない
  • 過去に書かれたドキュメントの遡及点検。既存文書に同型の破損が残っていないかの棚卸しは 行わない（判断は別issueへ送る）。
  • 敵対的レビューのサブエージェント定義の改修。観点表へ書けば足りるかをフェーズ2の問い5で 判定し、足りないと分かった場合のみフェーズ4で扱う。
  • 4件以外の事例の発掘（判断は flow-id 2-1 の個別調査計画へ送る）。

検証

issue全体として、次がすべて満たせたら完了とする。

  • 該当ルールが4件の実例すべてを説明できる文言になっている（4件それぞれについて、ルールの 文言を読んで「見るべきだった」と分かるか机上で突き合わせる）。
  • issue #64 由来の既存2実例が残っている（差分の削除行で確認する）。
  • DDRの要否について結論が記録されている。
  • 各フェーズで敵対的レビューを実施し、投稿された指摘へ対応・返信している。
