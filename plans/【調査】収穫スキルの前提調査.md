# 【調査】収穫スキルの前提調査 — issue #27

## 目的

収穫スキルの個別作業計画（flow-id 3-1）を確度高く書けるだけの材料を揃える。
全体作業計画 `plans/quiet-orchard-harvest.md` のフェーズ2節に列挙した7問へ答える。

## 調査項目（問いの形）

| # | 問い | 調べ方 |
|---|---|---|
| Q1 | 配布先 manifest（`.claude/.asset-manifest.json`）の正確な形式は何か。とくに `merge` 層の指紋はどう記録されているか（issue #27 コメントの「読む側が無い」の実装コメント確認） | `install-to-project.sh` の manifest 書き出し部を読解 |
| Q2 | 収穫スクリプトと単体テストはどこへ置くのが規約に合うか | `install-to-project.sh` のテストの所在を確認（`.claude/scripts/test/` か、スキル配下か）。`.claude/rules/directory-structure.md` と突き合わせ |
| Q3 | 3-way突き合わせは何で実装するか。base の取得（`git show <記録SHA>:<path>`）が本家リポジトリで失敗するのはどんな場合で、どう縮退するか | `git merge-file` の挙動確認（実行検証）。shallow clone・squash merge 環境での記録SHA到達性の検討 |
| Q4 | manifest が無い配布先で、層分け定義（`dist-layers.json`）から比較対象ファイルを列挙する既存手段はあるか | `install-to-project.sh` の走査パス・`check-dist-coverage.sh` の pathspec 評価部を読解 |
| Q5 | 出口レベル2種（issue起票のみ／個別作業計画草案）は既存の何へ接続するか | `issue-create` スキル（`create-issue.sh`）の入力形式・非対話時の挙動を確認 |
| Q6 | 「配布先で機構DDRを書かず本家へissue起票する」規約の明文化先はどこが適切か | 配布層が `core` のルールファイル（`.claude/rules/` 配下・`agent-common.md` 等）の構成と、DDR識別子ルール（`markdown-frontmatter.md`）の既存記述を確認 |
| Q7 | 判断材料3種（`ai-asset:` prefix コミット・変更回数・プロジェクト固有語）は配布先から何で取得でき、どんな限界があるか | 配布先が git リポジトリでない場合・浅い履歴の場合の縮退を検討（机上＋git コマンド確認） |

## 変更対象

このフェーズで書き換えるのは `reports/`（調査結果）と worklog のみ。実装・ルール・スキルには
触らない。

  合成した疑似配布先で代替する方針。実データ検証の要否はフェーズ3の計画で判断する）

## 検証（何が分かれば次へ進めるか）

`reports/2026-08-23_quiet-orchard-harvest_調査結果.md`（＋同名.html）に記録されていること。
