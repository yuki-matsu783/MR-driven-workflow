## 目的

`.gemini/` を「`.claude/` からの変換生成物」にするために、**変換の規則そのものを確定する**。
実装（スクリプト）とテストは別計画（`【実装】【テスト】…`）が扱い、本計画は**実装前に人間の
合意が要る判断**だけを集める。

**調査結果で既に確定した事項は、ここで蒸し返さない**（ホワイトリスト方式・skillsは変換不要・
`tools` はYAML配列、など）。本計画が扱うのは、調査で「フェーズ3で決める」と積み残した論点である。

## A. 未確認3件の一次情報を追加取得する — **完了（2026-08-22・flow-id 3-6）**

**3件とも一次ソースで確定した（S）。** 結果の正文は
`reports/20260822_nimble-syncing-lantern_gemini同期方式の調査.md`「5・6・7 の結果」節にあり、
`.html` も同期済みである。ここには**この計画の判断が変わった点だけ**を書く。

| 順 | 論点 | 結果 | この計画への影響 |
|---|---|---|---|
| 1 | SessionStart の `matcher` で縦棒つなぎが有効か | **無効**（ライフサイクル系は完全一致） | **打ち切り条件で用意していたフォールバック（単一値で複数エントリ登録）は採らない。`matcher` を省略する**（下記） |
| 2 | `${GEMINI_PROJECT_DIR}` 未解決時の挙動 | **プレースホルダがそのまま残る**（空文字にならない）。実運用では未定義になる経路が実質無い | **フォールバック（`${VAR:-DEFAULT}`）は不要**。書けることは記録するが、既定では使わない |
| 3 | `general.plan.directory` に policy が要るか | **要否は未確認のまま。**ただし **Workspace 層（プロジェクト単位の policy）が現在無効** | **B の根拠が変わる**（下記「決定: B-1」への追記） |

### 1 の結果 — `matcher` は省略する

`hookPlanner.ts` の `matchesContext` は、`context.toolName` があれば正規表現、`context.trigger`
があれば**完全一致**と判定を使い分ける。SessionStart は後者なので、`startup|resume|clear` は
どの `source` にも一致せず**hookが一度も発火しない**。

**対処は `matcher` の省略とする。** `!entry.matcher` は無条件に `true`（全ソースで発火）を返し、
Claude側の `startup|resume|clear|compact` は Gemini の全3ソースを覆っているため、省略が等価かつ
最短である。**打ち切り条件に書いていた「単一値で複数エントリ登録」は、確定したので使わない。**

ただし**変換規則としては一般形で実装する**。Claude の `matcher` を `|` で分割して Gemini の
enum 値の集合と突き合わせ、**全体を覆うなら `matcher` を落とし、部分集合なら値ごとにエントリを
複製する**。今回のClaude側の値はたまたま前者に当たる、という位置づけにしておかないと、
`.claude/settings.json` 側が一部ソースだけを指定するよう変わったときに黙って壊れる。

### `args` の連結規則 — **決定（2026-08-22・flow-id 3-6）**

**`bash $GEMINI_PROJECT_DIR/.claude/hooks/x.sh` の形へ連結する。** 要素を半角スペースで繋ぐだけで、
**こちらでは引用符を付けない。変数は素の `$VAR` 形式で書き、波括弧を付けない。**

一次情報（`packages/core/src/hooks/hookRunner.ts` L519・L527、
`packages/core/src/utils/shell-utils.ts` `escapeShellArg`。評価: S）:

| 事実 | 帰結 |
|---|---|
| `escapedCwd = escapeShellArg(input.cwd, shellType)` を `$GEMINI_PROJECT_DIR` へ代入する。bashでは `quote([arg])`（shell-quote）でPOSIXクォート済みの文字列になる | **代入される値は既にクォートされている。** こちらで囲むと二重になる |
| 置換は `.replace(/\$GEMINI_PROJECT_DIR/g, …)` | **`${GEMINI_PROJECT_DIR}` にはマッチしない**（波括弧形式は非対応） |
| `GEMINI_PROJECT_DIR` はhookの子プロセス環境（L350）にのみ設定される | 波括弧形式は環境変数解決でも埋まらず、**リテラルのまま残って壊れる** |

```
悪い例1: bash "$GEMINI_PROJECT_DIR/.claude/hooks/x.sh"
         → bash "'/c/My Dir'/.claude/hooks/x.sh"   ← 単一引用符がリテラル化して壊れる
悪い例2: bash ${GEMINI_PROJECT_DIR}/.claude/hooks/x.sh
         → 置換されずリテラルのまま残る
良い例:  bash $GEMINI_PROJECT_DIR/.claude/hooks/x.sh
         → bash '/c/My Dir'/.claude/hooks/x.sh     ← 妥当なシェル構文として解釈される
```

**空白を含むパスの引用符付けは、こちらの責務ではなくGemini側が持っている**、というのがこの決定の
中身である。当初は「連結時にこちらでクォートする」と想定していたが、それは誤りだった。

### `if` の写像 — **決定（2026-08-22のチャットで確定）**

**`if` は落とす。落としたうえで、各hookスクリプトの冒頭へ「ゼロforkの前置フィルタ」を置く**
（ユーザーの提案「共通チェックシェルでラップする」に対し、実測のうえ本案を採った。経緯は同日の
worklog）。

#### なぜ前置フィルタが要るのか — 空振り1回が14 fork

`if` を落とすと、対象外のツール呼び出しでもスクリプトが起動して自己判定する。**その空振りが
安くない。** 早期終了パスに `raw="$(cat)"` と `printf | jq` が4回あり、判定に辿り着く前の
材料取り出しだけでこれだけのプロセスを生む（`strace` による実測。2026-08-22）。

| 早期終了パスの計測（push以外のペイロード） | execve | clone |
|---|---|---|
| 空関数（ベースライン） | 1 | 0 |
| `post-push-usage-report.sh` | 6 | 14 |
| `post-push-compact-prompt.sh` | 6 | 14 |
| `post-issue-create-notice.sh` | 7 | 17 |
| `block-direct-git-commit.sh` | 5 | 10 |

git bashの外部プロセス起動は約95ms/回（`.claude/rules/shell-script-style.md`「外部プロセス起動の
コスト」）なので、空振り1回で数百ms規模になる。**加えて `if` を落とすとBash用・PowerShell用の
2エントリが同一内容になるため、重複排除しないと同じスクリプトが2回ずつ走る。**

#### 前置フィルタの形

```bash
IFS= read -r -d '' raw || true                 # $(cat) をやめる → fork 0
[ -n "$raw" ] || exit 0
case "$raw" in *push*) ;; *) exit 0 ;; esac    # jq を通さず生JSONで足切り → fork 0
```

- **`read` も `case` もbash組み込みなのでforkしない。** 実測で空関数と同じ（execve 1 / clone 0）。
- **パターンは精密判定の超集合にする。** `*push*` は `git -C /x push` のように `git push` が連続
  しない形も通す。**`git[[:space:]]+push` へ縮めてはいけない**（そちらは超集合ではなく、
  取りこぼす）。
- **緩い側へ倒す。** 空振りしても後段の `command_invokes_git_subcommand` が正しく落とすので、
  前置フィルタの誤検知は無害である。逆に取りこぼすと機能が黙って死ぬ。

#### 採らなかった案 — `.gemini/` 側にディスパッチャを置く

同時に発火する2本を1本のラッパーで束ね、判定を1回で済ませる案。**実測では案の差はexecve 1回
だけだった**（ディスパッチャ 13/27 対 前置フィルタ 14/27）。

- **`.gemini/` にだけ存在する手書きスクリプトが増える。** issue #70 は「`.gemini/` を `.claude/` の
  変換生成物にする」ことが目的なので、変換元を持たないファイルを足すと二重管理が形を変えて戻る。
- **前置フィルタは `.claude/hooks/` 側の変更なので、Claude Codeにも効く。** `if` を持たず毎回
  起動している `block-direct-git-commit.sh`・`post-issue-create-notice.sh` にも同じ手を入れると、
  **現状の 12/27 が 4/0 になる**（ディスパッチャ案はここに届かない）。
- push系hookが増えたときはディスパッチャが有利になる。そのときに移ればよい。

#### 変換規則としての帰結

| 規則 | 内容 |
|---|---|
| `if` キー | **出力しない**（Gemini の `CommandHookConfig` に無い） |
| 重複エントリ | `if` を落とした結果**同一内容になったエントリは1つへ畳む**（4→2）。畳まないと同じスクリプトが2回走る |
| 前置フィルタ | 変換で生成するものではなく、**`.claude/hooks/*.sh` 側へ恒久的に入れる**（`【実装】【テスト】` の変更対象へ追加する） |

## B. `permissions` 相当（policy engine）の扱い

**調査で「Geminiに相当機能は無い」という結論が誤りだったことが判明している**
（`docs/reference/policy-engine.md` に `commandRegex = "git (commit|push)"` ＋
`decision = "deny"` がある）。したがって「無いから写像しない」とは書けない。

### 選択肢

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| B-1 | **本issueのスコープ外**とし、`.gemini/policies/` は作らない | 変換対象が `settings.json` に閉じる。差分が小さい | コミット強制の多重防御が**Gemini経路だけ hook の1枚**になる |
| B-2 | `permissions.deny` を `.gemini/policies/*.toml` へ変換する | 多重防御が両経路で揃う | 変換対象が `settings.json` の外へ広がる。TOML生成が要る |
| B-3 | 変換はせず、**手書きの `.gemini/policies/` を置く**（同期対象外） | 実装が増えない | 二重管理になる（本issueが無くそうとしているもの） |

### 決定: B-1（2026-08-22のレビューで確定）

**「スコープ外にして理由を残す」。** `.gemini/policies/` は作らず、`permissions` は写像しない。
本issueは「`.gemini/` を生成物にする」ことが主題であり、防御層を増やすのは別の目的のため。

**「理由を残す」を口約束にしない。** 次の2箇所へ具体的に落とす。

| 残す先 | 書く内容 |
|---|---|
| フェーズ4で更新する spec（`.claude/docs/spec/`） | policy engine が**存在する**こと（`docs/reference/policy-engine.md` に `commandRegex` ＋ `decision = "deny"` がある）／そのうえで本issueでは写像しないこと／写像するなら `.gemini/policies/*.toml` の生成が要ること |
| `sync-gemini-assets.sh` の写像表のコメント | `permissions` を**意図的に対象外にしている**こと（実装を読んだ人が「対応漏れ」と誤読しないため） |

**残る帰結を明記しておく**: コミット強制の多重防御は、**Gemini経路では hook
（`block-direct-git-commit.sh`）の1枚だけ**になる。Claude Code経路の `permissions.deny` に
相当する層は無い。これは受け入れたうえでの状態であり、検知漏れではない。

採らなかった案: **B-2**（TOMLへ変換）は変換対象が `settings.json` の外へ広がり、本計画の範囲を
超える。**B-3**（手書きの `.gemini/policies/`）は二重管理であり、本issueが無くそうとしている
ものそのもの。

#### 追記（2026-08-22・A の結果）: **根拠が「選ばなかった」から「今は動かない」へ変わる**

A の 3 で、**policy engine の Workspace 層（プロジェクト単位の `.gemini/policies`）が現在無効**
であることが確定した（`docs/reference/policy-engine.md` L126–L130 の WARNING、優先度表 L144 の
**(Currently disabled)**、upstream issue #18186）。**リポジトリへ `.gemini/policies/*.toml` を
置いても効果はゼロである。**

- **B-2 と B-3 は、スコープの問題以前に「置いても動かない」ため成立しない。** 上の
  「採らなかった案」の理由は今も正しいが、**それ以前に選択肢として機能しない**。
- **spec へ書く理由も差し替える。** 上の表の「本issueでは写像しない」を、
  **「Workspace 層が無効なため、リポジトリからは配れない。必要なら利用者が User/Admin 層へ
  自分で置く」**と書く。「スコープ外だから」と書くと、**Workspace 層が有効化されれば解決する
  課題**であることが読み取れない。
- **`sync-gemini-assets.sh` のコメントにも upstream issue #18186 を書く。** 将来 Workspace 層が
  有効化されたときに、この判断を見直す入口になる。
- **多重防御が1枚になるという帰結は変わらない**（むしろ、こちらの都合ではなく Gemini CLI 側の
  制約による、と分かった）。

## C. `--check` の実行位置

`--check` は「`.claude/` と `.gemini/` が食い違っていたら非0で落とす」モード。
**flow-id 5-3 の新設により、`--check` は「忘れ防止の主役」ではなく補助**になった。

| 案 | 位置 | 効果 | コスト |
|---|---|---|---|
| C-1 | **どこにも自動で挿さない**（手動／CI用に用意するだけ） | ゼロ | flow-id 5-3 を飛ばすと気づけない |
| C-2 | `create-commit.sh` の中（コミット前） | 差分があれば**止められる** | **全コミットが遅くなる**。`.claude/` を編集した直後は必ず食い違うので、**通常の作業が止まる** |
| C-3 | PostToolUse hook（push後） | **気づかせるだけ** | push のたびに走る。外部プロセス起動のコストが乗る |

### 決定: C-1（2026-08-22のレビューで確定）

**「どこにも自動で挿さない」**（手動／CI用に用意するだけ）。理由は次の2点。

1. **C-2 は運用が破綻する。** このフローでは `.claude/` の編集とコミットが何度も繰り返され、
   同期は flow-id 5-3（フェーズ5）で1回行う設計である。コミットのたびに止めると、
   **同期を前倒しで何度も走らせることになり、flow-id 5-3 を新設した意味が消える。**
2. **C-3 は「気づかせるだけ」なのに、全pushへコストを課す。** 同じ「気づき」は flow-id 5-3 が
   確実に与える（そこで必ず同期するため）。

**`--check` 自体は実装する**（CI・手動確認・将来の自動化のため）。**挿す位置を決めないだけ**である。

**C-1 が残す穴と、その受け皿**: flow-id 5-3 を飛ばすと食い違いに気づけない。これは
**`HANDOFF.md` の進捗表が担保する**（5-3 は表に現れるステップなので、飛ばすと `[]` のまま残る）。
自動検知を足すのは、この担保が実際に破れたことを観測してからでよい。

## D. `.gemini/settings.json` の3つの役割の切り分け

現行の `.gemini/settings.json` は**手書きの実体**だが、本issue後は次の3つの役割が重なる。

| 役割 | 何を指すか |
|---|---|
| ① 変換の**出力** | `sync-gemini-assets.sh` が生成して書き込む先 |
| ② `--check` の**比較対象** | 「生成したらこうなるはず」と突き合わせる相手 |
| ③ 単体テストの**ゴールデンファイル** | 変換規則が壊れていないことを固定する期待値 |

**①と②を同じファイルにすると、`--check` は自分自身を比較することになり常に一致する**
（検査として無意味になる）。

### 選択肢

| 案 | ①出力 | ②比較 | ③ゴールデン | 評価 |
|---|---|---|---|---|
| D-1 | `.gemini/settings.json` | 一時ファイルへ生成して①と比較 | `.claude/scripts/test/fixtures/` に別置き | **推奨**。3役割が別の実体になる |
| D-2 | `.gemini/settings.json` | 同上 | ①を流用 | ゴールデンが出力と同じなので、**変換が壊れても両方同時に壊れて気づけない** |
| D-3 | `.gemini/settings.json.generated` を別に持つ | 生成物同士 | 別置き | ファイルが増え、Gemini CLI が読む実体がどれか分かりにくい |

### 決定: D-1（2026-08-22のレビューで確定）

`--check` は「入力（`.claude/`）から**その場で生成**し、Git管理下の `.gemini/` と突き合わせる」
という形にする。ゴールデンファイルは**テスト専用の入力**から生成した期待値であり、リポジトリの
実体とは別（`.claude/scripts/test/fixtures/`）に置く。

**D はチャットで個別に問われた3点（B・C・配布アセット）には含まれていない。** 計画そのものへの
合意が得られたことをもって D-1 で確定するが、異議があれば実装着手前に差し戻せる
（変わるのはゴールデンファイルの置き場だけで、**変換規則そのものには影響しない**）。

採らなかった案: **D-2**（ゴールデンに出力を流用）は、変換が壊れたときに出力と期待値が同時に
壊れて検出できない。**D-3**（`.generated` を別に持つ）は、Gemini CLI が読む実体がどれか
分かりにくくなる。

**③のゴールデンは、現行の手書き `.gemini/settings.json` をそのまま採用しない。**
調査で「10観点のうち8つは正しいが、`permissions` は誤り・SessionStart matcher は未確認」と
判明しているため、**A と B の確定後に作り直す。**
