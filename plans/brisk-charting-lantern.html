この計画で何をするか

.claude/skills/issue-mr-flow/SKILL.md に 「AIアセット反映の対象の洗い出し」節を新設し、flow-id 4-1・4-6 の行からそこを参照させる。節が持つのは次の6つである。

  1. 洗い出しの起点（今回のMRで、既存アセットで対応できなかったもの）
  2. 4類型（(a) アセットが無かった／(b) あったが誤っていた／(c) あったが罠が書かれていなかった／(d) あったのに辿り着けなかった）
  3. 再現性の証拠を要求する範囲（(a) のみ。(b)(c)(d) は1回でも反映する）
  4. 証拠集めの段階と打ち切り条件（同一MR内 → doc-search → 直近のPR・DDR一覧、で打ち切る）
  5. 反映先の形態の選び方（「いつ効いてほしいか」×「守らせ方の強さ」の2軸）。どの形態までを対象に含めるかは、既存の除外規定（.claude/scripts/ 配下は 【AIアセット作成】 の対象外）と衝突するため、フェーズ2のQ7で決める
  6. 削除・統合も対象であること

あわせて plans/REVIEW-POINTS.md へ 【AIアセット反映】 の計画に対するレビュー観点を足し、判断の理由と却下案をDDRへ残す。.claude/docs/spec/issue-mr-workflow.md は入口のみとし、手順そのものを二重に持たない。

方針

  • 手順の正はSKILL.mdの1箇所に置く。 issueの受け入れ条件が明示的に「spec側は入口のみ」と求めており、このリポジトリが繰り返し問題にしてきた二重管理を避ける。
  • 4類型は「アセットの有無」と「不足の性質」で切る。 (a) だけ再現性の証拠を要求するのは、新設が継続コスト（読む量・(d) の温床）を伴うのに対し、(b)(c)(d) は既存アセットの精度を上げるだけで、書かないコスト（次のセッションが同じ罠を踏む）と書くコストが非対称なためである。
  • 証拠集めは安い側から見て打ち切る（全MR横断の網羅探索はしない）。flow-id 5-4 で plans/ worklog/ reports/ を消して squash merge するため、過去MRの一次資料は main には残らず、PR単位の履歴を1件ずつ辿るしかない（PRのコミット一覧には削除前の断面が残るので、「原理的に辿れない」わけではない）。探索コストがMR件数に比例して増える一方、そこで得られる確度の上がり幅は小さいため、費用対効果で打ち切る。
  • 反映先の2軸は「いつ効いてほしいか」×「守らせ方の強さ（読ませる → 手順化 → 検証で落とす）」。 issue #155 は形態として rules / skills / scripts / hooks / REVIEW-POINTS.md / agents の6つを挙げているが、現行のSKILL.mdは .claude/scripts/ 配下を 【AIアセット作成】 の対象から明示的に除外しており、flow-id 4-6 の反映先も4つに限定している。この衝突を放置したまま6形態を書くと、同じSKILL.md内に矛盾する2つの定義が並ぶ。どちらへ揃えるかはQ7で決め、決めた側に合わせて既存記述も書き換える（片方だけ足さない）。
  • 削除・統合を対象に含める場合、配布経路での実害を打ち消す記述を手順側に持たせる。 install-to-project.sh は上流で消えたファイルを配布先から削除しない（コピーのみ）ため、削除・統合したアセットが配布先には旧版のまま残り、新旧が両方読まれる。手順が問題視している (d)「あったのに辿り着けない」を配布先で自ら増やすことになる。何を書けば打ち消せるかはQ8で決める。
  • 削除・統合を対象に含める。 追加だけを見ているとアセットが単調増加し、(d)（辿り着けない）を自ら量産する。

  4. 証拠集めの段階で使う doc-search は、何を入力に何を返すか。打ち切り条件として書ける形か。
  5. 【AIアセット作成】（フェーズ3）と 【AIアセット反映】（フェーズ4）の既存の使い分け（issue #110）と、新設する洗い出し手順が矛盾しないか。

issue分割の判定

分割しない 受け入れ条件は「SKILL.mdの節」「表」「打ち切り条件」「2軸」「REVIEW-POINTS」「DDR」「spec入口」と並ぶが、これらは同型の成果物の並列列挙ではなく、1つの手順定義を成立させるための構成要素である。「各項目が単独でマージされてもシステムが壊れないか」で判定すると、たとえば4類型だけをマージしても証拠要求範囲が無く手順として機能しない。横断的変更に当たるため分割の対象ではない。

進め方の前提（このブランチ固有）

  • ハーネスの指定によりブランチ名は claude/ai-asset-reflection-scope-njqn95 を使う（.mrworkflow.json の feature-<issue番号>-<slug> 規則の例外）。
