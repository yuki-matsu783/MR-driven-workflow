## 反映対象（flow-id 4-1 で洗い出した結果）

### 1. `.claude/rules/shell-script-style.md`

いずれも**今回実際に踏んだ**もの。既存の類似項目のすぐ近くへ入れる（重複した節を新設しない）。

| 追加する内容 | 入れる節（**節の内外を一意に書く**） | 実例 |
|---|---|---|
| **数値の桁区切りは、行全体ではなく「数値と分かっている場所」へ適用する** | **`## 文字コード` 節の中**、`awk`/`sed` の置換文字列に `\r` を書くなという項の**直後** | markdownの表を組み立てたあとに `sed -E ':a; s/([0-9])([0-9]{3})...'` を行全体へかけ、モデル名 `claude-3-5-sonnet-20241022` を `claude-3-5-sonnet-20,241,022` へ壊しかけた。整形は組み立て前（jq側の数値セル）で行う |
| **`grep` へ `-` で始まるパターンを渡すときは `--` を置く** | **`## JSON操作` 節の `jq --args` の `--` の項の直後**（下記「配置の判断」参照） | `grep -cF '- 使用モデル:'` が `unknown option` で失敗した。`jq --args` と同じ理由（先頭のハイフンをオプションとして解釈する） |
| **`perl -0pi -e "..."` / `sed "..."` をダブルクォートで囲まない** | **`## 文字コード` 節の中**、既存の「AIエージェント向け注記: バックスラッシュが1つに潰れることがある」の項へ**1文追加**（独立した項を作らない） | 置換文字列に含めた `$(printf ...)` をシェルが先に展開し、意図しないコマンドが走った。小さな修正はEditツールで行う |
| **Windows版jqにプロセス置換 `<(...)` のパスを渡せない**（フェーズ2で判明。worklog push3 に「フェーズ4で検討」と明記） | **`## git bashのパス変換の落とし穴` 節の中**、`MSYS_NO_PATHCONV` とWindows版jqの項の**直後** | `jq -s -c '...' <(jq -c . session2.jsonl)` が `Could not open file /proc/48730/fd/63` で失敗。WindowsネイティブのjqへMSYS側の疑似ファイルパスを渡せない。一時ファイル経由へ書き換えて解決した |

**「節の後」と書かない。** 当初の記述は1件目を「『文字コード』節の**後**、`sed`/`awk` の項の
近く」としていたが、`awk`/`sed` の項は**その節の中**にあるため両立しない自己矛盾だった。
差し込み先は必ず「どの節の**中**の、どの項の直後か」で書く。

**配置の判断（`grep` の項をどこへ置くか）**: 内容は「引数の先頭ハイフン」の話で、
`## JSON操作` という節名とは噛み合わない。それでも `jq --args` の項の直後へ置くのは、
**原因も対処も同じ（`--` を置く）ため、隣接させたほうが両方を一度に思い出せる**からである。
実施時に、`jq --args` の項の見出し的な一文を「`--` を置く」という共通の主題へ広げ、
`jq` と `grep` の両方を例として並べる形にする（節をまたいだ相互参照より読みやすい）。

### 2. `.claude/skills/resolve-conflict/SKILL.md`

| 追加する内容 | 入れる箇所 |
|---|---|
| **コンフリクトした範囲だけでなく、同じマージで「自動マージされて入った行」も確認する** | **Step 5（検証）へ1項目**（類型に依存せず必ず通るため。「解消の一部」と読めば Step 4 だが、Step 5 のほうが漏れにくい） |
| **`main` 側に既存のテスト失敗がある場合の扱い**（Step 5 は「1つでも落ちたらコミットしない」としか書いておらず、マージ由来でない既存の失敗をどう扱うかが無い） | **Step 5 の「1つでも落ちたらコミットしない」の直後** |

実例1（自動マージ）: 2回目の `main` マージで、`HANDOFF.md` の競合部分は解消したものの、
**コンフリクトせずに自動マージで入り込んだ別タスクのHTMLコメント**が残った。`HANDOFF.md` は
「このブランチの現在の状態」だけを表すべきファイルなので、これは誤りである。gitが競合と見なさない
変更は `git status` にも `git diff --check` にも出ないため、**マージ後に対象ファイルを通しで読む**
必要がある。

実例2（既存の失敗）: `main` 上に `test_post_issue_create_notice.sh` の `failures=1` が既にあり
（issue #94）、Step 5 の記述をそのまま適用するとコミットできない。今回は
**「マージ由来でないことを `main` 単体で再現して確認したうえで続行し、報告する」**と判断した。
この判断基準がスキルに無いと、同じ状況で毎回判断が割れる。書くのは次の3点。

1. 失敗が**マージ由来かどうかを切り分ける**（`origin/<base>` を単体でチェックアウトして再現するか）。
2. 再現するなら**既存の失敗**として続行してよい。再現しないならマージ由来なので直す。
3. 続行した場合は、**どのテストがなぜ失敗しているかを Step 7 の報告に必ず含める**（黙って通さない）。

### 3. `.claude/REVIEW-POINTS.md`（`.claude/` 配下のレビュー観点）

| 追加する観点（案） | 根拠 |
|---|---|
| **既存の出力を変えないはずのリファクタで、変えていないことを機械的に確認しているか**（旧実装との `diff`、旧テストの実行など。目視や「テストを足した」だけで済ませていないか） | 今回 `build_usage_report_body` の切り出しで実際に必要になった。「テストを足した」だけでは切り出し時点の劣化を検出できない |

**判断が必要な点**: この観点は `.claude/` 配下に限らずリポジトリ全体に効く。
**ルート直下の `REVIEW-POINTS.md` へ置くべきか**を実施時に判断する
（`.claude/rules/directory-structure.md`「一般的な観点ほど上位へ置き、下位で重複して書かない」）。

## 検証手順

```bash
# 1. frontmatterインデックスが再生成できること（変更したmdのfrontmatterが妥当か）
bash .claude/scripts/src/extract-frontmatter.sh .

# 2. レビュー観点の収集が壊れていないこと（REVIEW-POINTS.mdを触った場合）
bash .claude/scripts/src/collect-review-points.sh .claude/hooks/lib/UsageTracking.sh
bash .claude/scripts/test/test_collect_review_points.sh   # passed=N failures=0

# 3. 単体テスト全体への巻き添えが無いこと
for t in .claude/scripts/test/test_*.sh; do echo "== $t"; bash "$t"; done

# 4. 差し込み位置の前後を目視で確認する（N=差し込んだ行番号。差し込み箇所ごとに実行する）
#    見るのは「空行が2つ連続していないか」「次の見出しの直前に空行が1つあるか」の2点
sed -n "$((N - 3)),$((N + 12))p" .claude/rules/shell-script-style.md
sed -n "$((N - 3)),$((N + 12))p" .claude/skills/resolve-conflict/SKILL.md
sed -n "$((N - 3)),$((N + 12))p" REVIEW-POINTS.md    # 観点を足した側のファイル
```

- 手順3では `test_post_issue_create_notice.sh` の `failures=1`（既存の失敗。issue #94）**だけ**が
  出ることを確認する。
- **手順4を省略しない。** 既存ドキュメントへ節を差し込む作業であり、
  `.claude/rules/docs-workflow.md`「既存ドキュメントへ新しい見出しを差し込むときは、挿入位置の
  直前の節が『その節全体にかかる地の文』で終わっていないかを必ず確認する」が直接効く。
