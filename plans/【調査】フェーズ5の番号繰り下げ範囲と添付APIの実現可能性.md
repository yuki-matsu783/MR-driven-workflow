# 個別調査計画: フェーズ5の番号繰り下げ範囲と添付APIの実現可能性（issue #111）

全体作業計画: `plans/mellow-drifting-lantern.md`

## 目的

フェーズ3（作業）の前に、**机上で決め切れない3点**を確定させる。いずれも、外したまま実装へ
進むと後戻りが大きい。

## 調査1: フェーズ5の番号繰り下げが波及する範囲

### 何を調べるか

`flow-id 5-3` / `5-4` / `5-5` を参照している箇所を全件列挙し、次の3群へ分類する。

| 群 | 扱い |
|---|---|
| **書き換える** | 現在の手順・状態を説明している記述 |
| **書き換えない（注記で補う）** | DDR本文、spec内の過去changelog（point-in-timeの記録） |
| **書き換えない（無関係）** | 別の意味で同じ数字列を含むだけのもの |

### なぜ必要か

`.claude/rules/docs-workflow.md` が「ファイル移動・改番に伴うパス／番号の一括置換を、DDR本文や
過去changelogへ当ててはいけない」と明示的に禁じており、**issue #47 で実際に踏んでいる**。
`sed` の一括置換を当てる前に、当ててよい範囲を確定させておく必要がある。

### 進め方

1. `grep -rno 'flow-id 5-[1-6]'` で全件を機械的に列挙する。
2. ファイルごとに前後を読み、上表の3群へ分類する。
3. 「書き換えない」と分類したもののうち、**注記（DDRなら frontmatter の `note`）で補うべきもの**を
   決める。issue #112 の前例（`i0028-01` の `note`）に倣う。

### 完了条件

分類表が `reports/` に残り、フェーズ3の置換作業がその表だけを見て機械的に実行できる状態。

## 調査2: GitHub添付APIの実現可能性

### 何を調べるか

issue #111 が挙げた `https://uploads.github.com/user-attachments/assets` が、**この実行環境で
使えるか**を確認する。確認する軸は次の3つ。

1. `gh auth token` 相当のトークンをこの環境で取得できるか（`gh` CLIは不在）。
2. MCP経路（`mcp__github__*`）に添付相当のツールがあるか。
3. 到達性そのもの（プロキシ経由で `uploads.github.com` へ出られるか）。

### なぜ必要か

**使えないと分かること自体が、設計判断（層3を任意にする）の裏付けになる。** 逆に使えるなら、
`Provider.sh` の実装を実際に動かして確かめられる。どちらに転んでも設計へ効く。

### 進め方

- 到達性は `curl -sS -o /dev/null -w '%{http_code}'` で**認証なしのHEAD/POST**を1回だけ試す
  （401/403が返れば到達はしている、という切り分けに使う）。**実ファイルをアップロードしない。**
- MCPツールの有無は `ToolSearch` で `attachment` / `upload` を検索して確認する。
- GitLab側（`projects/:id/uploads`）は公式APIドキュメントの仕様確認に留める（実機なし）。

### 完了条件

「この環境で層3が動くか／動かないか」と、その根拠（実行したコマンドと返ってきたステータス）が
記録されている。**確かめられなかったことは、確かめたことと区別して書く。**

## 調査3: PR/MR通常コメントの種別識別

### 何を調べるか

issue #111 のコメントで指摘された「`add_mr_comment` で投稿される通常コメントが3種類になるため、
読み手が判別できる形が要る」への対応方針を、**既存2種の実装から**決める。

- 既存2種（チャット由来の判断の記録／スレッドを持たない指摘への対応記録）が、実際にどんな
  1行目を持っているか。
- 統括レポートのサマリを足したときに、既存2種を書き換えずに区別できる形があるか。

### なぜ必要か

既存2種の書式を変える案（例: 全種へラベルを付け直す）は、`SKILL.md` の複数箇所と過去の投稿に
波及する。**既存を変えずに済む形があるならそちらを採るべき**で、それは既存の書式を見ないと
決められない。

### 完了条件

1行目の規約が1案に決まり、既存2種を書き換える必要があるかどうかが明示されている。

## やらないこと

- **添付の実装**（フェーズ3の担当）。本調査は可否の確認までとする。
- **実際のファイルをGitHubへアップロードする試行**。未ドキュメントの内部エンドポイントへ
  実データを投げるのは、可否確認に必要な範囲を超える。
- **GitLab実機での検証**（実機なし。issue #127 の担当）。

## 検証手順

- 調査1: 分類表の件数と `grep` の総ヒット数が一致すること（数え落としが無いことの確認）。
- 調査2: 実行したコマンドと終了コード・ステータスコードをそのまま記録すること。
- 調査3: 既存2種の1行目を実ファイルから引用すること（記憶で書かない）。
