# 【全体作業計画】PR作成後のdefaultブランチ追従を自動監視する手順の整備（issue #88）

対象issue: [#88 PR作成後のdefaultブランチ追従を自動で監視し、コンフリクトを検知しだい解消する手順を整備する](https://github.com/yuki-matsu783/MR-driven-workflow/issues/88)

> **注記**: 本ファイルは flow-id 1-4 の「全体作業計画」だが、非対話的なリモート実行セッション
> （Claude Code on the web）ではPlanモードでの合意を取れないため、**planツールを使わず**
> Write/Editで作成している。合意（flow-id 1-5）は取れていない。

## このissueで解決したいこと

レビュー待ちの間にdefaultブランチ（`main`）が進んで生じるコンフリクトを、人間が都度指摘しなくても
AIエージェントが検知・解消できるようにする。現在のフローはマージ直前の flow-id 5-2 でしか検知せず、
マージまでの時間が長い場合・並行PRが多い場合に追いつかない（実例: issue #39 のPR #81 で、PR作成後の
短時間に `main` が4回進み、DDR番号を 0034→0035→0036→0038 と3回繰り下げた）。

## 何を調査するか

**フェーズ2（調査）は省略する。** 必要な事実はissue #88 の本文に既に整理されており（衝突箇所の
性質・過去実績・暫定対応の限界）、追加で確認すべきなのは既存アセットの現状記述だけで、これは
個別作業計画の作成時に実測できる。確認する対象は次の4点。

1. `.claude/skills/issue-mr-flow/SKILL.md` の flow-id 5-2 と「defaultブランチとのコンフリクト
   検知・解消」節の現行記述
2. `.claude/skills/resolve-conflict/SKILL.md` の類型A〜Eと Step 2（ユーザー承認）の現行記述
3. `.claude/docs/ddr/0029-...md` の決定6（解消時はユーザーの承認を必ず取る）との関係
4. `HANDOFF.md` のヘッダ項目と `update-handoff-progress.sh` の `set-header` が扱う範囲

## 何を実装するか

ドキュメント（AIアセット）の整備が本体で、スクリプトの新規追加・変更は行わない
（`check-base-conflicts.sh` は既に繰り返し実行できる設計のため、監視のための機構追加は不要）。

**人間のレビュー往復（3-3/3-4・3-8/3-9・4-3/4-4・4-8/4-9）は、非対話的セッションのため実施できない。**
該当するループ範囲の進捗記号は `[]` のまま残し、実施した内容はHANDOFF.mdの「やったこと」で補う
（`.claude/rules/docs-workflow.md` の非対話的実行環境の運用に従う）。

## 判断が必要な点

- **flow-idを増やすか、フェーズ横断の並行手順として定義するか。** 監視は「開始（1-3の直後）から
  停止（5-4）まで続く状態」であり、1つの時点で完了するステップではない。40ステップの繰り下げは
  HANDOFF.mdの進捗表・`update-handoff-progress.sh`・複数のrules/specへ波及する。→ 本計画では
  **並行手順として定義し、flow-idは増やさない**方針で進め、理由と却下案をDDRへ残す。
- **自動解消をどこまで許すか。** DDR 0029 の決定6は「解消時はユーザーの承認を必ず取る」と定めて
  いる。issue #88 は類型A/C/Dの自動解消を求めており、この決定を監視モードに限って緩和することに
  なる。→ 新DDRで「解消方法が一意に決まる類型に限る」という基準を明示し、DDR 0029 の決定6は
  それ以外（類型E・対話可能な通常の flow-id 5-2）では引き続き有効とする。
