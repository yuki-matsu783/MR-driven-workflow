# 【調査】ベースブランチ追従確認の差し込み地点と検知方法（issue #67）

- 全体作業計画: `plans/base-branch-sync-check.md`
- 対象issue: [#67](https://github.com/yuki-matsu783/MR-driven-workflow/issues/67)

## 目的

「作業開始・再開時にベースブランチの最新を取り込めているか」を確認するステップを追加するにあたり、
**どこへ差し込むか**と**何をもって『遅れている』と判定するか**を、実物のコード・実際のgitの
挙動で確定させる。issue本文の「現状」に書かれた内容（`sync_branch()` が fetch と ff-only pull
しかしていない等）を鵜呑みにせず、自分で確かめる。

## 調べること

### 調査1: 既存機構の守備範囲（この空白は本当に空いているか）

- `.claude/scripts/src/vcs/Provider.sh` の `sync_branch()` が何をしているか（行番号つきで確認）
- `.claude/scripts/src/check-base-conflicts.sh` の出力JSONに、遅れ（behind）を表すキーがあるか
- `.claude/agents/issue-mr-resume.md` の現在地サマリの項目に、ベースブランチとの差分があるか
- `.claude/hooks/session-start.sh` がセッション開始時に注入する情報に含まれていないか
  （issue本文は触れていないが、「作業開始時」という点で重複しうるため確認する）

**確認の観点**: 「コンフリクトは無いが遅れている」状態を、既存のどれかが検知できてしまわないか。
できるなら本issueの前提が崩れるので、その旨を報告して方針を見直す。

### 調査2: 差し込み地点

`.claude/skills/issue-mr-flow/SKILL.md` のどこへ手順を足すかを確定する。候補は次の3つ。

| 地点 | 状況 | 調べること |
|---|---|---|
| `start` 手順2「見つかった場合（セッション再開）」 | 既存ブランチを検出して `sync_branch` するだけの経路 | `origin/<base>` が最新化済みか |
| `resume` | セッションを跨いだ引き継ぎ | 同上 |
| `sync` | 「ブランチを最新化したいだけ」の経路 | 同上 |

- 新規ブランチ作成時（`start` の「見つからない場合」）は、`main` から切るため定義上追従済み。
  確認が不要であることを確かめる。
- **各地点で `origin/<base>` を誰が最新化するかを確かめる**（これが無いと、古いリモート追跡参照を
  見て「遅れていない」と誤って報告する）。とくに `resume` は `issue-mr-resume` サブエージェントが
  担っており、**同エージェントは「読み取り専用」と規定されている**。fetchを新スクリプト側で行うのか
  呼び出し元で行うのか、読み取り専用の規定と矛盾しないかを判断材料まで含めて調べる。
- **ブランチ名が `branchPrefixTemplate` に一致しない場合の挙動**を確かめる（本ブランチ
  `claude/base-branch-sync-check-17vdvq` がまさに該当し、`get_issue_number_from_branch` は
  終了コード1を返す）。追従確認をissue番号に依存しない設計にできるか、`resume` 手順4の
  「命名規則から外れている旨を伝える」分岐に入ったときも追従確認まで到達するかを見る。
- flow-id 5-2（`check-base-conflicts.sh`）・「PR作成後のdefaultブランチ追従（監視）」との
  **役割の違いを1つの表で説明できるか**を確認する（受け入れ条件の最後の項目）。

### 調査3: 検知に使うgitコマンドと境界条件

- behindコミット数: `git rev-list --count HEAD..origin/<base>`
- 未取り込みの変更ファイル: `git diff --name-only HEAD...origin/<base>`（3点リーダ）
  - **2点（`..`）との違い**を実際に確かめる。3点は「merge-base から見た base 側の変更」であり、
    作業ブランチ自身の変更を含まない。ここを取り違えると「自分が変えたファイル」を
    「取り込めていないファイル」として提示してしまう。
- 境界条件として次を確認する。
  1. `origin/<base>` のリモート追跡参照が存在しない場合に何が起きるか
  2. `--no-fetch` を付けた場合と付けない場合で結果が変わるか（fetch前は古い `origin/<base>` を見る）
  3. merge-base が取れない場合（無関係な履歴）
  4. behind が 0 でも ahead がある通常の状態を「遅れ」と誤判定しないか
  5. **リポジトリが shallow clone の場合**（`git rev-parse --is-shallow-repository` が `true`）。
     本セッションの実行環境（Claude Code on the web）がこれに該当する。merge-base が取得済みの
     深さの外にあると `rev-list --count` が実際より小さい値を返しうる。**誤検知の向きが安全側で
     ない**（遅れているのに0件と報告する）ため、他の境界条件より優先して確かめる。

### 調査4: 出力形式と既存スクリプトとの整合

- `check-base-conflicts.sh` の引数（`--base` / `--head` / `--no-fetch`）・出力JSON・終了コードの
  規約を確認し、新スクリプトを**同じ規約に揃えられるか**を判断する。
- 変更ファイルが多いときにJSONが肥大化しないよう、件数上限と切り詰めの表現を決める。

### 調査3（**使い捨ての別リポジトリ**を作って確認する）

**この作業ブランチ・リモートには一切触れない。** behind のある状態を作るには最低1コミットが
必要だが、`.claude/hooks/block-direct-git-commit.sh`（PreToolUse hook）がBashツールへ渡した
コマンド文字列を部分一致でブロックするため、**フィクスチャ構築はスクリプトファイルへ書き出して
`bash <script>` で実行する**（コマンド文字列に該当語が現れないため発火しない）。スクリプトと
リポジトリはスクラッチパッド配下へ作り、確認後はディレクトリごと削除する（`plans/` `worklog/`
`reports/` へは残さない）。

フィクスチャの形: `main` を4コミット進め（うち1つは両ブランチが触っていないファイルの変更）、
`feat` を1コミット進めた状態。境界条件ごとに次を確認する。

| 境界条件 | 再現方法 |
|---|---|
| 通常（behind>0・ahead>0） | 上のフィクスチャで `rev-list --left-right --count` と3点／2点diffを比較する |
| 1. `origin/<base>` 不在 | 存在しない参照名（`origin/nonexistent`）を指定して終了コードを見る。あわせて `--depth 1 --branch <b>` の single-branch clone で `origin/main` が作られないことと、`git fetch origin 'main:refs/remotes/origin/main'` で復旧できるかを見る |
| 2. fetch の有無 | clone直後（fetch前）と `git fetch origin main` 後で `origin/main` のSHAが変わることを見る |
| 3. merge-base 無し | `--orphan` ブランチに1コミット積み、`merge-base` / `rev-list --left-right` / 3点diff の**それぞれ**の終了コードを見る |
| 4. ahead のみ | `origin/main` からブランチを切って1コミット積み、`0<TAB>1` になることを見る |
| 5. shallow | `--depth 1` でcloneし、`is-shallow` が `true` の状態で上の各コマンドがどう振る舞うかを見る |

### 後始末

確認が終わったら、フィクスチャのディレクトリを削除する（`rm -rf <スクラッチパッド>/gt`）。
作業ツリー・`git status` に影響が出ていないことを確認する。
