# 【AIアセット作成】残置テキストの係り先ルールを一般化する

issue #142 / PR #188 / flow-id 3-1。

## 前提（合意状況）

- 上位の計画: `plans/brisk-weaving-lantern.md`（flow-id 1-4）。
- **調査結果が確定させたこと**は `reports/20260823_brisk-weaving-lantern_係り先ルールの射程調査.md`
  「設計への反映（フェーズ3で決めること）」の8項目が正である。**本計画はそれを実行手順へ落とすもので、
  結論を蒸し返さない。**
- flow-id 3-3（人間の作業計画レビュー）は非対話的セッションのため成立しない。**本計画に対する
  敵対的レビュー（フェーズ3の1回目）をもって代替する。**

## この計画で何をするか

書き換え先は**2箇所**。どちらも「残置したテキストの係り先が変わっていないか」という同じ観点を
述べるが、**役割が違うので同じ文言にはしない**。

| # | ファイル | 現在 | 何をするか |
|---|---|---|---|
| A | `.claude/rules/docs-workflow.md` 104〜114行 | 見出しの挿入に限定された規約＋実例2件 | **正**。発動条件を一般化し、実例を4件へ増やす |
| B | ルート `REVIEW-POINTS.md` 47〜48行 | 「新しい見出しの挿入位置が…係り先を壊していないか」 | **敵対的レビューが実際に読む唯一の経路**。単独で「何を疑うか」が伝わる中身にする |

**Bを「Aを見よ」というポインタで済ませない。** `collect-review-points.sh` は `REVIEW-POINTS.md` /
`REVIEW-POINTS.local.md` しか集めず、**`.claude/rules/` は敵対的レビューへ渡らない**（Q5）。
ポインタだけでは、辿る動機そのものが生まれない。

## A: `.claude/rules/docs-workflow.md` の書き換え

### A-1. 発動条件（トリガー）

- **操作の分類で書かない。**「見出しの差し込み」も「構造変更全般」も操作の分類であり、
  issue #155（箇条書きへ項を1つ足しただけ）が含まれるかどうかが読み手に委ねられる。
- **残置テキストの側から書く。**「既存の記述を残したまま、その周囲を編集したとき」という形にする。
  周囲の編集には、見出しの挿入・節の分割・項の追加・並べ替えのいずれもが自動的に入る。

### A-2. 確認の観点

- 「**残置した地の文・箇条書きが、変更前と同じものに係っているか**」を見る。
- **前後どちらの残置テキストも見る。** 現行の「直前の節が…」は、PR #139（新設した見出しの配下へ
  既存の段落群が入ってしまった形）を**射程内の操作なのに検出できなかった**。

### A-3. 実例（計4件）

**既存2件を1行も消さない**（受け入れ条件）。109〜114行の6行はそのまま残し、2件を足す。

| 実例 | 何を示すか | 扱い |
|---|---|---|
| `計画の2階層構造` の位置（issue #64） | 挿入位置の**前**が壊れる | **既存のまま残す** |
| ファイルごとに結論が変わる（issue #64） | 同じ節名でも判定が変わる | **既存のまま残す** |
| issue #109 | **分割前は正しかった行が、分割によって誤りになる** | 追加 |
| PR #139 | 新設した見出しの**後ろ**が巻き込まれる | 追加 |

- issue #155 は**5件目として並べない**（4件で方向・操作の両軸が揃い、5件は読み手の負担になる）。
  代わりに A-1 の根拠として**1行だけ**触れる（「箇条書きへ項を1つ足しただけでも起きた」）。
- 4件それぞれについて、**書き換え後の文言を読んで「見るべきだった」と分かるか**を机上で
  突き合わせる（上位計画の検証条件）。

### A-4. 書き換えるときに自分が踏んではいけない罠

**この段落の直後（116行以降）は `HANDOFF.md` の進捗記号を扱う無関係な段落である。**
一般化にあたって新しい見出しを立てると、その段落が新しい見出しの配下に入り、**PR #139 と
まったく同じ事故**を起こす。次のいずれかを守る。

- 新しい見出しを**立てない**（現行と同じく、見出しを持たない段落として書く）。
- 立てるなら、直後の `HANDOFF.md` の段落にも**見出しを与える**。

**どちらを採るかは flow-id 3-6 の作業時に決めてよい**が、決めた根拠を作業結果へ書く。

## B: ルート `REVIEW-POINTS.md` の書き換え

「ドキュメントの構造」節の該当2行を、次の2点を**単独で読めるだけの中身**を持つ形へ書き換える。

1. **発動条件**: 既存の記述を残したまま、その周囲を編集したとき。
2. **前後どちらも見る**こと。

- 詳細（4件の実例・背景）はAへのリンクで足りる。観点表は**判定に必要な最小限**を持てばよい。
- **既存の「挿入するなら節の末尾（次の見出しの直前）へ回す」という具体的な逃げ道は残す**
  （一般化で抽象度が上がった分、対処の手がかりが消えるのを避ける）。
- **同じ節の他の観点との重複を作らない。** 直下に「同じ内容が複数ファイルに重複して書かれて
  いないか」があるため、そこと混ざらない位置・粒度にする。

## 検証

**作業が終わったと言える条件は、次の4つがすべて満たされていることである。**

- **既存2実例（計6行）が1行も消えていない。** 下記コマンドが `0` を出す。
- **4件の実例すべてが、書き換え後の文言の下で「見るべきだった」と説明できる。** 4件×判定を
  作業結果（`reports/…md`）へ表で書く。
- **ルート `REVIEW-POINTS.md` が、Aを読まなくても (i) 発動条件と (ii) 前後どちらも見ること を
  伝えている。** 該当行だけを抜き出して読み、2点が読み取れるかで判定する。
- **A-4 の罠を踏んでいない。** 書き換え後の `.claude/rules/docs-workflow.md` で、
  `HANDOFF.md` の進捗記号を扱う段落が、新しい見出しの配下に入っていないことを確認する。

```bash
# 既存2実例（.claude/rules/docs-workflow.md の109〜114行、計6行）が1行も消えていないこと。
# 判定語は6行それぞれに固有のものを選ぶ（1語だと途中行の削除を見逃す）。
# 対象パスは書き換え先2箇所の両方（.claude/ とルート REVIEW-POINTS.md）。
# 分岐点SHAは直接渡す（origin/main は fetch のたびに動くため）。
base=4be448af553c82c0fcf731705b0cd1d08bf23f29
git diff "$base" -- .claude/ REVIEW-POINTS.md | grep '^-' | grep -cF \
  -e '末尾に節全体へかかる地の文' \
  -e 'での機械的列挙・flow-id 1-4の判定' \
  -e 'の直前へ新節を入れた' \
  -e '同じ節名でもファイルごとに結論が変わる' \
  -e '直後に地の文が無く' \
  -e '入れられたから安全' || true

# A-4 の確認: 書き換えた段落と HANDOFF.md の段落の間に見出しが増えていないか、
# 増えているなら HANDOFF.md の段落にも見出しが付いているかを目視する。
sed -n '100,130p' .claude/rules/docs-workflow.md
```

**上のコマンドが空振りしないことは flow-id 2-6 で確認済みである**（6行を1行ずつ削ったツリーで
それぞれ `1` が出る。結果は `reports/20260823_brisk-weaving-lantern_係り先ルールの射程調査.md`
「全体作業計画の検証コマンドの空振り確認」）。**2つ目の `sed` は目視の材料であって合否判定では
ない**（実行できたことは何も保証しない）。
