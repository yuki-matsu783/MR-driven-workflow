# 【調査】報告HTMLのホスティング手段とタイミングの選定

## 前提（合意状況）

- 上位の計画: `plans/binary-soaring-eclipse.md`（**flow-id 1-5 で合意**）。
  **調査する4つの問いの定義（案の内容・却下候補の一覧を含む）は、上位計画の
  「フェーズ2〈調査〉」節が正である。** 本計画は重複させず、**実行手順と比較の観点表**だけを持つ。
- issue を分割せず1件で進めること・GitHub / GitLab とも**実機検証まで行う**ことは、
  **flow-id 1-4 でユーザーが判断**した。
- **ホストするタイミングは案(b)で確定**（flow-id **5-4** でホスト、**5-6** で通知のみ）。
  **flow-id 2-4（レビュー1周目）でユーザーが判断**した。
- **flow-id の番号は #111・#112・#157 で繰り下がっている。** 対応表は上位計画
  「issue 起票後に前提が変わっている」が正。本計画は**現行の番号**で書く。
- **まだ合意されていない**: 手段の選定結果そのもの。本調査の結論は `reports/` へ書き、
  flow-id 2-8 の人間のレビューで合意する。

## この計画で何をするか

issue #114 の実装方針を決めるために、次の4つを確定させる。

1. **どの手段でホストするか**（GitLab / GitHub それぞれ。却下した手段は却下理由つきで残す）
2. **確定済みの案(b)が成立する条件**（案の選定はやり直さない。下記「方針」問い1）
3. **`plans/` のHTMLビューをホスト対象に含めるか**（上位計画が本フェーズへ送った判断）
4. **配布物としてのCI設定の扱い**（含める／含めないと、それを実現する実装箇所）

あわせて、**実機検証に必要な環境の構築コスト**（GitHub Pages の有効化操作、GitLab Runner の
構築手順）を見積もる。

## 変更対象

**この調査ではリポジトリのコード・設定を変更しない。** 成果物は `reports/` と `worklog/` 配下のみ。

| ファイル | 操作 | 何をするか |
|---|---|---|
| `reports/20260823_binary-soaring-eclipse_ホスティング手段の比較.md` | 新規 | 調査結果の**正文**。4つの問いへの結論・根拠・却下案 |
| `reports/20260823_binary-soaring-eclipse_ホスティング手段の比較.html` | 新規 | 同内容の人間レビュー用ビュー（土台は `.claude/skills/issue-mr-flow/assets/reports.template.html`） |

（下記「やらないこと」）。**読み取り専用の実機確認**（`gh api …/pages` が404を返す、

## 方針

### 問い1: 案(b)の成立条件と、(a)(c)の却下理由の裏取り

**案の選定はやり直さない**（flow-id 2-4 でユーザーが案(b)を選択済み）。案(a)(b)(c) の定義は
上位計画が持つ。この調査で確かめるのは次の2点である。

**(i) 案(b)が成立する条件**

| 確認すること | なぜ |
|---|---|
| flow-id 5-4 の push を CI がどのトリガで捉えるか | ホストが始まる契機を特定するため |
| flow-id 5-5（`reports/` 削除）の push が、既にホストされた内容を壊さないか | **案(b)の成否を分ける最大の点**。同じデプロイ先を上書きする構成だと、通知する前に消える |
| flow-id 5-6 でURLをどう取得するか | 通知するのはこのステップであり、5-4 の結果を後から引くことになる |
| CIが無い／失敗する環境で、フローが止まらないか | 配布先の大半はCIを持たない。`upload_attachment` と同じく**失敗は正常系**にできるか |
| デプロイ完了を待つ必要があるか・待つならどれだけか | 5-4 と 5-6 の間に人間の操作は挟まらないため、待ち時間がそのままフローの遅延になる |

**(ii) (a)(c) を却下した理由の裏取り**

DDR（`i0114-01`）へ却下案として残すため、**推測のまま却下理由にしない**。「不変パスにすると
デプロイが何個溜まるか」「5-6 から過去SHAを指定してCIを起こせるか」を実際の仕様で確かめる。

**(iii) `plans/` のHTMLビューをホスト対象に含めるか**

`plans/` も `reports/` と同じく flow-id 5-5 で削除される。含めると対象が増えてデプロイ時間と
デプロイ物のサイズが増える一方、レビュー時に計画も同じURLから辿れる。**結論を必ず書く。**

### 問い2: GitHub の手段

第一候補は **GitHub Pages ＋ Actions**。確認項目は上位計画の問い2が持つ（並列プレビューの表現・
デプロイ完了の待ち方とURL取得・fork PRでの `GITHUB_TOKEN`・Pages 有効化操作・**可視性設定との
一致**）。却下候補の一覧も同様に上位計画が持つ。

**この計画が足すのは、確認の順序だけである。** 「可視性設定との一致」を最初に確かめる
（ここで満たせない手段は、他の条件を調べる価値が無いため）。

### 問い3: GitLab の手段

CI/CD Review Apps（動的環境）。確認項目は上位計画の問い3が持つ（CI記法・ホストの実体・Runner
構築手順・URL取得・**可視性設定との一致**）。

**この計画が足すのは、ホストの実体を先に決めることである。** 「GitLab Pages」か「Runner 上の
静的サーバ」かで、可視性の扱いも Runner の構成も変わる。後者は**GitLabのアクセス制御の外**に
出るため、private プロジェクトで受け入れ条件を破りうる。

### 問い4: 配布物としての扱い

前提は上位計画の問い4が持つ（`sync-assets.sh` が `.github/` を丸ごと配布資産へ集めており、
**何もしなければ配布対象に載る**）。この計画では次の順で確かめる。

1. `.claude/docs/spec/distribution-assets.md` を読み、既存の配布経路（`.gitattributes` の
   `dist:begin`〜`dist:end` 方式）が何を解決しているかを把握する
2. 「含めない」と決めた場合の除外位置（`sync-assets.sh` の `.github/` コピー箇所か、
   `install-to-project.sh` の `safe_copy_dir` 箇所か）を特定する
3. 「含める」と決めた場合、配布先の既存ワークフローを `.bak` 退避で上書きする現在の挙動が
   許容できるかを判断する

### 進め方

1. 一次情報（GitHub Docs / GitLab Docs）を読み、問い2・問い3の必要条件を確定する
2. リポジトリ内の既存資産（`Provider.sh` の `upload_attachment`、`distribution-assets.md`、
   `gitlab-verification-environment.md`、`sync-assets.sh` / `install-to-project.sh`）を読む
3. 問い1の (i)(ii)(iii) を確かめる
4. 結果を `reports/` のmd（正文）とHTMLへ書く。worklog には試行錯誤を随時書き足す

## やらないこと（スコープ外）

- **実装（コード・CI設定・SKILL.md の変更）**。方針を決めるところまでで、実装は
  flow-id 3-1 以降で個別作業計画を立ててから行う
- **リポジトリ設定を変える実機検証**（GitHub Pages の有効化・GitLab Runner の実構築）。
  必要条件と手順の確認までに留める。**ユーザーの判断（flow-id 1-4）で実機検証まで行うと
  決まっているが、それはフェーズ3で行う**（調査段階でリポジトリ設定を変更すると、方針が
  覆ったときに戻す手間だけが残るため）。読み取り専用の実機確認は上記のとおり行ってよい
- **案(a)(b)(c) の選び直し**。flow-id 2-4 で確定済み。却下理由の裏取りは行うが、結論は覆さない
- ホストしたHTMLの公開範囲・寿命の**制御**（issue の受け入れ条件でスコープ外と確定済み）。
  ただし「可視性設定に従えるか」の**確認**は行う（問い2・問い3）
- `reports/` の削除タイミング（flow-id 5-5）の変更（上位計画でスコープ外と確定済み）

8. **フェーズ3で立てる個別作業計画が、この結果だけを読んで書ける**こと
9. md と HTML の節見出しが一致しており、内容が同期していること
