# 個別反映計画 — 洗い出し手順の根拠をDDRとspecへ残す

- issue: #155 / PR: #175
- 全体作業計画: `plans/brisk-charting-lantern.md`
- 直前の作業結果: `reports/20260823_brisk-charting-lantern_洗い出し手順の新設.md`
- フェーズ: 4〈反映〉 flow-id 4-1
- 種別: `【設計反映】`
- **対になる計画**: `plans/【AIアセット反映】洗い出し手順を自身へ適用して得た観点を反映する.md`

## なぜ2つの計画に分けたか

**当初は `【設計反映】` と `【AIアセット反映】` を1つの計画へ併記していたが、敵対的レビューの
指摘を受けて分割した。** `plans/REVIEW-POINTS.md` 24-25行目が
「`【設計反映】` `【AIアセット反映】` `【実装反映】` を併記していないか（**対象・評価軸が異なる
ため原則分ける**）」と明示しており、当初の理由（「合意を1回で取れる」）は22-23行目の一般則の
ほうだった。**一般則で個別則を上書きする前例を作ると、以後どの併記も「合意を1回で取れる」と
書けば通る**——しかも観点を新設した当のissueが最初の違反例になる。

**評価軸は実際に異なる。** こちらは「DDR・specの記述が正しいか（本文不変・却下案・changelogの
形式）」を見るのに対し、AIアセット反映側は「反映先の選択と、洗い出し手順の適用が規定どおりか」を
見る。

## この計画で何をするか

### 1. DDR `i0155-01` の新規作成

**記録する決定**（issue #155 で実際に選んだもの）:

| 決定 | 却下した案 |
|---|---|
| 洗い出しを**4手順**（起点の列挙／4類型への分類／痕跡の確認と打ち切り／反映先の形態の決定）に分ける | 手順を分けず「気づいたことを反映する」のままにする案 |
| **4類型**（(a) 無かった／(b) 誤っていた／(c) 罠が書かれていなかった／(d) 辿り着けなかった）で分類する | 「不足」「誤り」の2類型で済ませる案 |
| **再現性の証拠を要求するのは (a) だけ** | 全類型に要求する案／どれにも要求しない案 |
| **痕跡の確認は (a) と (c) の両方**で行う | (a) だけで行う案（**初回適用で穴が出たため改めた**。対になる計画の項目H） |
| 打ち切りを**3段階**（同一MR内／`doc-search`＋`grep`／直近10件のマージ済みPR＋DDR一覧）にする | 段階を設けず「見つかるまで探す」案／`git log` で遡る案 |
| 反映先を**2軸**（いつ効くか／守らせ方の強さ）で選ぶ | 反映先ごとの決め打ちの対応表にする案 |
| **`.claude/scripts/` `.claude/hooks/` もフェーズ4ではAIアセットとして扱い、種別は `【AIアセット反映】`** | `【実装反映】` にする案（**AIが当初採り、ユーザー判断で覆った**） |
| `【実装反映】` との判別は**反映先ではなく「どこから来た項目か」**で行う | 反映先のパスで分ける案（`i0110-01` の元の形） |

**`.claude/scripts/` の扱いについては、`i0110-01` の却下案を採る形になる**ため、その事実と
「境界の消失」への回答（判別を反映先から切り離した）をDDRへ明記する。

### 2. DDR `i0110-01` の frontmatter へ `note:` を追加

**本文は1文字も変更しない。** `status: superseded` ではなく `note:` を使う。

**理由**: 置き換えられたのは「`.claude/scripts/` を対象に含めない」という**決定の一部だけ**で、
issue #110 が決めた8種への拡張そのものは現役である
（`.claude/rules/markdown-frontmatter.md`「DDRのnote」の類型「**決定の一部だけが後で変わった**」）。

**この判断は人間に確認する**（PR #175 のレビュー依頼で問いかけ済み。`status: superseded` を
選ぶなら `superseded_by: "i0155-01"` を併記する形になる）。

### 3. DDR一覧の再生成

`bash .claude/scripts/src/generate-ddr-list.sh` を実行し、`.claude/docs/README.md` の差分を
同じコミットへ含める。**手書きで行を足さない**（issue #135）。

### 4. `.claude/docs/spec/issue-mr-workflow.md`

**2箇所を触る。当初は「入口1行のみ」としていたが、changelogが落ちていたため足した**
（敵対的レビューの指摘。全体作業計画43行目は当初から「入口（1〜数行＋SKILL.mdへの参照）と
**changelogの追記**のみ」と定めていた）。

| 箇所 | 内容 |
|---|---|
| 「仕様」側（フェーズ4を説明している箇所） | **入口1〜2行**。「AIアセット反映の対象の洗い出し手順は `.claude/skills/issue-mr-flow/SKILL.md` が正」と述べるだけ。**手順そのものは書かない** |
| 「影響範囲」（1824行目〜） | `### issue #155（AIアセット反映の対象を洗い出す手順の新設）` エントリ。**変更したファイル表**＋DDR `i0155-01` へのリンク。**却下案はDDR側に置き、ここには書かない** |

**changelogが必要な理由**（指摘で挙がった3つ）:

- squash mergeで `plans/` `worklog/` `reports/` は消えるため、**変更したファイル一覧が残るのは
  specだけ**である。
- DDR `i0155-01` の「影響範囲」節から参照する先になる（`i0110-01` が同じ形を採っている）。
- `.claude/docs/spec/distribution-assets.md` が「**据え置く場合は、そのissueのspecのchangelogへ
  据え置いた事実を残す**」と定めており、下記5の記録先がここになる。

## やらないこと

- **DDR `i0110-01` の本文の変更**。frontmatterの `note:` 追加のみ。
- **specへの手順の転記**。入口1〜2行とchangelogだけにする。
- **却下案をspecへ書くこと**。却下案はDDRが持つ。
- **AIアセットへの追記**。対になる `【AIアセット反映】` の計画が担当する。
- **配布経路が上流の削除を伝播しない件の修正**（調査結果Q8）。**別issueの起票を提案する**に留める。

（ルート `REVIEW-POINTS.md`「『変えていない』ことの検証」）。

### S6の測り方

**当初は「追記した節の行数が5行以内」という目視の判断だったが、(1) 実行できるコマンドが無い、
(2) 閾値の出どころが計画内に無い、(3) changelogエントリを書くと必ず落ちる、の3点を指摘されて
書き直した。**

```bash
# 「影響範囲」より前（＝「仕様」側）への追加行だけを数える
git diff 99fe2f2 -- .claude/docs/spec/issue-mr-workflow.md \
  | awk '/^\+\+\+/{next} /^\+/{print}' | grep -c 'AIアセット反映の対象の洗い出し'
```

**期待値は1〜2**（入口の参照が1〜2行）。changelogエントリはこの検証の対象外である。
