# issue #103 全体作業計画

## Context

Claude Codeが公式に備えるOpenTelemetry（OTLP）エクスポートを、ワークスペース配下の`usage/`へ
保存できる機構を追加する。

現在の対応工数レポート（`.claude/hooks/post-push-usage-report.sh` /
`.claude/hooks/lib/UsageTracking.sh`）は`transcript_path`が指すJSONLの自前パースに依存しており、
この非公開フォーマット依存のリスクはDDR
[i0000-04](.claude/docs/ddr/i0000-04-対応工数レポートはtranscript自前パースで実装する.md)に
記録済みである（実際、issue #28で判明したトークン数の過小カウント・issue #37で判明した重複行
問題など、非公開フォーマット依存に起因する不具合が繰り返し発生してきた）。

本issueは、この非公開フォーマット依存に対して**Claude Code公式のテレメトリ経路（OTLP）を
並行して確保する土台を作るもの**である。**対応工数レポートの集計元をtranscriptパースから
テレメトリへ置き換える作業ではない**（期待する動作9で明示的にスコープ外）。したがって
本issueのDDRは、i0000-04を「置き換える」のではなく「並行経路を追加する」関係として記録する。

技術的な核心は、常駐HTTPサーバが必要（bashでは実装できない）という制約のもと、追加インストール
不要なperlコアモジュールのみで実装することにある。実行環境のgit bashにperl 5.36.0が同梱されており
（実機確認: `IO::Socket::INET` 1.49・`JSON::PP` 4.07・`threads`・`POSIX`いずれも使用可能）、
`.claude/docs/spec/shell-scripts.md`が定める「bashで実現できないものだけPowerShellへ」という
既存の二択方針に、「常駐プロセスが必要な場合はperl」という枝を追加する判断になる。

## 参考資料の扱い

issue本文が言及する「参考にできるローカル資料」は、リポジトリ内の`参考ディレクトリ/otel/`
（Git管理外）に実在した。全文読了済み。

- `README.md`: Windows/WSLでポート（4318/4319）・出力先を分ける設計。仕組み（SessionStartフックが
  `sessions.jsonl`に`session_id`→`cwd`を追記しリスナーが落ちていれば起動、リスナーが`session.id`
  属性から出力先を引く、引けない分は`unrouted.jsonl`）。設定は各利用者の`~/.claude/settings.json`
  に`env`（`CLAUDE_CODE_ENABLE_TELEMETRY`等）と`hooks.SessionStart`を書く形。既知の制限（起動直後
  数秒の取りこぼし、cwd変更への追従なし、リスナーは常駐、ファイルは無限に伸びる）も明記されている。
- `listener.py`: `http.server.ThreadingHTTPServer`で127.0.0.1:PORTを待受。`sessions.jsonl`をmtime
  変化時のみ再読み込みしてキャッシュ。`find_session_ids`でOTLP JSONを再帰的に全走査し
  `key=="session.id"`のstringValueを収集。`_lock`でファイル書き込みを排他。振り分け失敗はFALLBACKへ。
- `session-start.sh`: stdinのJSONから`session_id`/`cwd`を拾い`sessions.jsonl`へ追記（500行超えたら
  直近300行へ切り詰め）。`/dev/tcp/127.0.0.1/${PORT}`への接続試行で多重起動を判定（外部コマンド
  不要）。`setsid nohup … & disown`でデタッチ起動。
- `listener.ps1` / `session-start.ps1`: 同等ロジックのPowerShell実装。

**今回のissueはこれをperlへ移植する。** 設計思想（対応表方式・session.id全走査・unrouted退避・
多重起動防止・キャッシュ）はそのまま踏襲する想定だが、以下はこのリポジトリの規約・受け入れ条件
との差分があり、そのまま持ち込まずフェーズ2で要検証。

- 参考実装は`~/.claude/settings.json`（ユーザーホーム）への設定を前提にしているが、受け入れ条件は
  「可能な限りリポジトリ内で完結」を求めている。
- 参考実装の`sessions.jsonl`は「マシン全体で1リスナーが複数ワークスペースを横断して振り分ける」
  設計（状態がリポジトリ外の共有位置にある）であり、リポジトリ内完結の方針との折り合いを検証する。
- 実装言語をPython/PowerShellからperlへ変えるため、HTTPサーバ部分（`HTTP::Daemon`不使用、
  `IO::Socket::INET`での自前HTTP/1.1最小パーサ）は移植ではなく新規設計になる。

## 全体像

### フェーズ2〈調査〉

以下7点の未決定論点を中心に、個別調査計画（`plans/【調査】〜.md`）で検証する。事前調査（本計画
時点）は見出しレベルにとどめ、深追いしない。

1. **配置場所の決定**: リスナー本体・SessionStartフック追加分・共有ライブラリを`.claude/hooks/`
   配下のどこに置くか（新設サブディレクトリ案 vs 既存`.claude/hooks/lib/`案）。
   `.claude/rules/directory-structure.md`の配置指針（`.claude/scripts/src/`は「AIエージェントが
   能動的に実行するスクリプト」の置き場であり、Claude Codeのhookが自動起動する常駐プロセスは
   これに当たらない）と照らして決める。
2. **状態の置き場所の範囲**: `sessions.jsonl`・リスナーのPID/ログを、単一ワークスペース内で
   完結させるか、複数ワークスペースを横断する共有位置（ユーザーホーム、OS一時ディレクトリ等）に
   置く必要があるか。受け入れ条件「別ワークスペースのセッションが混ざらない」「複数ワークスペースが
   同時に動く」との両立の観点で検証する。
3. **ポート決定方式**: Windows/WSLで固定2ポート（参考実装は4318/4319）のままでよいか、複数
   リポジトリ・複数実行環境を同時に開いた場合の衝突可能性を検証する。
4. **設定の適用範囲（プロジェクトスコープ vs ユーザーホーム）**: `env`/`hooks.SessionStart`設定が
   プロジェクトスコープの`.claude/settings.json`（このリポジトリ内）で完結できるか、公式仕様・
   実機確認で確定する。困難と判明した場合に必要な手順のドキュメント化方法も検討する。
5. **perlでのHTTPサーバー実装方式の実現可能性**: `IO::Socket::INET`での自前HTTP/1.1最小パーサ
   （Content-Lengthを読んでbodyを受ける程度）の方針が、git bash付属perlとWSL/Linux側perl
   （コアモジュールのみ）双方で成立するか、小さな検証コードで確認する。
6. **WSL側の実機検証可否**: 本セッションの実行環境でWSL実機検証が可能かを確認し、可能ならその場で
   最小限の疎通確認を行う。不可能な場合の代替確認方法（コードレビューベース、ユーザーへの検証依頼）
   を明記する。
7. **perlスクリプトの単体テスト方法の確立**: 既存bashの`assert_eq`/`passed=N failures=N`パターンに
   相当する枠組みをperlでどう書くか（`Test::More`等コア添付モジュールの利用可否を含む）。

加えて、以下も調査範囲に含める。

- 出力ファイルのローテーション方針・エクスポート間隔の既定値（期待する動作8）の具体案の妥当性。
- 機微情報（メールアドレス・アカウントUUID・セッションID・`OTEL_LOG_USER_PROMPTS`有効時の
  プロンプト本文）の扱いと`.gitignore`対象範囲の確定方法。
- ベストエフォート方針（受け口・フック失敗時もセッション継続）を、フックのタイムアウト設計・
  リスナー起動の非同期デタッチ方式にどう落とし込むか。

調査結果は`reports/`へまとめ、各論点の結論（採用案・却下案とその理由）を記載する。この結論が
フェーズ3の個別作業計画の前提になる。

## issue分割の要否についての判定

**結論: 分割不要。1つのissueとして進める。**

`.claude/skills/issue-mr-flow/SKILL.md`の分割提案基準は、同型の成果物が並列に列挙されている
（＝個別に独立して着手・完了できる単位に分けられる）ケースを想定している。本issueが扱う
「OTLPリスナー」「SessionStartフックの拡張」「perl移植」「テレメトリ設定（`env`/`hooks`）」は、
いずれも単独では意味を成さない一つの機構の構成要素である。SessionStartフックが記録する対応表が
無ければリスナーは振り分け先を引けず、リスナーが無ければフックが対応表を記録しても消費されず、
`env`設定が無ければClaude Code自体がOTLPを送信しない。これらは並列に分けて別々にレビュー・
マージできる単位ではなく、1つの機構として不可分に連動する横断的変更であるため、分割の基準に
当てはまらない。

なお、本issueが本来含みうる大きな論点（対応工数レポートの集計元をテレメトリへ置き換えること）は
期待する動作9で明示的にスコープ外として既に切り出されており、「issueが大きすぎる場合の分割」を
先取りして行った状態と言える。フェーズ2の調査で「状態の共有位置」等の論点がリポジトリの前提を
大きく変える規模の変更を要すると判明した場合は、2-6（調査実施時点）で改めて分割を検討する。

## 検証方法の見通し

受け入れ条件は基本的にフェーズ3の実装完了後、実機での動作確認で確かめる。

| 受け入れ条件 | 検証方法の見通し |
|---|---|
| プロンプト1回実行で`<ワークスペース>/usage/`にJSONLが生成・追記される | Windows実機でプロンプトを1回実行し、`usage/`配下のファイル生成・追記を確認 |
| 別ワークスペースのセッションが混ざらず振り分けられる | 2つのワークスペースで同時にセッションを起動し、それぞれの`usage/`に自分のセッション分のみが記録されることを確認 |
| session.idを引けなかったペイロードが失われない | `curl`等で`session.id`を含まないペイロードを直接送信し、未振り分けファイルへの出力を確認 |
| 二重起動せずセッション開始が遅延しない | リスナー起動済み状態で2つ目のセッションを起動し、プロセスが増えないこと・フック応答時間を確認 |
| Windows/WSL双方でポート・出力先を奪い合わない | 双方で同時にセッションを起動し想定通り出力されることを確認（WSL実機検証が困難な場合はフェーズ2の結果に従い代替手段） |
| 追加パッケージ無しでgit bash・WSL双方のperlで起動できる | 各環境の`perl -v`とコアモジュールのみ使用をコードレビュー＋実行確認 |
| 受け口・フック失敗時もセッションが継続する | ポートを塞ぐ・フックを一時的に壊す等でエラーを意図的に発生させ、セッション自体が継続することを確認 |
| テレメトリ出力先が`.gitignore`対象 | `git check-ignore`で新設パスが除外対象になっていることを確認 |
| 単体テストが`passed=N failures=N`を出力する | テストスクリプトを実行し出力形式を確認 |
| DDR・spec・導入手順が揃っている | フェーズ4で人間レビュー |

WSL側の実機検証可否は未確定のため、フェーズ2の結果次第で、フェーズ3・受け入れ条件確認の一部が
「コードレビューベースの確認＋ユーザーによる別途検証」に切り替わる可能性がある。この場合はその旨を
フェーズ2調査結果・フェーズ3計画の双方に明記する。
