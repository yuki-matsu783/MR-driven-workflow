1. 層分け定義ファイル .claude/dist-layers.json

  • 1エントリ＝1ルール。layer と path（git pathspec）を持ち、 必要に応じて source / strategy / keys / header / gitignorePattern を添える。
  • 後に書いたエントリが勝つ（.gitignore と同じ規約）。例外はこれだけで表せる。
  • upstream: true は本家の印。配布時に落とし、配布先では網羅性チェックをスキップさせる。

2. 網羅性チェック .claude/scripts/src/check-dist-coverage.sh

検査4種（追跡ファイル全件の分類／.gitignore の行の被覆／空振りエントリ／ layer・strategy の妥当性）。どれも件数を出す——異常が無ければ何も出ない検証にしない。

3. manifest .claude/.asset-manifest.json（配布先に置く）

本家のコミットSHA・版・URLと、ファイルごとの層・sha256（merge は指紋）を記録する。 LF正規化してから sha256 を取る（Windows の core.autocrlf=true で全件が「変更された」と誤検知されるため）。 local / exclude は書かない（書くと「配布した」と誤読される）。

4. インストーラの処理順序（install-to-project.sh）

2パス構成にする。受け入れ条件4が「上書きの前に警告と対象一覧を出す」ことを求めており、 配置しながら警告を出す1パスの形では満たせない。

  1. 引数・配布先の検証 → 定義の読み込み → dirty 判定 → 網羅性チェック
  2. 走査パス（ファイルを一切変更しない）: core を新規／変更なし／適用後に変更された／判定不能 に振り分ける
  3. 提示: 件数と警告・対象一覧を出す（--dry-run はここで終了）
  4. 配置パス → .gemini/ のセットアップ → manifest の書き出し → サマリ

個別の指示（置き換え前後）

既存ファイルへ手を入れる箇所は、置き換え前と置き換え後の形を両方書く （plans/REVIEW-POINTS.md）。「どこを何に変えるか」だけだと、置き換え対象の行が兼ねていた役割の 巻き添えを計画の段階で検出できない。

敵対的レビュー1回目で検出した漏れ .gitignore の /build/ について、対の計画は「マーカーの中に入れない」としか書いておらず 削除の指示になっていなかった。項目10へ「5〜6行目を削除する」という置き換え前後の形を明記した。

現行テストの表明の棚卸し（引き継ぐもの）

受け入れ条件に対応するケースだけで書き直すと、既存の保証が無言で失われる。 現行テストが表明していることを列挙し、新実装に対しても流して差分を見る。

  • PR/MRテンプレートの見出しが describe の生成物と一致する
  • .gitattributes の行追記が何度適用しても増えない（配布先がCRLFの場合を含む）
  • .claude/VERSION の更新が .bak と警告を生まない

新規・追加するテスト

  • 受け入れ条件1〜10の各項目に対応するケース（配布・再適用・編集済み seed・改変済み core・dirty ガード）
  • 異常を実際に検出できることのテスト（定義から意図的に1件落とした一時ツリーで落ちるか）
  • setup-gemini-links.sh のフォールバック検証（symlink も NTFS ジャンクションも作れない環境）

検証（この計画の完了判定に実際に流すコマンド）

  1. 構文チェック: 新規・変更したすべての .sh に bash -n。
  2. 定義が有効なJSONで、網羅性チェックが通ること。
  3. 網羅性チェックが「実際に検出できる」ことの確認（異常が無ければ何も出ない検証にしない）。
    2つの落とし穴 実物の dist-layers.json は書き換えない（中断すると壊れた定義が作業ツリーに残り、 dirty 判定の材料にもなる）。プローブはルート直下へ置く——.claude/ 配下だと 広域の core エントリに被覆され、「検出できないのに検証は通る」状態になる（実際に踏んだ）。
  4. 単体テスト・結合テストを規約どおり passed=N failures=N で見る。
