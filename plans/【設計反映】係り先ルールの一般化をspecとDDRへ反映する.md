# 【設計反映】係り先ルールの一般化をspecとDDRへ反映する

issue #142 / PR #188。フェーズ4〈反映〉の個別反映計画（flow-id 4-1）。

## 前提（合意状況）

- **フェーズ3〈作業〉は完了している**（flow-id 3-10 まで）。書き換えた2箇所は
  `.claude/rules/docs-workflow.md` 104〜132行と ルート `REVIEW-POINTS.md` 47〜57行。
  結果は `reports/20260823_brisk-weaving-lantern_係り先ルールの一般化.md`。
- **非対話的セッションのため、人間のレビュー往復（flow-id 4-3/4-4・4-8/4-9）は敵対的レビューで
  代替する**（ユーザーの指示）。この計画に対して1回、反映実施後に1回。
- 種別は `【設計反映】`。今回の反映先は **spec と DDR のみ**で、AIアセット（`.claude/rules/` 等）は
  フェーズ3で**主たる成果物として**書き換え済みであり、フェーズ4の反映対象ではない
  （`references/planning.md`「対象は作業の副産物に限る」）。

## AIアセット反映の対象の洗い出し（issue #155 の手順）

### 手順1: 起点の列挙

入力は `worklog/`（push1〜5）・`reports/`（調査結果・作業結果）・MRのレビューコメント（4回・
計29スレッド）の3つ。**今回の作業のうち既存のアセットで対応できなかったもの**は次の3件。

| # | 何が起きたか | 出所 |
|---|---|---|
| 1 | 発動条件を操作の分類（「構造変更全般」）で書こうとして、issue #155 の形を取りこぼしかけた | 調査 Q3・作業計画のレビュー |
| 2 | **この書き換え自身が、対象としている欠陥を作った**（既存2実例の帰属が消えた） | 書き換え結果のレビュー（2件が別方向から到達） |
| 3 | 同じ規約を A（`.claude/rules/`）と B（`REVIEW-POINTS.md`）の2箇所へ書く必要があった | 調査 Q5・書き換え結果のレビュー |

### 手順2: 4類型への分類

| # | 類型 | 根拠 |
|---|---|---|
| 1 | **反映対象ではない**（今回の主たる成果物そのもの） | 条文の書き方の問題であり、`docs-workflow.md` の書き換えで解決済み。**アセットの副産物ではない** |
| 2 | **反映対象ではない**（同上） | 一般化後の条文が扱う形そのもの。ルール側は既に「残した記述の側へ係り先を明示する」を持つ |
| 3 | **(a) 該当するアセットが無かった** → 手順3へ | 「同じ規約を2箇所へ意図的に置く」ことの是非を扱った記述が見当たらない |

**1と2をAIアセット反映の対象にしない理由**を明示する。どちらも「アセットが足りなかった」のでは
なく、**このissueが直そうとしていた当のもの**である。フェーズ3の成果物へ既に入っており、ここで
重ねて別のアセットへ書くと同じ内容が3箇所に散る。

### 手順3: 痕跡の確認（#3 について）

段階2（frontmatter検索 ＋ 本文grep）を実施した。**打ち切りの条件（両方0件）は満たさなかった**が、
ヒットした記述はいずれも**別のことを述べている**ため、(a) のまま扱う。

| 手段 | 結果 | 判定 |
|---|---|---|
| `search-frontmatter.sh --text 二重管理 --type ddr` | `matched=2` | ヒットは `i0077-02`（レビュー観点をディレクトリごとに外だしする設計）と 1件。**「同じ規約を意図的に2箇所へ置く」ことは扱っていない** |
| `search-frontmatter.sh --text 発動条件 --type ddr` | `matched=0` | — |
| `grep -rn 二重管理 .claude/docs .claude/rules` | 9件 | **すべて「二重管理を避ける」側**の記述（specへ再掲しない・手順を重複させない）。**避けずに許容した判断**の記録は無い |

**`i0077-02` は追記先にならない。** DDRは本文を変更しない運用であり、かつ同DDRが決めたのは
「観点を**どこへ置くか**（ディレクトリごとの `REVIEW-POINTS.md`）」であって、
「**規約と観点表の両方へ同じ発動条件を書くか**」ではない。

**結論: 新規DDR `i0142-01` を作る**（フェーズ2の Q4 が出した「追記先になりうる既存DDRは0件」と
同じ結論に、別の入力（今回のレビューで新たに生じた #3）からも到達した）。

### 手順4: 反映先の形態の決定

**AIアセットへの新規反映は無い**（#1・#2 は対象外、#3 は spec/ddr で扱う）。よって
`AGENTS.md` / `.claude/rules/` / `.claude/skills/` / `.claude/hooks/` のいずれも触らない。

## 反映するもの（3件）

### R-1. 新規DDR `.claude/docs/ddr/i0142-01-….md`

**記録する意思決定は3つ。** タイトルは決定の中身を表すものにする（案:
`i0142-01-係り先確認の発動条件は残置テキストの側から書き上限を付ける.md`）。

| # | 決定 | 却下案 |
|---|---|---|
| 1 | **発動条件を操作の分類ではなく、残置テキストの側から書く** | 「構造変更全般」への言い換え（**それ自体が操作の分類**であり、#155 の「同じ深さの項を1つ足しただけ」が入る保証がない）。操作を列挙して増やす案（列挙は必ず漏れる。#155 が既に4操作の外だった） |
| 2 | **上限を付ける**（残置側に依存する文があるときへ絞る） | 無条件で発動させる案（**常時発動＝実質的に無視される規約**になる）。件数・行数での閾値（意味の依存はサイズと相関しない） |
| 3 | **A（規約）と B（観点表）の両方へ同じ発動条件を置く** | Bをポインタにする案（`collect-review-points.sh` は `.claude/rules/` を集めないため**辿る動機が生まれない**）。A を廃して B 一本にする案（規約としての正が観点表へ移り、レビュー時以外に読まれなくなる） |

**#3 には残るコストを併記する。** 発動条件を変えるときは A・B 2箇所の更新が要る。これを
許容した理由（Bが敵対的レビューへの唯一の経路であること）と、**実例の固有名は A にのみ置いて
更新点を1箇所へ寄せている**ことを書く。

**書いたら `bash .claude/scripts/src/generate-ddr-list.sh` を実行し、`.claude/docs/README.md` の
差分を同じコミットへ含める**（一覧は生成物。手書きしない）。

### R-2. `.claude/docs/spec/issue-mr-workflow.md` の changelog へ `### issue #142` を追記

**追記位置は `## 未決定事項・懸念点` の直前**（既存の `### issue #155` の後ろ）。書く内容は
変更したファイルの表と、却下案はDDRへのリンクで代替する形（`### issue #155` の構成に揃える）。

**`### issue #64`（2538〜2556行）は書き換えない。** 当時の作業の point-in-time な記録であり、
2547行の「そこへ見出しを差し込むとその地の文が新節の配下に入ってしまうため、位置を変更した」は
**当時の判断の記録**である。今回の一般化で古くなったように見えても、**過去の記録として正しい**。
（`.claude/rules/docs-workflow.md`「ファイル移動に伴うパス参照の一括置換は…過去issueごとの
changelogを対象に含めない」と同じ理由。）

### R-3. `.claude/VERSION` の判断

**据え置く**（現在 `0.3.0`）。理由は `### issue #155` が記録したものと同じで、`0.3.0` はまだ
どの配布先にも渡っていないため、同じ未リリース版へ相乗りする。**changelogのエントリへ1段落で
判断を残す**（`.claude/docs/spec/distribution-assets.md`「人間の判断で据え置くことがある」）。

**上げる判断になった場合は `0.4.0` とし、その段落を書き換える。**

## この反映で自分が踏んではいけない罠

**この計画自体が、issue #142 が扱う欠陥を作りうる。** 反映作業は「既存ドキュメントへ節を差し込む」
操作そのものである。

- **R-2 の追記位置の前後を両方見る。** 追記先の直前は `### issue #155` の末尾（`.claude/VERSION`
  の判断を述べた箇条書き）で、**直後は `## 未決定事項・懸念点` という見出し**である。
  見出しの直前へ差し込むので、**後ろ方向の係り先は変わらない**。前方向は、#155 の末尾が
  **#155 自身の VERSION 判断**を述べており、新しい `###` 見出しを立てれば係り先は #155 に
  留まる（同じ深さの見出しが境界になる）。**着手前に前後3行を実際に読んで確かめる。**
- **DDR一覧（`.claude/docs/README.md`）は生成物なので手で書き足さない。**
