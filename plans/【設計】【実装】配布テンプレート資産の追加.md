# 【設計】【実装】配布テンプレート資産の追加

全体作業計画: `plans/配布テンプレート資産の整備.md`（issue #33）
前提となる調査結果: `reports/20260820_配布テンプレート資産の整備_配布経路と追加資産の調査.md`

種別を `【設計】【実装】` と併記するのは、**設計判断が調査フェーズで既に確定しており**
（配置場所・上書き方針・見出し構成のすべてが調査結果で決着している）、残るのは
「決まったものを書く」だけで、設計と実装を分けても合意の単位が変わらないため。

## 実装するもの

### 1. `.github/pull_request_template.md`

`describe` の生成物（`Closes #N` / `## Plan` / `## 実装状況`）と同一構成にする。記入ガイドは
**HTMLコメント**で入れる（`describe` が本文を全文置換しても情報を失わない形にするため）。

### 2. `.gitlab/merge_request_templates/Default.md`

1と同一内容。ファイル名を `Default.md` にするのは、GitLabがこの名前を**既定テンプレート**として
特別扱いし、MR作成時に自動で本文へ入るため（issueテンプレートで同じ理由により `Default.md` を
採用した経緯: `.claude/docs/ddr/0036-GitLab-issueテンプレートは予約名Default.mdを正とし文書側を合わせる.md`）。

**frontmatterは付けない。** `.claude/rules/markdown-frontmatter.md` の「対象外・特殊対応ファイル」が
GitLabのissueテンプレートについて「frontmatterを追加するとMR/issue本文へYAMLがそのまま挿入される」
としており、MRテンプレートも同じ理由で対象外になる。GitHub側も同様に付けない（`.github` の
issueテンプレートが対象外とされているのと揃える）。

### 3. `.gitattributes`（本家用）

```gitattributes
* text=auto
*.sh text eol=lf
```

- `* text=auto`: このリポジトリ全体の正規化方針。**配布はしない**（配布先が自分で決めるべき方針のため）。
- `*.sh text eol=lf`: 配布対象。CRLFで取り出されると `bash: $'\r': command not found` で動かない。

### 4. `.claude/VERSION`

内容は `0.1.0` の1行（末尾改行あり）。SemVer。

### 5. `sync-assets.sh` の対応

ルートファイルの列挙（`.mrworkflow.json`・`AGENTS.md`・…の6行）へ `.gitattributes` を追加する。

### 6. `install-to-project.sh` の対応

`.gitattributes` を**行追記**で配置する処理を追加する。既存の `.gitignore` 追記処理と同じ形にし、
配布先に既存の `.gitattributes` があってもその内容を保つ。追記する行は `*.sh text eol=lf` のみ。

- 配布先に `.gitattributes` が無ければ新規作成する。
- 既に同じ行があれば何もしない（**冪等**。再適用で同じ行が増えていかないこと）。

## 変更しないもの

- `.github/ISSUE_TEMPLATE/` `.gitlab/issue_templates/` の既存テンプレート。
- 配布経路のうち、PR/MRテンプレートと `.claude/VERSION` に関わる部分（調査のとおり**変更不要**で、
  既存のディレクトリ単位コピーにそのまま載る）。
- 調査で見つかった範囲外の問題（`index.jsonl`・`.claude/state/` の混入、`.gitignore` 追記行の陳腐化）。
  issue #26 の受け入れ条件が既に扱っているため直さない。

## 検証（実行するコマンドと期待結果）

1. **構文チェック**: `bash -n` を変更した2つの `.sh` に対して実行 → エラー0。
2. **既存テストの全件実行**: `for f in .claude/scripts/test/test_*.sh; do bash "$f"; done`
   → すべて `failures=0`。
3. **配布の実機確認（新規の配布先）**: 空の `git init` 済みディレクトリへ `sync-assets.sh` →
   `install-to-project.sh` を実行し、次を確認する。
   - `.github/pull_request_template.md` と `.gitlab/merge_request_templates/Default.md` が配置される
   - `.claude/VERSION` が配置され、内容が本家と一致する
   - `.gitattributes` が作られ、`*.sh text eol=lf` を含む
4. **配布の実機確認（既存の `.gitattributes` を持つ配布先）**: 配布先に
   `*.png binary` 等を書いた `.gitattributes` を置いた状態で適用し、次を確認する。
   - 既存の行が**すべて残っている**
   - 末尾に `*.sh text eol=lf` が追記されている
   - `.gitattributes.bak` が作られて**いない**（＝全文置換になっていない）
5. **冪等性の確認**: 4の直後にもう一度 `install-to-project.sh` を実行し、
   `grep -c -- '\*.sh text eol=lf' <配布先>/.gitattributes` が **1** のままであることを確認する
   （増えていたら追記処理が冪等でない）。
6. **frontmatterインデックス**: `bash .claude/scripts/src/extract-frontmatter.sh .` が正常終了する。

**検証3〜5は、異常があるときに本当に落ちる形にする。** 「エラーが出なければOK」ではなく、
`grep -c` の件数・ファイルの有無を数として突き合わせる。

## 想定される失敗

- 追記処理の判定に `grep -F '*.sh text eol=lf'` を使うと、パターンが `*` で始まるためオプションと
  誤解される可能性がある。`.claude/rules/shell-script-style.md` の「`--` を置く」規約に従い
  `grep -Fq -- '<pattern>'` と書く（同じ失敗が `-` 始まりのパターンで実際に起きている）。
- 配布先の `.gitattributes` が末尾に改行を持たない場合、単純な `>>` 追記は**前の行と連結する**。
  追記前に末尾が改行で終わっているかを確認し、必要なら改行を1つ足してから追記する。
