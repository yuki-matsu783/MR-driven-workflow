# 【調査】git addの削除済みパス挙動

- issue: [#60](https://github.com/yuki-matsu783/MR-driven-workflow/issues/60)
- 全体作業計画: `plans/cheeky-baking-lantern.md`
- flow-id: 2-1〜2-10

## 目的

`.claude/scripts/src/create-commit.sh` の `git add -- "${files[@]}"` を
`git add -A -- "${files[@]}"` へ変更してよいかを、**実機の挙動で**確定させる。特に次の2点は
コードを読むだけでは判断できないため、必ず実測する。

1. `-A` を付けたときの**巻き込み範囲**（pathspecに含めていない場所の変更が入らないか）
2. `.` のような「実質的にリポジトリ全体を指す pathspec」を渡された場合に、`-A` の有無で差が出るか
   （差が出るなら、issueの受け入れ条件「無制限のステージングは引き続き構造的に不可能」を満たすため、
   ラッパー側にガードが必要になる）

## 前提・環境

- git version 2.39.2.windows.1（git bash / MSYS）
- 検証は**このリポジトリの外**（scratchpad配下の一時リポジトリ）で行い、本体のワーキングツリーを汚さない
- 検証スクリプトは一時ディレクトリに置き、リポジトリにはコミットしない（結果のみ worklog・reports へ残す）

## 調査項目

| # | 項目 | 確認したいこと | 期待/判断基準 |
|---|---|---|---|
| 1 | 現行実装の失敗再現 | 削除済みの追跡対象パスを `git add -- <path>` に渡したときの終了コードとメッセージ | issue記載どおり `fatal: pathspec ... did not match any files` / 128 で落ちること。落ちない場合は前提（issueの現状認識）自体を再検討する |
| 2 | `-A` での混在ステージ | `git add -A -- <削除済み> <変更済み> <新規>` を1回で実行 | 3種すべてが `git diff --cached` に載ること（受け入れ条件そのもの） |
| 3 | `-A` のスコープ | pathspecに含めない別ディレクトリに変更・新規・削除を用意した状態で #2 を実行 | 含めていない変更が**一切ステージされない**こと。ここが崩れると `-A` 案は採用できない |
| 4 | サブディレクトリからの実行 | リポジトリのサブディレクトリをカレントにして `git add -A -- <相対パス>` を実行 | git 2.0で変わった「カレント配下 vs リポジトリ全体」の差が、pathspec併用時に影響しないことを確認する |
| 5 | ディレクトリ指定時の差 | `git add -- dir/` と `git add -A -- dir/` を比較 | 差分は「dir/配下の削除もステージされる」ことだけであること |
| 6 | 全体を指す pathspec | `git add -- .` と `git add -A -- .`、および `:/` を比較 | `-A` で巻き込み範囲が広がるか。広がる場合、ガード（`.` `./` `:/` 等の拒否）を実装するかを判断する |
| 7 | 存在しないパス | 追跡もされておらず存在もしないパスを `-A` 付きで渡す | 従来どおりエラーになること（タイプミスが黙って無視されない） |
| 8 | 代替案の比較 | 「渡されたパスの存在有無で `git add` / `git rm` に振り分ける」案の実装量・失敗モード | 実装行数と、`git rm` が失敗する条件（未追跡ファイルを渡した場合等）を整理し、却下理由を書けるようにする |

## 調査結果

検証環境: git version 2.39.2.windows.1（git bash / MSYS, bash 5.2.12）。scratchpad配下に一時
リポジトリを4本作り、計36ケースを実測した（検証スクリプトはリポジトリに含めない）。
視覚的なまとめ: `reports/20260819_cheeky-baking-lantern_git-addの削除済みパス挙動.html`

### 結論

1. **issue本文の前提が再現しない。** 追跡済みファイルを削除しただけのパスは、
   `git add -- <path>` に渡して **rc=0 で成功**し、削除（`D`）がステージされる。
   ディレクトリごと消えた `reports/` をディレクトリ指定で渡しても成功する。
2. **`-A` は症状を直さない。** 失敗する3ケースはいずれも `-A` を付けても同じく rc=128 で失敗し、
   成功するケースは `-A` なしでも成功する。ディレクトリ指定時の差も観測されなかった。
3. **真の失敗条件は「ワーキングツリーにも index にもエントリが無いパス」**。判定は「ファイルが
   存在するか」ではなく「index にエントリがあるか」。該当するのは次の3つ。
   - (a) `git rm` 等で**削除を先にステージ済み**のパスを再度渡した場合
     ← issueが「回避策」と呼ぶ2段構えの手順そのものが、この失敗を生んでいる（本命）
   - (b) 一度もコミットされないまま作って消したファイル
   - (c) 綴り誤り、および `git status` の8進エスケープ表記（`plans/\343\200\220...`）をそのまま渡した場合
4. **`-A` には副作用がある。** 引数が空のとき `git add --` は "Nothing specified, nothing added."
   で何もしないが、`git add -A --` は**リポジトリ全体をステージする**。`-A` を入れると、
   受け入れ条件「無制限のステージングは構造的に不可能」の担保が引数バリデーション1枚だけになる。

### 項目別の実測

| # | 項目 | 結果 |
|---|---|---|
| 1 | 現行実装の失敗再現 | **再現せず**。`git add -- <追跡済み削除>` は rc=0 で `D` をステージ |
| 2 | `-A` での混在ステージ | rc=0。削除＋変更＋新規の3種が1回で載る（`-A` なしでも同結果） |
| 3 | `-A` のスコープ | pathspec 外（`other/`）の変更・新規・削除は一切ステージされない。issueの前提どおり限定される |
| 4 | サブディレクトリからの実行 | 相対パス（`../target/...`）で rc=0。リポジトリルート基準の表示で正しくステージ |
| 5 | ディレクトリ指定時の差 | `git add -- dir/` と `git add -A -- dir/` の結果は**同一**（削除も拾う） |
| 6 | 全体を指す pathspec | `.` `:/` はどちらも `-A` の有無で結果が同じ。**ただし pathspec 自体が空の場合のみ** `-A` で全体がステージされる |
| 7 | 存在しないパス | `-A` の有無にかかわらず rc=128 `fatal: pathspec ... did not match any files`。タイプミス検知は維持される |
| 8 | 代替案（`git rm` 併用）の失敗モード | `git rm -- <変更済みで存在する>` は rc=1（local modifications）、`git rm --cached -- <未追跡>` は rc=128。振り分け実装は失敗モードが増える |

補足: Windows形式の区切り（`plans\...`）・`./` 付き・絶対パスはいずれも正しくマッチする
（パス表記の揺れは失敗要因ではない）。`.gitignore` 対象を明示指定した場合は rc=1（ignored 警告）。

### 採用する方針（フェーズ3へ）

`-A` は採用せず、**渡されたパスを3分類してから `git add` する**。

| 分類 | 条件 | 扱い |
|---|---|---|
| ADD | worktree に存在する、または index にエントリがある | `git add -- <ADD>` に渡す（通常変更・新規・追跡済みの削除） |
| SKIP | worktree にも index にも無いが HEAD にはある | 既に削除がステージ済み。**冪等にスキップして成功させる** |
| UNKNOWN | どこにも無い | 想定原因が分かる文言でエラー終了（タイプミス検知を維持） |

- 外部コマンドは `git ls-files -z` と `git ls-tree -r -z --name-only HEAD` の**2回のみ**
  （ループ内 fork なし。`shell-script-style.md`「外部プロセス起動のコスト」に適合）。
  どちらも日本語パスを8進エスケープせず出力することを確認済み
- **ADD が空のときに `git add -- "${add[@]}"` を実行しないガードが必須**（空 pathspec の危険性は
  `-A` を入れない限り実害が無いが、将来 `-A` を足された場合に備えて構造的に守る）
- `.` / `:/` を拒否するガードは**不要**と判断（`-A` を入れないため巻き込み範囲が現行と変わらない）

### レビューで合意が必要な点

issueの「期待する動作」に書かれた実装案（`git add -A`）を**採用しない**結論になっている。
受け入れ条件そのものは満たせる（上記の対応表）が、実装方針が issue 本文と異なるため、
フェーズ3に進む前に合意を取る。
