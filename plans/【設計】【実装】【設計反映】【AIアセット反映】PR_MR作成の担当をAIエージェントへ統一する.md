# 【設計】【実装】【設計反映】【AIアセット反映】PR/MR作成の担当をAIエージェントへ統一する

対象: issue #41 「PR/MR作成はAIエージェントが実施してよいものとし、マージのみ明示指示必須に統一する」

## 背景（issueの要約）

`.claude/skills/issue-mr-flow/SKILL.md` の flow-id 1-3（担当: `start`＝エージェント）と
`.claude/rules/git-workflow.md`「PR・マージ」節（「PR作成・レビュー依頼・マージは人間が実施する」）が
**同じ操作について逆のことを言っている**。実運用でも揺れており（issue #22ではDraft PR #30を自ら作成、
issue #34ではPRを作らずpushで停止し後から明示指示でPR #40を作成）、フローの再現性が損なわれている。

## 種別を併記する理由

本タスクの成果物は**AIアセット（ルール・スキル定義）とドキュメント（DDR・spec）のみ**であり、
「実装」＝AIアセットの書き換えそのものである。設計・実装・設計反映・AIアセット反映を分けても
同じファイル群を触ることになり、合意を分ける意味が無いため1つの計画に併記する。

## 方針（設計）

担当の切り分けを次の1行に統一する。

> **PR/MRの作成・更新はAIエージェントが実施してよい。マージのみユーザーの明示指示を必須とする。**

判断の根拠は「**取り消せるか**」で切る。PR/MRの作成・Draft解除・description更新は、Draftへ戻す・
クローズする・本文を書き直すことでいつでも取り消せる（mainは1バイトも変わらない）。一方マージは
mainの正史を書き換える不可逆な操作であり、squash mergeでは元のコミット粒度も失われる。

### ハーネス側が「明示指示が無ければPRを作成しない」と指示する環境の扱い

**ハーネス側の指示を優先する。** リポジトリ内のドキュメントでハーネスのシステムプロンプトを
上書きすることはできないため（リポジトリ方針を優先させると、衝突の解釈をAIが都度行うことになり、
issue #41が問題にした「セッションごとに判断が変わる」状態に逆戻りする）。

ただし**振る舞いは決め打ちにして再現性を確保する**。そのような環境では flow-id 1-3 を次の形で行う。

1. ブランチ作成とリモートへの反映までは通常どおり行う。
2. Draft PR/MR作成の可否を `AskUserQuestion` で1回だけ確認する。
3. 応答を待てない非対話的セッションでは、PRを作成せずに止め、**「PR未作成であること」「作成には
   明示指示が必要なこと」を最終応答へ明示する**（黙ってpushだけして終わらない）。
