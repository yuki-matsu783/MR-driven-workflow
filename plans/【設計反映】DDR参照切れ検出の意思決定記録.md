# 【設計反映】DDR参照切れ検出の意思決定記録（issue #171）

## 前提（合意状況）

- 上位の計画: `plans/sequential-purring-tulip.md`（全体作業計画、flow-id 1-5で合意）。
  「フェーズ4〈反映〉」節で「検出の仕組みに関する意思決定をDDRとして記録し、
  `generate-ddr-list.sh`でREADMEの一覧を再生成する」ことが既定路線として合意済み。
- 直前の実装結果: issue #171・PR #177のコミット履歴（`e7d5dd1`・`e51da6f`）。詳細な経緯は
  マージ後に削除される`reports/`ではなく、本計画とこれから書くDDR本文へ要約して残す
  （**v2で修正**: 当初「詳細はworklog参照」としていたが、`worklog/`はflow-id 5-4で削除され
  squash mergeによりmainへ残らないため、恒久記録であるDDRから参照してはいけない対象だった。
  `.claude/rules/docs-workflow.md`「恒久的な参照先はissue番号と`.claude/docs/spec/`
  `.claude/docs/ddr/`のみ」に反する誤りであり、本issueが修正しようとしている参照切れと
  同種の欠陥を計画自身が作っていたため訂正した）。
- **v2での主な訂正点**（フェーズ4個別反映計画への敵対的レビュー12件対応。詳細は
  worklog「反映計画（flow-id 4-1）への敵対的レビュー対応」節）:
  - 「手動実行のみ」の決定主体を全体作業計画からフェーズ3個別作業計画へ訂正（下記）
  - worklog参照の削除（上記）
  - 新規specファイルを作らない判断 → **作る判断**へ変更（下記「この計画で何をするか」3）
  - ロケール依存の罠・grep一括抽出の性能実測を、DDR止まりにせず
    `.claude/rules/shell-script-style.md`へ反映する作業を、別ファイル
    `plans/【AIアセット反映】DDR参照切れ検出運用のルール・VERSION反映.md`として分離
  - DDR本文に書く内容から、レポートの誤記訂正履歴（「当初3つと誤記」等）を除外し、
    最終的な判断のみを書く方針へ変更
  - 検証節へ`check-doc-references.sh`自身によるDDR自己参照の検証を追加

## この計画で何をするか

1. issue #171で行った意思決定（対象範囲の限定・検出方式・実装が2回の敵対的レビューを経て
   変遷した経緯）を1件のDDRとして記録する。
2. `bash .claude/scripts/src/generate-ddr-list.sh`を実行し、`.claude/docs/README.md`の
   DDR一覧を再生成する。
3. **新規spec `.claude/docs/spec/check-doc-references.md`を作成する**（**v2で訂正**:
   個別作業計画（flow-id 3-1）は「規模の小さいスクリプトであり本計画＋テストコード＋
   フェーズ4のDDRで十分」としていたが、その前提にしていた「本計画」自体もflow-id 5-4で
   削除されmainに残らないため、マージ後に残るのはテストコードとDDRだけになる。DDRは
   「〇〇を決めた」という意思決定記録であって「現在の正史（呼び出し方・実行タイミング等の
   運用手順）」ではなく、後者の役割は`.claude/docs/spec/`が担う
   （`.claude/rules/docs-workflow.md`のライフサイクル表）。手動実行のみという運用が
   恒久ドキュメントのどこにも書かれない状態を避けるため、小規模でよいので新設する）。
4. **AIアセット反映（ルール追記・`.claude/VERSION`増分提案）は本計画に含めない**。
   `【設計反映】`と評価軸が異なるため、別ファイル
   `plans/【AIアセット反映】DDR参照切れ検出運用のルール・VERSION反映.md`として分ける
   （`.claude/skills/issue-mr-flow/SKILL.md`「種別を複数併記する場合／分ける場合」、
   `plans/REVIEW-POINTS.md`）。

## 変更対象

- `.claude/docs/ddr/i0171-01-<タイトル>.md`（新規DDR）
- `.claude/docs/README.md`（`generate-ddr-list.sh`による自動再生成）
- `.claude/docs/spec/check-doc-references.md`（新規spec。上記3参照）

## 方針

### DDRに記録する内容

1. **対象範囲を「DDRファイルパスへの絶対パス参照」に限定した判断**（個別調査計画
   （flow-id 2-1で作成、flow-id 2-6の調査で確定）・個別作業計画（flow-id 3-1）の両方で
   踏襲）とその理由:
   - 裸の識別子表記（`i0159-01`等）は規約説明の例示として頻出し誤検知源になるため対象外
   - 相対パス表記（`../docs/ddr/…`、`ddr/…`）は今回のスコープ外（`reports/`のflow-id 2-6
     調査結果によれば5件が候補。うち相対パス全体の母数は別途フェーズ2調査で確認した約79件
     ―根拠は`reports/20260823_sequential-purring-tulip_DDR参照切れの網羅調査結果.md`
     「相対パス参照」節の走査結果―であり、今回はいずれも未検査のまま残る。将来の課題として
     DDRに明記するが、追跡先となる新規issueは本計画では起票しない
     （下記「やらないこと」参照。理由も明記する）
   - 旧形式（4桁連番、`i`接頭辞なし）は本リポジトリに現存しないため対象外（配布先で必要に
     なった場合の拡張余地として記録）
2. **検出方式の実装が2回の敵対的レビューを経て変遷した経緯**（設計判断そのものが変わった
   点を中心に記録する。バグ修正の経過そのものではなく、**最終的にどの方式を採用し、なぜか**
   を書く。修正前の値の誤記履歴（例:「除外ディレクトリは当初3つと誤記していた」）は
   reportsの改訂履歴であり、DDRには含めない）:
   - 対象ディレクトリからの除外は`.claude/scripts/test/` `plans/` `reports/` `worklog/`の
     4つとする（テストフィクスチャの誤検知回避、および恒久ドキュメントから寿命の短い
     ファイルへの参照を防ぐため）
   - フェンス除外は「行番号の集合を求め、走査側（grep）が返す元の行番号と突き合わせる」
     方式を採用する（行削除による2パス処理は報告行番号がずれるため不採用）
   - フェンス判定は「開始行と同じマーカー種別・同じ長さ以上でのみ閉じる」方式を採用する
     （単純な出現回数トグルは、種別の異なるフェンス風行が挟まると偶数回トグルになり
     参照切れを無言で見逃す偽陰性を生むため不採用）
   - 全角句読点等による連結への対策は、**正規表現の文字クラスへ直接追加しない**。抽出後の
     文字列をASCII構造（`.claude/docs/ddr/`という固定プレフィックスの再出現位置）だけで
     分割する後処理方式を採用する。**この実行環境（`LANG`未設定のPOSIXロケール）では、
     POSIX ERE のブラケット式へ多バイト文字を含めるとgrep・bashの正規表現マッチングの
     いずれもリポジトリ全体に対して0件しかヒットしなくなる致命的な罠がある**ことを実機で
     発見したため（**他プロジェクトへの配布時にも再現しうる罠として重要**。詳細な追記は
     `plans/【AIアセット反映】DDR参照切れ検出運用のルール・VERSION反映.md`参照）。
   - 候補抽出はbash単独ループではなくgrep一括抽出を採用する（実測でリポジトリ全体
     約37,000行の走査時間が5.2秒→0.96秒に短縮したため。外部プロセス起動コストの規約
     `.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」が原則とする
     「ループ内で外部コマンドを呼ばない」から見ると一見逆行するが、grepを1回だけ呼び
     ループ自体を無くす設計であるため規約とは矛盾しない。この整理も上記ルール追記の
     対象とする）
3. **実行タイミングを手動実行のみとし、hook等への自動組み込みを行わない判断**は、
   **フェーズ3の個別作業計画（flow-id 3-1で作成、敵対的レビュー対応のv2で確定）で
   決定した**（**v2で訂正**: 当初「全体作業計画で決定済み」としていたが、全体作業計画
   （flow-id 1-4）が決めていたのは「hookへ組み込まない」ことだけで、実行タイミングの
   具体案自体は「フェーズ2の成果物として決定し、ここでは決めない」と明示的に留保
   していた〈`plans/sequential-purring-tulip.md`111-117行〉。個別作業計画側でもこの
   留保が一度reportsに引き継がれず帰属を誤ったため、v2で個別作業計画自身の決定として
   確定させた）。理由は`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」に
   照らし、頻度の低い整合性チェックをhookへ組み込む価値は無いという判断。
4. **新規spec`.claude/docs/spec/check-doc-references.md`を作る判断**（**v2で訂正**:
   上記「この計画で何をするか」3参照）とその理由。

### 却下案

- 検出の仕組みを作らず目視確認のみで済ませる案（全体作業計画（flow-id 1-4作成・1-5合意）で
  却下済み、DDRにも記録する）。
- 正規表現の文字クラスへ全角句読点を直接追加する案（フェーズ3の実装（flow-id 3-6）に対する
  2回目の敵対的レビュー対応で、ロケール依存の破綻を実機で発見し却下。代替のASCII構造による
  後処理方式を採用）。
- 新規specファイルを作らない案（個別作業計画（flow-id 3-1）で一度採用したが、フェーズ4
  個別反映計画への敵対的レビューで指摘を受けv2で却下。上記「この計画で何をするか」3参照）。

## やらないこと（スコープ外）

- 相対パス表記への対応拡張（DDRに将来課題として記録するのみで、今回は実装しない。**追跡先の
  新規issueは本計画では起票しない**。非対話セッションでは重複チェック・最終確認
  〈`.claude/skills/issue-create/SKILL.md`〉に必要な人間との対話が成立しないため。
  代わりに最終統括レポート（flow-id 5-3）と関連issue通知（flow-id 5-2）で、この残件を
  明示し起票の要否を人間の判断に委ねる）。
- 検出スクリプトのhook・CI等への自動組み込み。
- git bash実機での動作確認（個別作業計画で見送りと決定済み。DDRにも実施していない事実として
  記録する）。
- `.claude/VERSION`の増分提案（`plans/【AIアセット反映】DDR参照切れ検出運用のルール・
  VERSION反映.md`で扱う）。

## 検証（この反映が完了したと言える条件）

```bash
bash .claude/scripts/src/check-doc-references.sh
bash .claude/scripts/src/generate-ddr-list.sh --check
git diff --stat "$(git merge-base origin/main HEAD)" -- .claude/docs/
head -8 .claude/docs/ddr/i0171-01-*.md
```

- 新規DDR（`i0171-01-*.md`）が`.claude/rules/markdown-frontmatter.md`のDDR識別子・
  frontmatter規約（`type: ddr`、`title`は`i0171-01. <タイトル>`形式）に沿って作成されている
  ことを、frontmatterの先頭8行の目視（`head -8`）で確認する。
- `check-doc-references.sh`を新規DDR自身を含むリポジトリ全体に対して実行し、参照切れ0件・
  候補数が0件でないこと（0件だと「正規表現が当たっていないだけ」の可能性を排除できない）を
  確認する。issue #171自身が防ごうとしている参照切れを、その成果物であるDDRが新たに
  作っていないことの検証を兼ねる。
- `generate-ddr-list.sh --check`が終了コード0（再生成しても差分が無い＝手動実行を忘れて
  いない）であることを確認する。**手動実行を忘れた場合は終了コード2が返るため、そのときは
  `--print`無しで再実行し反映してから、もう一度`--check`を通す。**
- `git diff --stat <ブランチ分岐点> -- .claude/docs/`で、新規DDR・新規specの追加行数が
  意図どおりであることを確認する（分岐点固定は`REVIEW-POINTS.md`「ブランチ分岐点との差分」
  参照。作業ツリー比較ではなく`main`マージ後も有効な基準にする）。
