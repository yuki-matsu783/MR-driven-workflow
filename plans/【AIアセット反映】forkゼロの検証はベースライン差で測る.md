## なぜ反映するか（今回実際に起きたこと）

`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」節は、**起動を減らせ**とは書いて
いるが、**減らせたことをどう確かめるか**は書いていない。そのため今回、以下の誤りに実際に陥りかけた。

- `split_remote_url` は外部コマンド・コマンド置換・パイプを一切含まない。設計上forkはゼロのはず。
- ところが20回ループでの計測が **177ms** と出た。1回あたり約9ms。「どこかで見落としたforkがある
  のでは」と疑い、実装を疑う方向へ調査を進めかけた。
- 実際には `$(seq 20)` と時刻取得の `date` 自体のfork、および20回という試行回数の少なさによる
  ノイズだった。**空関数を基準にした200回計測**で切り分けたところ次のとおりで、両関数とも
  外部プロセスを起動していないことが数字で確認できた。

  | 計測対象（200回） | 所要 | 空関数との差 |
  |---|---|---|
  | 空関数 `noop` | 80ms | — |
  | `split_remote_url` | 93ms | +13ms（0.065ms/回） |
  | `provider_from_remote_url` | 132ms | +52ms（0.26ms/回） |

  同条件で `jq -nc '1'` は1回あたり138ms。**両関数はその1/500以下**。

計測の枠組み自体（ループとタイマー）が数十msを持ち込むため、「ゼロであるはずのもの」を素朴に
測ると必ず正の値が出る。**その値をそのまま関数のコストと読むと、存在しないforkを探し始める。**

この知見はプロジェクト固有ではなく、git bashでプロセス起動コストを扱う限り繰り返し必要になるため、
worklog（PR作成前に削除される）ではなくルールへ残す。

## 追記する内容

同節の**末尾**（`- **どうしても起動回数を減らせない場合は…（キャッシュ）を検討する。**` の後ろ）へ、
既存の箇条書きと同じ書式（`- **要点。**（issue #NNで実際に踏んだ）… + コード例`）で追加する。

書く要点は次の3つに絞る。

1. **「forkがゼロであること」を計測で確かめるときは、必ず空関数をベースラインに取り、その差で見る。**
   ループ構文・時刻取得自体が数十msを持ち込むため、素朴な計測では常に正の値が出る。
2. **試行回数を十分に取る**（今回は20回では判別できず、200回で差が見えた）。1回あたりの差が
   0.1ms前後なのに対し、ベースラインのゆらぎが数msあるため。
3. **比較の基準として、同条件での外部コマンド1回の実測値（例: `jq -nc '1'`）を併記する。**
   「差が基準の1/500」という形にすれば、絶対値のブレに影響されずに結論が出せる。

コード例は次の骨子で書く（`seq`・`date` をループの外に出し、空関数と対象を同じ形で測る）。

```bash
noop() { :; }
bench() { # $1=回数 $2=関数名
  local s e i
  printf -v s '%(%s)T' -1   # 実際はミリ秒が要るため date +%s%3N 等を使う
  for ((i=0; i<$1; i++)); do "$2" 'https://github.com/o/r.git'; done
  ...
}
# 空関数との差で見る。差が jq 1回分の数百分の一なら fork していない
```

**実際に書く例では、計測部分の `date` 呼び出しがループの外に1回ずつだけ現れる形にする**
（ループ内に置くと計測対象よりノイズの方が大きくなり、まさに今回の失敗が再現する）。
