方針

問い1: 案(b)の成立条件と、(a)(c)の却下理由の裏取り

案の選定はやり直さない（flow-id 2-4 でユーザーが案(b)を選択済み）。案(a)(b)(c) の定義は 上位計画が持つ。この調査で確かめるのは次の2点である。

(i) 案(b)が成立する条件

確認することなぜ
flow-id 5-4 の push を CI がどのトリガで捉えるかホストが始まる契機を特定するため
flow-id 5-5（reports/ 削除）の push が、既にホストされた内容を壊さないか 案(b)の成否を分ける最大の点。同じデプロイ先を上書きする構成だと、通知する前に消える
flow-id 5-6 でURLをどう取得するか 通知するのはこのステップであり、5-4 の結果を後から引くことになる
CIが無い／失敗する環境で、フローが止まらないか 配布先の大半はCIを持たない。upload_attachment と同じく失敗は正常系にできるか
デプロイ完了を待つ必要があるか・待つならどれだけか 5-4 と 5-6 の間に人間の操作は挟まらないため、待ち時間がそのままフローの遅延になる

(ii) (a)(c) を却下した理由の裏取り
DDR（i0114-01）へ却下案として残すため、推測のまま却下理由にしない。「不変パスにすると デプロイが何個溜まるか」「5-6 から過去SHAを指定してCIを起こせるか」を実際の仕様で確かめる。

(iii) plans/ のHTMLビューをホスト対象に含めるか
plans/ も reports/ と同じく flow-id 5-5 で削除される。含めると対象が増えて デプロイ時間とデプロイ物のサイズが増える一方、レビュー時に計画も同じURLから辿れる。結論を必ず書く。

問い2: GitHub の手段

第一候補は GitHub Pages ＋ Actions。確認項目は上位計画の問い2が持つ（並列プレビューの表現・ デプロイ完了の待ち方とURL取得・fork PRでの GITHUB_TOKEN・Pages 有効化操作・可視性設定との 一致）。却下候補の一覧も同様に上位計画が持つ。

この計画が足すのは、確認の順序だけである。 「可視性設定との一致」を最初に確かめる （ここで満たせない手段は、他の条件を調べる価値が無いため）。

問い3: GitLab の手段

CI/CD Review Apps（動的環境）。確認項目は上位計画の問い3が持つ（CI記法・ホストの実体・Runner 構築手順・URL取得・可視性設定との一致）。

この計画が足すのは、ホストの実体を先に決めることである。 「GitLab Pages」か「Runner 上の 静的サーバ」かで、可視性の扱いも Runner の構成も変わる。後者はGitLabのアクセス制御の外に 出るため、private プロジェクトで受け入れ条件を破りうる。

問い4: 配布物としての扱い

前提は上位計画の問い4が持つ（sync-assets.sh が .github/ を丸ごと配布資産へ集めており、 何もしなければ配布対象に載る）。この計画では次の順で確かめる。

  1. .claude/docs/spec/distribution-assets.md を読み、既存の配布経路 （.gitattributes の dist:begin〜dist:end 方式）が何を解決しているかを把握する
  2. 「含めない」と決めた場合の除外位置（sync-assets.sh の .github/ コピー箇所か、 install-to-project.sh の safe_copy_dir 箇所か）を特定する
  3. 「含める」と決めた場合、配布先の既存ワークフローを .bak 退避で上書きする現在の挙動が 許容できるかを判断する

進め方

  1. 一次情報（GitHub Docs / GitLab Docs）を読み、問い2・問い3の必要条件を確定する
  2. リポジトリ内の既存資産（Provider.sh の upload_attachment、 distribution-assets.md、gitlab-verification-environment.md、 sync-assets.sh / install-to-project.sh）を読む
  3. 問い1の (i)(ii)(iii) を確かめる
  4. 結果を reports/ のmd（正文）とHTMLへ書く。worklog には試行錯誤を随時書き足す
