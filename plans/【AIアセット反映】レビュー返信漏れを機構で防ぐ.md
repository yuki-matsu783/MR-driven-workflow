# 【AIアセット反映】レビュー返信漏れを機構で防ぐ

対象: issue #70 / PR #157 / flow-id 4-1
ユーザー指示（チャット・2026-08-23）: 「返信漏れがないようにAIアセットを修正すること」

## 何が起きたか（事実）

フェーズ2の敵対的レビューが **PR #157 へ10件のスレッドを投稿**した（HANDOFF「やったこと」に
記録あり）。flow-id 2-9 で **21件すべての内容をレポートへ反映**し、flow-id 2-8 で人間の合意を得て
**`mark-done` でループを閉じた**。

**しかし、10スレッドのいずれにも返信が付いていなかった。** 発覚したのは、フェーズ3の
`comments` 取得時（2026-08-23）である。約1日、10件が「未対応と区別が付かない」状態で残った。

## なぜ既存のルールで防げなかったか（原因の分解）

ルール自体は存在した。`.claude/skills/issue-mr-flow/SKILL.md`「レビュー完了合図の確認」節の
**(2) 返信が1件も付いていないスレッドが残っていないか**（issue #109）が、まさにこの事故を
名指しで禁じている。それでも起きた。原因は4つある。

| # | 原因 | 種類 |
|---|---|---|
| 1 | **`comments` サブコマンドを実行しなかった。** 指摘の内容が会話のコンテキストに残っていたため、スレッドを取得せずに直接レポートを直せてしまった | 手順の飛ばし |
| 2 | **「レビュー完了合図の確認」を実行しなかった。** 節が全体フロー表から離れた位置にあり、`mark-done` の前提として結び付いていない | 手順の飛ばし |
| 3 | **投稿したスレッドの存在が、会話にしか無かった。** `adversarial-review` の手順8は件数の報告を求めるが、**返信が未了であることをどこにも残さない**。投稿と返信の間に人間のレビューを挟む設計（issue #109）なので、その間にセッションが切れれば情報ごと消える | **記録の欠落** |
| 4 | **HANDOFF が「反映した」と書けてしまう。** 義務は〈修正〉と〈返信〉の2つなのに、記録は片方しか追わない。「21件すべてを反映した」は事実だが、返信ゼロと両立する | **記録の粒度** |

**1・2は「守らなかった」だが、3・4は「守れる形になっていなかった」である。** ルールの文言を
強めても1・2は再発しうるので、**3・4を機構で塞ぐ**ことを主眼に置く。

## この計画で決めないこと（スコープ外）

- **未返信スレッドを取得するスクリプトの新設**。この実行環境は `gh`/`glab` CLI が無く
  `Provider.sh` のCLI経路が使えないため、スクリプトを書いても MCP 経路では動かない。
  取得はAIエージェントがMCPツールで行い、**結果の記録と検査だけを機構化する**。
- 敵対的レビューの回数上限・観点表の内容（別の関心事）。
- issue #109 の判断（返信を省略してよい類型を作らない）そのものの見直し。**維持する。**

## 案の比較

| 案 | 内容 | 採否 |
|---|---|---|
| **A** | `HANDOFF.md` のヘッダへ `- 未返信スレッド:` を新設し、投稿時に件数を書き、`mark-done` がループ範囲に対して呼ばれたとき **0件でなければ拒否する** | **採用** |
| B | SKILL.md の文言強化のみ（「ループを閉じる前に必ず確認する」を太字で再掲する等） | 不採用 |
| C | 未返信スレッドを列挙するスクリプトを新設する | 不採用（上記スコープ外） |

**Bを採らない理由**: 原因3・4（記録の欠落・粒度）が残る。**文言はすでに十分強い**——
「次のステップへ進んでよいのは (1) と (2) の両方を満たしたときだけである。どちらか一方だけを
確認して離脱しない。」と書いてあってなお起きた。同じ種類の対策を重ねても効果が薄い。

**Aを採る理由**: このリポジトリは「ドキュメント上のルールだけでなく、技術的にも強制する」
という方針を持ち（`.claude/rules/git-workflow.md`「コミット運用」のhook）、
`update-handoff-progress.sh` は既に **「ループ範囲の一部だけを完了扱いにできない」**という制約を
機械的に強制している（`.claude/docs/spec/update-handoff-progress.md`）。**同じ場所へ同じ形で足せる。**

**Aの限界を明記しておく**: 値を書くのはAI自身なので、嘘を書けば通る。これは
`block-direct-git-commit.sh` と同じ位置づけ——**敵対的な安全境界ではなく、既定動作を確実な方向へ
倒す仕組み**である。効くのは「うっかり飛ばす」に対してであり、今回の事故はまさにそれだった。

## 変更内容（5件）

### 1. `.claude/scripts/src/update-handoff-progress.sh`

- `set-header` に `--unreplied <n>` を追加し、`- 未返信スレッド:` 行を書き換える。
- **`mark-done` がループ範囲（`LOOP_RANGES`）に対して呼ばれたとき、`- 未返信スレッド:` が
  `0` 以外なら非0で終了し、1件も書き換えない**（既存の「記号が揃わない指定を拒否する」と
  同じ作法）。エラーメッセージに「`comments all` で再取得し、返信ゼロのスレッドへ `reply`
  してから `set-header --unreplied 0` を実行する」と手順を出す。
- **単発ステップへの `mark-done` は対象外**（ループ範囲だけを見る）。
- **行が存在しない場合の扱い**: `set-header` の既存仕様（ちょうど1件見つからなければ失敗）に
  合わせ、`mark-done` 側は**行が無ければ「未確認」とみなして拒否**する。雛形へ足す（下記4）ので
  新規タスクでは必ず存在し、既存の `HANDOFF.md` は1回だけ手で足せば済む。

### 2. `.claude/skills/adversarial-review/SKILL.md`

手順8（結果を報告する）へ、**投稿直後の記録**を義務として追加する。

- 投稿したスレッド数を `set-header --unreplied <n>` で `HANDOFF.md` へ書く。
- 投稿したスレッドのURL一覧を「やったこと」へ残す（会話が失われても辿れるように）。
- **理由を明記する**: 本スキルは投稿までを担い返信は担わないため、**投稿と返信の間に必ず
  人間のレビューを挟む**。その間にセッションが切れると、返信すべき対象が失われる。

### 3. `.claude/skills/issue-mr-flow/SKILL.md`

- `comments` サブコマンドの**手順2の直後**に、「取得したスレッドのうち**コメントが1件だけ
  （＝返信ゼロ）のものを先に一覧で出す**。これがこのループで返信すべき最小の集合である」を追加する。
  現在の手順4は「敵対的レビューのスレッドも同列に扱う」と方針を述べるだけで、**対象の列挙を
  求めていない**。
- 「レビュー完了合図の確認」節へ、**確認後に `set-header --unreplied 0` を実行する**ことを追加する。
- 全体フロー表のループ範囲の行（2-4/2-9/3-4/3-9/4-4/4-9）から、この節への参照を貼る。
  現在この節は表から離れており、表だけを見て進むと存在に気づかない。

### 4. `.claude/scripts/src/cleanup-task.sh`

`HANDOFF.md` の雛形ヘッダへ `- 未返信スレッド: 0` を追加する（既存6行の後ろ、`- 追従監視:` の
直前か直後）。**位置は `.claude/docs/spec/update-handoff-progress.md`「HANDOFF.mdのヘッダ行」が
正なので、そちらと合わせる。**

### 5. `.claude/rules/docs-workflow.md`

ループ範囲を `[x]` にする条件へ「**未返信スレッドが0件であること**」を追加する。現在は
「1周（レビュー往復1回）が完全に完了して初めて `[x]` にする」とだけ書かれており、
**何をもって完了とするかが書かれていない**。

## 想定される反論と、それへの答え

- **「AIが自分で0と書けるなら意味が無い」** → 上記「Aの限界」のとおり。ただし
  **`set-header --unreplied 0` という明示的な操作**が要るようになる点が効く。今回の事故は
  「確認する手順に到達しなかった」ものであり、`mark-done` が止まれば必ず到達する。
- **「ヘッダ行が増えると `set-header` の失敗経路も増える」** → そのとおり。だから雛形へ足す
  （4）ことと、`.claude/docs/spec/update-handoff-progress.md` の「HANDOFF.mdのヘッダ行」を
  正として1箇所で定義することを、同じ変更に含める。
