# 全体作業計画: .gitignoreのDDR参照切れ修正と同種検出の仕組み（issue #171）

## Context

issue #133で全DDRを4桁ゼロ埋めのissue番号ベース識別子（`i0000-01`形式）へ一括改番した際、
`.gitignore`内のコメントに書かれた**参照文字列**は改番対象に含まれず、古い識別子のまま
取り残された。issue #171はこの取りこぼしを修正するとともに、「同じ事故が三度目に起きない
ようにする」ため、実在しないドキュメントを指す参照を機械的に検出できるようにすることを
求めている（issue #70で1回、今回で2回目の同種インシデント）。

**事前調査で判明した重要な事実**: issueの「現状」節は「`i00-13`（正しくは`i0000-13`）を
指す参照はissue #70で既に消えた」としているが、実際には`.gitignore`の28行目にまだ
`i00-13-gemini配下は…md`という参照が残っている。issue本文の前提は古く、**修正対象は
40行目（`i36-01`）だけでなく28行目（`i00-13`）も含めて2箇所**である。この差分は
フェーズ2〈調査〉のreportsへ明記する。

## この計画で何をするか

1. `.gitignore`内の2箇所のDDR参照切れ（`i00-13` → `i0000-13`、`i36-01` → `i0036-01`）を
   実在するファイル名に修正する。
2. リポジトリ全体を走査し、「実ファイルを指す意図で書かれたDDR参照でゼロ埋めが漏れている」
   箇所が上記2件以外に無いことを、件数付きの検索結果で確認する。
3. 同種の参照切れ（DDRファイルパスへの参照が実在しない）を検出する仕組みを追加する
   （既存の`check-base-conflicts.sh`の`ddr_identifier_to_reply`と同系統のbash実装）。
   単体テストを付ける。入れないという結論にはしない方針だが、フェーズ2の調査で
   実装コストが見合わないと判明した場合は理由をDDRへ残す。
4. 設計反映として、今回の意思決定（検出の仕組みを入れる/入れない、入れるならどう判定するか）
   をDDRとして記録する。

## 変更対象

- `.gitignore`（DDR参照コメント2箇所の修正）
- `.claude/scripts/src/`（新規: DDR参照切れ検出スクリプト。既存スクリプトへの追記で足りる
  可能性もフェーズ2で検討する）
- `.claude/scripts/test/`（新規: 上記の単体テスト）
- `.claude/docs/ddr/`（新規: 今回の検出方式・判定基準についての意思決定記録）
- `.claude/docs/spec/`（該当する既存specがあれば更新。無ければ新規specの要否をフェーズ2で判断）

## 方針

- 修正は`.gitignore`のコメント文字列の書き換えのみで、ignoreパターン自体（`**/index.jsonl`等）は
  変更しない。
- 検出の仕組みは、**DDRファイルパスへの参照**（`.claude/docs/ddr/i<番号>-<枝番>-...`という
  形の文字列）に絞る。ゼロ埋め規約を説明する例示的な記述（例:「ゼロ埋めなし: i106-01, ...」）は
  パス形式を取らないため、パス形式に限定することで誤検知を避けられる（.gitignoreの実例で
  確認済み）。DDR以外のドキュメント（spec等）への参照切れ検出は本issueのスコープ外とする
  （issueタイトルが「同種の参照切れ」＝DDR参照切れと明記しているため）。
- 既存の`ddr_identifier_to_reply`（`check-base-conflicts.sh`）はDDR**ファイル名**から識別子を
  抽出する関数であり、今回必要なのは逆方向（**ドキュメント本文中の参照文字列**から候補パスを
  抽出し実在確認する）である。流用より新規関数が妥当かはフェーズ2で判断する。

## フェーズ2〈調査〉

- リポジトリ全体（`git ls-files`ベース、バイナリ除く）を対象に、DDRパス形式の参照
  （`\.claude/docs/ddr/i[0-9]+-[0-9]{2}-` 等）を抽出し、対応する実ファイルが存在するかを
  1件ずつ確認する。結果は件数付きで`reports/`へ記録する（0件を期待する検索は当たらないパターンでは
  常に成功するため、実際にヒットした行を示す）。
- 上記のうち`.gitignore`の2箇所以外に参照切れが無いことを確認する（無いことの確認であっても
  「何件中何件が有効だったか」を示す）。
- 検出の実装方式を検討する。候補:
  - (a) 新規スクリプト`.claude/scripts/src/check-doc-references.sh`として独立させる
  - (b) `check-base-conflicts.sh`または`generate-ddr-list.sh`に検証ステップとして追記する
  - (c) `.claude/scripts/test/`配下の単体テストとして、リポジトリ全体を走査するテストを書く
  実行タイミング（手動実行のみか、既存フローの一部に組み込むか）もあわせて検討する。
- 既存の`.claude/rules/shell-script-style.md`の規約（外部プロセス起動コスト・jq引数長上限・
  NULバイト等）に沿った実装方針を確認する。

## フェーズ4〈反映〉

- 検出の仕組みに関する意思決定（どの方式を採ったか、なぜその粒度に絞ったか、入れない場合は
  その理由）をDDRとして記録し、`generate-ddr-list.sh`でREADMEの一覧を再生成する。
- 該当する既存specがあれば実装内容を反映する（無ければ新規spec作成の要否をフェーズ2の結果を
  見て判断する。過剰なドキュメント化は避け、小規模なスクリプトであればテストコード＋DDRで
  十分な可能性が高い）。
- AIアセット反映: 作業中に気づいたルール・スキルの不備があれば反映する（現時点では想定なし）。

## やらないこと（スコープ外）

- DDR以外（spec・plans・reports等）への参照切れ検出は行わない（本issueのタイトル・受け入れ条件が
  DDR参照切れに限定しているため）。
- 検出をSessionStart hook等へ自動組み込みし毎回実行する仕組みは作らない（起動コストの規約
  `.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」に照らし、頻度の低い
  整合性チェックを毎ツール呼び出しで走らせる必要は無いと判断。手動実行またはflow-id 5-1相当の
  タイミングでの実行を基本とする。この判断が変わる場合はフェーズ2で理由とともに更新する）。

## 検証

- `.gitignore`の28行目・40行目が、実在するDDRファイル名（`i0000-13-...`, `i0036-01-...`）を
  指していること。
- リポジトリ全体でのDDRパス参照の走査結果が、`.gitignore`修正後に**参照切れ0件**になること
  （件数付きで示す）。
- 追加した検出スクリプトが、意図的に参照切れを含む一時データに対して正しく検知できること
  （`bash -n`構文チェック＋単体テストの`passed=N failures=N`が失敗0件）。

## issueの受け入れ条件との対応

- [ ] `.gitignore`のコメントが`i0036-01-…`を指している → フェーズ3で修正（40行目、および
      本計画で追加確認した28行目の`i0000-13-…`も含む）
- [ ] ゼロ埋りが漏れたDDR識別子の参照が0件であることを件数付きの検索結果で示す → フェーズ2・
      フェーズ3のreportsに記録
- [ ] 同種の参照切れを検出する仕組みを入れるか、入れない理由を記録する → フェーズ3で実装、
      フェーズ4でDDRへ記録

## 比較検討した案

- **検出仕組みを作らず、目視確認のみで済ませる案**: 受け入れ条件が「検討」を求めているだけで
  実装を必須にしていないため選択肢としてはあるが、issueタイトルが「検出できるようにする」と
  明記しており、実装コストも小さいと見積もられるため、実装する方向を基本方針とする
  （フェーズ2で見積もりが外れた場合のみ再検討する）。
