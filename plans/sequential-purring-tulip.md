# 全体作業計画: .gitignoreのDDR参照切れ修正と同種検出の仕組み（issue #171）

## Context

issue #133で全DDRを4桁ゼロ埋めのissue番号ベース識別子（`i0000-01`形式）へ一括改番した際、
`.gitignore`内のコメントに書かれた**参照文字列**は改番対象に含まれず、古い識別子のまま
取り残された。issue #171はこの取りこぼしを修正するとともに、実在しないドキュメントを指す
参照を機械的に検出できるようにすることを求めている。**issue本文は「issue #70で1回、同種の
参照切れが発生していた」と述べているが、これはissue本文の記述の引用であり、本計画では
issue #70の該当コミットまでは特定していない**（フェーズ2の調査で必要になれば確認する）。

**事前調査で判明した重要な事実**: issueの「現状」節は「`i00-13`（正しくは`i0000-13`）を
指す参照はissue #70で既に消えた」としているが、実際には`.gitignore`の28行目にまだ
`i00-13-gemini配下は…md`という参照が残っている。issue本文の前提は古く、**修正対象は
40行目（`i36-01`）だけでなく28行目（`i00-13`）も含めて2箇所**である。詳細は
`reports/20260823_sequential-purring-tulip_DDR参照切れの網羅調査結果.md`を正とする
（本節では要点のみ記載し、以後の更新はreports側で行う）。

## この計画で何をするか

1. `.gitignore`内の2箇所のDDR参照切れ（`i00-13` → `i0000-13`、`i36-01` → `i0036-01`）を
   実在するファイル名に修正する。
2. リポジトリ全体を走査し、「実ファイルを指す意図で書かれたDDR参照でゼロ埋めが漏れている」
   箇所が上記2件以外に無いことを、件数付きの検索結果で確認する。
3. 同種の参照切れ（DDRファイルパスへの参照が実在しない）を検出する仕組みを追加する
   （既存の`check-base-conflicts.sh`の`ddr_identifier_to_reply`と同系統のbash実装）。
   単体テストを付ける。入れないという結論にはしない方針だが、フェーズ2の調査で
   実装コストが見合わないと判明した場合は理由をDDRへ残す。
4. 設計反映として、今回の意思決定（検出の仕組みを入れる/入れない、入れるならどう判定するか）
   をDDRとして記録する。

## 変更対象

- `.gitignore`（DDR参照コメント2箇所の修正）
- `.claude/scripts/src/`（新規: DDR参照切れ検出スクリプト。既存スクリプトへの追記で足りる
  可能性もフェーズ2で検討する）
- `.claude/scripts/test/`（新規: 上記の単体テスト）
- `.claude/docs/ddr/`（新規: 今回の検出方式・判定基準についての意思決定記録）
- `.claude/docs/spec/`（該当する既存specがあれば更新。無ければ新規specの要否をフェーズ2で判断）

## 方針

- 修正は`.gitignore`のコメント文字列の書き換えのみで、ignoreパターン自体（`**/index.jsonl`等）は
  変更しない。
- 検出の仕組みは、**DDRファイルパスへの参照**（`.claude/docs/ddr/i<番号>-<枝番>-...\.md`という
  形の文字列）に絞る。**この設計判断はリポジトリ全体を対象に実測して検証済み**（フェーズ2の
  調査で確認。当初は「.gitignoreの実例だけで確認した」段階だったが、全体作業計画の時点では
  未検証だった。詳細: `reports/20260823_sequential-purring-tulip_DDR参照切れの網羅調査結果.md`）。
  実測の結果、単純な「パス形式に限定するだけ」では誤検知が残ることが判明し、追加で
  「テストファイル（`.claude/scripts/test/`配下）除外」「Markdownコードフェンス内除外」
  「省略記法（`...`/`…`を含む候補）除外」の3フィルタが必要だった。
- **見逃す範囲**: この設計は「DDRファイルパス形式」の参照に限定するため、パスを伴わない
  裸の識別子表記（例:「DDR i0159-01参照」）はスコープに含めない。issueの受け入れ条件(2)は
  「ゼロ埋めが漏れたDDR識別子の参照」を対象にしており文言上はパス形式に限定していないが、
  今回の調査対象は主に`.gitignore`のようなコメント内の**ファイルパスとして書かれた参照**
  であり、裸の識別子はドキュメント中で規約の例示として多用され誤検知源になりやすい
  （実測でも確認済み）ため、本issueではパス形式限定とする。この限定は「やらないこと」節にも
  明記する。
- DDR以外のドキュメント（spec等）への参照切れ検出は本issueのスコープ外とする
  （issueタイトルが「同種の参照切れ」＝DDR参照切れと明記しているため）。
- 既存の`ddr_identifier_to_reply`（`check-base-conflicts.sh`）はDDR**ファイル名**から識別子を
  抽出する関数であり、今回必要なのは逆方向（**ドキュメント本文中の参照文字列**から候補パスを
  抽出し実在確認する）である。新規関数として実装する（フェーズ2で確認済み）。
- **参照文字列の終端規則**: 一部のDDRファイル名自体に`.md`という文字列が含まれる
  （例: `i0032-01-GitLab-issueテンプレートは予約名Default.mdを正とし文書側を合わせる.md`）。
  非貪欲マッチで最初の`.md`を終端にすると誤って途中で切れるため、**貪欲マッチ**
  （bashの`[[ =~ ]]`は既定で貪欲）で終端記号（空白・`)` `]` `"` `'` `` ` `` `(`）の
  直前までを候補として拾い、`.md`で終わることを要求する設計とする（フェーズ2で実測により
  この2件を含めて正しく判定できることを確認済み）。

## フェーズ2〈調査〉

- リポジトリ全体（`git ls-files`ベース、バイナリ除く）を対象に、DDRパス形式の参照
  （`\.claude/docs/ddr/i[0-9]+-[0-9]{2}-` 等）を抽出し、対応する実ファイルが存在するかを
  1件ずつ確認する。結果は件数付きで`reports/`へ記録する（0件を期待する検索は当たらないパターンでは
  常に成功するため、実際にヒットした行を示す）。
- 上記のうち`.gitignore`の2箇所以外に参照切れが無いことを確認する（無いことの確認であっても
  「何件中何件が有効だったか」を示す）。
- 検出の実装方式を検討する。候補:
  - (a) 新規スクリプト`.claude/scripts/src/check-doc-references.sh`として独立させる
  - (b) `check-base-conflicts.sh`または`generate-ddr-list.sh`に検証ステップとして追記する
  - (c) `.claude/scripts/test/`配下の単体テストとして、リポジトリ全体を走査するテストを書く
  実行タイミング（手動実行のみか、既存フローの一部に組み込むか）もあわせて検討する。
- 既存の`.claude/rules/shell-script-style.md`の規約（外部プロセス起動コスト・jq引数長上限・
  NULバイト等）に沿った実装方針を確認する。

## フェーズ4〈反映〉

- 検出の仕組みに関する意思決定（どの方式を採ったか、なぜその粒度に絞ったか、入れない場合は
  その理由）をDDRとして記録し、`generate-ddr-list.sh`でREADMEの一覧を再生成する。
- 該当する既存specがあれば実装内容を反映する（無ければ新規spec作成の要否をフェーズ2の結果を
  見て判断する。過剰なドキュメント化は避け、小規模なスクリプトであればテストコード＋DDRで
  十分な可能性が高い）。
- AIアセット反映: 作業中に気づいたルール・スキルの不備があれば反映する（現時点では想定なし）。

## やらないこと（スコープ外）

- DDR以外（spec・plans・reports等）への参照切れ検出は行わない（本issueのタイトル・受け入れ条件が
  DDR参照切れに限定しているため）。
- パスを伴わない裸のDDR識別子表記（例:「DDR i0159-01参照」）の参照切れ検出は行わない
  （上記「方針」の「見逃す範囲」参照。ドキュメント中で規約説明の例示として多用され誤検知源に
  なりやすいため）。
- **毎ツール呼び出し・毎コミットで自動実行する仕組み（SessionStart/PostToolUse hookへの組み込み）
  は作らない**（起動コストの規約`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」
  に照らし、頻度の低い整合性チェックを毎回走らせる価値が無いと判断）。**実行タイミングの具体案
  （手動実行のみか、`resolve-conflict`スキル・`generate-ddr-list.sh`実行時への合流か）は
  フェーズ2の成果物として決定し、ここでは決めない**（フェーズ2の調査結果:
  `reports/20260823_sequential-purring-tulip_DDR参照切れの網羅調査結果.md`「検出方式の設計」
  参照）。

## 検証

- `.gitignore`から参照確認に使う正規表現でDDRパス文字列を抽出し、実在しないものを検索する
  （`grep -noE '\.claude/docs/ddr/i[0-9]+-[0-9]{2}-[^]\)\ "'"'"'`(]*\.md' .gitignore`
  で候補を出し、各候補について`test -f`で存在確認する）。**修正前は2件ヒットし、修正後は
  0件になること**を確認する（既存DDRファイルの存在確認だけでは`.gitignore`側の記述が
  直っているかを検出できないため、検証は必ず参照側＝`.gitignore`から行う）。
- リポジトリ全体でのDDRパス参照の走査（上記「方針」の3フィルタを適用）が、`.gitignore`修正後に
  **参照切れ0件**になること（件数付きで示す。フェーズ2で既に123件中2件〈`.gitignore`のみ〉と
  確定済み。フェーズ3の修正後に同じ走査を再実行し0件になることを確認する）。
- 追加した検出スクリプトが、意図的に参照切れを含む一時データに対して正しく検知できること
  （`bash -n`構文チェック＋単体テストの`passed=N failures=N`が失敗0件）。

## issueの受け入れ条件との対応

- [ ] `.gitignore`のコメントが`i0036-01-…`を指している → フェーズ3で修正（40行目、および
      本計画で追加確認した28行目の`i0000-13-…`も含む）
- [ ] ゼロ埋めが漏れたDDR識別子の参照が0件であることを件数付きの検索結果で示す → フェーズ2で
      調査済み（`reports/`参照）、フェーズ3で修正後に再走査し記録
- [ ] 同種の参照切れを検出する仕組みを入れるか、入れない理由を記録する → フェーズ3で実装、
      フェーズ4でDDRへ記録

## 比較検討した案

- **検出仕組みを作らず、目視確認のみで済ませる案**: 受け入れ条件が「検討」を求めているだけで
  実装を必須にしていないため選択肢としてはあるが、issueタイトルが「検出できるようにする」と
  明記しており、フェーズ2の調査で判定ロジック（正規表現・3フィルタ）が既に確立し実装可能な
  見通しが立ったため、**却下**し実装する方向を採用する。
