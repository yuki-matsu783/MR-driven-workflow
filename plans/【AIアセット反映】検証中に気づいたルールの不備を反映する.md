# 個別反映計画（フェーズ4・AIアセット反映）

- 全体作業計画: `plans/zippy-petting-crown.md`
- 詳細ログ: `worklog/20260820_zippy-petting-crown_【設計】【実装】GitLab差分アンカーの土台と未定義関数呼び出しの修正_push9.md`
- issue: [#127](https://github.com/yuki-matsu783/MR-driven-workflow/issues/127) / PR: [#128](https://github.com/yuki-matsu783/MR-driven-workflow/pull/128)

設計反映（spec/ddr）は `plans/【設計反映】GitLab実機検証の結果をspecとDDRへ反映する.md` で扱う。
本計画は**運用ルール・レビュー観点の改訂**を対象にする。**例外が1件だけある**: §5 は
`.claude/docs/spec/update-handoff-progress.md` を触りうる（スクリプトの運用面の話であり、
`.claude/rules/docs-workflow.md` 側の記述と対になっているため、どちらへ書くかを §5 で決める）。
この例外を明示しておかないと、設計反映側のレビュアーがspecの変更を予期できない。

**「今回たまたま起きたこと」ではなく「同じ失敗が次も起きる形になっているもの」だけを入れる。**
ルールが増えるほど1件あたりの重みは下がるため、実際に踏んだ失敗に限定する。

## 反映対象

### 1. `.claude/rules/shell-script-style.md`「テスト」節

いずれも本issueで**実際にテストを失敗させた**もの。

| 追記内容 | 実例 |
|---|---|
| **`declare -F <名前>` は名前だけを出力する**（引数なしのときだけ `declare -f <名前>` 形式）。`\| awk '{print $3}'` で受けると空になる。存在確認は `declare -F x >/dev/null && echo x` の形にする | 共有関数の定義を表明するケースで6件失敗した |
| **テスト内で既存関数を再定義してから `unset -f` すると、スタブではなく実定義そのものが消える**（bashの関数定義はスタックしない）。差し替えはサブシェル `( fn() { ...; }; 対象関数 )` へ閉じ込めるか、`declare -f` で退避して復元する | `unset -f get_repo_url` が `Provider.sh` の定義を消していた。後続にケースを1つ足すだけで `command not found` になる状態だった |
| **「関数名らしい文字列」を正規表現で拾う静的検出は、同じ接頭辞を持つ別種の識別子を巻き込む** | MCPツール名（`github__list_pull_requests` のように**アンダースコア2つ**）が `(github\|gitlab)_[a-z0-9_]+` に一致し、未定義の関数として9件検出された |
| **jqのフィールド名とシェル関数の呼び出しは静的に区別できない** ため、機械的な導出には偽陽性が混ざる（`new_path` / `head_sha` / `start_sha` 等）。明示的な一覧を持つ場合は、**その一覧が形骸化していないこと**（実際に呼ばれていること）も併せて表明する | 共有関数の検出で十数件の偽陽性を確認した |
| **純粋関数の単体テストは、その関数へ至る呼び出し経路を何も保証しない。** 呼び出し経路を通すテストを併せて書く（`glab` 等の外部コマンドはシェル関数で差し替えられる） | `gitlab_get_mr_url` / `gitlab_get_note_url` は単体テストから**直接**呼ばれていたためテストは緑のままで、**実運用経路が丸ごと到達不能**になっていた（issue #127 で検出した不具合2） |

**上2行のうち後者は、設計反映側の計画（§6）が「教訓はAIアセット反映側で扱う」と委譲してきた
2件のうちの1件である。** もう1件（**並行ブランチのsemantic conflictをgitは報告しない**）は
`.claude/skills/resolve-conflict/SKILL.md` に既存の記述があるため、**本issueの実例
（`7ebc615` が呼び出しを足し、`8d01fbb` が定義を消した。どちらも単体では正しい）を追記するか、
重複と判断して「反映不要」と結論するかを 4-6 で決める**。どちらにするにせよ、
**「片方の計画が委譲し、もう片方が受け取っていない」状態にはしない。**

### 2. `reports/REVIEW-POINTS.md`

- **md版とHTML版の同期は「追記」だけでは足りない。既存記述の更新まで含める。**
  本issueでは、md側で3箇所（サマリ・検証表・未完了節）を更新したのにHTMLへは末尾へ節を
  追記しただけ（削除0行）で、**視覚版だけを見た読み手には「受け入れ条件1は未達」と読める**
  状態のまま公開していた。既存の観点「markdown版とHTML版の内容が同期しているか」は
  あるが、**「追記だけして満足していないか」という失敗様態が読み取れない**ため補強する。
- 判定の目安も添える: **md側の差分が「追加のみ」でないなら、HTML側も「追加のみ」では
  同期していない可能性が高い。**

### 3. `plans/REVIEW-POINTS.md`

- **計画に書く修正指示が「既存の2行を1行へ置き換える」のような形のとき、置き換え前後の
  形を両方書く。** 本issueでは、置き換え対象の行が別の変数の `local` 宣言を兼ねており、
  指示どおり実装すると未定義変数参照になる状態だった（敵対的レビューで検出）。
  **「どこを何に変えるか」だけでは、巻き添えを計画の段階で検出できない。**
- **同一計画内の別の作業が、ある作業の前提を崩していないか。** 本issueでは、作業4で
  「外部プロセスを使わないテスト」と書いた一方、作業2の変更でその経路が
  `git remote get-url origin` を起動するようになっていた。

### 4. `.claude/rules/git-workflow.md`「コミット運用」（反映先を確定させた）

**反映先は `.claude/rules/git-workflow.md` に確定する。** 役割で切り分けた結果である
——**一般則（新種の副産物を見つけたら `.gitignore` へ追加する）はGit運用ルール**、
**除外リストそのものの運用は `commit` スキルの Step 3**。`commit/SKILL.md` の Step 3 へ
一般則を書くと、具体的な除外パターンの列挙とルールが同じ節に混在する。

- **`git status` の出力を機械的に全件渡さない。** 本issueで `bash.exe.stackdump`
  （MSYSのクラッシュダンプ）を1度コミットに含めてしまった。`commit` スキルの
  「ファイルフィルタ」節は除外リストを持つが、**呼び出し側が `git status` から
  組み立てたパス配列をそのまま渡す**運用だと、リストに無い新種の副産物が素通りする。
- `*.stackdump` は本issueで既に `.gitignore` へ追加済み（**指示されていない変更のため、
  レビューで不要と判断されたら戻す**）。ルール側には「新種の副産物を見つけたら
  `.gitignore` へ追加する」という一般則として書く。

### 5. ループ範囲へ初めて入るときの `add-round`（置き場所を1つに決める）

**ループ範囲の外から中へ初めて入るとき、`add-round <flow-id>` は使えない。** 進捗列が既に
`[]` のため「前回の往復が未完了の可能性」で拒否される（本issueで実際に踏んだ）。この場合は
`set-header --loop '<範囲> の1周目（進行中）'` を使う。

**必要なのは新しい事実の追記ではなく、既にある2つの記述を結び付ける1文である。**

- `.claude/docs/spec/update-handoff-progress.md` は、`add-round` のエラー条件として
  「対象行のいずれかで末尾が既に `[]` の場合（前回往復が未完了）」を**既に書いている**。
- `.claude/rules/docs-workflow.md` も「ループ範囲の外へ出たときなど、**表から決まらない値を
  入れる場合だけ `set-header --loop <text>` を使う**」と、逃げ道を**既に許可している**。

欠けているのは、この2つが**「ループ範囲へ初めて入るとき」という具体例で繋がっていない**ことだけ。
**置き場所はどちらか一方に決め、両方には書かない**（検証3の重複禁止）。実運用でAIが常時読むのは
`.claude/rules/docs-workflow.md` 側なので、そちらを第一候補とする。
