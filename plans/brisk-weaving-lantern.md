# 【全体作業計画】残置テキストの係り先ルールを構造変更全般へ広げる

issue #142 / PR #188。

## この作業で何をするか

`.claude/rules/docs-workflow.md` にある「既存ドキュメントへ新しい見出しを差し込むときは、挿入位置の
直前の節が『その節全体にかかる地の文』で終わっていないかを必ず確認する」というルール（issue #64 で
追加）を、**見出しの挿入に限定された書き方から、「残置したテキストの係り先が変わっていないか」という
観点の書き方へ一般化する**。

同型の事故が既に4件確認されている（issue #64 / #109 / PR #139 / issue #155）。現行の文言は
そのうち #64 の形しか拾えない。

## 背景（issueと通知コメントから確定している事実）

**「壊れた位置」は、新しく書いた部分から見て前か後ろかで揃える**（「分割点の直後」のように
別の基準を混ぜると、同じ事例が前とも後ろとも言えてしまう）。

| # | 何を変えたか | 壊れたテキストの位置（新しく書いた部分から見て） | 現行ルールで拾えるか |
|---|---|---|---|
| issue #64 | 新しい見出しを差し込んだ | **前**（挿入位置の直前の節の末尾） | 拾える（このルールの元ネタ） |
| issue #109 | 既存の節を (1)(2) に**分割**した | **前**（新設した (2) の手前に残した、(1) 直下の結論行） | 拾えない（見出しの挿入ではない） |
| PR #139（issue #135） | 新しい見出しを差し込んだ | **後ろ**（新設した見出しの配下に入ってしまった、見出しを持たない段落群） | **拾えない**（射程内の操作なのに「直前を見よ」という手順では検出できない） |
| issue #155 | 既存の箇条書きへ**項を1つ足した** | **前**（直前の項の末尾にあった補足） | 拾えない（見出しも節も階層も動いていない） |

4件とも**自己確認では見つからず、敵対的レビューが検出**している。書いた本人は「新しく書いた部分が
正しいか」を見ており、「既にあった行の係り先が変わったか」を見ていない。

**この表の正は、フェーズ2の調査結果（`reports/…md`）へ移す。** 各件の判定（拾えるか／どちらが
壊れたか）は調査の成果物であり、計画側で確定させるものではない。ここに置くのは着手時点の見立てで
あって、調査結果と食い違った場合は調査結果が正である。

| `.claude/docs/usecase/` | 変更（見込み） | 影響の有無を確認する |
| `.gemini/`（`rules/` 等） | 再生成 | `.claude/` を変更したことに伴う変換生成物の再生成。実行は flow-id 5-3 の `bash .claude/scripts/src/sync-gemini-assets.sh` であり、**直接編集はしない**（`.claude/rules/directory-structure.md`） |

## フェーズ2〈調査〉

**実施する。** 次の問いに答える。

1. 現行ルール（`.claude/rules/docs-workflow.md` の該当段落と実例2件）は、どの範囲を射程にしているか。
   一般化したとき、既存の実例2件はそのまま残せるか。
2. 同じ趣旨のルールが**他のファイルにも重複していないか**（ルート `REVIEW-POINTS.md`「ドキュメントの
   構造」に同型の観点がある。正を1箇所にするのか、観点表と規約で役割を分けるのかを決める）。
3. 4件の実例のうち、ルール本文へ載せるのはどれか。**「分割前は正しかった行が分割によって誤りになる」
   （#109）と「挿入位置の後ろが壊れる」（PR #139）は方向が逆**で、2つ並べると観点が立体的になる、と
   issue #142 のコメントが示している。何件までなら読み手の負担にならないか。
4. 受け入れ条件が求める「拡張の判断をDDRへ残すか、既存DDRへの追記で足りるか」の材料。
   **係り先・見出し挿入のルールを扱ったDDRがあるか**を、識別子ではなく内容で確定する。
5. このルールを**実際に守らせる場所**はどこか（`.claude/rules/docs-workflow.md` だけでよいか、
   `REVIEW-POINTS.md`・敵対的レビューの観点にも要るか）。

## フェーズ3〈作業〉

調査結果をもとに、`.claude/rules/docs-workflow.md` の該当ルールを書き換える。想定する形は次のとおり
（**暫定案**であり、確定はフェーズ3の個別計画で行う）。

- 適用対象を「見出しの差し込み」から**構造変更全般**へ広げる。ただし**操作の種類を列挙する形にしない**
  （issue #155 の3例目が、列挙した4操作のどれにも入らなかったため）。
- 確認の観点を「**残置した地の文・箇条書きが、変更前と同じものに係っているか**」という形で書く。
- 「**前後どちらの残置テキストも見る**」ことを明示する（PR #139 のコメントの指摘）。
- issue #64 の既存の実例（`計画の2階層構造` の位置、ファイルごとに結論が変わる話）は**消さない**。
- 「分割前は正しかった行が、分割によって誤りになる」形を明示した実例を足す。

種別は `【AIアセット作成】` を想定する（ルール文書そのものが今回の主たる成果物であるため）。

## フェーズ4〈反映〉

flow-id 4-1 で反映対象を洗い出す。現時点の見込みは次のとおり（確定した反映内容ではない）。

- **DDR**: 「なぜ操作の列挙ではなく観点で書くのか」の判断を残すか、既存DDRへの追記で足りるか。
  issue #142 の受け入れ条件が明示的に求めているため、**結論の記録は必須**。
- **`REVIEW-POINTS.md`**: ルート `REVIEW-POINTS.md`「ドキュメントの構造」の同型の観点を、
  一般化後の記述と揃えるか。
- **`.claude/docs/usecase/`**: 影響の有無を確認する。
- **`.gemini/`**: `.claude/` を変更した以上、再生成が要る（実行は flow-id 5-3）。

## この計画で決めないこと（スコープ外）

- **過去に書かれたドキュメントの遡及点検**。今回はルールの文言を直すところまでで、既存文書に同型の
  破損が残っていないかの棚卸しは行わない（判断は別issueへ送る）。
- **敵対的レビューのサブエージェント定義（`.claude/agents/adversarial-reviewer.md`）の改修**。
  観点表へ書けば足りるかをフェーズ2の問い5で判定し、足りないと分かった場合のみフェーズ4で扱う。
- 4件以外の事例の発掘（判断は flow-id 2-1 の個別調査計画へ送る）。

## 検証

issue全体として、次がすべて満たせたら完了とする。

- `.claude/rules/docs-workflow.md` の該当ルールが、**4件の実例すべてを説明できる**文言になっている
  （4件それぞれについて、ルールの文言を読んで「見るべきだった」と分かるか机上で突き合わせる）。
- issue #64 由来の**既存2実例（計6行）が1行も欠けずに**残っている。
- DDRの要否について結論が記録されている。
- 各フェーズで敵対的レビューを実施し、投稿された指摘へ対応・返信している。

```bash
# issue #64 由来の既存2実例（.claude/rules/docs-workflow.md の109〜114行、計6行）が
# 1行も消えていないこと。判定語は6行それぞれに固有のものを選ぶ（1語だと途中行の削除を見逃す）。
# 対象パスは書き換え先2箇所の両方（.claude/ とルート REVIEW-POINTS.md）。
# 分岐点SHAは直接渡す（origin/main は fetch のたびに動くため）。
base=4be448af553c82c0fcf731705b0cd1d08bf23f29
git diff "$base" -- .claude/ REVIEW-POINTS.md | grep '^-' | grep -cF \
  -e '末尾に節全体へかかる地の文' \
  -e 'での機械的列挙・flow-id 1-4の判定' \
  -e 'の直前へ新節を入れた' \
  -e '同じ節名でもファイルごとに結論が変わる' \
  -e '直後に地の文が無く' \
  -e '入れられたから安全' || true
```

合格条件: 上のコマンドが **`0` を出す**こと（削除行に6行のどれも現れない）。

**この検証が空振りしないことは、flow-id 2-6 で確認済みである。** 109〜114行を1行ずつ削ったツリーで
同じコマンドを実行し、**6行すべてでそれぞれ `1` が出る**ことを確かめた（結果は
`reports/20260823_brisk-weaving-lantern_係り先ルールの射程調査.md`「全体作業計画の検証コマンドの
空振り確認」）。

## 進め方の前提（このセッション固有）

- **非対話的セッション**のため、人間のレビュー往復（flow-id 2-3/2-8・3-3/3-8・4-3/4-8）は成立しない。
  **各フェーズの計画時に1回・作業実施ごとに1回、敵対的レビューを自動起動し**、その指摘への修正・返信を
  もってレビュー往復の代替とする。
  **出所**: ユーザーがこのセッションの最初の指示で明示したもの（flow-id 1-1 の依頼と同じ発言に含まれる）。
  flow-id 1-5（全体作業計画への人間の合意）は非対話的セッションのため実施できず `[-]` としており、
  **人間の合意を経た前提ではない**。
- ブランチ名はハーネス指定の `claude/docs-workflow-heading-rule-mi3krb` を使う
  （`.mrworkflow.json` の `feature-<issue番号>-<slug>` 規則とは異なる）。
  **出所**: ハーネス（実行基盤）のシステムプロンプトによる制約で、flow-id 1-3（ブランチ作成）の
  時点で決まっていた。ユーザーの判断ではない。
