# 【調査】ルール自動読込条件とコマンド文字列の前方一致

- issue: [#47](https://github.com/yuki-matsu783/MR-driven-workflow/issues/47)
- 全体作業計画: `plans/prancy-prancing-dewdrop.md`
- flow-id: 2-1

## 目的

issue #47 が追加しようとしているのは「〜だから、こう書け」という**根拠つきの規約**である。
受け入れ条件も、根拠（`description` の1行表示制約・前方一致が外れる理由・hook誤検知）を本文へ
明記することを求めている。根拠が事実でなければルール自体が無効になるため、**ルール本文を書き
始める前に、依拠する事実を確定させる**。

## このフェーズを実施する理由（省略しない判断）

flow-id 2-1 時点で「既に分かっていることだけで個別作業計画（3-1）が書けるか」を問うと、
書けない。以下2点が未確定で、どちらもルール本文の**書き方そのもの**を変えるためである。

- 新規ルールファイルがセッション開始時に読み込まれるか（読み込まれないなら、受け入れ条件1を
  満たすために別の手段—既存ファイルへの追記、`AGENTS.md` からの参照—が要る）
- 「1行目コメントで前方一致が外れる」の裏付けが取れるか（取れないなら、断定ではなく
  「リスク回避」として書く必要がある）

## 調査項目

### 調査1: `.claude/rules/` 配下のmarkdownが自動でコンテキストへ読み込まれる条件

**問い**: 新規に `.claude/rules/<名前>.md` を作ったとき、次セッションの開始時に自動で読み込まれるか。
読み込まれるための条件は何か（`alwaysApply: true` frontmatterか、ディレクトリ単位か、
`AGENTS.md` / `CLAUDE.md` からの参照か）。

**分かっていること**（flow-id 1-4 の事前調査）:

- `.claude/rules/` の6ファイル中、`alwaysApply: true` を持つのは
  `directory-structure.md` / `docs-workflow.md` / `git-workflow.md` の3つだけ。
- 本セッションの開始時コンテキストには**6ファイルすべて**が入っていた。
- `AGENTS.md` は `.claude/rules/` を文章で参照しているだけで `@import` していない。
  `CLAUDE.md` が `@import` しているのは `./AGENTS.md` のみ。

**確認方法**:

1. `.claude/settings.json` に読み込み対象を指定する設定が無いことを確認する。
2. `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` の `@` 参照をすべて洗い出し、間接的な取り込み経路が
   無いことを確認する。
3. `.claude/docs/spec/` 配下に、この読み込みについて既に記録された仕様が無いかを
   `doc-search` スキル（frontmatterインデックス検索）で探す。
4. 上記で決め手が無い場合は、**「本セッションで6ファイルすべてが読み込まれた」という観測事実**を
   根拠として採用し、断定できる範囲と推測に留まる範囲を分けて記述する。

**この調査で決めないこと**: Claude Code本体の実装がどうなっているか。観測できるのは
「このリポジトリのこの構成で、実際に読み込まれたかどうか」までである。

### 調査2: `permissions.allow` / `deny` の前方一致が何に対して行われるか

**問い**: issue本文の「複数行コマンドの1行目にコメントを書くと `permissions.allow` / `deny` の
前方一致が外れる」は正しいか。外れるとしたら、照合対象はコマンド文字列全体の先頭か、
パース後の最初のコマンドか。

**分かっていること**: `.claude/settings.json` の `permissions.deny` には、コミット操作を
prefixパターンで拒否する設定が実在する。したがって「外れる」場合の影響は仮想の話ではない。

**確認方法**:

1. リポジトリ内の既存ドキュメント（`.claude/docs/spec/` `.claude/docs/ddr/` `.claude/rules/`）に
   前方一致の挙動についての記述が無いかを `doc-search` で探す。
2. `.claude/hooks/` 配下で `permissions` の挙動に言及している箇所を確認する。
3. `.claude/settings.json` の `hooks.PostToolUse` にある `"if": "Bash(git push*)"` という
   **同じ書式のパターン**が、実際にどう照合されているかを手がかりにする（このリポジトリは
   複数行コマンドを日常的に使っており、hookの発火実績が観測材料になる）。

**この調査で決めないこと**: 実機での網羅的な検証。承認プロンプトの表示はリモート実行環境の
権限モードに依存し、`deny` の挙動を試すこと自体が危険な操作を伴う。**裏付けが取れなくても、
「1行目にコメントを置かない」という結論は変わらない**（外れる可能性がある以上、避けるのが
妥当）。この調査の成果は「ルール本文の理由を断定形で書けるか、リスク回避として書くか」の判断材料。

### 調査3: hook誤検知がコメント本文で発火する範囲

**問い**: コメント行に `git` と `commit` / `push` が連続して現れると、既存hookは実際に発火するか。
`.claude/rules/git-workflow.md` に既にある同趣旨の注意と、新ルールでの再掲をどう書き分けるか。

**分かっていること**:

- `.claude/hooks/block-direct-git-commit.sh` は `tool_input.command` **全体**を正規表現で検査する
  （コメント行を除外していない）。
- `.claude/settings.json` の PostToolUse hook も同じ書式のパターンで発火する。
- **本セッションで実際に発火させた**（flow-id 1-6 でHANDOFF.mdの地の文へdenyパターンを書いた
  ところ、PreToolUse hookがブロックした）。これは再現済みの事実として使える。

**確認方法**:

1. 2つのhookスクリプトの検査ロジックを読み、コメント行が除外されないことをコードで裏付ける。
2. `.claude/rules/git-workflow.md` の既存記述（コミット側・push側の2箇所）を読み、
   **どこまでが既存で、新ルールが何を足すのか**を切り分ける。重複記載はしない方針
   （`.claude/rules/docs-workflow.md` の運用）。

### 調査4: 新規ファイルにするか既存ファイルへ追記するか、および命名

**問い**: 受け入れ条件は「新規ファイル／既存ファイルへの追記のどちらにするかは実装時に判断する」と
している。どちらにするか、新規ならファイル名は何にするか。

**確認方法**:

1. 既存6ファイルのスコープ（`title` / `description` / 冒頭の「適用範囲」節）を一覧化し、
   今回の内容が既存のどれかに収まるかを判定する。
2. `.claude/rules/directory-structure.md` と `.claude/rules/markdown-frontmatter.md` の
   命名・frontmatter規約を確認する。
3. 調査1の結果（自動読込の条件）と突き合わせる。

## この計画で決めないこと（スコープ外）

- **ルール本文の文面そのもの**。文面はフェーズ3（flow-id 3-1 の個別作業計画）で決める。
  本フェーズが出すのは「何を根拠として書けるか」までである。
- **DDRの本文**。同じくフェーズ3。
- **`description` が1行しか表示されないことの再確認**。リモート実行環境にはコンソール表示が
  無く、再現できない。issue #47 起票時の実機確認を出典として引用する形で扱う（この扱い自体は
  確定事項とし、調査項目には含めない）。
