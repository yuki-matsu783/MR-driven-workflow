# 【調査】ルール自動読込条件とコマンド文字列の前方一致

- issue: [#47](https://github.com/yuki-matsu783/MR-driven-workflow/issues/47)
- 全体作業計画: `plans/prancy-prancing-dewdrop.md`
- flow-id: 2-1

## 目的

issue #47 が追加しようとしているのは「〜だから、こう書け」という**根拠つきの規約**である。
受け入れ条件も、根拠（`description` の1行表示制約・前方一致が外れる理由・hook誤検知）を本文へ
明記することを求めている。根拠が事実でなければルール自体が無効になるため、**ルール本文を書き
始める前に、依拠する事実を確定させる**。

## このフェーズを実施する理由（省略しない判断）

flow-id 2-1 時点で「既に分かっていることだけで個別作業計画（3-1）が書けるか」を問うと、
書けない。以下2点が未確定で、どちらもルール本文の**書き方そのもの**を変えるためである。

- 新規ルールファイルがセッション開始時に読み込まれるか（読み込まれないなら、受け入れ条件1を
  満たすために別の手段—既存ファイルへの追記、`AGENTS.md` からの参照—が要る）
- 「1行目コメントで前方一致が外れる」の裏付けが取れるか（取れないなら、断定ではなく
  「リスク回避」として書く必要がある）

## 調査項目

### 調査1: `.claude/rules/` 配下のmarkdownが自動でコンテキストへ読み込まれる条件

**問い**: 新規に `.claude/rules/<名前>.md` を作ったとき、次セッションの開始時に自動で読み込まれるか。
読み込まれるための条件は何か（`alwaysApply: true` frontmatterか、ディレクトリ単位か、
`AGENTS.md` / `CLAUDE.md` からの参照か）。

**分かっていること**（flow-id 1-4 の事前調査）:

- `.claude/rules/` の6ファイル中、`alwaysApply: true` を持つのは
  `directory-structure.md` / `docs-workflow.md` / `git-workflow.md` の3つだけ。
- 本セッションの開始時コンテキストには**6ファイルすべて**が入っていた。
- `AGENTS.md` は `.claude/rules/` を文章で参照しているだけで `@import` していない。
  `CLAUDE.md` が `@import` しているのは `./AGENTS.md` のみ。

**確認方法**:

1. `.claude/settings.json` に読み込み対象を指定する設定が無いことを確認する。
2. `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` の `@` 参照をすべて洗い出し、間接的な取り込み経路が
   無いことを確認する。
3. **SessionStart hook（`.claude/hooks/session-start.sh`）が注入する内容に `.claude/rules/` が
   含まれないことを確認する。** このリポジトリでセッション開始時にコンテキストを注入する経路として
   最も直接的であり、潰さないまま結論を出すと注入経路を1つ見落とすことになる。
4. `.claude/docs/spec/` 配下に、この読み込みについて既に記録された仕様が無いかを
   `doc-search` スキル（frontmatterインデックス検索）で探す。
5. **新規ファイルで実際に確かめる**（下記「受け入れ条件1を満たすための実測」）。

#### 受け入れ条件1を満たすための実測

受け入れ条件1が求めているのは「**今回追加する**ルールがセッション開始時に自動で読み込まれることを
確認できている」ことである。**「既存6ファイルが読み込まれた」という観測は、新規ファイルについての
証拠にならない**（既存ファイルが他所から名指しで参照されている可能性を排除できないため）。
したがって、上記1〜4で経路を潰しただけで受け入れ条件1を満たしたことにしない。

フェーズ3でルールファイルを作った後に、次のいずれかで実測する。

- **新しいセッションを開始し、当該ファイルの内容が開始時コンテキストへ入るかを見る**（最も直接的）。
- 本セッション内で確かめられない場合は、**ユーザーへ確認を依頼する**（新しいセッションを開いて
  当該ファイルがコンテキストに載っているかを見てもらう）。依頼すること自体を計画へ書いておき、
  「確認できていないまま満たしたことにする」状態を作らない。

**実測が取れるまでは受け入れ条件1を満たしたと書かない。** この実測ステップはフェーズ3の検証節にも
再掲する。

#### 結論を適用してよい範囲

**この観測は「Claude Code on the web のリモート実行環境」1経路のものである。** このリポジトリは
Claude Code（ローカルのgit bash）・Claude Code on the web・Gemini CLI の3経路を想定しており
（`.claude/rules/directory-structure.md` の `.gemini/` の記述、`GEMINI.md`）、`GEMINI.md` が
`@import` しているのは `./AGENTS.md` だけで `.gemini/rules` は `.claude/rules` へのローカルリンク
である。**「新規ルールファイルが自動で読み込まれるか」の答えは経路ごとに異なりうる。**
どの実行環境で確認できたのか、他経路については未確認なのかを、調査結果へ明示的に書き分ける。

**この調査で決めないこと**: Claude Code本体の実装がどうなっているか。観測できるのは
「このリポジトリのこの構成で、その実行環境で、実際に読み込まれたかどうか」までである。

### 調査2: `permissions.allow` / `deny` の前方一致が何に対して行われるか

**問い**: issue本文の「複数行コマンドの1行目にコメントを書くと `permissions.allow` / `deny` の
前方一致が外れる」は正しいか。外れるとしたら、照合対象はコマンド文字列全体の先頭か、
パース後の最初のコマンドか。

**分かっていること**: `.claude/settings.json` の `permissions.deny` には、コミット操作を
prefixパターンで拒否する設定が実在する。したがって「外れる」場合の影響は仮想の話ではない。

**確認方法**:

1. リポジトリ内の既存ドキュメント（`.claude/docs/spec/` `.claude/docs/ddr/` `.claude/rules/`）に
   前方一致の挙動についての記述が無いかを `doc-search` で探す。
2. `.claude/hooks/` 配下で `permissions` の挙動に言及している箇所を確認する。
3. **無害なパターンで実測する**（下記「安全に実機確認する方法」）。

#### hookの `if` の発火実績を根拠に使わない

当初この計画は、`hooks.PostToolUse` の `if` を「同じ書式のパターン」とみなし、その発火実績から
`permissions` の照合を推し量る方針だった。**この手がかりは使わない。**

`.claude/rules/git-workflow.md`「push検知hookの誤検知」は、この `if` について
**前方一致ではなく部分一致**であると実機観測（3件）として記録している。hook側が先頭一致で照合して
いないなら、hookが発火した／しなかったという観測は `permissions.allow` / `deny` の照合が外れるか
どうかの証拠にならない。**`if` と `permissions` は別物として扱う。**

この区別を怠ると、「先頭にコメントがあっても照合される＝1行目コメント禁止の根拠は無い」という、
受け入れ条件4と正反対の結論へ誘導される危険がある。

**さらに、`if` の実挙動そのものが環境で違う可能性がある。** 本セッション（Claude Code on the web）で
push検知hookの `if` パターンを実測したところ、上記の「部分一致」とも食い違う結果が出た（`echo` の
引数に該当語があるだけでは発火せず、1行目がコメントでも発火した）。**片方の環境の観測だけを根拠に
断定しない**。実測値は `reports/` の調査結果へ、環境を明記したうえで両方載せる。

#### 安全に実機確認する方法

危険なのは**既存の `deny` パターン（コミット操作）を対象に試す場合**であって、実機確認そのものが
危険なわけではない。次を試みる。

- ローカル設定（`.claude/settings.local.json`）へ **無害なパターン**（例:
  `Bash(echo arv-probe*)` を `deny` へ）を一時的に置き、
  (a) 1行目が当該コマンド、(b) 1行目がコメントで2行目が当該コマンド、の2通りで挙動が変わるかを見る。
- 実行後は**必ずこのローカル設定を削除し、コミットしない**（`.gitignore` に
  `.claude/settings.local.json` は無いため、放置すると追跡対象になる）。

**限界も先に書いておく**: Claude Codeがセッション途中で設定を再読込しない場合、この実験は効かない。
効かなかったときは「効かなかった」という事実を調査結果へ記録し、推測で埋めない。

**この調査で決めないこと**: 承認プロンプトの表示挙動そのもの（リモート実行環境の権限モードに
依存するため、`allow` 側の検証は行わない）。**裏付けが取れなくても、「1行目にコメントを置かない」
という結論は変わらない**（外れる可能性がある以上、避けるのが妥当）。この調査の成果は
「ルール本文の理由を断定形で書けるか、リスク回避として書くか」の判断材料である。

### 調査3: hook誤検知がコメント本文で発火する範囲

**問い**: コメント行に `git` と `commit` / `push` が連続して現れると、既存hookは実際に発火するか。
`.claude/rules/git-workflow.md` に既にある同趣旨の注意と、新ルールでの再掲をどう書き分けるか。

**分かっていること**:

- `.claude/hooks/block-direct-git-commit.sh` は `tool_input.command` **全体**を正規表現で検査する
  （コメント行を除外していない）。
- `.claude/settings.json` の PostToolUse hook も同じ書式のパターンで発火する。
- **本セッションで実際に発火させた**（flow-id 1-6 でHANDOFF.mdの地の文へdenyパターンを書いた
  ところ、PreToolUse hookがブロックした）。これは再現済みの事実として使える。

**確認方法**:

1. 2つのhookスクリプトの検査ロジックを読み、コメント行が除外されないことをコードで裏付ける。
2. `.claude/rules/git-workflow.md` の既存記述（コミット側・push側の2箇所）を読み、
   **どこまでが既存で、新ルールが何を足すのか**を切り分ける。重複記載はしない方針
   （`.claude/rules/docs-workflow.md` の運用）。

### 調査4: 新規ファイルにするか既存ファイルへ追記するか、および命名

**問い**: 受け入れ条件は「新規ファイル／既存ファイルへの追記のどちらにするかは実装時に判断する」と
している。どちらにするか、新規ならファイル名は何にするか。

**確認方法**:

1. 既存6ファイルのスコープ（`title` / `description` / 冒頭の「適用範囲」節）を一覧化し、
   今回の内容が既存のどれかに収まるかを判定する。
2. `.claude/rules/directory-structure.md` と `.claude/rules/markdown-frontmatter.md` の
   命名・frontmatter規約を確認する。
3. 調査1の結果（自動読込の条件）と突き合わせる。

## 検証

調査そのものの正しさは、以下で確認する。**各コマンドには「何が出れば成功か」を添える。**
「異常が無ければ何も出ない」形の検証は、パターンが実データに合っていないと**常に成功する**ため
（ルート `REVIEW-POINTS.md`「検証コマンドが、異常があるときに本当に検出できるか」）。

```bash
# 調査1: 読み込み対象を指定する設定
# 期待: permissions / plansDirectory / autoCompactWindow / hooks.* のみが出て、
#       rules・instructions 等の読み込み対象を指すキーが1つも無いこと
jq -r 'paths(scalars) as $p | "\($p|join(".")) = \(getpath($p))"' .claude/settings.json

# 調査1: @参照の洗い出し
# 期待: ちょうど2行（CLAUDE.md:11 と GEMINI.md:11。どちらも @./AGENTS.md）。
#       0行なら grep のパターンか対象ファイルが誤っている（空振り）と判断して再実行する
grep -rn '^@' AGENTS.md CLAUDE.md GEMINI.md

# 調査1: SessionStart hookが .claude/rules/ を注入していないこと
# 期待: 0件。ただし 0件は「参照が無い」と「パターンが誤っている」を区別できないため、
#       対にして .claude/hooks/ 全体での件数も出し、grep 自体が機能していることを示す
grep -c 'rules' .claude/hooks/session-start.sh || true
grep -rc 'rules' .claude/hooks/ | grep -v ':0$' || echo '（.claude/hooks/ 配下に rules への参照は無い）'

# 調査1・2: 既存ドキュメントに記録済みの仕様が無いかを横断検索
# `--query` というオプションは存在しない（`error: unknown option` になる）。`--text` を使う。
# 期待: 末尾の `matched=N total=N` を必ず確認する。matched=0 は「無かった」とは限らず、
#       検索語が実データに合っていないだけのこともあるため、語を変えて最低2回試す
bash .claude/scripts/src/search-frontmatter.sh --text 'permissions'
bash .claude/scripts/src/search-frontmatter.sh --text '前方一致'

# ただし `--text` が見るのは frontmatter（title/description/tags/keywords）であって本文ではない。
# 実測では `--text '前方一致'` は matched=3（今回作った plan/worklog のみ）で、本文に記述を持つ
# spec・DDRはヒットしない。**本文中の文字列を探すのは grep の役割**（AGENTS.md の使い分け）。
# 期待: 複数のspec/DDRがヒットすること。0件なら探索語が誤っていると判断して語を変える
grep -rn '前方一致\|部分一致' .claude/docs/ .claude/rules/ --include='*.md'

# 調査3: hookの検査ロジック（コメント行を除外していないこと）
# 期待: block-direct-git-commit.sh 側に、コマンド文字列全体を渡す grep が1件見えること
grep -n 'tool_input.command' -A 6 .claude/hooks/block-direct-git-commit.sh

# 調査4: 既存ルールのスコープ一覧
# 期待: .claude/rules/ の6件＋AGENTS/CLAUDE/GEMINI の計9件（matched=9）
bash .claude/scripts/src/search-frontmatter.sh --type rule
```

結果は `reports/20260820_prancy-prancing-dewdrop_ルール読込条件と前方一致の調査.md`（正文）と
同名 `.html`（視覚化）へ記録する。**この計画ファイルには結果を書かない**
（`.claude/skills/issue-mr-flow/SKILL.md`「計画と実施結果の分離」）。
