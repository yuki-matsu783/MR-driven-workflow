# 【設計】【実装】【テスト】敵対的レビュースキルと専任サブエージェント

全体作業計画: `plans/prancy-herding-kahan.md`（issue #77 / PR #80）
調査結果: `reports/20260819_prancy-herding-kahan_インラインコメント投稿APIとセッション種別判定.md`

## 目的

フェーズ2の調査で技術的制約が確定したため、敵対的レビューの機構一式を実装する。**種別を
`【設計】【実装】【テスト】`で併記する**のは、調査で外部APIの制約（投稿単位・失敗の粒度・
判定材料）が確定しており、設計方針と実装方式・テスト対象を分けて合意する必要が無いため
（テストは純粋関数の切り出し方と表裏一体で、実装と同時に書く）。

あわせて、flow-id 3-3のレビューで追加された要件として、**レビュー観点をスキル本文へ直書きせず、
ディレクトリごとの `REVIEW-POINTS.md` として外だしする仕組み**（成果物4）を含める。観点表が
無いと「何を観るか」が定義できず敵対的レビューが成立しないため、issue #77 から切り離さず
同じMRで実装する（ユーザー確認済み）。

## 調査結果から確定している制約（再掲しない前提の要点のみ）

| 制約 | 実装への影響 |
|---|---|
| GitHubのレビュー投稿は**原子的**（1件でも不正な行があると全件失敗） | 投稿前の行検証が必須。検証は純粋関数へ切り出す |
| 投稿できるのは**diffに現れる行**（hunk内のコンテキスト行を含む） | `patch` のhunkヘッダから有効行集合を算出する |
| **提出済みレビューは削除できない** | 承認は投稿前に1回だけ取る（取り消し前提の設計にしない） |
| GitLabは**1リクエスト1指摘**で巻き添えが無い代わりに、失敗理由を区別できない | 戻り値の形をGitHubと揃え、呼び出し側に差を意識させない |
| GitLabの`position`は`diff_refs`だけで組める。`--input`＋`Content-Type`明示が必須 | `diff_refs`は関数先頭で1回取得。`null`なら数秒待って1回再取得 |
| `AUTOMATION`は自動設定されない（片方向の運用契約） | 未設定は対話モード（＝自律起動禁止）へ倒す |

## 成果物と実装順序

依存関係の順に並べる。**1〜4（純粋関数・スクリプト・観点表の実体）を先に完成させ、テストが
通ってから 5〜7（エージェント・スキル）に着手する。** 逆順にすると、スキル本文が未実装の関数・
未作成の観点表を参照する時間が生じる。

### 1. `Github.sh` — 有効行の算出と投稿

| 関数 | 純粋性 | 内容 |
|---|---|---|
| `github_valid_lines_from_patch <patch文字列>` | **純粋** | hunkヘッダ`@@ -a,b +c,d @@`を読み、新ファイル側の有効行を`c`〜`c+d-1`として列挙する。複数hunkは連結する。空patchなら何も出力しない |
| `github_filter_findings_by_valid_lines <findings JSON> <path→有効行のマップJSON>` | **純粋** | 各findingの`line`が有効行に含まれるかで「投稿する／サマリへ回す」へ振り分ける。**`line`が未指定のfinding（ファイル全体にかかる指摘）は、そのファイルの有効行の最小値へ割り当てる** |
| `github_build_review_payload <投稿するfindings JSON> <サマリ本文>` | **純粋** | `{"event":"COMMENT","body":...,"comments":[{path,line,side,body}]}`を組み立てる |
| `github_add_mr_inline_comments <MR番号> <findings JSONファイル>` | 非純粋 | `pulls/<n>/files`で`patch`を取得 → 上記3つを順に適用 → 一時ファイルへ書いて`gh api ... --input`でPOST |

- **`line`未指定のfindingを有効行の最小値へ寄せる**のは、flow-id 2-9のレビューで決めた方針
  （ファイル全体にかかる指摘をサマリへ埋もれさせない）。新規追加ファイルではhunkが
  `@@ -0,0 +1,N @@`となるため、この値は1行目に一致する。
- `patch`がAPIから省略されたファイル・diffに現れないファイルの指摘は、有効行が空になるため
  自動的にサマリへ回る（特別扱いのコードを書かない）。

### 2. `Gitlab.sh` — position付き投稿と、既存の欠陥修正

| 関数 | 純粋性 | 内容 |
|---|---|---|
| `gitlab_build_discussion_body <finding JSON> <diff_refs JSON>` | **純粋** | 1件ぶんのPOSTボディJSON（`body`＋`position`）を組み立てる。新規行=`new_line`のみ／削除行=`old_line`のみ／コンテキスト行=両方 |
| `gitlab_add_mr_inline_comments <MR番号> <findings JSONファイル>` | 非純粋 | `diff_refs`を1回取得（`null`なら数秒待って1回再取得）し、findingごとに一時ファイルへ書いて`glab api --input`＋`-H "Content-Type: application/json"`でPOST。失敗した指摘は集めて戻り値に含める |
| `gitlab_format_discussion_notes`（**既存の修正**） | **純粋** | `position`から`new_path:new_line`（削除行なら`old_path:old_line`）を組み立てて出力へ含める。positionが無い通常コメントは現状の出力のまま |

`gitlab_format_discussion_notes`の修正は、**GitLab APIの制約ではなくこのリポジトリの実装の
欠陥**（GitHub版は`path:line`を出しているのに揃っていない）であり、flow-id 2-9のレビューで
修正必須と確認済み。

### 3. `Provider.sh` — ディスパッチと実施回数カウンタ

- `add_mr_inline_comments <MR番号> <findings JSONファイル>` を既存関数と同じ形で追加する
  （先頭で`require_vcs_cli add_mr_inline_comments || return 1`、`case "$(get_provider)"`で振り分け）。
- `mcp_tool_hint`に`add_mr_inline_comments`のケースを追加する
  （`mcp__github__pull_request_review_write` → `add_comment_to_pending_review` → `submit_pending`）。
- `.claude/scripts/src/adversarial-review-count.sh` を新規作成する。

  | サブコマンド | 動作 |
  |---|---|
  | `get <phase>` | 現在の実施回数を標準出力へ |
  | `increment <phase>` | 上限（3回）に達していれば**終了コード1と理由メッセージ**、そうでなければ加算して新しい値を出力 |
  | `reset` | 現在のブランチの状態を消す |

  状態は`.claude/state/adversarial-review/<ブランチ名>.json`に`{"2":N,"3":N,"4":N}`で持つ
  （`.claude/state/`は`.gitignore`対象）。**上限判定・状態ファイルのパス組み立ては純粋関数へ
  切り出す**（`adversarial_review_state_path <ブランチ名>` / `adversarial_review_can_run <状態JSON> <phase>`）。

- **findings JSONのスキーマ**（全体作業計画の案から`line`を任意へ変更）:

  ```json
  {"findings":[{"path":".claude/scripts/src/x.sh","line":42,"side":"RIGHT",
    "severity":"major","confidence":"high","category":"shell-pitfall",
    "title":"...","body":"..."}]}
  ```

  `line`・`side`は任意とし、無い場合は「ファイル全体にかかる指摘」として1で述べた寄せ方をする。

### 4. レビュー観点表の外だし（`REVIEW-POINTS.md` ＋ 収集スクリプト ＋ スキル）

flow-id 3-3のレビューで追加された要件。**レビュー観点をスキル本文へ直書きせず、ディレクトリ
ごとの `REVIEW-POINTS.md` として外だしする。** レビュー対象ファイルのあるディレクトリから
プロジェクトルートまでを遡って観点表を集め、1つへマージして使う。

#### 4-a. ファイル規約

**各ディレクトリ直下に `REVIEW-POINTS.md` を置く**（置かないディレクトリがあってよい）。
ルートの `AGENTS.md` / `HANDOFF.md` 等と命名が揃い、リポジトリを見た人が存在に気づける形にする。
適用範囲は**そのディレクトリ配下すべて（孫以下を含む）**。例えば `.claude/REVIEW-POINTS.md` は
`.claude/scripts/src/vcs/Github.sh` のレビューにも効くが、`plans/` 配下には効かない。

現在の構成では次の4つを作る（アプリ本体を追加したら、そのディレクトリにも置けばよい）。

| 配置 | 主な観点（実際の中身は実装時に確定する） |
|---|---|
| `./REVIEW-POINTS.md` | 全体に効くもの。issue番号・spec/DDR以外への恒久参照を書かない、hook誤検知語（`git`＋`commit`/`push` の連続）、日本語での応答 |
| `.claude/REVIEW-POINTS.md` | `.claude/rules/shell-script-style.md` の既知の罠（外部プロセス起動コスト、`jq`の引数長、NULバイトとコマンド置換、`${N:-\{\}}`、CR混入、終了コード検査、日本語の部分文字列）、`.ps1`のBOM、frontmatter規約 |
| `plans/REVIEW-POINTS.md` | 種別`【】`の妥当性、併記/分割の判断、受け入れ条件との対応漏れ、planツールの誤用、issue分割トリガー（並列列挙構造）、**結果を計画へ書いていないか**（issue #87） |
| `reports/REVIEW-POINTS.md` | 自己完結HTMLであること（CDN以外の外部依存が無い）、md版とHTML版の内容が同期していること、point-in-time記録を壊していないこと |

frontmatterは `.claude/rules/markdown-frontmatter.md` に従い、`type: review-points` を新設する
（typeの値の表への追記はフェーズ4の`【AIアセット反映】`で行う）。

#### 4-b. `.claude/scripts/src/collect-review-points.sh`

```bash
bash .claude/scripts/src/collect-review-points.sh <ファイルパス...>
```

- 各ファイルのディレクトリから**リポジトリルートまで祖先を遡り**、存在する `REVIEW-POINTS.md`
  を集める。複数ファイルを渡した場合は各チェーンの**和集合**を取り、同じ観点表は1回だけ出す。
- 出力順は**ルート → 深い方**（一般 → 具体）。由来が分かるよう
  `## <ディレクトリパス>/REVIEW-POINTS.md` の見出しを挟んで連結する。
- 観点表が1つも見つからなければ**何も出力せず終了コード0**（観点表が無くてもレビューは行える）。
- 純粋関数 `review_points_ancestor_dirs <ファイルパス>` を切り出す（ルート順の祖先ディレクトリ列を
  返す）。**リポジトリルートより上へ出ない**こと、日本語を含むパスを壊さないことを単体テストで担保する。
- ループ内で外部コマンドを起動しない（`${p%/*}` でディレクトリを辿る。
  `.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」）。

#### 4-c. `.claude/skills/review-points/SKILL.md`

観点表を収集してレビューへ適用するための独立スキル。**敵対的レビュー専用にしない**
（人間のレビュー・組み込み `/code-review` の補助としても使えるようにする）。手順は
「レビュー対象ファイルを列挙 → `collect-review-points.sh` へ渡す → 得られた観点を順に適用し、
観点ごとに該当箇所の有無を判断する」。観点表が空だった場合の振る舞い（一般的な観点のみで
レビューする）も明記する。

### 5. `.claude/agents/adversarial-reviewer.md`

`issue-mr-resume.md`と同じfrontmatter形式（`name`/`description`/`tools`/`model` ＋
`.claude/rules/markdown-frontmatter.md`のキー）に従う。

- `tools: Read, Grep, Glob, Bash`（**読み取り専用**）。findings JSONを返すだけで投稿は行わない。
- `model: opus`。
- **渡すのはdiff・ファイルパス・マージ済みのレビュー観点表だけ**とし、「なぜそう実装したか」の
  経緯は渡さない（実装者の文脈に引きずられると敵対的レビューにならないため）。観点表は
  呼び出し元（スキル）が `collect-review-points.sh` で集めたものを渡す。サブエージェント側から
  観点表を探しに行かせない（対象範囲の判断を1箇所へ寄せるため）。
- 出力は上記スキーマのJSONに限定し、**確度（`confidence`）を必ず自己申告させる**。

### 6. `.claude/skills/adversarial-review/SKILL.md`

- **手順1＝実行モードの判定**（他のどの手順よりも先・スキップ不可）。
  `echo "AUTOMATION=${AUTOMATION:-unset}"`が`1`なら非対話モード、それ以外は対話モード。
- **起動ポリシーを絶対ルールとして書く**: 対話セッションではAIから自律起動しない
  （人間が`/adversarial-review`を呼んだときのみ）。非対話セッションでのみ自律起動を許す。
- **手順2＝実施回数の確認**。当該フェーズで既に3回実施済みならレビューを実行せず打ち切り、
  その事実を報告して`HANDOFF.md`にも残す。カウンタ更新は**投稿の成否に関わらずレビュー実行の
  直後**に行う（失敗を口実に無限リトライできないようにする）。
- **承認モデル**: 起動時に`AskUserQuestion`で投稿可否を1回だけ確認し、承認後は指摘ごとの個別
  承認を求めない（提出済みレビューは削除できないため、承認は投稿前に集約する）。
- **手順3＝レビュー対象の判別と観点表の収集**。対象（diff全体／`plans/`の個別計画／設計反映）は
  現在のflow-idから自動判別し、曖昧なら選択させる（非対話モードの既定は「diff全体」）。
  **観点の中身はこのSKILL.mdへ書かず、対象ファイル群を`collect-review-points.sh`へ渡して
  `REVIEW-POINTS.md`から集める**（成果物4）。SKILL.mdが持つのは「対象の決め方」と「観点表の
  集め方」だけにする。
- **冒頭に組み込み`/code-review`との棲み分け**を明記する。
- **MCP経路の読み替え**を節として持たせる（`create`→全件追加→必ず`submit_pending`まで実行し、
  途中で失敗したら`delete_pending`で片付ける）。

### 7. `issue-mr-flow/SKILL.md` への追記

全体フロー表は変えず、「敵対的レビューの位置づけ」節を追加する（push直後・人間レビュー前という
位置づけと、対話セッションでの自律起動禁止）。**挿入位置は直前の節の地の文の係り先を壊さない
場所を選ぶ**（`.claude/rules/docs-workflow.md`の注意。issue #64の実例では`## サブコマンド`の直前へ
回した）。挿入後は前後3行を目視で確認する。

## テスト

`Github.sh`/`Gitlab.sh`/`Provider.sh` の純粋関数は `.claude/scripts/test/test_vcs_provider.sh`
へケースを追加する（既存の`gitlab_format_discussion_notes`のテストと同じ形。
`passed=N failures=N`規約）。新設スクリプトの純粋関数は同じファイルへ混ぜず、対象スクリプトごとに
`.claude/scripts/test/test_adversarial_review_count.sh` と
`.claude/scripts/test/test_collect_review_points.sh` を新設する。

| 対象 | ケース |
|---|---|
| `github_valid_lines_from_patch` | 単一hunk／複数hunk／新規ファイル（`@@ -0,0 +1,N @@`）／空patch |
| `github_filter_findings_by_valid_lines` | findings 0件／全件が有効行外（＝投稿0件）／`line`未指定→最小値へ寄る／diffに無いパス→サマリ行き |
| `github_build_review_payload` | 投稿0件のときも`body`だけのレビューになること／`path`にマルチバイト文字 |
| `gitlab_build_discussion_body` | 新規行／削除行／コンテキスト行の3ケース |
| `gitlab_format_discussion_notes` | **position付き→`path:line`が出る**／position無し（通常コメント）→従来どおり／resolved除外の既存挙動が壊れていないこと |
| `adversarial_review_can_run` | 0回・2回→可／3回→不可／状態ファイルが壊れている→「状態なし」へフォールバック |
| `review_points_ancestor_dirs` | ルート直下のファイル／深いパス（`.claude/scripts/src/vcs/x.sh`）／**リポジトリルートより上へ出ない**こと／日本語を含むパス |
| `collect-review-points.sh` | 観点表が1つも無い→無出力・終了コード0／複数ファイルで祖先チェーンが重なる→同じ観点表を1回だけ出す／出力順がルート→深い方 |

## この計画で決めないこと（スコープ外）

- **レビュー観点の網羅性の追求**。`REVIEW-POINTS.md` は既存ルール（`.claude/rules/`）から
  現時点で分かっているものを書き出すに留め、運用しながら育てる前提とする。
- **`REVIEW-POINTS.md` を置くディレクトリの拡張**。今回はルート・`.claude/`・`plans/`・`reports/`
  の4つのみ。アプリ本体を追加した際の配置は、そのとき判断する。
- 敵対的レビューの結果でマージをブロックする仕組み（CI連携等）は作らない。
- スレッドの解決（resolve）操作は行わない（レビュアー側の操作という既存方針を踏襲）。
- spec・DDRへの反映はフェーズ4（`【設計反映】`）で行う。本計画では実装とテストまで。
