# 全体作業計画: issue #47

- issue: [#47 AIが実行する複数行コマンドに日本語コメントを必須とするルールを追加する](https://github.com/yuki-matsu783/MR-driven-workflow/issues/47)
- PR: [#132](https://github.com/yuki-matsu783/MR-driven-workflow/pull/132)（Draft）
- ブランチ: `claude/multiline-command-japanese-comments-k8c2pr`

## Context（なぜこの変更をするか）

AIエージェントがBash/PowerShellツールへ渡すコマンドは、ユーザーが承認前に読む唯一の材料である。
ところが説明を載せられるはずの `description` パラメータは**コンソール上に1行しか表示されない**
（issue起票時に実機確認）。そのため複数行コマンドでは、各ブロックが何をしているかを
`description` では表現できず、ユーザーはコマンド文字列そのものを読み解くしかない。

一方、AIがツールへ渡す**コマンド文字列そのもの**に関する規約は `.claude/rules/` に存在しない。
`.claude/rules/shell-script-style.md` は `.sh` ファイルとして保存するスクリプトの規約であり、
スコープが異なる（issue本文も同じ整理をしている）。

この空白を埋め、「承認前にコマンドの意図が読み取れる」状態を規約として定める。出力トークンは
増えるが、意図しないコマンドを承認してしまうリスクの低減を優先する。**まずは試行的に運用し、
運用感が悪ければ見直す**前提とする（このトレードオフ自体をDDRへ残す）。

## ブランチ運用に関する注記

このリポジトリの規約（`.mrworkflow.json` の `branchPrefixTemplate`）では `feature-47-<slug>` だが、
本作業はハーネス（Claude Code on the web）が指定したブランチ `claude/multiline-command-japanese-comments-k8c2pr`
で進める。ハーネスのシステムプロンプトが「指定ブランチ以外へpushしない」と定めており、そちらが
優先されるため。フロー上の他の手順は通常どおり適用する。

## issue分割の判定

**分割しない。** issue本文の受け入れ条件は7項目あるが、いずれも「1つのルール文書に何を書くか」の
内訳であり、同型の成果物（画面・エンドポイント・サブコマンド等）が並列に列挙された構造ではない。
「各項目が単独でマージされても壊れないか」を問うと、ルール文書は分割してマージする意味がなく、
むしろ1ファイルの中で相互参照する内容である。フローの固定費（5フェーズ41ステップ）を考えても
分割コストが本体を上回る。

## フェーズ2〈調査〉

このルールは「〜だから、こう書け」という**根拠つきの規約**であり、根拠が事実でなければルール自体が
無効になる。受け入れ条件も根拠の明記を求めている。したがって、ルール本文が依拠する事実を先に
確定させる。

調査項目は以下（詳細は flow-id 2-1 の個別調査計画で確定する）。

1. **`.claude/rules/` 配下の新規ファイルが、セッション開始時に自動でコンテキストへ読み込まれる
   条件**（受け入れ条件1に直結）。現時点で分かっているのは、6ファイル中 `alwaysApply: true` を
   持つのは3ファイルだけなのに、本セッションでは6ファイルすべてが読み込まれているという事実。
   `alwaysApply` が読み込みの条件なのか、ディレクトリ単位で読まれているのかを切り分ける
   （`AGENTS.md` / `CLAUDE.md` は `.claude/rules/*.md` を `@import` していないことは確認済み）。
2. **「複数行コマンドの1行目にコメントを書くと `permissions.allow` / `deny` の前方一致が外れる」
   という主張の裏付け**。`.claude/settings.json` は実際に `deny: ["Bash(git commit*)"]` を持つ。
   前方一致が何に対して行われるか（コマンド文字列の先頭か、パース後の最初のコマンドか）を
   確認し、**確認できた範囲と、推測に留まる範囲を分けて記述できる状態にする**。裏付けが取れない
   場合でも「先頭にコメントを置かない」という結論自体は変わらない（リスク回避として妥当）ため、
   ルール本文の理由の書き方を調整する形で扱う。
3. **hook誤検知（`git`＋`commit`/`push` の連続）が、コメント本文で実際に発火するか**の確認。
   `.claude/hooks/block-direct-git-commit.sh` は `tool_input.command` 全体を
   `grep -qiE 'git[[:space:]]+commit'` で検査しており、コメント行も対象に入ることはコードから
   読み取れる。既存ルール（`.claude/rules/git-workflow.md`）との記述の重複をどう避けるかを含めて
   整理する。
4. **新規ファイルにするか既存ファイルへ追記するか**の判断材料。既存6ファイルのスコープ・粒度・
   frontmatterの書き方を確認し、命名（`.claude/rules/<名前>.md`）を決める。

調査結果は `reports/日付_prancy-prancing-dewdrop_<内容>.md`（正文）と同名 `.html`（視覚化）へ記録する。

**省略の判断は flow-id 2-1 で行う**（現時点では上記1・2に未確定事項があるため、実施する見込み）。

## フェーズ3〈作業〉

調査結果をもとに、次の2つを作る。

1. **ルール本文**: `.claude/rules/` 配下（新規ファイルを想定。命名はフェーズ2で確定）。
   受け入れ条件が求める要素をすべて含める。
   - 根拠: `description` はコンソール上1行しか表示されない（実機確認の事実として明記）
   - 説明の置き場所の表（1行コマンド / 複数行コマンド / 複雑すぎる場合は `.sh` へ切り出し）
   - 言語（日本語）・文体（敬語・助詞・無駄な装飾なし、単語と短文）と**良い例／悪い例**
   - 複数行コマンドの1行目にコメントを書かない理由と**良い例／悪い例**
   - hook誤検知（`git` と `commit` / `push` を連続させない）への注意をコメント記述の文脈で再掲
   - `.claude/rules/shell-script-style.md` との**スコープの違いを冒頭で明示**し、相互リンクする
   - `.claude/rules/markdown-frontmatter.md` に沿ったfrontmatterを付ける
2. **DDR**: `.claude/docs/ddr/00NN-<タイトル>.md`（現時点の空き番号は 0059。`main` が進めば
   flow-id 5-1 / 追従監視で繰り下げる）。記録する判断は4つ。
   - `description` の1行制約を前提に、説明の置き場所をコマンド内コメントへ寄せたこと
   - 出力トークン増よりも承認前の安全性を優先したトレードオフ（試行的運用である旨を含む）
   - 1行コマンドを対象外とした理由（`#` が行末までを飲むリスクだけが残り、得るものが無い）
   - 1行目コメントを禁止した理由（前方一致が外れる）

**検証**: ルール本文の良い例／悪い例が受け入れ条件7項目をすべて満たすか、逐条で突き合わせる。
frontmatterは `bash .claude/scripts/src/extract-frontmatter.sh .` を通し、`index.jsonl` へ
正しく載ることを確認する。
