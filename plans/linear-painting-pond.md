# 全体作業計画: issue #143 — docs-workflow.mdの`reports/`行flow-id矛盾の解消確認と再発防止策の検討

## Context（背景・目的）

issue #143は「`.claude/rules/docs-workflow.md`の`reports/…md` `reports/…html`行の『運用』欄が
flow-id 5-1（片付けの意味）のままで、同じ行の『寿命』欄・表直後の段落（flow-id 5-3）と矛盾している」
という問題を報告している。issue #112のフェーズ5並べ替えに`reports/`行だけが追従できなかったことが
原因。受け入れ条件は次の4点。

- [ ] `reports/…md` / `reports/…html` 行の運用欄がflow-id 5-3（もしくは現在正しい番号）を指す
- [ ] 「片付け＝flow-id 5-1」と読める現行記述が他に残っていない
- [ ] `.claude/docs/spec/` `.claude/docs/ddr/`の過去changelogを変更しない
- [ ] **再発防止策の要否を検討し、結論を記録する**

## 事前調査で判明した事実（重要）

Exploreエージェントによる調査の結果、以下が判明した（詳細は`reports/`のフェーズ2調査結果として
正式にまとめる）。

1. **issueが報告した矛盾は既に解消済み。** issue #143とは無関係の **PR #144**（issue #111「最終統括
   レポート」対応、commit `e33b468`、2026-08-21マージ）が、flow-id 5-3（統括レポート）の新設に伴う
   フェーズ5全体の繰り下げ作業の中で、`docs-workflow.md`の該当箇所を一括で`5-1`→`5-4`、`5-3`→`5-4`
   へ書き換えていた。現在のブランチ（`origin/main`と差分なし）で確認した限り、`reports/`行を含む
   全ての「片付け」言及はflow-id 5-4に統一されており、SKILL.mdの現行テーブル（5-4=片付け）とも一致
   している。「flow-id 5-1」「flow-id 5-3」を片付けの意味で使う現行記述は残っていない。
2. **再発防止の機構的な検知手段は存在しない。** `.claude/scripts/src/` `.claude/hooks/`配下を確認したが、
   `docs-workflow.md`・`SKILL.md`内の「flow-id N-M」参照を横断的に洗い出し・検証するスクリプト/CI/hookは
   無い。`update-handoff-progress.sh`はHANDOFF.mdの進捗記号操作専用で対象外。
3. **過去のDDR `i0112-01`（フェーズ5並べ替え）は、機械的検知の仕組みを作る方向ではなく「変更範囲を
   最小化する」方向で対処してきた**（却下案として明記）。今回のissue #143は、まさにその方針のもとで
   実際に追従漏れが起きた実例である。
4. 同型の食い違いに対応した**issue #51ではDDRを作らず**、`.claude/docs/spec/issue-mr-workflow.md`の
   changelog節のみで対応していた（SKILL.mdを正として他ファイルを揃えるという是正のみ。新しい意思決定
   ではないと判断された）。

## 全体方針

矛盾自体は既に解消済みのため、**このタスクの実質的な成果物は「解消済みであることの確認記録」と
「再発防止策の検討結果」**になる。再発防止策は、機械的検知の新設ではなく、flow-id並べ替え作業を行う
際の手順をドキュメント側へ明記する方向で検討する（機械的検知はコスト対効果が悪いというDDR i0112-01の
既存判断を踏襲しつつ、今回実際に追従漏れが起きた事実を踏まえて手順面での軽い予防策を追加する案）。
最終的な採否はフェーズ3の設計段階で複数案を比較して決める。

### フェーズ2〈調査〉

- 個別調査計画`plans/【調査】〜.md`を作成し、Exploreエージェントの調査結果を裏付けとして正式な
  調査結果`reports/…_調査.md`へまとめる。
- 調査内容: (a) 現状のdocs-workflow.md/SKILL.mdに矛盾が残っていないことの最終確認、(b) 再発防止策の
  選択肢の整理（機械的検知案・手順明記案・現状維持案の比較）。

### フェーズ3〈作業〉

- 【設計】再発防止策の方針を決定する（有力案: 機械的検知スクリプトの新設は見送り、flow-idの並べ替え
  作業を行う際に「関連ファイル内の`flow-id N-M`参照を横断grepし、新しい意味と一致するか確認する」旨の
  手順注意を`SKILL.md`または`docs-workflow.md`へ追記する）。
- 【実装】決定した方針に沿ってドキュメントへ手順を追記する。矛盾自体は解消済みのため、コード変更は
  発生しない見込み（ドキュメントのみの変更）。

### フェーズ4〈反映〉

- 反映対象を洗い出す。有力候補: 再発防止策の意思決定を新規DDR（`i0143-01`）として記録し、
  `.claude/docs/README.md`のDDR一覧を`generate-ddr-list.sh`で再生成する。
- 反映対象が実装コード・テストに及ばない（ドキュメントのみ）と判明すれば、その旨を明記してフェーズ4を
  完了とする。

## 各フェーズでの敵対的レビュー実施方針（ユーザー指示）

ユーザーからの指示により、**各フェーズの計画作成時（2-1/3-1/4-1相当）に1回・各フェーズの作業実施後
（2-6/3-6/4-6相当のcommit・push後）に1回**、`.claude/skills/adversarial-review/SKILL.md`による敵対的
レビューを自動実施する。実施は非対話セッション（Claude Code on the webのリモート実行環境で人間の
レビュー往復を待てない）という既存の例外条件、および今回のユーザーからの明示指示の両方に基づく。
回数上限は各フェーズ最大3回（`.claude/scripts/src/adversarial-review-count.sh`が機械的に強制）。
指摘は投稿のみで完結させず、対応または対応しない理由を`reply`で返信してから次のステップへ進む。

## 検討した代替案

- **案A: 機械的な整合性チェックスクリプトを新設する**（flow-id文字列を横断grepしSKILL.mdのテーブルと
  突合）→ 現時点では却下候補。自然言語の文脈（「片付け」の意味で使われているか等）の判定が必要で、
  単純な数値範囲チェックでは今回のような「存在するが古い番号」を検知できない。DDR i0112-01の既存判断
  とも整合しない。ただしフェーズ3の設計段階で再検討はする。
- **案B: 何もしない（現状維持）** → 却下。issueの受け入れ条件が「再発防止策の要否を検討し記録する」
  ことを明示的に求めており、検討自体を省略できない。
- **案C（現時点の有力案）: 機械的検知は見送り、flow-id並べ替え時の確認手順をSKILL.mdへ明記し、
  意思決定をDDRとして記録する** → フェーズ3で詳細設計する。

## 検証方法

- `grep -rn "flow-id 5-1\|flow-id 5-3" .claude/rules/docs-workflow.md`等で、片付けの意味を持つ古い
  flow-id記述が残っていないことを確認する（changelog/DDR本文は対象外）。
- 新規DDRを追加した場合は`bash .claude/scripts/src/generate-ddr-list.sh`を実行しDDR一覧の差分を確認する。
- 追記したドキュメントに構文・リンク切れが無いことを目視確認する。
