# 【実装】【テスト】ベースブランチ追従確認の検知スクリプトとフローへの組み込み（issue #67）

- 全体作業計画: `plans/base-branch-sync-check.md`
- 調査結果（正文）: `reports/20260819_base-branch-sync-check_調査結果.md`

**種別を併記する理由**: テストは検知スクリプトと同時に書き、1回のレビューでまとめて合意を取る
（分けても合意の単位が変わらず、記述が重複するだけのため）。

## 目的

作業を開始・再開する時点で「ベースブランチの最新を取り込めているか」を機械的に検知し、
遅れがあればユーザーの承認を得てから取り込む、という流れをフローへ組み込む。

## 1. `check-base-sync.sh` の仕様

### 入出力

```
check-base-sync.sh [--base <branch>] [--head <ref>] [--no-fetch]
```

`check-base-conflicts.sh` と同じ引数・同じ規約にそろえる（引数名・fetchの既定・出力JSON1つ・
検査が完了すれば終了コード0）。

```json
{
  "base": "main", "baseRef": "origin/main", "baseSha": "...",
  "headRef": "HEAD", "headSha": "...", "mergeBase": "..." ,
  "behind": 4, "ahead": 1,
  "changedFiles": ["..."], "changedFilesTotal": 4, "changedFilesTruncated": false,
  "hasCommonHistory": true, "isShallow": true,
  "isBehind": true
}
```

| キー | 意味 |
|---|---|
| `behind` | ベース側にあって作業ブランチに無いコミット数 |
| `ahead` | 作業ブランチ側にあってベースに無いコミット数（遅れの判定には使わない。誤解防止のため返す） |
| `changedFiles` | **未取り込みの**変更ファイル（3点リーダで取る）。先頭50件まで |
| `changedFilesTotal` | 切り詰め前の全件数 |
| `hasCommonHistory` | merge-base が取れたか。偽なら `changedFiles` は空 |
| `isShallow` | `git rev-parse --is-shallow-repository` の結果 |
| `isBehind` | `behind > 0`。呼び出し側はこれを見る |

### 処理順（調査で確定した順序。入れ替えない）

1. 引数と `.mrworkflow.json` から `base` を決める（`check-base-conflicts.sh` と同じjq1回の読み方）。
2. `--no-fetch` でなければ `git fetch origin "$base"`（失敗しても止めない）。
3. `git rev-parse --verify --quiet "origin/$base"` で参照の存在を確認する。**無ければ終了コード1**。
   メッセージには復旧コマンド `git fetch origin '<base>:refs/remotes/origin/<base>'` を含める
   （single-branch cloneで参照が作られないケースの実測に基づく）。
4. `git rev-list --left-right --count "origin/$base...$head"` で `behind<TAB>ahead` を取る。
5. `git merge-base "$head" "origin/$base"` の**成否を先に見る**。
   - 成功 → 3点リーダ `git diff --name-only "$head...origin/$base"` で変更ファイルを取る。
   - 失敗 → `hasCommonHistory: false`、`changedFiles: []`。**3点diffを実行しない**
     （実行すると `fatal: no merge base` で終了コード128になり、`set -euo pipefail` 配下で
     スクリプトごと落ちる）。
6. jq 1回でJSONを組み立て、`tr -d '\r'` を通して出力する。可変長のファイル一覧は
   `--arg`/`--argjson` ではなく**標準入力**から渡す。

### 切り出す純粋関数（テスト対象）

| 関数 | 責務 |
|---|---|
| `parse_left_right_to_reply <出力>` | `"4\t1"` を `behind` / `ahead` へ分解して `REPLY_BEHIND` / `REPLY_AHEAD` へ返す。TAB以外の空白・空文字列・数値でない入力を弾く |
| `truncate_file_list <改行区切り> <上限>` | 先頭N件へ切り詰めた一覧をstdoutへ、全件数を `REPLY_TOTAL` へ返す |

どちらもgitを呼ばず、入力→出力だけで検証できる。`BASH_SOURCE` ガードで `main` と分離し、
テストから `source` できるようにする（`check-base-conflicts.sh` と同じ形）。

### やらないこと

- **マージ・リベースの実行**。このスクリプトは検知だけを行い、作業ツリーを変更しない。
- `check-base-conflicts.sh` の責務（衝突の検知）を取り込むこと。判定軸が違うため分けたままにする。

## 2. 単体テストの観点

`.claude/scripts/test/test_check_base_sync.sh`（`passed=N failures=N` を出力し、失敗時は終了コード1）。

| 対象 | ケース |
|---|---|
| `parse_left_right_to_reply` | 通常（`4\t1`）／両方0／空文字列（失敗を返す）／TABが無い（失敗）／数値でない（失敗）／大きな値 |
| `truncate_file_list` | 0件／1件／上限ちょうど／上限+1件（切り詰めと全件数）／**日本語を含むパス**／末尾に空行がある入力 |

**終了コードの検査に `"$(func; echo $?)"` の形を使わない**（`set -e` 配下でサブシェルが `echo` へ
到達しないことがある。`.claude/rules/shell-script-style.md`「テスト」）。`if func; then` で受ける。

## 3. SKILL.md への組み込み

**新節「作業開始・再開時のベースブランチ追従確認」**を追加する。flow-idは**増やさない**
（issue #88 の「PR作成後のdefaultブランチ追従（監視）」と同じく、特定のflow-idに属さない
並行手順として定義する）。節に書くこと:

1. **いつ行うか**: `start`（既存ブランチを検出したとき）・`resume`・`sync` の3地点。
   新規ブランチ作成時は `<base_branch>` から切るため不要。
2. **どう検知するか**: `bash .claude/scripts/src/check-base-sync.sh` を実行し `isBehind` を見る。
3. **遅れがあったら**: **`AskUserQuestion` で確認し、承認を得るまで取り込まない**
   （受け入れ条件3に対応）。選択肢は次の3つ。
   - `main を merge して取り込む (Recommended)`
   - `今は取り込まない`
   - `rebase で取り込む`（このリポジトリは `resolve-conflict` スキルで rebase を使わない方針の
     ため非推奨である旨を添える）
4. **issue #46・#88 との役割の違い**（受け入れ条件5に対応）。調査結果の表をそのまま使う。
5. **注意**: `isShallow` が真かつ `behind` が0のときは、判定が過小評価である可能性がある。

**挿入位置**: 「PR作成後のdefaultブランチ追従（監視）」節の**直前**へ置く。時系列（作業開始 →
PR作成後 → マージ直前）の順に3つの節が並ぶ形になる。挿入位置の直前の節が「節全体にかかる
地の文」で終わっていないかを、挿入後に前後3行で目視確認する
（`.claude/rules/docs-workflow.md`）。

## 4. `issue-mr-resume.md` への組み込み

- 手順を1つ追加し、`check-base-sync.sh` を実行して `behind` と `changedFiles` を取る。
- 現在地サマリのフォーマットへ `- ベースブランチとの差分:` を追加する（受け入れ条件2）。
- **「読み取り専用」の規定と `git fetch` の関係を1行明記する**。`git fetch` はリモートから
  読むだけで作業ツリー・ローカルブランチを変更しないため、この規定に反しない
  （調査で `git fetch` が同エージェントに1つも無いことを確認済み）。

## 検証

```bash
bash -n .claude/scripts/src/check-base-sync.sh
bash -n .claude/scripts/test/test_check_base_sync.sh
bash .claude/scripts/test/test_check_base_sync.sh          # passed=N failures=0
bash .claude/scripts/src/check-base-sync.sh | jq .          # 実リポジトリで1回流す
bash .claude/scripts/src/check-base-sync.sh --no-fetch | jq -c '{behind,ahead,isBehind}'
bash .claude/scripts/src/check-base-sync.sh --base nonexistent; echo "終了コード=$?"   # 1になること
```

境界条件（merge-base無し・shallow・single-branch）は、調査フェーズと同じく**使い捨ての別
リポジトリ**をスクリプトファイル経由で作って確認し、確認後に削除する。
