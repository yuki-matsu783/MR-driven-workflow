方針

スクリプト harvest-from-projects.sh

  • 読み取り専用: 本家・配布先のワークツリーを変更しない。書き込みは mktemp -d の一時領域のみ。git 操作は show / cat-file / ls-files / log / rev-list / rev-parse（gitリポジトリ判定） / merge-file -p に限る（いずれも読み取り専用。add/commit/checkout/clean/stash 等の書き込み系は使わない）。
bash harvest-from-projects.sh [--upstream <dir>] scan <配布先パス>...
bash harvest-from-projects.sh [--upstream <dir>] diff <配布先パス> <相対パス>
bash harvest-from-projects.sh [--upstream <dir>] merge3 <配布先パス> <相対パス>
  • scan: 配布先ごとに manifest を読み、core/merge の modified / added / deleted と衝突有無・判断材料を JSON 1つで返す（複数配布先を一度に受け取る）。manifest 無しは degraded: true で2-way差分一覧へ縮退。配布先単位のエラー隔離: 1件が読めなくても全体を中断せず、error レコードを返して次へ進む。manifest は [ -s ]（空でない）→jq -e .（有効JSON）の順で検証し、無効なら縮退へフォールバック。
  • diff: 2-way差分（本家HEAD vs 配布先現在。LF正規化後）。
  • merge3: 3-wayマージ結果（3入力ともLF正規化）。終了コードは意味ごとに正規化して返す: 0=衝突なし／1=衝突あり／2=base取得不可で縮退／3=その他エラー／4=3-way の対象外（git merge-file 自体は 0／1〜127=衝突数／≧128=エラー（実測255）の3分岐で解釈。衝突数を露出させないのは縮退・エラーの信号と数値域が重なるため。2 と 4 を分けるのは呼び出し元が stderr の文言に頼らずメッセージを選べるようにするため）。merge 層と dist-layers.json は対象外＝exit 4（前者は base が本家のどのコミットにも無い、後者は del(.upstream) 済みで配布されるため。2-way比較では本家側へ del(.upstream) を掛ける）。
  • --upstream: テストが合成本家を差し込むための上書き（既定はスクリプト位置から導出）。
  • scan の JSON 形（トップレベルは {"schemaVersion":1,"targets":[...]}。読めない配布先は {"path":..., "error":...}）:
{ "schemaVersion": 1, "targets": [
  { "path": "/abs/dest", "manifestExists": true, "degraded": false,
    "sourceCommit": "abc123", "sourceCommitDirty": false,
    "baseResolvable": true, "baseApproximate": false,
    "files": [
      { "path": ".claude/rules/x.md", "layer": "core", "status": "modified",
        "conflict": "clean|conflict|unknown",
        "aiAssetCommits": 2, "changeCount": 5,
        "upstreamHasPath": true, "upstreamDeleted": false }
    ] }
] }
  • status: modified/added/deleted。modified の比較は層・strategy 別——core=LF正規化sha256・merge/lines-marker=LF正規化後の全体sha256（記録側 merge_fingerprint_json と同一の式。正規化しないとCRLF配布先で常にmodified）・merge/json-keys=キーごとの jq -c getpath 出力のsha256（こちらだけ正規化なし）。deleted は core/merge に限る。added は自前の pathspec 照合（完全一致＋ディレクトリ前方一致・後勝ち。build_plan の git ls-files 展開は本家に無いパスへ適用できない）で core に解決され、gitignorePattern を持つ local エントリ9件との照合でも除外されないパスに限定。除外の正は配布先の dist-layers.json の1つだけ（層解決・パターン照合とも配布先へ配布された定義を読む。パターン照合は gitignore 規則のサブセットの自前実装のみで、git check-ignore は使わない——参照データが違い「正が2つ」になるため）。機構自身の生成物（.claude/.asset-manifest.json 自身・*.bak）も added から明示的に除外。
  • upstreamHasPath / upstreamDeleted: added・deleted の両方に持たせる。upstreamDeleted は本家の git log --diff-filter=D の削除履歴の有無（「配布先の新規追加」と「本家の削除漏れ」の区別材料）。deleted のうち本家HEADにも無いものは「本家でも削除済み（収穫対象外）」の別枠にする（SCAN_CORE_REMOVED の案内に従って手で消した配布先を毎回候補に出さない）。
  • conflict: clean/conflict/unknown（core 層かつ base 解決可のときだけ算出。merge 層は 3-way 対象外のため常に unknown）。記録SHAが -dirty 付きなら、-dirty を落として解決を試み、解決できれば 3-way を実行して conflict を算出したうえで baseApproximate: true を立てる（一律 unknown にすると --allow-dirty 配布の配布先で衝突区別が丸ごと死ぬ。調査結果 Q3 の縮退順序1）。SHA が真に未到達のときだけ baseResolvable=false・conflict=unknown。
  • 縮退時（degraded）の files[] は別の形: status: "differs" 固定・conflict キーを出さない（確定分類と区別する）。
  • 判断材料: aiAssetCommits・changeCount。非gitリポジトリは null（0や空への縮退は「改善なし」と誤読されるため不可）。aiAssetCommits の0件は「改善なし」と読ませない——commitスキルは .claude/scripts/ を ai-asset 対象外にしている。merge 層は記録済み指紋との比較で modified 判定（読む側の初実装）。
  • 実装規約: set -euo pipefail・jq をループ内で起動しない・git の起動もファイル数に比例させない（git bash では約95ms/回。判断材料は git log --name-only を配布先ごと1回で取得しファイル別に集計、内容取得は git cat-file --batch を1プロセスで使い回し、merge-file は「core かつ modified」と確定した件数だけ、縮退モードの全件比較も cat-file --batch＋sha256sum 一括）・main ガードで source 可能にし純粋関数（pathspec照合の層解決・gitignoreパターン照合・分類・-dirty 除去・LF正規化比較）を単体テスト可能にする。

SKILL.md（AIエージェントの手順）

  1. 配布先パス（複数可）を受け取り scan を実行。
  2. 結果を層・分類・衝突・判断材料つきで提示（プロジェクト固有語の判定は AI が diff を読んで行う）。
  3. AskUserQuestion で取り込む差分を選択。
  4. AskUserQuestion で出口レベルを確認（a. issue起票のみ／b. 起票＋個別作業計画の草案）。
  5. 差分ごとに issue 本文（4見出し）を組み立て、issue-create スキルの手順で起票（重複チェック込み。CLI不在時はMCPフォールバック）。
  6. レベル b は草案をセッションの scratchpad へ書きパスを提示して停止（本家の plans/ へは置かない）。
  7. どのレベルでも本家の正史（rules/skills/docs）を直接編集しない（「してはいけないこと」で明文化）。
