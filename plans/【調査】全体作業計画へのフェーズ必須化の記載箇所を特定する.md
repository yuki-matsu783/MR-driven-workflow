# 【調査】全体作業計画へのフェーズ必須化の記載箇所を特定する

## 調査の目的

issue #92 のルール（全体作業計画には調査・反映のフェーズを必ず含める／事前調査は軽めでよい／
反映は枠だけ置く）を、**どのファイルのどの位置に、既存記述と矛盾しない形で書けるか**を確定する。

本格的な設計判断（文言そのもの）はフェーズ3で行う。ここでは「現状どう書かれているか」と
「差し込み位置の制約」だけを確認する。

## 調査項目

| # | 調べること | 確認の手段 |
|---|---|---|
| 1 | SKILL.md の flow-id 1-4 と「計画の2階層構造」節が、全体作業計画の**中身**を規定しているか | 該当節の読み取り |
| 2 | `docs-workflow.md` の `[-]` の説明が「いつ決めてよいか」を規定しているか | 該当段落の読み取り |
| 3 | 新しい見出しの差し込み位置の候補と、docs-workflow.md の差し込みルールへの適合 | 前後の節末尾の読み取り |
| 4 | 既存記述との矛盾（特に「フェーズ1,4,5は必ず実施する」の一文） | 全体フロー節の読み取り |
| 5 | 反映先（spec・DDR番号・README）の現状 | `ls .claude/docs/ddr/`、spec の `## 影響範囲` 末尾 |

## 調査結果

### 1. 全体作業計画の「中身」に関する規定は無い

- SKILL.md flow-id 1-4 の行が規定しているのは「planツールで作ること」「出力先」「既にあれば
  新規作成しないこと」「issue分割の判定を先に行うこと」の4点のみで、**計画に何を書くか**（どの
  フェーズを節として置くか）は書かれていない。
- 「計画の2階層構造」節も、全体作業計画と個別計画の**作り方・単位**の区別が主題で、中身には
  触れていない。
- したがって「調査・反映の枠を必ず置く」というルールは**新しい規定**であり、既存文の修正では
  なく新設が必要。

### 2. `[-]` は「粒度」だけが規定され「タイミング」が無い

`.claude/rules/docs-workflow.md` の該当段落は「フェーズ単位・ループ範囲単位でまとめて実施しない
場合に使う」「ループ範囲内の一部だけを `[-]` にしない」という**粒度**の規定にとどまり、
**いつ `[-]` を決めてよいか**が無い。issue #92 が問題にしているのはこの空白部分である。

参考: 直近の issue #39 対応時のHANDOFF.md では、flow-id 1-4/1-5 とフェーズ2の全行が着手時点で
`[-]` になっていた（この空白の実例）。

### 3. 差し込み位置

`.claude/rules/docs-workflow.md`「既存ドキュメントへ新しい見出しを差し込むときは〜」に従い、
**直前が「節全体にかかる地の文」で終わっていない位置**を選ぶ必要がある。

| 候補位置 | 直前の要素 | 判定 |
|---|---|---|
| 全体フロー表の直後（`### 計画の2階層構造` の直前） | flow-id 表の最終行 | **適合**。表の直後であり、係り先が変わる地の文が無い |
| 「計画の2階層構造」節の末尾 | HANDOFF更新に関する地の文・箇条書き | 不適合。節全体にかかる地の文の直後になる（issue #64 と同じ形） |
| 「issueが大きすぎる場合の分割提案」節の末尾 | 分割時の運用に関する箇条書き | 不適合（同上） |

→ **全体フロー表の直後**へ新しい `###` 節を置く。flow-id 1-4 の行が直前にあるため、
参照関係も自然になる。

### 4. 既存記述との矛盾（要調整）

全体フロー節に「フェーズ2,3はどちらかのみ実施する計画となることがありうるが、フェーズ1,4,5に
ついてはこのフローを利用する際は必ず実施する。」という一文がある。

- 「フェーズ2,3はどちらかのみ」＝**省略しうる**という記述だが、いつ判断するかが無い。
- 「フェーズ4は必ず実施する」は、issue #92 の「反映対象が無ければ flow-id 4-1 でスキップ判断して
  よい」と表面上ぶつかる。**フェーズ4は必ず通る（4-1で反映対象を洗い出す）／洗い出した結果が
  空なら以降をスキップしてよい**、という形へ整理する必要がある。

### 5. 反映先の現状

- 既存DDRの最大番号は `0039`。新規DDRは **0040**。
- spec `.claude/docs/spec/issue-mr-workflow.md` は `## 影響範囲` 配下に issue ごとの
  changelog エントリを時系列で持つ（最新は `### issue #88`）。仕様節は
  `### 計画の2階層構造（issue #9）` の周辺に追記できる。
- `.claude/docs/README.md` はDDR一覧の末尾へ1行追加する形式。

## 結論（フェーズ3への引き渡し）

1. SKILL.md の**全体フロー表の直後**へ `### 全体作業計画に必ず含めるフェーズ（issue #92）` を新設する。
2. 併せて、全体フロー表の直前にある「フェーズ1,4,5は必ず実施する」の一文へ、省略判断の
   タイミングに関する参照を足して矛盾を解消する。flow-id 1-4 の行にも新節への参照を足す。
3. `docs-workflow.md` の `[-]` 段落の直後へ「`[-]` を決めてよいタイミング」を追記する。
4. 反映（フェーズ4）の対象見込み: spec の仕様節・`## 影響範囲`、DDR 0040、README のDDR一覧。
