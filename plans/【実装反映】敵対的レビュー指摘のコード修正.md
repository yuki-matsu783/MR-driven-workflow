# 【実装反映】敵対的レビュー指摘のコード修正

対象: issue #70 / PR #157 / flow-id 4-1

フェーズ3の敵対的レビュー（1/3）でフェーズ4送りにした9件のうち、**実装コード・テストコードの
修正を伴う5件**を扱う。残る4件（ドキュメント整合）は `【設計反映】` が扱う。

`【設計反映】` と分けるのは、評価軸が違うため（記録への書き戻しだけで足りるか、コードの修正を
伴うか）。`.claude/skills/issue-mr-flow/SKILL.md`「種別を複数併記する場合／分ける場合」に従う。

## 方針

### 1. `tr -d '\r'`

`convert_settings .claude/settings.json | tr -d '\r' > "$dst/settings.json"` にする。

**検証はスタブ `jq` で行う**（`.claude/rules/shell-script-style.md`「テスト」）。
`sed '$!s/$/\r/'` を通すスタブをPATH先頭へ置けば、**Linux上でもWindows native jq のCR付与を
再現できる**。実機が無い環境で「直った」と言い切るために、これをテストへ残す。

### 2. CRLFの `agents/*.md`

`mapfile` 直後に `lines[i]="${lines[i]%$'\r'}"` でCRを落とす（bash組み込みなのでforkは増えない）。
CRLF化したフィクスチャで変換が通ることをテストへ足す。

**`.gitattributes` の `dist:begin`〜`dist:end` へ `.claude/agents/*.md` 向けの `eol=lf` を足すかは
この計画では決めない。** 配布先の `.gitattributes` へ追記される行なので影響がこのリポジトリに
閉じず、`.claude/docs/spec/distribution-assets.md` と突き合わせる別の判断になる。
**スクリプト側でCRを吸収すれば動作としては足りる**ので、まずそちらだけを行う。

### 3. `settings.local.json`

- `.gitignore` へ `/.claude/settings.local.json` を追加（このリポジトリ限定）
- `commit` スキルの「ファイルフィルタ」へも追加（**`.claude/` ごと配布先へ配られるため、
  片方では足りない**。`.claude/rules/git-workflow.md`「コミット運用」）
- `COPY_EXCLUDED_PREFIXES` への追加は**行わない**。`.gitignore` に入れば `--exclude-standard` が
  落とすので二重になる。ただし**配布先の `.gitignore` にこの行が無い**場合は落ちないため、
  そこは `install-to-project.sh` の ignore ルールへ足すかを検討する。
- 3案目（未追跡ファイルのコピー件数を標準エラーへ出す）は**採らない**。孤児検出（フェーズ3で
  新設）と違い、正常時に毎回出力が増えるだけで、判断材料にならない。**この判断の理由は
  スレッドへ返信する。**

### 4. `build_into` の0件時メッセージ

原因を3つに切り分けて出す。

| 原因 | メッセージ |
|---|---|
| `.claude/` が存在しない | ディレクトリが無い旨 |
| すべて ignore されている | `git check-ignore` の結果を添える |
| `agents/*.md` と `settings.json` しか無い | — |

**3つ目はエラーにしない方向で見直す。** `agents/` と `settings.json` だけでも変換出力としては
成立するので、「コピー対象0件」を失敗条件にしている現在の判定自体が広すぎる。
**判定を変えるなら、既存テスト（0件で非0を期待しているもの）の期待値も変わる**ので、
契約の変更として扱い、テストを置き換える（フェーズ3の T13 と同じ扱い）。

### 5. `read -d ''` の実機計測

**この実行環境（Linux）では決められない。** 指摘の実測もLinuxであり、対象環境は Windows git bash
である。`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」の 95ms/回 は git bash の
実測値で、Linux の fork/exec とは桁が違う。**forkが高い側とsyscallが高い側のどちらに倒れるかは、
同じ環境で両方を測らないと決まらない。**

したがってこの計画では**コードを変更しない**。代わりに:

- **計測手順を `.claude/docs/spec/` へ残す**（何を測るか・ベースラインの取り方・同一セッション内で
  連続測定すること）。`reports/` は flow-id 5-5 で消えるため、そこに書くだけでは残らない
- **未決定事項として spec へ記録する**（`【設計反映】` と重なるので、そちらで書く）
- 実機で測れる人が測ったら判断できる形にしておく

**「測れないから現状維持」と「測ったうえで現状維持」は別物**なので、前者であることを明示する。
