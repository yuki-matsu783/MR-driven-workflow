# issue #92 全体作業計画

## 目的（issueの要約）

flow-id 1-4 の全体作業計画で、フェーズ2〈調査〉・フェーズ4〈反映〉を先回りして省略できてしまう
状態を解消する。枠は必ず残し、省略の判断は各フェーズの直前（flow-id 2-1 / 4-1）まで遅らせる。
あわせて「全体作業計画を書くための事前調査は軽めでよい」ことを明示する。

## 現在地

- issue: #92
- ブランチ: `claude/master-plan-rule-addition-gcw0t6`（ハーネス指定。`feature-<issue番号>-<slug>` の対象外）

## フェーズ2〈調査〉

**このフェーズは省略しない前提で枠を置く。** 実際に省略してよいと判断できるのは flow-id 2-1 で
「既に分かっていることだけで作業計画が書ける」と確認できた時点である。

調べること（軽い読み取りで足りる範囲）:

1. `.claude/skills/issue-mr-flow/SKILL.md` の flow-id 1-4・2-1・4-1 の記述と、
   「計画の2階層構造」節が全体作業計画の**中身**について何を規定しているか。
2. `.claude/rules/docs-workflow.md` の進捗記号 `[-]` の説明が、**いつ** `[-]` を決めてよいかを
   規定しているか。
3. 新しい見出しの差し込み位置（`.claude/rules/docs-workflow.md`「既存ドキュメントへ新しい見出しを
   差し込むときは〜」に適合する位置はどこか）。
4. 既存記述との矛盾の有無（特に全体フロー節の「フェーズ1,4,5は必ず実施する」という一文）。

成果物: `plans/【調査】〜.md`（調査計画と結果）、`reports/` の報告HTML、worklogへの記録。

## フェーズ3〈設計・実装〉

調査結果をもとに、次の2ファイルを変更する（このissueの成果物はドキュメントそのもの）。

- `.claude/skills/issue-mr-flow/SKILL.md`
  - 全体作業計画に**フェーズ2〈調査〉・フェーズ4〈反映〉の節を必ず含める**ことを明記する。
  - **事前調査は軽めでよい**理由（本格的な調査はフェーズ2で行うため、1-4で深追いすると重複する）を書く。
  - **反映は枠だけ置く**（中身は作業が終わるまで決まらない）ことと、省略判断のタイミングを表で示す。
- `.claude/rules/docs-workflow.md`
  - `[-]` の説明へ「いつ `[-]` を決めてよいか」を追記し、SKILL.md 側と矛盾しないようにする。

成果物: `plans/【設計】【実装】〜.md`、上記2ファイルの変更、worklogへの記録。

## フェーズ4〈反映〉

**枠だけ置く。** 何を反映するかは作業が終わるまで確定しないため、flow-id 4-1 で反映対象を
洗い出したうえで個別反映計画を作る。現時点での見込みは次のとおり（確定ではない）。

- 設計反映: `.claude/docs/spec/issue-mr-workflow.md`（仕様節＋`## 影響範囲`のエントリ）、
  新規DDR、`.claude/docs/README.md` のDDR一覧。
- AIアセット反映: 今回は変更対象そのものがAIアセット（SKILL.md・rules）であるため、
  フェーズ3と重複する可能性がある。重複する場合は 4-1 でその旨を記録する。

## フェーズ5〈クローズ〉

`plans/` `worklog/` `reports/` の削除とHANDOFF.mdのリセット、defaultブランチとのコンフリクト確認、
リモートへの反映まで。PRの作成・マージはこのセッションでは行わない
（`.claude/rules/git-workflow.md`「ハーネスがPR作成を制限する環境での扱い」）。

## 進め方の制約

- 非対話的セッションのため、人間のレビュー往復（2-3/2-4, 2-8/2-9, 3-3/3-4, 3-8/3-9, 4-3/4-4,
  4-8/4-9）は実施できない。該当ループの進捗記号は `[]` のまま残し、実施内容はHANDOFF.mdの
  「やったこと」に文章で残す（`.claude/rules/docs-workflow.md`）。
- issueの分割は不要と判断した。受け入れ条件は同型の成果物の並列列挙ではなく、
  1つのルール追加に対する記載箇所の内訳である（`.claude/skills/issue-mr-flow/SKILL.md`
  「issueが大きすぎる場合の分割提案」の判定「各項目が単独でマージされても壊れないか」に対し、
  SKILL.md と docs-workflow.md は同時に変えないと記述が食い違う＝横断的変更に該当する）。
