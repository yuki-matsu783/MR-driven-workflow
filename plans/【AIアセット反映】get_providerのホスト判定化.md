## 候補1: `set -e` 配下で終了コードを検査するテストの書き方（**反映する**）

反映先: `.claude/rules/shell-script-style.md`「テスト」節

### 何があったか

`provider_from_remote_url` が「ホスト名が空なら終了コード1」を返すことのテストを、最初こう書いた。

```bash
assert_eq "..." "1" "$(provider_from_remote_url 'https://' 2>/dev/null; echo $?)"
```

実行すると `1` が返って**テストは通った**。しかしテストスクリプトも `Provider.sh` も
`set -euo pipefail` を宣言しており、コマンド置換のサブシェルは `-e` を引き継ぐ。関数が失敗した
時点でサブシェルが終了すれば `echo $?` に到達せず、空文字列が返って別の理由で落ちる書き方である。
**「たまたま通っている」状態を残すべきでない**と判断し、`if` の条件式（`-e` が一時停止される文脈）へ
寄せた。

```bash
if provider_from_remote_url 'https://' >/dev/null 2>&1; then
  empty_host_status=0
else
  empty_host_status=1
fi
assert_eq "..." "1" "$empty_host_status"
```

### なぜルール化する価値があるか

既存の「エラー方針」節は「失敗しても処理を継続したい箇所」の書き方（関数をコマンド置換・
明示サブシェルで呼ぶ）を扱っているが、**テストで終了コードそのものを assert したい**という用途は
扱っていない。しかもこの誤りは**テストが通ってしまうため気づけない**種類のものである。
「テスト」節に3〜5行で足す。

### 書く内容

- `"$(func; echo $?)"` の形で終了コードを取らない（`set -e` 配下ではサブシェルが `echo` に
  到達しない可能性がある）。
- `if func; then status=0; else status=1; fi` の形にする。`if` の条件式では `-e` が一時停止される
  （同ファイル「エラー方針」節を参照）。
- 悪い例／良い例のコードブロックを添える（同節の既存の書き方に合わせる）。
- issue #45の実例（`provider_from_remote_url` の空ホスト検査）を根拠として1行添える。

## 候補4: `create-commit.sh` は事前ステージ済みの変更も巻き込む（**flow-id 4-6実施中に判明・要判断**）

反映先候補: `.claude/skills/commit/SKILL.md`（および必要なら `.claude/rules/git-workflow.md`）

**これは flow-id 4-3 のレビュー時点では存在しなかった候補で、設計反映のコミット時に判明した。**
勝手に反映せず、flow-id 4-8のレビューで採否を判断してもらう。

### 何があったか

設計反映のコミット（flow-id 4-7）で、`create-commit.sh` の引数に渡していない `HANDOFF.md` と
本ファイルが同じコミットへ入った。`create-commit.sh` は最後に**対象ファイルを指定しない
コミット操作**を実行するため、`git add <指定ファイル>` の対象外であっても、**それ以前に別経路で
ステージされていた変更はindexに残ったまま取り込まれる**。

今回はユーザーがレビュー中に対応工数レポートの文言変更をステージしており、その操作が
作業中のファイルまで巻き込んでいた。

### なぜルール化する価値があるか

`.claude/skills/commit/SKILL.md`の「絶対ルール」は
「ステージングされていない変更（unstaged / untracked）はコミット対象に含めない」と書いているが、
**その裏側にある「ステージング済みなら指定外でも含まれる」ことは書かれていない**。
同スキルはprefixごとに複数のコミットへ分割する運用を定めており、この挙動と噛み合わない
（分割したつもりが1つ目のコミットに全部入る）。

### 書く内容（案）

- Step 1（現状把握）で `git status` を見る際、**指定予定外のステージ済み変更が無いか確認する**。
  あれば、それが意図した同梱かをユーザーへ確認するか、`git restore --staged` で外す。
- Step 4に、`create-commit.sh` は指定ファイルを `git add` したうえで**index全体をコミットする**
  ことを1行明記する。

### 判断が要る理由

**実害は「コミット粒度が意図どおりに分かれない」ことだけ**で、内容が失われたり誤ったものが
入ったりする性質ではない。またステージ操作は通常ユーザーが意図して行うものなので、
巻き込みが常に間違いとは限らない。記述を足すだけで十分か、`create-commit.sh` 側の実装を
変える（指定ファイルのみをコミットする）べきかも含めて判断してほしい。
**後者は本issueの範囲を明確に超えるため、その場合は別issueとして起票する。**
