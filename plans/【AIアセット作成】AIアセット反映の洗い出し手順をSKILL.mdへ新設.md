- **`【実装反映】` という種別自体は残る**（フェーズ3のレビュー往復で解消しきれず持ち越した

**`## 全体フロー` 配下の h3 として、`### issueが大きすぎる場合の分割提案（issue #64）` の直後・

### 新設する節の構成（4手順）

調査結果の「設計への反映」2 のとおり、次の4手順で構成する。**スキップ条件（手順1〜2まで）を
手順の番号で書けるようにするための区切り**である。

| 手順 | 内容 | 打ち切り・境界 |
|---|---|---|
| 手順1 | **起点の列挙。** `worklog/` の「試したこと」「ダメだったこと」を入力にする | **主たる成果物としてのアセット作成は対象外**（`【AIアセット作成】` で扱う） |
| 手順2 | **4類型への分類**（下表） | **ここで0件ならフェーズ4のAIアセットの項は充足**（手順3・4は入力が無い） |
| 手順3 | **証拠集めと打ち切り**（(a) のみ）。**段階を持つ**（下記） | 各段階で見つからなければ次へ進み、最後の段階でも0件なら打ち切る |
| 手順4 | **反映先の形態の決定**（2軸）＋削除・統合の検討 | 形態によらず種別は `【AIアセット反映】` |

#### 手順2で使う4類型の表（新節はこの3列で持つ）

受け入れ条件が「4類型と、再現性の証拠を要求する範囲が**表で示されている**」を求めるため、
**新節では箇条書きではなく表**にする。

| 類型 | 意味 | 証拠を要求するか |
|---|---|---|
| (a) | 該当するアセットが**無かった** | **要求する**（新規作成のため） |
| (b) | アセットは**あったが誤っていた** | しない（1回でも直す） |
| (c) | アセットはあったが、**その罠が書かれていなかった** | しない（同上） |
| (d) | アセットはあったのに、**辿り着けなかった** | しない（同上） |

#### 手順3の段階（安い側から見て打ち切る）

全体作業計画「方針」が定めた段階を、新節へそのまま持たせる。**打ち切り条件だけでは受け入れ
条件を満たさない**（段階も書かれている必要がある）。

| 段階 | 何を見るか | 打ち切ってよい条件 |
|---|---|---|
| 1 | **同一MR内**（`worklog/` の他の項目・同じPRの他のコミット） | 同じ罠が2回以上出ていれば (a) の証拠として十分。ここで確定すれば以降は見ない |
| 2 | **`doc-search`（frontmatter）＋ `grep`（本文）** | **両方0件**であること（下記） |
| 3 | **直近のPR・DDR一覧** | 見つからなければ痕跡なしとして打ち切る。**それ以上は遡らない** |

段階2の打ち切りは**2段**にする。`doc-search`（`search-frontmatter.sh`）は**frontmatterのキーしか
見ない**ため、`matched=0` 単独では偽陰性が出る（実測: `--text` で1件 対 `grep -rl` で7ファイル）。

```bash
bash .claude/scripts/src/search-frontmatter.sh --text '<罠を表す語>' --type ddr --format count
grep -rn '<罠を表す語>' .claude/docs .claude/rules
```

**DDRを証拠に使う場合は `status` を別途確認する。** `--format detail` は
`status` / `superseded_by` / `note` / `resource` を出力しないため、`--format jsonl` かファイル本体で
見る（後続のDDRに置き換えられた決定を現役の根拠として引かないため。調査結果Q4）。
