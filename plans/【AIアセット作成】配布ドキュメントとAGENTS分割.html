作業1: AGENTS.md の分割（受け入れ条件9）

「ルール」節の9項目を .claude/rules/agent-common.md（type: rule）へそのまま移す。 AGENTS.md は「共通ルールのimport＋プロジェクト概要＋開発・実行」の3節だけになる。

項目9を落とさない 「ドキュメント探索は frontmatterインデックスの横断検索を第一手段にする」は「ルール」節で最も長い項目で、 doc-search スキルの入口そのもの。切り出しから落とすと配布先で全文探索が既定に戻る。

作業2: CLAUDE.md / GEMINI.md のポインタ化（前提3のセット変更）

現状の2ファイルは末尾が空の見出しで終わっている。core にする以上、配布先でも意味を持つ 内容にしなければならないので、空見出しを .claude/rules/ へのポインタへ差し替える （「プロジェクト固有のルールは .claude/rules/<名前>.md へ置く。このファイルは配布元が所有しており、 再適用で上書きされる」）。

作業3: apply-mr-workflow-to-project/SKILL.md の全面改訂

.skill 前提の記述を落とし、新方式（5層・--dry-run・再適用・manifest）へ書き換える。 配布先で削除・改名された core が残ることと、その提示のみを行う設計も明記する。

作業4: DEVELOPERS.md の書き換え（受け入れ条件10の後半）

sync-assets.sh → package_skill.cjs → gemini skills install の手順を、 インストーラを直接実行する形へ差し替える。層の一覧・主なオプション・網羅性チェックの流し方を載せる。

作業5: build/ の存廃を決める（調査7の宿題）

build/ は .skill のビルド成果物の置き場としてのみ存在しており、ビルド工程が無くなる。 決めずに放置すると、次の作業者には「漏れ」と区別できない。

  • 提案は「削除」。将来別のビルドが要るなら、そのとき必要な形で作り直せばよく、 存在しない工程の記述がセッションごとに読み込まれるルールファイルに残り続けるほうが害が大きい。
  • ただし .gitignore の /build/ 行は対の計画が触る同じファイルなので、実際の削除は対の計画で行う （同じファイルへ2つの計画から別々に手を入れない）。この計画が持つのは判断だけで、編集は対の計画にある。
  • build/ への参照のうち2箇所は point-in-time の記録なので触らない。

作業6: REVIEW-POINTS.local.md に伴うルールの更新

markdown-frontmatter.md「typeの値」表・docs-workflow.md・directory-structure.md の 「flow-id 5-4で削除しない」の記述へ .local を加える。スクリプト側の変更（cleanup-task.sh の KEEP_BASENAMES）は対の計画が持つ。
