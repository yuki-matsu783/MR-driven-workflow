## 作業1: DDR 0032 を新規作成する

ファイル名: `.claude/docs/ddr/0032-issueの分割は並列列挙構造を主トリガーにAIが提案し人間が決定する.md`

- 現行の最大番号は `0031`。**他ブランチとの衝突は flow-id 5-2 の `check-base-conflicts.sh` で
  確認**し、衝突していれば `resolve-conflict` スキルで繰り下げる。
- frontmatter は `.claude/rules/markdown-frontmatter.md` の規約に従い
  `title` / `type: ddr` / `description` / `tags` / `keywords` を付ける（`status` は付けない＝有効）。

### 構成

- **背景**: 「1 issue = 1ブランチ = 1 MR」が単位でありながら、issue自体の粒度基準が無かったこと。
  個別計画ファイルの分割基準（「迷ったら分ける」）はあるが層が違うこと。DDR 0013（issue #24）で
  スコープが後から膨らみ全面書き直しになった実例。
- **決定**: 並列列挙構造を主トリガーにAIが分割を提案し、決定は人間が行う。判定は
  「各項目が単独でマージされてもシステムが壊れないか」の一問。分割しない条件（横断的変更／
  分割コストが本体を上回る／基盤issue先行）を併記して誤爆を防ぐ。判定タイミングは flow-id 1-4 が主、
  flow-id 1-1 が副。記載先は `issue-mr-flow/SKILL.md`（正）と `issue-create/SKILL.md`（参照のみ）。
- **却下案**（4件。いずれも「なぜ採らなかったか」を明記する）
  1. **受け入れ条件の個数・本文の行数といった定量閾値で機械判定する**
     → 量と可分性は相関しない。不可分な大issueを割ろうとし、独立した小issueを見逃す。閾値の
     数字自体が根拠を持てず、運用のたびに議論になる。
  2. **スクリプト化して自動検知する**（`check-base-conflicts.sh` のような機構化）
     → 「同型の成果物か」の判定は本文の意味理解を要し、文字列処理では表現できない。判定を
     機構に委ねると、外した場合に**黙って**分割を促す／促さないことになり、DDR 0029 で機構化
     した「gitが検知できない衝突」のような**決定的に判定できる対象**とは性質が違う。
  3. **AIが分割を強制する（子issueを自動起票する）**
     → issueの粒度はリリース単位・レビュー体制といった、リポジトリ外の事情に依存する。
     `issue-create` スキルが既に「ユーザーの明示的な確認なしに起票しない」方針であることとも矛盾する。
  4. **issue分割は導入せず、個別計画ファイルの分割だけで済ませる**
     → 計画ファイルを分けてもMRは1本のままで、マージ単位・切り戻し単位は分割されない。
     「レビューを分けたい」には効くが「別々にマージしたい」には効かないため、層が異なる。
- **影響範囲**: `issue-mr-flow/SKILL.md`（新節・flow-id 1-4/2-6 行）、`issue-create/SKILL.md`
  （手順追加・番号繰り下げ）、`.claude/docs/spec/issue-mr-workflow.md`。
