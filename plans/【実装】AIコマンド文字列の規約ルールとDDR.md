# 個別作業計画: ルール本文とDDRの作成（flow-id 3-1）

- issue: [#47](https://github.com/yuki-matsu783/MR-driven-workflow/issues/47)
- 全体作業計画: `plans/prancy-prancing-dewdrop.md`
- 調査結果（根拠の正文）: `reports/20260820_prancy-prancing-dewdrop_ルール読込条件と前方一致の調査.md`

## 目的

AIエージェントがBash/PowerShellツールへ渡す**コマンド文字列そのもの**の規約を定め、ユーザーが
承認前にコマンドの意図を読み取れる状態にする。issue #47 の受け入れ条件7項目をすべて満たす。

## 受け入れ条件（issue #47 からの転記）と対応箇所

レビュー時にissueを開かずに対応の妥当性を判定できるよう、条文をそのまま転記する。

1. 上記のルールが `.claude/rules/` 配下に記載され、セッション開始時に自動でコンテキストへ
   読み込まれることを確認できている（新規ファイル／既存ファイルへの追記のどちらにするかは実装時に判断する）
2. ルール本文に、根拠として「`description` はコンソール上1行しか表示されない」という実機確認の事実が明記されている
3. ルール本文に、`description`・コメントの言語（日本語）と文体（敬語・助詞・装飾なし、単語と短文）が
   明記され、良い例／悪い例が併記されている
4. ルール本文に「複数行コマンドの1行目にはコメントを書かず、2行目以降に置く」ことが、前方一致が
   外れる理由とともに明記され、良い例／悪い例が併記されている
5. hook誤検知（該当2語の連続）への注意が、コメント記述の文脈で再掲されている
6. 新規ファイルを作成する場合、`.claude/rules/markdown-frontmatter.md` の規約に沿ったfrontmatterが付いている
7. 判断の経緯（`description` の1行制約、出力トークン増よりも承認前の安全性を優先したトレードオフ、
   1行コマンドを対象外とした理由、1行目コメントを禁止する理由）がDDRとして記録されている

## ルール本文の構成（何を書くか）

上表に加えて、条件番号を持たない節も置く。

| 節 | 書く内容 |
|---|---|
| 冒頭（見出し前） | 適用範囲。**`shell-script-style.md` とのスコープの違いを明示**し相互リンクする（**条件文には無いが、既存ルールとの二重管理を避けるために要る**） |
| 説明の置き場所 | 1行コマンド／複数行コマンド／複雑すぎる場合の3行の表。**切り出し先の2択（scratchpad か `.claude/scripts/src/` か）の判断基準まで書く**。issue本文「期待する動作」の表に対応する（条件文には現れないが、本issueの中心要件） |

### 受け入れ条件4の理由の書き方（案B。flow-id 3-1 時点でユーザーが指示）

**記録**: PR #132 のコメント [#issuecomment-5356574028](https://github.com/yuki-matsu783/MR-driven-workflow/pull/132#issuecomment-5356574028)
（DDR 0041 の運用どおり、チャットで受けた判断をMRの通常コメントへ記録した）。`plans/` `worklog/` は
flow-id 5-3 で削除され `HANDOFF.md` はリセットされるため、**同じ参照をDDR判断4にも残す**。

issueの断定（「前方一致が外れるため」）をそのまま書かず、次のリスク回避として書く。

> `deny` 側はこの環境では外れなかったが、`allow` 側は未確認であり、照合の実挙動は環境・
> バージョンで異なる観測がある。ゆえに先頭は避ける。

根拠として本文へ載せるもの:

- 調査2の実測表（A〜Dの4ケース。`deny` のみ）。**測定環境（Claude Code on the web / Linux、
  実施日）と、ユーザーの常用環境（Windows / git bash）が未確認である旨を必ず併記する。**
  `reports/` は flow-id 5-3 で消えるため、限定を書き落とすと**限定だけが失われた実測表が
  `.claude/rules/` に永続する**。
- `allow` を確かめられなかった理由（結論の中身は
  `reports/…調査.md`「設計への反映 > 受け入れ条件4の扱い」が正。ここでは要点のみ）。

**同じ実測表をルール本文とDDR判断4の両方へ載せる。正はルール本文とし、DDR側は「判断の材料」として
同じ表を再掲する**（DDRは本文不変で、ルール本文は更新されうるため。両者が食い違ったらルール本文を
正とする）。

**確度の書き分けを本文で保つ。** 受け入れ条件2の根拠は「出典を添えた断定」、受け入れ条件4の
根拠は「リスク回避（`allow` 未確認を明記）」であり、読み手が両者を取り違えない書き方にする。

### 受け入れ条件5の書き方

「コメントに2語を並べると常に誤発火する」とは**書かない**。当てはまり方がhookによって違う
（結論の中身は `reports/…調査.md`「調査3」が正。ここへ複製しない）。

- **コミットをブロックする側**は、`settings.json` の `if` を経由しないという**コード上の事実**に
  基づくため、環境に依らず断定してよい。
- **push検知の2つは、発火するかどうかをルール本文で結論づけない。** `.claude/rules/git-workflow.md`
  「push検知hookの誤検知」はissue #23 で計3回の誤発火を観測したと記録しており、今回の観測とは
  **逆のこと**を言っている。切り分ける材料が無いまま新ルールへ結論を書くと、`.claude/rules/` 配下に
  同じ事象について逆のことを書いた2つのルールが同時に存在し、どちらに従うかが不定になる。
  **両論併記のうえ「安全側に倒して連続させない」という結論だけを守る**書き方にする。
  食い違いの扱い（既存記述の訂正か環境差の併記か）は flow-id 4-1 で決める。

### 切り出し先の判断基準

| 切り出し先 | 使う場面 |
|---|---|
| scratchpad | その場限り。使い捨て |
| `.claude/scripts/src/` | 繰り返し使う。`.claude/rules/directory-structure.md` の配置ルールに従い、単体テストとドキュメントも伴う |

使い捨てを `.claude/scripts/src/` へ置くと配置ルール（「skills経由で能動的に実行するスクリプト」の
置き場）と衝突し、`cleanup-task.sh` の削除対象でもないため残り続ける。

## DDRに書く判断（4つ）

| # | 判断 |
|---|---|
| 1 | `description` の1行制約を前提に、説明の置き場所をコマンド内コメントへ寄せた |
| 2 | 出力トークン増よりも承認前の安全性を優先したトレードオフ（**試行的運用であり、運用感が悪ければ見直す**前提を含める） |
| 3 | 1行コマンドを対象外とした理由（`#` が行末までを飲むリスクだけが残り、得るものが無い） |
| 4 | 1行目コメントを禁止した理由。**issueの断定ではなく案Bのリスク回避として記録し、`deny` の実測と `allow` 未確認の両方を残す**。**案Bを誰がいつ決めたかの参照（PR #132 の #issuecomment-5356574028）も書く** |

判断4については、**却下案（案A: 制約撤回／案C: issueの記述どおり）と、それを採らなかった理由**も
DDRへ書く（DDRの本質は「〇〇を検討したが✕✕を採用した」の記録であるため）。

## 受け入れ条件1が否だった場合（新規ファイルが読み込まれなかったとき）

検証3の実測は、新しいセッションの開始かユーザーへの確認依頼に依存するため、**結果が本セッションの
外（フェーズ4以降）で返ることがある**。否だった時点で本計画の中心的な前提（新規ファイル1枚で
条件1を満たす）が崩れ、成果物の置き場所そのもの（調査4の結論）を作り直すことになるため、
戻り先を先に決めておく。

| 選択肢 | 内容 | 評価 |
|---|---|---|
| a | `AGENTS.md` の「ルール」節から新ファイルを明示的に参照する | **第一候補。** 既存の導線を使うだけで、ファイルの置き場所を変えずに済む |
| b | `alwaysApply: true` を付ける | 次点。ただし調査1では読み込みの条件だと確認できておらず、効く保証が無い |
| c | 既存ファイル（`shell-script-style.md`）へ追記する | 最後の手段。スコープが違うものを1ファイルへ混ぜることになる |

- **どれを選ぶかはユーザーが決める。** AIは実測結果と上表を提示し、`AskUserQuestion` で確認する。
- **実測結果が出ないままフェーズ5へ進む場合は、条件1を未達として明示する。** `HANDOFF.md` と
  MR descriptionの両方へ「条件1は未確認」と書き、Draft解除（flow-id 5-4）まで進めてよいかを
  ユーザーへ確認する。**未確認であることを伏せてマージ依頼へ進まない。**

## やらないこと

- **受け入れ条件1を「満たした」と書くこと**。新規ファイルが実際に読み込まれるかは未確認であり、
  実測（下記「検証」3）が取れるまで満たしたと書かない。
- `.claude/rules/markdown-frontmatter.md` の `alwaysApply` の説明を書き換えること
  （新規ファイルでの実測が取れるまで保留。調査「恒久知見#3」）。
- `.claude/rules/git-workflow.md` や `.claude/docs/spec/` の既存記述を訂正すること
  （恒久知見の反映先の確定は flow-id 4-1 の担当。ここでは触らない）。
- ルール本文へ hook の仕組みそのものを説明し直すこと（`git-workflow.md` との二重管理になる）。

## 検証

**各項目の結果は `reports/20260820_prancy-prancing-dewdrop_ルール本文とDDRの作成結果.md` へ書く**
（この計画ファイルへは書かない。issue #87）。

1. **受け入れ条件7項目との逐条突き合わせ。** 上の「受け入れ条件（issue #47 からの転記）と対応箇所」
   の表の順に、ルール本文・DDRの該当箇所を指し示せることを確認する。満たせていない項目があれば、
   満たせない理由を明示する。

2. **frontmatterがインデックスへ載ること。** 件数比較ではなく、**当該ファイル自体が載ったことを
   直接見る**（`main` の取り込みやフェーズ4の追加でDDRが増えると、総件数の期待値はずれる。
   逆に他が1件増えたのと同時に新規ファイルのfrontmatterが壊れていると、件数だけ合って通る）。

   ```bash
   bash .claude/scripts/src/extract-frontmatter.sh .

   # 期待値: それぞれ matched=1
   bash .claude/scripts/src/search-frontmatter.sh --path ai-command-style
   bash .claude/scripts/src/search-frontmatter.sh --path 0059
   ```

   総件数（`--type rule` / `--type ddr`）は**参考値**として控えるにとどめる。

3. **DDR一覧（`.claude/docs/README.md`）へ 0059 の行があること。** この目次は手動維持で、
   `extract-frontmatter.sh` は欠落を検出しない。

   ```bash
   # 期待値: 1
   grep -c '](ddr/0059-' .claude/docs/README.md
   ```

4. **受け入れ条件1の実測（新規ファイルが自動で読み込まれるか）。**
   既存6ファイルが読み込まれた観測は、新規ファイルについての証拠にならない（レビュー指摘
   #discussion_r3821645797）。**新しいセッションを開始して当該ファイルがコンテキストへ入るかを
   確認する。本セッションで確かめられない場合はユーザーへ確認を依頼する。**
   実測が取れるまで、受け入れ条件1を満たしたと書かない。否だった場合は上記
   「受け入れ条件1が否だった場合」へ戻る。

5. **ルール本文・DDRが自分自身の規約に違反していないこと。** 良い例／悪い例として載せるコマンド
   断片に、hookが誤検知する2語の連続を書かない。**目視ではなく機械的に検査する。**

   ```bash
   # 期待値: 「なし」と表示される（マッチ行があればその行番号が出る）
   grep -nE 'git[[:space:]]+(commit|push)' .claude/rules/ai-command-style.md .claude/docs/ddr/0059-*.md || echo 'なし'
   ```

   **この検査コマンド自体、パターンを `[[:space:]]+` で書くことで連続文字列になるのを避けている。**
   該当2語を空白区切りで直書きすると、検査コマンドを実行した時点でhookにブロックされる
   （本計画の作成中に実際に1回踏んだ）。

6. **DDR番号の重複が無いこと。**

   ```bash
   # 期待値: 1
   ls .claude/docs/ddr/0059-*.md | wc -l
   ```

   最終確認は flow-id 5-1 の `check-base-conflicts.sh` で行う。
