# 個別作業計画: ルール本文とDDRの作成（flow-id 3-1）

- issue: [#47](https://github.com/yuki-matsu783/MR-driven-workflow/issues/47)
- 全体作業計画: `plans/prancy-prancing-dewdrop.md`
- 調査結果（根拠の正文）: `reports/20260820_prancy-prancing-dewdrop_ルール読込条件と前方一致の調査.md`

## 目的

AIエージェントがBash/PowerShellツールへ渡す**コマンド文字列そのもの**の規約を定め、ユーザーが
承認前にコマンドの意図を読み取れる状態にする。issue #47 の受け入れ条件7項目をすべて満たす。

## 変更対象

| ファイル | 種別 | 内容 |
|---|---|---|
| `.claude/rules/ai-command-style.md` | **新規** | ルール本文 |
| `.claude/docs/ddr/0059-AIが渡すコマンド文字列の説明はdescriptionとコメントへ分けて置く.md` | **新規** | 判断の経緯（受け入れ条件7） |

DDR番号は本計画作成時点の空き番号が 0059（既存の最大は 0058）。`main` が進むと重複しうるため、
flow-id 5-1 の `check-base-conflicts.sh` で確認し、必要なら繰り下げる。

**既存ファイルへの追記ではなく新規ファイルにする**（調査4の結論）。`shell-script-style.md` は
`.sh` として保存するスクリプトの規約であり、対象が「ツールへ渡す文字列」である本ルールとは
スコープが異なる。

## ルール本文の構成（何を書くか）

見出し単位で、書く内容と対応する受け入れ条件を先に決めておく。

| 節 | 書く内容 | 受け入れ条件 |
|---|---|---|
| 冒頭（見出し前） | 適用範囲。**`shell-script-style.md` とのスコープの違いを明示**し相互リンクする | — |
| 根拠 | `description` はコンソール上**1行しか表示されない**。**issue #47 起票時の実機確認を出典として引用する形**で書く（本環境では再現できないため。調査「設計への反映」） | 2 |
| 説明の置き場所 | 1行コマンド／複数行コマンド／複雑すぎる場合の3行の表。**切り出し先の2択（scratchpad か `.claude/scripts/src/` か）の判断基準まで書く** | — |
| 言語・文体 | 日本語。敬語・助詞・無駄な装飾を使わず単語と短文。**良い例／悪い例を併記** | 3 |
| 1行目にコメントを書かない | 結論と理由。**理由は案B（下記）の書き方にする**。**良い例／悪い例を併記** | 4 |
| hook誤検知への注意 | コメント本文で `git` と `commit` / `push` を連続させない。**コメント記述の文脈での再掲**にとどめ、仕組みの説明は `git-workflow.md` を参照する | 5 |
| frontmatter | `markdown-frontmatter.md` の規約に沿う。`type: rule`。**`alwaysApply` は付けない** | 6 |

### 受け入れ条件4の理由の書き方（案B・チャットで合意済み）

issueの断定（「前方一致が外れるため」）をそのまま書かず、次のリスク回避として書く。

> `deny` 側はこの環境では外れなかったが、`allow` 側は未確認であり、照合の実挙動は環境・
> バージョンで異なる観測がある。ゆえに先頭は避ける。

根拠として本文へ載せるもの:

- 調査2の実測表（A〜Dの4ケース。`deny` のみ）。
- `allow` を確かめられなかった理由。`deny` はANY一致で拒否、`allow` はALL一致で自動承認という
  非対称のため、先頭のコメント行が「無視される」のか「どの許可規則にも一致しない部分コマンド
  として数えられる」のかを `deny` の実験では区別できない。加えて、権限モードをプロンプトが出る
  形へ変えると**セッションが止まる**ため実測を見送った。

**確度の書き分けを本文で保つ。** 受け入れ条件2の根拠は「出典を添えた断定」、受け入れ条件4の
根拠は「リスク回避（`allow` 未確認を明記）」であり、読み手が両者を取り違えない書き方にする。

### 受け入れ条件5の書き方

「コメントに2語を並べると常に誤発火する」とは**書かない**（調査3）。当てはまり方が違う。

| hook | 発火 |
|---|---|
| コミットをブロックする側 | `if` を経由せずコマンド文字列全体を検査するため、**地の文でも必ず発火する** |
| push検知の2つ | `if` に絞られ、この環境では地の文だけでは発火しなかった |

### 切り出し先の判断基準

| 切り出し先 | 使う場面 |
|---|---|
| scratchpad | その場限り。使い捨て |
| `.claude/scripts/src/` | 繰り返し使う。`.claude/rules/directory-structure.md` の配置ルールに従い、単体テストとドキュメントも伴う |

使い捨てを `.claude/scripts/src/` へ置くと配置ルール（「skills経由で能動的に実行するスクリプト」の
置き場）と衝突し、`cleanup-task.sh` の削除対象でもないため残り続ける。

## DDRに書く判断（4つ）

| # | 判断 |
|---|---|
| 1 | `description` の1行制約を前提に、説明の置き場所をコマンド内コメントへ寄せた |
| 2 | 出力トークン増よりも承認前の安全性を優先したトレードオフ（**試行的運用であり、運用感が悪ければ見直す**前提を含める） |
| 3 | 1行コマンドを対象外とした理由（`#` が行末までを飲むリスクだけが残り、得るものが無い） |
| 4 | 1行目コメントを禁止した理由。**issueの断定ではなく案Bのリスク回避として記録し、`deny` の実測と `allow` 未確認の両方を残す** |

判断4については、**却下案（案A: 制約撤回／案C: issueの記述どおり）と、それを採らなかった理由**も
DDRへ書く（DDRの本質は「〇〇を検討したが✕✕を採用した」の記録であるため）。

## やらないこと

- **受け入れ条件1を「満たした」と書くこと**。新規ファイルが実際に読み込まれるかは未確認であり、
  実測（下記「検証」3）が取れるまで満たしたと書かない。
- `.claude/rules/markdown-frontmatter.md` の `alwaysApply` の説明を書き換えること
  （新規ファイルでの実測が取れるまで保留。調査「恒久知見#3」）。
- `.claude/rules/git-workflow.md` や `.claude/docs/spec/` の既存記述を訂正すること
  （恒久知見の反映先の確定は flow-id 4-1 の担当。ここでは触らない）。
- ルール本文へ hook の仕組みそのものを説明し直すこと（`git-workflow.md` との二重管理になる）。

## 検証

1. **受け入れ条件7項目との逐条突き合わせ。** 上の対応表の順に、ルール本文・DDRの該当箇所を
   指し示せることを確認する。満たせていない項目があれば、満たせない理由を明示する。
2. **frontmatterがインデックスへ載ること。**

   ```bash
   bash .claude/scripts/src/extract-frontmatter.sh .
   bash .claude/scripts/src/search-frontmatter.sh --type rule
   bash .claude/scripts/src/search-frontmatter.sh --type ddr
   ```

   期待値: `--type rule` の `matched=` が現在の **9 → 10**、`--type ddr` が現在の **54 → 55**
   へ増える（本計画作成時に実測した現在値。**`--type ddr` の 54 はDDRの連番の最大 0058 とは
   一致しない**ので、番号から推測せず実行時に現在値を控えてから比較する）。

3. **受け入れ条件1の実測（新規ファイルが自動で読み込まれるか）。**
   既存6ファイルが読み込まれた観測は、新規ファイルについての証拠にならない（レビュー指摘
   #discussion_r3821645797）。**新しいセッションを開始して当該ファイルがコンテキストへ入るかを
   確認する。本セッションで確かめられない場合はユーザーへ確認を依頼する。**
   実測が取れるまで、受け入れ条件1を満たしたと書かない。

4. **ルール本文が自分自身の規約に違反していないこと。** 良い例／悪い例として載せるコマンド断片に、
   `git` と `commit` / `push` を連続させた文字列を書かない（書くとこのファイルを扱うBash呼び出しで
   hookが誤発火する）。言い換えるか、行を分ける。

5. **DDR番号の重複が無いこと。** `.claude/docs/ddr/` に 0059 が1つだけであることを確認する
   （最終確認は flow-id 5-1 の `check-base-conflicts.sh`）。
