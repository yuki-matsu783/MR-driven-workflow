# 【AIアセット反映】削除済みパスの扱いをcommitスキル・git-workflowへ反映

- issue: [#60](https://github.com/yuki-matsu783/MR-driven-workflow/issues/60)
- 全体作業計画: `plans/cheeky-baking-lantern.md`
- 対象flow-id: 4-6（2周目。設計反映の完了・レビュー後に着手する）

## 目的

**実行して失敗して初めて気づく**状態を解消する。issue #36・#55 の flow-id 5-1 では、削除を含む
コミットに失敗してからその場で2段構えの回避策を編み出しており、同じ発見を毎回やり直していた。
AIエージェントが**事前に読むファイル**（スキル・ルール）へ書くことで再発を止める。

## 作業内容

### 1. `.claude/skills/commit/SKILL.md` の絶対ルールへ注記を添える

対象は「**`git add .` / `git add -A` は使わない** — 必ず個別ファイル指定」（32行目付近）。

- 呼び出し側の禁止は**維持する**（緩めない）
- 添える内容: 削除済みファイルのパスも、他のファイルと同じように `--` の後ろへ並べてよいこと。
  `git rm` で先に削除をステージしてから残りを渡す2段構えは**不要**であり、むしろそれを行うと
  当該パスが index から消えて後続が失敗すること
- Step 3（ファイルフィルタ）にも、削除されたファイルは除外対象ではない旨が読み取れるようにする
- 参照先として `.claude/docs/spec/create-commit.md` を示す

**`-A` を採用しなかったため、当初想定していた「ラッパー内部のパス限定 `-A` は例外」という
注記は不要になった**（全体作業計画の想定からの変更点）。絶対ルールは文言どおりのまま成立する。

### 2. `.claude/rules/git-workflow.md`「コミット運用」節へ追記する

- 削除を含むコミットもラッパーへそのまま渡せること（issue #60）
- 既に削除がステージされているパスを渡した場合は、冪等にスキップして通知するだけであること
- 参照先として `.claude/docs/spec/create-commit.md` を示す
- 分量は数行に留める（詳細はspecが正史。ルール側へ仕様を二重記載しない）

### 3. `.claude/rules/shell-script-style.md` への追記を検討する

今回の作業で得られた、**このリポジトリの他のスクリプトにも当てはまる**知見のみを対象とする。

| 候補 | 追記するか |
|---|---|
| コマンド置換 `$(...)` の中で `-z`（NUL区切り）出力を受けると `ignored null byte in input` 警告が出る。出力の中身を使わず「1件でもマッチしたか」だけ見るなら `-z` は不要 | **追記する**（既存の「文字コード」節または「JSON操作」節の近く。他のgit系スクリプトでも踏みうる） |
| 判定ロジックを差し込む際、判定単位（パス文字列 対 pathspec）が元の実装と同じかを疑う | **追記する**（「テスト」節。合成フィクスチャの教訓と同系統で、既存記述に1〜2行で接続できる） |
| テストのgrepパターンは `^plans/` のように位置を固定する | **追記しない**（一般的すぎる。specの検証手順に留める） |

**判断基準**: 「今回限りの話ではなく、次に別のスクリプトを書くときにも効くか」。
効かないものはworklog・specに留め、ルールへは持ち込まない。

## 検証

- 変更した各ファイルのfrontmatterを壊していないこと
- SKILL.md の絶対ルールが、**呼び出し側に対する禁止として弱まっていない**こと
  （「使わない」の断定を維持する）
- 参照先 `.claude/docs/spec/create-commit.md` が、設計反映（1周目）で作成済みであること

- `AGENTS.md` `CLAUDE.md` への追記（コミットの細目はスキル・ルール側の粒度）
