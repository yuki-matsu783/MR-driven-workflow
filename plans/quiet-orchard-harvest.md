# 全体作業計画: 収穫（逆輸入）スキルの新設 — issue #27

## 目的

配布先プロジェクトで加えられたAIアセットの改善のうち、汎用的で価値のあるものを本家へ取り込む
「収穫（逆輸入）」スキルを新設し、配布（issue #26: `apply-mr-workflow-to-project`）と収穫の
双方向プロセスを完成させる。

issue #26 で整備済みの土台（`.claude/dist-layers.json` の5層定義・配布先の
`.claude/.asset-manifest.json`（適用元コミットSHA・ファイル別のLF正規化sha256））を前提とする。

## 変更対象（領域粒度）

| 領域 | 何をするか |
|---|---|
| `.claude/skills/<収穫スキル>/`（新規） | SKILL.md と収穫スクリプト（`scripts/`）。配布対象外（本家専用）とする想定 |
| `.claude/scripts/test/` または スキル配下 | 収穫スクリプトの純粋ロジックの単体テスト（置き場所はフェーズ2で確定） |
| `.claude/rules/` または既存ルールファイル | 「配布先で機構に関するDDRを書かず本家へissue起票する」運用規約の明文化（配布物に含まれる場所へ置く） |
| `.claude/dist-layers.json` | 新スキルの層エントリ追加（`exclude` 想定。`apply-mr-workflow-to-project` と同じ理由） |
| `.claude/docs/spec/` `.claude/docs/ddr/` | フェーズ4で仕様書・意思決定記録を反映 |

## 方針

- **読み取り専用の分析＋人間の選択＋既存フロー接続**という構成にする。収穫スキル自身は本家の
  `.claude/rules/` `.claude/skills/` `.claude/docs/` を直接書き換えない（出口は issue 起票
  （`issue-create` スキル経由）または個別作業計画草案の作成まで）。
- 差分検出は配布先の `.claude/.asset-manifest.json` の記録sha256と現在内容の比較で行い、
  `core` / `merge` 層の modified / added / deleted を抽出する。
- 3-way突き合わせ（base=`git show <記録SHA>:<path>`、ours=本家HEAD、theirs=配布先現在）で
  「衝突なし／衝突あり」へ仕分ける。
- manifestが無い配布先（issue #26 以前の適用）では縮退モード（層分け定義に含まれる全ファイルを
  本家HEADと差分表示）で動く。
- 複数の配布先ローカルパスを一度の実行で受け取れる。
- 判断材料（`ai-asset:` prefix コミットの有無・変更回数・プロジェクト固有語の含有）を提示する。

## フェーズ2〈調査〉

実施する。個別調査計画（`plans/【調査】〜.md`）を作り、次の問いに答える。

1. manifest の正確な形式と `merge` 層の指紋の記録形（`install-to-project.sh` の実装読解。
   issue #27 コメントの「merge層の指紋は記録のみで読む側が無い」の確認）
2. 収穫スクリプト・単体テストの置き場所の規約（`install-to-project.sh` がどうテストされているか）
3. 3-way突き合わせの実装手段（`git merge-file` / `git show <SHA>:<path>` の可否と、記録SHAが
   本家リポジトリに存在しない場合の縮退）
4. 縮退モード（manifest無し）で層分け定義から対象ファイルを列挙する方法
5. 出口レベル2種（issue起票のみ／個別作業計画草案）の実装接続点（`issue-create` スキル・
   `create-issue.sh` のインターフェース）
6. DDR運用規約の明文化先（配布物に含まれ、かつ二重管理にならない場所）
7. 判断材料3種（コミットメッセージ・変更回数・固有語）を配布先リポジトリから取得する方法と限界

## フェーズ3〈作業〉

調査結果をもとに個別作業計画（`plans/【AIアセット作成】【実装】【テスト】〜.md`）を立て、
収穫スキル（SKILL.md＋スクリプト＋単体テスト）と運用規約の明文化を実装する。

## フェーズ4〈反映〉

flow-id 4-1 で反映対象を洗い出す（ここでは枠のみ置く）。見込みの候補:

- `.claude/docs/spec/asset-harvest.md`（仕様書・新規）と DDR `i0027-01`（方式選定の経緯）
- `.claude/docs/spec/asset-distribution.md` への相互参照追記（merge層指紋の読む側が出来た旨）
- `.claude/docs/usecase/` への逆引き文書追加の要否確認
- 作業中に気づいたアセット不備の反映（4-1 の洗い出し手順で確定）

## フェーズ5〈クローズ〉

通常どおり実施する（コンフリクト検知・関連issue通知・`.gemini/` 変換同期・統括レポート・片付け・
Draft解除）。マージは人間が行う。

## やらないこと（スコープ外）

- 収穫スキルによる本家正史（`.claude/rules/` `.claude/skills/` `.claude/docs/`）の直接書き換え
  （issue の受け入れ条件で明示的に禁止されている）
- GitLab MCP 対応・リモート配布先（同一マシン上に無い配布先）の収穫（issue が「配布先は
  同一マシン上にある前提」と明示）
- 配布側（`install-to-project.sh`）の機能変更（manifest形式の変更等はしない。読むだけ）

## 非対話セッションでの進め方（この回の特記）

- ユーザー指示により、各フェーズの計画 commit/push 後と作業実施 commit/push 後に敵対的レビュー
  （`adversarial-review` スキル）を自動起動し、指摘を修正しながら進める（非対話モードのため
  自律起動が許可される。各フェーズ上限3回の範囲内＝計画1回＋実施1回）。
- 人間レビューのステップ（2-3/2-8/3-3/3-8/4-3/4-8 等）は待てないため、該当ループの進捗記号は
  `[]` のまま残し、実施内容は HANDOFF.md「やったこと」へ文章で補足する。
- 敵対的レビューの指摘へは、修正後に同スレッドへ返信し、未返信スレッド0を維持する。

## 検証（issue全体として何が満たせたら完了か）

issue #27 の受け入れ条件に対応する。

| 受け入れ条件 | 対応 |
|---|---|
| 配布先で `core` 層を変更→変更ありとして列挙 | 収穫スクリプトの差分検出＋単体テスト |
| 本家も同一ファイル変更→衝突ありとして区別 | 3-way仕分け＋単体テスト |
| 配布先の新規追加ファイルが候補として列挙 | added検出＋単体テスト |
| 配布先の削除ファイルが削除として列挙 | deleted検出＋単体テスト |
| manifest無しでも縮退モードで差分一覧 | 縮退モード実装＋単体テスト |
| 複数の配布先パスを一度に指定できる | スクリプトの引数設計＋単体テスト |
| 出口レベルが確認され、選ばれたレベルで停止。本家正史は直接変更されない | SKILL.md の手順設計（スクリプトは読み取り専用） |
| issue起票を選んだ場合 `issue-create` スキル経由 | SKILL.md の手順で接続 |
| 配布先での機構DDRの扱いに関する規約が配布物のルールに記載 | ルールファイルへの明文化（配布層 `core`） |
