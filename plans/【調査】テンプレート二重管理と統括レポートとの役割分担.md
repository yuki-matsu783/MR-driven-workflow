# 【調査】テンプレート二重管理と統括レポートとの役割分担

issue #145 / PR #187 / 全体作業計画 `plans/mellow-archiving-lantern.md`（flow-id 1-4）

## 前提（合意状況）

- 上位の計画: `plans/mellow-archiving-lantern.md`（flow-id 1-4 で作成。**非対話セッションのため
  flow-id 1-5 の人間合意は実施していない**）。
- 見出し構成そのもの（10節・順序）は issue #145「期待する動作」で確定済みであり、**この調査の
  対象外**である。調べるのは「どう実装するか」に限る。

## この計画で何をするか

フェーズ3（個別作業計画）を書けるようにするため、次の5つの問いへ答える。**答えは
`reports/` の調査結果mdへ書き、この計画には書かない。**

### 問1. テンプレートファイルと `describe` 節の二重管理をどう解消するか

現状、同じ雛形が `.github/pull_request_template.md` / `.gitlab/merge_request_templates/Default.md` と
`.claude/skills/issue-mr-flow/references/review-loop.md` の `describe` 節の3箇所にある。
テンプレート側のコメントは「SKILL.md（現 `review-loop.md`）が正」と書いている。

調べること:

- 案A（`describe` がテンプレートファイルを読み込む）が成立するか。
  - (a) MCP経路（`gh`/`glab` CLI不在）でも動くか。`describe` は最終的に本文を文字列で渡すため、
    ローカルファイルの読み込みは経路に依存しないはずだが、**GitHub/GitLabのどちらのファイルを
    読むかの判定**が必要になる。`get_provider` で判定できるか。
  - (b) 配布先で、テンプレート2本が `.claude/dist-layers.json` のどの層に属するか。
    `core`（配布元所有・上書き）なら読み込み方式が安定するが、`seed`/`merge` なら配布先の
    改変が入りうる。
  - (c) 配布先がテンプレートを改変していた場合に何が起きるか（`describe` の出力が配布先ごとに
    変わってよいのか）。
  - (d) テンプレートのHTMLコメントを、生成するdescriptionへそのまま持ち込んでよいか
    （GitHub/GitLab上では表示されないが、本文が長くなる）。
- 案B（テンプレートを正とし、`describe` 節は見出し名だけを列挙して雛形を持たない）。
- 案C（`describe` 節を正とし、テンプレート側から重複を削って参照だけにする）。
  - GitHub/GitLabはテンプレートファイルの中身をそのままPR作成画面へ入れるため、
    「参照だけ」にすると人間が手で作るPRで見出しが得られない。この副作用の大きさを見積もる。

**判定基準**: 「見出し構成を1箇所直せば、テンプレート・`describe` の両方が追随するか」と
「人間が手でPRを作るときにも見出しが得られるか」を両立できるか。

### 問2. #111（flow-id 5-4 の統括レポート）との役割分担

issue #111 は PR #144 でマージ済みで、flow-id 5-4 が稼働している。**廃止ではなく棲み分けを定義する。**

調べること:

- flow-id 5-4 が実際に何を作り、どこへ何を投稿するか（`references/phase5-close.md`・
  `.claude/docs/spec/` の該当箇所）。
- 内容が重複する範囲はどこか（「検証」「反映先」「残課題」あたりが競合しうる）。
- MR descriptionは `describe` により**6回全文置換される**のに対し、サマリコメントは**1回だけ
  投稿される**という寿命の違いが、役割分担の根拠になるか。

### 問3. `plans/` `worklog/` `reports/` 参照禁止をどこにどう書くか

調べること:

- `.claude/rules/docs-workflow.md` の既存記述（「コード・スクリプト内のコメントから参照しない」）が
  どの節にあり、MR/PR本文の話をどこへ足すのが自然か（既存の節の係り先を壊さないか）。
- 「参照しない」だけでは足りず「代わりに何を書くか」まで書く必要があるか
  （実例: `reports/` の内容を要約して本文へ転記する、issue番号とspec/DDRのパスで代替する）。
- 例外を認めるか（レビュー中はまだ削除されていないため、レビュー時点では参照が有効に見える）。

### 問4. 10節構成が `describe` の6回の全文置換と噛み合うか

`describe` は flow-id 2-5/2-10/3-5/3-10/4-5/4-10 の6箇所で本文を**全文置換**する。

調べること:

- 各時点でまだ書けない節（`## レビューの結果`・`## 検証`・`## 受け入れ条件との対応`）の扱い。
  「特になし」と書くのか、「未実施」と書くのか、フェーズ名を添えるのか。
- 「固定見出しは残す」というルールと、6回置換のたびに全節を再生成するコストの兼ね合い。
- 前回のdescriptionの内容が失われないか（全文置換なので、前回書いた内容を引き継ぐには
  読み直しが要る）。**これは現行の2節構成でも同じ問題があるはずで、実態を確認する。**

### 問5. 配布物としての影響

調べること:

- `.claude/dist-layers.json` におけるテンプレート2本の層（問1(b)と同じ調査で兼ねる）。
- `.gemini/` への変換同期（flow-id 5-3）の対象に、テンプレート2本・`review-loop.md` が
  含まれるか。含まれるなら、変更後に `sync-gemini-assets.sh` の実行が要る。
- `.claude/VERSION` の更新が要るか（配布物の版の更新規則）。
