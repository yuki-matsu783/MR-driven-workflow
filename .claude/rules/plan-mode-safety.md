# Planモードの安全な運用（Claude Code固有）

## planツールを使う場面（issue #9で確定）

**planツール（Planモード＝`EnterPlanMode`/`ExitPlanMode`）は「全体作業計画」の作成にのみ使う。**

Claude Code / Gemini CLI は**セッションごとに1つのplanファイルしか割り当てない**。この制約に
複数の計画を押し込もうとすると計画同士が混ざるため、次のように役割を分ける
（フロー上の位置づけは `.claude/skills/issue-mr-flow/SKILL.md` を参照）。

| 種類 | 作り方 | 置き場所 |
|---|---|---|
| **全体作業計画** | **planツールで作成**。issue（ブランチ）につき**1回だけ** | ハーネスが提示するパス（`plans/<自動命名>.md`）をそのまま使う |
| **個別作業計画** | **planツールを使わない**。Write/Editで直接作成する | `plans/【種別】タスク内容.md` |

### 全体作業計画は「issue（ブランチ）につき1回」

**現在のブランチに既に全体作業計画があれば、planツールで新しい計画ファイルを作らない。**
`.claude/settings.json` の `"defaultMode": "plan"` により新しいセッションは必ずPlanモードで
始まるが、その場合も**既存の全体作業計画を読むだけ**にとどめ、計画ファイルを新規作成しない
（セッションが変わるとハーネスは新しいパスを提示するため、作ってしまうと全体作業計画が
セッションごとに増えてしまう）。

既存の有無は、ブランチ固有のplansファイルを列挙する `get_branch_work_files`
（`.claude/scripts/src/vcs/Provider.sh`）で機械的に判定できる。`plans/【*.md` に一致するものが
個別作業計画、それ以外が全体作業計画である。

## 背景（過去に起きた事故）

`ExitPlanMode` で計画をユーザーに提示する際に、**過去の計画テキストを誤って再送信する事故**が
実際に発生した（2026-08-15、issue #3 のセッション）。同一セッション内で2つ目の計画を提示しよう
とした際、`plan` 引数に「既に承認・実行済みの古い計画」の全文が入った状態で、3回連続して
送信された。直前に対象ファイルをReadしてから転記するという対策をとっても再発した。

原因は、同じ見出し構成（Context／実施内容／対象外／検証方法）の長文が会話履歴内に複数回
出現すると、出現回数の多い側（＝古い内容）へ生成が引っ張られること。当時の `ExitPlanMode` は
長文をテキストとして丸ごと引数に渡す仕様であり、機械的なコピーではなく実質的な再生成になる
ため、この混同が起きやすかった。「気をつける」という意図レベルの対策では防げなかった。

現在の `ExitPlanMode` は `plan` 引数を取らず、ハーネスが提示するパスのファイルから内容を読む
仕様に変わっているため、この事故の直接的な原因自体は解消している。ただし「どの計画を提示して
いるつもりか」を取り違えるリスクは残るため、以下の規則は引き続き守る。

## 守ること

1. **計画の本体はファイルを正とする**
   計画の詳細は `plans/` 配下のファイル本体を正とし、チャットへ全文を再掲しない。長文を
   会話中に繰り返し出現させると、履歴内の類似テキストとの混同リスクが上がる。

2. **既存の承認済み計画の内容を失わない**
   同一セッション内で計画を更新する場合も、既存の承認済み `plans/*.md` の内容を上書きして
   失ってはならない（`docs-workflow.md` の「plansはそのままコミットして履歴に残す」方針と同じ）。
   全体作業計画への追記・個別作業計画の新規作成はいずれも既存内容を保持したまま行う。

3. **送信直前のセルフチェック**
   `ExitPlanMode` を呼ぶ直前に、次の2点を確認してから送信する。
   - ハーネスが提示している `planFilePath` が**今回のタスクの全体作業計画**を指しているか
   - その内容の主題（タイトル・扱うファイル名）が、直前に自分が書いた計画と一致しているか

4. **異常を検知したら再試行せず止める**
   `ExitPlanMode` の返り値（Approved Planのエコー）が意図した内容と違っていた場合、同じ操作を
   繰り返さない。直ちに作業を止めてユーザーに状況を報告する。ツール経由での再現に失敗し続ける
   場合は、計画本文を通常のチャットメッセージとして直接提示し、ユーザーの明示的な確認を得てから
   実装に進む。

5. **承認の取り違えに注意**
   古い計画が「承認済み」の状態になっても、それを根拠に実装を進めてはいけない。ユーザーが
   承認したのは画面に表示された内容であって、こちらが意図した計画とは限らない。表示された内容と
   自分の意図がずれていると気づいた時点で、承認は無効として扱い、取り直す。

## 廃止した対処（履歴）

issue #7・#26 の時点では、**同一セッション内でPlanモードへ再突入するたびにハーネスが直前と
同じパスを提示し続ける**という制約に対し、`archive-reentrant-plan.sh` で1つ前の計画を `_pushN`
付きの別名へ退避してから上書きする、という規則6を設けていた（詳細:
`.claude/docs/ddr/0009-Planモードre-entry時はgit checkout復元でなくarchiveスクリプトで対処する.md`）。

issue #9 で、**planツールの利用を全体作業計画1回に限定する**方針を採ったことにより、
同一セッションで別々の計画をplanツールで作る場面自体が無くなったため、この規則とスクリプトは
廃止した。なお「ハーネスが再突入時に同じパスを提示し続ける」という観測自体は issue #9 の調査
時点でも有効であることを実地確認済みであり、上記の方針はその制約を回避するのではなく、
**制約に触れない運用へ変えた**ものである。
