# bashスクリプトの規約

issue #6でリポジトリ内の開発補助スクリプトを全てPowerShellからbashへ移行した際に定めた規約。
設計方針・移行の経緯は [.claude/docs/spec/shell-scripts.md](../../.claude/docs/spec/shell-scripts.md)
を参照（このファイルは規約のみを記載し、経緯の重複は避ける）。

**対象は「`.sh` ファイルとして保存するスクリプト」である。** AIエージェントがBash/PowerShell
ツールへ渡す**その場限りのコマンド文字列**と `description` の書き方は
[ai-command-style.md](ai-command-style.md) が扱う（issue #47）。

## 前提・保存形式

- 実行環境はgit bash（Git for Windows付属のMSYS bash）。WSL/Linux実機での動作確認は行っていない
  （`.claude/docs/spec/shell-scripts.md`の未決定事項参照）。
- ファイルはUTF-8・**BOM無し**・LF改行で保存する（PowerShellの`.ps1`と異なり、BOMは不要かつ
  有害。シバン行`#!/usr/bin/env bash`の直前にBOMがあるとインタプリタ判定に失敗する処理系がある）。
  **LF改行はリポジトリルートの`.gitattributes`が保証する**（issue #33で導入）。`*.sh text eol=lf`
  により、各開発者の`core.autocrlf`設定に関係なく`.sh`は作業ツリーでもLFで取り出される
  （CRLFで取り出されるとシバン行の解釈に失敗し`bash: $'\r': command not found`になる）。
  この指定は他プロジェクトへの配布時にも配布先の`.gitattributes`へ追記される。配る行の定義・
  追記の仕組みは[.claude/docs/spec/distribution-assets.md](../docs/spec/distribution-assets.md)を参照。
- 先頭に `#!/usr/bin/env bash` を置く。

## エラー方針

- スクリプト冒頭で `set -euo pipefail` を宣言する（PowerShellの`$ErrorActionPreference = "Stop"`
  相当。「失敗したら即座に止まる」を既定にする）。
- **bashでのtry/catch相当の書き方**: 「失敗を検知しつつ処理を継続したい／握りつぶしたい」箇所は、
  該当処理を関数化し、**フォークされる側の内側で `set -e` を掛け直して**呼ぶ。出力の要否で2形。
  ```bash
  # 出力を捨ててよい場合（サブシェル。条件文脈に入れない）
  set +e
  ( set -e; risky_func )
  rc=$?
  set -e
  if [ "$rc" -ne 0 ]; then fallback; fi

  # 出力を受け取る場合（コマンド置換の内側で set -e を掛け直す。
  # 外側の set +e だけでは inherit_errexit 既定オフのため効かない）
  set +e
  out="$(set -e; risky_func)"
  rc=$?
  set -e
  if [ "$rc" -ne 0 ]; then fallback; fi
  ```
  - **理由（原因は2つあり、混同しないこと。いずれも bash 5.2.21 で実測。実測の詳細・却下案は
    DDR `i0027-02` が正）**:
    1. bashは`if cmd; then...else...fi`や`cmd1 || cmd2`のような条件式の中では、`set -e`による
       「コマンド失敗時に即座にシェルを終了する」動作が一時停止される仕様があり、この一時停止は
       **明示サブシェル `( func )` の内側にまで伝播する**。`( func ) || rc=$?` と書くと、
       関数内の複数コマンドが途中で失敗しても最後まで実行され続けてしまう（サブシェル自体は
       `-e`を継承しており、条件文脈の**外**なら `( func )` 単体で正しく即時終了する）。
    2. **コマンド置換 `$(...)` は `shopt inherit_errexit`（既定オフ）のため、条件文脈かどうかに
       関係なく `-e` を一切継承しない**。`out="$(func)"` は条件文脈の外でも関数本体が最後まで
       走る。「条件文脈の外へ出せばコマンド置換でも即時終了する」と読める書き方をしないこと
       （`inherit_errexit` を立てて回避する案は、bash 4.4未満で使えない・既存コードへの副作用が
       広い・機構1には効かない、の3点で却下した。DDR `i0027-02`）。
  - 上記2形は、フォークされた側で`set -e`を掛け直すことで両方の機構を一様に回避する
    （実測: 途中失敗が rc=1 に現れ、出力受け取り形では out が空になる）。
  - **従来の `if result="$(risky_func)"` パターンは、関数の最終コマンドの失敗しか検知できない**
    （機構2により途中の失敗は素通りする）。最後のコマンドの成否だけ分かればよい場合に限って
    使い、複数コマンドから成る関数の途中失敗を検知する目的には使わない。既存の実例
    （`.claude/hooks/session-start.sh` の `build_context`、
    `.claude/hooks/post-push-usage-report.sh` の `main`）はこの制約に照らした見直し候補である
    （必要になった時点で別issueで扱う）。
  - 実例: `.claude/skills/harvest-from-projects/scripts/harvest-from-projects.sh` の `cmd_scan`
    （配布先単位のエラー隔離。**本家専用スキルのため配布先にはこのファイルは存在しない**——
    配布先では上記のコード例2形を直接参照すること）。

## JSON操作

- JSONの生成・パースは `jq` を使う（PowerShellの`ConvertFrom-Json`/`ConvertTo-Json`相当。新規の
  外部依存としてインストールが必要。`.claude/docs/spec/shell-scripts.md`「前提」参照）。
- 関数の戻り値はPSCustomObjectに代えてJSON文字列をstdoutへ出力する設計にする。呼び出し側は
  `jq`でフィールドを取り出す（例: `get_issue 6 | jq -r '.title'`）。JSONのキー名はPascalCaseでは
  なくcamelCase（`number`/`title`/...）に統一する。
- Windows PowerShell 5.1の`ConvertFrom-Json`が`-AsHashtable`を持たないための回避策
  （`ConvertTo-HashtableDeep`等）は、jqのネイティブなJSON操作機能により不要になる。移植の際に
  引き継がないこと。
- **Windows版jq（`C:\Program Files\jq\jq.exe`等のネイティブ実行ファイル）は`strptime`/`mktime`が
  未実装**（実機確認: `jq -n '"..." | fromdateiso8601'` が
  `strptime/1 not implemented on this platform`で失敗する。issue #28対応時に判明）。
  `fromdateiso8601`/`fromdate`/`strptime`/`mktime`はいずれも内部で`strptime`/`mktime`を使うため
  **使用不可**（日付文字列→エポック秒の変換に使えない）。`gmtime`/`strftime`（エポック秒→日付文字列の
  向き）は問題なく動作する。日付文字列→エポック秒の変換が必要な場合は、`strptime`に依存しない
  自前実装（`days_from_civil`アルゴリズムによる四則演算のみの変換）を使う。実装例・境界値検証は
  `.claude/hooks/lib/UsageTracking.sh`の`epoch_from_iso8601`を参照。
  - 加えて、この`strptime`未実装エラーが、直前段階の`try ... catch empty`と組み合わさると、
    jqがエラーメッセージを一切出さず出力全体が`null`になるという実機確認済みの現象があった
    （原因調査が非常に困難だったため記録に残す）。日付変換を含むjqフィルタを`try/catch`と
    組み合わせる場合は、この現象を疑ってまず日付変換部分だけを単体で動作確認すること。
- **`jq --args`へ可変長の値を位置引数として渡すときは、フィルタの直後に`--`を置く**（issue #69で
  実際に踏んだ）。`--`が無いと、`-A`のように**ハイフンで始まる値**をjqがオプションとして解釈し
  `jq: Unknown option -A`（終了コード2）で失敗する。値は自分で決めた固定文字列とは限らず、
  markdownのfrontmatterやユーザー入力に由来しうるため、「今は先頭がハイフンの値が無い」ことを
  前提にしてはいけない。

  ```bash
  # 悪い例（要素に -A があると jq: Unknown option -A で落ちる）
  jq -nc --args '$ARGS.positional' "${items[@]}"
  # 良い例（-- 以降はすべて位置引数として扱われる）
  jq -nc --args '$ARGS.positional' -- "${items[@]}"
  ```

  **この失敗は気づきにくい**。`extract-frontmatter.sh`では、jqの失敗直後に`return 0`が書かれて
  いたため終了コードが握りつぶされ、`index.jsonl`へ空行が1行入るだけで正常終了しており、
  該当ファイルがインデックスから丸ごと欠落していた。**jqの終了コードを`return 0`等で捨てない**
  こと（`status=0; jq ... || status=$?; return "$status"` のように伝播させる）。

  **同じ「先頭がハイフンの値」の問題は`grep`でも起きる**（issue #97で実際に踏んだ）。
  `grep -cF '- 使用モデル:'` のようにハイフンで始まるパターンを渡すと
  `grep: unknown option --` で失敗する。パターンだと明示する印が要る（jqの `--` に相当。grepでの
  推奨形は下記のとおり `-e`）。パターンは自分で決めた固定文字列で
  あっても、markdownの箇条書き（`- `）やコマンドラインオプションを検索したい場面で普通に
  ハイフン始まりになる。

  ```bash
  # 悪い例（grep: unknown option -- で落ちる）
  grep -cF '- 使用モデル:' "$file"
  # 良い例（`-e` でパターンだと明示する。下記のとおり `--` より安全）
  grep -cF -e '- 使用モデル:' "$file"
  ```

  **逆に、`--` を前へ置きすぎるとオプションが無効になる**（issue #185で実際に踏んだ）。
  `--` 以降はすべて非オプション引数として扱われるため、`--include` のようなオプションを
  `--` の**後ろ**へ置くと、grepはそれを**検索対象のファイル名**として受け取る。

  ```bash
  # 悪い例（grep: --include=*.md: No such file or directory）
  grep -rn -- '--message "' --include='*.md' .claude
  # 良い例（オプションはすべて -- より前に置く）
  grep -rn --include='*.md' -e '--message "' .claude
  ```

  **この失敗は「フィルタが効かないまま全件走査になる」形で現れる。** stderrへ
  `grep: --include=*.md: No such file or directory` が出るものの、**残りの引数での検索はそのまま
  実行され、結果が返る**ため、出力だけを見ていると気づかない。issue #185では、絞ったつもりの
  検索が絞られていないまま**件数が偶然一致していたため、検証を素通りした**。件数を根拠にする
  ときは、stderrを捨てずに見ること。

  **ハイフン始まりのパターンは、`--` ではなく `-e` で渡す。** 上の issue #97 の記述は「jqと同じく
  `--` を置く」としていたが、**両方を挙げるのではなく `-e` を正とする**（上の良い例も `-e` へ
  揃えた）。`--` はパターン以外にオプションを取らない呼び出しでしか安全に使えず、後から
  `--include` のようなオプションを足したときに無言で壊れる。`-e` は並び順に依存しない。

  **同じ「ハイフン始まりの引数」の問題は bash 組み込みの `printf` でも起きる**（issue #145で
  実際に踏んだ）。**書式文字列が `-` で始まると、`printf` はそれをオプションとして解釈しようとして
  失敗する**（`printf: --: invalid option`、終了コード2）。変数を書式側へ置くと踏みやすい。

  **バックスラッシュでエスケープしても直らない。** `printf '\-\->\n'` はシングルクォート内なので
  バックスラッシュがシェルに落とされず、`printf` が受け取る書式の先頭は `\` になる。そのため
  オプション扱いにはならない代わりに、`\-` が未定義エスケープとして**そのまま出力される**
  （実測: `\-\->` が出て終了コード0）。**エスケープはこの問題の対処ではなく、症状を
  「落ちる」から「黙って違う値が出る」へ変えるだけである**——後者のほうが気づきにくい。

  **書式文字列がハイフンで始まりうるなら、`printf '%s\n' "$s"` の形にして書式側へ値を持ち込まない。**

  ```bash
  # 悪い例1（printf: --: invalid option で落ちる。終了コード2）
  s='-->'; printf "$s\n"
  # 悪い例2（落ちないが \-\-> がそのまま出る。終了コード0なので気づかない）
  printf '\-\->\n'
  # 良い例（値は %s 側へ渡す）
  printf '%s\n' '-->'
  ```

- **大きなJSONを`--argjson`/`--arg`等のコマンドライン引数としてjqへ渡さない**（issue #37対応時に
  実機確認: 対応工数レポートの集計で、外部ファイル・コマンド出力等に由来する可変長のJSON
  データを`jq -n --argjson entries "$data" ...`という形で渡していたところ、データが数十KB程度
  （実例: transcriptの新規行32件、約120KB）でも`jq: Argument list too long`（終了コード126）で
  jqの起動自体が失敗した。Windowsのプロセス生成時のコマンドライン長上限（実測でおよそ32KB程度）に
  容易に達するため）。**渡すデータのサイズがファイルサイズ・ユーザー入力等に応じて可変・無制限に
  なりうる場合は、一時ファイルへ書き出すか、そもそも元のファイルパスをjqへ渡して`-R -n`と
  `inputs`でjq側に読ませる**（`.claude/hooks/lib/UsageTracking.sh`の`_usage_aggregate_transcript`/
  `_usage_aggregate_new_lines`が実例。後者は元々「シェル変数へ切り出してから引数で渡す」2関数
  構成だったが、この問題が判明し1関数（常にファイルパスを渡す設計）へ統合した）。`--argjson`/
  `--arg`が安全なのは、渡す値のサイズが呼び出し元のロジックで明確に小さいと保証できる場合
  （集計済みのサマリ値、固定長の設定値等）に限る。**この問題はコマンドの起動自体が失敗するため、
  失敗時に何もエラー出力が無いように見えるケース（`set -e`配下でエラーメッセージが握りつぶされる
  呼び出し方をしている場合）もあり、`jq: Argument list too long`という文言を直接見ないまま
  「処理が急に動かなくなった」としか気づけないことがある点に注意する。**
- **上記の失敗が別の関数へ波及して恒久化するケースに注意する**: あるjq呼び出しが上記の理由で
  失敗し、その戻り値を状態ファイルへ書き込むはずだった処理が（`set -e`により）実行されないまま
  終わっても、**それより前の別の書き込み処理が既に完了している場合**、ファイルが空／壊れた
  状態のまま残ることがある（issue #37の対応工数レポートで実際に発生: 状態ファイルが0バイトに
  壊れた状態で、カーソル的な位置情報だけが正常に進んでいた）。壊れた状態ファイルを次回`--argjson`で
  読み込もうとすると、空文字列は不正なJSONとして扱われ**同じ理由で毎回失敗し続け、恒久的に
  回復不能になる**。外部状態ファイルを読み込んで`--argjson`等へ渡す前には、内容が空でなく
  有効なJSONであることを検証し（例: `[ -n "$content" ] && printf '%s' "$content" | jq -e .
  >/dev/null 2>&1`）、無効なら「状態なし」の既定値にフォールバックする自己回復ロジックを
  入れておくと安全（`sync_usage_state`の`existing`読み込みが実例）。
  - **`jq -e .`は空文字列の入力に対して失敗を検知できないことがある**（実機確認:
    `printf '%s' "" | jq -e .`が終了コード0を返した）。空文字列チェック（`[ -n "$content" ]`）を
    `jq -e .`の判定より先に行うこと。
- **`配列 | index(.field)` のように、パイプの右辺で `.` を参照すると、フィルタ内の `.` が
  パイプ元（左辺）の値に置き換わる**（issue #182対応時に実際に踏んだ）。`.` はパイプが進むたびに
  更新されるため、`$known | index(.severity)` と書くと `.severity` は各要素ではなく `$known`
  （配列）に対して評価され、`jq: error: Cannot index array with string "severity"` になる。
  `select()`・`map()`の内側で「今見ている要素のフィールド」と「外側の配列」を両方使いたい場合は、
  **先に要素側のフィールドを変数へ束縛してから、外側の配列をパイプする。**

  ```bash
  # 悪い例（.severity が $known に対して評価される）
  jq -n '["blocker","major"] as $known | [{severity:"nit"}] | map(select(($known | index(.severity)) == null))'
  # 良い例（.severity を先に $sv へ束縛する）
  jq -n '["blocker","major"] as $known | [{severity:"nit"}] | map(select(.severity as $sv | ($known | index($sv)) == null))'
  ```

## 外部プロセス起動のコスト

**git bash（MSYS）の外部プロセス起動は約95ms/回**（実機計測: `jq -nc '1'` を50回実行して4.73秒 =
94.6ms/回）。Linuxのfork/execと比べて桁で遅く、**ファイル数に比例して外部コマンドを起動する
スクリプトは、アルゴリズムではなく起動回数だけで所要時間が決まる**。

issue #11の実例: `extract-frontmatter.sh` がfrontmatterのキー・配列要素ごとに`jq`を呼んでおり、
1ファイルあたり約30回 × 43ファイルでリポジトリルート一括実行が2分でタイムアウトしていた。
起動回数を1ファイル1回へ減らすことで**136秒→約10秒**になった（詳細:
[.claude/docs/spec/extract-frontmatter.md](../docs/spec/extract-frontmatter.md)「性能」、
[.claude/docs/ddr/i0011-01-frontmatter抽出は1ファイル1回のjq呼び出しとmtimeキャッシュで高速化する.md](../docs/ddr/i0011-01-frontmatter抽出は1ファイル1回のjq呼び出しとmtimeキャッシュで高速化する.md)）。

- **ループ内で`jq`等の外部コマンドを呼ばない。** 処理対象ごとに1回まで、可能なら実行あたり1回に
  集約する。JSONの組み立てなら、シェル配列へ中間表現を溜めて`jq --args`へまとめて渡し、jq側で
  `reduce`する（引数長の上限に注意。上記「JSON操作」節）。
- **コマンド置換 `$(...)`・パイプもサブシェルをforkするため、同じコストを持つ。** 「外部コマンドを
  呼んでいないから安全」ではない。実例として、`jq`起動を1ファイル1回へ減らした後も
  `part="$(unquote "$(trim "$x")")"` のような書き方が残っていたために9.7秒かかっており、これを
  除いて3.0秒になった（同じ処理で3倍の差）。
- **ホットパスの小さなヘルパー関数は、標準出力ではなくグローバル変数 `REPLY` へ返す。**
  bashの`read`が使う慣習に合わせた命名で、呼び出し側はコマンド置換なしで結果を受け取れる。

  ```bash
  # 悪い例（呼ぶたびにサブシェルをfork）
  trim() { local s="$1"; ...; printf '%s' "$s"; }
  value="$(trim "$line")"

  # 良い例（forkなし）
  trim_to_reply() { local s="$1"; ...; REPLY="$s"; }
  trim_to_reply "$line"
  value="$REPLY"
  ```

- **`REPLY` へ返す形が要るのは、性能のためだけではない。戻り値が複数ある関数（本体＋メタ情報）も
  同じ形にする。** コマンド置換で受けるとサブシェルへforkするため、**関数内で設定した他の
  グローバル変数が呼び出し元へ伝わらない**（issue #43で実際に踏んだ。断面のソースを返す
  `read_source_at_ref` を `content="$(read_source_at_ref ...)"` で受けたところ、同時に設定して
  いた `REVIEW_SOURCE_REF` / `REVIEW_SOURCE_NOTE` が空のままになり、`set -u` 配下で
  `REVIEW_SOURCE_REF: unbound variable` として表面化した）。**ホットパスでないから標準出力で
  よい、とは判断しないこと。** 戻り値が2つ以上なら `REPLY` ＋専用のグローバル変数へ返し、
  関数名を `*_to_reply` にして呼び出し側へ示す（実例: `Provider.sh` の
  `read_source_at_ref_to_reply`、`split_remote_url` の `REPLY_HOST` / `REPLY_PATH`）。

  ```bash
  # 悪い例（サブシェルへforkするため REVIEW_SOURCE_REF が呼び出し元へ伝わらない）
  content="$(read_source_at_ref "$sha" "$path")"
  ref="$REVIEW_SOURCE_REF"
  # 良い例
  read_source_at_ref_to_reply "$sha" "$path"
  content="$REPLY"
  ref="$REVIEW_SOURCE_REF"
  ```

- **`REPLY`やその他のグローバル変数へ結果を返す関数は、パイプではなくヒアストリングで呼ぶ。**
  `cmd | func` の右辺はサブシェルで実行されるため、代入が呼び出し元へ伝わらない
  （関数は正常に動いているのに変数だけが空、という形で表面化するので気づきにくい）。

  ```bash
  printf '%s' "$block" | parse_block   # NG: 代入がサブシェルに閉じる
  parse_block <<<"$block"              # OK
  ```

- **標準出力へ返す関数をループの中で何度も呼ぶ必要がある場合は、ループ全体を1つのプロセス置換
  `< <( ... )` の中へ入れる**（issue #42）。`$(...)` を要素ごとに書くとそのたびにforkするが、
  同じ関数呼び出しでも、既にforkされたサブシェルの中で標準出力へ書く分には**追加のforkは
  発生しない**。これにより「関数は標準出力へ返す」という既存のインターフェースを崩さないまま、
  fork回数を要素数に依存しない定数へ抑えられる（`REPLY` へ返す形へ書き換えるのは、その関数が
  他所から `$(...)` で使われていない場合に限られる）。

  ```bash
  # 悪い例（要素数 × 2 回forkする）
  for p in "${paths[@]}"; do
    blob="$(get_blob_url "$repo_url" "$ref" "$p")"
    anchor="$(get_diff_anchor_url "$compare_url" "$p")"
    ...
  done
  # 良い例（プロセス置換1回だけforkし、中の関数呼び出しはforkしない）
  while IFS= read -r line; do urls+=("$line"); done < <(
    for p in "${paths[@]}"; do
      get_blob_url "$repo_url" "$ref" "$p"
      get_diff_anchor_url "$compare_url" "$p"
    done
  )
  ```

  この形にすると出力は「1要素あたり固定行数」のフラットな配列になるため、**要素ごとに必ず同じ
  行数を出すこと**（出さない項目がある場合は空行を出して埋める）。行数が可変だと添字と要素の
  対応が崩れる。実例: `.claude/hooks/post-push-compact-prompt.sh` の `build_file_links_text`
  （削除ファイルはblobリンクの代わりに空行を出している）。

- **ディスパッチャの中で毎回外部コマンドを呼んでいないか確認する。** 上のように呼び出し側の
  forkを消しても、呼ばれる関数自身がコマンド置換を含んでいれば意味が無い（issue #42の実例:
  `get_blob_url` → `get_provider` → `$(git remote get-url origin)`）。プロセス内で結果が変わらない
  判定はグローバル変数へメモ化する（`.claude/scripts/src/vcs/Provider.sh` の
  `_PROVIDER_CACHE` が実例）。

- 外部コマンドは、できるものからbash組み込みへ置き換える。

  | 外部コマンド | bash組み込みでの代替 |
  |---|---|
  | `date -d "@$epoch" +%FT%T` | `printf -v var '%(%Y-%m-%dT%H:%M:%S)T' "$epoch"` |
  | `dirname "$p"` | `${p%/*}`（`/`を含まなければ`.`） |
  | `basename "$p"` | `${p##*/}` |
  | `cat file` | `$(<file)`（forkは1回で済む） |
  | `tr -d '\r'` | `${var//$'\r'/}` |
  | `realpath --relative-to=X Y` | 基準ディレクトリへ`cd`しておき相対パスを直接扱う |
  | ファイルごとの`stat -c %Y` | `printf '%s\0' "${files[@]}" \| xargs -0 stat -c '%Y'` で一括取得 |

- **どうしても起動回数を減らせない場合は、そもそも実行しない工夫（キャッシュ）を検討する。**
  `extract-frontmatter.sh`は、mtimeが変わっていないファイルの結果を前回の出力から再利用することで、
  差分が無いときの所要時間を約2秒にしている。

- **「起動回数がゼロである」ことを計測で確かめるときは、必ず空関数をベースラインに取り、その差で
  見る**（issue #55で実際に誤った結論へ飛びかけた）。ループ構文・時刻取得そのものがforkを伴うため、
  素朴に測ると**ゼロであるはずのものが必ず正の値になる**。その値をそのまま関数のコストと読むと、
  存在しないforkを実装の中に探し始めることになる。
  - 実例: 外部コマンド・コマンド置換・パイプを一切含まない `split_remote_url` を20回ループで
    測ったところ177ms（約9ms/回）と出た。「見落としたforkがある」と疑ったが、実際は `$(seq 20)` と
    `date` 自体のfork・試行回数の少なさによるノイズだった。
  - **試行回数を十分に取る。** 上の例では20回では判別できず、200回で初めて差が見えた。1回あたりの
    差が0.1ms前後なのに対し、ベースライン自体のゆらぎが数msあるため。

    | 計測対象（200回） | 所要 | 空関数との差 |
    |---|---|---|
    | 空関数 `noop` | 80ms | — |
    | `split_remote_url` | 93ms | +13ms（0.065ms/回） |
    | `provider_from_remote_url` | 132ms | +52ms（0.26ms/回） |

  - **比較の基準として、同条件での外部コマンド1回の実測値を併記する**（上の例では `jq -nc '1'` が
    1回138ms）。「差が外部コマンド1回の1/500」という形にすれば、マシン負荷による絶対値のブレに
    左右されずに結論を出せる。
  - **旧実装との性能比較も、同一セッション内に旧実装を再現して連続で測る。** 別のタイミング・別の
    セッションで測った値と突き合わせると、マシン負荷の差がそのまま改善幅として見えてしまう
    （issue #55では、先に測っていた285ms/回と比較しかけたが、同一セッションで測り直すと旧415ms/回
    対 新105ms/回だった）。

  ```bash
  # 計測の骨子。date はループの外に置く（中に置くとノイズが計測対象を上回る）
  noop() { :; }
  bench() { # $1=回数 $2=関数名
    local start end i
    start=$(date +%s%3N)
    # 標準出力へ書く関数を測る場合は捨てる（リダイレクトはforkを伴わないので計測に影響しない）
    for ((i = 0; i < $1; i++)); do "$2" 'https://github.com/o/r.git' >/dev/null; done
    end=$(date +%s%3N)
    printf '%s: %sms\n' "$2" "$((end - start))"
  }
  bench 200 noop              # ベースライン
  bench 200 split_remote_url  # 差がベースラインの数分の一なら fork していない
  ```

- **大量データの走査は、bash単独ループより`grep`等への一括委譲が有利な場合がある。** 上の
  「ループ内で外部コマンドを呼ばない」の否定ではない。指しているのは**外部コマンドをファイル
  ごと・行ごとに呼び直す**設計であり、**まとめて1回だけ**呼ぶ設計とは区別する。測定環境:
  Claude Code on the web（Linux）／2026-08-23。git bash実機では未計測（fork単価が桁違いの
  環境のため、下記の「数万行」という閾値をそのままgit bashへ持ち込まないこと）。issue #171の
  DDR参照切れ検出スクリプトで、リポジトリ全体約37,000行に対する正規表現マッチを実測比較した
  ところ、(a) `git ls-files`で得た各ファイルをbashの`while read`ループ＋`[[ =~ ]]`で1行ずつ
  判定する方式が5.2秒、(b) 全対象ファイルを`grep -nHoE`へ1回で渡す方式が0.96秒だった。目安:
  判定対象の総行数が数万行を超える場合は、ループ＋bash内蔵正規表現よりも一括grepを先に検討する
  （詳細: [DDR i0171-01](../docs/ddr/i0171-01-DDR参照切れ検出は絶対パス形式に限定しgrep一括抽出で実装する.md)）。

### hookの前置フィルタ（issue #70, #159）

**`if`フィールドを持てない・持たないhook**は、対象ツールの呼び出しごとに毎回起動される。
「持てない」のはGemini CLIのhook設定（`if`相当のキーを持たない）、「持たない」のはClaude Code
側で判定対象が単純な文字列一致に収まらずhook自身が本文を読んで判定する必要があるhook
（`block-direct-git-commit.sh`・`post-issue-create-notice.sh`等）である。**push系hook
（`post-push-usage-report.sh`・`post-push-compact-prompt.sh`）はこれに該当しない**——
Claude Code側の`.claude/settings.json`では`if: "Bash(git push*)"`を持っており、Gemini CLI
経路でのみ`if`が効かない（`.claude/docs/spec/issue-mr-workflow.md`「制約」参照）。それでも
Gemini CLI経路の空振りコストを下げるため、issue #70はこの2本にも同型のパターンを適用する
（下記「実例」）。

対象ツールの呼び出しごとに毎回起動されるいずれのhookでも、判定本体（jq呼び出しを含む）へ
入る前に、次の型で
**bash組み込みだけの前置フィルタ**を`main()`冒頭に置くと、空振り（対象外のペイロード）の
コストを空関数と同じ水準（jq起動ゼロ）まで落とせる。

```bash
main() {
  set -euo pipefail
  local raw
  # `|| true` を省かない。`read -d ''` は入力にNULが無いとEOFで非0を返すため、
  # `set -e` 配下では値が取れているのに終了する。
  IFS= read -r -d '' raw || true
  [ -n "$raw" ] || exit 0
  <前置フィルタ関数> "$raw" || exit 0
  # ここから先が既存の判定本体（jq呼び出しを含む）
  ...
}
```

- `read`・`case`はいずれもbash組み込みでforkしない。
- **前置フィルタは、判定本体が検知する入力を1件も取りこぼさない「超集合」でなければならない。**
  取りこぼすと判定本体が実行されず、そのhookの機能そのものが無言で失われる（安全側のhookなら
  ガードの無効化そのものになる）。過剰検知（本体なら素通りする入力を前置フィルタが通すこと）は
  jq呼び出し1回分の無駄で済むため許容してよい——**この非対称ゆえに、前置フィルタは常に
  「緩める」方向へ倒す。**
- **その前置フィルタを、判定本体の代わり（縮退時のフォールバック）へ流用してはいけない**
  （issue #17で実際に踏んだ）。**前置フィルタとブロック判定は、緩めてよい向きが逆である。**

  | | 過剰検知したときのコスト | 倒す方向 |
  |---|---|---|
  | 前置フィルタ（足切り） | jq起動1回の無駄 | **緩める側**（超集合を保つ） |
  | ブロック判定 | **実行の停止** | **締める側** |

  - 「判定ライブラリを読めないときはブロック側へ倒す」という方針自体は妥当だが、**倒した先が
    回復不能では方針として成立しない。** 実例: `block-unchecked-push.sh` の前置フィルタは
    「`push` という語がどこかに現れるか」しか見ないため、これをフォールバックへ流用すると、
    **回復のために叩く `push-checklist.sh check` がパスに `push` を含むせいで必ずブロックされ、
    縮退環境から自力で抜け出せなくなる**。
  - フォールバックは**専用の関数を書く**。実例の `command_hints_at_git_push_degraded` は、
    (1) basename が `git` のトークンがある、(2) その後ろに `push` トークンがある、の**両方**が
    揃ったときだけブロックする。`git` を **AND 条件**にしたことで、回復コマンドは構造的に
    ブロックされない。
  - この形は精密判定の超集合ではなくなる（`eval "git push"` 等を取りこぼす）。縮退時は元々
    best-effort であり、**取りこぼしの害（1回素通りする）より回復不能の害が大きい**という
    判断である。**縮退時のフォールバックを書くときは「この判定が誤って発火したら、
    それを直すためのコマンド自身が止まらないか」を必ず確かめる。**
- **前置フィルタを`main()`内へ直書きせず、独立した純粋関数へ切り出す。** `source`してから
  直接呼ぶ高速な単体テストが書ける（結合テスト——実際にサブプロセスを起動し、`PATH`先頭へ
  「呼ばれたら失敗するスタブ`jq`」を置いて「対象外ペイロードでjqが1回も呼ばれないこと」を
  確認するテスト——と両方用意する）。
- **判定本体が独自の正規化（クォート除去・バックスラッシュエスケープの解決・大文字小文字の
  吸収等）を持つ場合、前置フィルタの比較対象にも同じ正規化を先に施さないと超集合が壊れる。**
  実例（issue #159）: `.claude/hooks/lib/CommandPosition.sh`は`\x`（xが英数字等）のバックスラッシュを
  落としてxだけを残すため、`git com\mit`は判定本体では「commit」として検知されるが、単純な
  `*commit*`部分一致の前置フィルタでは素通りしていた。
- **前置フィルタが受け取るのは、hookへの入力そのもの（jqがデコードする前の生JSON文字列）で
  あることに注意する。** 上のバックスラッシュ除去を`${raw//\\/}`のように単純に行うだけでは
  不十分な場合がある（issue #159で実際に検出）。実コマンド中の1文字（改行・タブ等の制御文字）は
  JSONへエンコードされると2文字のエスケープ列（`\n` `\t`等）になるため、バックスラッシュだけを
  除去すると2文字目（`n`や`t`）が単独の文字として残り、語の分割位置に紛れ込んで超集合が壊れる
  （実例: `git com\<改行>mit`はJSON化すると`com\\\nmit`になり、バックスラッシュだけの除去では
  `comnmit`になって`*commit*`に一致しなくなる）。対策は、JSON文字列エスケープの2文字シーケンス
  （`\\` `\"` `\n` `\t` `\r` `\/` `\b` `\f`）を2文字ともまとめて除去してから、残った
  バックスラッシュ（`\uXXXX`等）を落とすこと。`\\`（エスケープされたバックスラッシュ）を
  最初に処理するのは、`\\n`を`\n`と誤って分解しないため。いずれの除去も単調にマッチ候補を
  増やすだけなので、既存のマッチを壊さない。詳細・実測コード例はDDR `i0159-01`
  「なぜバックスラッシュ1文字だけの除去でも足りないのか」参照。
- **大文字小文字を吸収する比較には`${var,,}`（bash 4.0以降）ではなく、ブラケット式
  （`case "$s" in *[Cc][Oo][Mm]*)`）を使う。** hookは`bash`という起動コマンド名でしか
  呼ばれず、実行環境のbashバージョンを制御できないことがある。判定本体側がbash 4.3未満への
  フォールバックを持つ設計（`command_invokes_git_subcommand`呼び出し前の`BASH_VERSINFO`確認）
  であっても、前置フィルタに`${var,,}`を使うと**そのフォールバックへ到達する前に展開エラーで
  hookプロセスごと落ちる**（issue #159で実際に検出）。
- **`IFS= read -r -d '' raw`は、パイプ入力に対して1バイトずつread(2)する**（bashが区切り文字を
  越えて読み過ぎないための仕様）。小さいペイロードでは無視できるが、大きな`tool_input.command`
  （ヒアドキュメント等。`CommandPosition.sh`が1行8192バイトの上限を持つのも、hookが数十KB〜
  数百KBのコマンド文字列を受け取りうることを前提にしているため）では、read(2)の回数が入力
  バイト数に比例して増える。`fork`が無いため execve/clone の実測には現れないが、
  この特性自体は未計測（git bash実機でしか確度高く確認できない。issue #159の作業結果への
  敵対的レビューで指摘）。大きな入力を扱う可能性があるhookへこのパターンを適用する際は、
  この特性を踏まえた検証を行うこと。
  - **計測手順**（git bash実機で行う。issue #70 のフェーズ4で手順だけを決め、計測は未実施）。
    測りたいのは「入力バイト数に比例して増えるread(2)のコスト」が、`$(cat)` の**fork 1回分
    （約95ms）**を超えるかどうかである。**超えなければ現状のままでよい。**
    1. ペイロードを3種（1KB / 100KB / 1MB）用意する。中身は `tool_input.command` に
       ヒアドキュメントが入った実際の形に寄せる（改行が多いほど不利な側に倒れる）。
    2. **空のhook**（`IFS= read -r -d '' raw || true; exit 0`）をベースラインに取る。
       これを省くと、パイプの生成やプロセス起動そのものの時間を受け口のコストと読み違える
       （上記「起動回数がゼロであることを計測で確かめるとき」と同じ罠）。
    3. 同じセッション内で、`read -d ''` 版と `raw="$(cat)"` 版を**連続して**測る
       （別セッションの値と突き合わせると、マシン負荷の差が結果になる）。
    4. 判断は絶対値ではなく**差**で行う。`read -d ''` 版 − 空hook が、
       `$(cat)` 版 − 空hook を上回るペイロードサイズがあれば、そこが乗り換え点である。
    - **「測れないから現状維持」と「測ったうえで現状維持」は別物である。** 現状は前者で
      あり、Linux実機での計測をもって結論としない（Linuxのfork/execはgit bashより桁で速く、
      forkが高い側とsyscallが高い側のどちらへ倒れるかがそもそも変わる）。
- 実例: `.claude/hooks/block-direct-git-commit.sh` / `post-issue-create-notice.sh`
  （issue #159。純粋関数への切り出し・JSONエスケープを考慮したバックスラッシュ除去・
  ブラケット式を組み合わせた版。詳細・却下案はDDR `i0159-01`）。push系2本
  （`post-push-usage-report.sh` / `post-push-compact-prompt.sh`）は本ルールのパターンの
  初出（issue #70）で、`raw_hints_at_git_push` として**同型の実装を持つ**。
  - **当初この2本は `case "$raw" in *push*) ;; *) exit 0 ;; esac` を `main()` 内へ直書き
    していた。これは超集合ではなかった**（issue #70 のフェーズ4で、本節を書いた直後に
    自分で踏んで気づいた）。`git pu\sh` は精密判定では push と読まれるのに、生JSONには
    `pu\\sh` としか現れないため前置フィルタが取りこぼす。**判定対象が `commit` か `push` か、
    コマンド名かサブコマンドかは関係しない**——正規化の食い違いは、精密判定がバックスラッシュを
    落とす限り必ず起きる。
  - **教訓: 「この語なら大丈夫」と語ごとに考えないこと。** 前置フィルタを新設したら、
    判定本体が持つ正規化を**そのまま**前置フィルタ側にも施す。
  - 超集合であること・過検知が存在すること・2本の実装が同一であることを、
    `test_sync_gemini_assets.sh` の T11 が固定している。テストは**実装を `source` して
    呼ぶ**（テスト側へ写経すると、実装が変わってもテストだけが正しいままになる）。

## パラメータ展開の既定値

- **二重引用符の中で `${N:-...}` の既定値にバックスラッシュを書かない**（issue #23で実際に踏んだ）。
  bashは二重引用符内の `\{` のバックスラッシュを除去しないため、`"${7:-\{\}}"` は引数省略時に
  `{}` ではなく **`\{\}` という文字列**になる。これを `jq --argjson` へ渡すと不正なJSONとして
  失敗する。既定値がJSONリテラル等の記号を含む場合は、**代入してから補う**。

  ```bash
  # 悪い例（省略時に \{\} になる）
  local agent_ranges="${7:-\{\}}"
  # 良い例
  local agent_ranges="${7:-}"
  [ -n "$agent_ranges" ] || agent_ranges='{}'
  ```

## コマンド置換とNULバイト

- **コマンド置換 `$(...)` はNULバイトを保持できない。** NUL区切りで出力するオプション
  （`git ls-files -z`, `grep -z`, `find -print0` 等）の結果を `$(...)` で受けると、bashは
  `warning: command substitution: ignored null byte in input` を標準エラーへ出し、NULを捨てる
  （issue #60で実際に踏んだ）。`set -e` 配下でも警告止まりで処理は継続するため、**出力は一見
  正しく、標準エラーにだけ異常が出る**という気づきにくい形になる。
- 判定に使うのが「1件でもマッチしたか」だけなら、**`-z` を付けない**のが正しい
  （区切りが曖昧でも `[ -n "$(...)" ]` の結果は変わらず、日本語パスが8進エスケープされても
  判定に影響しない）。実例: `.claude/scripts/src/create-commit.sh` の `classify_files`。
- 出力そのものをパスとして使う場合は `-z` が必要になるが、その受け口はコマンド置換ではなく
  `while IFS= read -r -d ''` にする。

  ```bash
  # 悪い例（NULが捨てられ、警告が出る）
  if [ -n "$(git ls-files -z -- "$path")" ]; then ...
  # 良い例1（存在判定だけなら -z は不要）
  if [ -n "$(git ls-files -- "$path")" ]; then ...
  # 良い例2（各パスを個別に使うなら read -d '' で受ける）
  while IFS= read -r -d '' f; do ...; done < <(git ls-files -z -- "$path")
  ```

- **`git ls-files` を全ファイル走査に使うときは、`-z` を「NULを保持したいから」ではなく
  「パスがクォートされるのを避けるため」に付ける**（issue #32で実際に踏んだ）。gitは既定
  （`core.quotePath=true`）で非ASCIIを含むパスを `"\343\203\254..."` のように**ダブルクォート＋
  8進エスケープした文字列**として出力する。この行をそのままループ変数として受けてファイル操作へ
  渡すと、実在するファイルに対して `No such file or directory` になる。`-z` を付けると
  クォートは行われない（`while IFS= read -r -d ''` で受ける）。

  ```bash
  # 悪い例（日本語ファイル名が "\343\203\254..." のまま渡り、必ず失敗する）
  git ls-files | while IFS= read -r f; do wc -c < "$f"; done
  # 良い例
  while IFS= read -r -d '' f; do wc -c < "$f"; done < <(git ls-files -z)
  ```

- **`git ls-files` の列挙結果を、ワーキングツリーに実体があるものとして扱わない**（issue #117で
  実際に踏んだ）。`--cached`（既定）は**gitのindexの内容**を返すため、**削除したがまだステージ
  していない追跡ファイル**も含まれる。列挙結果をそのまま `stat`・`cat`・`wc` 等へ渡すと
  `No such file or directory` で失敗する。列挙とファイル操作の間に「実体があるか」の判定を挟む。

  ```bash
  # 悪い例（削除済み・未ステージのファイルで必ず失敗する）
  while IFS= read -r -d '' f; do files+=("$f"); done < <(git ls-files -z)
  printf '%s\0' "${files[@]}" | xargs -0 stat -c '%Y'
  # 良い例（[[ -f ]] はbash組み込みなのでforkは増えない）
  while IFS= read -r -d '' f; do [[ -f "$f" ]] || continue; files+=("$f"); done < <(git ls-files -z)
  ```

  **この失敗は「たまに起きる」ものではない。** コミット前に走るスクリプト（`cleanup-task.sh` の
  frontmatterインデックス再生成、SessionStart hookでの再生成等）では、**追跡ファイルを1件でも
  削除した時点で必ず**発生する。`extract-frontmatter.sh` では、`xargs stat` の失敗で件数が合わなく
  なり、フォールバックの1件ずつ取り直すループが `set -e` 配下で倒れて**走査全体が中断**していた
  （削除と無関係なディレクトリの `index.jsonl` まで再生成されない）。
  スキップする場合は**件数を必ず出す**こと（無言のスキップは、今度は本当の欠落を隠す）。

- **NULバイトの有無を `od -c` の目視で判定しない**（issue #32で実際に誤読しかけた）。`od -c` は
  NULを `\0` と表示する一方、**印字可能文字はそのまま出す**ため、本文中の**数字の `0`**（例:
  「要素0個なら」）が出力に現れると、区切りの空白込みで見たときにNULと見分けがつかない。
  上記の「CR混入の検査」と同じく、**除去の前後でバイト数を比較する**のが確実。

  ```bash
  # 悪い例（本文中の数字の 0 をNULと読み違える）
  sed -n '94p' "$f" | od -c
  # 良い例（差が0ならNULは無い）
  [ "$(wc -c < "$f")" = "$(tr -d '\0' < "$f" | wc -c)" ] && echo 'NULなし'
  ```

- **`git status --porcelain` からパスを取り出すときは `-z` を付ける**（issue #115。issue #97の
  作業中に2回踏んだ）。行単位形式は改名・コピーを `R  <旧パス> -> <新パス>` の**1行**で出すため、
  先頭3文字（XY＋空白）を落とす `sed -E 's/^...//'` では、**どちらのパスとしても存在しない
  1行**が残る。そのままファイル操作へ渡すと `No such file or directory` になる。
  さらに空白を含むパスはダブルクォートで囲まれるため、アンクォート処理まで要る。
  **パス自体が ` -> ` を含みうる以上、行単位形式は後段でどれだけ丁寧に分解しても曖昧**である。
  `-z` なら改名エントリは `XY <新パス>\0<旧パス>\0` の2フィールド（**行単位形式とは順序が逆で
  新パスが先**）になり、クォートも行われない。

  ```bash
  # 悪い例（改名があると "旧パス -> 新パス" という存在しない1行が混ざる）
  git -c core.quotepath=false status --porcelain -- "$dir" | sed -E 's/^...//'
  # 良い例（改名・コピーは新パスだけを採り、旧パスのフィールドは読み捨てる）
  while IFS= read -r -d '' entry; do
    printf '%s\n' "${entry:3}"
    case "${entry:0:2}" in [RC]?|?[RC]) IFS= read -r -d '' _origin || break ;; esac
  done < <(git -c core.quotepath=false status --porcelain -z -- "$dir")
  ```

  この分解は**純粋関数へ切り出して単体テストを書く**（実例: `Provider.sh` の
  `porcelain_z_to_paths`）。NULを吸収して改行区切りへ変換する関数にしておけば、呼び出し側は
  従来どおり `$(...)` で結果を受け取れる（上記「コマンド置換はNULバイトを保持できない」制約を
  呼び出し側へ波及させずに済む）。

## タブ区切り（TSV）の分割

- **`IFS=$'\t' read -r -a` でTSVの行を分割しない**（issue #17で実際に踏んだ）。**タブはIFS
  空白文字**として扱われるため、`read` は (1) **連続するタブを1つの区切りへ畳み**、
  (2) **行末のタブを捨てる**。「フィールド数は固定」という前提のTSVでは、**空フィールドが
  あるだけで配列の長さが変わる**。
  - 実例: `push-checklist.sh` のチェックリストは4フィールド固定（未実施の行は4列目が空なので
    行末がタブで終わる）だが、`read -a` で分割すると3要素になり、**検証が自分の生成物を必ず
    落とす**という形で表面化した。
  - **この失敗は「空フィールドが無いうちは正しく動く」ため気づきにくい。** 全フィールドが
    埋まったサンプルでテストすると通ってしまう。**フィクスチャには必ず空フィールド（とくに
    行末）を含める。**
  - この罠は `IFS` の指定漏れではない。`IFS=$'\t'` と正しく書いても起きる。タブが空白文字で
    ある以上、`read` の分割規則そのものが畳む側に働く。
  - 対処はbash組み込みだけの分割関数を書くこと（forkしない）。実例:
    `push-checklist.sh` の `split_tsv_line`。
  - 同じ理由で、**`awk -F'\t'` は畳まない**ので使ってよい（ただし外部プロセスを1回起動する。
    上記「外部プロセス起動のコスト」）。

  ```bash
  # 悪い例（行末タブが捨てられ、4フィールドのはずが3要素になる）
  IFS=$'\t' read -r -a fields <<<"$line"
  # 良い例（区切りの数だけ確実に分割する。fork無し）
  split_tsv_line() {
    local line="$1" field
    TSV_FIELDS=()
    while [ -n "$line" ] || [ "${#TSV_FIELDS[@]}" = 0 ]; do
      field="${line%%$'\t'*}"
      TSV_FIELDS+=("$field")
      [ "$field" = "$line" ] && break
      line="${line#*$'\t'}"
    done
  }
  ```

- **同じ「区切り文字が空白文字かどうか」の違いは、`generate-ddr-list.sh` でも既に踏まれている。**
  罠の説明はそちらと DDR `i0135-01` にもあるので、写経せずに参照する
  （[.claude/docs/spec/generate-ddr-list.md](../docs/spec/generate-ddr-list.md)、
  [.claude/docs/ddr/i0135-01-DDR一覧は生成物にしつつGit管理下へ残す.md](../docs/ddr/i0135-01-DDR一覧は生成物にしつつGit管理下へ残す.md)）。
  **本節は「.sh を書くときに必ず読まれる場所」に同じ罠への入口を置くためのものである**——
  issue #17 では、罠の記述が spec と DDR にあったのに `.claude/rules/` に無かったため、
  実装中に同じ失敗を再現した（類型 (d): アセットはあったのに辿り着けなかった）。

## 命名規則

- 関数名はsnake_caseにする（PowerShellの`Verb-Noun`規約から移植する場合は
  `Get-Issue`→`get_issue`のように変換する）。

  （PowerShell版の`GitHub-Xxx`/`GitLab-Xxx`に相当）。

## git bashのパス変換の落とし穴

`/in`のようなDOS形式の単一スラッシュ引数を、Windowsネイティブの非MSYS実行ファイル
（`tasklist.exe`, `taskkill.exe`等）に渡すと、git bash（MSYS）が「POSIXパスらしき
文字列」と誤認しWindowsパスへ自動変換してしまう既知の問題がある（実機確認: `/in`が
`C:/Program Files/Git/in`に化け`Unrecognised parameter`エラーになった）。**先頭を`//`にする
（`//in`）とこの自動変換を回避でき、ネイティブ側には`/in`として渡る。** DOS形式フラグを持つ
ネイティブコマンドを呼ぶ際は必ずこの対策を行う（`dev-tools/src/build.sh`の`//in` `//out` `//base`
`//icon`、`tests/test_external_command_server.sh`の`//FI` `//IM` `//F`が実例）。

**コンテナ内の絶対パスを渡す場合は`//`では回避できず、`MSYS_NO_PATHCONV=1`が必要**（issue #48で
実際に踏んだ）。`docker exec <container> cat /etc/gitlab/gitlab.rb`のように、**引数がフラグでは
なく純粋なPOSIX絶対パス**である場合、MSYSはそれをパスとみなして`C:/Program Files/Git/etc/gitlab/
gitlab.rb`へ書き換えてしまう。この用途で先頭を`//`にするとパスの意味自体が変わるため使えない。

```bash
# 悪い例（コンテナ内のパスがWindowsパスへ化ける）
docker exec gitlab cat /etc/gitlab/gitlab.rb
# 良い例（そのスクリプト／セッション全体で自動変換を止める）
export MSYS_NO_PATHCONV=1
docker exec gitlab cat /etc/gitlab/gitlab.rb
```

`docker exec` / `docker run`・WSL経由のコマンド等、**git bashの外にあるファイルシステムのパスを
引数で渡すコマンド**を扱うスクリプトでは、冒頭で`export MSYS_NO_PATHCONV=1`しておくとよい。

**ただし`MSYS_NO_PATHCONV=1`を効かせたシェルでは、Windowsネイティブの`jq`がMSYS形式のパス
（`/c/Users/...`）を開けなくなる**（issue #77で実際に踏んだ）。自動変換は「MSYSのパスをWindowsの
パスへ直す」働きもしているため、止めると`jq -f /c/tmp/filter.jq`や`jq . /c/tmp/data.json`のような
呼び出しが「そんなファイルは無い」で失敗する。**docker操作のための`export`を、`jq`を使う処理と
同じシェルへ広げないこと。** 必要な範囲だけを`( export MSYS_NO_PATHCONV=1; docker exec ... )`の
ようにサブシェルへ閉じ込めるか、`jq`へ渡すパスをWindows形式（`C:/tmp/...`）にする。

**同じ理由で、Windowsネイティブの`jq`へプロセス置換`<(...)`のパスを渡せない**（issue #97で実際に
踏んだ）。`jq -s -c '...' <(jq -c . session2.jsonl)` と書いたところ
`jq: error: Could not open file /proc/48730/fd/63: No such file or directory` で失敗した。
プロセス置換が渡すのはMSYSが用意する疑似ファイルパスであり、Windowsネイティブのプロセスからは
そもそも見えない。**一時ファイルへ書き出してからパスを渡す**こと。

```bash
# 悪い例（Could not open file /proc/<pid>/fd/<n> で落ちる）
jq -s -c '...' <(jq -c . session2.jsonl)
# 良い例
jq -c . session2.jsonl > "$tmp/normalized.jsonl"
jq -s -c '...' "$tmp/normalized.jsonl"
```

なお、これは**jqへ引数としてパスを渡す場合**の話である。`jq ... < <(...)`のように**標準入力へ
繋ぐ**のは、パス名を渡していないので問題なく動く。

## 文字コード

- git bashの標準入出力・パイプ・`jq`/`gh`とのやり取りはシステムのANSI/OEMコードページの影響を
  受けない。PowerShell版で必要だった明示的なUTF-8切り替え（`.claude/rules/powershell-encoding.md`
  参照）はbash版には不要。
- ただし`tasklist.exe`のような非MSYSネイティブコマンドの出力はシステムのコードページ（cp932等）の
  ままになる。この種のコマンドの出力を判定に使う場合は、日本語メッセージの文字列一致を避け、
  終了コードやASCII文字列（イメージ名等）での判定に留める。
- Windows版のnative `jq`バイナリ（`C:\Program Files\jq\jq.exe`のような、MSYS版ではなくWindows
  ネイティブ実行ファイルとして配布されるもの）は、標準出力をファイルへリダイレクトする際に行末へ
  CRを付与することがある（実機確認: `.claude/scripts/src/extract-frontmatter.sh`実装時。git bashの
  `core.autocrlf=input`設定下ではコミット時に自動でLFへ変換されるため実害は限定的だが、コミット前の
  ワーキングツリー上ではCRLFが混入する）。jqの出力を直接ファイルへ書き出す箇所は`tr -d '\r'`を
  挟んでLF改行に統一する。
  - **同じCR付与は、ファイルリダイレクトだけでなくコマンド置換・パイプでも起きる**（issue #34
    対応時に実機確認: `printf '%s' '{"a":1,"b":2}' | jq -r 'keys[]' | od -c` で各行末に`\r`が
    付くことを確認）。`for x in $(... | jq -r ... )`のようなループでは、`$(...)`によるコマンド
    置換が「文字列全体の末尾」の改行しか取り除かないため、**要素が2件以上ある場合、最後の要素
    以外はループ変数へ`\r`が付いたまま渡る**（最後の要素だけ、末尾の`\r\n`ごと丸ごと取り除かれる
    ため`\r`が付かない）。この状態で`jq --arg`によるキー参照（`.[$var]`等）を行うと、
    最後の要素以外は文字列不一致で`null`になる。要素が1件しかない場合は表面化しないため、
    複数要素を扱うループを新設・変更する際に見落としやすい（`.claude/hooks/post-push-usage-report.sh`
    で実例あり）。対策は同じく`| tr -d '\r'`を、`for`に渡す`$(...)`の直前に挟むこと。
  - **同じ理由で、複数行の値を1つの文字列としてコマンド置換で受ける場合も、最終行以外のCRが残る**
    （issue #94で実際に踏んだ）。上のループの話は「要素が複数あるとき」だったが、**要素が1つでも
    その値自体が複数行なら同じことが起きる**。`assert_eq`で比較すると、期待値と実際の値は目視で
    完全に同一に見えるのに一致しない、という最も気づきにくい形で表面化する（実例:
    `.claude/scripts/test/test_post_issue_create_notice.sh`が、7行の注意文を`jq -r`で取り出して
    比較しており、6個のCRが残って常に1件失敗していた）。
  - **横断的に点検するときの判定基準は「`jq -r`かどうか」ではなく「取り出す値が複数行になりうるか」**
    である。**単一行の値は表面化しない**（行末のCRは末尾の`\r\n`ごとコマンド置換に落とされるため）。
    issue #94の時点で`tr -d '\r'`の無い`jq -r`はテスト側25箇所・本体側70箇所あったが、実際に
    壊れていたのは複数行を取り出す1箇所だけだった。`@tsv`・`join(", ")`・`length`・単一フィールド
    参照のように**出力が1行に収まる箇所を機械的に直して回らないこと**（fork1回の追加は
    「外部プロセス起動のコスト」節のとおり無料ではない）。

    ```bash
    # 危ない（値が複数行になりうる）: 必ず tr -d '\r' を挟む
    body="$(printf '%s' "$json" | jq -r '.body' | tr -d '\r')"
    # 表面化しない（値が1行に収まる）: 挟まなくてよい
    name="$(printf '%s' "$json" | jq -r '.title')"
    ```

  - **ただし「hookが受け取るコマンド文字列」のように、複数行になりうるが判定にしか使わない値は
    例外**である。`.tool_input.command`はヒアドキュメントを含むと複数行になるが、
    `grep -qiE 'git[[:space:]]+push'`（`[[:space:]]`はCRにマッチする）や
    `[[ "$command" == *create-issue.sh* ]]`のような部分一致は**CRがあっても判定が変わらない**。
    これらのhookは毎ツール呼び出しで発火するため、効果の無い`tr`を足すとfork1回分の遅延だけが
    残る。**判定をCRに依存しない書き方に保つ**ことで対処し、行の一致（`^...$`のような
    アンカー付き正規表現・完全一致）へ変更する場合にだけCR除去を入れる。

    **issue #53で判定がコマンド位置ベース（トークン走査）へ変わったが、`tr -d '\r'` が不要と
    いう結論は変わらない。ただし理由が変わった。** 部分一致ではなくなったため「どこにCRが
    あっても影響しない」とは言えず、代わりに**判定側がCRを吸収する**設計にしている。
    具体的には (1) トークン走査の`IFS`へ`\r`を含める、(2) ヒアドキュメント区切り語の比較前に
    末尾の`\r`を落とす、の2点である（`.claude/hooks/lib/CommandPosition.sh`）。スタブ`jq`で
    CRの有無により判定が1件も変わらないことを確認済み。**判定ロジックを変更する際は、この
    2点が維持されているかを確認すること**（`tr`を足さずに済んでいる根拠がここにあるため）。

    **追記（issue #149）: `[[ "$command" == *create-issue.sh* ]]`という部分一致の例も、
    上記のgit系hookと同じ経緯をたどった。** `post-issue-create-notice.sh`のCLI経路判定は
    `command_invokes_script`（コマンド位置判定）へ移行しており、この部分一致は**ライブラリを
    使えない環境でのみ通る縮退時のフォールバック**としてのみ残っている（詳細:
    `.claude/docs/spec/command-position.md`、DDR `i0149-01`）。CRが判定へ影響しないという
    結論自体は変わらない（フォールバック時は部分一致のまま、通常経路はトークン走査の`IFS`が
    `\r`を吸収する上記の設計を引き継いでいる）。

- **`awk`/`sed`の置換文字列で、`\r`を含むシェルコードを生成しない**（issue #48で実際に踏んだ）。
  スクリプトへ`| tr -d '\r'`という行を差し込もうとして`awk 'NR==95{print "... tr -d '\''\r'\''"}'`と
  書いたところ、**awkが文字列リテラル中の`\r`をCR文字そのものへ展開**し、ソースコードに生の
  CRバイトが混入した（結果として`tr -d ''`に見える行が出来上がり、CR除去が無言で効かなくなる）。
  `sed`の置換文字列でも同様に、処理系によって`\r`・`\n`・`\t`がエスケープとして解釈される。
  **生成したい行はクォート済みヒアドキュメントで別ファイルへ書き出し、`sed -n`で分割した
  前後と連結する**のが確実。

  ```bash
  # 悪い例（\r がCR文字へ展開されてソースに混入する）
  awk -v n=95 'NR==n{print "  '\'' | tr -d '\''\r'\''"; next} {print}' f.sh > f.new
  # 良い例（ヒアドキュメントの中身はそのままのバイト列で出る）
  cat > line.txt <<'EOF'
    ' | tr -d '\r'
  EOF
  { sed -n '1,94p' f.sh; cat line.txt; sed -n '96,$p' f.sh; } > f.new
  ```

  上の例の`EOF`は読みやすさのためインデントしているが、**実際に書くときは行頭（列0）に置く**こと
  （インデントすると終端として認識されない）。混入したかどうかは、CR除去前後のバイト数比較で
  確認する（下記「テスト」節のとおり
  `grep -c $'\r'`は使わない）。

  **そのヒアドキュメントの区切り語は必ずクォートする**（`<<'EOF'`。issue #185で実際に踏んだ）。
  クォートし忘れると、本文中の**バックティック・`$VAR`・`$(...)`・行末のバックスラッシュが
  すべて展開・解釈される**。日本語ドキュメントを流し込む場面ではmarkdownのインラインコードが
  必ず含まれ、シェルやjqの説明を書く場面では `$ARGS.positional` `${var:-}` のような `$` が
  必ず含まれるため、**踏まないほうが難しい**。
  **失敗の現れ方が分かりにくい**のがこの罠の本体で、現れ方は展開されたものによって変わる。

  | 展開されたもの | 現れ方 |
  |---|---|
  | バックティック・`$(...)` | 置換されたコマンドが標準入力を待つと、Bash/PowerShellツールが**タイムアウトまでハングする**。出力には `Co-Authored-By: command not found` のような**本文の一部を実行した無関係なエラー**しか出ない |
  | `$VAR` | **未定義の変数が空文字へ置き換わり、本文から静かに欠落する**（エラーが出ないので最も気づきにくい） |

  「ツールが固まった」「知らないコマンドが無いと言われた」「書いたはずの `$` から先が消えている」と
  感じたら、まずクォートを疑う。

- **数値の桁区切りのような整形は、行全体ではなく「数値と分かっている場所」へ適用する**
  （issue #97で実際に踏んだ）。markdownの表をjqで組み立てたあと、出来上がった行全体へ
  `sed -E ':a; s/([0-9])([0-9]{3})([^0-9]|$)/\1,\2\3/; ta'` をかけたところ、**表の1列目の
  モデル名に含まれる数字列まで区切られた**（`claude-3-5-sonnet-20241022` →
  `claude-3-5-sonnet-20,241,022`）。整形は組み立てる前の段階、すなわち**値が数値であると
  分かっている場所**で行う（この例ではjq内に`def commafy`を定義してセル単位で適用した）。
  出力の形（markdownの行）に引きずられて、後段でまとめて整形したくなる場面に注意する。

- **AIエージェント向け注記: ツールへ渡すコマンド文字列の中では、バックスラッシュが1つに
  潰れることがある**（issue #77で実際に踏んだ）。`jq`・`perl`・`sed`の正規表現に`\+`のような
  二重エスケープを書いたつもりでも、実際のプロセスには`\+`として渡り、意図と違うマッチになる。
  **正規表現は`[+]`のような文字クラスで書き**、エスケープを含む修正はヒアドキュメント経由で
  ファイルへ書き出してから使う（上の例と同じ対処で、原因も同じ「文字列がもう1段解釈される」
  ことである）。**同じ理由で、`perl -0pi -e "..."`・`sed "..."`のように置換スクリプトを
  ダブルクォートで囲まない**（issue #97で実際に踏んだ。置換文字列に含まれる`$(...)`をシェルが
  先に展開してしまい、意図しないコマンドが実行された）。シングルクォートで囲むか、
  **数行程度の修正ならEdit/Writeツールで直接行う**ほうが確実である。
- **AIエージェント向け注記: ソースコードへ生の制御文字（NUL・`\037`等）を書かない。エスケープ
  表記を使う**（issue #43で実際に踏んだ）。jqのフィルタで区切りを判定するために
  `startswith("<0x1F の生バイト>")` と書いたところ、フィルタとしては正しく動くものの、
  **Bashツールへ渡すコマンド文字列が「非表示の制御文字を含む」として弾かれ**、
  Writeツールで書いた後もdiff・`grep`の出力には**見えないまま残る**（`od -c` で初めて分かる）。
  jqなら`"\u001f"`、bashなら`printf '\037...'`のように、その言語のエスケープ表記で書く。
  混入の検査は、除去の前後でバイト数を比較するのが確実（下記「テスト」節の
  CR検査と同じやり方）。

  ```bash
  # 悪い例（フィルタは動くが、生の0x1Fがソースへ残りツール経由の編集で弾かれる）
  jq -R -n 'if ($l | startswith("<0x1F>")) then ...'
  # 良い例（jqのエスケープ表記。bash側は printf '\037%s\n' で出す）
  jq -R -n 'if ($l | startswith("\u001f")) then ...'
  # 検査（差が0なら生の制御文字は無い）
  [ "$(wc -c < "$f")" = "$(tr -d '\037' < "$f" | wc -c)" ] && echo '制御文字なし'
  ```

- **AIエージェント向け注記: 長いスクリプト・長文ファイルの生成は、Bashツールのヒアドキュメント
  ではなくWriteツールで行う**（issue #77で実際に踏んだ）。150行規模のヒアドキュメントをBashツールへ
  渡すとコマンド文字列のパースに失敗することがあり、**失敗の仕方が「途中まで書かれたファイルが
  残る」形になる**ため気づきにくい。数十行までの差し込みはヒアドキュメント、それを超える新規
  ファイルはWriteツール、と切り分ける。

- **差し込むファイルは、先頭に空行を置かず、末尾に空行をちょうど1つ持たせる**（issue #64で実際に踏んだ）。
  上の`{ sed -n ...; cat line.txt; sed -n ...; }`という連結は、3つの断片をそのまま繋ぐだけなので、
  差し込む側の先頭に空行があると**連結後に空行が2つ連続し**、逆に末尾の空行が無いと**次の見出しが
  直前の段落へくっつく**。markdownの段落へ差し込む場合、この崩れはdiffでは目立たないのに読みづらさ
  として残る（実例では、差し込んだ段落の直後にあった`## 設定項目`の直前の空行が失われ、`sed -i`で
  事後修正することになった）。
- **連結したら、差し込み位置の前後3行を必ず目視で確認する。** 見るのは「空行が2つ連続していないか」
  「次の見出しの直前に空行が1つあるか」の2点で足りる。
- **差し込みではなく「範囲の置き換え」を行った場合は、範囲の末尾も同じように確認する**
  （issue #145で実際に踏んだ）。`{ sed -n '1,Ap'; cat 断片; sed -n 'B,$p'; }` という形は、
  `A` と `B` の両方が正しいときにだけ正しい。**先頭側だけを見て「連結できた」と判断すると、
  `B` の取り違えによる行の重複・欠落が末尾に残る**（実例: `review-loop.md` の差し替えで、
  置き換えたはずの範囲の末尾1行がそのまま残り、同じ文が2度現れた）。
  - 前後3行の目視は**先頭側にしか効かない**。範囲を置き換えたなら、確認箇所は2つになる。
  - 行数で見るのが確実（`wc -l` の差が「断片の行数 − (B − A − 1)」と一致するか）。

  ```bash
  # 差し込み位置が N 行目直後なら、その周辺だけを表示する
  sed -n "$((N - 3)),$((N + 12))p" target.md
  ```

- **POSIX/`LANG`未設定のロケールでは、POSIX ERE のブラケット式（`[...]`）へ多バイト文字を
  直接含めると、`grep -E`・bashの`[[ =~ ]]`のいずれも該当行がマッチしないだけでなく、
  パターン全体が一致しなくなることがある。** 測定環境: Claude Code on the web（Linux）／
  2026-08-23。git bash実機では未計測（issue #171で実機確認: `.gitignore`のDDR参照検出
  スクリプトで、全角句読点1文字をブラケット式の終端文字クラスへ追加したところ、リポジトリ
  全体37,411行に対する候補抽出が121件から0件へ落ちた）。`LC_ALL=C.UTF-8`を明示すれば
  再現しないが、git bash/Windows配布先ではロケールを制御できないため、**正規表現自体には
  多バイト文字を含めず、抽出後の文字列をASCII構造（固定の英数字プレフィックスの再出現位置等）
  だけで判定する後処理で対応する。**（実装例:
  `.claude/scripts/src/check-doc-references.sh`の`split_concatenated_candidates_to_reply`。
  詳細: [DDR i0171-01](../docs/ddr/i0171-01-DDR参照切れ検出は絶対パス形式に限定しgrep一括抽出で実装する.md)
  「理由」2、および同DDRが挙げる却下案。ここでは適用結果のみを示し、再発条件・却下案の
  詳細はDDR側を正とする。）

## Claude Code hookとして登録する場合

`.claude/settings.json`のhook `command`は `"bash"` とだけ指定する（フルパス直書きはしない。他環境
への移植性を優先）。ただし環境によっては、Windowsの`PATH`で`C:\Windows\System32\bash.exe`
（WSL起動用スタブ）が`Git\bin`より先に解決され、エラーも出さずgit bashではなくWSLが起動する
可能性がある（このマシンで実機確認済み。Git for Windowsのインストーラは既定で`bash.exe`のある
`Git\bin`を`PATH`に追加しないことが原因）。**システム環境変数（`Machine`スコープ）の`Path`に
`Git\bin`（例: `C:\Program Files\Git\bin`）を`C:\Windows\System32`より前に来る位置で追加する**
ことで解決する（ユーザー環境変数に追加するだけでは効果が無い。Windowsの有効PATHはシステム環境変数
側が先に連結されるため）。具体的な手順は
[.claude/docs/spec/shell-scripts.md](../../.claude/docs/spec/shell-scripts.md)
「Claude Code hookの起動コマンド」参照）。`${CLAUDE_PROJECT_DIR}`（Windows形式パス）はこの
`bash.exe`へargvで渡しても正しく解決される。

## テスト

- 副作用の無い純粋ロジック（文字列変換・正規表現マッチ等）は、外部コマンド呼び出しを伴わない
  単体テストスクリプトを`.claude/scripts/test/`に置く（実例:
  `.claude/scripts/test/test_vcs_provider.sh`）。機構自身のテストを`.claude/`配下（plugin配布
  単位）へ収めることで、他プロジェクトへ導入したときに導入先本体の`tests/`と場所を取り合わない
  （issue #63）。
- **本節の`passed=N failures=N`規約はbashスクリプトが対象。** perlで書いた常駐プロセス
  （`.claude/hooks/`配下の`otel/`等）の単体テストは、`Test::More`を使いTAP形式で出力してよい
  （bash版の出力形式へ変換する必要は無い）。テストの置き場所自体は`.claude/scripts/test/`では
  なくそのプロセス自身の配下に置く（`.claude/rules/directory-structure.md`「配置の指針」参照。
  実例: `.claude/hooks/otel/test/`）。
- 実プロセス起動・TCP通信等の結合確認は、「`passed=N failures=N`を出力し
  失敗があれば終了コード1」という規約に合わせる（実例: `tests/test_external_command_server.sh`）。
- 作成した`.sh`は最低限 `bash -n <file>` で構文チェックする。
- **stdinを読むスクリプト（hook等）は、本体を `main` にまとめ、末尾で
  `if [ "${BASH_SOURCE[0]}" = "${0}" ]; then main; fi` のガードを通す**（issue #57）。
  トップレベルで `raw="$(cat)"` を実行していると、テストから `source` した時点でstdin待ちの
  まま**ハングする**（構文エラーのような分かりやすい失敗ではなくタイムアウトになるため、
  原因に気づきにくい）。ガードがあれば、`source` 時は関数定義だけが読み込まれ、副作用の無い
  純粋関数を単体テストできる（実例: `.claude/hooks/session-start.sh` と
  `.claude/scripts/test/test_session_start.sh`）。
- **CR混入の検査に `grep -c $'\r' <file>` を使わない**（issue #23で実際に踏んだ）。環境によっては
  `$'\r'` が空パターンとして渡り、**全行にマッチして総行数を返す**ため、CRが無いのに検査が
  失敗する（実機で確認: CRを含まないファイルに対し `0` ではなく行数 `2` が返った）。
  CR除去の前後でバイト数を比較する方が確実。

  ```bash
  # 悪い例（空パターン扱いになり全行にマッチしうる）
  assert_eq "CRが無い" "0" "$(grep -c $'\r' "$f" || true)"
  # 良い例
  assert_eq "CRが無い" "$(wc -c < "$f")" "$(tr -d '\r' < "$f" | wc -c)"
  ```

  なお、WindowsネイティブjqがCRを付与すること自体は「文字コード」節のとおり実在するため、
  `tr -d '\r'` による除去は引き続き必要である（検査方法だけの話）。

- **Windows固有のCR問題は、スタブ`jq`をPATHの先頭へ置けばLinux／WSL上でも再現・検証できる**
  （issue #94）。Windows実機が無い環境で「直った」と言い切るために使える。再現したいのは
  **native jqのCR付与とMSYS bashのコマンド置換の合成結果**なので、`sed '$!s/$/\r/'`（最終行
  **以外**の行末へCRを付ける）が実際に観測される値と一致する。

  ```bash
  # $SP/crjq/jq として保存し chmod +x してから PATH="$SP/crjq:$PATH" でテストを流す
  #!/usr/bin/env bash
  set -o pipefail
  /usr/bin/jq "$@" | sed '$!s/$/\r/'
  ```

  - このスタブは`test_post_issue_create_notice.sh`の`passed=13 failures=1`を正確に再現した
    （再現できたことをもって、原因の理解が正しいと確認できる）。
  - **スタブが合わない2つのケースを、実際の不具合と取り違えないこと。** (1) `jq`の後段に
    `head`/`sed`等が挟まる場合（実jqは最終行にもCRを付けるため、後段を通してもコマンド置換が
    落とせる。スタブでは最終行にCRが無いので結果がずれる）。(2) テストが`PATH`自体を差し替える
    場合（`test_extract_frontmatter.sh`の`fake_bin`が実例。スタブが呼ぶ`sed`もPATHから消える）。
    どちらもスタブ側の限界であり、実機では失敗しない。
- **合成フィクスチャのテストだけで完了としない**。ペイロードサイズやデータ構造のゆらぎなど、
  実データでしか顕在化しない性質がある（DDR i0000-04「追記（issue #37 続き）」の教訓）。transcript等の
  実データを扱うロジックを変更したら、実際のファイルに対して関数を直接呼ぶ確認を併せて行う。
- **終了コードを検査するテストで `"$(func; echo $?)"` の形を使わない**（issue #45で実際に書いた）。
  `"$(func; echo $?)"` が返す値は、errexit・`inherit_errexit` の設定とbashの版に依存する
  （`inherit_errexit` が有効な環境では、関数が失敗した時点でサブシェルが終了して `echo $?` に
  到達せず**空文字列**が返る。既定オフの環境では `echo $?` まで到達して値が返る。上記
  「エラー方針」節の機構2）。環境によって挙動が変わるものに依存しない。`if` の条件式では
  `-e` が一時停止されるため、そちらで受ける。

  ```bash
  # 悪い例（set -e 配下ではサブシェルが echo に到達しないことがある）
  assert_eq "空なら1" "1" "$(provider_from_remote_url 'https://' 2>/dev/null; echo $?)"
  # 良い例
  if provider_from_remote_url 'https://' >/dev/null 2>&1; then
    empty_host_status=0
  else
    empty_host_status=1
  fi
  assert_eq "空なら1" "1" "$empty_host_status"
  ```

  **この誤りは、環境によっては期待どおりの値が返ってテストが通ってしまうため、「通ったこと」を
  根拠に正しいと判断できない**（issue #45では実際に `1` が返って通ったが、依存したくない挙動の
  ため書き換えた）。
- **日本語を含む文字列の先頭を `${var:0:N}` で切り出して比較しない**（issue #57で実際に踏んだ）。
  bashの部分文字列展開はロケール次第で**バイト単位**で切られるため、切り出し位置がマルチバイト
  文字の途中に当たると文字が壊れ、目視では正しく見える期待値と一致しなくなる（実機確認:
  `"## 次にやること"` の先頭20を取り出したところ `## 次にやるこ<壊れた文字>` になった）。
  行の比較なら `head -1`、部分一致なら `[[ "$haystack" == *"$needle"* ]]` を使う。

  ```bash
  # 悪い例（環境によりバイト単位で切られ日本語が壊れる）
  assert_contains "見出しで始まる" "${section:0:20}" "## 次にやること"
  # 良い例
  assert_eq "見出し行で始まる" "## 次にやること" "$(printf '%s' "$section" | head -1)"
  ```

  **同じ「バイトか文字か」の取り違えが `awk` の `length()` でも起きる**（issue #185で実際に踏んだ）。
  **測定環境: Claude Code on the web（Linux）／2026-08-23。`awk` の実体は mawk 1.3.4。
  git bash実機では未計測。** mawkの `length()` は**バイト数**を返し、`LC_ALL=C.UTF-8` を付けても
  変わらない（実機確認: `LC_ALL=C.UTF-8 awk 'BEGIN{print length("あいう")}'` → **9**）。
  日本語を含む文字列の長さをこれで測って「文字数」として報告すると、**およそ2倍に膨らんだ値**になる。

  **ただしこれはawk一般の性質ではなく、実装依存である。** gawkは `length()` を文字数と定義して
  おり、マルチバイトロケールでは 3 を返す（gawkマニュアルの記述。本環境にgawkが無いため未検証）。
  **git bash（Git for Windows）が同梱するawkはgawk系のため、同じスクリプトが環境によって別の値を
  返しうる。**

  **`wc -m` も同じくロケール依存で、ロケール未設定ならバイト数になる。** 下表はこの環境
  （`LANG`・`LC_ALL` いずれも未設定）での実測値。**環境に関係なく文字数が欲しいなら
  `perl -CSD` を使う**（ロケール設定に依存せず3を返す）。

  | 測り方 | ロケール未設定 | `LC_ALL=C.UTF-8` |
  |---|---|---|
  | `awk 'BEGIN{print length("あいう")}'`（mawk） | 9 | 9 |
  | `printf 'あいう' \| wc -m` | **9** | 3 |
  | `perl -CSD -ne 'chomp; print length($_),"\n"' <<<'あいう'` | 3 | 3 |

  **バイトのまま示すなら「バイト」と明記する。** 単位を書かずに数だけ出すと、読み手は文字数だと
  解釈する（gitの慣習が「件名50〜72文字」で語られるため、コミットメッセージの長さを扱う場面では
  特に誤解を招く）。

- **末尾の改行を含む期待値の検証に `$(...)` を使わない**（issue #57で実際に踏んだ）。コマンド置換は
  末尾の改行をすべて落とすため、`$(printf 'a\nb\n')` は3バイトになり「末尾改行も数える」という
  検証が意図どおりにならない。`$'a\nb\n'` のようにANSI-Cクォートで直接書く。

- **既存の処理の前後に判定ロジックを挟むときは、判定単位が元の実装と同じかを疑う**
  （issue #60で実際に踏んだ）。`create-commit.sh` に「渡されたパスを分類してから `git add` する」
  処理を足したところ、分類を**パス文字列**で行ったため、gitが**pathspec**として解釈していた
  ディレクトリ指定（配下のファイルがすべて削除された `reports/`）が「gitが把握していないパス」に
  分類され、それまで成功していたケースが失敗するようになった。**元の実装が外部コマンドへ委ねて
  いた解釈を自前で再実装すると、粒度の違いが機能後退として表面化する。** 検証ケースに
  「ディレクトリ指定」「末尾スラッシュ」「相対/絶対表記」のような**表記のゆらぎ**を含めること。

- **純粋関数の単体テストは、その関数へ至る呼び出し経路を何も保証しない**（issue #127で実際に
  踏んだ）。`gitlab_get_mr_url` / `gitlab_get_note_url` は単体テストから**直接**呼ばれていた
  ためテストは緑のままで、**実運用経路からは到達不能**になっていた。経路上の
  `gitlab_get_mr_unresolved_comments` / `gitlab_add_mr_thread_reply` の**2箇所**が、既に定義の
  消えていた `gitlab_get_repo_url` を呼んでおり、`2>/dev/null` が `command not found` を
  握りつぶすため**無言で空へ縮退**して、その先の2関数まで進まなかった。
  **呼び出し経路を通すテストを併せて書く。** `glab`・`gh` のような外部コマンドはシェル関数で
  差し替えられるので、経路を通すこと自体は難しくない。

- **テスト内で既存関数を再定義してから `unset -f` すると、スタブではなく実定義そのものが消える**
  （issue #127で実際に踏んだ）。bashの関数定義は**スタックしない**ため、`unset -f` は
  「1つ前の定義」ではなく定義そのものを消す。以降のケースは `command not found` になる
  （このときは後続にケースが無かったため表面化せず、敵対的レビューで見つかった）。
  **差し替えはサブシェルへ閉じ込める**か、`declare -f` で退避して復元する。

  ```bash
  # 悪い例（Provider.sh の実定義が消える）
  get_repo_url() { printf 'https://example.com/o/r\n'; }
  target_function
  unset -f get_repo_url
  # 良い例（サブシェルを抜ければ元の定義が残っている）
  assert_eq "経路を通す" "$expected" \
    "$( get_repo_url() { printf 'https://example.com/o/r\n'; }; target_function )"
  # 後片付けが効いていることも、失敗が数えられる形で表明する
  assert_eq "実定義が残っている" "get_repo_url" \
    "$(declare -F get_repo_url >/dev/null && echo get_repo_url)"
  ```

  - **アサーションはサブシェルの外で行う。** `assert_eq` は `passed` / `failures` という
    グローバル変数を加算するため、`( ...; assert_eq ... )` のように括弧の中へ入れると
    **失敗しても `failures` が増えず、`failures=0` のまま緑になる**。サブシェルからは
    コマンド置換で**値だけ**を持ち出す。
  - 後片付けの表明を `declare -F x >/dev/null && echo x` の1行だけで済ませない。`a && b` の
    左辺の失敗は `set -e` の対象外なので、**壊れていても何も出ずに通過する**（下記
    「異常が無ければ何も出ない検証」と同じ罠）。

- **`declare -F <名前>` は名前だけを出力する**（issue #127で実際に踏んだ）。定義本体を出す
  `declare -f <名前>` と紛らわしいが、`-F` の出力に `declare -f` のような接頭辞が付くのは
  **引数を省略したときだけ**である。`| awk '{print $3}'` のように列で受けると空になり、
  6件のケースが一斉に失敗した。**存在確認は終了コードで行う。**

  ```bash
  # 悪い例1（空文字列になる）
  actual="$(declare -F to_slug | awk '{print $3}')"
  # 悪い例2（未定義のとき set -e でスクリプトごと落ちる。検出したい異常のときだけ落ちる）
  actual="$(declare -F to_slug >/dev/null && echo to_slug)"
  # 良い例（単純コマンドの引数に置く。set -e は発火しない）
  assert_eq "to_slugが定義されている" "to_slug" \
    "$(declare -F to_slug >/dev/null && echo to_slug)"
  ```

  **代入の形にしないこと。** 代入文の終了ステータスはコマンド置換のそれなので、`set -e` 配下では
  関数が未定義のときにスクリプトが `passed=N failures=N` を出さずに終了コード1で落ちる
  （実機確認済み）。同じコマンド置換でも、単純コマンドの**引数**に置けば `set -e` は発火しない。
  下記「終了コードを検査するテストで `"$(func; echo $?)"` の形を使わない」と同根の罠である。

- **「関数名らしい文字列」を正規表現で拾う静的検出は、同じ接頭辞を持つ別種の識別子を巻き込む**
  （issue #127で実際に踏んだ）。未定義の `github_*` / `gitlab_*` 呼び出しを検出するテストを
  書いたところ、**MCPツール名**（`github__list_pull_requests` のように**アンダースコア2つ**）が
  `(github|gitlab)_[a-z0-9_]+` に一致し、未定義の関数として9件を誤検出した。さらに接頭辞を持たない
  共有関数を同じ方法で導出しようとすると、jqのフィールド名（`new_path` / `head_sha` /
  `start_sha` 等）が十数件混ざる。**jqのフィールド参照とシェル関数の呼び出しは静的に区別できない。**
  - 除外パターンを足して絞るか、**明示的な一覧を持つ**かのどちらかにする。後者を採る場合は、
    **その一覧が形骸化していないこと**（列挙した名前が実際に定義され、呼ばれていること）も
    併せて表明する。
  - **「異常が無ければ何も出ない」形の検出は、パターンが実データに合っていないと常に成功する。**
    件数を併せて出し、意図的に未定義呼び出しを1件戻した一時ツリーで**実際に検出できる**ことまで
    確かめる。

- **`grep` で「母数」を作るときは、数えたい対象そのものの語で数えているかを確かめる**
  （issue #176で実際に踏んだ）。調査の母数・検証の基準値・カバレッジの分母のように、
  **件数がそのまま結論になる**場面では、パターンの部分一致・語の広さがそのまま誤った結論になる。
  実例は3つで、いずれも同じ「検索語と実データの形が食い違う」型である。

  | 何を数えたかったか | 使った語 | 何が起きたか |
  |---|---|---|
  | 「別issueへの切り出しに言及した記録」 | `別issue` | **`個別issue` にも一致**し、無関係な2件が母数へ混入した |
  | 「`5フェーズ43ステップ` という固定費の数字を再掲している箇所」 | `5フェーズ` | `43ステップ` だけが単独で現れる行を取りこぼし、6件と数えたが実際は8件だった |
  | 「新節が追記されたこと」 | `判断基準` | **変更前から4ファイルに存在**し、追記の有無に関わらず同じ値を返した |

  - **部分一致で広がる方向を先に確かめる。** 数える前に `grep -o` で**一致した文字列そのもの**を
    出し、意図した語だけが並ぶかを見る（`grep -c` は行数しか返さないので、何に一致したのかが
    分からない）。
  - **「増える／減る」を測るなら、変更前のツリーで基準値を実測する。** 変更前から既にヒットする
    語は、追記の有無を区別できない。見出し・目次に使われている**構造語を避け**、罠の内容に固有の
    語を選ぶ。
  - **ファイル数か行数かを取り違えない。** `grep -c` は1ファイルの**行数**、`grep -rl … | wc -l` は
    **ファイル数**である。同じ「2」でも意味が違う。
  - **取りこぼす方向は、`grep -o` では気づけない。** 上表の2行目だけは過検知ではなく**取りこぼし**で、
    `grep -o` が見せるのは「拾えたもの」だけだからである。**数えたい対象を2通り以上の語で数え、
    件数が一致するかを見る**（`5フェーズ` で6件・`43ステップ` で8件と食い違ったことで、母数が
    どちらか一方ではなく**和集合**だと分かる）。一致しないなら、少ないほうが取りこぼしている。
  - **数え上げの対象から、point-in-time の記録を先に除く。** 上表の2行目で数えたのは「現行の値を
    再掲している箇所」であって、当時の値をそのまま残す過去の記録ではない（`.claude/docs/ddr/` の
    本文・spec の changelog エントリがこれに当たり、`.claude/rules/docs-workflow.md` が書き換えを
    禁じている）。**除外した件数も併せて出す**と、後から母数の定義を確かめ直せる。

- **計画に書いた検査コマンドは、文字列としてそのまま流す**（issue #176で実際に踏んだ）。
  読みやすさや語感で書き換えると、**検査は期待どおりの値を返すのに、測っている対象が計画の
  定義と違う**という形になる。上の3つ目の実例がこれで、`見送ってマージ`（変更前0を実測済み）と
  定めていた語を実行時に `判断基準` へ差し替えており、**新節を1行も書かなくても合格する検査**に
  なっていた。
  - **この失敗は自己検証をすり抜ける。** 「計画に検証コマンドを書き、基準値を実測してから作業
    する」という規律が守るのは「検査を流したか」であって「流した検査が計画のものと同じか」では
    ない。上の3例のうち他の2つは自己検証で見つかったが、これだけは敵対的レビューで初めて
    見つかった。
  - **書き換えるなら、計画側の定義も同時に直し、変更前のツリーで基準値を測り直す**
    （`git show <変更前のSHA>:<path>` で測れる）。検査の定義が誤っていたと分かった場合も同じで、
    直した定義で測り直した値を計画へ書き戻す。

- **テストのフィクスチャを別のパスへ差し替えるときは、そのパスが「検証したい経路」に乗って
  いるかを確かめる**（issue #184で実際に踏みかけた）。プロダクトコード側のパスを移設し、それに
  合わせてテストのフィクスチャも機械的に移すと、**テストは緑のまま何も検証しなくなる**ことがある。
  - 実例: `test_sync_gemini_assets.sh` のT8は「`.gitignore` 対象のファイルが `.gemini/` へ
    出ないこと」を確かめるテストで、フィクスチャに `.claude/state/last-push-sha` を使っていた。
    `.claude/state/` を `wip/state/` へ移したのに合わせてフィクスチャも `wip/state/` にすると、
    `sync-gemini-assets.sh` の列挙は `git ls-files … -- .claude` に限られるため、
    **`.gitignore` の効果と無関係に列挙対象外**になり、テストが常に成功する空振りへ変わる。
    `.claude/` 配下に残る `.gitignore` 対象の実在パス（`/.claude/settings.local.json`）へ
    差し替えることで、検証したい性質を保った。
  - 判定は「**そのフィクスチャを意図的に壊したとき、テストが落ちるか**」で行う。落ちないなら、
    そのフィクスチャは検証経路に乗っていない。上記「異常が無ければ何も出ない形の検出は、
    パターンが実データに合っていないと常に成功する」と同根の罠である。

- **フィクスチャの既定値展開に `${N:-既定}` を使わない。`${N-既定}` を使う**（issue #17で
  実際に踏んだ）。`:-` は**未設定のときに加えて空文字列のときも**既定値へ置き換わるため、
  「空文字列を渡したときの挙動」を検証したいテストが、**空文字列を渡したつもりで既定値を
  渡している**空振りになる。

  ```bash
  # 悪い例（空文字列を渡す検証が、既定値を渡す検証にすり替わる）
  make_fixture() { local body="${1:-既定の本文}"; ... }
  make_fixture ''            # → 「既定の本文」が入ってしまう
  # 良い例（未設定のときだけ既定値。空文字列はそのまま通る）
  make_fixture() { local body="${1-既定の本文}"; ... }
  ```

  - **これも「意図的に壊したら落ちるか」で検出できる。** 空文字列のケースだけ本体を壊して
    みて落ちなければ、そのケースは空振りである。
  - `${N:-}`（既定値が空）は上記の問題を起こさないので、そのまま使ってよい。問題になるのは
    **既定値が非空**のときだけである。
  - 上記「パラメータ展開の既定値」節はテスト以外も含む一般の注意（`\{\}` の展開）を扱う。
    ここはテストのフィクスチャに固有の空振りを扱う。

## 秘密情報の扱い

秘密情報（トークン・パスワード等）を含む出力の扱いは、次の3つを守る。issue #127で
`glab auth status --show-token` の出力を扱った際に実際に踏んだもので、具体的な経緯は
[gitlab-verification-environment.md](../docs/spec/gitlab-verification-environment.md)「PATの扱い」
にある（本節はbashスクリプト一般の規約、あちらはGitLab検証環境という個別の手順）。

- **値そのものを置換する。** `glpat-` のような接頭辞は設定で変更できるため、接頭辞決め打ちの
  正規表現に頼らない。
- **マスク（伏せ字）は、そのパターンが実データに当たることを確かめてから使う。**
  `sed -E 's/(Token: ).*/\1<masked>/'` をかけたが、**実際の行は `Token found in operating system
  keyring: <値>`** でパターンに一致せず、トークンがそのまま出力に現れた。**当たらないマスクは
  無いのと同じで、しかも「マスクした」という誤った安心を与える分たちが悪い。**
- **そもそも値を出さない形にできないかを先に考える。** 「取り出せたか」を確かめたいだけなら、
  長さと先頭数文字だけを出せば足りる（`echo "長さ=${#tok} 先頭3文字=${tok:0:3}***"`）。
- **秘密情報をファイルへ書かない。** 必要になるたびに取得元から取り出す。
