# AIが実行するコマンド文字列の規約

AIエージェントが**Bash/PowerShellツールへ渡すコマンド文字列そのもの**と、その `description`
パラメータの書き方を定める（issue #47）。

## 適用範囲

**`.sh` ファイルとして保存するスクリプトは対象外**で、そちらは
[shell-script-style.md](shell-script-style.md) が扱う。両者はスコープが異なる。

| | 本ファイル | `shell-script-style.md` |
|---|---|---|
| 対象 | ツールへ渡す**その場限りのコマンド文字列**と `description` | リポジトリへ**保存する `.sh` ファイル** |
| 読み手 | **承認前のユーザー**（実行を許可するか判断する） | 後からコードを読む人・AI |
| 関心 | 何をしようとしているかが**実行前に**読み取れるか | 正しく動くか・速いか・罠を踏まないか |

コマンドを `.sh` へ切り出した場合、そのファイルには `shell-script-style.md` が適用され、
`bash <path>` という**呼び出し側の1行**には本ファイルが適用される。

**この規約は試行的に運用する。** 出力トークンは増えるが、意図しないコマンドを承認して
しまうリスクの低減を優先している。運用感が悪ければ見直す（経緯・トレードオフ:
[.claude/docs/ddr/0061-AIが渡すコマンド文字列の説明はdescriptionとコメントへ分けて置く.md](../docs/ddr/0061-AIが渡すコマンド文字列の説明はdescriptionとコメントへ分けて置く.md)）。

## 根拠: `description` はコンソール上1行しか表示されない

**Bash/PowerShellツールの `description` パラメータは、コンソール上に1行しか表示されない**
（issue #47 起票時に実機確認。複数行を渡しても2行目以降は表示されなかった）。

したがって、複数行コマンドの各ブロックが何をしているかを `description` で表現することはできず、
ユーザーは**コマンド文字列そのもの**を読み解くしかない。この空白をコマンド内のコメントで埋める。

> **この事実の出典はissue #47 起票時の観測である。** 本リポジトリのリモート実行環境
> （Claude Code on the web）にはコンソール表示が無く、再現できないため、後続の調査でも
> 確かめ直していない。

## 説明の置き場所

| コマンドの形 | 説明の置き場所 |
|---|---|
| **1行** | `description` に1行で書く。**コマンド内コメントは書かない**（`#` が行末までを飲むリスクだけが残り、得るものが無い） |
| **複数行** | `description` は「全体として何をするか」の1行。**各論理ブロックの意図を日本語コメントで書く** |
| **コメントを付けても読み解けないほど複雑** | `.sh` として切り出し、`bash <path>` で実行する（切り出し先は下記） |

### 切り出し先の選び方

| 切り出し先 | 使う場面 |
|---|---|
| **scratchpad**（セッション用の一時ディレクトリ） | その場限り。使い捨て |
| **`.claude/scripts/src/`** | 繰り返し使う。単体テスト（`.claude/scripts/test/`）とドキュメント（`.claude/docs/`）を伴う |

**迷ったらscratchpad。** `.claude/scripts/src/` は
[directory-structure.md](directory-structure.md) が「AIエージェントが `.claude/skills/*` 経由で
能動的に実行するスクリプト」の置き場と定めており、使い捨てのスクリプトを置くと配置ルールと
衝突する。加えて `cleanup-task.sh` の削除対象でもないため、**残り続ける**。

## 言語・文体

`description` とコマンド内コメントは、いずれも**日本語**で書く。
**敬語・助詞・無駄な装飾を使わない。** 単語と短文で要点だけを書く。

```
悪い例: description: 現在のブランチ名を取得します
良い例: description: ブランチ名取得

悪い例: # 直近のコミットの短縮SHAを取得する
良い例: # 短縮SHA取得
```

`description` は1行しか表示されないので、**複数行を渡さない**。

## 複数行コマンドの1行目にコメントを書かない

**コメントは2行目以降に置く。1つ目のブロックの説明は `description` が担う。**

```
悪い例:
# ブランチ名取得
branch=$(git rev-parse --abbrev-ref HEAD)
# 短縮SHA取得
sha=$(git rev-parse --short HEAD)

良い例:
branch=$(git rev-parse --abbrev-ref HEAD)

# 短縮SHA取得
sha=$(git rev-parse --short HEAD)
```

### 理由（リスク回避であり、断定ではない）

`.claude/settings.json` の `permissions.allow` / `deny` は、コマンド文字列をパターンで照合して
自動承認・拒否を決める。**先頭がコメント行だと、この照合が意図どおりに働かない可能性がある。**

issue #47 の起票時に想定していた帰結は2つあり、**実測で確かめられたのは片方だけ**である。

> **測定環境: Claude Code on the web（Linux）／2026-08-20。ユーザーの常用環境
> （Windows / git bash）では未確認。** 下表は1環境・1バージョンの観測であり、全環境の事実として
> 扱わないこと。

| 想定した帰結 | 対応する設定 | 実測 |
|---|---|---|
| `deny` をすり抜ける | `permissions.deny` | **この環境では起きなかった**（4ケース） |
| 許可済みのはずの操作で承認プロンプトが出る | `permissions.allow` | **未確認** |

`deny` は**いずれか**の部分コマンドが一致したら拒否（ANY）、`allow` は**すべて**の部分コマンドが
一致して初めて自動承認（ALL）という非対称の意味論を持つ。この非対称のもとでは、先頭のコメント行が
「無視される」のか「どの許可規則にも一致しない部分コマンドとして数えられる」のかを、
**`deny` の実験では原理的に区別できない**（後者でも `deny` の結果は変わらない）。`allow` 側を
直接確かめるには権限モードをプロンプトが出る形へ変える必要があり、そうすると以降のあらゆる
コマンドが承認待ちになってセッションが止まるため、実測を見送っている。

**よって、この制約は「照合が外れる」という断定ではなく、次のリスク回避として置く。**

> `deny` 側はこの環境では外れなかったが、`allow` 側は未確認であり、照合の実挙動は環境・
> バージョンで異なる観測がある。ゆえに先頭は避ける。

1行目をコメントにしないコストはほぼ無い（説明は `description` へ移すだけ）のに対し、
外れた場合の損失は「拒否されるはずの操作が通る」「毎回承認を求められる」であり、非対称である。

## コメント本文でのhook誤検知に注意する

PreToolUse / PostToolUse hookは、コマンド文字列を**部分文字列でマッチ**する。**コメント行も
コマンド文字列の一部**であり、除外されない。仕組みと既存の実例は
[git-workflow.md](git-workflow.md)「コミット運用」「push検知hookの誤検知」を参照する
（ここではコメントを書くときの注意だけを述べる）。

- **コメント本文で `git` と `commit` / `push` を半角スペース区切りで連続させない。**
  コメントは自由文であり、コマンドを日本語で説明しようとすると最も踏みやすい。
  「コミット操作」「リモートへ反映」のように言い換える。

**コミットをブロックするhookは、`settings.json` の `if` を経由せずコマンド文字列全体を検査する**
ため、コメント行の地の文でも**必ず発火する**（これはコード上の事実であり、環境に依らない）。

push検知の2つについては、**発火するかどうかをここでは結論づけない。** `git-workflow.md` は
issue #23 で計3回の誤発火を観測したと記録している一方、issue #47 の調査（Claude Code on the web /
Linux）では地の文だけでは発火しなかった。**どちらが現行かを切り分ける材料は無い**（バージョン差か
プラットフォーム差かも不明。この食い違いの扱いは今後の設計反映で決める）。**安全側に倒し、
どちらのhookについても連続させない**という結論だけを守る。

## コメントは独立行に置く

`cmd ; # 説明 ; cmd2` のように、**後続のコマンドを飲む書き方をしない**。`#` は行末までを
コメントにするため、同じ行に置いた後続コマンドは実行されない。

```
悪い例:
mkdir -p out ; # 出力先作成 ; cp src/a.txt out/

良い例:
mkdir -p out

# 出力先へコピー
cp src/a.txt out/
```
