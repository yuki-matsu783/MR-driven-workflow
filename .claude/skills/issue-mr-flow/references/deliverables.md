# issue-mr-flow 参照: 成果物の分離とHTMLビュー

## 計画と実施結果の分離（issue #87）

**個別計画（`wip/plans/【*】〜.md`）には「これから何をするか」だけを書き、実施した結果は書かない。**
調査結果・作業結果・反映結果は `wip/reports/日付_<全体計画名>_<内容を簡潔に>.md` へ記録する。

| | 個別計画 `wip/plans/【*】〜.md` | 結果 `wip/reports/…md` | 詳細ログ `wip/worklogs/…md` |
|---|---|---|---|
| **書くもの** | 目的・変更対象・方針・やらないこと・検証手順 | 実施した内容と、その結論・根拠・確認結果 | 何を試した／うまくいった／ダメだったか |
| **確定する時点** | 人間の合意時（flow-id 2-4・3-4・4-4） | 実施後（flow-id 2-6・3-6・4-6） | 作業中に随時 |
| **読み手の関心** | 「この方針でよいか」 | 「結果は妥当か」 | 「どう辿り着いたか」 |

同居させると次の3点が問題になる（issue #77 のフェーズ2で実際に発生し、レビューで分離の指示を受けた）。

1. レビュー時に「合意した計画」と「その後の結果」の区別がつかない。
2. 計画としての差分（レビュー往復で計画のどこが変わったか）が、結果の追記に埋もれる。
3. ライフサイクルが食い違う。計画は合意のスナップショットとして固定されるべきものだが、
   結果はpushのたびに書き換わる。

**`wip/plans/` `wip/reports/` のいずれにも、mdとHTMLを併存させる。md が正文であり、HTMLはその視覚化
（人間レビュー用ビュー）である。** 両者の寿命は同じで、flow-id 5-5 でまとめて削除する
（`.claude/rules/docs-workflow.md` の「ドキュメント運用」表）。

**本節が決めるのは「どこへ書くか」だけである。** HTMLビューの見出し構成は下記
「計画・レポートのHTMLビュー」のテンプレートが持つ（issue #54）。

## 計画・レポートのHTMLビュー（issue #54, #203）

`wip/plans/` `wip/reports/` の**人間レビュー用HTMLビュー**は、`.claude/skills/issue-mr-flow/assets/`
配下のテンプレートを土台にする。**記述の型（見出し構成）の正はテンプレート側にあり、SKILL.md
（フロー定義）は列挙しない**（二重管理を避けるため。型を変えたいときは、フロー定義である
SKILL.md ではなくテンプレートの中身を差し替える）。

| 用途 | テンプレート |
|---|---|
| **計画**（全体作業計画 flow-id 1-4／個別計画 2-1・3-1・4-1） | `plans.template.html`（1本） |
| **レポート**（調査結果 2-6／作業結果 3-6／反映結果 4-6／最終統括 5-4） | **5本から選ぶ**（下記「レポートテンプレートの選び方」） |

### レポートテンプレートの選び方（issue #203）

**既定は `reports-clean.template.html` である。迷ったらこれを使う。**
**新4本は共通のDOMを持ち、`<style>` だけが違う**（`<style>` を除いた部分がバイト単位で完全に
一致する）。**この4本の間なら、乗り換えても書き方を覚え直す必要は無い。**
**現行 `reports.template.html` だけは節構成が違う**（`nav.toc` ＋ `#review-focus` ＋ `#summary`
対 `aside.sidebar` ＋ 統合した `#overview`）。`<style>` の差し替えでは乗り換えられず、作り直しが要る。

| テンプレート | テーマ | `@media print` | 向く場面 |
|---|---|---|---|
| **`reports-clean.template.html`** | ライト／ダーク | 無し | **既定。** サイドバー常時表示で、章数が多くても迷子にならない |
| `reports-neobrutal.template.html` | ライト単一 | 無し | 結論を強く押し出したいとき（太い黒枠＋ハードシャドウ） |
| `reports-mono.template.html` | ライト／ダーク | 無し | **色が付いている＝意味がある**を徹底したいとき。白黒での閲覧・スクリーンショットでの色の誤読を避けたい場合 |
| `reports-paper.template.html` | ライト単一 | **有り** | **印刷・PDF化して配る**とき |
| `reports.template.html`（現行） | ライト／ダーク | 無し | **移行期のみ。** issue #203 以前に作られ、まだ片付いていないレポートを更新する場合に限る |

- **既定以外を選ぶのは、右列に当てはまる理由があるときだけ**にする。レポートごとに見た目が
  変わると、読み手が毎回レイアウトを学び直すことになる。
- **競合したら `paper` を優先する。** 「白黒で読む」は `mono` と `paper` の両方に当てはまるが、
  実際に印刷するなら `@media print` を持つのは `paper` だけである。
- 要素間の関連・依存関係が主題のレポートは、これら5本ではなく canvas 形式
  （`.claude/skills/canvas-report/SKILL.md`）の利用を検討する。
- **現行を残しているのは移行のためである。** 新規作成で選ぶ理由は無い。いつ廃止するかは
  未確定（`.claude/docs/ddr/i0203-01-レポートHTMLビューは共通DOMと4スタイルで持ち現行を残す.md`）。

### 検査手順の正はこの節にある（issue #203）

**HTMLビューを書いたあとに流す検査の正は、テンプレートの冒頭コメントではなく本節である。**
テンプレートの冒頭コメントにも同じ検査が書かれているが、あれは**読む場所にあることに意味がある
使い方の説明**であり、正ではない。

**issue #203 で新4本を足した結果、同じ検査手順の実体が5つに増えた。** 正を1箇所に決めないと、
検査を改訂したときに一部だけが古くなる（ルート `REVIEW-POINTS.md`「正は1箇所に決め、他はそこを
指すリンクだけにする」）。

| # | 検査 | 合格条件 |
|---|---|---|
| 1 | プレースホルダ | `grep -c '<!-- ここに書く' <出力ファイル>` が **0**（**テンプレート本体では逆に「0でない」ことが正しい**。下記） |
| 2 | リンク破断 | href集合 − id集合 が **0行** |
| 3 | 重複ID | id集合の `sort \| uniq -d` が **出力なし** |
| 4 | 外部依存（src/href） | `grep -nE "(src\|href)=['\"]?(https?:)?//"` が **0件** |
| 5 | 外部依存（url()/@import） | 同上（**0件**） |
| 6 | **構造の妥当性** | **コメントを除去してから**数えた `<style` と `</style>` が**どちらも 1** |

```bash
f=<出力ファイル>
grep -c '<!-- ここに書く' "$f"                                    # 1

hrefs=$(grep -oE 'href="#[A-Za-z0-9_-]+"' "$f" | sed 's/^href="#//;s/"$//' | sort -u)
ids=$(grep -oE '<[a-z][^>]*[[:space:]]id="[A-Za-z0-9_-]+"' "$f" | sed 's/.*id="//;s/"$//' | sort)
printf '拾えたhref=%s id=%s\n' "$(printf '%s\n' "$hrefs" | grep -c .)" "$(printf '%s\n' "$ids" | grep -c .)"
comm -23 <(printf '%s\n' "$hrefs") <(printf '%s\n' "$ids" | sort -u)   # 2
printf '%s\n' "$ids" | uniq -d                                          # 3

grep -nE "(src|href)=['\"]?(https?:)?//" "$f"                     # 4
grep -nE "(url\(|@import[[:space:]]+)['\"]?(https?:)?//" "$f"      # 5
# 6. コメントを先に除く（一般則1）。行頭・属性に依存しない形で数える
nc=$(perl -0pe 's/<!--.*?-->//gs' "$f")
printf 'open=%s close=%s\n' "$(printf '%s' "$nc" | grep -c '<style')" "$(printf '%s' "$nc" | grep -c '</style>')" 
```

**検査6を足したのは、issue #203 で実際に踏んだためである。** 計画のHTMLビューで `<style>` が
二重に出力されていた。**検査1〜5はどれも捕まえなかった**（アンカー・IDと外部依存しか見ないため）。

**足す理由は「`<style>` が2つある＝構造として不正」だけで足りる。** そこから先の描画結果——
2つ目がCSSのテキストとして扱われ続く `:root { … }` ブロックごと破棄される、ダーク環境では
メディアクエリ内の `:root` 再定義により正常に見えライト環境でだけ配色が落ちる——は
**CSSのエラー回復規則からの推論であり、ブラウザでは確認していない**（issue #203 の作業環境に
表示確認の手段が無い）。**推論を検査の根拠に据えない。**

**機械的に検査するときの一般則が3つある**（issue #203。詳細・経緯は
`.claude/docs/ddr/i0203-01-レポートHTMLビューは共通DOMと4スタイルで持ち現行を残す.md`）。

1. **コメントと地の文を先に除く。** HTMLコメント中に地の文として書かれた `<li>` `<details>` を
   タグとして数えて不一致が出た。**「検査が失敗した＝成果物が壊れている」とは限らない。**
   **ただし、これは「ヒットを残してよい」という意味ではない。** 外部依存検査（4・5）は
   **0件が合格**であり、地の文の引用が当たったなら**引用の書き方で0件へ戻す**
   （URLのスラッシュを `&#47;&#47;` と書く）。「ヒットするが問題ない」を残すと、
   次の人が本物の外部依存を見落とす（`wip/reports/REVIEW-POINTS.md`）。
2. **「出力なし＝合格」の検査は、負のコントロールを取る。** 検査コマンド自体が壊れていても
   同じく無出力になる。意図的に壊したコピーで検出できることを確かめる。
   `<h3 id="f1">` を `id="overview"` に変えると、**検査2と3の両方が反応する**（2つの検査を持つ理由）。
   **検査6も同じく負のコントロールを取る**——`<style>` をもう1つ挿入したコピーで `open=2` に
   なることを確かめる（実測済み）。**検査6は一般則1の適用例でもある**——`^<style>` と行頭に
   固定するとインデントされた重複を取りこぼし、固定を外すと**冒頭コメントの地の文で
   `<style>` に触れているだけのファイル**（このテンプレート自身がそうである）が誤検出になる。
   **コメントを先に除いてから数える**ことで両方を避ける。
3. **構造の同一性は、タグ名ではなくバイト単位で比べる。** タグ名の並びの比較は属性もテキストも
   見ないため、成立していない主張を「合格」と報告してしまう。

**空振りガード（拾えた件数）を必ず出す。** href・idが0件なら、抽出そのものが壊れている。

**プレースホルダ検査の合格条件は、テンプレート本体と成果物で逆になる。**

| 検査対象 | 合格条件 |
|---|---|
| **成果物**（`wip/plans/*.html` `wip/reports/*.html`） | **0件**（埋め忘れが無い） |
| **テンプレート本体**（`assets/*.template.html`） | **0件でない**（雛形なのでプレースホルダがあるのが正しい） |

### HTMLビュー共通の書き方（計画・レポートとも）

**この項は計画・レポートの両方にかかる**（上の2項は「レポートテンプレートの選び方」「検査手順」
という個別の話題だが、ここから下はHTMLビュー全般の規則である）。

**書く前にテンプレートを読む。** テンプレートは冒頭のHTMLコメントに使い方・必須／任意
セクションの区別・埋め忘れの検査方法を持つので、置いてあるだけでは伝わらない。

- **ファイル名は、対応する `.md` と同じベース名で拡張子だけ `.html` にする**（`wip/plans/` `wip/reports/`
  とも同じ規則）。全体作業計画のHTMLも、ハーネスが提示した自動命名をそのまま使う。
- **任意セクションは、書くことが無ければ `<section>` ごと削除する。** 埋めるために内容を
  水増ししない。必須セクションは削除しない。
- **プレースホルダ（`ここに書く: …` のHTMLコメント）を成果物に残さない**（上の
  「検査手順の正はこの節にある」の検査1）。**`<!--` まで含めて数える**——テンプレート自身を説明する計画・レポートの
  ように、地の文で「ここに書く」という語に触れる成果物を誤検知しないため。
- **md側と内容を同期させる。** md側の差分が「追加のみ」でないなら、HTML側も「追加のみ」では
  同期していない（`wip/reports/REVIEW-POINTS.md`）。
- **外部依存を持たせない**（CDN・外部フォント・画像を参照しない。上の検査4・5。**0件が合格**）。
  テンプレートのスタイルは自己完結しているので、`<style>` を差し替えない限りこの条件は保たれる
  （経緯: `.claude/docs/ddr/i0054-01-計画レポートのHTMLビューはassets配下のテンプレートへ切り出す.md`）。

**md側のテンプレートは無い。** `wip/plans/*.md` `wip/reports/*.md` の見出し構成は規定せず、自由記述の
ままとする（型を固定する価値があるのは、人間が繰り返し目を通すHTMLビューの側だけであるため）。
