# issue-mr-flow 参照: 成果物の分離とHTMLビュー

## 計画と実施結果の分離（issue #87）

**個別計画（`wip/plans/【*】〜.md`）には「これから何をするか」だけを書き、実施した結果は書かない。**
調査結果・作業結果・反映結果は `wip/reports/日付_<全体計画名>_<内容を簡潔に>.md` へ記録する。

| | 個別計画 `wip/plans/【*】〜.md` | 結果 `wip/reports/…md` | 詳細ログ `wip/worklogs/…md` |
|---|---|---|---|
| **書くもの** | 目的・変更対象・方針・やらないこと・検証手順 | 実施した内容と、その結論・根拠・確認結果 | 何を試した／うまくいった／ダメだったか |
| **確定する時点** | 人間の合意時（flow-id 2-4・3-4・4-4） | 実施後（flow-id 2-6・3-6・4-6） | 作業中に随時 |
| **読み手の関心** | 「この方針でよいか」 | 「結果は妥当か」 | 「どう辿り着いたか」 |

同居させると次の3点が問題になる（issue #77 のフェーズ2で実際に発生し、レビューで分離の指示を受けた）。

1. レビュー時に「合意した計画」と「その後の結果」の区別がつかない。
2. 計画としての差分（レビュー往復で計画のどこが変わったか）が、結果の追記に埋もれる。
3. ライフサイクルが食い違う。計画は合意のスナップショットとして固定されるべきものだが、
   結果はpushのたびに書き換わる。

**`wip/plans/` `wip/reports/` のいずれにも、mdとHTMLを併存させる。md が正文であり、HTMLはその視覚化
（人間レビュー用ビュー）である。** 両者の寿命は同じで、flow-id 5-5 でまとめて削除する
（`.claude/rules/docs-workflow.md` の「ドキュメント運用」表）。
**例外は `html-slides` スキルの成果物 `*.slides.html`＋`*.slides.json`（issue #168）**。スライドは
対応するmdを持たず、機械可読の対は構成案JSON側である（md同期の検査対象にしない。詳細:
`.claude/docs/spec/html-slides.md`）。

**本節が決めるのは「どこへ書くか」だけである。** HTMLビューの見出し構成は下記
「計画・レポートのHTMLビュー」のテンプレートが持つ（issue #54）。

## 計画・レポートのHTMLビュー（issue #54）

`wip/plans/` `wip/reports/` の**人間レビュー用HTMLビュー**は、次の2つのテンプレートを土台にする。
**記述の型（見出し構成）の正はテンプレート側にあり、SKILL.md（フロー定義）は列挙しない**
（二重管理を避けるため。型を変えたいときは、フロー定義である SKILL.md ではなく
テンプレートの中身を差し替える）。

| テンプレート | 使う場面 |
|---|---|
| `.claude/skills/issue-mr-flow/assets/plans.template.html` | 全体作業計画（flow-id 1-4）と個別計画（2-1・3-1・4-1）のHTMLビュー |
| `.claude/skills/issue-mr-flow/assets/reports.template.html` | 調査結果（2-6）・作業結果（3-6）・反映結果（4-6）・最終統括レポート（5-4）のHTMLビュー |

**書く前にテンプレートを読む。** テンプレートは冒頭のHTMLコメントに使い方・必須／任意
セクションの区別・埋め忘れの検査方法を持つので、置いてあるだけでは伝わらない。

- **ファイル名は、対応する `.md` と同じベース名で拡張子だけ `.html` にする**（`wip/plans/` `wip/reports/`
  とも同じ規則）。全体作業計画のHTMLも、ハーネスが提示した自動命名をそのまま使う。
- **任意セクションは、書くことが無ければ `<section>` ごと削除する。** 埋めるために内容を
  水増ししない。必須セクションは削除しない。
- **プレースホルダ（`ここに書く: …` のHTMLコメント）を成果物に残さない。**
  `grep -c '<!-- ここに書く' <出力ファイル>` が 0 であることで確認する（**`<!--` まで含めて
  数える**。テンプレート自身を説明する計画・レポートのように、地の文で「ここに書く」という語に
  触れる成果物を誤検知しないため）。
- **md側と内容を同期させる。** md側の差分が「追加のみ」でないなら、HTML側も「追加のみ」では
  同期していない（`wip/reports/REVIEW-POINTS.md`）。
- **テンプレートが定義していない要素・クラスを使わない**（issue #145 で2度踏んだ）。
  テンプレートの `<style>` は、そこに現れる要素とクラスにだけスタイルを当てている。
  **定義に無いものを書いても、エラーにはならず「スタイルが当たらないだけ」になる**ため、
  HTMLを開いて初めて——多くは開かないまま——気づく。
  - 実例1: `<h3>` の下へ `<h4>` を足したところ、見出しの階層が視覚的に表現されなかった
    （`plans.template.html` は `h4` を定義していない）。
  - 実例2: 注意書きを `class="warn"` と書いたが、テンプレートが定義しているのは
    `class="box warn"` である（`box` が枠と余白、`warn` が色）。`warn` 単体では何も当たらず、
    注意書きが地の文と区別できない状態になっていた。
  - **確認は「使った側」と「定義した側」の差を取る。** ただし**要素とクラスで信頼度が違う**。

    ```bash
    out='wip/reports/….html'; tpl='.claude/skills/issue-mr-flow/assets/reports.template.html'
    # 要素（機械的に判定できる。何も出なければ良い）
    comm -23 <(grep -oE '</h[1-6]>' "$out" | sed -E 's|</||;s|>||' | sort -u) \
             <(grep -oE '\bh[1-6]\b' "$tpl" | sort -u)
    # クラス（候補の列挙まで。ヒットは1件ずつ目で見る）
    sels="$(sed -E 's|/\*[^*]*\*+([^/*][^*]*\*+)*/||g' "$tpl" \
            | grep -oE '\.[a-zA-Z][a-zA-Z0-9_-]*(\.[a-zA-Z][a-zA-Z0-9_-]*)*' | sort -u)"
    grep -oE 'class="[^"]+"' "$out" | sed -E 's/class="//; s/"$//' | sort -u | while read -r v; do
      printf '%s\n' "$sels" | grep -qxF -- ".$(printf '%s' "$v" | tr ' ' '.')" || echo "候補: $v"
    done
    ```

    - **要素側は信用してよい。** 地の文が要素名に触れるときは `&lt;h4&gt;` とエスケープされるため、
      `</h4>` に一致するのは実際の使用箇所だけである（実測: `<h4>` を1件混ぜると検出できた）。
    - **クラス側は「名前が定義されているか」では足りない。** テンプレートは `.box.warn`
      `.chip.warn` のような**組み合わせ**にスタイルを当てており、`warn` という名前自体は定義に
      現れる。実例2の `class="warn"` は名前としては存在するのに何も当たらないので、
      **組み合わせのまま突き合わせる**必要がある（上のコードはそうしている）。
    - **クラス側は誤検知する。** 地の文がアンチパターンを引用していると、それも属性と同じ形で
      ヒットする（実測: この教訓を書いた `wip/reports/…_設計反映の結果.html` 自身が、
      `<code>class="warn"</code>` という引用で1件ヒットする）。**`grep` の結果を合否として
      扱わず、ヒットごとに属性か引用かを見る。**
  - **`main` を取り込んだ直後は、土台にしたテンプレート自身が古くなっていないかを確かめる。**
    テンプレートは配布アセットなので上流で更新される。古い版から生成したHTMLは、
    上の検査を通っても現在のテンプレートとは別物になる。
- **外部依存を持たせない**（CDN・外部フォント・画像を参照しない）。テンプレートのスタイルは
  自己完結しているので、`<style>` を差し替えない限りこの条件は保たれる
  （経緯: `.claude/docs/ddr/i0054-01-計画レポートのHTMLビューはassets配下のテンプレートへ切り出す.md`）。
- 要素間の関連・依存関係が主題のレポートは、`reports.template.html` ではなく canvas 形式
  （`.claude/skills/canvas-report/SKILL.md`）の利用を検討する。

**md側のテンプレートは無い。** `wip/plans/*.md` `wip/reports/*.md` の見出し構成は規定せず、自由記述の
ままとする（型を固定する価値があるのは、人間が繰り返し目を通すHTMLビューの側だけであるため）。
