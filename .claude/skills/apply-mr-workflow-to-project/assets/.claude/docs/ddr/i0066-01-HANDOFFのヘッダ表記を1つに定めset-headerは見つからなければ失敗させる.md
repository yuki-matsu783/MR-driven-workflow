# i0066-01. HANDOFFのヘッダ表記を1つに定めset-headerは見つからなければ失敗させる

対象issue: [#66](https://github.com/yuki-matsu783/MR-driven-workflow/issues/66)
関連仕様: [.claude/docs/spec/update-handoff-progress.md](../spec/update-handoff-progress.md)「HANDOFF.mdのヘッダ行」

## 背景

`update-handoff-progress.sh set-header --pr` は、`HANDOFF.md` のPR行が `- Draft PR:` 表記だと
どの行にもマッチせず、**ファイルを1バイトも変えないまま終了コード0を返して**いた。エラーも警告も
出ないため、AIエージェントは更新できたと誤認する（issue #46 の作業中に実際に踏み、ヘッダを手で
書き換えて回避した）。

調査で分かったのは、`- Draft PR:` は**引き金であって原因ではない**ということである。原因は
`cmd_set_header` が一致件数を持たず、0件でも無条件に書き戻していたこと。表記を統一しても、
ヘッダ行を消した・`--file` で別のファイルを指した場合には同じことが起きる。

さらに根には「**`HANDOFF.md` のヘッダ行の正しい表記がどこにも定義されていない**」という問題が
あった。リポジトリにコミットされている空テンプレートにヘッダ行の雛形が無く、タスクごとに
AIエージェントが書き起こしていたため、表記が揺れる構造になっていた。

## 決定

次の4つをまとめて採る。

1. **ヘッダ行の表記を1つに定める。** 項目名は `issue` / `ブランチ` / `PR` / `push回数` /
   `現在のループ` / `追従監視` の6つに固定し、`- Draft PR:` のような別名を認めない
   （Draftかどうかは値の側に書く）。定義の置き場は
   `.claude/docs/spec/update-handoff-progress.md`「HANDOFF.mdのヘッダ行」1箇所とする。
2. **`cleanup-task.sh` の `HANDOFF_TEMPLATE` へ雛形6行を持たせる。** 書き起こしを無くし、
   ゆらぎの発生源を断つ。
3. **`set-header` は、指定した項目のヘッダ行がちょうど1件見つからなければ、ファイルを書き戻さずに
   非0で終了する。** これを `set-header` 固有の話にせず、**スクリプト全体の方針**として仕様書へ
   1本立てる（`mark-done` は当初からこの形だった）。
4. **ヘッダ行の探索範囲を「ヘッダブロック」へ限定する。** 「やったこと」節の引用行を書き換えない。

### なぜ「表記を1つに定める」と「失敗させる」を両方やるのか

issueの「期待する動作」は、1（別名を受け入れる／表記を統一する）と2（無言で成功しない）を
別々に挙げていた。**片方だけでは足りない。**

- 表記を統一しても、`set-header` が無言で成功する構造そのものは残る（上記の「引き金であって
  原因ではない」）。
- 失敗させるだけでは、既存のゆらぎに毎回ぶつかる。ゆらぎの発生源（テンプレートに雛形が無い）を
  断って初めて、失敗が「異常時にだけ出るもの」になる。

## 却下した案

### 却下1: `- Draft PR:` を別名として受け付ける

issueの「期待する動作」1の前半にあたる案。`^-[[:space:]](Draft )?PR:` のようにパターンを広げれば
既存ファイルはそのまま動く。

**却下理由**: 表記のゆらぎを仕様として抱え込むことになり、次に別の別名（`- MR:`、
`- Pull Request:` 等）が現れたときに同じ判断を繰り返す。ゆらぎの原因は「表記が定義されて
いないこと」なので、そこを直さずに受け入れ口を広げても、書く側は次も自由に書く。

**この却下が成立するのは、決定3（失敗させる）とセットだから**である。単に別名を拒否するだけ
なら、既存ファイルで無言の失敗が起き続けて事態は悪化する。既存の `- Draft PR:` に当たったときは
エラーメッセージで正しい表記と直し方を示し、**1回だけ手で直せば以降はテンプレートが維持する**
形にした。

### 却下2: 見つからないヘッダ行を `set-header` が自動で挿入する

「無ければ作る」ほうが呼び出し側は楽で、`--loop` は既にそうしている。

**却下理由**: 誤記のヘッダ行を残したまま正しい行が増える状態（`- Draft PR:` と `- PR:` が並ぶ）を
作る。どちらが現在の値なのかファイルから判断できなくなり、人間が読む前提の `HANDOFF.md` として
最も避けたい壊れ方になる。`--loop` が例外なのは、その行が**後から増える項目**として設計されて
いて（issue #58）、「無い状態」が正常だからである。

### 却下3: issue #140（`mark-skip` のループ範囲伝播）と1つにまとめる

issue #140 のコメントが「スクリプト全体の方針として1本立てるなら1つにまとめる判断もあり得る」と
提案していた。両者は「呼び出しは成功したように見えるが、ファイルは期待した状態になっていない」
という同じ症状を持つ。

**却下理由**: 症状は同じでも、欠陥の性質が違う。

| | #66（`set-header`） | #140（`mark-skip`） |
|---|---|---|
| 何が起きるか | **何も書き換えられていない**のに成功する | **指示どおりに書き換えた**が、結果が表のルールに反する |
| 正しい挙動 | 決まっている（`mark-done` と同じ形にすればよい） | 決まっていない（issue本文が案A/B/Cの比較検討を求めている） |
| インターフェース | 影響しない | 案Aは「列挙したものだけを書き換える」という意味を変える |
| 仕様書の現在の記述 | 触れていない | 「意図した挙動である」と明記済み |

1つのPRへ混ぜると、レビューで「不具合の修正」と「設計判断」の評価軸が混ざる
（`.claude/skills/issue-mr-flow/SKILL.md`「種別を複数併記する場合／分ける場合」の
「迷ったら分ける」）。また #140 は仕様書の既存記述の書き換えを伴うため、#66 側で先に触ると
#140 の検討材料を消してしまう。

**まとめなくても #66 の成果は #140 へ効く。** 決定3で「書き換え対象が見つからなければ非0で
終了する」を仕様書へ1本立てたので、#140 は「`mark-skip` がこの方針をどう満たすか」という形で
検討を始められる。あわせて仕様書には、**`mark-skip` が作りうる不整合はこの方針の射程外であり
#140 の担当である**ことを明記した（「無言の失敗を全部まとめて直した」と読めると、#140 が
対応済みに見えてしまうため）。

### 却下4: ヘッダ行の表記を `.claude/rules/docs-workflow.md` 側に定義する

`docs-workflow.md` は `HANDOFF.md` の運用（何を書くか・いつ更新するか）を定めており、そこに
ヘッダ行の書式も置く案。

**却下理由**: この表記は `update-handoff-progress.sh` の探索パターンと**必ず一致していなければ
ならない**。スクリプトの仕様書から離れた場所に置くと、片方だけが更新される。`docs-workflow.md`
からは参照だけを張り、表記そのものは再掲しない（同じ内容を複数ファイルへ書かない）。

## 副次的に直したもの

調査の過程で、**`- 現在のループ:` 行の挿入位置が実物の `HANDOFF.md` と噛み合っていない**ことが
分かった。`set_loop_header_in_lines` は挿入位置の基準を「`## フロー進捗状況` 見出しより**前**に
あるヘッダ項目」に限っていたが、実物はヘッダブロックを見出しの**下**に置く。そのため基準が1件も
見つからず、フォールバックの「見出しの直前へ挿入」が働いて、この行だけが他のヘッダ項目から
切り離されていた（終了コードは0、警告も無し）。

既存テストのフィクスチャは「見出しが無くヘッダ項目がある」か「見出しがありヘッダ項目が無い」の
どちらかで、**実物が持つ「両方ある」組み合わせだけが抜けていた**。ヘッダ行の位置を定義する
本DDRの決定1と同じ根（位置を決めていなかった）から出た欠陥のため、同じissueで直した。

## 影響

- **非互換**: 旧テンプレートでリセットされた `HANDOFF.md`、および別名を使っている作業中の
  `HANDOFF.md` では `set-header` が必ず失敗する（変更前は無言で成功していた）。復旧は1回だけ手で
  6行を置けばよく、失敗時のメッセージにその手順を出している。詳細は仕様書の「影響範囲」。
- `mark-skip` の挙動は変更していない（issue #140 の担当）。
- `- 追従監視:` を `set-header` の対象へ加えることは行っていない（issue #88 の既存仕様のまま、
  手で書き換える）。
