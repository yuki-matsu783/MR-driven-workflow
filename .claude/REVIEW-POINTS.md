# レビュー観点（.claude配下）

## bashスクリプトの既知の罠

いずれも `.claude/rules/shell-script-style.md` に実例つきで記録されている。**過去に実際に
踏んだもの**なので、機械的に照合する。

- **外部プロセス起動のコスト**: ループ内で `jq` 等の外部コマンドを起動していないか。
  コマンド置換 `$(...)`・パイプも同じコストを持つ。ホットパスのヘルパーは `REPLY` へ返す。
- **jqの引数長**: サイズが可変・無制限になりうるデータを `--argjson` / `--arg` で渡していないか
  （`Argument list too long` でjqの起動自体が失敗する）。ファイル経由にする。
- **状態ファイルの自己回復**: 外部の状態ファイルを読んで `--argjson` へ渡す前に、空でなく有効な
  JSONであることを検証しているか（空文字列チェックを `jq -e .` より**先に**行っているか）。
- **NULバイトとコマンド置換**: `-z` 付きの出力を `$(...)` で受けていないか。存在判定だけなら
  `-z` を付けない、パスとして使うなら `while IFS= read -r -d ''` で受ける。
- **パラメータ展開の既定値**: 二重引用符の中で `${N:-...}` の既定値にバックスラッシュを
  書いていないか（`"${7:-\{\}}"` は `{}` にならない）。
- **CR混入**: Windows版jqの出力をファイル・コマンド置換・パイプで受ける箇所に `tr -d '\r'` が
  あるか。`for x in $(... | jq -r ...)` は最後の要素以外にCRが残る。
- **`awk`/`sed` の置換文字列**: 生成するシェルコードに `\r` `\n` `\t` を書いていないか
  （処理系がエスケープとして展開し、生のバイトが混入する）。
- **git bashのパス変換**: ネイティブ実行ファイルへDOS形式フラグを渡すなら `//in` の形か。
  コンテナ内の絶対パスを渡すなら `MSYS_NO_PATHCONV=1` か。

## スクリプトの作法

- 冒頭に `#!/usr/bin/env bash` と `set -euo pipefail` があるか。
- 「失敗しても継続したい」箇所を、コマンド置換または明示サブシェルの中で呼んでいるか
  （`if func; then` に直接置くと `set -e` が関数内部でも一時停止される）。
- stdinを読むスクリプトが `main` にまとまり、
  `if [ "${BASH_SOURCE[0]}" = "${0}" ]; then main; fi` のガードを通っているか
  （無いとテストで `source` した瞬間にハングする）。
- **書き換え・検索の対象範囲が、意図した範囲に限定されているか。** ファイル全体を走査すると、
  本文中に引用された同じ形の行まで巻き込む（issue #66 で実際に踏んだ。`HANDOFF.md` の
  「やったこと」節の `- PR: …` をヘッダ行として書き換えていた）。**限定は「見出しがあるときだけ」の
  ような条件付きにしない**（条件から外れた入力で、防ぎたかった事故がそのまま残る）。
- **「対象が見つからなかった」ことを検知して非0で終わるか。** 一致件数を数えずに書き戻すと、
  何も変えていないのに成功として返る。**書き換え側だけでなく読み取り側にも同じ範囲・同じ検知を
  適用したか**（片方だけ直すと、誤りが値に化けて残る）。
- 関数名がsnake_case、プロバイダ固有実装が `github_` / `gitlab_` 接頭辞か。
- BOM無しUTF-8・LF改行か（新規 `.ps1` を作るなら**BOM付き**UTF-8か）。

## テスト

- 副作用の無い純粋ロジックが `.claude/scripts/test/test_<対象>.sh` に切り出され、
  `passed=N failures=N` を出力し失敗時に終了コード1を返すか。
- 終了コードの検査に `"$(func; echo $?)"` を使っていないか（`if` で受ける）。
- 日本語を含む文字列の先頭を `${var:0:N}` で切り出して比較していないか。
- 末尾の改行を含む期待値に `$(...)` を使っていないか。
- CR混入の検査に `grep -c $'\r'` を使っていないか（バイト数比較で行う）。
- 合成フィクスチャだけで完了とせず、実データに対しても確認しているか。
- **純粋関数を直接呼ぶテストだけで済ませていないか。** 実運用の呼び出し経路（ディスパッチャ経由）を
  通すテストがあるか。単体テストが緑でも、経路の途中が未定義の関数を呼んでいれば本番は死んでいる
  （issue #127）。
- **既存処理の前後に判定ロジックを挟んだ場合**、判定の粒度が元の実装（外部コマンドの解釈）と
  同じか。表記のゆらぎ（ディレクトリ指定・末尾スラッシュ・相対/絶対）を検証しているか。

## VCS抽象化層（`.claude/scripts/src/vcs/`）

- 新しいProvider関数に `require_vcs_cli <自関数名> || return 1` があるか。
- `mcp_tool_hint` に対応するケースを追加したか。`SKILL.md` の対応表と揃っているか。
- GitHub版とGitLab版で戻り値の形が揃っているか（呼び出し元にプロバイダ差を見せない）。
- GitHub/GitLabの情報取得に `gh`/`glab` を使い、WebFetch・curlへ流れていないか。

## スキル・ルール・エージェント定義

- `SKILL.md` の手順番号が本文中の相互参照とずれていないか。
- 判定基準を複数ファイルへ再掲していないか（ルート `REVIEW-POINTS.md`「ドキュメントの構造」の
  「正は1箇所に決める」を、スキル・ルール・エージェント定義へ適用する）。
- `.claude/agents/*.md` `.claude/skills/*/SKILL.md` の `description` を、
  frontmatter規約の `description` で上書きしていないか（選択に使われる実キーのため）。

## ユースケース文書（`.claude/docs/usecase/`）

- **手順詳細（コマンド列・手順番号・オプションの説明）を再掲していないか。** usecase文書は
  逆引きの入り口であり、手順の正はspec/SKILL.md側にある。コードフェンス0は機械検査で
  確認できるが、**散文・箇条書きの形をとった手順再掲はこの観点でしか検出できない**
  （「まず〜を実行し、次に〜」のような順序付きの操作列は再掲の兆候）。
- 4見出し（どんな場面か／使う機能と流れの概要／何が得られるか／詳細へのリンク）が
  揃っているか。frontmatterは `type: usecase` か。
- リンクはファイル位置（`.claude/docs/usecase/`）からの相対パスで書かれ、実在するか。
- 文書を追加・改名・削除した変更に、`.claude/docs/README.md` のusecase節の更新が
  同じコミットで含まれているか（一覧の正はREADME1箇所）。
