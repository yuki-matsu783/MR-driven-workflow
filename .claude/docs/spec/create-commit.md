# コミット実行ラッパー（create-commit.sh）

対象: `.claude/scripts/src/create-commit.sh`

## 背景・目的

issue #39で、このリポジトリのコミットは `commit` スキル（`.claude/skills/commit/SKILL.md`）経由に
限定され、gitのコミットコマンドの直接実行は `.claude/hooks/block-direct-git-commit.sh`
（PreToolUse hook）がブロックするようになった（DDR i0000-09）。

当時のhookは「コマンド文字列にその2語が現れたらブロックする」という**部分一致**の仕組みで、
正規経路も例外ではなかった。そこで、**呼び出し文字列自体にその2語を含まないコミット手段**として
本ラッパーを置いた。スキルのStep 4はこのラッパーを呼ぶため、hookの対象にならず正規に実行できる。

**issue #53でhookの判定はコマンド位置ベースへ変わったが、本ラッパーの存在意義は変わらない。**
判定が正確になっても、`.claude/scripts/src/create-commit.sh` を呼ぶことが**コマンド位置で
gitのコミットを実行することそのもの**である以上、直接実行すればブロックされる。ラッパーは
「その2語を含まないから通る」のではなく、**別のコマンドとして実行されるから通る**（判定は
コマンド名をパスの末尾で比べるため、`bash …/create-commit.sh` の実行体は `bash` である）。
仕様: [command-position.md](command-position.md)。

issue #60で、**削除を含むコミットだけが正規経路で完結しない**ケースがあることが分かった。
flow-id 5-5（`wip/plans/` `wip/worklogs/` `wip/reports/` の片付け。issue #60 当時は 5-1）は全タスクが必ず通る工程であり、
issue #36・#55 の 5-1 では、その場で「先に削除をステージし、削除以外だけをラッパーへ渡す」という
2段構えの回避策を毎回編み出していた。本仕様はこの回避策を不要にし、かつ**なぜ不要なのか**を
記録として残すためのものである。

## 仕様

### 実行方法

```bash
bash .claude/scripts/src/create-commit.sh --message "<コミットメッセージ>" -- <file1> [file2 ...]
```

| 引数 | 必須 | 内容 |
|---|---|---|
| `--message <text>` | 必須 | コミットメッセージ。**内容・形式の正は `.claude/skills/commit/SKILL.md`「コミットメッセージの内容規約」**（本ファイルへは具体形式を書かない。両方に書くと片方だけが古くなるため。issue #185）。改行を含む複数行の文字列を渡してよく、`git commit -m` の仕様どおり1行目が件名・空行以降が本文になる |
| `--` 以降 | 1件以上必須 | 対象パス。ファイル・ディレクトリのどちらでもよく、gitのpathspecとして解釈される |
| `-h` / `--help` | — | 使い方を表示して終了（0） |

`--message` が空、または `--` 以降が0件の場合は使い方を表示して終了コード1で終わる。

**渡したパスに加えて、既にステージ済みの変更も同じコミットへ入る**（issue #54）。本スクリプトは
`git add -- <files>` で対象をステージした後、`git commit -m "$message"` を**パス指定なしで**実行する
ため、呼び出し前からindexに載っていた変更もそのままコミットされる。**「渡したパスだけがコミット
される」わけではない**点に注意する。

- **呼ぶ前に `git status` を見て、意図しないステージ済みの変更が無いことを確かめる**
  （運用上の注意は `.claude/rules/git-workflow.md`「コミット運用」にも置いてある）。
- 実例: issue #54 のフェーズ3で、`git mv` によりステージ済みだったディレクトリ改名が、別の
  コミットへ混ざった。同一ブランチかつsquash mergeのため実害は無かったが、**コミットメッセージと
  中身が食い違った**。
- **この挙動は意図的なものとして扱い、本issueでは変更しない**（理由は後述「なぜパス指定で
  コミットしないのか」）。

**持たないオプション**: `--amend` / `--no-verify` / パス指定なしのステージング手段
（`git add .` `git add -A` 相当）。commitスキルの絶対ルールを、呼び出し側の規約だけでなく
ラッパー側でも構造的に不可能にするためである。**内部でも `-A` は使わない**ため、何らかの経路で
パス指定が空になっても無制限のステージングへ化けることはない（後述「設計判断」）。

### 削除済みファイルのパスの扱い

**削除済みファイルのパスは、他のファイルと同じように `--` の後ろへ並べてよい。**
追跡済みファイルを削除しただけのパスは、`git add` がそのまま「削除」としてステージする。

**`git rm` で先に削除をステージしてから残りをこのラッパーへ渡す2段構えは不要であり、
むしろ有害である。** 削除をステージすると当該パスは index からも消えるため、後続の `git add` が
pathspec 不一致で失敗する（issue #60が「回避策」として挙げていた手順が、そのまま失敗の原因になる）。

既に削除がステージ済みのパスを渡した場合は、冪等にスキップして通知するだけで、コミットには
そのまま含まれる。

### パスの分類

`git add` が失敗したときに限り、渡されたパスを次の3つに分類する。

| 分類 | 条件 | 挙動 |
|---|---|---|
| ADD | worktree に存在する、または index にマッチするものがある（通常の変更・新規追加・追跡済みファイルの削除・配下を持つディレクトリ） | `git add` へ渡し直す |
| SKIP | worktree にも index にも無いが HEAD にはある（削除が既にステージ済み） | 標準出力へ1行通知し、そのままコミットに含める |
| UNKNOWN | いずれにも無い | **一切ステージせずに終了コード1**。該当パスと本仕様への参照を標準エラーへ出す |

判定はパス文字列の一致ではなく、pathspecごとに git 自身へ問い合わせる
（`git ls-files -- <path>` / `git ls-tree -r --name-only HEAD -- <path>`）。ディレクトリ指定・
末尾スラッシュ・相対/絶対表記の違いを自前で正規化しないためである。

分類上すべてADDなのに `git add` が失敗した場合（`.gitignore` 対象のパスを渡した等）は、gitの
エラー出力をそのまま見せて終了コード1で終わる。

### 終了コード

| コード | 状況 |
|---|---|
| 0 | コミット成功 |
| 1 | 引数不正／UNKNOWNを含む／ADDのみなのに `git add` が失敗 |
| その他 | `git commit` 自体の失敗（pre-commitフック失敗等）をそのまま返す |

## 失敗条件と、その原因

**唯一の失敗条件は「worktree にも index にもエントリが無いパスを渡したこと」である**
（引数不正・`.gitignore` 対象を除く）。UNKNOWNとして報告されたパスは、次のいずれかであることが多い。

- **削除を先にステージしてしまった**（`git rm` 等）。この場合は本来SKIPになるが、HEADにも無い
  （＝そのブランチで新規追加されたファイルを、コミットせずに削除ステージした）ならUNKNOWNになる
- **未追跡のまま削除された**ファイルのパス（gitはそのファイルを一度も知らない）
- **パスの綴り誤り**、または `git status` の出力からコピーした際の**8進エスケープ表記**
  （日本語を含むパスは既定で `"wip/plans/\343\200\220..."` のようにエスケープされる。
  `git -c core.quotepath=false status` を使うと生のパスで表示される）

**エラーメッセージ側にはこれらの推測を書かない**（issue #60でのレビュー判断）。実際には別の原因
だったときに誤誘導になるため、メッセージは事実（どのパスが把握されていないか・何もステージして
いないこと）だけを述べ、原因の解説は本仕様に集約する。

## 設計判断

### なぜ「先に `git add` を試し、失敗時だけ分類する」のか

- **正常系の挙動とコストを変えないため。** `git add` の呼び出し方は従来と同一で、追加のgit起動は
  発生しない。「既存の使い方が従来どおり動作する」ことがコードの構造として保証される
  （git bashの外部プロセス起動は約95ms/回と高くつく。`.claude/rules/shell-script-style.md`
  「外部プロセス起動のコスト」）
- **pathspecの解釈をすべてgitへ委ねられるため。** 常に自前で分類する案は、分類をパス文字列で
  行うことになり、**ディレクトリごと削除された `wip/reports/` をディレクトリ指定で渡すと UNKNOWN に
  なる**（`git ls-files -- wip/reports` が返すのは `wip/reports/xxx.html` であって `wip/reports` ではない）。
  これは現行動作からの機能後退であり、issue #60の実装中に検証で判明して作り直した
- **失敗しても中途半端なステージ状態にならないため。** `git add` はpathspecを先に検証し、1件でも
  不一致なら何もステージせずに終了する（下記「根拠にした git の挙動」）。リカバリ側で部分適用の
  ロールバックを考える必要がない

### なぜパス指定でコミットしないのか

`git commit -m "$message"` をパス指定なしで実行しているため、上記「実行方法」のとおり
ステージ済みの変更が同じコミットへ入る。`git commit -m "$message" -- <files>` へ変えれば
「渡したパスだけ」にできるが、次の2点で噛み合わない。

- 同じファイルのステージ済み部分と未ステージ部分の扱いが分かれ、直前に実行した `git add` の
  結果と食い違う。
- **「削除ステージ済みパスを冪等にスキップする」設計**（後述「削除済みファイルのパスの扱い」・
  DDR `i0060-01`）が、SKIPと判定したパスを「コミットには含める」ことを前提にしている。
  パス指定へ変えると、この前提の成否をあらためて確かめ直す必要がある。

**この2点は読解による判断で、実際にパス指定へ変えて壊れることは確かめていない**（issue #54。
挙動を変えないことが前提のため実測していない）。**変更を検討する場合は、issue #60 の10ケース、
とくに削除ステージ済みパスとディレクトリ指定のケースを実測すること。** 是非そのものは
独立した意思決定であり、変えるなら別issueを起票する。

### なぜ `-A` を使わないのか

issue #60の本文は `git add -A -- "${files[@]}"` を提案していたが、採用しなかった。理由と
却下の詳細は
[i0060-01-create-commitは削除ステージ済みパスをgit-addの失敗時分類で吸収する.md](../ddr/i0060-01-create-commitは削除ステージ済みパスをgit-addの失敗時分類で吸収する.md)
を参照。要点は、`-A` が症状を直さないこと（削除ステージ済みパスは `-A` でも失敗する）と、
**pathspecが空のときリポジトリ全体をステージしてしまう**ことである。

## 根拠にした git の挙動

issue #60のフェーズ2で、一時リポジトリ4本・36ケースを実測して確認した
（git 2.39.2.windows.1 / git bash / bash 5.2.12）。

| 挙動 | 内容 |
|---|---|
| 削除のステージ | `git add -- <追跡済みファイルを削除したパス>` は成功し、削除がステージされる。**issue本文の前提（削除済みパスは渡せない）は再現しない** |
| pathspecの照合先 | pathspecは worktree だけでなく **index に対しても**照合される。したがって「worktreeから消えていてもindexにあるパス」は一致する |
| 検証の原子性 | `git add` は渡されたpathspecを**すべて検証してから**ステージする。1件でも不一致があれば何もステージせずに終了する |
| 空のpathspec | `git add --`（パス指定なし）は何もしないが、`git add -A --` は**リポジトリ全体**をステージする |

  複数行でも1行目が件名・空行以降が本文になる）。**実測はLinux実機のみで、git bash実機では

- **`.claude/docs/usecase/` への影響は無い。** 唯一 `commit` スキルを指している
  `新しい機能開発を始める.md` は「フロー中のコミットの唯一の経路」としてリンクしているだけで、
  **規約の中身に踏み込んでいないため記述が古くならない**。確認した事実をここへ残す
  （確認したのに痕跡が無いと、確認していない回と外形上区別できないため）。
