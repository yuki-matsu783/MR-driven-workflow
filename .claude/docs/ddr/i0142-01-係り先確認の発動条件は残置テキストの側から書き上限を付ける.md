# i0142-01. 係り先確認の発動条件は残置テキストの側から書き上限を付ける

## 背景

`.claude/rules/docs-workflow.md` には issue #64 で追加された次のルールがあった。

> 既存ドキュメントへ新しい見出しを差し込むときは、挿入位置の直前の節が「その節全体にかかる
> 地の文」で終わっていないかを必ず確認する。

この文言が拾えるのは **#64 の形（見出しの差し込み・壊れたのは挿入位置の前）だけ**である。
しかし同型の事故は、issue #142 起票時点で4件確認されていた。

| 事故 | 何を変えたか | 壊れたテキストの位置 | 現行ルールで拾えるか |
|---|---|---|---|
| issue #64 | 新しい見出しを差し込んだ | **前**（挿入位置の直前の節の末尾） | 拾える（このルールの元ネタ） |
| issue #109 | 既存の節を (1)(2) に**分割**した | **前**（(1) 直下の結論行） | 拾えない（見出しの挿入ではない） |
| PR #139 | 新しい見出しを差し込んだ | **後ろ**（新設した見出しの配下に入った、見出しを持たない段落群） | **拾えない**（射程内の操作なのに「直前を見よ」という手順では検出できない） |
| issue #155 | 既存の箇条書きへ**項を1つ足した** | **前**（直前の項の末尾にあった補足） | 拾えない（見出しも節も階層も動いていない） |

**4件とも自己確認では見つからず、敵対的レビューが検出している。** 書いた本人は「新しく書いた
部分が正しいか」を見ており、「既にあった行の係り先が変わったか」を見ていない。

## 決定

### 1. 発動条件を、操作の分類ではなく残置テキストの側から書く

「新しい見出しを差し込むとき」を「**既存の記述を残したまま、その周囲を編集したとき**」へ置き換え、
**操作の名前で射程を判断しない**と明記した。見出しの差し込み・節の分割・並べ替え・箇条書きへの
項の追加は**例示**であって、条件の定義ではない。

**却下した案**

- **「構造変更全般」への言い換え。** 最初に思いつく一般化だが、**それ自体が操作の分類である**。
  issue #155 の形（同じ深さの項を1つ足しただけ。見出しも節も階層も動いていない）が「構造変更」に
  含まれるかは読み手に委ねられ、実際 #155 では含まれないと読まれて事故が起きた。
- **操作を列挙して増やす案。** #155 の時点で、当時列挙されていた4操作のどれにも当たらない形が
  既に現れている。**列挙は必ず漏れる**うえ、漏れたことは事故が起きるまで分からない。

### 2. 発動条件に上限を付ける

「残した記述の中に**直前・直後の内容に依存して意味が決まる文**があるとき」へ絞り、該当する5種を
例示した——節・項の全体にかかる補足／結論行／箇条書きを締める一文／**見出しを持たない段落**／
**指示語や省略で前を受ける文**。**そういう文が1つも無いと確かめられたときだけ、確認を省いてよい。**

**上限が要るのは、無条件の発動条件が「常時発動＝実質的に無視される規約」になるためである。**
ドキュメントの編集はほぼ必ず「既存の記述を残したまま、その周囲を編集する」形を取るので、
上限が無ければこのルールはすべての差分で発火する。

**同時に、上限が抜け穴にならないようにした。** 省けるかどうかは**前後を実際に読んで初めて決まる**
ため、「末尾へ足すだけだから」のような**操作の種類を理由にした省略を明示的に禁じた**。上限は
事後の確認結果としてしか成立せず、事前のショートカットには使えない。

**却下した案**

- **件数・行数での閾値**（「N行以上の編集なら確認する」等）。意味の依存はサイズと相関しない。
  #155 は1項の追加であり、閾値では必ず落ちる。
- **免除の例を操作名で書く案**（「独立した段落を末尾へ1つ足す等」）。issue #142 の初版はこう
  書いていたが、**#155 の実際の形とほぼ同じ操作**であり、直前の「操作の名前で射程を判断しない」と
  正面から衝突していた。読み手は括弧の中の具体例を先に拾うため、#155 と同型の編集を「これは免除の
  例だ」と落とす経路になる。

### 3. 規約（`.claude/rules/`）と観点表（`REVIEW-POINTS.md`）の両方へ、同じ発動条件を置く

**同じ条件を2箇所へ書くことを、二重管理と承知のうえで選んだ。**

理由は `collect-review-points.sh` の収集範囲である。同スクリプトが集めるのは
`REVIEW-POINTS.md` / `REVIEW-POINTS.local.md` だけで、**`.claude/rules/` は敵対的レビューへ
一切渡らない**。規約側にどれだけ丁寧に書いても、レビューの場では読まれない。

**却下した案**

- **観点表をポインタ（「詳細は `.claude/rules/docs-workflow.md`」）にする案。** 上記のとおり
  観点表がレビューへの唯一の経路なので、ポインタだけでは**辿る動機が生まれない**。実際、issue #142 の
  初版は観点表側に上限と「操作の名前で射程を判断しない」を欠いており、**同じルールが2ファイルで
  別物**になっていた（過検知と、列挙外の操作の素通りが同時に起きる状態）。
- **規約を廃して観点表1本にする案。** 規約としての正が観点表へ移り、**レビュー時以外に読まれ
  なくなる**。このルールは書いているその場で効いてほしいものなので、常時読込の規約側が要る。

**残るコストを、次の形で最小化した。**

- **実例（`計画の2階層構造` 等の固有名）は規約側にのみ置き、観点表からは参照で済ませる。**
  実例は運用しながら増えていく部分なので、更新点が規約側1箇所に寄る。
- **発動条件そのものは両方に書く。** ここだけは条件を変えるときに2箇所の更新が要る。この
  非対称（実例は1箇所・条件は2箇所）が、二重管理の範囲を条件の数行に閉じ込めている。

## 影響

- `.claude/rules/docs-workflow.md`（104〜132行）が正。実例は4件で、うち2件は issue #64 由来の
  既存の記述をそのまま残している。
- ルート `REVIEW-POINTS.md`「ドキュメントの構造」の先頭項目が、規約と同じ発動条件を持つ。

## 決定の適用中に踏んだこと

**この一般化を書き換える作業自体が、このルールの対象とする欠陥を作った。** 実例2件を既存2件の
**前**へ足した結果、既存2件目の書き出し「同じ作業で」が指す先を本文から特定できなくなった。
**既存6行はバイト単位でそのままなのに、係り先（どの作業の記録か）だけが変わっていた。**

対処は、この決定が新設した「**残した記述の側へ係り先を明示する**」をそのまま当てたもので、
既存2件の直前へ帰属を示す地の文を1行置き、リストを2つに分けた（既存6行は1バイトも変えていない）。

**検証の側も同じ形で不足していた。** 当初の自己検証は「締めの一文が箇条書きの末尾のままか」という
**位置の代理指標**しか測っておらず、「**位置は動かないが係り先が変わる**」形を原理的に検出でき
なかった。この形はまさに上記の対処が扱う領域である。検証へ「残した記述が指す先が、書き換え前と
同じものを指すか」を加えて判定し直した。

**5種の例示は、この2件を受けて3種から増えたものである。** 実際に起きた PR #139 の
「見出しを持たない段落」と、今回自分で作った「指示語で前を受ける文」が、**どちらも当初の3種の
例示の外**にあった。2件とも外れたのは偶然ではないと判断した。
