# i0172-01. 読まれない `.gemini/` 複製と `.agents/skills` エイリアス化と自立化はいずれも見送る

issue #172

## 背景

issue #172 は当初「`.gemini/hooks/` `.gemini/scripts/` `.gemini/docs/` の3ディレクトリを
外すべきか」を問うていた。調査の過程で次の2論点が加わり、最終的に3論点を判断した。

1. **論点1（自立化）**: `.gemini/` を「`.claude/` からの変換生成物」ではなく、
   Gemini CLI 単体で完結する独立資産へ改めるべきか。
2. **論点2（読まれない4ディレクトリ）**: `.gemini/rules/` `.gemini/docs/` `.gemini/hooks/`
   `.gemini/scripts/`（実行時に読まれる経路が公式ドキュメント上確認できないもの）を
   生成対象から外すべきか。
3. **論点3（`.agents/skills/` エイリアス）**: `.claude/skills/` と `.gemini/skills/` の
   二重管理を、共用パス `.agents/skills/` への一本化で解消できるか。

判断材料は issue #172 / PR #193 のフェーズ2（2回の調査）・フェーズ3（1回目・2回目の判断、
計2往復のレビュー）で作成した調査・作業結果である。**これらのレポート・計画は
`wip/plans/` `wip/worklogs/` `wip/reports/` 配下にあり、タスク完了時（flow-id 5-5）に
削除される**ため、恒久的な参照はこのDDRとPR #193のコミット履歴のみとする
（`.claude/rules/docs-workflow.md`「恒久的な参照先」）。数値・根拠の要点は以下の各節に
取り込んである。

## 決定

1. **論点1（自立化）: 見送る。** `.gemini/` は引き続き `.claude/` からの変換生成物とし、
   `.claude/docs/spec/sync-gemini-assets.md` の既定方針（編集は必ず `.claude/` 側へ行う）を
   維持する。
2. **論点2（読まれない4ディレクトリ）: 現状維持（4つとも生成対象に残す）。** 「外す根拠の
   有無」だけが未確定であり、決定そのものは確定している。
3. **論点3（`.agents/skills/` エイリアス）: 不成立。** `.claude/skills/` と `.gemini/skills/`
   の二重管理は解消しない。

用語変換規則・生成対象の列挙方法の詳細は `.claude/docs/spec/sync-gemini-assets.md` が正である。

## 理由

### 論点1: なぜ自立化を見送るのか

**この判断は flow-id 1-4（issue #172のスコープ拡大時、2026-08-23）にユーザーが下した**もので、
フェーズ3の分析結果ではない。理由は次の3点で、いずれも「今の構成でそう決めた」ではなく
「構成を変えても消えない」構造的な依存である。

1. ルート直下の `AGENTS.md`（`layer: seed`、常に配布される）が `.claude/rules/agent-common.md`
   を `@import` している。`.claude` 自体も `layer: core` で常に配布される
   （`.claude/dist-layers.json`）。
2. `.gemini/settings.json` の hook 6本すべてが `$GEMINI_PROJECT_DIR/.claude/hooks/…` を指す
   （用語変換規則3「パス部分は書き換えない」。上記「仕様」節）。
3. `.gemini/agents/issue-mr-resume.md` のようなサブエージェント定義が、実行時に
   `source .claude/scripts/src/vcs/Provider.sh` のような形で `.claude/scripts/` を直接使う。

**`.gemini/` だけを切り離しても、Claude Code 側の入口・Gemini CLI 側の hook とエージェント
定義の実体が `.claude/` を参照し続ける以上、依存はどの構成を選んでも残る。** ユーザー判断は
これを踏まえ「自立化ではなく、依存があることを明示する」を選んだ。この明示は
`GEMINI.md`「geminiCLI固有ルール」節へ追記した（2回目調査 Q10-3: 配布先の Gemini CLI
セッションへ実際に届く記録先は `GEMINI.md` だけであるという実測に基づく）。

### 論点2: なぜ4ディレクトリとも残すのか

4軸（軸1: 実行時に読む経路の有無／軸2: 残るファイルから切れる相対リンク数／軸3: 外すコスト／
軸4: 外す利得）を4ディレクトリへ適用した結果は次のとおり。

| | `.gemini/hooks/` | `.gemini/scripts/` | `.gemini/docs/` | `.gemini/rules/` |
|---|---|---|---|---|
| 軸1（読む経路） | 0件 | 0件 | 0件 | 0件（他3つと同じ消極的根拠） |
| 軸2（切れる相対リンク） | 1件 | 1件 | 18件（`rules/`発17・`skills/`発1を含む、自身は着信のみ） | 17件（自身が発、docs/が宛先） |
| 軸3（外すコスト） | 実装＋テスト＋ドキュメント2箇所＋配布先移行 | 左に加え死んだ設定2ファイル3行 | 実装＋テスト＋ドキュメント2箇所＋配布先移行 | 未評価 |
| 軸4（利得） | 14ファイル・217,308 B | 47ファイル・813,984 B | 115ファイル・1,456,431 B | 8ファイル・189,256 B |

**軸2の表記に注意**: 「17件」「1件」は `rules/` `skills/` が**発**（リンク元）で `docs/` が
**宛**（解決先）である。`rules/`・`skills/`単体の行は「自身が発、宛先はdocs/」という意味で、
`docs/`行の「18件（`rules/`発17・`skills/`発1を含む）」は`docs/`が受ける被リンク数の内訳を表す
（同じリンクを発側・着側の両方から数えている）。

3つの決め手（フェーズ3・1回目に導出）は `rules/` を加えても崩れなかった。

| 決め手 | 3ディレクトリ（hooks/scripts/docs/） | 4ディレクトリ（rules/を追加） |
|---|---|---|
| 1. 配布物は1バイトも減らない | 有効（`dist-layers.json` の `.gemini` は `layer: exclude`） | 変わらず有効 |
| 2. 部分的に外すと中間状態になる（落ちる割合が根拠） | 案3で81.9%（176/215ファイル）／78.7%（バイト数） | むしろ大きい: 184/215ファイル＝85.6%、2,676,979/3,159,948 B＝84.7%。決め手2の根拠は弱まらない |
| 3. 外す根拠は未観測の推論で対象を選べない | 有効（`.gemini/rules/` `.gemini/skills/` にも同じ根拠が当たり、3ディレクトリだけを外す線引きができない） | 前半は変わらず有効。後半は一部解消——`.gemini/skills/` `.gemini/agents/` が読まれることは公式ドキュメントで確定したため、「読まれる2つ」と「記載の無い4つ（`rules/`含む）」という線引きは可能になった |

**壊れる相対リンクの「件数」は18件（`rules/`発17・`skills/`発1、いずれも解決先は`docs/`）から
1件へ減るが、これは決め手2〈落ちる割合〉とは別の指標であり、決め手2の評価には使わない。**
残る1件のリンク元（`.gemini/skills/apply-mr-workflow-to-project/SKILL.md`）は Gemini CLI が
実際に読むファイルであり、消える17件（読まれない `.gemini/rules/` の中の壊れたリンク）とは
性質が異なる。件数の増減だけをもって「外す根拠が強まった／弱まった」と判定しない。

**それでも外さない。** 決め手1・決め手2は変わらず有効、決め手3前半（`rules/` `docs/`
`hooks/` `scripts/` が読まれないという結論自体）も「公式ドキュメントに記載が無い」という
消極的根拠のままで変わっていない。Gemini CLI 実機は一度も動かしていない。

#### 現在のコピー対象に「集合」は無く、正しい問いは別にある

`.gemini/` の生成対象は特定ディレクトリの集合ではなく、`.claude/` 配下の追跡ファイル**全件**
から `agents/*.md` と `settings.json`（変換生成する2つ）を除いたものである
（`git -c core.quotepath=false ls-files --cached --others --exclude-standard -z -- .claude`。
上記「対象ファイルの列挙」節）。issue #70 は当時の TARGETS（`docs hooks rules scripts skills`。
`agents` を欠いていた）の不足を是正した結果として全件列挙へ置き換えており、**この集合は
issue #70 で再検討済みであって、リンク運用時代からの単なる引き継ぎではない**（DDR
`i0070-01`）。

それでも、リンク運用時代は複製が生じないため対象を広く取るコストがほぼゼロだったのに対し、
issue #70でコピー方式へ変えた時点でそのコストが発生するようになった。**「`.claude/` 配下を
全部コピーしてよいか」という問い自体は、issue #70でも今回でも立てられていない。** issue #172
の問い方（「特定の3〜4ディレクトリを外すか」）は、この意味で切り方が合っていない——正しい問いは
**「`.gemini/` に何を置くべきか」**であり、それに答えるには Gemini CLI の読み込み経路の完全な
観測が要る（上記「受け入れた制約」）。この指摘は `i0000-13` → `i0070-01` の系譜に連なるもので、
次に同じ疑問を持つ人はこのDDRと `i0070-01` を最初に読むとよい。

### 論点3: なぜ不成立なのか

2回目調査で、Gemini CLI が `.agents/skills/` を読む経路が公式ドキュメントで確認できた一方、
Claude Code の公式ドキュメントには `.agents` への言及が0件だった。共用パスへ一本化すると
**Claude Code からスキルが見えなくなる**ため、二重管理の解消という狙い自体が成立しない。

## 却下した案

| 案 | 却下理由 |
|---|---|
| **案A: `.gemini/` を自立化する**（論点1） | ルート直下の `AGENTS.md`（常に配布される`seed`層）が`.claude/rules/agent-common.md`を`@import`し、`.claude`自体も`layer: core`で常に配布される。hook・エージェント定義の実体も`.claude/`を直接参照する。`.claude/`への依存を切ること自体が構造的に不可能（上記「論点1: なぜ自立化を見送るのか」）。 |
| **案B: `hooks/` `scripts/` だけ外す**（フェーズ3・1回目で検討） | 残る`.gemini/docs/`から2件の壊れたリンクが出る。加えて「読まれないから外す」という論拠は`.gemini/rules/`にも同じ強さで当たり、3ディレクトリだけを外す線引きを説明できない。 |
| **案C: `hooks/` `scripts/` `docs/` の3つを外す**（フェーズ3・1回目で検討） | 軸2が0件にならず18件残る。これを許容するには`.gemini/rules/`が読まれないという未観測の推論が要る（`.gemini/skills/`は本DDR作成時点で読まれることが確定済みなので、この推論の対象に含まれない）。仮に`rules/`について推論が正しいなら`rules/`も同時に外すのが筋だが、issue #172のスコープを越える。壊れたリンクを抱えた`rules/`を残す中間状態はどちらの前提からも正当化できない。 |
| **案D: `rules/` を加えた4つを外す**（論点2） | 案Cの理由に加え、4ディレクトリ版の「落ちる割合」（85.6%／84.7%）は3ディレクトリ版（81.9%／78.7%）より**大きく**、中間状態の悪さが強まる。件数が18件→1件へ減ることは、決め手2の根拠（落ちる割合）とは別の指標であり、外す根拠を強めない。 |
| **案E: `.agents/skills/` への一本化**（論点3） | Claude Code公式ドキュメントに`.agents`の言及が0件で、一本化するとClaude Codeからスキルが見えなくなる。 |

## 受け入れた制約

いずれの決定も、**Gemini CLI 実機は一度も動かしていない**（`command -v gemini` がこの
実行環境で空）。`.gemini/rules/` `.gemini/docs/` `.gemini/hooks/` `.gemini/scripts/` を
実行時に読む経路の有無（軸1）と `.agents/skills/` を Claude Code が読むか（論点3）は、
いずれも Gemini CLI・Claude Code の**公式ドキュメントの読解のみ**に基づく消極的根拠である
（「記載が無い＝未対応」は論理的には言い切れない）。**用語変換規則（ツール名対応表・
frontmatterスキーマ・settings.jsonのキー対応）の根拠は issue #70 で gemini-cli の
ソースコードを読んで確認済みだが、それとは別に、上記4ディレクトリ・`.agents/skills/`
が実際に読まれるかどうかのソースコード確認は、今回は行っていない。**

- 軸1（実行時に読む経路の有無）の「0件」は、公式ドキュメントに記載が無いという消極的根拠
  であり、ソースコードを読んで確認したものではない。
- `.agents/skills/` を Claude Code が読まないという判断（論点3）も、公式ドキュメントの
  読解のみに基づく。
- **この2点のソースコード確認は、ユーザーの判断により Gemini CLI のソースコードを
  参照できる別環境へ委ねられている。** このissueのセッションでは着手していない。

## 再検討の条件

次のいずれかが起きたら、`.gemini/` に何を置くかを問い直す。

| # | 条件 | 何を確かめるか | 判断がどちら向きに動くか |
|---|---|---|---|
| 1 | Gemini CLI のソースコードを参照できる環境が用意された（まだ着手していない） | `.gemini/rules/` `.gemini/docs/` `.gemini/hooks/` `.gemini/scripts/` が実際に読まれるか。あわせて `.agents/skills/` を Claude Code が読むか（論点3）も確認する | 4つとも読まれないと確認できれば、外す判断の根拠が明確になる（外すかどうか自体は改めて判断する）。いずれか読まれると確認できれば、その対象は除去候補から外れ、残す根拠が確定する |
| 2 | Gemini CLI 側に `.gemini/rules/` 等を読み込ませる設定キーが追加された | `settings.json` のトップレベルキー | 残す根拠が強まる（複製が死蔵でなくなる） |
| 3 | 複製が実害を出した | grepの二重計上・検索ノイズ・リポジトリサイズが繰り返し作業を誤らせた事例が複数出たか | 外す側へ動く |
| 4 | `.gemini/` の生成方式そのものが変わった（配布物へ含める・差分更新にする等） | `dist-layers.json` の `.gemini` が `exclude` でなくなれば、決め手1が崩れる | 外す側へ動く |

条件2〜4はこのリポジトリの中で観測できるが、条件1だけは実行環境の用意という外部要因に依存する。
