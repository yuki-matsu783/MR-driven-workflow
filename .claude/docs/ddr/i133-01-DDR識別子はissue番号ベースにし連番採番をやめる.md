# i133-01. DDR識別子はissue番号ベースにし連番採番をやめる

## 背景

issue #133「DDRの識別子を連番からissue番号ベースへ変更し、並行開発時の番号衝突を原理的に無くす」。

DDRは `.claude/docs/ddr/NNNN-タイトル.md` という4桁の連番で識別していた。**これは分散した
ブランチ上で共有の単調増加カウンタを採番する設計であり、2つのブランチが同時に新しいDDRを追加
すれば必ず同じ番号になる。** gitに単調増加カウンタを衝突なく採番する手段は原理的に無い。

さらに悪いことに、この衝突は**gitからは見えない**。`0027-A.md` と `0027-B.md` はファイル名が
異なるため、gitはコンフリクトを報告せず無言で両方をマージする（semantic conflict）。

この問題には既に2つの機構で対処していた。

- 検知: `check-base-conflicts.sh` の `hasDuplicateDdrNumber`（DDR 0029・issue #46）
- 解消: `resolve-conflict` スキルの類型A（作業ブランチ側を空き番号へ繰り下げ改番する）

しかし**過去4回（PR #29 / #37 / #49 / #52）のコンフリクトはすべてこの形**であり、対処の機構が
あっても発生自体は減っていなかった。そして改番には固有の危険がある。改番の対象はファイル名だけで
なく、frontmatterの `title`・本文冒頭の見出し・`.claude/docs/README.md` のDDR一覧・他ファイルからの
参照に及ぶ。**実際にissue #36の改番で `.gitignore` のコメントが古い番号のまま残り、issue #46で
修正するまで存在しないDDRを指していた。**

対処の機構を磨いても、この2つ（衝突が必ず起きること・改番のたびに参照が追従漏れしうること）は
無くならない。**採番方式そのものを変えるしかない。**

## 決定

1. **新規DDRの識別子を `i<issue番号>-<枝番2桁>` にする。** ファイル名は
   `.claude/docs/ddr/i<issue番号>-<枝番2桁>-<タイトル>.md`（例:
   `i133-01-DDR識別子はissue番号ベースにし連番採番をやめる.md`）。
   **issue番号はGitHub/GitLabが中央で採番するため、別ブランチ同士で同じ識別子が生まれることが
   原理的に無い。**
2. **枝番は2桁ゼロ埋めで `01` から振り、1件しか作らない場合も省略しない。** 枝番の採番は
   同一issue＝同一ブランチ内で閉じるため衝突しない。省略可にすると、後から2件目を足すときに
   1件目の改番が要り、いま無くそうとしているリスクを呼び戻す。
3. **issue番号はゼロ埋めしない。** `#133` とファイル名の数字を完全に一致させ、「何桁に揃えるのか」
   という新たな転記ミスの余地を作らない。
4. **接頭辞は小文字の `i` で固定する**（`I133-01` や `issue133-01` は認めない）。表記の揺れを
   許すと、同じDDRが別の識別子として二重に採番されうる。
5. **既存の連番DDR（本DDR作成時点で55件、`0003`〜`0059`）は改番しない。** ファイル名・本文・
   他ファイルからの参照（リポジトリ全体で262行・919箇所）をすべてそのまま維持する。新旧は
   **先頭が数字かどうか**で機械的に区別できる。
6. **重複検知の機構は廃止せず残す。** 識別子の抽出だけを新旧両方式へ一般化し、重複判定の
   ロジックは変えない（理由は下記「残した理由」）。
7. **`check-base-conflicts.sh` のJSON出力キー（`duplicateDdrNumbers` /
   `hasDuplicateDdrNumber`）は改名しない。** 値は「番号」ではなく「識別子」になるため名前は
   実態とずれるが、改名の是非は下記「JSONキーを改名しなかった理由」に記す。

命名規則は `.claude/rules/markdown-frontmatter.md`「DDRの識別子」、検知の仕様は
`.claude/docs/spec/check-base-conflicts.md`、解消手順は `.claude/skills/resolve-conflict/SKILL.md`
の類型Aが正。

## 却下した案

### 案A: 連番を維持し、採番をマージ直前まで遅延させる

DDRを作る時点では番号を決めず（`draft-タイトル.md` 等）、flow-id 5-1 の直前にdefaultブランチの
最新を見て空き番号を採る、という案。**衝突の窓を狭めるだけで、無くならない**。

- 2つのブランチが同じ日にマージ直前まで進めば、やはり同じ番号を採る。窓が数日から数分に縮む
  だけで、**確率を下げても原理は変わらない**。
- 採番が「マージ直前」に集まるため、衝突したときの手戻りが最も痛いタイミングで起きる
  （レビューが終わった後に、改番のためにもう一度差分が動く）。
- DDRは**マージ前からファイル名で相互参照される**（他のDDR・spec・スキル・plansから）。番号が
  最後まで決まらないと、参照を書く側が「後で直す」前提で書くことになり、これは今回無くそうと
  している追従漏れそのものである。

### 案B: 番号レンジを担当者・ブランチごとに分割する

`0100〜0199` は担当者A、`0200〜0299` は担当者B、のようにレンジを事前に割り当てる案。
**中央の調整が必要な点で、issueの目的と噛み合わない**。

- レンジの割り当て自体が中央の合意を要する。それを行うくらいなら、既に中央で採番されている
  issue番号をそのまま使うほうが単純で、追加の運用が要らない。
- レンジが枯渇したときの再割り当てが必要になる。枯渇の検知も再割り当ても人間の作業であり、
  **恒久的に運用コストが乗り続ける**。
- 1人の担当者が複数ブランチを並行して持つ場合（このリポジトリでは普通に起きる）、レンジ内で
  同じ衝突が再発する。担当者ではなくブランチ単位でレンジを割るなら、ブランチを作るたびに
  中央調整が要る。

### 案C: issue番号をゼロ埋めして `0133-01-…` とする

接頭辞を持たせず、issue番号を4桁ゼロ埋めして既存の連番と見た目を揃える案。
**新旧を機械的に区別できないため失格**。

- `0133-01-…` は既存の判定 `^[0-9]{4}-` にマッチしてしまう。issueが明示的に求めている
  「新旧を機械的に区別できる命名にする」を満たさない。
- 既存の連番が0059まで進んでいるため、**issue番号が59以下の古いissueに対してDDRを書くと、
  実在する連番DDRと同じ識別子になる**（例: issue #29 → `0029`）。

### 案D: 重複検知（`hasDuplicateDdrNumber`）を廃止する

新方式で衝突が起きないなら検知も要らない、という案。**残る衝突経路が2つあるため却下**。

1. **既存の連番DDR同士。** 今後は新規追加しないが、既存分が消えるわけではない。古いブランチが
   連番のDDRを持ったまま残っている可能性もある。
2. **同一issueへの追加作業を2つのブランチで並行して行った場合。** 枝番だけはローカルで決めるため、
   両ブランチが同じ枝番（例: どちらも `i133-03`）を採りうる。**この残存リスクは新方式でも
   消えない。**

検知の維持コストは正規表現の分岐1つで、廃止して得られるものより残して防げるもののほうが大きい。
なお2つ目のケースは、`resolve-conflict` スキルの類型A-2として「枝番だけを繰り下げる」手順を
定めたうえで、**同一issueを2ブランチで並行して進めている状態そのものを人間へ確認する**扱いに
した（衝突は症状であって原因ではないため）。

## JSONキーを改名しなかった理由

`duplicateDdrNumbers` / `hasDuplicateDdrNumber` は「番号」という語を含むが、値は今後 `i133-01`
のような**識別子**にもなる。`...Identifiers` へ改名するほうが実態に合う。それでも改名しなかった
のは、**このキー名が `resolve-conflict/SKILL.md`（4箇所）・`check-base-conflicts.md`（3箇所）から
参照される公開インターフェースだから**である。改名は全参照の追従を要求し、それは
**このissueが無くそうとしているリスクそのものを、別の場所に作り出す**。

一方、内部の純粋関数名（`ddr_number_to_reply` → `ddr_identifier_to_reply`、
`find_duplicate_ddr_numbers` → `find_duplicate_ddr_identifiers`）は改名した。こちらは
スクリプト本体と単体テストの2ファイルしか参照しておらず、追従漏れが起きようがないためである。

**この非対称（内部は実態へ合わせ、外部インターフェースは据え置く）は意図的である。**
片方へ揃えようとする前に、このDDRを読むこと。

## 受け入れたトレードオフ

- **ディレクトリの並び順が識別子の数値順にならない。** issue番号をゼロ埋めしないため、
  `i99-01` は `i133-01` より後ろに並ぶ。これは受け入れる。DDRはもともと番号順に通読するもの
  ではなく、`doc-search`（frontmatterインデックス）と `.claude/docs/README.md` の一覧から引く。
  README側は**issue番号の数値順**に並べることで補う。
- **一覧が2ブロックに分かれ、見た目の統一性が失われる。** 既存分を改番すれば統一できるが、
  改番の利益（見た目）に対して参照の追従漏れという実害のほうがはるかに大きい
  （上記のissue #36 → #46 の実例）。
- **DDRを書くにはissueが要る。** 記録したい意思決定があってissueが無い場合は、先にissueを起票する
  （`issue-create` スキル）。DDRはissueを起点とするフローの成果物であり、実運用では本DDR作成
  時点の55件中53件が本文にissue番号を持っていた（＝ほぼ全件が既にissueと対応している）ため、
  実質的な制約にならないと判断した。
