# 0066. AIが渡すコマンド文字列の説明はdescriptionとコメントへ分けて置く

issue #47。AIエージェントが Bash/PowerShell ツールへ渡すコマンド文字列の規約を
`.claude/rules/ai-command-style.md` として新設した際の判断を記録する。

## 背景

ユーザーがAIの実行するコマンドを承認するとき、判断材料は**コマンド文字列と `description` の2つ
だけ**である。ところが `description` は**コンソール上に1行しか表示されない**（issue #47 起票時に
実機確認。複数行を渡しても2行目以降は表示されなかった）。

一方、AIがツールへ渡す**コマンド文字列そのもの**についての規約は `.claude/rules/` に存在しなかった。
`.claude/rules/shell-script-style.md` は `.sh` ファイルとして保存するスクリプトの規約であり、
対象が違う。

## 決定1: 説明の置き場所を `description` とコマンド内コメントへ分ける

`description` は「全体として何をするか」の1行に固定し、**各論理ブロックの意図はコマンド内の
日本語コメントで書く**（複数行コマンドの場合）。

**検討したが採らなかった案:**

- **`description` を複数行にして、そこへ全部書く。** 2行目以降が表示されないため、書いても
  ユーザーに届かない。「書いたのに読まれない」状態はレビューの空白を隠すので、単に無効なだけの
  案より悪い。
- **コメントを書かず、コマンドを短く分割して1回ずつ承認させる。** 承認回数が増え、1回あたりの
  確認が形骸化する。ツール呼び出し1回あたりの往復コストも増える。

## 決定2: 出力トークン増よりも承認前の安全性を優先する（試行的運用）

コメントを必須にすると、AIの出力トークンは確実に増える。それでも、**意図しないコマンドを承認して
しまうリスクの低減を優先する**。

このトレードオフは定量的に比較できるものではない（トークン増は測れるが、「承認しなくて済んだ事故」
は数えられない）。したがって**まずは試行的に運用し、運用感が悪ければ見直す**前提とする。
この「試行である」という位置づけ自体を、ルール本文と本DDRの両方へ明記した。後から
「なぜこんな冗長な規約があるのか」と問われたときに、撤回してよい前提だったと分かるようにするため。

## 決定3: 1行コマンドは対象外にする

1行コマンドにはコメントを書かない。

`description` の1行で説明が尽きるため、コメントを足しても**得るものが無い**。一方で、`#` は
行末までをコメントにするため、1行のコマンドへコメントを差し込むと**後続を飲んで実行されなくなる**
リスクだけが残る。得るものが無く失うものがある以上、対象外にするのが妥当である。

## 決定4: 複数行コマンドの1行目にコメントを置かない（リスク回避として）

**結論は issue #47 の記述どおりだが、理由の書き方を変えた。**

issue #47 は理由を「先頭がコメント行だと `permissions.allow` / `deny` の前方一致が外れ、許可済みの
はずの操作で承認プロンプトが出る／`deny` をすり抜ける」と断定していた。フェーズ2の調査で実測した
ところ、**この断定は片方が反証され、片方は未確認**だった。

> **測定環境: Claude Code on the web（Linux）／2026-08-20。ユーザーの常用環境
> （Windows / git bash）では未確認。** 1環境・1バージョンの観測である。

| issueが挙げた帰結 | 対応する設定 | 実測 |
|---|---|---|
| `deny` をすり抜ける | `permissions.deny` | **この環境では起きなかった**（4ケース） |
| 許可済みの操作で承認プロンプトが出る | `permissions.allow` | **未確認** |

（この表は `.claude/rules/ai-command-style.md` にも載せている。**正はルール本文**であり、
本DDRのものは判断の材料としての再掲である。DDRの本文は不変で、ルール本文は更新されうるため。）

`deny` は**いずれか**の部分コマンドが一致したら拒否（ANY）、`allow` は**すべて**の部分コマンドが
一致して初めて自動承認（ALL）という非対称の意味論を持つ。この非対称のもとでは、先頭のコメント行が
「無視される」のか「どの許可規則にも一致しない部分コマンドとして数えられる」のかを、**`deny` の
実験では原理的に区別できない**（後者でも `deny` の結果は変わらない）。issue #47 が問題にしていたのは
まさに後者であり、**実測はissueの主張を反証していない**。

`allow` 側を直接確かめるには権限モードをプロンプトが出る形へ変える必要があり、そうすると以降の
あらゆるコマンドが承認待ちになって**セッションが止まる**（承認する人間が不在なら、実験用の設定を
削除するコマンドすら実行できず復旧できない）。実験のために作業不能になるリスクは取らず、
`allow` 側の実測は見送った。

**採用した書き方（案B。flow-id 3-1 時点でユーザーが指示した。記録: PR #132 のコメント
[#issuecomment-5356574028](https://github.com/yuki-matsu783/MR-driven-workflow/pull/132#issuecomment-5356574028)）:**

> `deny` 側はこの環境では外れなかったが、`allow` 側は未確認であり、照合の実挙動は環境・
> バージョンで異なる観測がある。ゆえに先頭は避ける。

**検討したが採らなかった案:**

- **案A: 制約自体を撤回する（1行目にコメントを書いてよい）。** `allow` 側を反証できておらず、
  撤回の根拠が無い。加えて実測は1環境・1バージョンのものであり、常用環境（Windows / git bash）では
  未確認である。1行目をコメントにしないコストはほぼ無い（説明を `description` へ移すだけ）のに対し、
  外れた場合の損失は非対称に大きい。
- **案C: issue #47 の記述どおり「前方一致が外れる」と断定して書く。** 少なくとも `deny` 側は実測と
  食い違う記述をルールとして残すことになる。根拠が事実でないルールは、次に読んだ人が実測して
  食い違いに気づいた時点で、ルール全体の信頼を落とす。

**「照合の実挙動が環境・バージョンで異なる」の出どころ**は、同じ調査で観測した hook の `if` の
挙動が `.claude/rules/git-workflow.md`・`.claude/docs/spec/issue-mr-workflow.md` に記録された
issue #23 時点の観測（Windows / git bash）と食い違ったことである。どちらが現行かを決める材料は
無く、**照合の実装は環境やバージョンで変わりうる**という一段抽象度の高い事実だけが残った。
この不確実性こそが、断定ではなくリスク回避として書く根拠になっている。

## 影響範囲

- 新規: 本DDR。
