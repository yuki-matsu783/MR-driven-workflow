# i0017-01. push前チェックリストはGit管理下のTSVで持ちPreToolUseで一律ブロックする

## 背景

push前に済ませるべき作業（worklogの追記・`HANDOFF.md` の更新・`index.jsonl` の最新化・
md/htmlの同期・`commit` スキル経由でのコミット）は、ドキュメント上のルールとしてしか存在せず、
AIエージェントの遵守に依存していた。issue #17 の作業中だけでも「`HANDOFF.md` の `- push回数:`
をpushの後に更新し、その1行だけが未コミットで残る」という形で1度失敗している。

issue #17 は、これを機構として強制することを求めた。

仕様は `.claude/docs/spec/push-checklist.md` が正である。本DDRは**採用した方式と却下案**を残す。

## 決定

### 1. チェックリストはGit管理下のTSVとして、pushごとに別ファイルで持つ

**却下案A: `.gitignore` 対象のローカル状態ファイルとして持つ。**
`wip/state/` に置けばコンフリクトの心配が無く、diffも汚さない。しかし issue #17 の受け入れ条件は
**「レビュアーがPRのdiffで見られること」**を求めている。本機構は**AIの自己申告**に立っており、
申告内容がレビューの俎上に載らなければ、申告が正しいことを誰も確かめられない。却下。

**却下案B: 1本のファイルを追記・上書きしていく。**
`HANDOFF.md` と同じ形になり、ファイル数が増えない。しかし**ブランチをまたぐと必ずコンフリクト
する**。同じ問題はDDRの4桁連番で繰り返し起きており（PR #29 / #37 / #49 / #52 の4回）、
issue #133 で「中央採番の値を使う」ことで解決した経緯がある。pushごとに
`<日付>_<ブランチのスラッグ>_push<N>_checklist.tsv` という名前にすれば、別ブランチが同じ名前を
作ることが原理的に無い。却下。

**却下案C: markdownのチェックボックス（`- [ ]`）で持つ。**
人間が読みやすい。しかし**機械的な検証がパースの正確さに依存する**。TSVなら「4フィールド固定」
という不変条件を立てられ、`verify` がそれ自体を検査できる。読みやすさは、TSVでも十分に保てる
（PRのdiffで表として表示されるわけではないが、1行1項目で状態が3列目に並ぶ）。却下。

> **TSVを採ったことで、実装中に1つ罠を踏んだ。** `IFS=$'\t' read -r -a` はタブをIFS空白文字と
> して扱うため、**行末タブを捨てる**。4フィールド固定という前提が壊れ、`verify` が自分の
> 生成物を必ず落とす形になっていた。bash組み込みだけの `split_tsv_line` で解決した
> （`.claude/rules/shell-script-style.md` へも記載）。

### 2. `check` は作業ツリーを書き換え、`verify` はHEAD断面を読む

この非対称は意図的である。両方を作業ツリーで見ると、**「作業ツリーだけ埋めてpushする」ことが
できてしまう**。HEADを読むことで、「埋める」だけでなく「コミットへ含める」までが強制される。

副作用として、**チェックリストを埋めただけではpushが通らない**（同じコミットへ含める必要が
ある）。これは意図した挙動であり、ブロックメッセージにもその旨を書いている。

### 3. push検知を自前で書かず `CommandPosition.sh` へ委譲する

issue #17 のコメントによる明示の指示である。issue #53 で判定がコマンド位置ベースへ変わって
おり、`command_invokes_git_subcommand` を使えばヒアドキュメント本文・クォート内・コメントの
地の文で誤発火しない。**同じ判定を2箇所に持つと、片方だけが更新されて挙動が分岐する。**

### 4. 縮退時のフォールバックに、前置フィルタを流用しない

**これは実装中に一度作り込んで、敵対的レビューで指摘された誤りである。**

本hookは `if` フィールドを持たずBash/PowerShellの全呼び出しで起動するため、
`.claude/rules/shell-script-style.md`「hookの前置フィルタ」に従って
`raw_hints_at_git_push`（bash組み込みだけの超集合判定）で足切りしている。この関数を
`CommandPosition.sh` を使えない場合のフォールバックへも流用していた。

**前置フィルタとブロック判定は、超集合であるべき向きが逆である。**

| | 過剰検知したときのコスト |
|---|---|
| 前置フィルタ | jq起動1回の無駄。**緩める側へ倒してよい** |
| ブロック判定 | **実行の停止**。緩める側へ倒すと止まってはいけないものが止まる |

具体的な害は再現済みである。前置フィルタは「`push` という語がどこかに現れるか」しか見ないので、
**回復のために叩く `push-checklist.sh check` がパスに `push` を含むため必ずブロックされ、
縮退環境では自力で回復できなくなる。** 「縮退時はブロック側へ倒す」方針は妥当だが、倒した先が
回復不能では方針として成立しない。

専用の `command_hints_at_git_push_degraded` を用意し、(1) basename が `git` のトークンがある、
(2) その後ろに `push` トークンがある、の**両方**が揃ったときだけブロックする形にした。
`git` トークンをAND条件にしたことで、回復コマンドは構造的にブロックされない。

**却下案: `grep -qiE 'git[[:space:]]+push'` を使う。** これも精密判定の部分集合であり、
`git -C /x push` を取りこぼす。かつforkが1回増える。却下。

なお、この形は精密判定の超集合ではない（`eval "git push"` 等を取りこぼす）。縮退時は元々
best-effort であり、**取りこぼしの害（1回のpushが素通りする）より回復不能の害が大きい**という
判断である。

**この禁止が効くのは「フォールバックの結果が実行の停止（ブロック）につながる場合」だけである。**
`post-push-next-checklist.sh`（PostToolUse。次回分のチェックリストを生成するだけで、pushを
止めない）は、同じ `raw_hints_at_git_push` を縮退時のフォールバックへ**そのまま流用している**。
過剰検知の結果は「余分に1本生成する」だけで、`new` の冪等性（同じHEAD SHAには1本しか作らない）が
これを無害に吸収するため、`block-unchecked-push.sh` と同じ回復不能性は生じない。**フォールバックが
過剰検知したときに実行が止まるかどうかで、専用関数を書くか前置フィルタを流用してよいかが分かれる**
（issue #17フェーズ4の敵対的レビュー2回目で、この条件が `.claude/rules/shell-script-style.md` に
明記されていないと指摘された。同ファイルは本節を「詳細」として参照する）。

### 5. コミット忘れ（`stale`）も exit 2 でブロックする

**当初は exit 1（非ブロックの警告）だった。敵対的レビューでの指摘を受けて変えた。**

チェックリストは flow-id 5-5 まで蓄積するため、新しく生成された分をコミットし忘れても、
`verify` は HEAD に残る**古い（全 done の）チェックリスト**を見て 0 を返してしまう。つまり
**本機構が防ぎたい失敗そのもの——「必要な更新をcommitへ含め忘れる」——が、唯一ブロックされない
経路になっていた。**

加えて、PreToolUse の `exit 1` の stderr がユーザーへ届くかは未確認である。届かなければ
**無言で素通りする**。

ブロックへ倒しても回復手段は「チェックリストをcommitへ含める」だけで、その
`create-commit.sh` の呼び出しは push を含まないため止まらない。したがって**倒した先が回復可能**
であり、上記4の判断基準と整合する。

### 6. pushの引数を解釈せず、一律でブロックする

`git push --tags` / `git push origin --delete <branch>` のように**現在のブランチを送らないpush**
も、チェックリスト未完了なら一律でブロックする。

**前提として、逃げ道は既に1つ存在する。** `push-checklist.sh` は全項目に `skip <id> <理由>` を
提供しており、`verify` の合格条件は「全行が `done` **または** `skip`」である。つまり
**項目単位の文書化された迂回路は最初からある**。以下の比較はこの事実の上に立つ。

| 案 | 内容 | 評価 |
|---|---|---|
| **A（採用）** | 一律ブロックのままにし、**詰まったときは `skip` で解く**ことをspecとブロックメッセージへ明記する | pushの**引数**を解釈する必要が無い。逃げ道を新設せず、既にあるものを使う |
| B | `--tags` / `--delete` / 明示的なrefspecを判定して通す | **却下**。refspec・`--all` / `--mirror`・`push.default` の設定まで解釈しないと正しく判定できず、判定の面積がpush検知本体より大きくなる。issue #17 のコメントが「push検知を自前で書くな」と指示した理由と同種のリスク |
| C | 環境変数等による**新しい**無効化スイッチを用意する | **却下**。`skip` で足りるものを二重に作ることになる。`block-direct-git-commit.sh` が無効化スイッチを持っていないのとも揃わない |

**AとCの違いは「新設するか、既にあるものを使うか」だけである。** Cを却下しながらAを採るのは、
`skip` が**項目ごとに理由を書かせ、その理由がGit管理下のdiffに残る**——つまり迂回した事実が
レビュアーに見える——のに対し、環境変数のスイッチは何も残さないためである。

**Aを採る決め手は、誤りの向きの非対称である。** Bが誤ると**通してはいけないpushを通す**
（ガードが黙って効かなくなる）。Aの誤りは**通すべきpushを止める**だけで、その場で見えるうえ
必ず解ける。

**Aのコストは0ではない。**

- **本リポジトリの現時点のフローでは0**（`--tags` も `--delete` も行わない）。
- 詰まった場合の実コストは「全項目を `skip` で埋めて**1コミット積む**」ことである
  （`verify` はHEAD断面を読むので、作業ツリーだけ埋めても解けない）。
- **この機構は配布層 `core` として他プロジェクトへ配られる。** タグpushを日常的に行う配布先では
  このコストが繰り返し発生する。配布先の第一手は `skip`、次の手は `.claude/settings.json` から
  本hookの登録を外すこと（specへ記載済み）。

### 7. push成否の判定に `HEAD == @{upstream}` を使わない

PostToolUse で次回分を生成する条件のひとつが「HEADが公開済みであること」である。

**却下案: `HEAD` と `@{upstream}` のSHAを比較する。** 一時リポジトリでの実測により、
**両方向へ誤る**ことを確認した。`git branch --remotes --contains HEAD` が非空であることを
条件にする。

### 8. チェック項目を外部定義ファイルにしない

項目は `push-checklist.sh` の配列が持つ。

**却下案: `.mrworkflow.json` 等へ項目定義を持たせ、配布先が編集できるようにする。**
項目は**フロー定義そのもの**であり、`.claude/` は配布層 `core`（本家所有）である。配布先が
項目を編集できると、フロー定義が配布先ごとに分岐する。配布先が項目を変えたい場合は上流へ提案
する。却下。

**ただしディレクトリ名は決め打ちしない。** 項目の文言に `{plansDir}` / `{reportsDir}` の
プレースホルダを置き、`.mrworkflow.json` の実際の設定値で埋める。同じスクリプトが設定を
読んでいるのに文言だけ本リポジトリ固有の `wip/plans/` を埋め込んでいると、配布先で存在しない
パスを案内することになる（これも敵対的レビューでの指摘）。

## 結果として受け入れた性質

**本機構は「作業ツリーが常にクリーンかつリモートと一致」と構造的に両立しない。**

pushのたびに次回分が生成されるため、pushの直後には必ず未コミットのチェックリストが1本ある。
それを `pending` のままコミットすると、今度は `verify` の対象がそのファイルになるので埋めるまで
pushできない。

運用としてはこれで正しい（次のpushの作業をしながら埋める）が、**知らずに両方を満たそうとすると
「中身が確定していないチェックリストを埋めたくなる」——すなわち実施していないことを `done` と
書く動機になる。** 本機構は自己申告に立っているため、これが最も避けたい壊れ方である。
specの「未決定事項・懸念点」へも記載した。
