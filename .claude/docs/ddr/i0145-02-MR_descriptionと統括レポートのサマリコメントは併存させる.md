# i0145-02. MR descriptionと統括レポートのサマリコメントは併存させる

## 背景

issue #145 でMR descriptionを10節構成のアーカイブへ作り替えた結果、**issue #111 が導入した
最終統括レポートのサマリコメント（flow-id 5-4）と役割が重なった**。どちらも「このMRで何を・
なぜ・どうやったか」をMR/PRのページ上へ残すものである。

| | MR description | サマリコメント（flow-id 5-4） |
|---|---|---|
| 更新するのは | `describe`（flow-id 2-5 / 2-10 / 3-5 / 3-10 / 4-5 / 4-10） | flow-id 5-4 で1回 |
| 更新の仕方 | **全文置換**（`set_mr_description`） | **新規投稿**（`add_mr_comment`） |
| 見出し | 10節 | 5見出し |
| 位置 | PR/MRページの先頭（本文） | コメント欄の末尾 |

「片方に寄せるべきではないか」という論点が、issue #145 のフェーズ2の調査で挙がった。

## 決定

1. **併存させる。** どちらも廃止しない。
2. 分ける軸は「**自動処理が繰り返し上書きするか（description）／1回きりか（サマリコメント）**」
   という**上書きの非対称**である。
3. **descriptionの最終形は flow-id 4-10 であり、「常に最新」ではない。** flow-id 5-3〜5-5 で
   生じる変更（`.gemini/` の再生成・統括レポートの追加・作業ファイルの削除）はdescriptionに
   載らない。**この差は許容する。**
4. **flow-id 5-4 の後に `describe` を追加しない。**

## 理由

### なぜ併存させるのか

**2つは「同じことを2回書いている」のではなく、更新のされ方が違う。**

descriptionは `describe` が呼ばれるたびに**全文置換**される。フェーズが進むごとに内容が
差し替わり、**最後に書かれたものしか残らない**。一方サマリコメントは投稿されたら動かない。

この非対称は、**編集されない記録が1つ要る**という形で意味を持つ。フェーズ2の時点で「未実施」と
書いた検証が、フェーズ4のdescriptionでは「達成」に置き換わっている——それが正しい振る舞いだが、
「どの時点で何が分かっていたか」は失われる。サマリコメントはその断面を1つ固定する。

### 根拠は外部APIの性質ではない（限界の記録）

**「サマリコメントは編集されない」という性質は、GitHub/GitLabの制約ではない。** どちらのAPIも
コメントの編集を提供している。そうではなく、**このリポジトリの自動化経路にコメントを編集する
関数が無い**——`.claude/scripts/src/vcs/Provider.sh` は `add_mr_comment`（投稿）を持つが、
投稿済みコメントを更新する関数を持たない——というだけである。

**この限界を明記しておかないと、将来 `Provider.sh` へ編集関数が足された時点で、本DDRの根拠が
無言で消える。** そのときは本DDRを supersede するか、`add_mr_comment` を使い続けると
明示的に決め直す必要がある。

### なぜ「descriptionは常に最新」にしないのか

`describe` の最後の呼び出しは flow-id 4-10 である。以降のフェーズ5では次の変更が生じる。

| flow-id | 変更 | descriptionのどの節へ効くはずだったか |
|---|---|---|
| 5-3 | `.gemini/` の変換同期 | `## 変更内容` |
| 5-4 | 統括レポートの作成・投稿 | `## 変更内容` `## 検証` |
| 5-5 | 作業ファイルの削除 | `## 変更内容` |

いずれも**本質的な変更ではなく、フローの後始末である**。descriptionが「フェーズ4までの記録」で
あることを明示すれば、読み手が誤解する余地は無い。

## 却下案

### 案1: flow-id 5-4 の後に `describe` をもう1回追加する

**却下。理由は2つある。**

1. **置ける位置が無い。** flow-id 5-5（作業ファイルの削除）より後で呼ぶと、手順1（作業ファイルを
   読んで要点を掴む）の材料そのものが消えている。5-4 と 5-5 の間なら材料は残っているが、そこで
   組み立てたdescriptionは 5-5・5-6 の結果を含められないため、**結局「4-10 時点の全体像＋後始末の
   一部」にしかならない**（理由2へ吸収される）。5-5 と 5-6 の間は、「生成と確定の間に他のステップを
   挟まない」ために issue #112 が意図的に詰めた位置なので、そこへは挟めない。
2. **得られるのが後始末の記録だけである。** 上表のとおり、載るのは `.gemini/` の再生成・
   統括レポートの追加・作業ファイルの削除であり、いずれも読み手の判断を変えない。
   `describe` の1往復（テンプレートの読み込み・全文の組み立て・API呼び出し）に見合わない。

### 案2: サマリコメントを廃止し、descriptionへ一本化する

**却下。** 上記「なぜ併存させるのか」のとおり、**編集されない断面が失われる**。加えて
サマリコメントはコメント欄の末尾に付くため、**通知が飛ぶ**（descriptionの更新では飛ばない）。
レビュアーへ「作業が一区切りついた」と伝える手段でもある。

### 案3: サマリコメントを、descriptionへのリンク1行にする

**却下。** リンク先（description）は `describe` で全文置換されるため、**リンクを踏んだ先の内容が
コメント投稿時点とは違う**。断面を固定するという目的をまったく果たさない。

## 粒度の違い

サマリコメントの5見出しはdescriptionの10節より粗く、1つの見出しが複数の節を受け持つ。この
関係は `.claude/docs/spec/issue-mr-workflow.md` の issue #111 の節が扱う。**本DDRでは再掲しない**
（仕様は spec が正であり、本DDRはなぜそう決めたかを持つ）。

**節と見出しの対応表は、specにも本DDRにも置かない。** 見出しの正はdescription側が
テンプレートファイル、サマリコメント側が `references/phase5-close.md` にあり、対応表はその両方を
写すことになる（issue #145 が解消した二重管理を作り直す）。
