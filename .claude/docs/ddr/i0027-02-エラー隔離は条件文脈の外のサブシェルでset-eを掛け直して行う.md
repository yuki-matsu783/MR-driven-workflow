# i0027-02. エラー隔離は条件文脈の外のサブシェルでset-eを掛け直して行う

## 背景

issue #27。収穫スキルの `scan` は複数の配布先を受け取り、読めない配布先があっても他の結果を
返す「配布先単位のエラー隔離」を要件とした。当初 `( scan_one_dest "$dest" ) || rc=$?` と
書いたところ、敵対的レビューで「この形は途中失敗を検知できない」と指摘され、実測で確認した。

あわせて、`.claude/rules/shell-script-style.md`「エラー方針」の従来記述——「コマンド置換・
明示サブシェルはフォークされるため、フォークされた側では `set -e` が正しく機能する」——が、
少なくとも bash 5.2 では成り立たないことも判明した（規約本体の訂正は issue #27 の
AIアセット反映として実施。本DDRはその根拠の記録）。

## 実測（bash 5.2.21 / Claude Code on the web・Linux／2026-08-23）

原因は**2つの独立した機構**であり、混同しないこと。

1. **明示サブシェル `( f )` は `-e` 自体を継承する**。条件文脈の外なら `( f )` 単体で
   正しく fail-fast する（実測: `( f ); echo after` は何も出力せず exit=1）。壊れるのは
   **条件文脈（`||`・`if`）に置いたとき**で、errexit の一時停止がサブシェルの**内側まで
   伝播**し、途中失敗が素通りする（実測: `rc=0; ( f ) || rc=$?` は f 内の `false` の後の
   `echo REACHED` まで実行され rc=0）。
2. **コマンド置換 `$(...)` は `shopt inherit_errexit` が既定オフ**のため、条件文脈かどうかに
   関係なく `-e` を一切継承しない（実測: `out="$(f)"` は条件文脈の外でも関数本体が最後まで
   走り exit=0。`shopt -s inherit_errexit` を立てると exit=1 になる）。
   「条件文脈の外へ出せばコマンド置換でも fail-fast する」とは言えない。

再現コマンド（いずれも `f() { false; echo R; }` を `set -euo pipefail` 下で呼ぶ）:

```bash
# 機構1: 条件文脈で途中失敗が素通り（REACHED が出て rc=0）
bash -c 'set -euo pipefail; f() { false; echo REACHED; }; rc=0; ( f ) || rc=$?; echo "rc=$rc"'
# 機構1の裏: 条件文脈の外なら fail-fast（何も出力せず exit=1）
bash -c 'set -euo pipefail; f() { false; echo R1; }; ( f ); echo after'; echo "exit=$?"
# 機構2: コマンド置換は条件文脈の外でも -e を継承しない（R2 と after が出て exit=0）
bash -c 'set -euo pipefail; f() { false; echo R2; }; out="$(f)"; echo "after out=$out"'; echo "exit=$?"
```

## 決定

**フォークされる側の内側で `set -e` を掛け直す。** 出力の要否で2形。

```bash
# 出力を捨ててよい場合（サブシェル。条件文脈に入れない）
set +e
( set -e; risky_func )
rc=$?
set -e

# 出力を受け取る場合（コマンド置換の内側で掛け直す。外側の set +e だけでは機構2により不足）
set +e
out="$(set -e; risky_func)"
rc=$?
set -e
```

いずれも実測で、途中失敗が rc=1 に現れること（出力受け取り形では out が空になること）を
確認済み。実例は `harvest-from-projects.sh` の `cmd_scan`。この決定に伴う
`shell-script-style.md`「エラー方針」「テスト」節の訂正内容は同ファイルが正。

既存の `if result="$(risky_func)"` パターン（`session-start.sh` の `build_context` 等）は
「関数の最終コマンドの失敗」は検知できるため即時の実害はないが、複数コマンドから成る関数の
**途中失敗**は検知できない。横断的な実装見直しは規模が読めないため本issueのスコープ外とし、
必要になった時点で別 issue へ切り出す。

## 却下案

- **`shopt -s inherit_errexit` を全スクリプトで常時オンにする案**: コマンド置換側（機構2）の
  直接の対処で、立てると `out="$(f)"` が fail-fast することは実測で確認済み。却下理由は
  (1) **bash 4.4 未満では使えない**（この機構は git bash 配布先で bash の版を制御できない
  前提。`shell-script-style.md`「hookの前置フィルタ」が `${var,,}` を却下したのと同根）、
  (2) スクリプト全体へ効く宣言のため、既存コードの「継承しない」前提の箇所（`$(cmd)` の
  失敗を無視して続行する意図的な書き方）を一括で挙動変更してしまう副作用の広さ、
  (3) サブシェル側の条件文脈問題（機構1）には効かず、単独では解決にならない。
- **`set -E` ＋ `trap ERR` 案**: ERR トラップの発火条件も条件文脈で抑止されるため機構1を
  解決せず、トラップの継承規則（サブシェル・関数への伝播が `-E` の有無で変わる）が
  さらに難解になりデバッグが困難。
- **各コマンドの終了コードを1つずつ `|| return 1` で検査する案**: 漏れが出やすく、
  コマンドを追加するたびに検査を書く負担が残る。採用形なら関数全体が既定で fail-fast になる。
