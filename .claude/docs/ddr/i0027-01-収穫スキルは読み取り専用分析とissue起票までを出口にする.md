# i0027-01. 収穫スキルは読み取り専用分析とissue起票までを出口にする

## 背景

issue #27。`apply-mr-workflow-to-project` スキルで配布したAIアセット（`.claude/` 一式等）が
配布先プロジェクトで改善されたとき、その差分を本家へ還流する仕組みが無かった。配布は
issue #26 で manifest 方式（配布先へ `.claude/.asset-manifest.json` を残す）になっており、
収穫はその最初の読み手になる。

## 決定

1. **出口は issue 起票（＋任意で個別作業計画の草案）までとする。** スキルは差分の分析と
   候補の提示だけを行い、本家の正史（`.claude/rules/` `.claude/skills/` `.claude/docs/`）は
   一切変更しない。取り込みの実装は、起票した issue を起点とする通常の issue-mr-flow が担う。
2. **分析は読み取り専用とする。** 本家・配布先のどちらのワークツリーも変更しない
   （書き込みは一時領域のみ。git は読み取り専用サブコマンドに限定）。
3. **added 判定の除外の正は、配布先の dist-layers.json（`del(.upstream)` 済み）1つだけとする。**
4. **merge 層・seed 層・`.claude/dist-layers.json` は 3-way の対象外とし、層を判定できない
   場合はフェイルクローズ（実行せずエラー終了）とする。**
5. **本家でも削除済みのファイルは `removedUpstream` という別 status にし、収穫候補に混ぜない。**

仕様の詳細は [spec/harvest-from-projects.md](../spec/harvest-from-projects.md) が正。

## 理由

- 出口を issue 起票までにするのは、**どの改善をいつ取り込むかの判断を人間が握る**ため
  （issue 起票が着手指示ではないという issue #39 の原則と同根）。取り込み自体を
  issue-mr-flow に載せることで、計画・レビュー往復・spec/DDR 反映という通常の品質ゲートを
  収穫にもそのまま適用できる。
- 読み取り専用にするのは、分析の実行を「いつ実行しても安全」にするため。配布先は他者の
  作業ツリーでもあり、分析のついでに整理（`.bak` の削除等）まで行うと、実行の敷居が
  承認事項になってしまう。
- 除外の正を dist-layers.json 1つにするのは、**正が2つあると食い違ったときにどちらを
  信じるか決められない**ため（下記の却下案参照）。

## 却下案

- **本家の正史を自動で書き換える案／PR を自動作成する案**: 収穫のたびに本家の変更が
  無人で進む形になり、着手判断を人間が握る原則と衝突する。分析の誤り（プロジェクト固有語の
  混入・衝突の見落とし）がそのまま正史へ入るリスクもある。
- **added 判定へ `git check-ignore` を併用する案**: dist-layers.json の gitignorePattern と
  配布先の実際の `.gitignore` は独立に編集されうるため、併用すると「除外の正が2つ」になり、
  食い違ったときの優先順位という新しい決めごとが増える。自前の pathspec/gitignorePattern
  照合（サブセット実装）1本に絞った。
- **層を判定できない場合に 3-way をスキップして正常終了する案**: 「exit 0=そのまま
  取り込める」という誤読を招く。判定不能はエラーとして止め、判断材料が無いことを明示する
  （フェイルクローズ）。
- **`removedUpstream` を deleted に混ぜる案**: 配布元が削除案内したファイルを配布先が手で
  消した跡は「配布先の改善」ではなく、候補に混ぜると収穫の判断を汚す。status 値ごと分けた。
