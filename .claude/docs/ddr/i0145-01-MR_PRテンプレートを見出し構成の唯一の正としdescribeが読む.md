# i0145-01. MR/PRテンプレートを見出し構成の唯一の正としdescribeが読む

## 背景

issue #145 は、MR/PRのdescriptionを「レビュー時だけの説明」から「**後から見返して何を・なぜ・
どうやったかを一望できるアーカイブ**」へ作り替えるものである。`wip/plans/` `wip/worklogs/`
`wip/reports/` は flow-id 5-5 で削除され、squash mergeによりdescription自身もmainには残らない。
**spec/DDRへ昇格しなかった経緯・却下案・検証結果の唯一の恒久的な置き場がPR/MRのページである**、
というのがこの変更の前提にある認識である。

過去64件のPRを集計したところ、当時のテンプレート（`Closes #N` / `## Plan` / `## 実装状況` の
3点）を忠実に使っていたのは28%にとどまっていた（**出所は issue #145 の本文に載っていた集計であり、
本PRでは数え直していない**。母数64件は起票時点のもの）。残りは独自の見出しを立てており、そこで自然に
書かれていた見出し（変更内容・検証・概要・受け入れ条件との対応・設計判断…）を**当時の
テンプレートは1つも含んでいなかった**。

見出しを増やすにあたり、**同じ見出し構成が2箇所に書かれている**という構造上の問題に突き当たった。

| 書かれていた場所 | 役割 |
|---|---|
| `.github/pull_request_template.md` / `.gitlab/merge_request_templates/Default.md` | GitHub/GitLabがPR作成画面で読む実体 |
| `issue-mr-flow` の `describe` 節（issue #160 以降は `references/review-loop.md`） | AIエージェントがdescriptionを組み立てるときの雛形 |

当時のテンプレートの先頭コメントは「**`references/review-loop.md` の `describe` 節が正**」と
明記していた（このブランチの分岐点 `d31dfd8` の実物。issue #160 で `SKILL.md` が `references/` へ
分割される前は `SKILL.md` を指しており、分割時にこの参照も更新されていた）。つまり実体のほうが
写しであり、見出しを1つ増やすには2箇所を同時に直す必要があった。

## 決定

**この方向（案B）は人間の承認を得ている**（2026-08-23。issue #145 のフェーズ4で確認）。

1. **`.github/pull_request_template.md` を見出し構成の唯一の正とする。** `describe` はこの
   ファイルを読んで見出しを決める（案B）。
2. **`references/review-loop.md` の `describe` 節から、見出しの記述そのものを削除する。**
   節はテンプレートを読む手順だけを持つ。
3. **GitLab版は「複製」と定義する。** 先頭のHTMLコメントだけを固有にし、それ以降の本文は
   GitHub版と完全に一致させる。生成は `awk` で機械的に行い、手で写さない。
4. **`.github` / `.gitlab` の配布層は `core` のまま変えない。**
5. 全10節に「何を書くか」「**計画段階では**何を書くか」の記入ガイドをHTMLコメントで置く。
   `特になし`（検討した結果書くことが無かった）と `未実施`（まだその段階に達していない）の
   書き分け規約は、`## 概要` の記入ガイドへ**1回だけ**置く。
6. **節ごと削除してよいのは `## 備考` のみ**とする。

## 理由

### なぜテンプレートファイルを正にするのか

テンプレートファイルは**GitHub/GitLabが直接読む実体**である。人間がPR作成画面を開いたときに
表示されるのはこのファイルであり、`describe` 節はそれを模した写しにすぎない。**実体と写しが
あるなら、実体を正にするのが自然**である。

一本化すると、`describe` 節から見出しの記述が消える。**二重管理は「ずれを検知する」のではなく
「ずれようがない」形で消える**——正が1つしかなければ、そもそも比べる相手がいない。

### なぜGitLab版だけは複製が残るのか

**GitLabにGitHub版を読ませることはできない。** GitLabはテンプレートを
`.gitlab/merge_request_templates/` 配下から読む仕様で、他のパスを指す設定を持たない。
プラットフォームの仕様上、2ファイルが要る。

手で写すと必ずずれるので、**先頭のHTMLコメントを除いた全文差分が空**という不変条件を
`test_install_to_project.sh` の検査 (b) で固定した。生成も `awk` で機械的に行う。

```bash
tmp="$(mktemp -d)"
# GitLab版の先頭コメントだけを取り出す
awk 'NR==1 && /^[[:space:]]*<!--/ { lead=1 } lead { print; if (/-->/) { exit } }' \
  .gitlab/merge_request_templates/Default.md > "$tmp/gl-lead.md"
# GitHub版から先頭コメントを除いた本文を取り出す
awk 'NR==1 && /^[[:space:]]*<!--/ { lead = 1 }
     lead { if (/-->/) lead = 0; next }
     { print }' .github/pull_request_template.md > "$tmp/gh-body.md"
cat "$tmp/gl-lead.md" "$tmp/gh-body.md" > .gitlab/merge_request_templates/Default.md
```

### なぜ配布層を `core` のまま変えなかったのか

「配布先が独自の見出しを増やしたい」という要求は想定できる。`core`（再適用のたびに上流の内容で
上書きされる）から `seed`（初回のみ配り、以降は配布先が所有する）へ変えれば、増やした見出しは
残る。

**だが `seed` にすると、上流のテンプレート改善が配布先へ二度と届かなくなる。** issue #145 自身が
「テンプレートが実態に合っていない」ことへの対処であり、同じことが将来また起きたときに配れない
のは損失が大きい。改変は失われるのではなく `.bak` へ退避され、再適用時に一覧で通知される
（`.claude/docs/spec/asset-distribution.md`）。

代わりに、**配布元と配布先で扱いが違うこと**をテンプレートの先頭コメントへ明記した。

| | 見出しを増やしたとき |
|---|---|
| **配布元**（このリポジトリ） | `describe` がこのファイルを読む以上、増やした見出しは消えない |
| **配布先** | `core` 層として再適用のたびに上書きされる。改変は `.bak` へ退避され一覧で通知される |

### なぜ `## 備考` だけを削除可にしたのか

「該当が無ければ `特になし` と書き残す」という設計にした。節ごと消してしまうと、**「検討した
結果、書くことが無かった」のか「書き忘れた」のかを後から区別できない**。アーカイブとして
読み返すことが目的である以上、この区別は失えない。

`## 備考` は「上のどの節にも入らないもの」の受け皿である。受け皿が空であることに情報は無いので、
ここだけは節ごと削除してよい。

### なぜ書き分け規約を1箇所にしか置かないのか

`特になし` と `未実施` の書き分けは10節すべてに効く。10節すべての記入ガイドへ書くと、**それ自体が
二重管理になる**（本DDRが解消しようとしている問題と同型）。`## 概要` は最初に読まれる節なので、
そこへ1回だけ置いた。

## 却下案

### 案A: `describe` 節を正とし、テンプレートファイルをそこから生成する

**却下。** テンプレートファイルはGitHub/GitLabが直接読む実体である。これを生成物にすると、
**生成し忘れたときに人間がPR作成画面で見る本文が古くなる**。生成物であることは画面上のどこにも
現れないため、誰も気づかない。

`.gemini/` が `.claude/` からの変換生成物であるのと同じ形に見えるが、あちらは**AIしか読まない**
ため生成漏れに気づく機会があとから何度もある。テンプレートは人間の入力欄に直結する。

### 案C: 両方に書き、テストで一致を検査する

**却下。** 二重管理そのものは残る。検査は「ずれたら気づく」だけであって「ずれない」保証ではなく、
見出しを1つ増やすたびに2箇所を直す手間も変わらない。

さらに、この案には**検査自体が穴を持つ**という問題がある。issue #145 の作業中、敵対的レビューが
「両テンプレートから記入ガイドを**同時に**削除すると全検査を素通りする」ことを実測で示した。
テンプレートの先頭コメント自身が「GitHub版を直して本文をGitLab版へ複製する」という**両側を
同時に変える運用**を規定している以上、これは机上の話ではない。

**「2つを比べる検査」は、2つが同じ向きにずれたときに無力である。** この性質は案Cの本質的な限界で
あり、検査を足して塞ぐたびに同型の穴が別の場所に開く。正を1つにすれば、比べる必要そのものが消える。

## 検査 (a2) が生まれた経緯

上記の実測を受けて、`test_install_to_project.sh` へ**テンプレート2本を比べるのではなく、
片方の内容そのものを数える**検査 (a2) を追加した（記入ガイドが10個あること・書き分け定義が
あること・`**計画段階では**` が10個あること）。

**「2本を比べる検査」と「1本の中身を数える検査」は別物である**というのがここでの学びで、
検査を設計するときは「両側が同時に壊れたらどうなるか」を必ず問う。

## 影響範囲

- `.github/pull_request_template.md`（全面書き換え。10節構成）
- `.gitlab/merge_request_templates/Default.md`（同上。先頭コメントのみ固有）
- `.claude/skills/issue-mr-flow/references/review-loop.md`（`describe` 節から見出しの記述を削除）
- `.claude/scripts/test/test_install_to_project.sh`（検査を6種類へ: (a)(a2)(b)(b2)(c)(c2)）
- `.claude/docs/spec/distribution-assets.md` / `index.md` / `.claude/rules/directory-structure.md` /
  `.claude/skills/apply-mr-workflow-to-project/assets/index.md.template`（「正の向き」の記述を反転）
