# i0140-01. mark-skipはループ範囲の一部指定を書き換え後の状態で拒否する

issue #140。`.claude/scripts/src/update-handoff-progress.sh` の `mark-skip` が、ループ範囲の一部
だけを `[-]` にした表を終了コード0で書き戻していた問題への対応。

## 背景

`.claude/rules/docs-workflow.md` は「同じループ範囲内のステップは常に同じ記号を持つ」と定めて
いる。`mark-done`/`add-round` は対象をループ範囲全体へ広げてこれを守るが、`mark-skip` は広げず、
渡されたflow-idだけを書き換えていた。

issue #109 の作業中に `mark-skip 2-1 2-2 2-3 2-5 2-6 2-10` を実行したところ、2-4・2-7〜2-9 が
`[]` のまま残り、ルールに反する表が**終了コード0で**書き戻された。この状態は、その後同じ範囲へ
`mark-done`/`add-round` を実行して初めて「末尾が `[]` でない」エラーとして表面化する。

つまり既存の強制は、**不整合を作る操作ではなく、その後の正当な操作のほうを拒否する**形で働いて
いた。issue #66 で直した `set-header` の「無言の失敗」と症状は同系統だが、欠陥の性質は違う
（#66は「何も書き換えていないのに成功する」、#140は「指示どおり書き換えたが結果がルールに反する」）。

## 決定1: `mark-skip` はループ範囲へ伝播させず、不整合になる指定をその場で拒否する

issue本文の案B（入口で止める）を採用した。`mark-skip` が「列挙したものだけを書き換える」という
既存インターフェースの意味を変えずに、不整合が生まれる時点で止められるためである。

- 拒否したときは**1件も書き戻さない**。これは issue #66 で仕様書へ1本立てた「書き換えを求められた
  対象が見つからなければ書き戻さずに非0で終了する」というスクリプト全体の方針と、結論としては
  揃う（検査しているものは違う。下記「#66との関係」）。
- エラーメッセージには、揃わない範囲ごとの記号の内訳と**指定し直すコマンド例**
  （`mark-skip 2-6 2-7 2-8 2-9`）を出す。呼び出し側が範囲テーブルを知らなくても、そのまま
  貼り直せば回復できる。
- `mark-done`/`add-round` 側の「末尾が `[]` でない」エラーは残す。`HANDOFF.md` は人間も直接
  手編集するファイルであり、`mark-skip` を通らずに作られた不整合はそちらでしか止まらない。

## 決定2: 判定は引数の網羅性ではなく「書き換え後のファイルの状態」で行う

「指定されたflow-idがループ範囲を網羅しているか」ではなく、**書き換えた結果その範囲の記号が
揃っているか**を検査する。守りたいルールが引数の形ではなく**ファイルの性質**だからである。

この違いは3つの場面で結果を変える。

| 場面 | 引数の網羅性で判定 | 書き換え後の状態で判定（採用） |
|---|---|---|
| 範囲内の他のflow-id行が表に存在しない | 拒否（渡しようのない行を要求する） | **通る**（存在しない行は検査に加えない） |
| 範囲内の一部が既に `[-]` のファイルへ、残りだけを指定 | 拒否（網羅していない） | **通る**（結果が揃う） |
| 範囲を丸ごと指定 | 通る | 通る |

1つ目が決め手である。表がループ範囲の全行を持たない場合、存在しないflow-idを渡すと上流の件数検査
（「指定flow-idの一部が見つかりませんでした」）で弾かれる。**網羅を要求すると、その範囲へ二度と
`mark-skip` できない**という詰みが生まれる（実際、単体テストの簡略フィクスチャがこの形をしている）。

2つ目は、手作業や旧版の `mark-skip` で作られてしまった不整合を直す場面である。引数の網羅性で
判定しても、既に `[-]` の行まで含めて範囲全体を渡し直せば通るので実害は小さい。それでも、
**通る／通らないが「引数に何を並べたか」ではなく「ファイルがルールを満たすか」で決まる**ほうが、
守っている性質と検査が一致していて説明しやすい。

検査対象は**指定flow-idが属する範囲だけ**に限る。全範囲を検査すると、今回の操作と無関係な範囲に
元から残っていた不整合まで拒否してしまい、やはり直す手段が無くなる。

## 却下した案

### 1. `mark-skip` も `mark-done` と同様にループ範囲へ伝播させる（issue本文の案A）

実装は最も小さく（`find_loop_range_to_reply` で `targets` を広げるだけ）、呼び出し側は範囲を
意識しなくてよくなる。しかし却下した。

- **`mark-skip` は複数flow-idを受け取る唯一のサブコマンドであり、「列挙したものだけを書き換える」
  という意味を持つ。** 伝播させると、`mark-skip 2-6` が 2-7〜2-9 まで黙って `[-]` にする。
  `mark-done`（対象は常に1つ）と違い、**指定していないflow-idが混ざる**ため、どこまでが指示で
  どこからが自動かが引数から読めなくなる。
- issue #66 以降このスクリプトが立てている方針は「呼び出し側の意図とファイルの状態を食い違わせ
  ない」ことである。**足りない指定を黙って補うのは、その食い違いを逆向きに作る。**
  「フェーズ2を丸ごと省略する」という意図なら、範囲内の全flow-idを書き下すコストは1回きりで
  済み、エラーメッセージがその文字列をそのまま提示する。
- 伝播させると、`[-]` にしたくない行まで巻き込む操作を**止める手段が無くなる**。案Bなら、
  意図と違えばエラーで気づける。

### 2. 挙動は現状維持とし、呼び出し側の責務としてルールへ明記する（issue本文の案C）

`.claude/rules/docs-workflow.md` へ「範囲内の全flow-idを渡すこと」と書けば、コードは1行も
変わらない。しかし却下した。

- **本issueが問題にしているのは、ルールが書かれていないことではなく、破ったときに何も起きない
  ことである。** 「ループ範囲内の一部だけを `[-]` にする使い方は想定しない」は、issue #140 以前
  から `docs-workflow.md` に明記されていた。それでも issue #109 で実際に踏んでいる。
- 文書だけの対策は、`.claude/docs/spec/update-handoff-progress.md` が「意図した挙動である」と
  書いていたのと同じ状態に留まる（読み手が仕様書を先に読んでいることを前提にする）。
- ただし**ルールへの明記自体は有用**なので、案Bとあわせて `docs-workflow.md`・
  `issue-mr-flow/SKILL.md` にも「範囲を丸ごと省略するなら全flow-idを渡す（渡さなければエラーに
  なる）」を書いた。案Cを捨てたのではなく、案Bの補助として取り込んでいる。

### 3. ループ範囲を丸ごと `[-]` にしたとき、ヘッダの `- 現在のループ:` 行も追従させる

範囲を丸ごとスキップした後、ヘッダに直前の周回数（例: `2-6〜2-9 の2周目（進行中）`）が残りうる。
しかし `mark-skip` をヘッダ追従の対象にしない判断は issue #58 のもので、**スキップした範囲に
周回数という概念が当てはまらない**という理由も変わっていない。「なし」を書くべきか、直前の周回数を
残すべきかはスキップの文脈次第であり、機械が一意に決められない。`set-header --loop 'なし'` で
明示的に更新する運用を仕様書へ書くに留めた。

## #66（`set-header` の無言の失敗）との関係

**個別に直し、1つの方針へまとめようとはしなかった。** issue #66 の対応時にこの切り分けを検討し、
別issueのまま残すと結論している（`i0066-01` 却下3）。本issueの受け入れ条件が求める「結論の記録」は
その判断のことであり、本issueでも覆さない。

- 症状（呼び出しは成功したように見えるが、ファイルは期待した状態になっていない）は同じだが、
  **検査するものが違う**。#66 は「書き換え対象の行が見つかったか」、#140 は「書き換えた結果が
  ルールを満たすか」であり、共通の関数へ畳めるものではない。
- 結論（**書き戻さずに非0で終了する**）だけが揃う。仕様書では #66 が立てた
  「書き換え対象が見つからないときの扱い（スクリプト全体の方針）」節から本issueの節へ相互参照を
  張り、「結論は同じ・検査対象は別」と読めるようにした。
- 残る同系統の候補として、`follow_loop_header_in_lines` の警告止まり（ヘッダ行を書けなくても
  `mark-done`/`add-round` は成功する）がある。これは #58 で「進捗表の更新だけでも書き戻せたほうが
  状態として正しい」と意図して決めた挙動であり、本issueでは変更していない。
