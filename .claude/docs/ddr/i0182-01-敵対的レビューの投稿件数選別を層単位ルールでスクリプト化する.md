# i0182-01. 敵対的レビューの投稿件数選別を層単位ルールでスクリプト化する

## 背景

issue #182。`adversarial-review` スキル手順6は、findings を確度×重大度の表で「投稿」「報告」へ
1次振り分けしたあと、**「1回あたりの投稿上限は10件。超える場合は重大度の高い順に10件へ絞り、
残りは報告へ回す」**とだけ規定していた（issue #77）。

この規定には2つの問題があった。

1. **同一重大度内のタイブレークが未定義。** 例えば major が13件あり、上限10件のうち5件しか
   major の枠が残っていない場合、どの5件を選ぶかは決められておらず、実行するAIエージェントの
   その場の判断に委ねられていた。同じfindingsを渡しても、実行のたびに異なる投稿集合になりうる。
2. **選別が機械化されていない。** スキルを実行するAIが findings JSON を目視して手作業で絞る
   設計であり、`.claude/rules/shell-script-style.md` 等が求める「決定的な処理は関数・スクリプトへ
   切り出す」という他の機構（`adversarial-review-count.sh` の実施回数、`collect-review-points.sh` の
   観点表マージ等）との一貫性も欠いていた。

加えて、確度（confidence）は1次振り分けの表にのみ使われ、件数を絞り込む際の順序付けには
使われていなかった。高確度の指摘が低確度の指摘より先に落ちる、といった逆転が起こりうる設計だった。

## 決定

1. **投稿件数の選別を、新設スクリプト `.claude/scripts/src/select-adversarial-findings.sh` による
   決定的な処理へ置き換える。** 確度×重大度による1次振り分け（投稿候補／報告）はスキルの手順に
   残し、変更しない。1次振り分けを通過した「投稿候補」だけを本スクリプトへ渡す。

2. **選別規則は「層単位」で定める。**
   - **blocker は全件投稿する。** 件数上限の対象外とし、blocker が単独で20件を超える場合も
     全件投稿して、下位層（major・minor）は追加しない。**blocker を無制限にする**のは、
     blocker は「マージすると壊れる」水準の指摘であり、件数で機械的に間引いてよい対象ではない
     ため。
   - **major → minor の順に、層単位で追加する。** 層の途中では切らない（例えば major を
     一部だけ投稿し残りを報告に回す、ということはしない）。累計投稿数が**10件**（層追加の
     しきい値）に達した時点で、それより下の層は一切追加しない。
   - **絶対上限（ハードシーリング）を20件とする。** 層を丸ごと追加すると20件を超える場合に
     限り、その層内で**確度の降順（high→medium→low）→パスの昇順→行番号の昇順**という
     決定的な順序に並べ、20件に達するまでで切る。

3. **層追加のしきい値（10）とハードシーリング（20）は固定値とし、緩める口を用意しない。**
   `adversarial-review-count.sh` の実施回数上限（3回／フェーズ）と同じ方針である。

4. **スクリプトはfindings JSONをファイル経由で受け取り、jqの起動を1回に集約する。**
   層ごとの処理は `reduce` で1つのjqプログラムにまとめて書き、`{"posted":{...},"reported":{...}}`
   を出力する。`posted.findings` はそのまま `add_mr_inline_comments` へ渡せる形にする。

5. **確度×重大度による1次振り分け自体は変更しない。** 「技術的に投稿可能か」ではなく「人間に
   見せる価値があるか」という運用判断であり、スキルの手順（調整しやすい場所）に置くという
   issue #77 時点の判断を維持する。件数選別だけをスクリプト化するのは、そちらが「同じ入力なら
   常に同じ出力になるべき」という決定性の要件を持つためである。

仕様の詳細は [.claude/docs/spec/adversarial-review.md](../spec/adversarial-review.md)
「投稿件数の選別」節を正とする。

## 却下した案

- **1回あたりの投稿上限を維持したまま、タイブレーク規則だけを追記する**（例:
  「同一重大度内は確度降順→パス昇順→行番号昇順」）。実装コストは最も低い。しかし
  「どれを選ぶか」の規則をスキル本文の自然文だけで規定すると、AIエージェントが規則を
  正確に再現できているかを検証する手段が無い（単体テストが書けない）。issue #182 の受け入れ
  条件が「境界ケースを含む単体テスト」を明示的に求めていることとも整合しない。

- **投稿上限を10件に固定したまま、層単位の考え方だけを導入する**（例: 「10件のうち何件かは
  blockerに優先的に割り当てる」）。blocker と major/minor を同じ予算プールで奪い合う設計に
  なり、「blocker は絶対に見逃されない」という保証が弱くなる。blocker は severityの定義上
  「マージすると壊れる」指摘であり、件数の都合で investigatorの目に触れないことがあってはならない
  ため、**blocker だけは予算の外に置く**設計を採った。

- **層単位ルールをスキルの手順（自然文）に留め、スクリプト化しない。** `adversarial-review/SKILL.md`
  の変更だけで完結し、新規スクリプト・テストが不要になる。しかし本issueの動機そのものが
  「AIエージェントの裁量からスクリプトによる決定的な選別へ置き換える」ことであり、自然文の
  ままでは同じ問題（実行のたびに解釈がぶれる）が形を変えて残る。

- **確度×重大度の1次振り分け表も本スクリプトへ統合する。** 選別ロジックを1箇所に集約でき、
  スキル側の手順が短くなる。しかし1次振り分けの表は「人間に見せる価値があるか」という運用判断
  であり、運用しながら調整する対象として issue #77 時点でスキルの手順に意図的に置かれている
  （`.claude/docs/ddr/i0077-01` は対象外だが、`.claude/docs/spec/adversarial-review.md` の
  旧「投稿／報告の振り分け」節にこの理由が明記されていた）。決定性が要る件数選別と、運用感で
  調整する1次振り分けは性質が異なるため、両方を1つのスクリプトへ混ぜず分離を維持した。

- **層追加のしきい値・ハードシーリングを環境変数や引数で調整可能にする。** 運用しながら
  チューニングできる柔軟性を持たせられる。しかし `adversarial-review-count.sh` の実施回数上限が
  「緩められる上限は上限ではない」という理由で調整口を持たないのと同じ理由で、本スクリプトの
  2つの定数も緩める口を用意しないことにした。値を変えたくなった場合は、コード（定数）を直接
  変更しコミットレビューを経る運用とする。
