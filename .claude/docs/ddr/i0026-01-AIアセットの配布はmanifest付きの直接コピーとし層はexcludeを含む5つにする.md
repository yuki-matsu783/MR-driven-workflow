# i0026-01. AIアセットの配布はmanifest付きの直接コピーとし層は `exclude` を含む5つにする

issue #26。配布機構の仕様は
[.claude/docs/spec/asset-distribution.md](../spec/asset-distribution.md)、
配る資産の側の仕様は
[.claude/docs/spec/distribution-assets.md](../spec/distribution-assets.md)。

**このDDRは3つの決定を節に分けて持つ。** 当初は3件のDDRへ分ける案だったが、
「細かいので1つにする」という判断を受けて1件へ束ねた（issue #26 の flow-id 4-4）。

## a. 配布方式としてmanifest付きの直接コピーを選ぶ

**決定**: 本家の実状態を層分け定義（`.claude/dist-layers.json`）に従って配布先へ直接コピーし、
何をどの版から配ったかを配布先の `.claude/.asset-manifest.json` へ記録する。

### 解こうとしている問題

配布は一方通行ではない。**配布先で育ったルール・スキルを本家へ持ち帰る（逆輸入する）**ことが
この機構の前提にある。そのためには、配布先で「どこまでが上流から来たもので、どこからが自分で
書いたものか」が判別できなければならない。旧方式（`sync-assets.sh` → `install-to-project.sh`）は
この判別を持たず、「本家と1バイトでも違えば改変」としか言えなかった。

### 却下案

| 案 | 却下理由 |
|---|---|
| **git subtree / submodule** | 上流を取り込む仕組みとしては正攻法で、履歴も残る。しかし**配布先が自分のリポジトリの履歴へ上流のコミットを混ぜること**を強制する。この機構の配布先は「ワークフローの雛形を借りたい既存プロジェクト」であり、履歴の混入は受け入れ難い。さらに `seed`（配布先が所有し、上流が二度と触らない）という概念を表現できない——subtreeは全ファイルを一様に扱う |
| **Claude Code の plugin として配布する** | 公式の配布経路に乗れる。しかし**配れるのは `.claude/` の中身だけ**で、`AGENTS.md` / `.mrworkflow.json` / `.gitattributes` / issueテンプレートといったリポジトリルートの資産が配れない。この機構はルート直下の資産と `.claude/` が噛み合って初めて動くため、片方だけを配ると壊れた状態が配布先に残る。加えて `merge` 層（`.gitignore` への行追記・`settings.json` のキー単位マージ）を表現する手段が無い |
| **差分をAIが都度判断して適用する** | 「上流が変わった箇所だけを、配布先の事情を汲んで取り込む」という理想形。しかし**再現性が無い**。同じ入力に対して毎回同じ結果になる保証が無く、配布のたびに配布先の内容が微妙に変わりうる。配布は人間が結果を検証しない場面（`--dry-run` を見ずに実行する等）で走るため、決定的でない仕組みを土台に置けない。**AIが判断すべきなのは層分けの定義を書くときであって、適用のときではない** |
| **旧方式を維持し、欠陥だけを個別に直す** | 変更が小さく済む。しかし欠陥の根が「配る内容の定義がスクリプトの中にある（本家の実状態の写しを持つ）」ことにあり、個別修正では**同じ形の漏れが再発する**。実際、`REVIEW-POINTS.md` 4件中1件しか配られていない・`worklog/TEMPLATE.md` が配られていない、という漏れは、どちらも「スクリプトへ書き足し忘れた」ことが原因だった |

### 採用案が満たすもの

- **配る内容の定義が本家の実状態そのものである。** pathspec をgitに評価させるので、写しが
  存在しない。本家へファイルを足したら、網羅性チェックが「どの層か決めろ」と言ってくる。
- **上流の更新と配布先の改変を区別できる。** manifest に「前回適用したときの sha256」を
  残しているため、配布先が触っていないファイルは黙って上書きし、触ったものだけ `.bak` を残す。
- **配布先の履歴を汚さない。** ただのファイルコピーなので、配布先は自分の粒度でコミットできる。

## b. 層は4つではなく、`exclude` を加えた5つにする

**決定**: 「配らない」を `exclude` 層として**明示指定**させる。どのエントリにも一致しないパスは
「配らない」ではなく**未分類（エラー）**として扱う。

**却下案: 暗黙の既定値（未指定＝配らない）とする。** 定義ファイルが短くなり、`README.md` の
ような明らかに本家固有のファイルをいちいち書かずに済む。

**却下理由: 網羅性チェックが常に通ってしまう。** 未指定を「配らない」と読むなら、定義が空でも
すべてのファイルが正しく分類されていることになる。配り忘れは**何も書かなかったとき**に起きるの
だから、それを検出できない仕組みには意味が無い。実際、旧方式の漏れ（`REVIEW-POINTS.md`・
`worklog/TEMPLATE.md`）はどちらも「書き忘れ」であり、暗黙の既定値のもとでは永久に検出されない。

`exclude` を明示必須にすると、本家へファイルを足した人に「これは配るのか」を1回だけ考えさせる
ことになる。**その1回のコストが、この層の価値そのものである。**

## c. 旧形式のまま残った `seed` は `core` へ昇格させず、`requiredLine` で一覧提示にとどめる

**決定**: `AGENTS.md` は `seed`（配布先が所有）のまま置き、`requiredLine` に
`@./.claude/rules/agent-common.md` を指定して、その行を含まない配布先へ**一覧で知らせる**。
書き換えは行わない。

### 背景

issue #26 以前は、本家の `AGENTS.md` を全文配っていた。共通ルール9項目がその中にあったためで
ある。issue #26 でこの9項目を `.claude/rules/agent-common.md`（`core`）へ切り出し、
`AGENTS.md` はそれを `@import` するだけにした。

しかし**旧方式で配られた配布先の `AGENTS.md` には、9項目が全文コピーとして残っている**。
`seed` は触らない層なので、放置すると共通ルールが二重化し、以後 `agent-common.md` だけが
更新されて恒久的に食い違う。

### 却下案

| 案 | 却下理由 |
|---|---|
| **`AGENTS.md` を `core` へ昇格させ、常に上書きする** | 食い違いは確実に消える。しかし `AGENTS.md` は共通ルールへのポインタだけでなく**「プロジェクト概要」**（このリポジトリが何を実装するか）を持つ。これは配布先が書くものであり、`core` にすると**配布先が書いた概要が毎回消える**。`.bak` は残るが、再適用のたびに書き戻す運用は現実的でない |
| **`AGENTS.md` を自動で書き換える**（共通ルールの節を削り `@import` 行を足す） | 一見よさそうだが、**配布先がその節をどう編集したかを機械的に判別できない**。9項目のうち一部だけを配布先の事情に合わせて書き換えている場合、その変更を無言で捨てる |
| **何もしない（`requiredLine` を持たない）** | 二重化に気づく手掛かりが配布先に残らない。**気づかないまま食い違いが広がる**のが最悪の結末である |

### 採用案の性質

**「直せないが、気づかせることはできる」という中間を取っている。** 配布先の所有物を書き換えない
という `seed` の原則は崩さず、移行が必要なことだけを一覧で伝える。何をどう直すかは配布先が決める。

## 束ねたことの帰結

**3つの決定を1件のDDRへ束ねたため、後から一部だけが無効になっても `status: superseded` を
付けられない**（frontmatterの `status` はDDR単位でしか表せない）。その場合は、
**後続のDDRの本文で「`i0026-01` の a のみを置き換える」と明示する**こと。
