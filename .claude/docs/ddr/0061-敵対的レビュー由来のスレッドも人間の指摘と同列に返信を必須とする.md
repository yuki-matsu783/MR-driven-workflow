# 0061. 敵対的レビュー由来のスレッドも人間の指摘と同列に返信を必須とする

## 背景

敵対的レビュー（`.claude/skills/adversarial-review/SKILL.md`）がMRへ投稿した指摘が、対応後も返信
のないまま残っていた。実例として、PR #107 はインラインコメント11件すべてが返信0件・未解決のまま
であり、マージ済みのPR #104 も8件が返信ゼロだった。返信が付いていたPR #101 は、人間がスレッドへ
書き込んだスレッドだけである。

返信が無いと、人間のレビュアーから見て「未対応」と区別が付かない。指摘を直したこと自体はコードの
差分に現れるが、「どの指摘をどう扱ったか」はMRに残らない。

**仕組みの側には欠けが無かった。** `get_mr_unresolved_comments` は敵対的レビューのスレッドも
`unresolved` として返しており（`.claude/docs/spec/adversarial-review.md`「投稿されたスレッドの
取得」が「敵対的レビューのために新しい取得経路を作る必要はない」と明言している）、flow-id
2-4/2-9/3-4/3-9/4-4/4-9 の `comments` / `reply` ループは元からこれらのスレッドを対象に含んでいた。
欠けていたのは「AI自身が投稿した指摘も返信の対象である」というルールの明文化だけである。

実際には、AIが敵対的レビューの直後に自分で指摘を直してしまい、x-4/x-9 では人間のコメントだけを
対象として扱っていたため、**AI単独で対応した場合は構造的に返信されない**状態になっていた。

## 決定

1. **返信の手順を新設せず、既存の `comments` / `reply` ループのルールとして明文化する。**
   `.claude/skills/issue-mr-flow/SKILL.md` の `comments` サブコマンドへ、敵対的レビュー由来の
   スレッド（`Claude Codeより（敵対的レビュー）:` で始まるもの）も人間の指摘と同列のレビュー入力
   として扱う旨を書く。**AI自身が投稿した指摘であることは、返信を省いてよい理由にならない。**
2. **対応しないと判断した指摘にも理由を返信する。返信を省略してよい類型は作らない。**
3. **返信のタイミングは x-4/x-9（人間のレビュー取得と同じ往復）に揃え、敵対的レビューの直後には
   返信しない。** 投稿と返信の間に人間のレビュー（x-3/x-8）を挟むことで、同じスレッドへ人間が
   判断を示す余地を残す。
4. **「レビュー完了合図の確認」節のゲートへ、未返信スレッドの確認を加える。** 従来のゲートは
   `unresolved` が残っていないかだけを見ており、「返信済みか」を見ていなかったため、返信ゼロの
   スレッドを素通りさせていた。
5. **`.claude/skills/adversarial-review/SKILL.md` には返信手順を書かず、担当が `comments` /
   `reply` ループであることを示す参照の1文に留める**（責務の所在を示しつつ、手順の二重管理を
   避けるため）。あわせて「してはいけないこと」へ「投稿した自分の指摘へその場で返信すること」を
   加える（これはタイミングの規定であって返信手順ではない）。
6. **未返信スレッドを機械的に検出する専用の関数・スクリプトは設けない。** 判定条件だけを
   ドキュメントへ明記する（`comments all` の出力で、同じ `threadId=` を持つ `[review ...]` 行が
   1本しか無いスレッド＝返信ゼロ）。
7. **本決定は新規DDRとして残す**（既存DDRへの追記では足りない。下記「却下した案」の(e)）。

## 却下した案

### (a) `adversarial-review` スキル側へ返信手順を持たせる

投稿したスレッドを最もよく知っているのは投稿した本人（スキル）である、という理由で成り立ちうる
案。だが、返信の手順（署名・`add_mr_thread_reply` の呼び出し・返信URLの控え）は `reply`
サブコマンドが既に持っており、同じ手順が2箇所に書かれることになる。片方だけが更新されて食い違う
状態は、このリポジトリが繰り返し避けてきた失敗である（「唯一の実装フロー定義」を
`issue-mr-flow/SKILL.md` に置いている理由と同じ）。**取得経路を共有しているのだから、返信経路も
共有するのが自然**であり、スキル側は参照だけを持つ形にした。

### (b) 敵対的レビューの直後に、その場で返信する

対応と返信の間隔が最短になり、返信漏れが起きにくい。しかし敵対的レビューは commit・push の直後
＝**人間のレビュー（x-3/x-8）の前**に走るため、この案ではAIの指摘・AIの対応・AIの返信がすべて
人間の目に触れる前に閉じてしまう。人間が同じスレッドで「その指摘は違う」「その直し方は困る」と
判断を示す余地が消え、レビューの主体が人間であるという前提（`issue-mr-flow/SKILL.md`「敵対的
レビューの位置づけ」）が崩れる。**返信が早いことより、人間が割り込める順序であることを優先した。**

### (c) AI自身の指摘は返信を免除する（自分で直したのだから自明とする）

返信の手間を減らせるが、**MRを読む人間から見れば、返信ゼロのスレッドが「対応済みで自明」なのか
「見落とし」なのかは区別が付かない**。区別できない以上、免除は「対応漏れを隠せる抜け道」として
だけ働く。本issueが問題にしたPR #107・#104 がまさにこの状態であり、免除を認めることは現状の追認に
なる。

### (d) 「対応した指摘だけ返信し、対応しない指摘は黙って閉じる」類型を作る

対応しないと判断した指摘こそ、**判断の理由がどこにも残らない**（対応した指摘は少なくとも差分に
痕跡が残る）。返信を省略してよい類型を1つでも作ると、「これは省略してよい側だ」という自己判断が
入り込み、(c) と同じ抜け道になる。

### (e) 既存DDRへの追記で足りるとする

`.claude/rules/markdown-frontmatter.md` のとおり、DDRの**本文は一度マージしたら変更しない**（追記
のみ）運用であり、既存DDRへ書き足すこと自体は制度上できなくはない。しかし本決定の主題は「敵対的
レビューの起動ポリシー」（DDR 0045・0055）でも「投稿の形式」（issue #77・#121）でもなく、
**投稿した後の責務がどこにあるか**という別の論点である。既存DDRのどれに書いても、そのDDRの
タイトル・`description` から辿れなくなる（`description` は「そのDDRが何を決めたか」の要約であり、
後から書き換えない）。**検索で辿れることを優先し、新規DDRとして起こした。**

### (f) 未返信スレッドを機械的に検出する関数・スクリプトを追加する

「返信ゼロのスレッドを列挙する」処理自体は、`get_mr_review_threads` が返す正規化JSONに対して
`comments` 配列の長さを見るだけで書ける。それでも追加しなかった理由は次の2点である。

- **CLI経路でしか動かない手段になる。** `Provider.sh` の関数は `require_vcs_cli` を通るため、
  `gh`/`glab` CLIが無い実行環境（Claude Code on the web。`get_vcs_access_mode` が `mcp`）では
  呼べない。ゲートは両方の経路で同じように働く必要があり、片方でしか動かない検出手段は
  「使える環境と使えない環境でルールの強度が変わる」二層構造を作ってしまう。
- **判定条件がそもそも目視で機械的に読める。** `get_mr_unresolved_comments` はスレッド内の全
  コメントを1行ずつ `[review ... threadId=...]` の形で並べるため、**同じ `threadId=` の行が1本しか
  無い＝返信ゼロ**が確定する。数え上げではなく重複の有無の判定であり、`unresolved` の確認と同じ
  1回の `comments all` の出力から読み取れる。新しい外部依存・単体テスト・仕様書を増やしてまで
  自動化する対象ではないと判断した。

将来、返信漏れがこの明文化だけでは止まらないと分かった場合は、CLI経路とMCP経路の両方から使える
形（例: 正規化JSONを標準入力から受け取る純粋なフィルタ）で再検討する。

## 影響

  返信の行を追加）
- `.claude/skills/adversarial-review/SKILL.md`（手順8末尾の参照1文、「してはいけないこと」1項目）
