# i0185-01. コミットメッセージは件名1行必須で本文を任意許容にし件名の判定を2段階にする

## 決定

`.claude/skills/commit/SKILL.md` に `## コミットメッセージの内容規約` を新設し、次を定めた。

| 項目 | 決定 |
|---|---|
| **件名（1行目）** | **必須。1行で書く。**「何を」「どう」を満たす（「なぜ」は対象と手段から自明なら省略可） |
| **本文（2行目以降）** | **任意で許容する。** 件名だけでは要素を満たせない場合に回す |
| **追跡用フッター**（`Refs #NNN` 等） | **許容する。** 人間が書いても同じ形になる情報のため |
| **AI生成物を示すフッター**（`Co-Authored-By: Claude` 等） | **絶対に付けない**（従来どおり） |
| **「どう」の判定** | **2段階**（下記） |

これにより、`commit/SKILL.md` の従来の記述「`<prefix>: <日本語説明>` の**1行のみ** / 本文・
フッター・Co-Authored-By など一切付けない」は**廃止**した。

### 件名の「どう」を2段階で判定する

1. **1段目（機械的）**: 次の6語のいずれかで終わる件名を**候補として拾う**。**合否は決めない。**

   ```
   修正 / 更新 / 反映 / 追加 / 作成 / 記録
   ```

2. **2段目（1問）**: 「**その6語と直前の助詞を取り除いたとき、残るのは変更対象の名前だけか。**」

   | 残るもの | 判定 | 例 |
   |---|---|---|
   | 名前だけ | **不合格** | `docs: HANDOFFを更新` → 「HANDOFF」 |
   | 変更後の状態・採った手段・追加したものの働き | **合格** | `docs: HANDOFFのflow-id 3-6完了とpush回数6を記録` → 「flow-id 3-6完了とpush回数6」 |

## 背景

issue #185 は「1行コミットログが後から見てもあまり参考にならない」ことを問題にしている。
調査（フェーズ2）で次を実測した。

- **`main` の `git log --oneline` に出るのは、個別コミットの件名ではなく PRタイトル**である
  （squash merge のため）。個別の件名は squash 本文の `* 件名` として残り、**恒久的に参照できる**。
- 直近5件のsquashに畳まれた**80件のうち51件（64%）**が「対象＋動詞」で終わり、どう変えたかを
  伝えていなかった。
- **本文を持つコミットは、GitHubのsquash mergeが `* 件名` → 空行 → 本文 の形でそのまま畳む**
  （PR #175 で実測）。フッター（`Refs #NNN`）も落とさない。

つまり本文を書けば、それは `main` に残る。**1行のみという制約は、残せる情報を自分から捨てていた。**

### この前提が成り立つ範囲

**上の「本文は `main` に残る」は無条件の事実ではない。** 実測したのは
**GitHub（PR #175）／squashコミットメッセージ設定が既定（`COMMIT_MESSAGES`）の場合**であり、
次の2つの条件に依存する。

| 条件 | 成り立たなくなる場合 |
|---|---|
| GitHubのリポジトリ設定 | `squash_merge_commit_message` が `PR_BODY` / `BLANK` だと、個別コミットの件名・本文はsquashコミットに入らない。マージ実行者が本文を手で編集することもできる |
| プロバイダ | **GitLabは既定のsquashコミットメッセージがMRタイトル（`%{title}`）** で、個別コミットのメッセージは畳み込まれない |

本機構は `Provider.sh` でGitHub/GitLab両対応として**他プロジェクトへ配布される**ため、
**配布先がGitLabの場合、または上記の設定を変えている場合は、この根拠がそのまま成り立たない。**
その環境では「本文を書く価値」は `main` への残存ではなく、**ブランチ上のコミット履歴
（PRのコミット一覧）を読む人**にとっての価値へ縮む。件名1行必須という決定はどちらでも変わらないが、
本文を推奨する強さは弱まる。

## 却下した案

### 却下案1: 「1行のみ」を維持する

**却下。現行規約は既に破られている。** 直近5件のsquashの内側に、本文を持つエントリが**6件**
（最長19行）、`Refs #NNN` フッターが**6件**、いずれもマージ済みで存在する。守られていない規約を
維持しても実態は変わらない。

### 却下案2: 本文を必須にする

**却下。** 母数の**15%（12件）**は事務的な作業記録（`HANDOFF.md` の進捗更新等）であり、そこまで
本文を強いると書く手間に見合わない。件名だけで「何を・どう」が伝わるなら本文は要らない。

### 却下案3: 6語で終わる件名を一律に不合格とする

**却下。規約自身の模範例4件を不合格にする自己矛盾を起こした**（敵対的レビュー4回目のblocker）。
同じ節が「良い例」「求める形」として示す件名のうち4件が、この6語で終わっていた。
機械的に従えば模範例が全滅し、模範例を真似れば規約違反になる——**どちらへ倒しても矛盾する**ため、
規約を読むAIエージェントは判断できない。

**原因は、機械的に測れること（6語で終わるか）と、合否そのものを同一視したことである。**
「HANDOFFを更新」と「HANDOFFのflow-id 3-6完了とpush回数6を記録」は**どちらも6語で終わる**が、
前者は対象名しか伝えず、後者は変更後の状態を伝える。**6語は候補を絞る網であって、判定ではない。**
これが上記の2段階へ分けた理由である。

## 既存の「絶対ルール」を2箇所限定した

新設節が `Refs #NNN` を許容したことで、`commit/SKILL.md` の既存記述2箇所と矛盾した。両方を
**目的で限定**することで解消した。

| 箇所 | 変更前 | 変更後 |
|---|---|---|
| 「絶対ルール」 | `Co-Authored-By: Claude` **などのフッター**は絶対に付けない | `Co-Authored-By: Claude` **のような、AIの生成物であることを示すフッター**は絶対に付けない |
| フッター小節のモデル名行 | モデル名・モデルIDを含む記述は**リポジトリへ入る成果物すべて**で絶対に付けない | **どのAIが書いたかを示す目的で**書くことを、コミットメッセージ・PR/MRのタイトルと本文・コード内コメントで禁止 |

**モデル名行を限定しなければ、リポジトリの既存資産3箇所と矛盾する。**

- `.claude/rules/shell-script-style.md` — 桁区切りの誤適用例としてモデルIDを挙げている
- `.claude/scripts/test/test_usage_tracking.sh` — `report(claude): 3桁区切りが入りモデル名の
  数字は区切られない` のアサーションが、期待値としてモデルIDを持つ
- `.claude/hooks/post-push-usage-report.sh` — 対応工数レポートの `- 使用モデル:` 行を出力する

いずれも「どのAIが書いたか」を示すものではない。**禁止は対象で書かず、目的で書く。**

**この2箇所は禁止の緩和である。** 後から「なぜ緩めたのか」が最も問われる種類の変更なので、
結論（限定された文面）だけでなく理由をここへ残す。**元の広い禁止へ戻すと、上の3箇所と再び
矛盾する。**

## 懸念・残るリスク

**「現行規約が既に破られている」という実測は、方針決定にとって二面の材料である。**

| 読み | 内容 |
|---|---|
| 本文許容を支持する側 | 規約が実態と乖離している。実務は既に本文を書いている |
| **規約の実効性を疑う側** | **規約を追加しても守られない可能性がある。** フッター禁止は明文の「絶対ルール」だったのに、6回すり抜けてマージされた |

**今回は規約の追記のみで、機械的な強制（hook等）は入れていない。** したがって、この規約も同じ形で
すり抜けうる。**この懸念は起票時から予見していたが、対策は打たなかった**——後からこの規約が
守られていないと分かったときに、それが想定外だったのか予見済みだったのかを判別できるよう、
ここへ残す。
