# i33-01. 配布物の版はVERSIONファイル1つで表しCHANGELOGを持たない

issue #33。

## 背景

このリポジトリは他プロジェクトへワークフロー機構（`.claude/` 一式・ルート設定・テンプレート）を
配布するテンプレートだが、**配布物の版を識別する手段が無かった**。配布先は「どの版の資産を
導入したか」を判別できず、本家の変更に追随すべきかどうかを自力で判断できない。

issue #26 は配布方式をmanifest方式へ作り直し、「版＝適用元のコミットSHA」で同一性を機械的に
扱う予定である。本DDRはそれと衝突しない範囲で、**人間が扱える版**をどう持つかを決める。

## 決定

**`.claude/VERSION` に SemVer 1行だけを置く。CHANGELOGは持たない。**

- 位置は**リポジトリルートではなく `.claude/` 配下**。
- 初期値は `0.1.0`。
- 更新は flow-id 4-6（AIアセット反映）で、配布対象アセットに変更があった回だけ行う。
- 増分（MAJOR/MINOR/PATCH）は**AIエージェントが提案し、人間が決める**。
- 変更内容はコミット履歴／PR一覧で辿る。

仕様の詳細は [.claude/docs/spec/distribution-assets.md](../spec/distribution-assets.md)。

## 理由

### CHANGELOGを持たない

版管理の目的は「配布先が、自分の持つ資産がいつの版かを言えること」であり、変更内容の一覧では
ない。このリポジトリの変更はすべてissue・PR単位で記録されており、CHANGELOGはその**三重目の
記録**になる（コミット履歴・PR一覧・CHANGELOG）。二重・三重管理はいずれ片方が腐る。
本issueの対応時点で、ユーザーが「VERSIONファイルのみ採用（CHANGELOGなし）」を選択した。

### ルートではなく `.claude/` に置く

**配布先が自分のアプリの版として `VERSION` をルートに持ちうる。** issue #33 の調査で、
使い捨ての配布先へ `VERSION`（`1.2.3`）を置いた状態で `install-to-project.sh` を適用する実験を
行った。現状はルートの `VERSION` が配布経路に載っていないため無変更で済んでいるが、ここへ
配布物の版を載せると、配布先のアプリの版を `.bak` 退避のうえ上書きすることになる。
「テンプレートを入れたらアプリの版が書き換わった」は事故として重い。

`.claude/` はワークフロー機構が所有するディレクトリであり、名前が衝突しない。副次的な利点として、
`sync-assets.sh`（`.claude/*` のループ）と `install-to-project.sh`（`safe_copy_dir` の
`find -type f`）が既に配下の全ファイルを対象にしているため、**スクリプトを1行も変えずに配布経路へ
載る**。

### issue #26 のmanifestと重複しない

manifestが持つのは「適用元コミットSHA＋ファイルごとのsha256」という機械可読で正確な同一性で、
VERSIONは人間が口頭・issue上で示せる粗い識別子である。役割が異なるため、#26 のmanifestには
両方を記録すればよい。

### 初期値を 1.0.0 にしない

issue #26 が配布方式そのもの（manifest化・層分け・`sync-assets.sh` 廃止）を作り直す予定であり、
配布インターフェースはまだ安定していない。`0.x` はその状態を素直に表す。

## 却下した案

- **CHANGELOG.md を併用する**: 「何が変わったか」を配布先から読めるのは利点だが、上記のとおり
  三重管理になる。更新を忘れた瞬間に、**空でないのに嘘をつくドキュメント**になる（空のCHANGELOGは
  無害だが、古いCHANGELOGは有害）。
- **リポジトリルートに `VERSION` を置く**: 発見しやすいが、配布先のアプリの版と名前が衝突する
  （上記）。
- **`.mrworkflow.json` へ `templateVersion` キーとして持たせる**: 新しいファイルを増やさずに済むが、
  `.mrworkflow.json` は**配布先が編集する設定ファイル**（ブランチ命名規則等をプロジェクトごとに
  書き換える前提）である。配布元が上書きしたい版番号と、配布先が書き換えたい設定が同じファイルに
  同居すると、そのファイルの上書き方針が決まらない。
- **版管理を採用せず、issue #26 のコミットSHAへ一本化する**: 二重管理を避けられるが、人間が
  「うちは0.3系を入れている」と口頭・issue上で示せない。40桁のSHAは会話の単位にならない。
