# 0056. フェーズ5は片付けをcommit直前へ移した順序に並べ替える

## 背景

issue #112。フェーズ5（クローズ）のステップは、コンフリクト検知（issue #46）・関連issue通知
（issue #86）が後から挿入された結果、次の順序になっていた。

| 旧flow-id | 内容 |
|---|---|
| 5-1 | `plans/` `worklog/` `reports/` の削除・`HANDOFF.md` のリセット（片付け） |
| 5-2 | defaultブランチとのコンフリクト検知・解消 |
| 5-3 | 関連issueへのマージ前通知 |
| 5-4 | commit・push・Draft解除 |

issue #67 の対応中に、この順序が次の4点で実際の作業手順と噛み合わないことが判明した。

1. **5-3 が `HANDOFF.md` へ書けない。** 5-3 は「影響先が無ければスキップしてよい。その場合も
   『影響先なし』と判断したことを `HANDOFF.md` の『やったこと』へ1行残す」と定めているが、
   5-1 が既に `HANDOFF.md` を空テンプレートへリセットしているため書き戻す先が無い。書き戻せば
   リセットが無効になり、書かなければ「判断を省いたのか、判断した結果なしだったのか」を次の
   セッションが区別できない。
2. **5-1 を先に置く利点が存在しない。** `check-base-conflicts.sh` は `git merge-tree` を
   コミット済みの ref（`HEAD`）に対して実行するため、5-1 が行う削除は未コミットの間 5-2 の
   判定から見えない。「先に片付けてから衝突を見る」という効果は得られていなかった。
3. **5-2 の解消が汚れた作業ツリーの上で走る。** 5-1 の直後は削除（issue #67 では13ファイル）と
   `HANDOFF.md` の変更が未コミットで残る。この状態で `resolve-conflict` が `git merge` を実行すると、
   コンフリクト解消の結果と片付けの削除が同じ作業ツリーに混ざり、5-4 のコミットで切り分けが要る。
4. **5-1 と 5-4 が離れている。** `cleanup-task.sh` は「コミットまでは行わない」設計（DDR 0048）で、
   その結果は 5-4 の `commit` スキルでコミットすると定めている。生成と確定の間に別のステップを
   2つ挟む理由が無い。

## 決定

- **フェーズ5のステップを次の順序へ並べ替える。** ステップの内容・総数（41ステップ）は変えない。
  5-4（commit・push・Draft解除）・5-5（マージ）は番号・内容とも変更しない。

  | 新flow-id | 内容 | 旧flow-id |
  |---|---|---|
  | 5-1 | defaultブランチとのコンフリクトを検知し、あれば解消する | 5-2 |
  | 5-2 | 今回のMRが影響する関連issueを特定し、承認を得てから通知する | 5-3 |
  | 5-3 | `plans/` `worklog/` `reports/` を削除し `HANDOFF.md` をリセットする | 5-1 |
  | 5-4 | commit・push して Draft を解除する（AIエージェントはここで止まる） | 5-4 |

- **関連issue通知（新5-2）のキーワード抽出では、差分から `plans/` `worklog/` `reports/` を
  除外する。** 新順序ではこれらがまだ削除されておらず差分に含まれるため、除外しないと
  マージ後には残らないファイルの語が候補検索へ混ざる。手順には
  `git diff --stat "origin/${base}...HEAD" -- . ':(exclude)plans' ':(exclude)worklog'
  ':(exclude)reports'` を明示する。
- **DDR 0044 の理由のうち「5-1（片付け）より後に置く必要がある」は、この除外指定で置き換える。**
  0044 は「通知の根拠を『マージされる差分』に一致させるには削除も含んだ状態で差分を見るのが
  正しい」としていたが、片付けで消えるのは**そもそもマージ後に残らないタスク用ファイルだけ**で
  あり、通知先の判定に効く情報を持たない。差分に含めるか除外するかの違いでしかなく、順序で
  担保する必要は無い。**0044 の本文は書き換えない**（DDRは本文不変。`.claude/rules/docs-workflow.md`）。
  0044 のもう一方の理由「5-2（コンフリクト解消）より後に置く必要がある」は新順序でも成立している
  （新5-1 → 新5-2 の並びは維持される）。
- **既存DDR・過去のchangelogに残る旧番号は書き換えない。** DDR 0044・0048 の本文、および
  `.claude/docs/spec/*.md` の `## 影響範囲` 配下の過去issueごとのエントリは当時の記録である。
  DDR 0048 はファイル名にも `flow-id5-1` を含むが、リンク切れを避けるためリネームしない。
  現在の番号との対応は、本DDRと `.claude/docs/spec/cleanup-task.md`「背景・目的」で示す。

## 理由

- **新5-2（関連issue通知）が `HANDOFF.md` を持てる。** リセット（新5-3）より前に置くことで、
  「影響先なし」という判断の記録先が存在する状態になる。issue #112 のコメントによれば、
  PR #118 では実際にこの順序で実行し、通知先を持つケースで記録が失われずに済んだ。
- **コンフリクト解消をフェーズ5の先頭へ置くと、`git merge` がcleanな作業ツリーの上で走る。**
  上記2のとおり、片付けを先に済ませても検知の精度は上がらない。一方で3の混線は確実に起きるため、
  「先に解消し、片付けは後」の順序に一方的な利がある。
- **片付けと commit が隣接する。** `cleanup-task.sh` がコミットを行わない設計（DDR 0048）は
  変えずに、生成（5-3）と確定（5-4）が間に何も挟まずに並ぶ。

## 却下した案

- **順序は変えず、関連issue通知の記録先を `HANDOFF.md` 以外にする**（worklog・MRコメント等）。
  worklog は同じ 5-1 で削除されるため書き戻し先にならない。MRコメントは残るが、次のセッションが
  現在地を知るために読むのは `HANDOFF.md` であり（`resume`・SessionStart hook）、判断の記録だけを
  別の場所へ切り出すと「どこを見れば判断の有無が分かるか」が増える。記録先を分散させるより、
  記録先が生きている順序へ直すほうが単純である。
- **順序は変えず、片付け（5-1）で `HANDOFF.md` のリセットだけを 5-4 の直前へ遅らせる。**
  1ステップの内容を2箇所へ分割することになり、`cleanup-task.sh` の4操作が1コマンドである
  という前提（DDR 0048）も崩れる。不整合2・3・4は残ったままになる。
- **片付けを 5-4（commit）へ統合して1ステップにする。** DDR 0048 が却下済み。片付けの結果を
  人間が確認してからコミットできる状態を保つため、スクリプトはコミットを行わない。
- **フェーズ5全体を作り直し、ステップ番号を振り直す。** flow-idは `HANDOFF.md` の進捗表・rules・
  spec・スクリプトのコメントへ散っており、番号の意味を変える範囲は小さいほどよい。今回動かすのは
  5-1〜5-3 の3つだけで、5-4・5-5 は据え置いた。

## issue #108（`HANDOFF.md` をタスク単位のファイルにする）との関係

issue #108 は `HANDOFF.md` を main に置かず、flow-id 1-6 で生成し**片付けのステップで削除する**
（リセットではなく削除する）ことを提案している。両者の関係は次のとおり。

- **本issue（#112）が先に入るのが望ましい。** #108 が先に入ると、旧順序のままでは関連issue通知
  （旧5-3）の時点で `HANDOFF.md` が**リセット済み**ではなく**削除済み**になり、不整合1がさらに
  悪化する（書き戻し先がテンプレートですら無くなる）。並べ替え後は、通知（5-2）→ 削除（5-3）の
  順になるため、#108 の変更を入れても記録先は残る。
- **#108 側は「片付け」の flow-id を 5-3 として書けばよい。** #108 の本文は旧番号（5-1）で
  書かれているが、指しているステップは同じである。
- 本issueは #108 のスコープ（`HANDOFF.template.md` の新設・`cleanup-task.sh` の削除化）には
  踏み込まない。
