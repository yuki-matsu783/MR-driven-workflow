# i0053-01. hookの検知は正規化とコマンド位置判定にし読めない実行体は部分一致へ縮退させる

## 背景

`.claude/hooks/block-direct-git-commit.sh` と push検知hook 2本は、`tool_input.command` に対する
**部分一致**（`grep -qiE 'git[[:space:]]+commit'`）だけで発火を決めていた。文字列のどこに該当語が
現れてもマッチするため、ヒアドキュメント本文・クォート内・コメント・日本語の地の文で誤検知する。

実際に issue #39 で2回、#45・#47 で各1回踏んでおり、issue #53 の作業中にも2回踏んだ
（いずれも「この仕組み自体を日本語で説明する文章」を書いたときである）。回避策として
`.claude/rules/git-workflow.md`・`.claude/rules/ai-command-style.md`・ルート `REVIEW-POINTS.md` に
「`git` と `commit`/`push` を半角スペース区切りで連続させない」というルールを置いていたが、
**AIエージェントが毎回思い出す必要のあるルールは守られない**（issue #53 の作業中に自分で2回
踏んだことがその証拠である）。

## 決定

1. 判定を**「正規化 → コマンド位置でのトークン走査 → 保守的フォールバック」の3段**にする。
2. 判定ロジックは `.claude/hooks/lib/CommandPosition.sh` へ切り出し、**外部コマンドを一切
   呼ばない純粋関数**として書く（コマンド置換・パイプも含まない）。
3. **静的に読めない入力は、必ず部分一致へ縮退させる**（＝ブロック側へ倒す）。対象は
   「文字列をコードとして受け取る実行系」「長すぎる1行」「ライブラリを読めない環境」の3つ。
4. **意図的な文字列分割（`git "commit"`）・変数展開・alias 経由には対応しない。**
5. `.claude/settings.json` の `if` フィルタは**変更しない**。

## 理由

### なぜ完全なシェルパーサにしないのか

「実行かどうか」を厳密に決めるにはシェルの構文をすべて解釈する必要があり、bashで書けば
数千行になる。一方、この仕組みは**敵対的な安全境界ではなく、既定動作を確実な方向へ倒すもの**
である（DDR `i0000-09`）。意図的な回避を防げないことは元から前提であり、精度を上げても
守れる範囲は広がらない。

必要なのは「AIエージェントが**普通に書いた**コマンド文字列を正しく分類すること」であって、
「あらゆるシェル構文を正しく解釈すること」ではない。線引きはこの目的から決めた。

### なぜクォートを外すだけでは足りないのか

最初に考えたのは「クォート・ヒアドキュメント・コメントを除外して部分一致する」だけの案だった。
しかしこれは**新しい素通りを5類型作る**（issue #53 のフェーズ2で列挙・実測した）。

`bash -c "… commit"` / `eval "… commit"` / `echo "$(… commit)"` / `xargs … commit` /
`find -exec … commit`

いずれも**クォートの中に実行がある**形であり、クォートを一律に除外した時点で見えなくなる。
誤検知を減らす変更が検知漏れを増やすなら、issue #53 の受け入れ条件5（素通りリスクが改善効果を
上回るならクローズしてよい）に抵触する。**除外と同時に塞ぐ**必要があった。

そのため、(a) ダブルクォート内の `$( )` と `` ` ` `` はコードとして展開し直し、
(b) それでも静的に読めない実行系は部分一致へ縮退させる、という2本立てにした。

### なぜ「読めないものはブロック」なのか（失敗の向き）

2種類の誤りは**許容度が非対称**である。

| 誤りの向き | 結果 | 回復手段 |
|---|---|---|
| 誤検知（実行でないものをブロック） | AIエージェントが一手止まる。理由が返るので書き直せる | **ある**（本文をファイルへ逃がす等） |
| 素通り（実行を見逃す） | `commit` スキルを経ないコミットが通る。強制の仕組み自体が無意味になる | **無い**（起きたことに気づけない） |

したがって、判断がつかない場合は必ずブロック側へ倒す。具体的には次の3つで縮退する。

- **文字列をコードとして受け取る実行系**（`eval` `xargs` `find` 等がコマンド位置にある）
- **8192バイトを超える行**（正規化が1行の特殊文字数に対して二乗のコストを持つため。
  PreToolUseの `timeout` に達するとhookが効かないまま素通りになる）
- **ライブラリを読めない環境**（bash 4.3未満・配布漏れ・構文エラー）

### なぜ外部コマンドを呼ばないのか

hookは**すべてのツール呼び出しで走るホットパス**であり、git bashでは外部プロセス起動が
約95ms/回かかる（`.claude/rules/shell-script-style.md`）。旧実装は `printf | grep` で
2回forkしていた。純粋bashにすればこれが0回になる。

短い入力での実測（Linux、200回）は 432ms → 98ms で4.5倍速い。一方、18KBのヒアドキュメントでは
480ms → 1450ms と3倍遅くなる。**それでもfork 0回を優先した**のは、git bashのfork 1回
（約95ms）がLinuxでの実測（数ms）と桁が違い、実行環境での比が逆転すると見込んだためである。
ただし**git bash実機では未実測**であり、この見込みは確かめられていない。

### なぜ `if` フィルタを変えないのか

push検知hookは `.claude/settings.json` の `if: "Bash(git push*)"` で絞ってから起動する。
これを緩めれば、いま届いていない入力にもコマンド位置判定を効かせられる。しかし:

- `if` を緩めると**発火が増える方向**の変更になり、誤検知を減らすという本issueの向きと逆である。
- `if` の照合規則（前方一致か部分一致か）は issue #47 が両論併記のまま残しており、
  本issueでも切り分けていない。**未解明の挙動を前提に設定を変えない。**

結果として push側は「`if` で絞ってから、スクリプト内でコマンド位置判定」という二段構えになる。
`if` が届かせた入力のうち、地の文・クォート内・ヒアドキュメント本文しか該当語を含まないものは
スクリプト側で落ちるようになった。

## 却下した案

### 案A: クォート・ヒアドキュメントの除外のみ（部分一致は維持）

**却下。** 上記のとおり5類型の素通りを新たに作る。実装は最も小さいが、受け入れ条件5に抵触する。

### 案B: 完全なシェルパーサを書く

**却下。** 規模が目的に見合わない。意図的な回避を防げないことは前提であり、精度を上げても
守れる範囲が広がらない。加えてホットパスで動かすには重い。

### 案C: `${s:i:1}` による1文字ずつの走査

**却下。** 文字列長に対して二乗のコストになり、10KB程度のヒアドキュメントで数百msかかる
（実測）。`LC_ALL=C` を指定しても改善しないことを確認しており、ロケールの問題ではない。
行配列（`mapfile`）＋チャンク読み飛ばし（`${rest%%$PATTERN*}`）を採った。

### 案D: 上限を設けずインデックス走査で二乗を解消する

**却下**（`_CP_MAX_LINE_LENGTH` による縮退を採用）。案Cと同じ理由で、bashの文字列操作だけでは
根本的に速くならない。上限を超えたら部分一致へ落とすほうが、**遅くなって timeout する**
（＝素通り）より失敗の向きが良い。

### 案E: `bash` を無条件にフォールバック対象へ入れる

**却下。** `bash .claude/scripts/src/create-commit.sh --message "…"` という**正規の呼び出し**
まで対象になり、issue #53 の受け入れ条件「ブロックされないこと」に反する。コード指定
オプション（`-c` 等）との併用時のみ対象にする2段構えにした。

### 案F: `post-issue-create-notice.sh` にも適用する

**見送り**（却下ではない）。同じ部分文字列マッチの構造を持つが、issue #53 が名指ししておらず
スコープ外である。必要なら別issueで扱う。

## 影響

- 20ケースの実測が 13/20 → **20/20**（変更前は誤検知6件・検知漏れ1件）。
- 検知漏れが1件減った。`git -C /repo commit` は変更前は素通りしていた。
- **回避策のルールが不要になるのは、hookスクリプト側の判定だけである。** `if` フィルタと
  縮退時（長すぎる1行・読めない実行体・ライブラリを読めない環境）では部分一致が残るため、
  ルールを一律には削除できない。この書き分けは
  `.claude/rules/git-workflow.md`・`.claude/rules/ai-command-style.md`・
  ルート `REVIEW-POINTS.md` へ反映した。

## 補足: 自分の実装が2件の機能後退を作っていた

フェーズ3の敵対的レビュー（`adversarial-review` スキル）で、**旧実装が検知していた入力を
新実装が取りこぼす**という指摘を2件受けた。

- 行継続（`git \`＋改行＋`commit`）— バックスラッシュを一律に潰していたため
- 値を別トークンで取るグローバルオプション（`git --git-dir /x/.git commit`）

いずれも意図的な回避ではなく**単なる整形・慣用表記**である。自分で用意した20ケースの検証表は
「変更前に誤検知していたもの」を中心に組んでおり、**「変更前に正しく検知できていたもの」の側が
薄かった**ことが原因である。

**回帰の観点は、直したい側からではなく壊しうる側から先に組む。** 判定の条件を狭める変更では、
「狭めた結果こぼれるもの」を列挙するのが検証の主眼になる。
