# i33-02. 配布テンプレートにLICENSEを同梱しない

issue #33。

## 背景

issue #33 は受け入れ条件のひとつに「LICENSE ファイルが追加される（**ライセンス種別はユーザーが
決定する**）」を挙げていた。このリポジトリは `apply-mr-workflow-to-project` スキルで他リポジトリへ
資産をコピー配布する前提であり、再配布条件が未定義であることが問題視されていた。

## 決定

**LICENSEファイルを追加しない。**

issue #33 の対応時、ライセンス種別の選択（MIT / Apache-2.0 / CC0・Unlicense / プロプライエタリ）を
ユーザーへ確認したところ、**「なし」**という回答だった。種別の決定権はユーザーにあると
issue本文自身が定めているため、その判断に従う。

結果として、**issue #33 の受け入れ条件のうちこの1件は意図的に満たさないまま完了とする。**
「対応し忘れた」のではないことを残すために、このDDRを設けた。

## 理由

ライセンスの選択は技術的な最適解ではなく、**権利者の意思決定**である。AIエージェントが
「一般的だから」という理由でMITを置くことは、権利者が意図していない許諾を与えることになりうる。
不可逆性の観点でも、いったん公開したライセンスの取り消しは（既に受領した第三者に対しては）
実質的に不可能であり、**足す方向にはいつでも動けるが、外す方向には動けない**。

## 帰結（このまま運用する場合に受け入れること）

- LICENSEが無いリポジトリは、既定で**著作権法上の保護下**にある。第三者がこのテンプレートを
  複製・改変・再配布してよいという明示的な許諾は存在しない。
- 公開リポジトリであることは許諾を意味しない。GitHubの利用規約により、公開リポジトリの
  閲覧とフォークは可能だが、それ以上の利用条件は定まらない。
- `apply-mr-workflow-to-project` スキルによる配布は、**権利者自身またはその許諾を得た者が行う**
  という前提で運用する。
- 配布先プロジェクトが自分のライセンスを選ぶことは、この決定によって妨げられない
  （`install-to-project.sh` は配布先の LICENSE を作成・変更しない）。

## 将来追加する場合

種別が決まった時点で、次を行えばよい。

1. リポジトリルートへ `LICENSE` を置く。
2. `sync-assets.sh` / `install-to-project.sh` の配布対象に**加えるかどうかを別途判断する**
   （配布先が自分のLICENSEを持つ場合に上書きするのは事故になるため、`.gitattributes` と同様、
   「配るか・どう配るか」は「本家に置くか」とは別の判断である）。
3. 本DDRを `status: superseded` にせず、**新しいDDRを起こして置き換える**
   （本DDRの本文は決定時点の記録として残す）。

## 却下した案

- **一般的なMIT Licenseを置く**: 選択肢として提示したが、ユーザーが「なし」を選んだ。AIの判断で
  「無難だから」と置くことは、権利者の意思決定を代行することになる。
- **LICENSEの代わりにREADMEへ一文だけ書く**: 「再配布条件は未定」と書くこと自体は無害だが、
  ライセンスとしての効力を持たない一方で**ライセンスがあるように見える**恐れがある。決定を
  DDRへ残し、READMEには書かない。
