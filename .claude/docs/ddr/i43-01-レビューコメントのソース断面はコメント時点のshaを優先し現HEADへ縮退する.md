# i43-01. レビューコメントのソース断面はコメント時点のshaを優先し現HEADへ縮退する

## 背景

issue #43。`get_mr_unresolved_comments` はGitHubの `diffHunk`（ハンク先頭から指摘行までの
差分テキスト）をそのまま出力していた。これには5つの問題があった。

1. **コンテキスト量が予測できない**（PR #10 の実測で 342B〜9,189B と24倍の開き）
2. **同一 `diffHunk` がスレッド内のコメント数だけ重複する**（PR #37 で2回重複を確認）
3. **指摘行より後ろの文脈が取れない**（`diffHunk` は指摘行で切れる）
4. **行番号が付かない**（`@@` ヘッダから自力で数える必要がある）
5. **GitHub固有機能への依存**（GitLabの `discussions` APIはハンクテキストを返さない）

`diffHunk` をやめ、GitHub/GitLab双方が持つ `(path, line, sha)` から共通ロジックで指摘行前後を
切り出す方式へ移行する。このとき **`sha` として何を採るか**が決めるべき点になった。

## 決定

**コメント時点のsha（レビュアーが実際に見た断面）を優先し、取得できない場合にのみ現HEADへ
縮退する。縮退した場合は、その旨を出力へ明示する。**

具体的には、プロバイダ層が次のように `sha` を解決する。

| プロバイダ | 指摘行が現行行（`line` あり） | 指摘行がoutdated（`line` が null） |
|---|---|---|
| GitHub | 先頭コメントの `commit.oid` | 先頭コメントの `originalCommit.oid`（行は `originalLine`） |
| GitLab | `position.head_sha`（`new_line` 側） | `position.base_sha`（`old_line` 側＝削除行） |

そのうえで、断面の取得は次の4段階へ縮退する。

| 段階 | 手段 | 出力への注記 |
|---|---|---|
| 1 | ローカルのblob（`git cat-file -e <sha>:<path>` → `git show`） | なし |
| 2 | プロバイダのファイル取得API（`read_file_at_ref`） | なし |
| 3 | `git show HEAD:<path>` | `(断面 <sha7> を取得できず現HEADを表示)` |
| 4 | すべて失敗 | ソースを出さない（**コメント本文だけは必ず出す**） |

### 理由

- **レビュアーが指摘した内容と、AIが読むソースを一致させるため。** レビューコメントは
  「その時点のコード」に対して書かれている。断面がずれると、指摘の主語が現在のコードに
  存在しない、あるいは別の内容になっている、という食い違いが起きる。とくに outdated な
  スレッド（本リポジトリの既存スレッドは全件がこれだった）では、現HEADを切ると指摘対象の
  コードがそもそも残っていないことがある。
- **ずれた場合に黙らないため。** 段階3へ落ちたときは注記を出す。注記が無ければ、AIは
  「レビュアーが見たコード」を読んでいるつもりで現在のコードを読むことになる。**縮退そのもの
  より、縮退したことが分からないほうが危険である。**
- **shallow cloneでも段階1で足りることが多い。** Claude Code on the web のリモート実行環境
  （`isShallow: true` / depth 190）で過去4commitのblobを引けることを確認した。履歴の切断点より
  新しいcommitのblobは存在し、レビューコメントが指す断面は通常その範囲に入る。段階2以降は
  保険である。

## 却下した案

### (a) 常に現HEADを切る

実装は最も単純で、「AIがこれから直す対象」と一致するという利点もある。しかし
**レビュアーが指摘した内容とずれる**。outdatedなスレッドでは指摘対象の行がもう存在しないことが
あり、その場合に無関係な行が `>>>` で示されると、指摘の読み違いを積極的に誘発する。
「一致する場合が多い」ことは、一致しない場合に気づけないことの理由にならない。

### (b) 常にコメント時点のshaで切り、取得できなければソースを出さない

断面の正確さでは最も強いが、**shallow cloneや履歴の切断で無出力になりうる**。この機構は
Claude Code on the web のリモート実行環境（常に shallow）でも使われるため、「取れないことが
あるが、取れないと何も出ない」という設計は運用に耐えない。現HEADでも文脈が無いよりは
遥かに良く、注記さえ出れば読み手は差を織り込める。

### (c) 断面のファイル全体を出し、切り出しをしない

行数・バイト数の制御を捨てることになる。issue #43 が解こうとした「コンテキスト量が予測できない」
問題がそのまま残るため採らない。

### (d) `diffHunk` を残したまま行番号だけ付ける

重複と「指摘行より後ろが取れない」問題が残るうえ、GitLab側は同等の実装ができない
（ハンクテキストが返らない）。**非対称の解消がこのissueの目的の半分**であるため採らない。

## 併せて決めたこと

### 上限は行数とバイト数を併用する

前後10行（既定）に加え、スライス本文へ 2,000バイト（既定）の上限を掛ける。
**行数だけでは上限にならない**ことを実測で確認したため。

`.claude/rules/docs-workflow.md`（131行 / 18,441B、最長行 1,387B）で指摘行を変えながら ±10行の
バイト数を測ると **684B〜8,971B（13.1倍）** ばらついた。一方 1行の短い
`.claude/scripts/src/vcs/Provider.sh` では 984B〜1,038B に収まる。**ファイル種別で1桁違う。**

上限を超えたときは指摘行から遠い側から1行ずつ落とす（指摘行が落ちては意味が無い）。1行だけに
なってもなお超える場合はその行自体を切り詰めるが、**UTF-8の文字境界まで戻してから返す**ため
文字が壊れることはない。既定値は環境変数（`REVIEW_SOURCE_CONTEXT_LINES` /
`REVIEW_SOURCE_MAX_BYTES`）で上書きできる。`.mrworkflow.json` へは置かない——他リポジトリへ
移植したときに書き換えたくなる値ではなく、その場の事情で一時的に変えたい値だからである。

### プロバイダ層はテキストを組み立てない

`line` / `sha` の解決（`originalLine` / `originalCommit` の使い分け、`new_line`/`old_line` の
使い分け）はプロバイダ層で閉じ、共通層へは解決済みの値だけを渡す。テキスト整形は共通層の
`format_review_comments` が単独で担う。

issue #48〜#42 の時点では、GitHub側とGitLab側がそれぞれ独立に整形しており、**行頭ラベルが
`[review unresolved ...]` / `[unresolved ...]` と非対称**だった。`.claude/hooks/session-start.sh`
は `^\[review unresolved threadId=` で未解決件数を数えているため、**GitLabリポジトリでは
未解決件数が常に0件と表示されていた**（issue #43 の調査で判明）。整形を1箇所へ寄せることで、
この種の非対称が構造的に起きなくなる。

副次的な効果として、**GitHub側の整形に単体テストが付いた**。それまでGitHub側の整形は `gh` 依存で
切り出せておらず、issue #94（PR #126）のCR混入をテストで検知できなかった。
