# issue-mr-flow 参照: 計画（全体作業計画・個別計画）

## 全体作業計画に必ず含めるフェーズ（issue #92）

flow-id 1-4 で作る全体作業計画には、**フェーズ2〈調査〉とフェーズ4〈反映〉を必ず節として置く**。
「今回は調査は要らない」「反映するものは無いだろう」と先回りして判断し、節ごと落とした形で
組み立てない。

**理由**: 計画に節が無いと、後から必要だと分かっても拾い直す先が無い。枠さえ残っていれば、
実施しないと決めたときにも「なぜ実施しないか」を同じ場所へ書けるため、判断の記録が残る。

### 全体作業計画のための事前調査は軽めでよい

1-4 の時点で必要なのは、**issue本文と、関連しそうなファイルの所在・見出しレベルの確認**までで
ある。「何を調べるか」「何を作るか」を節として書ける程度で足り、コードベースを読み込んで結論まで
出す必要はない。

- **本格的な調査はフェーズ2（flow-id 2-1〜2-10）で行う。** 1-4 で深追いすると同じ調査を
  フェーズ2で繰り返すことになり、しかも 1-4 側の結果は個別調査計画のレビュー（2-3〜2-4）を
  経ていないため、レビュー可能な形で残らない。
- 事前調査が軽くても困らないのは、**フェーズ2の枠を必ず残しているから**である。1-4 の見立てが
  外れても、2-1 で調査計画を立て直せる。

### 反映は枠だけ置く

何を `.claude/docs/spec/` `.claude/docs/ddr/` やAIアセットへ反映するかは、**作業が終わるまで
決められない**。1-4 では「反映対象は flow-id 4-1 で洗い出す」と書くにとどめ、見込みがある場合も
候補として添える程度にする（確定した反映内容として書かない）。

### 省略してよいと判断できるタイミング

| フェーズ | 判断できる最初のタイミング | 判断の材料 |
|---|---|---|
| フェーズ2〈調査〉 | **flow-id 2-1**（個別調査計画を作る段） | 既に分かっていることだけで個別作業計画（3-1）が書けるか |
| フェーズ4〈反映〉 | **flow-id 4-1**（個別反映計画を作る段） | 反映対象を洗い出した結果、spec/ddr・実装コード/テストコードに反映するものが無く、かつAIアセット側も下記「AIアセット反映の対象の洗い出し」の手順1〜2で分類結果が0件か |

**フェーズ4は必ず通る**（4-1 で反映対象を洗い出すところまでは省略しない）。spec/ddr・実装コード/
テストコードに反映するものが無く、**かつAIアセット側は下記「AIアセット反映の対象の洗い出し」の
手順1〜2まで実施して分類結果が0件だった**ときに限り、その時点でフェーズ4の残りをスキップしてよい。

進捗記号 `[-]`（今回は実施しない）を使ってよいのも、上表のタイミング以降である。**flow-id 1-4 の
時点でフェーズ2・4の行を `[-]` で埋めない**（記号の意味・粒度は `.claude/rules/docs-workflow.md`
「ドキュメント運用」を参照）。

## 計画の2階層構造（issue #9）

計画は**全体作業計画**（上位）と**個別調査計画・個別作業計画・個別反映計画**（下位）の2階層に分ける。
Claude Code / Gemini CLI は**セッションごとに1つのplanファイルしか割り当てない**ため、
planツールで複数の計画を作ろうとすると計画同士が混ざる。これを構造的に避けるための分離である。

| 種類 | 作り方 | ファイル名 | 単位 |
|---|---|---|---|
| **全体作業計画** | **planツール**（Planモード）で作成 | ハーネス提示パス `plans/<自動命名>.md` をそのまま使う | **issue（ブランチ）につき1回**（flow-id 1-4） |
| **個別調査計画** | **planツールを使わない**（Write/Editで直接作成） | `plans/【調査】タスク内容.md` | フェーズ2で必要な数だけ（flow-id 2-1） |
| **個別作業計画** | **planツールを使わない**（Write/Editで直接作成） | `plans/【種別】タスク内容.md` | フェーズ3で必要な数だけ（flow-id 3-1） |
| **個別反映計画** | **planツールを使わない**（Write/Editで直接作成） | `plans/【種別】タスク内容.md` | フェーズ4で必要な数だけ（flow-id 4-1） |

**タスク種別**（`【】`内）は次の8種を標準とする（issue #110で6種から拡張）。属するフェーズは
次のとおり。

| フェーズ | 種別 |
|---|---|
| フェーズ2〈調査〉 | `【調査】` |
| フェーズ3〈作業〉 | `【設計】` `【実装】` `【テスト】` `【AIアセット作成】` |
| フェーズ4〈反映〉 | `【設計反映】` `【AIアセット反映】` `【実装反映】` |

- **`【AIアセット作成】`**: そのissueの**主たる成果物**としてAIアセット（スキル・ルール・
  エージェント）を**新規作成・改訂**する作業。**設計ドキュメント（usecase文書等）を主たる
  成果物として新規作成・改訂する場合もこの種別に含む**（issue #170の実績。作業の過程で得た
  知見を既存のspec/ddrへ書き戻すのは`【設計反映】`（フェーズ4）の担当であり、この種別には
  含めない。また、実装に先立つ設計検討そのものは`【設計】`であり、成果物として残す
  設計ドキュメントの作成・改訂がこの種別、と区別する）。`.claude/scripts/`配下のスクリプトは実装コードと
  同じ性質（単体テストを持つ等）を持つため、**フェーズ3では**対象に含めない（`【実装】`側で
  扱う）。**フェーズ4で副産物として反映する場合は、`.claude/scripts/` `.claude/hooks/` 配下も
  AIアセットとして`【AIアセット反映】`で扱う**（下記「AIアセット反映の対象の洗い出し」）。
  作業の**副産物**として気づいた改善を反映する`【AIアセット反映】`（フェーズ4）とは、
  成果物か副産物かで使い分ける。
- **`【実装反映】`**: フェーズ3（とくに`【テスト】`）の**レビュー合意後**に判明した、または
  合意には至らずフェーズ4へ持ち越すと合意した不具合について、フェーズ4でその内容を記録
  （spec/ddr等）へ書き戻しつつ、実装コード・テストコードの修正もあわせて行う種別。フェーズ3の
  レビュー往復ループ（3-6〜3-9）で解消できる不具合はそちらで対応し、フェーズ4へは持ち越さない
  （`【実装反映】`が拾うのは、このループの外で見つかった・持ち越すと合意したものに限る）。
  `【設計反映】`とspec/ddrへの書き戻しという対象が重なる場合があるが、**実装・テストの修正を
  伴うかどうか**で使い分ける（伴わない書き戻しのみは`【設計反映】`を使う）。対応が1issueに
  収まらない規模になった場合は、下記「issueが大きすぎる場合の分割提案」の基準に従い別issueへの
  切り出しを検討する。

### 種別を複数併記する場合／分ける場合

1ファイルに複数の種別を併記してよい（例: `plans/【実装】【テスト】SKILLフロー改訂.md`）。
判断基準は「**その計画に対して人間の合意を1回で取るか、フェーズごとに分けて取るか**」である。

| | 併記する（1ファイル） | 分ける（複数ファイル） |
|---|---|---|
| **判断基準** | 分けても合意の単位が変わらず、記述が重複するだけの場合 | フェーズごとに個別の合意・レビューを挟みたい場合 |
| **例** | `【実装】【テスト】` — テストコードを実装と同時に書き、まとめて1回で合意する | `【調査】〜.md` → `【実装】〜.md` — 調査結果を見てから実装方針を決めるため、間に合意を挟む |
| | `【設計】【実装】` — 設計が小規模で、実装方針と一体で判断できる | `【実装】機能A.md` / `【実装】機能B.md` — 対象範囲が独立しており、別々にレビューしたい |

迷ったら**分ける**。1ファイルが大きくなるほど、レビューで一部だけを差し戻しにくくなる。
逆に、併記した計画のレビューで「この部分だけ先に進めたい」となった場合は、その時点で
ファイルを分割してよい（分割後も既存の合意内容は失わないこと）。

**`【設計反映】` `【AIアセット反映】` `【実装反映】` は、基本的に併記せず分ける**
（issue #36, #110）。`【実装反映】`は`【設計反映】`とspec/ddrへの書き戻しという対象が
重なりうるが、評価軸（正史ドキュメントへの記録のみで足りるか、実装・テストの修正を伴うか）が
異なるため、1回のレビューでまとめて合意を取ろうとすると評価軸が混ざりやすい。実施タイミングも
計画ファイルと合わせて
分離し、必要なものから順に完了・レビューしてから次へ着手する（flow-id 4-6〜4-10を種別の数だけ
セットで回す形になる。1つのみで完結する場合は無理に分けなくてよい）。

`【AIアセット作成】`は他のフェーズ3種別（`【設計】` `【実装】` `【テスト】`）と同じ併記/分割の
基準（上記「人間の合意を1回で取るか、フェーズごとに分けて取るか」）に従う。

- **囲み文字は全角の `【】` を使う**（ASCIIの `[]` は使わない）。`[]` はbashのglobで**文字クラス**
  として解釈されるため、`plans/[調査]*.md` のようなパターンが意図どおりマッチしない。全角の
  `【】` はglob特殊文字ではないため、`plans/【調査】*.md` と未クォートで書いても正しくマッチする。
- **下位の個別計画（調査・作業・反映）は `plans/【*.md` で機械的に列挙できる**。逆に、それに一致しないものが
  全体作業計画である。flow-id 1-4 で「既に全体作業計画があるか」を判定する際にこの区別を使う。
- 日本語を含むパスをgitの出力から扱う場合は `-c core.quotepath=false` が必要
  （既定では8進エスケープされる。実装例: `Provider.sh` の `get_branch_work_files`）。

**flow-id 1-4 の判定**: `get_branch_work_files` でブランチ固有のplansファイルを列挙し、
`【` で始まらないものが既にあれば、それが全体作業計画である。その場合は**planツールで新しい
計画ファイルを作らず**、既存を読んで次のステップへ進む。`.claude/settings.json` の
`"defaultMode": "plan"` により新セッションは必ずPlanモードで始まるが、それは新規作成の理由に
ならない（作ると全体作業計画がセッションごとに増えてしまう）。

セッションのcompactは任意のタイミングで行ってよく、特定のflow-idには割り当てない（コンテキストが
大きくなってきたと感じたタイミングで、人間の判断で `/compact` を実行すればよい）。
**そのタイミングを塞がないよう、レビュー依頼のターンでは `AskUserQuestion` を使わない**
（`references/review-loop.md`「レビュー依頼メッセージ」節）。

**`start` から着手する場合を除き、このセッションでこのフローのサブコマンドを初めて使う前には、
必ず先に `resume` を実行して「今どこにいるか」を特定する。** `git branch --show-current` 等で
ブランチ名やissue番号が判明していることは、`resume` を省略してよい理由にはならない。`resume` の
目的はブランチ名の特定ではなく、PR/MRの状態・未解決コメント件数・plan/worklogファイル・
HANDOFF.mdとの矛盾など、ブランチ名だけでは分からない「このセッションでまだ確認していない現在地
情報」を集約することにある。
**flow-idが1つ進むごとに、必ず`HANDOFF.md`を更新する**。進捗表の記号更新は
`.claude/scripts/src/update-handoff-progress.sh`（`mark-done <flow-id>`でその行を、ループ扱いの
flow-idなら同じループ範囲の全行をまとめて`[x]`にする。フェーズ・ループ範囲を丸ごと省略する場合は
`mark-skip <flow-id...>`で`[-]`にする。**`mark-skip`はループ範囲へ伝播しないので、範囲内の全
flow-idを渡す**。一部だけ渡すとその場でエラーになり1件も書き換わらない（issue #140）。詳細・制約は
`.claude/docs/spec/update-handoff-progress.md`参照）へ委譲し、それに続けて「やったこと」
「次にやること」を書き換える。更新はcommit（flow-id
2-2/2-7/3-2/3-7/4-2/4-7/5-4/5-6）より前に行い、**同じcommitに含める**（別commitに分けると、レビュー
時点の進捗表と実際の変更内容が食い違う）。

**ただし、ループ範囲に属するflow-idでは記号を動かす条件が違う**（issue #64で実際に踏んだ。作業を
終えた時点で`mark-done 4-6`を呼び、まだcommitもレビューもしていない4-7〜4-9まで`[x]`になった）。
ループ範囲は`2-3 2-4` / `2-6`〜`2-9` / `3-3 3-4` / `3-6`〜`3-9` / `4-3 4-4` / `4-6`〜`4-9`の6つ。

- **`mark-done`を呼ぶのは、レビュー合意まで進んで1周が完了した時点だけ**にする。範囲内の途中の
  flow-id（作業が終わった直後・リモートへ反映した直後など）では進捗記号を動かさず、「やったこと」の
  文章だけを更新する。`mark-done`はループ範囲の全行をまとめて`[x]`にするため、途中で呼ぶと
  「人間のレビューが済んでいる」という誤った状態が表に残る。
- **「1周が完了した」の条件は2つある**（issue #70）。(1) そのループのレビュー指摘を成果物へ
  反映したこと。(2) **返信が1件も付いていないスレッドが無いこと**（`references/review-loop.md`
  「レビュー完了合図の確認」）。**ループ範囲への`mark-done`は、ヘッダの`- 未返信スレッド:`が`0`でなければ
  （行が無い場合も）拒否する。** 拒否されたら、値を書き換えるのではなく`comments all`で
  取り直して返信する（値は結果であって、通すための入力ではない）。
- **ループ範囲へ「初めて」入るときは`set-header --loop '<範囲> の1周目（進行中）'`を使う。**
  そのループ範囲の進捗列はまだ`[]`のため、`add-round`は「前回の往復が未完了の可能性」として
  拒否する（issue #127で実際に踏んだ）。**`add-round`は2周目以降へ進めるためのコマンドであり、
  1周目を開始するためのものではない。**
- **2周目以降に入るときは、作業を始める前に`add-round <flow-id>`を呼ぶ。** 周回数が1つ進み、
  範囲の記号が`[]`へ戻る。
- 単発ステップ（1-4・2-5・3-1・4-1・4-10など）は従来どおり、そのステップを終えるたびに
  `mark-done`を呼んでよい。
- **`set-header`は失敗しうる。** 指定した項目のヘッダ行がちょうど1件見つからないと、ファイルを
  書き戻さずに非0で終了する（issue #66）。その場合は`HANDOFF.md`の`## フロー進捗状況`見出しの
  直下へ、`- issue:` / `- ブランチ:` / `- PR:` / `- push回数:` / `- 現在のループ:` /
  `- 未返信スレッド:` / `- 追従監視:`
  の7行をこの順で置いてから再実行する（`- Draft PR:`のような別名は使わない）。表記の定義は
  `.claude/docs/spec/update-handoff-progress.md`「HANDOFF.mdのヘッダ行」が正。flow-id 5-5の
  `cleanup-task.sh`を経たHANDOFF.mdには雛形として7行が入っているため、通常この失敗は起きない。
- **今が何周目かは、`HANDOFF.md`ヘッダの`- 現在のループ:`行を読む**（例:
  `- 現在のループ: 3-6〜3-9 の3周目（進行中）`。issue #58）。**進捗表には周回数が入っていない**
  ので、記号を数えて何周目かを判断しようとしないこと。表の記号はどの行も常に1つで、レビュー往復が
  何回あっても増えない。この行は`add-round`／ループ範囲への`mark-done`が更新するため手で書き換えず、
  **表から決まらない値を入れるときだけ**`set-header --loop <text>`を使う（上記の1周目の開始と、
  ループ範囲の外へ出たときの`'なし'`の2つ）。

## issueが大きすぎる場合の分割提案（issue #64）

1 issue = 1ブランチ = 1 MR がこのフローの単位である。**同型の成果物が並列に列挙された大きな
issue**をそのまま進めると、MRがレビュー可能な粒度を超え、フェーズ3以降でスコープが膨らんでも
軌道修正の契機が無くなる（実例: issue #24対応で、スコープ外としていた範囲を後から取り込むことに
なり全面書き直しが発生した。`.claude/docs/ddr/i0000-10-dev-toolsをAI専用_人間専用に分離する.md`）。
AIエージェントは以下の基準で**分割を提案する**。**判断そのものは人間が行う**。

**主トリガー: 並列列挙構造**

issue本文・受け入れ条件が「AとBとCを作る」という**同じ種類の成果物の並び**になっている場合に
提案する。典型例は次のとおり。

- 画面・機能
- APIエンドポイント
- CLIサブコマンド
- バッチジョブ
- テーブル・マイグレーション
- 外部連携先

判定は次の一問に集約する。**「各項目が単独でマージされても、システムが壊れないか」**。
壊れないなら分割候補であり、壊れるなら次の「分割しない条件」に該当する。行数・受け入れ条件の
個数のような量的な尺度では判定しない（量が多くても不可分なissueはあり、少なくても独立した
成果物が並んでいることはあるため）。

**分割しない条件（誤爆防止）**

次のいずれかに該当する場合は分割を提案しない。

- **横断的変更**: 共通の型定義・スキーマ・認証基盤など、**同時に変えないと壊れるもの**。
  項目が並んで見えても単独でマージできないため、分割の対象ではない。
- **分割コストが本体を上回る**: 1件あたりが極小の場合。このフローはissue 1件につき
  **5フェーズ43ステップ**とレビュー往復という固定費がかかるため、分割すると本体の作業量より
  手続きのほうが大きくなることがある。
- **共通部分の先行実装が必要**: この場合は均等に割らず、**「基盤issue → 機能ごとのissue」**と
  いう依存順に割る（分割はするが、割り方が変わる）。

**issue分割と個別計画ファイル分割の切り分け**

「分ける」には2つの層がある。どちらを使うかは**マージの単位を分けたいかどうか**で決まる。

| やりたいこと | 使うもの |
|---|---|
| 各項目を**別々にマージ**したい（リリース単位・切り戻し単位を分けたい） | **issue分割**（本節） |
| 1つのMRでまとめてマージし、**レビューだけ分けたい** | **個別計画ファイルの分割**（上記「計画の2階層構造」） |

**判定タイミング**

- **主: flow-id 1-4**（全体作業計画の作成前）。issue全体を読み込む最初の機会であり、まだ
  ブランチ・Draft MRが1本しか無いため、割り直しの手戻りが最も小さい。
- **副: flow-id 1-1**（`issue-create` スキルでの起票時）。並列列挙構造は本文だけで検出できる
  ため、起票前に気づければブランチすら作らずに済む（手順:
  `.claude/skills/issue-create/SKILL.md`）。
- **フェーズ2で規模が判明した場合**: 調査（flow-id 2-6）で初めて規模が分かったときは、着手済みの
  範囲を現issueに残し、**未着手の範囲を新しいissueへ切り出す**ことを提案する。

**決定は人間が行う**

AIエージェントは**兆候と分割案を提示するに留める**。勝手に子issueを起票したり、スコープを削って
進めたりしない。提示は `AskUserQuestion` で行い、選択肢には最低限「分割する」「このまま1件で
進める」を含める。分割しない判断がされた場合は、その理由を全体作業計画と `HANDOFF.md` に残す
（同じ議論を後から蒸し返さないため）。

**分割することになった場合**

- **元issueは親として残し**、子issueへのリンクをチェックリスト（`- [ ] #NN`）で束ねる
  （元issueを閉じて作り直すと、議論の経緯が追えなくなるため）。
- 子issueの起票には `issue-create` スキルを使う。
- **共通部分を含む1件目を先に完了**させてから残りに着手する。並走させると共通部分がコンフリクト
  しやすく、DDR識別子の重複（`references/base-branch-followup.md`「defaultブランチとのコンフリクト検知・解消」）も起きやすい。

## AIアセット反映の対象の洗い出し（issue #155）

flow-id 4-1 で「反映対象を洗い出す」とき、**AIアセット**（AIが読む・従うもの）について何をどこまで
探し、どこで打ち切り、どの形で反映するかを定める。flow-id 4-6 の**AIアセット反映**は、ここで
洗い出した結果に対して行う。

**対象は作業の副産物に限る。** そのissueの**主たる成果物**としてアセットを作る場合は
`【AIアセット作成】`（フェーズ3）で扱う（上記「計画の2階層構造」の種別の使い分け）。

### 手順1: 起点の列挙

**今回の作業のうち既存のアセットで対応できなかったもの**を列挙する。入力は次の3つで、
flow-id 4-1 の行が言う「作業結果と `plans/` `worklog/` の内容」と範囲を揃える。

| 入力 | どこを見るか |
|---|---|
| `worklog/` | 「試したこと」「ダメだったこと」「学び」 |
| `reports/`（このissueの調査結果・作業結果） | 「想定と異なった点」「確かめられなかったこと」「残課題」 |
| MRのレビューコメント | 指摘の内容と、それに対して何を直したか（**このリポジトリではレビュー往復が主要な発見源である**） |

- **過去のMRを遡らない**（探索コストが件数に比例して増える一方、今回の作業から得られる知見は
  上の3つに出揃っているため）。
- **`worklog/` が空・未作成の回を、そのまま「0件」と扱わない。** 記録が無いのか、記録した結果
  本当に無いのかを区別できないためである。まず記録の有無を確認し、無ければ `reports/` と
  レビューコメントだけで列挙する。

### 手順2: 4類型への分類

列挙した各項目を次の4類型のいずれかへ分類する。**どれにも当たらないものは反映対象ではない。**

| 類型 | 意味 | 反映の向き | 再現性の証拠を要求するか |
|---|---|---|---|
| (a) | 該当するアセットが**無かった** | 新規作成 | **要求する**（手順3へ進む） |
| (b) | アセットは**あったが誤っていた** | 訂正 | しない（1回でも直す） |
| (c) | アセットはあったが、**その罠が書かれていなかった** | 追記 | しない（同上） |
| (d) | アセットはあったのに、**辿り着けなかった** | 導線の改善（参照・キーワード・配置） | しない（同上） |

**再現性の証拠を要求するのは (a) だけである。** (b)(c)(d) は既存アセットの誤り・欠落・導線の
問題であり、1回でも起きたなら直す価値がある。(a) だけは「1回きりの事故に対してアセットを
増やす」ことになりかねない。

**「該当するアセット」はファイル単位ではなく記述単位で見る。** そのトピックのファイルが存在する
ことは (c) の根拠にならない——**その罠・その型を扱った記述**があるかで判定する。ファイル単位で
見ると近いファイルが必ず1つは見つかるため、**(a) が原理的に発生しなくなり、手順3が恒久的に
迂回される**（issue #155 の初回適用で実際に指摘された）。

**分類結果が0件なら、AIアセットについては反映するものが無い。** フェーズ4のスキップ判定
（上記「全体作業計画に必ず含めるフェーズ」）は、この手順2までを実施した結果で行う
（**spec/ddr・実装コード/テストコードの判定は別に必要**であり、この手順が代替するものではない）。

**スキップする場合は、実施した事実を `HANDOFF.md` の「やったこと」へ残す。** スキップすると
個別反映計画も `reports/` も作られないため、書かなければ**洗い出しをやっていない回と、やって
0件だった回が外形上区別できない**（issue #155 が解こうとしている反映漏れは、まさにこの経路で
起きる）。最低限、次の2つを書く。

- 手順1で列挙した件数（0件ならその旨）
- 手順2で「どれにも当たらない」と判断した根拠

### 手順3: 痕跡の確認と打ち切り

**確かめることは2つあり、対象が違う。** 混同すると判定を誤る。

| 確かめること | 何を意味するか | 対象 | 見つかったときの帰結 |
|---|---|---|---|
| **再現性** | 同じ罠を今回2回以上踏んだか | **(a) のみ** | (a) として反映してよい（1回きりの事故ではない） |
| **痕跡** | 既存アセットに同じ罠が書かれているか | **(a) と (c) の両方** | **(a)/(c) ではなく (d) である**（あったのに辿り着けなかった） |

**痕跡の確認を (c) にも要求するのは、(c)「アセットはあったが、その罠が書かれていなかった」と
判定するには「その罠を扱った記述が本当に無いこと」を確かめる必要があり、それが (a) の痕跡探索と
まったく同じ作業だからである。** 探さずに (c) と決めると、既にある記述の隣へ同じことを書き足す
形になる（issue #155 の初回適用で実際に踏んだ。ルート `REVIEW-POINTS.md` に同じ罠があるのに
`plans/REVIEW-POINTS.md` へ追記しようとした）。

**再現性が確かめられても (a) は確定しない。** **同じMR内で同じ罠を2回踏むのは、むしろ既存記述に
辿り着けていない (d) の状況でこそ起きやすい**ためである。

段階は次の3つで、**安い側から順に見る**。

| 段階 | 何を見るか | 見つかった場合 | 見つからなかった場合 |
|---|---|---|---|
| 1 | **同一MR内**（`worklog/` の他の項目・`reports/`・同じPRの他のコミット） | **再現性あり**と確定。以降、再現性の確認は行わない（**痕跡の確認は段階2へ進む**） | 再現性なし。**(a) はこの時点では反映しない**と決めてよい（(c) は段階2へ進む） |
| 2 | **`doc-search`（frontmatter）＋ `grep`（本文）** | **(d) として確定**し、打ち切る（導線を直す） | 段階3へ進む |
| 3 | **直近10件のマージ済みPR＋ `.claude/docs/README.md` のDDR一覧** | **(d) として確定**し、打ち切る | **痕跡なしとして確定**し、(a) のまま反映する。**それ以上は遡らない** |

段階2は**2段で判定する**。`doc-search`（`.claude/skills/doc-search/SKILL.md`、実体は
`search-frontmatter.sh`）は**frontmatterのキーしか見ない**ため、`matched=0` 単独では
「本文には書いてあるのに気づかない」形の偽陰性を出す。

```bash
bash .claude/scripts/src/search-frontmatter.sh --text '<罠を表す語>' --type ddr --format count
grep -rn '<罠を表す語>' .claude/docs .claude/rules
```

- **`matched=0` かつ `grep` も0件**のときだけ段階3へ進む。片方だけで打ち切ると、
  **この手順が減らそうとしている (d)「あったのに辿り着けなかった」を手順自身が生む**。
- **DDRを証拠に使うときは `status` を確認する。** `--format detail` は
  `status` / `superseded_by` / `note` / `resource` を出力しないため、`--format jsonl` か
  ファイル本体で見る（後続のDDRに置き換えられた決定を現役の根拠として引かないため。
  `.claude/rules/markdown-frontmatter.md`「DDRのstatus」）。

段階3で見るのは**マージ済みPRのコミット一覧**である。flow-id 5-5 で `plans/` `worklog/` `reports/` を
削除してからsquash mergeするため、**過去MRの一次資料はdefaultブランチに残らない**（`git log` で
探しても見つからないのはこのためで、「痕跡なし」の根拠にはならない）。`gh pr list --state merged
--limit 10` 相当（CLI不在時は `mcp__github__list_pull_requests`）でPRを引き、タイトルと
descriptionを見る。**10件で打ち切る**のは、それ以上遡っても得られるものが探索コストに見合わない
ためである。

- 痕跡が見つからず、かつ「次に同じ状況に置かれたAIが同じ失敗をする」と言えないなら、反映しない。

### 手順4: 反映先の形態の決定

**2軸で選ぶ**——「いつ効いてほしいか」と「守らせ方の強さ」。複数選んでもよい。
定義はここで再掲せず、**参照先を種類で分ける**。

| 何を知りたいか | 正 |
|---|---|
| **ディレクトリ**の役割 | `index.md`（Repository Map） |
| **ファイル**（`CLAUDE.md` / `AGENTS.md` / `GEMINI.md` / `REVIEW-POINTS.md`）の役割 | `.claude/rules/directory-structure.md`・`.claude/rules/docs-workflow.md` |
| 置き場のルール・ツリー構造 | `.claude/rules/directory-structure.md` |

| 反映先 | いつ効くか | 守らせ方の強さ |
|---|---|---|
| `AGENTS.md` | セッション開始時（常時読込。**Claude Code・Gemini CLI の両方に効く**） | 読ませる |
| `CLAUDE.md` / `GEMINI.md` | 同上（**そのエージェントにだけ効く**） | 読ませる |
| `.claude/rules/` | 同上（分量があるものをここへ切り出し、`AGENTS.md` から参照する） | 読ませる |
| `**/REVIEW-POINTS.md` | レビュー時（そのディレクトリに触れたとき） | 読ませる（レビュー時に限定） |
| `.claude/skills/` | その作業をするとき（スキルの呼び出し時） | 手順化する |
| `.claude/agents/` | サブエージェントに委譲するとき | 手順化する |
| `.claude/scripts/` | AIが能動的に実行したとき | 手順化する（実行結果で分かる） |
| `.claude/hooks/` | セッション開始時・特定のツール呼び出しのたび（いずれも自動） | **検証で落とす** |

**共通のルールを `CLAUDE.md` へ書かない。** `CLAUDE.md` と `GEMINI.md` はいずれも `AGENTS.md` を
取り込むだけのエージェント固有ルールの置き場であり、**`CLAUDE.md` へ書いた内容は Gemini CLI 経路
では一切読まれない**。両方に効かせたいなら `AGENTS.md`（分量があれば `.claude/rules/` へ切り出す）
が正しい。

- **反映先の形態によらず、種別は `【AIアセット反映】` である。** `.claude/scripts/`
  `.claude/hooks/` を選んだ場合も同じで、**単体テストを伴うならテストの追加・更新も同じ計画へ
  含める**（種別が形態ごとに分岐すると、1回の洗い出しの結果が2つの個別計画へ割れる）。
- **`【実装反映】` との判別は、反映先ではなく「どこから来た項目か」で行う**（issue #110 が置いた
  境界を、反映先で分けない形に言い直したもの）。**この洗い出し手順の手順1が拾った項目**は
  `【AIアセット反映】`、**フェーズ3のレビュー往復で解消しきれず持ち越した不具合**は
  `【実装反映】` である。同じ `.claude/scripts/` 配下のファイルを触る場合でも、この判別は変わらない。
- **常時読込のアセットを増やすことにはコストがある。** 毎セッションのコンテキストを消費するため、
  「そのときだけ効けばよい」知見は `skills` 側・`REVIEW-POINTS.md` 側へ寄せる。
- **削除・統合も反映である。** 誤った記述の訂正 (b) は、書き足すのではなく**消す**ことが正しい
  場合がある。重複した記述を1箇所へ寄せる (d) も同じ。
- **削除・統合を含めた回は、配布先に旧アセットが残る。** `install-to-project.sh` は上流で
  削除・改名されたファイルを**一覧で提示するだけで、配布先からは削除しない**（消すかどうかは
  配布先の人間の判断に委ねる。仕様: `.claude/docs/spec/asset-distribution.md`）。
  `.claude/VERSION` の扱いは `.claude/docs/spec/distribution-assets.md`「人間の判断で据え置く
  ことがある」に従って判断する。**版を上げても配布先の旧アセットは消えない**ことを承知して選ぶ。
