# 新しい機能開発を始める

## どんな場面か

新しい機能を追加したい、既存の動作を変えたい、リファクタリングしたい——「やりたいこと」は
決まっているが、まだissueが無い（またはissueはあるが着手していない）場面。誤字修正のような
ごく小さな変更を除き、このリポジトリのタスクはすべてissueを起点に進める（判定基準は
`AGENTS.md`）。

## 使う機能と流れの概要

起点は2つの機能で、間にセッションの切れ目を挟む。

- **issueの起票**は `issue-create` スキルで行う。目的・現状・期待する動作・受け入れ条件の
  4見出しを持つテンプレートに沿って、AIが起票を代行できる。起票しただけでは着手の指示には
  ならず、AIの側から着手を持ちかけることもしない。
- **着手**は原則として新しいセッションで `/issue-mr-flow start` から入る（ユーザーが明示的に
  指示したときに限り、起票と同じセッションで続けて進めてよい）。featureブランチとDraft PR/MRが
  作られ、全体作業計画（Planモード）→人間の合意→調査→作業→反映→クローズという
  5フェーズ43ステップのフローに乗る。
- フローの途中のコミットはすべて `commit` スキル経由で行われ、調査・作業の結果は
  `wip/reports/` のmdと視覚化HTML（関連・依存が主題なら `canvas-report` スキルのcanvas形式）で
  レビューへ出てくる。
- **pushの前には、そのpushで済ませるべき5項目（worklogの追記・`HANDOFF.md` の更新・
  `index.jsonl` の最新化・md/htmlの同期・`commit` スキル経由でのコミット）をチェックリストへ
  記録し、同じコミットへ含める。** 未完了のままpushしようとするとhookがブロックする。
  チェックリストはGit管理下にあるため、**自己申告の内容がPRのdiffでレビューできる**。

## 何が得られるか

- レビュー可能な粒度のissue・ブランチ・Draft PR/MRが揃い、計画への合意を経てから実装が始まる。
- 計画・試行錯誤・結果が `wip/plans/` `wip/worklogs/` `wip/reports/` に分離して残り、マージ後は
  spec/DDRだけが正史として残る。
- issueが大きすぎる場合は、着手前に分割の提案を受けられる。
