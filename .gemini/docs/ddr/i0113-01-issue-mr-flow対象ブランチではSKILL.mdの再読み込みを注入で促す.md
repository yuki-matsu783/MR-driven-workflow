# i0113-01. issue-mr-flow対象ブランチではSKILL.mdの再読み込みを注入で促す

issue #113。

## 背景

`.claude/skills/issue-mr-flow/SKILL.md` はこのリポジトリの**唯一の実装フロー定義**であり、
1,100行を超える。compact（自動・手動どちらも）は要約内容を指定できないため、AIエージェントが
この手順理解を要約で失ったまま作業を続け、レビュー往復・`commit` スキル経由の強制・
`HANDOFF.md` の進捗更新といったフローの手順を踏み外す事故が起こりうる。

DDR i0057-01 で SessionStart hook の matcher へ `compact` を加え、`HANDOFF.md` の「次にやること」節・
ブランチ固有の作業ファイル一覧・issue/PR情報を再注入するようにした。しかしこれらは
**「現在地」の再注入**であって、**「手順そのもの」を読み直させる指示ではない**。現在地だけが
戻っても、手順を要約で失っていれば同じ事故が起きる。

しかも、この失敗はエージェント側から見えない。SKILL.mdを読んだ事実は会話履歴に残っているため、
要約後のエージェントは「もう読んだ」と認識したまま、細部を失った理解で作業を進める
（DDR i0057-01が注入量の切り詰めを却下した理由と同じ失敗モードである）。

## 決定

### 1. 注入テキストの末尾へ「SKILL.mdを読み直すこと」の指示を足す

`build_work_context` が組み立てるローカル情報の**最後**に、次の内容を持つ節を足す。

- 読み直す対象のパス（`.claude/skills/issue-mr-flow/SKILL.md`）を明示する。
- **「このセッションで既に読んでいる場合も読み直すこと」を明示する。** 上記のとおり、
  「もう読んだ」という認識自体が要約後には信用できないため、これが指示文の要点である。
- なぜ読み直すのか（compactの要約で手順が失われうること）と、失われると何を踏み外すのか
  （レビュー往復・`commit` スキル経由の強制・`HANDOFF.md` の進捗更新）を1文で添える。

**末尾に置く**のは、この指示が「読んだあと何をするか」ではなく「作業を再開する**前に**すること」
であり、注入テキストの最後にあるほうがcompact直後のエージェントの目に留まりやすいためである。

**この追加は起動要因（startup/resume/clear/compact）で分岐させない。** DDR i0057-01 が
「起動要因ごとに注入内容を変えると、検証すべき組み合わせが増える」として全要因で同じ内容を
注入すると決めたのに従う。`compact` 以外の要因でも、SKILL.mdを読み直させて困ることは無い。

### 2. 対象ブランチの判定は「ブランチ名のissue命名規則一致」と「ブランチ固有の作業ファイル」の2材料で行う

| 判定材料 | 取得元 | 成り立つ場面 |
|---|---|---|
| ブランチ名から**issue番号を抽出できる** | `get_issue_number_from_branch`（`branchPrefixTemplate` と照合） | 命名規則どおりの `feature-<issue番号>-<slug>` ブランチ。flow-id 1-3 直後（plans/ をまだ作っていない段階）でも成り立つ |
| **ブランチ固有の作業ファイル**（`plans/` `worklog/` `reports/`）がある | `get_branch_work_files`（`build_work_context` が既に取得済み） | ブランチ名が命名規則から外れている場合。例: Claude Code on the web が自動生成する `claude/<slug>` 形式のブランチ |

**どちらか一方でも成り立てば対象**とする。片方だけでは、上表のとおりそれぞれ取りこぼしがある。

この2つに絞ったのは、どちらも「issue起点でフローに乗せた」ことの直接の痕跡であり、かつ
**hookから追加コストなしに得られる**ためである（前者はブランチ名の文字列照合だけ、後者は
`build_work_context` が既に取得している値の再利用で、`git`・`jq` の起動回数は1回も増えない）。

対象外と判定した場合は**何も足さない**。issue-mr-flowに乗せていない軽微な変更を直接進めている
ブランチに、フローの手順を読ませる指示は不要である（`main` ブランチ上ではそもそも
`build_context` が exit 2 で何も注入しないため、この判定より手前で除外される）。

### 3. 判定根拠を指示文へ埋め込む

「なぜこのブランチが対象と判定されたか」を指示文の中に書く（例:
`判定根拠: ブランチ名がissue命名規則に一致（issue #113）`）。誤判定が起きたときに、
エージェント・人間のどちらから見ても原因が一目で分かるようにするため。両方の材料が成り立つ
場合は両方を並べる。

### 4. DDR i0057-01 の設計方針と矛盾させない

- **切り詰めない**: 指示文の長さは有界で、入力サイズに依存しない（実測603バイト。判定根拠が
  2件そろう場合でも690バイト）。しきい値 `CONTEXT_SIZE_WARN_BYTES`（既定8000バイト）に対して
  十分小さく、この追加だけで肥大化検知が発火することはない。単体テストで「1000バイト未満」を
  固定した。
- **ファイルの中身は注入しない**: 注入するのは「SKILL.mdを読め」という指示であって、
  SKILL.mdの中身ではない。1,100行を毎セッション・毎compactで注入する案は下記のとおり却下した。
- **fail-open**: 判定材料の取得に失敗しても、指示行を出さずに他の項目の注入を続ける
  （`build_work_context` の既存方針を踏襲）。

## 却下した案

- **SKILL.mdの中身（または要約）を注入する**。読み直させる確実さでは上回るが、1,100行を毎回
  支払うことになり、DDR i0057-01 が `HANDOFF.md` 全文の注入を却下したのと同じ理由で過大である。
  さらに要約を注入する場合は「注入用の要約」を本体と二重管理することになり、両者がずれたときに
  **誤った手順を正史として注入する**という、何もしないより悪い状態を作る。
- **ブランチによらず常に注入する（判定を持たない）**。実装は最も単純だが、issue-mr-flowに
  乗せていないブランチ（軽微な変更を直接進めている場合）にまでフローの手順を読ませることになる。
  受け入れ条件の「対象外では既存の挙動を壊さない」に反する。
- **判定を `HANDOFF.md` の進捗表の有無で行う**。フローに乗っていることの証としては
  ブランチ名・作業ファイルより直接的だが、`HANDOFF.md` はリセット直後（flow-id 5-3 の直後）や
  ブランチ作成直後には空であり、**フローの最初と最後で取りこぼす**。また表の書式の変更に判定が
  引きずられる。上記2の2材料はどちらも書式に依存しない。
- **`compact` のときだけ注入する**。動機（compactでの手順喪失）には最も忠実だが、DDR i0057-01 の
  「起動要因ごとに内容を分岐させない」方針に反する。分岐させても節約できるのは他要因での
  約600バイトに過ぎない。
- **`PreCompact` hookで手順を残す**。DDR i0057-01 で確認済みのとおり `additionalContext` を
  サポートせず、標準出力もコンテキストへ注入されないため、この用途には使えない。
- **`AGENTS.md`／`CLAUDE.md` に「compact後はSKILL.mdを読み直す」と書くだけにする**。これらは
  セッション開始時に読み込まれるが、**compactの要約対象に入る**ため、失われうる点はSKILL.md
  自身と変わらない。hookによる注入は要約の外から毎回入るという点に価値がある。
