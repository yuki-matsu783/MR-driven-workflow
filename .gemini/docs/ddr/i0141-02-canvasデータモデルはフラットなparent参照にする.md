# i0141-02. canvasデータモデルはフラットなparent参照にする

issue #141（canvas-reportテンプレートのCode Canvas形式への全面刷新）での決定。

## 決定

`CANVAS_DATA.nodes` は**フラットな1つの配列**とし、メンバは `parent: <クラスid>` の参照で
表現する（クラスの中に `members: [...]` をネストさせない）。エンジンがparentチェーンを検証し、
未定義parent・循環・階層の深さ超過（レイヤ > クラス > メンバ の3層まで）を画面上の赤字パネルへ
列挙する。

## 背景

- issue #141の受け入れ条件に「**循環する親子関係**を含むデータを与えると、画面上にエラーが
  表示される」がある。ネスト記法では循環が**原理的に書けない**ため、この受け入れ条件が
  データ表現として成立しない。バリデーションは「起こりうる誤りを検出して見せる」ものであり、
  誤りを表現できない形式では「黙って壊れない」という設計目標（生成AIが書き間違えたときに
  気づける）も達成できない。
- 生成側（AIエージェント・bashスクリプト）にとって、`grep`で抽出した関数一覧を1行1ノードで
  追記していくフラット形式のほうが組み立てやすい（ネストはJSONの深い位置への挿入になる）。

## 却下した案

- **ネスト記法（クラスの `members` 配列）**: 構造が自明で検証が減る利点はあるが、上記のとおり
  受け入れ条件と衝突する。また、将来「クラスの下にさらに内部クラス」を許す拡張はフラット＋
  parent参照なら深さ制限の緩和だけで済む。
- **両記法の併用（ネストも受け付けて内部でフラット化）**: 生成側の書き方が2通りになり、
  SKILL.mdの手順・エラーメッセージが分岐する。テンプレートの読み手（レビュアー）にも
  2つのデータ形を強いるため見送った。
