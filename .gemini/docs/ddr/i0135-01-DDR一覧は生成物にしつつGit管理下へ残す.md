# i0135-01. DDR一覧は生成物にしつつGit管理下へ残す

## 背景

`.claude/docs/README.md` のDDR一覧（issue #135 時点で55件）は、DDRを追加するたびに手書きで
1行足す運用だった。一覧は**ファイル末尾への追記構造**のため、2ブランチが同時にDDRを追加すると
毎回テキストコンフリクトする（`resolve-conflict` の類型C）。解消はAIが一覧全体を読み直して
両方の行を残し番号順へ並べ直す手作業になり、そのつど出力トークンを消費していた。

一覧の内容はDDRのfrontmatterから機械生成できる。リンクテキストはファイル名そのものであり、
注記も `status` / `superseded_by` に入っている（例外は後述）。

## 決定

1. `.claude/scripts/src/generate-ddr-list.sh` で一覧を生成する。
2. **生成結果はGit管理下に置きコミットする**（`.gitignore` に加えない）。
3. 生成先は**README内をマーカーで囲んだ一区間**とし、別ファイルへは分離しない。
4. 実行は**AIエージェントの明示的な実行**とし、SessionStart hook等で自動化しない。
5. frontmatterから導けない散文の注記は、DDRのfrontmatterへ **`note` キー**を新設して持たせる。

## 理由

### なぜ生成物なのにGit管理下へ残すのか

前例の `index.jsonl` は生成物としてGit管理外にしている（DDR 0025）。DDR一覧を同じ扱いにすると
次の3つが壊れる。

- **GitHub上で人間が開く目次である。** Git管理外にするとブラウザで見えない。
- **clone直後に存在しない。** SessionStart hookが走るまで空になる。
- **Claude CodeのGrepツール（ripgrep）は既定で `.gitignore` を尊重する**ため、全文探索から
  消える（実測確認済み）。

`index.jsonl` がGit管理外でよいのは、**人間が直接読まない機械可読の中間生成物**だからであり、
「生成物だからGit管理外」という一般則ではない。ここが両者の分かれ目である。

Git管理下に置くことで「生成物なのにコミットされる」冗長さは残るが、コンフリクト時に
**統合せず片側を捨てて再生成すればよい**（類型B相当）ため、手書き時代の問題は解消する。

### なぜREADME内のマーカー区間か

別ファイルへ分離してREADMEからリンクする案もあったが、**目次を開く手数が1つ増える**。
DDR一覧はREADMEの主要な中身の1つであり、リンク先へ飛ばないと一覧が見えない構成は目次として
後退する。マーカー方式なら、READMEの他の節（由来の注記・spec一覧・欠番の説明）を手書きのまま
残せる。

マーカーが片方でも無ければ**エラーで停止し、区間を推測しない**。見出しの位置や前後の地の文が
変わったときに、一覧と無関係な行を巻き込んで消さないため。

### なぜ自動生成しないのか

出力がGit管理下にあるため、SessionStart hookで自動生成すると**無関係な差分が勝手に
ワーキングツリーへ現れる**（コミットするつもりのない変更が `git status` に出続ける）。
`index.jsonl` を毎セッション自動生成できるのはGit管理外だからであり、この違いがそのまま
自動化の可否を分ける。実行忘れは `--check`（終了コード2）で検出できる。

### なぜ `note` キーを新設したのか

issueは「唯一の注記は0009の `status: superseded`」と書いていたが、実際には
**frontmatterから導けない散文の注記が2件あった**（0022・0048）。これらはREADMEにしか無い情報で、
そのまま生成へ移すと**情報が消える**。

- サイドカーファイル（一覧の注記だけを別ファイルで持つ）は、DDRと注記が離れて同期の手間が
  戻るうえ、そのファイル自体が再びコンフリクトの発生源になる。
- 注記を捨てる案は情報欠落であり、採らない。

DDRは**本文は不変だがfrontmatterは後から更新してよい**運用（`.claude/rules/markdown-frontmatter.md`）
のため、`note` は本文不変の原則と衝突しない。注記の置き場がDDR本体になることで、DDRを読む人が
一覧を見なくても補足に気づける利点もある。

## 却下した案

| 案 | 却下理由 |
|---|---|
| 生成物としてGit管理外にする（`index.jsonl` と同じ扱い） | GitHubで見えない・clone直後に無い・ripgrepの探索から消える |
| 一覧を別ファイルへ分離しREADMEからリンクする | 目次を開く手数が増え、目次としての機能が後退する |
| 手書きを維持し、解消手順（`resolve-conflict`）だけ改善する | コンフリクトの発生自体は残り、毎回の手書き更新とトークン消費も残る |
| SessionStart hookで自動生成する | Git管理下の出力が勝手に変わり、意図しない差分が常時ワーキングツリーへ出る |
| 散文の注記をサイドカーファイルで持つ | DDRと注記が離れて同期が必要になり、そのファイルが新たなコンフリクト源になる |
| 散文の注記を捨てる | 情報欠落。0022・0048の補足はREADMEにしか無かった |

## 影響

- DDRを追加したら `bash .claude/scripts/src/generate-ddr-list.sh` を実行し、出た差分をコミットする
  （`.claude/rules/docs-workflow.md`）。
- DDR一覧のコンフリクトは統合せず再生成で解消してよい
  （`.claude/skills/resolve-conflict/SKILL.md` 類型B）。
- 仕様は `.claude/docs/spec/generate-ddr-list.md`。

## 補足（実装時に判明したこと）

- **ファイル名に空白を含むDDRのリンクは、それまで壊れていた。** CommonMark（GitHubのcmark-gfm）は
  `<>` で囲まない限りリンク先に空白を含められず、リンクとして解釈されない。
  `0009-Planモードre-entry時はgit checkout復元でなくarchiveスクリプトで対処する.md` は
  「git checkout」の空白を含むため、手書き時代のREADMEでは地の文として表示されていた（実測確認）。
  生成側で `<>` を付けるようにしたため、この1行だけは手書き時代と内容が異なる。
- **awkからbashへ値を渡す区切りにタブを使ってはいけない。** bashの `read` はタブを
  IFS空白文字として扱い連続する区切りを1つへ畳むため、`status` と `superseded_by` が両方空の
  DDR（＝大多数）で `note` が `status` の位置へずれ込んだ。US（0x1f）区切りにして解決した。
- **敵対的レビュー（`adversarial-review`）で、frontmatterの読み取りに4つの取りこぼしが
  見つかった。** いずれも**エラーにならず注記だけが黙って消える／壊れる**形であり、
  実装者の自己確認では拾えなかった。値の末尾空白（`status: superseded   ` が未知statusへ落ちる）・
  行内コメント（`superseded_by: "0019"  # 理由`）・UTF-8 BOM（frontmatterを丸ごと見落とす）・
  複数行スカラー（`（|）` という注記が出る）の4件。すべて修正し、単体テストへ回帰として入れた。
  **「無言で消える」性質の欠陥は、独立コンテキストのレビューを通さないと残る**という
  DDR 0045（敵対的レビューを専任サブエージェントへ切り出す）の想定どおりの結果になった。
- **同レビューは、この決定が `resolve-conflict` スキルの「絶対ルール」（`git checkout --ours`
  で片側を丸ごと採用しない）と正面から矛盾することも指摘した。** 類型Bの手順が
  `--ours` を前提にしているためである。矛盾を放置せず、「**捨てた側を機械的に作り直せる場合に
  限る**」という例外条件を絶対ルール側へ明記し、手順を「マーカー外に差分が無いことの確認 →
  片側採用 → 再生成」の順へ書き直した。**新しい手順を足すときは、同じファイルの禁止事項が
  古くなっていないかを見る**という教訓として残す。
