# i0159-01. hookの前置フィルタは純粋関数によるバックスラッシュ除去と大文字小文字非依存比較で超集合を保つ

## 背景

`.claude/hooks/block-direct-git-commit.sh`（PreToolUse）と
`.claude/hooks/post-issue-create-notice.sh`（PostToolUse）は、`.claude/settings.json` に
`if` フィールドを持たず、対象のツール呼び出し全件（前者はBash/PowerShell、後者はさらに
`mcp__github__issue_write`）で起動する。判定本体（`command_invokes_git_subcommand` /
`is_issue_create_call`）へ辿り着く前の材料取り出し（`raw="$(cat)"` と `printf | jq` の連鎖）
だけで、空振り1回あたり `block-direct-git-commit.sh` は execve 5 / clone 10、
`post-issue-create-notice.sh` は execve 7 / clone 17 に達する（Claude Code on the web
リモート実行環境、Linux x86_64でのstrace実測、2026-08-23。`lib/`を本番と同じ相対配置に
置いた上での測定値。作業結果への敵対的レビューで、最初の測定が`lib/CommandPosition.sh`の
無い配置で行われ縮退経路の値になっていたことが発覚し、再測定した）。この値はissue #159本文が
記載するgit bash実機（Windows, MSYS）実測値（execve5/10・7/17）と数値が一致するが、Linuxと
git bashはシステムコールの構成が異なるため偶然の一致として扱い、同じ数値だからといって
両環境の絶対コストが等しいことを意味しない。git bashの外部プロセス起動は約95ms/回のため、
判定へ辿り着く前に数百msを消費している（issue #159）。

**本issueに先立ち、同種の問題を issue #70（PR #157、本DDR作成時点で未マージ）が push系hook
2本（`post-push-usage-report.sh` / `post-push-compact-prompt.sh`）で解決している。** `main()`
冒頭を `IFS= read -r -d '' raw || true` + `case "$raw" in *push*) ;; *) exit 0 ;; esac` へ
置き換えるパターンで、`read`/`case` がbash組み込みでforkしないことを利用している。本DDRは、
このパターンを本issueが変更する2本のhookへ適用する際の判断を記録する。**push系2本の実装内容
そのものは issue #70/PR #157 の責任範囲であり、本DDRはそちらを代弁しない。**

## 決定

1. **判定本体（`command_invokes_git_subcommand` / `is_issue_create_call`）は変更しない。**
   前置フィルタは高速な足切りであり、正しさの根拠は従来どおり判定本体が持つ。
2. `main()` 冒頭を `IFS= read -r -d '' raw || true` に置き換え、直後に前置フィルタ
   （`case` によるパターンマッチ）を呼ぶ。
3. **前置フィルタは `main()` 内へ直書きせず、独立した純粋関数
   （`raw_hints_at_git_commit` / `raw_hints_at_issue_create`）へ切り出す。** `is_issue_create_call`
   と同じ形にすることで、`source` してから直接呼ぶ高速な単体テストが書ける。
4. **前置フィルタの比較対象は、判定本体の正規化仕様に合わせて「バックスラッシュを除去し、
   大文字小文字を区別しない」形にする。** ただし、この関数が受け取るのはjqデコード**前**の
   生JSON文字列であるため、バックスラッシュの除去は**JSON文字列エスケープの2文字シーケンス
   （`\\` `\"` `\n` `\t` `\r` `\/` `\b` `\f`）を丸ごと除去してから、残ったバックスラッシュ
   （`\uXXXX` 等）を落とす**という形にする（バックスラッシュ1文字だけを除去すると、
   `\n`（改行のエスケープ）の`n`が単独で残るなどして超集合が壊れる——下記「なぜ単純な
   `*commit*` 部分一致では足りないのか」参照）。除去した後、ブラケット式
   （`[Cc][Oo][Mm][Mm][Ii][Tt]` 等）で大文字小文字非依存に部分一致させる。`${raw,,}` の
   ようなbash 4.0以降専用の大文字小文字変換構文は使わない。
5. `.claude/settings.json` の `if` フィールドは変更しない。

## 理由

### なぜ前置フィルタが精密判定の「超集合」でなければならないか

前置フィルタが取りこぼす（＝精密判定なら検知するはずの入力を、jqへ渡す前に `exit 0` で
落としてしまう）と、判定本体そのものが実行されなくなる。`block-direct-git-commit.sh` は
コミットを止める安全側のhookであり、取りこぼしは**ガードの無効化そのもの**になる。
`post-issue-create-notice.sh` も、起票直後の着手抑止という多重防御の1枚を無言で失う。
したがって前置フィルタの設計は「精密さ」ではなく「精密判定が拾う入力を1件も取りこぼさない
こと（超集合であること）」を最優先する。過剰検知（精密判定なら素通りする入力を前置フィルタが
誤って通過させること）は、後段のjq処理へ回るだけで実害が無いため許容する。

### なぜ単純な `*commit*` 部分一致では足りないのか（当初案の反例）

当初は `${raw,,}` で小文字化した上で `*commit*` を含むかを見る案だった。個別作業計画への
敵対的レビュー（フェーズ3、1回目）で、この案が超集合になっていない反例が実機で確認された。

`.claude/hooks/lib/CommandPosition.sh` の正規化は、`\x`（xが `[A-Za-z0-9_./-]`）という
バックスラッシュエスケープを**バックスラッシュだけ落としてxを残す**形で解決する
（`\git commit` のようにエイリアスを迂回する定番の書式を拾うための仕様）。この結果、
`git com\mit -m x` は精密判定では「commit」として検知されブロックされるが、生の文字列には
`commit` という連続した並びが存在しないため、単純な部分一致では素通りしていた。

```bash
$ source .claude/hooks/lib/CommandPosition.sh
$ command_invokes_git_subcommand 'git com\mit -m "x"' commit && echo BLOCKED
BLOCKED
$ case "$(echo 'git com\mit -m "x"' | tr 'A-Z' 'a-z')" in *commit*) echo pass;; *) echo FILTERED;; esac
FILTERED   # 超集合が壊れている
```

対策として、比較前に `${raw//\\/}` でバックスラッシュを一括除去する。この除去は
「マッチする可能性のある文字列を増やす」方向にしか働かない（除去によって既存の `commit` という
並びが壊れることはない）ため、超集合であることを損なわない。

### なぜバックスラッシュ1文字だけの除去でも足りないのか（JSONエンコード層の反例）

上記の対策（バックスラッシュを一括除去するだけ）を実装しコミット前の作業結果へ2回目の
敵対的レビューを行ったところ、**さらに別の反例**が実機で確認された。

`raw_hints_at_git_commit` が受け取る `$1` は、hookへの入力そのもの——**jqがデコードする前の
生JSON文字列**である。実コマンド文字列中の1文字（改行・タブ等の制御文字）は、JSONへ
エンコードされると**2文字のエスケープ列**（`\n` `\t` 等）になる。バックスラッシュだけを
除去すると、このエスケープ列の2文字目（`n` や `t`）が**単独の文字として生JSON文字列中に
残ってしまう**。

具体例: 実コマンド `git com\<改行>mit -m "x"`（バックスラッシュ＋改行の行継続。
`CommandPosition.sh` はこれを結合して「commit」と判定しブロックする）は、JSONへ
エンコードすると `com\\\nmit`（バックスラッシュ3つ＋n）になる。内訳は、実コマンド中の
バックスラッシュ1文字がJSON上は `\\`（2文字）に、実コマンド中の改行1文字がJSON上は
`\n`（2文字）にそれぞれエンコードされ、連結されるため。

```bash
$ cmd=$'git com\\\nmit -m "x"'
$ raw="$(jq -n --arg c "$cmd" '{tool_input:{command:$c}}')"
$ printf '%s' "$raw" | jq -r '.tool_input.command'  # デコード後（判定本体が見る文字列）
git com\
mit -m "x"
$ echo "$raw" | grep -o 'com[^"]*mit'
com\\\nmit   # 生JSON文字列（前置フィルタが見る文字列）: バックスラッシュ3つ+n
$ probe="${raw//\\/}"; case "$probe" in *commit*) echo pass;; *) echo FILTERED;; esac
FILTERED   # バックスラッシュを一括除去しても comnmit が残り、超集合が壊れる
```

この反例は、1回目のレビューで見つかった反例（`\x` によるバックスラッシュ1個の分割）とは
**別の層**で起きている。1回目は「精密判定側の正規化（シェルレベルのエスケープ解決）を
前置フィルタが再現できているか」という問題だったのに対し、今回は「hookが受け取る入力
そのものがJSONエンコードされており、jqがデコードする前の生文字列を扱う前置フィルタは、
JSONエンコード層のエスケープも合わせて解決しないと、精密判定（jqデコード後の文字列を見る）
と食い違う」という、前置フィルタという設計そのものに内在する層の違いに起因する問題である。

対策として、JSON文字列エスケープの2文字シーケンス（`\\` `\"` `\n` `\t` `\r` `\/` `\b` `\f`）は
**2文字ともまとめて**除去してから、残ったバックスラッシュ（`\uXXXX` 等、対応しきれない
エスケープ）を落とす。`\\`（エスケープされたバックスラッシュ）を最初に処理するのは、
`\\n`（エスケープされたバックスラッシュ＋素のn）を`\n`（改行のエスケープ）と誤って
分解しないため（`bash`の`${var//pattern/}`は左から右への非重複マッチのため、長い
パターンを先に処理すれば実際のJSONデコードと同じ分解になる）。この除去も「マッチする
可能性のある文字列を増やす」方向にしか働かないため、超集合であることを損なわない
（`\uXXXX`のような対応しきれないエスケープも、バックスラッシュだけを落として英数字を
残す——マッチ候補を増やす方向の処理であり、安全側に倒れる）。

### なぜ `${raw,,}` を使わないのか（bash 4.0互換性）

`${raw,,}` はbash 4.0以降で追加された大文字小文字変換の構文である。`block-direct-git-commit.sh`
は元々、`command_invokes_git_subcommand` を使えない環境（bash 4.3未満・ライブラリの
source失敗）では従来の部分一致 (`grep -qiE 'git[[:space:]]+commit'`) へ縮退する2段構えを
持っている。この2段構えは `BASH_VERSINFO` を判定本体の呼び出し直前で確認しており、`main()`
冒頭（判定本体より前）に `${raw,,}` を置くと、**その分岐へ到達する前に `${raw,,}` の展開
自体がbash 4.0未満の環境でエラーになり、hookプロセスが丸ごと終了する**（フォールバックが
機能しない）。両hookは元々bash 4.0未満の構文を1つも持たない設計だったため、この後退は
前置フィルタの追加が持ち込むことになる。

対策として、大文字小文字非依存の比較にはブラケット式（`case "$probe" in
*[Cc][Oo][Mm][Mm][Ii][Tt]*)`）を使う。この構文はbash 2.0から動作し、`BASH_VERSINFO` による
分岐を必要としない。

### なぜ `post-issue-create-notice.sh` 側も同じ正規化にするのか（issue #149との関係）

issue #149（起票済み・本DDR作成時点で未着手）は、`is_issue_create_call` のCLI経路判定
（`[[ "$command" == *create-issue.sh* ]]`、大文字小文字を区別する部分一致）を、
`CommandPosition.sh` ベースのコマンド位置判定へ差し替える計画である。

**当初、「コマンド位置判定は部分一致の対象を絞り込む方向の変更なので、マッチする集合は
現状の部分一致の部分集合になり、前置フィルタ（部分一致での超集合）は無条件に#149適用後も
超集合であり続ける」と結論していたが、これは誤りだった**（同じ敵対的レビューで指摘）。
コマンド位置判定は絞り込みだけでなく、バックスラッシュエスケープ・大文字小文字の**正規化
による拡張**も伴うため、単純な包含関係（部分集合）は成り立たない。

この誤りを踏まえ、`post-issue-create-notice.sh` 側の前置フィルタ（CLI経路）も
`block-direct-git-commit.sh` と同じくバックスラッシュ除去・大文字小文字非依存の比較にした。
これにより、#149が `CommandPosition.sh` と同じ正規化（バックスラッシュ除去・小文字化）を
採用する限り、前置フィルタは#149適用後の新判定に対しても超集合であり続ける。**ただし、
これは前提を明記した設計判断であり、無条件に成り立つとは主張しない。#149の着手時には、
この関係が保たれているかを必ず再確認すること。**

### なぜクォート断片の連結による意図的な文字列分割には対応しないのか

`git 'com''mit'` のように、クォートで囲われた断片同士を連結して `commit` を合成する文字列
分割は、精密判定（`CommandPosition.sh`）自体が対象外としている（意図的な回避への対策は
行わない設計。`.claude/docs/ddr/i0000-09-....md`）。前置フィルタが精密判定の「超集合」で
あるべきなのは「精密判定が検知するものを取りこぼさない」ためであり、精密判定が検知しない
ものまで前置フィルタが検知する必要は無い。したがってこの類型への対応はスコープ外とする。

## 却下した案

| 案 | 却下理由 |
|---|---|
| `${raw,,}` で小文字化してから `*commit*` 部分一致 | bash 4.0未満の環境でhookが丸ごと落ち、既存の部分一致フォールバックが機能しなくなる（上記） |
| バックスラッシュエスケープを考慮しない単純な `*commit*` / `*create-issue.sh*` | `com\mit` のような分割で超集合が壊れる（上記） |
| バックスラッシュを一括除去するだけ（`${raw//\\/}`。JSON文字列エスケープの2文字シーケンスを考慮しない） | この関数が受け取るのはjqデコード**前**の生JSON文字列であり、実コマンド中の1文字（改行等）はJSON化されると2文字のエスケープ列（`\n`等）になる。バックスラッシュだけを除去すると2文字目（`n`等）が単独の文字として残り、語の分割位置に紛れ込んで超集合が壊れる（実例: `git com\<改行>mit` はJSON化すると`com\\\nmit`になり、単純なバックスラッシュ除去では`comnmit`になって一致しなくなる。作業結果への敵対的レビューで発見） |
| クォート断片の連結による文字列分割にも対応する（正規化をフル実装する） | 精密判定自体が対象外としている範囲であり、前置フィルタだけがそれを検知しても意味が無い。加えて、正規化をフル実装すると前置フィルタ自体が`CommandPosition.sh`並みに重くなり、「高速な足切り」という目的に反する |
| 前置フィルタを`main()`内に直書きする（関数へ切り出さない） | `source`してから直接呼ぶ単体テストが書けず、サブプロセス起動を伴う結合テストでしか検証できなくなる。`is_issue_create_call`との一貫性も失う |

## 影響

- `.claude/hooks/block-direct-git-commit.sh` / `.claude/hooks/post-issue-create-notice.sh`
  の空振り時のプロセス生成コストが、判定材料の取り出し（jq呼び出し）を含まない水準まで
  下がる（Linux上のstrace実測: `block-direct-git-commit.sh` execve 5→1・clone 10→0、
  `post-issue-create-notice.sh` execve 7→1・clone 17→1。詳細:
  `reports/20260823_reduce-hook-misfire-cost_前置フィルタ実装.md`）。
- **一方、`IFS= read -r -d '' raw` はパイプ入力に対して1バイトずつread(2)するため、大きな
  `tool_input.command`（ヒアドキュメント等）ではread(2)の回数が入力バイト数に比例して増える。
  今回の実測はいずれも小さいペイロード（60バイト程度）1件のみで、この特性は測っていない
  （作業結果への敵対的レビューで指摘）。git bash（MSYS）はLinuxよりシステムコールのコストが
  高いため、大きな入力での実際の遅速はgit bash実機でしか確認できない。実装は変更せず
  （issue #70のpush系hookとの一貫性を優先）、`.claude/rules/shell-script-style.md`
  「hookの前置フィルタ」節へこの特性を注記した。
- 判定本体の挙動（ブロック・注意喚起の対象となる入力）は変更しない。
- 将来issue #149に着手する際は、`post-issue-create-notice.sh` の前置フィルタが引き続き
  超集合であることを再確認する必要がある（上記「なぜ同じ正規化にするのか」節）。
