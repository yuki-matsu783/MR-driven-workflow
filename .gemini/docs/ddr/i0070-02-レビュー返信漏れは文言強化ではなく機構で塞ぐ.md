# i0070-02. レビュー返信漏れは文言強化ではなく機構で塞ぐ

issue #70

## 背景

issue #70 のフェーズ2で、敵対的レビューが PR #157 へ**10件のスレッドを投稿**した。flow-id 2-9 で
21件すべての指摘内容をレポートへ反映し、人間の合意を得て `mark-done` でループを閉じた。

**しかし、10スレッドのいずれにも返信が付いていなかった。** 発覚したのはフェーズ3で `comments` を
取得したときで、約1日、10件が「未対応と区別が付かない」状態で残った。

**ルール自体は存在した。** `.claude/skills/issue-mr-flow/SKILL.md`「レビュー完了合図の確認」の
**(2) 返信が1件も付いていないスレッドが残っていないか**（issue #109）が、この事故を名指しで
禁じている。それでも起きた。原因は4つに分解できる。

| # | 原因 | 種類 |
|---|---|---|
| 1 | `comments` サブコマンドを実行しなかった。指摘内容が会話に残っていたため、スレッドを取得せずに直接レポートを直せてしまった | 手順の飛ばし |
| 2 | 「レビュー完了合図の確認」を実行しなかった。節が全体フロー表から離れており、`mark-done` の前提として結び付いていない | 手順の飛ばし |
| 3 | **投稿したスレッドの存在が、会話にしか無かった。** `adversarial-review` は件数の報告を求めるが、返信が未了であることをどこにも残さない。投稿と返信の間に人間のレビューを挟む設計（issue #109）なので、その間にセッションが切れれば情報ごと消える | 記録の欠落 |
| 4 | **HANDOFF が「反映した」と書けてしまう。** 義務は〈修正〉と〈返信〉の2つなのに、記録は片方しか追わない。「21件すべてを反映した」は事実だが、返信ゼロと両立する | 記録の粒度 |

**1・2は「守らなかった」だが、3・4は「守れる形になっていなかった」である。**

## 決定

1. `HANDOFF.md` のヘッダへ **`- 未返信スレッド:`** を新設し、確認した結果を書く。
2. **ループ範囲（`LOOP_RANGES`）への `mark-done` は、この値が `0` でなければ拒否する**
   （1件も書き換えない）。**行が存在しない場合も「未確認」とみなして拒否する。**
3. 値の書き込みは `update-handoff-progress.sh set-header --unreplied <n>` で行い、
   **行が無ければ書き手の側が挿入する。**
4. `adversarial-review` の手順8（結果の報告）へ、投稿直後に件数を `--unreplied` で記録し、
   スレッドURLを「やったこと」へ残すことを義務として加える。
5. `cleanup-task.sh` が生成する `HANDOFF.md` の雛形へ、この行を含める。

## 理由

### なぜ文言強化ではないのか

**文言はすでに十分強かった。**「次のステップへ進んでよいのは (1) と (2) の両方を満たしたときだけ
である。どちらか一方だけを確認して離脱しない。」と書いてあってなお起きている。同じ種類の対策を
重ねても、原因3・4（記録の欠落・粒度）は残ったままになる。

このリポジトリは「ドキュメント上のルールだけでなく、技術的にも強制する」方針を持ち
（`.claude/rules/git-workflow.md`「コミット運用」の `block-direct-git-commit.sh`）、
`update-handoff-progress.sh` は既に「ループ範囲の一部だけを完了扱いにできない」という制約を
機械的に強制している。**同じ場所へ同じ形で足せる。**

### なぜ書き手と検査側で「行が無いとき」の扱いを変えるのか

**意図的な非対称である。**

- **検査側（`mark-done`）が行の不在を拒否する**のは、行が無い＝一度も確認していない状態だから
  である。ここを「行が無ければ通す」にすると、雛形を持たない古い `HANDOFF.md` で機構が丸ごと
  無効になる。
- **書き手側（`set-header --unreplied`）が行を挿入する**のは、そうしないとデッドロックする
  からである。拒否された側が値を書こうとしても「行が無い」で失敗し、そこから抜け出せない。

### 機構の限界を認めたうえで採る

値を書くのはAI自身なので、**嘘を書けば通る。** これは `block-direct-git-commit.sh` と同じ
位置づけで、**敵対的な安全境界ではなく、既定動作を確実な方向へ倒す仕組み**である。

効くのは「うっかり飛ばす」に対してであり、今回の事故はまさにそれだった。原因1・2は
「確認する手順に到達しなかった」ことなので、`mark-done` が止まれば必ず到達する。
**`set-header --unreplied 0` という明示的な操作が要るようになる点**が本質である。

## 却下した案

| 案 | 却下理由 |
|---|---|
| `SKILL.md` の文言強化のみ（「ループを閉じる前に必ず確認する」を太字で再掲する等） | 文言はすでに十分強く、それでも起きた。原因3・4（記録の欠落・粒度）が残る |
| 未返信スレッドを列挙するスクリプトを新設する | この実行環境は `gh`/`glab` CLI が無く `Provider.sh` のCLI経路が使えないため、書いても MCP 経路では動かない。取得はAIがMCPツールで行い、**結果の記録と検査だけを機構化する** |
| 行が無ければ `mark-done` を通す | 雛形を持たない `HANDOFF.md` で機構が丸ごと無効になる |
| 行が無ければ `set-header` も失敗させる（既存の `set-header` の作法に揃える） | 拒否された側が値を書けず、デッドロックする |
| 返信を省略してよい類型を作る（issue #109 の判断の見直し） | 「対応を求める指摘には必ず返信する」という前提そのものを崩す。**維持する** |
