# i0133-01. DDR識別子はissue番号ベースにし連番採番をやめる

## 背景

issue #133「DDRの識別子を連番からissue番号ベースへ変更し、並行開発時の番号衝突を原理的に無くす」。

DDRは `.claude/docs/ddr/NNNN-タイトル.md` という4桁の連番で識別していた。**これは分散した
ブランチ上で共有の単調増加カウンタを採番する設計であり、2つのブランチが同時に新しいDDRを追加
すれば必ず同じ番号になる。** gitに単調増加カウンタを衝突なく採番する手段は原理的に無い。

さらに悪いことに、この衝突は**gitからは見えない**。`0027-A.md` と `0027-B.md` はファイル名が
異なるため、gitはコンフリクトを報告せず無言で両方をマージする（semantic conflict）。

この問題には既に2つの機構で対処していた。

- 検知: `check-base-conflicts.sh` の `hasDuplicateDdrNumber`（DDR i0046-01・issue #46）
- 解消: `resolve-conflict` スキルの類型A（作業ブランチ側を空き番号へ繰り下げ改番する）

しかし**過去4回（PR #29 / #37 / #49 / #52）のコンフリクトはすべてこの形**であり、対処の機構が
あっても発生自体は減っていなかった。そして改番には固有の危険がある。改番の対象はファイル名だけで
なく、frontmatterの `title`・本文冒頭の見出し・`.claude/docs/README.md` のDDR一覧・他ファイルからの
参照に及ぶ。**実際にissue #36の改番で `.gitignore` のコメントが古い番号のまま残り、issue #46で
修正するまで存在しないDDRを指していた。**

対処の機構を磨いても、この2つ（衝突が必ず起きること・改番のたびに参照が追従漏れしうること）は
無くならない。**採番方式そのものを変えるしかない。**

## 決定

1. **新規DDRの識別子を `i<issue番号>-<枝番2桁>` にする。** ファイル名は
   `.claude/docs/ddr/i<issue番号>-<枝番2桁>-<タイトル>.md`（例:
   `i0133-01-DDR識別子はissue番号ベースにし連番採番をやめる.md`）。
   **issue番号はGitHub/GitLabが中央で採番するため、別ブランチ同士で同じ識別子が生まれることが
   原理的に無い。**
2. **枝番は2桁ゼロ埋めで `01` から振り、1件しか作らない場合も省略しない。** 枝番の採番は
   同一issue＝同一ブランチ内で閉じるため衝突しない。省略可にすると、後から2件目を足すときに
   1件目の改番が要り、いま無くそうとしているリスクを呼び戻す。
3. **issue番号は4桁へゼロ埋めする**（`#133` → `i0133-01`）。**当初は「ゼロ埋めしない」で決着して
   いたが、後から覆した**（下記「issue番号をゼロ埋めへ変えた経緯」）。9999を超えたら5桁で書く。
4. **接頭辞は小文字の `i` で固定する**（`I133-01` や `issue133-01` は認めない）。表記の揺れを
   許すと、同じDDRが別の識別子として二重に採番されうる。
5. **既存の連番DDR（本DDR作成時点で56件、`0003`〜`0060`）も、すべて新方式へ改番する。**
   当初は「改番しない（新旧2方式が併存する）」と決めていたが、ユーザーの判断により全件改番へ
   変更した（下記「全件改番へ方針を変えた経緯」）。**本リポジトリに連番のDDRは残っていない。**
6. **対応するissueを特定できないDDRには、予約番号 `i00` を使う。** 改番対象56件のうち43件は
   本文から対応issueを特定できたが、残る13件は特定できなかった（多くは移植元プロジェクトの
   issue番号を書いており、本リポジトリの同番号issueとは別物だった）。この13件へ
   `i0000-01`〜`i0000-13` を振った。**`i00` の枝番だけは、他と違ってリポジトリ全体で通しの連番に
   なる**（`i00` は単一のissueではなく「issueが無い」という状態を指すため）。
   **新しく `i00-*` を作ることはない。**
7. **重複検知の機構は廃止せず残す。** 識別子の抽出だけを新旧両方式へ一般化し、重複判定の
   ロジックは変えない（理由は下記「残した理由」）。
8. **`check-base-conflicts.sh` のJSON出力キー（`duplicateDdrNumbers` /
   `hasDuplicateDdrNumber`）は改名しない。** 値は「番号」ではなく「識別子」になるため名前は
   実態とずれるが、改名の是非は下記「JSONキーを改名しなかった理由」に記す。

命名規則は `.claude/rules/markdown-frontmatter.md`「DDRの識別子」、検知の仕様は
`.claude/docs/spec/check-base-conflicts.md`、解消手順は `.claude/skills/resolve-conflict/SKILL.md`
の類型Aが正。

## 却下した案

### 案A: 連番を維持し、採番をマージ直前まで遅延させる

DDRを作る時点では番号を決めず（`draft-タイトル.md` 等）、flow-id 5-1 の直前にdefaultブランチの
最新を見て空き番号を採る、という案。**衝突の窓を狭めるだけで、無くならない**。

- 2つのブランチが同じ日にマージ直前まで進めば、やはり同じ番号を採る。窓が数日から数分に縮む
  だけで、**確率を下げても原理は変わらない**。
- 採番が「マージ直前」に集まるため、衝突したときの手戻りが最も痛いタイミングで起きる
  （レビューが終わった後に、改番のためにもう一度差分が動く）。
- DDRは**マージ前からファイル名で相互参照される**（他のDDR・spec・スキル・plansから）。番号が
  最後まで決まらないと、参照を書く側が「後で直す」前提で書くことになり、これは今回無くそうと
  している追従漏れそのものである。

### 案B: 番号レンジを担当者・ブランチごとに分割する

`0100〜0199` は担当者A、`0200〜0299` は担当者B、のようにレンジを事前に割り当てる案。
**中央の調整が必要な点で、issueの目的と噛み合わない**。

- レンジの割り当て自体が中央の合意を要する。それを行うくらいなら、既に中央で採番されている
  issue番号をそのまま使うほうが単純で、追加の運用が要らない。
- レンジが枯渇したときの再割り当てが必要になる。枯渇の検知も再割り当ても人間の作業であり、
  **恒久的に運用コストが乗り続ける**。
- 1人の担当者が複数ブランチを並行して持つ場合（このリポジトリでは普通に起きる）、レンジ内で
  同じ衝突が再発する。担当者ではなくブランチ単位でレンジを割るなら、ブランチを作るたびに
  中央調整が要る。

### 案C: issue番号をゼロ埋めして `0133-01-…` とする

接頭辞を持たせず、issue番号を4桁ゼロ埋めして既存の連番と見た目を揃える案。
**新旧を機械的に区別できないため失格**。

- `0133-01-…` は既存の判定 `^[0-9]{4}-` にマッチしてしまう。issueが明示的に求めている
  「新旧を機械的に区別できる命名にする」を満たさない。
- 却下した時点では既存の連番を残す前提だったため、**issue番号が既存の最大値（0060）以下の
  古いissueに対してDDRを書くと、実在する連番DDRと同じ識別子になる**（例: issue #29 → `0029`）
  という致命的な問題もあった。全件改番した現在この衝突は起きないが、過去のコミットメッセージ・
  changelog・旧形式のまま配布された複製には連番が残り続けるため、**両者を見た目で区別できる
  ことの価値は失われていない**。
- **注意: 後から採用した `i0133-01` は、この案Cとは別物である。** 却下したのは
  「接頭辞を持たせずゼロ埋めする」ことであり、`i` 接頭辞が付く限り旧形式の `^[0-9]{4}-` と
  1文字目で区別できる。ゼロ埋めそのものが却下理由だったのではない
  （下記「issue番号をゼロ埋めへ変えた経緯」）。

### 案D: 重複検知（`hasDuplicateDdrNumber`）を廃止する

新方式で衝突が起きないなら検知も要らない、という案。**残る衝突経路が2つあるため却下**。

1. **旧形式（4桁連番）のDDR同士。** 本リポジトリからは全件改番で消えたが、改番前に切られた
   ブランチや、このワークフロー機構を旧版のまま導入した別リポジトリには残る。識別子の抽出は
   旧形式も受け付けたままにしてあるため、検知はそのまま働く。
2. **同一issueへの追加作業を2つのブランチで並行して行った場合。** 枝番だけはローカルで決めるため、
   両ブランチが同じ枝番（例: どちらも `i0133-03`）を採りうる。**この残存リスクは新方式でも
   消えない。**

検知の維持コストは正規表現の分岐1つで、廃止して得られるものより残して防げるもののほうが大きい。
なお2つ目のケースは、`resolve-conflict` スキルの類型A-2として「枝番だけを繰り下げる」手順を
定めたうえで、**同一issueを2ブランチで並行して進めている状態そのものを人間へ確認する**扱いに
した（衝突は症状であって原因ではないため）。

## JSONキーを改名しなかった理由

`duplicateDdrNumbers` / `hasDuplicateDdrNumber` は「番号」という語を含むが、値は今後 `i0133-01`
のような**識別子**にもなる。`...Identifiers` へ改名するほうが実態に合う。それでも改名しなかった
のは、**このキー名が `resolve-conflict/SKILL.md`（4箇所）・`check-base-conflicts.md`（3箇所）から
参照される公開インターフェースだから**である。改名は全参照の追従を要求し、それは
**このissueが無くそうとしているリスクそのものを、別の場所に作り出す**。

一方、内部の純粋関数名（`ddr_number_to_reply` → `ddr_identifier_to_reply`、
`find_duplicate_ddr_numbers` → `find_duplicate_ddr_identifiers`）は改名した。こちらは
スクリプト本体と単体テストの2ファイルしか参照しておらず、追従漏れが起きようがないためである。

**この非対称（内部は実態へ合わせ、外部インターフェースは据え置く）は意図的である。**
片方へ揃えようとする前に、このDDRを読むこと。

## 受け入れたトレードオフ

- **識別子と `#<issue番号>` の見た目が完全には一致しない。** `#133` に対して `i0133-01` と
  4桁へ揃えるため、「何桁に揃えるのか」という転記の判断が1つ増える。当初はこれを嫌って
  ゼロ埋めしない方式を採ったが、並び順の利益のほうが大きいと判断して覆した
  （下記「issue番号をゼロ埋めへ変えた経緯」）。桁数は
  `check-base-conflicts.sh` が機械的に検証するため、揺れたまま入ることはない。
- **全件改番のために、参照の追従漏れリスクを一度だけ引き受けた。** これは本DDRが無くそうと
  している当のリスクであり、矛盾している。**一度きりで終わること**、および機械的な一括置換と
  「全リンクが実ファイルへ解決すること」の検証で担保できることを理由に受け入れた
  （下記「全件改番へ方針を変えた経緯」）。
- **`i00` は「issueが無い」を表す番号であって、issue #0 ではない。** 識別子の形は他と同じ
  `i<数字>-<枝番>` なので、規則だけを見た読み手は「issue #0 に対応するDDR」と誤読しうる。
  README・`markdown-frontmatter.md` の両方に明記することで補う。
- **DDRを書くにはissueが要る。** 記録したい意思決定があってissueが無い場合は、先にissueを起票する
  （`issue-create` スキル）。DDRはissueを起点とするフローの成果物であり、本DDR作成時点の56件中
  43件は本文から対応issueを特定できた。残る13件も、多くは移植元プロジェクトのissueを起点に
  していた（本リポジトリのissue番号として特定できなかっただけ）ため、実質的な制約にならないと
  判断した。

## 全件改番へ方針を変えた経緯

本DDRは当初「既存の連番DDRは改番しない」（新旧2方式の併存）で決着していた。改番はファイル名・
frontmatterの `title`・本文冒頭の見出し・README一覧・他ファイルからの参照に及び、**issue #36 の
改番では実際に `.gitignore` のコメントが古い番号のまま残った**という実害があったためである。

これを**ユーザーの判断で全件改番へ変更した**。判断の理由は「一覧・参照の表記が2方式に分かれた
ままだと、以後すべての読み書きで『どちらの方式か』を意識し続けることになる」というもので、
併存のコストを恒久的に払うより、追従漏れのリスクを**一度だけ**引き受けるほうが安いという評価
である。

引き受けたリスクへの対処として、次を行った。

- 置換は機械的に行い、目視での書き換えを混ぜない（人手の見落としを設計から排除する）。
- 置換後に**すべてのDDRリンクが実ファイルへ解決すること**を機械的に検証する。
  この検証があるため、追従漏れは「気づかないまま残る」のではなく必ず落ちる。
- **過去の記録は書き換えない。** 具体的には、過去のコミットメッセージの引用
  （`chore: mainをマージしDDR番号を0028へ繰り下げて…`）、過去に重複した番号の一覧、
  `0034→0035→0036→0038` のような繰り下げの経過、`.claude/docs/spec/*.md` の
  issueごとのchangelogエントリ。これらは**ファイルを指す参照ではなく当時の事実の記録**であり、
  書き換えると歴史が壊れる（`.claude/rules/docs-workflow.md`）。
- 単体テスト `test_check_base_conflicts.sh` の `0027-…` フィクスチャも書き換えない。
  これは**PR #52 で実際に起きた衝突を再現している**ものであり、片方だけ改番すると
  「重複しない2ファイル」になってテストの意図が無言で失われる（実際に一度壊し、差し戻した）。

## issue番号をゼロ埋めへ変えた経緯

**決定3は当初「issue番号はゼロ埋めしない」だった。** `#133` とファイル名の数字を完全に一致させ、
「何桁に揃えるのか」という転記ミスの余地を作らないことを理由にしていた。これを
**`i0133-01` のような4桁ゼロ埋めへ覆した**。

きっかけは、本ブランチのレビュー待ちの間に `main` がマージした **issue #135「`.claude/docs/README.md`
のDDR一覧を生成スクリプト化する」**（DDR i0135-01）である。`generate-ddr-list.sh` は
**ファイル名の昇順（`LC_ALL=C` のglob順）**で一覧を出す。ゼロ埋めしない識別子では、この順序が
数値順と一致しない。

```
ゼロ埋めなし: i106-01, i109-01, i11-01, i112-01, …, i133-01, i14-01, …, i3-01
ゼロ埋めあり: i0003-01, i0011-01, i0014-01, …, i0106-01, i0109-01, i0112-01, i0133-01
```

本DDRは「一覧はissue番号の数値順に並べる」と決めていたので、**そのままでは生成結果と
ドキュメントの記述が食い違う**。取りうる選択肢は3つあった。

1. 生成スクリプトへ「issue番号→枝番」の数値ソートを実装する。
2. 一覧の並び順をファイル名順と認め、ドキュメント側の記述を変える。
3. **識別子をゼロ埋めし、ファイル名の辞書順が数値順と一致するようにする。**

**3を採った（ユーザーの判断）。** 1は453行のスクリプトと366行のテストへ手を入れることになり、
issue #133 のスコープを大きく超える。2は一覧の読みやすさを恒久的に捨てる。3は
**スクリプトを1行も変えずに済み**、しかも「識別子の桁が揃う」という副次的な読みやすさも得られる。

- **却下案Cの再来ではない。** 案Cが失格だったのは「接頭辞を持たせずゼロ埋めする」ために旧形式の
  `^[0-9]{4}-` と機械的に区別できなくなる点であり、`i` 接頭辞が残る `i0133-01` はその問題を踏まない。
- **`ddr_identifier_to_reply` は4桁未満を弾く**（`^(i[0-9]{4,}-[0-9]{2})-`）。ゼロ埋め漏れを
  通してしまうと、同じDDRが `i133-01` と `i0133-01` という**2つの識別子**を持ちうる。これは
  決定4（接頭辞を小文字の `i` に固定する）が防いでいるものと同じ種類の事故である。
- **上限は設けず `{4,}` にした。** issue番号が9999を超えたら5桁で書く。桁数が増える側が辞書順で
  必ず後ろに来るため、4桁と5桁が混在しても並び順は保たれる。ここを `{4}` と固定すると、
  10000件目のissueでスクリプトが黙って一覧から落とすことになる。
- 予約番号 `i00` も同じ規則に従い **`i0000`** になった（`i0000-01`〜`i0000-13`）。
