# i0143-01. flow-id並べ替え時の確認手順をSKILL.mdへ明記しDDRで記録する

issue #143

## 背景

issue #143は「`.claude/rules/docs-workflow.md`の`reports/…md` `reports/…html`行の『運用』欄が
flow-id 5-1（片付けの意味）のままで、同じ行の『寿命』欄・表直後の段落（flow-id 5-3）と矛盾している」
という問題を報告した。issue #112のフェーズ5並べ替え（DDR `i0112-01`）に`reports/`行だけが
追従できなかったことが原因。受け入れ条件は次の4点だった。

- (1) `reports/…md` / `reports/…html`行の運用欄がflow-id 5-3（もしくは現在正しい番号）を指す
- (2) 「片付け＝flow-id 5-1」と読める現行記述が他に残っていない
- (3) `.claude/docs/spec/` `.claude/docs/ddr/`の過去changelogを変更しない
- (4) 再発防止策の要否を検討し、結論を記録する

## 調査で判明した事実

フェーズ2〈調査〉（issue #143 / PR #181のブランチ上の作業記録。`reports/`はタスク単位で削除される
ため、恒久的な参照先としてはissue番号・PR番号を用いる）で、次を実測で確認した。

1. **issueが報告した矛盾は既に解消済みだった。** issue #143とは無関係の**PR #144**（issue #111
   「最終統括レポート」対応、commit `e33b468`、UTC 2026-08-21T09:27:32Z マージ）が、flow-id 5-3
   （統括レポート）の新設に伴うフェーズ5全体の繰り下げ作業の中で、`docs-workflow.md`の該当箇所を
   一括で`5-1`→`5-4`、`5-3`→`5-4`へ書き換えていた。解消前後の断面比較（`e33b468^`/`e33b468`/HEAD）
   で、「ファイルの削除は」に続く番号が「5-1」2件・「5-3」1件混在 → 「5-4」へ統一、という
   決定的証拠を確認した。
2. **受け入れ条件(1)「flow-id 5-3」自体が、起票後さらに繰り下がっていた。** issue #143の起票
   （UTC 2026-08-20T20:04:04Z）は、issue #112対応のPR #125マージ（UTC 2026-08-20T11:09:23Z）より
   約9時間後であり、起票時点では片付けは正しく5-3だった。しかしissue #111対応のPR #144
   （UTC 2026-08-21T09:27:32Z、起票の約13時間後）マージにより、その後さらに5-4へ繰り下がった。
   **片付けのflow-id番号は、issue #112対応（5-1→5-3）・issue #111対応（5-3→5-4）・本タスク中に
   判明したissue #70対応（`origin/main`側、5-4→5-5。下記事実5）と3回繰り下がっている
   （起票前の1回を含めれば計3回、起票後だけを数えれば2回）。**
3. **リポジトリ全体で「片付け＝flow-id 5-1」と読める現行記述は残っていない。** 追跡下の`.md`
   （25件）・`.sh`/`.html`（5件）計30件を分類し、正当な用法（コンフリクト解消の意味、8件）・
   過去changelog/DDR本文（15件）・複合（2件）・正しい現在値付きの参照（2件）・テストラベル
   （3件）のいずれかであることを確認した（8+15+2+2+3=30）。
4. **再発防止の機械的検知手段は存在しない。** `.claude/scripts/src/` `.claude/hooks/`配下を
   確認したが、`docs-workflow.md`・`SKILL.md`内の「flow-id N-M」参照を横断的に洗い出し・検証する
   スクリプト/CI/hookは無い。DDR `i0112-01`は「フェーズ5全体を作り直し番号を振り直す」案を
   「変更範囲最小化」を理由に既に却下していたが、機械的検知そのものについての議論・却下の形跡は
   無く、単に検討されていなかった。
5. **issue #70対応（本タスクとは別の対応）で、同型の追従漏れが実際に発生し、敵対的レビューで
   検知・修正されていたことを本タスクの調査中に発見した。** 本ブランチの分岐後、`origin/main`
   ではissue #70対応（`.gemini/`変換同期ステップの新設）により、片付けのflow-id番号がさらに
   **5-4→5-5**へ繰り下がっていた（発見当時は`git merge-tree`で確認しただけで本ブランチへは
   未取り込みだったが、その後flow-id 5-1で`origin/main`を取り込み、本DDRを含む本ブランチの
   記述はすべてこの番号へ揃っている）。
   `origin/main`側の`.claude/rules/docs-workflow.md`によれば、その繰り下げ作業の際に
   `reports/REVIEW-POINTS.md`の繰り下げ漏れが一時発生したが、**敵対的レビューで発見され、
   その場で修正済み**である旨が教訓として記載されていた。つまりこの追従漏れ自体は
   issue #70対応の作業中（本タスクの作業中ではない）に起き、機械的な仕組みではなく
   敵対的レビューという既存の検知手段によって捕捉・是正されていた。issue #143が問題にした
   種類の追従漏れが、issue #143の起票後も現に起こりうることを示す実例である。

## 決定

1. **`docs-workflow.md`本体は変更しない。** 上記1・3のとおり、現行記述に矛盾は残っていない。
2. **再発防止策として、機械的検知スクリプトの新設（案A）・現状維持（案B）を却下し、
   手順明記＋DDR記録（案C）を採用する。**
   `.claude/skills/issue-mr-flow/SKILL.md`へ「flow-idを並べ替える・挿入する作業を行う場合」節を
   新設し、flow-id並べ替え作業の**最後に**次を確認する手順を明記した。
   - まず今回変更した番号を固定文字列でgrepし、次に`[0-9]-[0-9]`という数字パターン
     （`flow-id`の接頭辞を問わない）全体を補助的に横断grepして取りこぼしを確認する
     （`core.quotePath=false`を付け、日本語ファイル名のクォート化を避ける）。
   - `plans/` `worklog/` `reports/`配下は走査対象から除外してよいが、除外は**ディレクトリ単位
     ではなくファイル単位**で判断する（`REVIEW-POINTS.md`は寿命が永続のため除外しない。
     パススペックの除外指定に明示的に戻す）。
   - ヒットした記述が**現在の状態を説明しているか、過去の記録（point-in-time）か**で判断する
     （`.claude/docs/spec/` `.claude/docs/ddr/`だけでなく`.claude/scripts/`配下のコメントも対象。
     同じ1行に現在値と経緯が同居する場合は現在値だけを更新する）。
   - 確認結果をコミットメッセージへ残す（`reports/`はタスク単位で削除されるため恒久的な記録先
     にならない）。
3. **docs-workflow.mdの既存の教訓段落（issue #70実例）とSKILL.mdの新節は役割を分ける。**
   SKILL.mdの新節が「何を確認するか」という手順そのものの正、docs-workflow.mdの既存段落が
   「なぜその確認が要るか」を示す具体的な失敗実例の正。同じ内容を2箇所で説明しない。

## 理由

### なぜ機械的検知（案A）を却下したのか

「片付け＝flow-id 5-1」のような**古い番号が別の意味で今も使われている**ケース（例: 現行の
コンフリクト解消はflow-id 5-1を正しく使っている）を、文字列の存在チェックだけでは検知できない。
自然言語の文脈（「片付け」の意味で使われているか）の判定が必要で、実装コストに対して実効性が
見合わない。DDR `i0112-01`が既に採用している「変更範囲最小化」の方針とも整合しない。

### なぜ現状維持（案B）を却下したのか

issueの受け入れ条件(4)が「再発防止策の要否を検討し、結論を記録する」ことを明示的に求めており、
検討自体を省略できない。また上記「調査で判明した事実」5のとおり、issue #143起票後もissue #70対応で
同型の追従漏れが実際に再発しており、「何もしない」を選ぶ根拠が無い。

### なぜ手順明記＋DDR記録（案C）を採用したのか

コストが低く（ドキュメント追記のみ）、次にflow-idを並べ替える作業者が確認を忘れにくくなる。
機械的強制ではないため実効性は完全ではないが、issue #70の実例（敵対的レビューという後段の
検知でしか捕捉できなかった）を踏まえると、**手順として明記しておくこと自体に価値がある**
（作業の最後に確認するという型を持たせることで、後段の検知に頼る前に自己点検できる）。

## 却下した案

- **案A: 機械的な整合性チェックスクリプトを新設する**（flow-id文字列を横断grepしSKILL.mdの
  テーブルと突合する）。上記「なぜ機械的検知を却下したのか」参照。
- **案B: 何もしない（現状維持）**。上記「なぜ現状維持を却下したのか」参照。
