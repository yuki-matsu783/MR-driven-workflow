# i0111-01. 統括レポートの添付は任意層に置きフローを止めない

## 背景

issue #111。`plans/` `worklog/` `reports/` は片付け（flow-id 5-4）で削除され、squash mergeにより
`main` にも残らない。ブランチ全体を統括した成果はMR descriptionと `.claude/docs/spec/` `ddr/` に
散っており、「このMRで何をどう検証したか」を後から一望する手段が無かった。

統括レポートをPR/MR上へ残せばこの穴は塞がるが、**どうやって残すか**が問題になる。issueが
挙げていた「HTMLファイルの添付」は、プロバイダで事情が大きく異なる。

| プロバイダ | 添付API |
|---|---|
| GitLab | **公式API**（`POST /projects/:id/uploads`）。レスポンスの `markdown` をそのまま埋め込める |
| GitHub | **公式APIが無い。** `gh` に添付用フラグは無く、要望は2020年から複数回上がって「プラットフォームAPI待ち」でクローズされ続けている（cli/cli#12960）。Web UIのドラッグ＆ドロップと同じ `uploads.github.com/user-attachments/assets` が `gh auth token` のBearerトークンで通るという報告があるが、**未ドキュメントの内部エンドポイント**である（以前はPATでは422でCookieセッション必須だった。cli/cli#13256） |

## 調査で分かったこと

issue #111 のフェーズ2で、この機構の主要な作業環境（Claude Code on the web / MCP経路）における
添付の可否を実測した。

| 確認内容 | 結果 |
|---|---|
| `gh` / `glab` CLI の有無 | **どちらも無し**（`curl` のみ） |
| `GH_TOKEN` / `GITHUB_TOKEN` | 存在するが**14文字**。GitHubのトークン形式（`ghp_`＋36文字＝40文字、`github_pat_` は82文字以上）のいずれにも一致しない |
| MCPの添付ツール | **該当なし**。返るのはリポジトリのファイル操作系（`create_or_update_file` 等）のみ |
| `uploads.github.com` への到達性 | **403**（認証情報を付けない状態） |
| 比較対照 `api.github.com` | **200** |

**403の発信元（エージェントプロキシかGitHubか）は切り分けられていない**（レスポンスヘッダを
取得するコマンドが実行環境の権限判定でブロックされた）。したがって言えるのは「**この環境では
動かない**」までで、「このエンドポイントが壊れている」とは言えない。1環境・1回の観測であり、
`gh` CLI のあるローカル（git bash）では結果が変わりうる。

**それでも設計上の含意は変わらない。** 未ドキュメントAPIが将来壊れるという想定以前に、
**現時点で既に動かない環境が存在し、しかもそれが主要な作業環境である**。

## 決定

**統括レポートのPR/MRへの反映を3層のフォールバック構造とし、外部依存の弱い添付を任意の層3へ
閉じ込める。層3が失敗しても警告のみでスキップし、フローを止めない。**

| 層 | 何をするか | 必須か | 依存する外部API |
|---|---|---|---|
| 層1 | レポート本体を `reports/` に載せ、`commit` スキル経由でリモートへ反映する | **必須** | 無し（git操作のみ） |
| 層2 | サマリをMarkdownでPR/MRへコメント投稿する（`add_mr_comment`） | **必須** | **公式API**（GitHub/GitLab両対応） |
| 層3 | HTMLを添付する（`upload_attachment`） | **任意** | GitHub: **未ドキュメントAPI** / GitLab: 公式API（実機未検証） |

**「層3が壊れても層1と層2でレビューは成立する」ことが、この分割の目的である。** 層2が
「ファイルが消えても残る」という本issueの要求を単独で満たしており、層3はその上に載る利便性に
すぎない。

あわせて次を決めた。

- **`upload_attachment` は失敗を正常系のひとつとして設計する。** 成功時はJSON
  （`url` / `markdown` / `provider`）をstdoutへ返し、失敗時は理由をstderrへ出して非0で終える。
  呼び出し側は非0を受けてスキップする。**成功したかどうかでサマリコメントの本質的な内容が
  変わってはならない。**
- **CLI不在時は `require_vcs_cli` でネットワークへ出る前に落とす。** `mcp_tool_hint` は
  `upload_attachment` に対して**唯一「代替が無い」ヒント**を返し、「層3はスキップしてよい」と
  名指しする。他の関数のように読み替え先を案内できないためである。
- **未ドキュメントAPIへの依存はコードと仕様の両方へ明記する。** `github_upload_attachment` の
  関数コメントに警告を置き、`.claude/docs/spec/issue-mr-workflow.md` にも同じ制約を書く。
- **統括レポート自体は flow-id 5-4 の削除対象に含める。** `main` に残るのはPR/MR上のコメントと
  `.claude/docs/spec/` `ddr/` であり、レポートファイルそのものではない。

### ステップの位置（新 flow-id 5-3）

フェーズ5へ新しいステップを挿入し、片付け以降を繰り下げた（5-3→5-4、5-4→5-5、5-5→5-6。
全体は41→42ステップ）。

| flow-id | 内容 |
|---|---|
| 5-1 | コンフリクト解消 |
| 5-2 | 関連issue通知 |
| **5-3** | **最終統括レポートの作成とPR/MRへの反映（新設）** |
| 5-4 | 片付け（旧 5-3） |
| 5-5 | commit・push・Draft解除（旧 5-4） |
| 5-6 | マージ（旧 5-5） |

- **5-4（片付け）より前**である必要がある。統括レポートは `plans/` `worklog/` `reports/` を
  materialにして書くため、削除後には書けない。
- **5-3 自身がcommit・pushまでを含む複合ステップとする。** 作るだけで 5-4 へ進むと、作成と削除が
  同じ作業ツリー上で相殺され、**ブランチのコミット履歴にすら残らない**（層1が成立しない）。
- **5-1（コンフリクト解消）より後**である必要もある。5-1 は作業ツリーがきれいなうちに
  `git merge` を走らせるステップであり（DDR i0112-01）、その前にファイルを作ると解消結果と混ざる。

issueの本文は「flow-id 5-1（片付け）より前に置く」と書いているが、これは**起票当時の番号**で
ある。issue #112 の並べ替え（DDR i0112-01）により片付けは 5-3 になっていたため、「片付けより前」
という**意図**を満たす位置として 5-3 を選んだ。

### サマリコメントの種別ラベル

`add_mr_comment` で投稿される通常コメントは、本issueの追加で**4種類**になる（issue #111 の
コメントは3種としていたが、対応工数レポートが数えられていなかった）。

**統括レポートのサマリだけが `Claude Codeより（最終統括レポート）:` という括弧付きラベルを持つ。**
既存3種の1行目は変更しない。

## 却下した案

### A. 添付を必須にする（層2を省いて層3だけにする）

issueが挙げた「HTMLファイルの添付」をそのまま必須の反映手段にする案。**却下**。

- **主要な作業環境で動かない。** 上記の調査のとおり、`gh` CLI 不在の環境では添付そのものが
  実行できない。必須にすると、その環境ではフェーズ5を完了できなくなる。
- GitHub側が未ドキュメントAPIである以上、**動く環境でも予告なく壊れる**。フローの必須経路に
  置くと、外部の都合でフローが止まる。

### B. GitHubの添付を諦め、GitLabだけ対応する

プロバイダで事情が違うのだから、公式APIのあるGitLabだけ実装する案。**却下**。

- このリポジトリのremoteはGitHubであり、**主対象で機能しない**。
- 3層構造にすれば、GitHubでも層1・層2は完全に動く。層3だけがプロバイダ差を持つ形にできる。

### C. 統括レポートを `main` へ残す（片付けの対象から外す）

レポートファイル自体を `main` へ残せば、コメント投稿も添付も要らないという案。**却下**。

- `.claude/rules/docs-workflow.md` のライフサイクル設計と衝突する。`reports/` はタスク単位の
  寿命を持つと定めており、1件だけ例外にすると「どれが残ってどれが消えるか」が読めなくなる。
- タスクごとにファイルが1つずつ増え続ける。**恒久的に残すべき知見は `spec/` `ddr/` へ反映する**
  というのが既存の設計判断であり、そちらの経路が既にある。

### D. MR descriptionへ統括を書き、コメントを投稿しない

`describe` サブコマンドで更新されるMR descriptionに統括を書けば足りるという案（issue #54 が
「最終統括レポートは作らない」と決めた際の理由でもある）。**却下**。

- **descriptionは上書きされる。** `describe` はフェーズごと（2-5・2-10・3-5・3-10・4-5・4-10）に
  本文を作り直すため、統括を書いても次の更新で消える。差分としても追えない。
- コメントは**追記**であり、投稿時刻とともに時系列で残る。「マージ直前の最終状態」を表すには
  コメントのほうが正しい器である。
- なお issue #54 の判断（レポート土台は個別作業の報告用途に限る）は**テンプレートの適用範囲**に
  ついてのもので、本issueはその判断を独立に扱い直したものである。`reports.template.html` を
  統括レポートのHTMLにも使う点で、#54 の成果物とは補完関係にある。

### E. 全種類の通常コメントへ括弧付きラベルを付け直す

読み手の判別のために、既存3種も `Claude Codeより（〜）:` へ統一する案。**却下**。

- `SKILL.md` の複数箇所・spec・**既に投稿済みのコメント**へ波及するのに対し、得られるのは表記の
  統一だけである。
- 判別に必要なのは「これは統括レポートか、それ以外か」であり、**新しい1種だけがラベルを持てば
  達成できる**。
