hooks/ と scripts/ の軸2は、docs/ の採否に依存して 1 にも 0 にもなる。 「独立に結論を出す」という方針は、軸2に関しては最初から成立していなかった。これは調査で数えたときには「hooks 1・scripts 1・docs 18」という並びに見えていて、依存関係としては読み取っていなかった。

結論5: 案2（hooks/ scripts/ だけ外す）を却下した理由

2つある。どちらか一方でも成り立てば却下に足りる。

  1. 残る .gemini/docs/ から2件の壊れたリンクが出る（上記）。3案の中で、「外す対象の中で完結するから実害が無い」という説明が使えない唯一の案であり、.gemini/ を見る読み手には壊れたリンクとして見える。
  2. 軸1の根拠が .gemini/rules/ にも当たる（調査 Q3-b）。「そのパスを実行時に読む経路が無い」という根拠は、.gemini/rules/ .gemini/skills/ にも同じ強さで当たる。にもかかわらず3ディレクトリだけを外すなら、なぜ rules/ skills/ は外さないのかを説明できなければならない。説明は見つからなかった（.gemini/rules/ を残す理由として提示できるのは「人間が .gemini/ を眺めたときに読める」ことだけで、それは .gemini/docs/ にも等しく当てはまる）。

結論6: 案3（3つとも外す）を却下した理由

軸2は0件にならず18件で、これを許容するかどうかの判断になる。許容してよいと言い切れる根拠が無いと判断した。

  • 仮にその推論が正しいなら、.gemini/rules/ .gemini/skills/ も同時に外すのが筋であり、それは issue #172 のスコープ外である。「18件の壊れたリンクを抱えた .gemini/rules/ を残す」という中間状態は、どちらの前提から見ても正当化できない。（この2点はフェーズ3・1回目時点の記述。スコープ拡大により rules/ はスコープ内になり、「論点2・論点3の判断」節で判断済み——現状維持。skills/ は判断対象外のまま。）

結論7: 生成物に含まれないファイルがあると、配布先の再適用が片肺になる（実測）

「無言で壊れる」ではない。 引用範囲を手前へ広げると、この継続は意図的なトレードオフとして記録されていることが分かる。

$ sed -n '909,923p' .claude/skills/apply-mr-workflow-to-project/scripts/install-to-project.sh
  # **失敗しても中断しない（警告のみ）。** ここに到達した時点で core / seed / merge の配置は
  # 済んでおり、`.gemini/` が無いこと以外は完了している。中途半端な状態で止めるほうが害が大きい。
  # とくに配布先が自前の `.gemini/` を持っていた場合、生成側の削除ファイル検出が働いて
  # **1バイトも書かずに中断する**ので、何も壊さずに警告だけが残る。
  ...
  if [ -f "${DEST_DIR}/.claude/scripts/src/sync-gemini-assets.sh" ]; then
    ( cd "$DEST_DIR" && bash .claude/scripts/src/sync-gemini-assets.sh ) || {
      printf '警告: .gemini/ の生成に失敗しました。配布先で次を実行してください:\n' >&2
      printf '  bash .claude/scripts/src/sync-gemini-assets.sh\n' >&2; }

警告は2系統出る。

  1. installer が 警告: .gemini/ の生成に失敗しました… を標準エラーへ出す。
  2. その前段で sync 自身が エラー: .gemini/ に、生成物へ含まれないファイルが N 件あります ＋全件の一覧＋消してよければ --force を付けて再実行してください（この実行では1バイトも書き込んでいません） を標準エラーへ出す。
それでも残る2つの弱点
  1. installer の終了コードが0のままである。 .gemini/ が更新されていないのに、インストールは成功として終わる。標準エラーを読まない自動実行（CI等）では検出できない。
  2. 案内される復旧コマンドに --force が無い。 そのまま実行しても同じ理由で再び失敗する（--force を案内しているのは sync 自身のエラーメッセージのほうで、installer の案内ではない）。

この失敗が起きる条件は「除外を実装したとき」ではない。 条件は生成物に含まれないファイルが配布先の .gemini/ に1件でもあることで、除外の実装はそのうちの一例にすぎない。sync-gemini-assets.sh のヘッダが、現行で起きる別の経路を名指ししている。

$ sed -n '9,10p' .claude/scripts/src/sync-gemini-assets.sh
# 再生成は .gemini/ の丸ごと置き換えなので、そのままでは手で置いたファイルが黙って消える
# （配布先が自前の .gemini/commands/*.toml や settings.json を持っている場合が該当する）。

つまり自前の .gemini/commands/*.toml を持つ配布先では、案1のままでも今日この状態が起きうる。「案1を採ったので実害が無い」とは言えない（「設計への反映」6）。

除外を実装する場合に限れば、これは「機械的に直せる追随箇所」ではなく配布先ごとに1回だけ必要な移行手順になる。移行方針として (a) spec へ手順を書いて手動実行に委ねる (b) install-to-project.sh 側で残骸を先に消す (c) 何もしない、の3択を計画に置いたが、案1を採るため今回はいずれも不要になった。

それでも、この経緯から言えることが1つ残る

リンク運用時代は複製が生じないので対象を広く取るコストがほぼゼロだったが、issue #70 でコピーへ変えた時点でそのコストは生じるようになった。にもかかわらず、「.claude/ 配下を全部コピーしてよいか」という問いは立てられていない（i0070-01 が問い直したのは agents/ の欠落であって、全件列挙の是非ではない）。

issue #172 はその問いに触れる初めての機会である。 ただし本issueの問い方（「3ディレクトリを外すか」）は切り方が合っていない——正しい問いは「.gemini/ に何を置くべきか」であり、それには Gemini CLI の読み込み経路の観測が要る（「設計への反映」2）。

採否の判断そのもの

3つとも残す（案1）。 決め手は次の3点で、いずれも3ディレクトリに共通して効く。

  1. 外しても配布物は1バイトも減らない（dist-layers.json で .gemini は layer: exclude）。得られるのはこのリポジトリと配布先で生成される .gemini/ のサイズだけで、失うもの（壊れたリンク・配布先の移行・未観測の推論への依存）と釣り合わない。
  2. 部分的に外すと、完全なコピーでも不在でもない中間状態になる。 .gemini/ の価値は「.claude/ と同じものが一式そろっている」ことにあり、大半を落として壊れたリンクを残すのは、残す・全部消すのどちらよりも悪い。落ちる割合は案によって違い、案3で81.9%（176/215ファイル。バイト数なら 2,487,723/3,159,948 = 78.7%）、案2で28.4%（61/215ファイル）である。
  3. 外す根拠は未観測の推論であり、しかも対象を選べない。 同じ根拠が .gemini/rules/ .gemini/skills/ にも当たる以上、3ディレクトリだけを外す線引きに根拠が無い。
取り消しやすい側へ倒した

残す側の失敗は「複製が残る」で、気づいた時点でいつでも外せる。外す側の失敗は「配布先の再適用が片肺になる」で、警告は出るが installer の終了コードは0のままなので、標準エラーを読まない経路では --check を回すまで気づけない（結論7）。非対称なので取り消しやすい側へ倒した。

再検討の条件

「永久に外さない」ではない

この判断は「いま外す根拠が無い」であって、「永久に外さない」ではない。 次のいずれかが起きたら、.gemini/ に何を置くかを問い直す。

#条件何を確かめるか判断がどちら向きに動くか
1Gemini CLI のソースコードを参照できる環境が用意された（2026-08-23、ユーザーの判断で別環境へ委ねた。このセッションでは未着手）.gemini/rules/ .gemini/docs/ .gemini/hooks/ .gemini/scripts/ が実際に読まれるか（.gemini/skills/ .gemini/agents/ は公式ドキュメントで読まれることを確認済み）。あわせて .agents/skills/ を Claude Code が読むかも確認する（論点3）4つとも読まれないと確認できた → 決め手3後半の「未観測の推論」が解消し、外す判断の根拠が明確になる（外すかどうか自体は改めて判断する。範囲がissue #172を越える場合は別issueへ）。いずれか読まれると確認できた → その対象は除去候補から外れ、残す根拠が確定する

4.gemini/ の生成方式そのものが変わった（配布物へ含める・差分更新にする等）dist-layers.json の .gemini が exclude でなくなれば、「配布物は1バイトも減らない」という決め手（判断1）が崩れる外す側へ動く
