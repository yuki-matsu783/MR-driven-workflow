結論4: 3ディレクトリは独立に決められない

issue #172 は3ディレクトリを並列に問うており、全体作業計画も「1つずつ独立に結論を出す」と書いた。軸1・軸3・軸4は独立に評価できるが、軸2は独立ではない。

決め方hooks/ の軸2scripts/ の軸2docs/ の軸2
3つとも残す———
hooks/ scripts/ だけ外す11—
3つとも外す0018

hooks/ と scripts/ の軸2は、docs/ の採否に依存して 1 にも 0 にもなる。 「独立に結論を出す」という方針は、軸2に関しては最初から成立していなかった。これは調査で数えたときには「hooks 1・scripts 1・docs 18」という並びに見えていて、依存関係としては読み取っていなかった。

結論5: 案2（hooks/ scripts/ だけ外す）を却下した理由

2つある。どちらか一方でも成り立てば却下に足りる。

  1. 残る .gemini/docs/ から2件の壊れたリンクが出る（上記）。「外す対象の中で完結するから実害が無い」という説明が使えない唯一のケースで、.gemini/ を見る読み手には壊れたリンクとして見える。
  2. 軸1の根拠が .gemini/rules/ にも当たる（調査 Q3-b）。「そのパスを実行時に読む経路が無い」という根拠は、.gemini/rules/ .gemini/skills/ にも同じ強さで当たる。にもかかわらず3ディレクトリだけを外すなら、なぜ rules/ skills/ は外さないのかを説明できなければならない。説明は見つからなかった（.gemini/rules/ を残す理由として提示できるのは「人間が .gemini/ を眺めたときに読める」ことだけで、それは .gemini/docs/ にも等しく当てはまる）。

結論6: 案3（3つとも外す）を却下した理由

軸2は0件にならず18件で、これを許容するかどうかの判断になる。許容してよいと言い切れる根拠が無いと判断した。

  • 18件が「誰も読まないファイルの中の壊れたリンク」だと言うには、.gemini/rules/ .gemini/skills/ が読まれないことが要る。それは未観測の推論である（調査 Q3-b・結論9）。
  • 仮にその推論が正しいなら、.gemini/rules/ .gemini/skills/ も同時に外すのが筋であり、それは issue #172 のスコープ外である。「18件の壊れたリンクを抱えた .gemini/rules/ を残す」という中間状態は、どちらの前提から見ても正当化できない。
  • 加えて次の結論7がある。

結論7: 除外は既存の配布先で無言の移行失敗を起こす（実測）

$ sed -n '920,923p' .claude/skills/apply-mr-workflow-to-project/scripts/install-to-project.sh
  if [ -f "${DEST_DIR}/.claude/scripts/src/sync-gemini-assets.sh" ]; then
    ( cd "$DEST_DIR" && bash .claude/scripts/src/sync-gemini-assets.sh ) || {
      printf '警告: .gemini/ の生成に失敗しました。配布先で次を実行してください:\n' >&2
      printf '  bash .claude/scripts/src/sync-gemini-assets.sh\n' >&2; }

sync-gemini-assets.sh の write モードは、生成物に含まれないファイルが1件でもあれば --force が無い限り1バイトも書かずに中断する。除外を実装した版を既存の配布先へ再適用すると、配布先に残っている3ディレクトリがこの検出に掛かって sync が失敗する。ところが手順7は || { 警告 } で続行するため、次のことが同時に起きる。

無言で片肺になる
  1. 配布先には古い3ディレクトリが残ったままになる。
  2. インストール自体は成功したように見える。
  3. 以後その配布先で --check が落ち続ける（手動で --force を実行するまで回復しない）。
  4. 案内される復旧コマンドにも --force が無いため、配布先の人がそのまま実行しても同じ理由で失敗する。

これは「機械的に直せる追随箇所」ではなく、配布先ごとに1回だけ必要な移行手順である。移行方針として (a) spec へ手順を書いて手動実行に委ねる (b) install-to-project.sh 側で残骸を先に消す (c) 何もしない、の3択を計画に置いたが、案1を採るため今回はいずれも不要になった。

結論8: 現在の集合は「リンク運用時代の TARGETS」の引き継ぎである

$ sed -n '15,16p' .claude/docs/ddr/i0070-01-*.md
`.gemini/` は `settings.json` 以外（`docs/` `hooks/` `rules/` `scripts/` `skills/`）を
`.claude/` 配下へのローカルリンクとして持ち、`setup-gemini-links.sh` が各開発者のマシン上で

DDR i0000-13 のタイトルは「.gemini/配下のリンク（docs/hooks/rules/scripts/skills）は…」で、この5つがリンクとして選ばれた理由は「Gemini CLIとClaude Code間でルール・スキル・スクリプトの二重管理を避ける」ことだった。リンクである限り複製は生じないので、対象を広く取るコストはほぼゼロだった。

issue #70（DDR i0070-01）が方式をリンクからコピーへ変えたとき、この集合そのものは再検討されていない。結果として、複製が生じない前提で選ばれた集合が、複製が生じる方式へそのまま持ち越されている。

正しい問いは何か

issue #172 はこの点を正面から問う初めての機会である。 ただし本issueの問い方（「3ディレクトリを外すか」）は、この経緯から見ると切り方が合っていない——正しい問いは「.gemini/ に何を置くべきか」であり、それには Gemini CLI の読み込み経路の観測が要る。

採否の判断そのもの

3つとも残す（案1）。 決め手は次の3点で、いずれも3ディレクトリに共通して効く。

  1. 外しても配布物は1バイトも減らない（dist-layers.json で .gemini は layer: exclude）。得られるのはこのリポジトリと配布先で生成される .gemini/ のサイズだけで、失うもの（壊れたリンク・配布先の移行・未観測の推論への依存）と釣り合わない。
  2. 部分的に外すと、完全なコピーでも不在でもない中間状態になる。 .gemini/ の価値は「.claude/ と同じものが一式そろっている」ことにあり、82%を落として壊れたリンクを残すのは、残す・全部消すのどちらよりも悪い。
  3. 外す根拠は未観測の推論であり、しかも対象を選べない。 同じ根拠が .gemini/rules/ .gemini/skills/ にも当たる以上、3ディレクトリだけを外す線引きに根拠が無い。
取り消しやすい側へ倒した

残す側の失敗は「複製が残る」で、気づいた時点でいつでも外せる。外す側の失敗は「配布先で無言に壊れる」で、--check を回すまで気づけない。非対称なので取り消しやすい側へ倒した。

確かめられなかったこと

  • Gemini CLI 実機の挙動は一切観測していない（command -v gemini が空）。軸1の「0件」も結論5-2の「rules にも当たる」も、生成物と設定から導いた推論である。この判断は未観測のまま行った。
  • .gemini/rules/ .gemini/skills/ .gemini/agents/ を外すべきかは判断していない（本issueのスコープ外）。結論5-2で使ったのは「同じ根拠が当たる」という整合性の指摘までで、それらを外すべきだとは言っていない。
  • 複製が実際にどれだけの害を出しているかは測っていない。 案1の難点として挙げた「grep の二重計上」は、フェーズ2の調査で実際に踏んだ1件だけが根拠である。
  • 配布先での再適用は実行していない。 結論7は install-to-project.sh と sync-gemini-assets.sh を読んで導いたもので、実際に古い .gemini/ を持つ配布先へ再適用して観測したわけではない（案1を採るため、この検証は不要になった）。
  • git bash（Windows）実機での確認はしていない。 --check の所要時間・テストの結果は Linux 1環境のものである。
