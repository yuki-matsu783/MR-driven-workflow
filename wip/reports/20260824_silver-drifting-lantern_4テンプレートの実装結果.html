  1. 1

    4テンプレートを共通パーツから組み立てた △注意 根拠: 実装

    「共通DOM＋4通りの <style>」を、コピーではなく組み立てで実現した。 scratchpad にパーツを置き、build 関数で連結している。

    パーツ内容共有
    head-common.txt使い方コメント（124行）4本で共通
    body.htmlDOM本体（216行）4本で共通
    style-common.partスタイルの骨格（143行。CSS変数を参照するだけ）4本で共通
    style-<design>.partCSS変数の定義＋デザイン固有の上書き（18〜43行）デザインごと

    結論

    組み立ての順序が要点で、<style> の中は「共通の骨格 → デザイン固有」の順にしている。逆にすると、同じ詳細度の規則で共通側が勝ち、デザイン固有の上書きが効かない。CSS変数は共通骨格より後ろで定義されていても問題ない（カスタムプロパティはスタイルシート全体を読んでから解決されるため）。

    「組み立てたから同一である」とは言えなかった

    冒頭コメントの中にデザイン固有の説明を書いていたため、共有パーツから組んでいても4本のうちその部分だけが異なっていた（f2）。組み立ては同一性を作りやすくするが、保証はしない。検証が要る。

  2. 2

    DOM共通性を「バイト単位」で検証した △注意 根拠: 実測

    計画の中心的な主張なので、主張したまま検証しないことはしない。

    最初に書いた検証は、タグ名の並びしか比べていなかった

    grep -oE '</?[a-z][a-z0-9]*' は属性もテキストも見ないため、「タグ構成は同じだが中身が違う」状態を素通りする（敵対的レビュー2回目の指摘）。<style> を除いた残り全体をバイト単位で比較する形へ改めた。

    根拠を見る（実行コマンドと結果） 
    $ tmp=$(mktemp -d)
$ for F in reports-clean reports-neobrutal reports-mono reports-paper; do
    sed '/^<style>$/,/^<\/style>$/d' "$F.template.html" > "$tmp/$F.nostyle"
    n=$(wc -l < "$tmp/$F.nostyle")
    [ "$n" -lt 100 ] && { echo "FAIL $F: 抽出が $n 行"; exit 1; }   # 空振りガード
  done
reports-clean     : 359行 22346バイト
reports-neobrutal : 359行 22346バイト
reports-mono      : 359行 22346バイト
reports-paper     : 359行 22346バイト

$ for v in reports-neobrutal reports-mono reports-paper; do
    diff "$tmp/reports-clean.nostyle" "$tmp/$v.nostyle"
  done
比較した組数=3 不一致の組数=0

    改めた結果、実際に差分が出た

    冒頭コメントの中にデザイン固有の説明文を置いていたため、4本のうちその8〜9行だけが異なっていた。タグ名の比較ではこの差が一切見えていなかった。
    修正: デザイン固有の説明を冒頭コメントから <style> ブロック先頭のCSSコメントへ移した。冒頭コメントには「デザインの説明は <style> 冒頭にある」という4本共通の1行だけを残した。

    結論

    <style> を除いた部分は4本とも 359行 / 22346バイト で完全に一致する（テンプレート全体は clean 529行 / neobrutal 543行 / mono 558行 / paper 547行。差は <style> だけ）。DOMを共有できているため、使い方コメント・プレースホルダ・検査手順を1回書けば4本へ同じものが配れる。

    最初の検証コマンドには、もう1つ誤りがあった

    sed '/^<style>/,/^<\/style>/d' は <style> ブロックしか落とさないため、使い方コメントの地の文にある <section> <li> <code> がタグとして数えられていた（289タグ ＝ 本文282＋コメント由来7）。バイト比較へ移行したことで、この問題も同時に解消した（コメントも含めて比較対象になり、かつ4本で一致するため）。

  3. 3

    5種の検査を4本へ流した ◎良 根拠: 実測

    検査cleanneobrutalmonopaper
    1. プレースホルダ（雛形なので>0が期待）24242424
    2. リンク破断（0行が合格）0000
    3. 重複ID（出力なしが合格）なしなしなしなし
    4. 外部依存 src/href0000
    5. 外部依存 url()/@import0000

    「出力なし＝合格」は、負のコントロールを取って初めて意味を持つ

    cleanのコピーを意図的に壊し、検査が反応することを確かめた。空振りガード（拾えた件数）は href=12 / id=8 で、0でないので検査は働いている。

    壊し方リンク破断重複ID
    href="#f1" → #f99f99 を検出反応せず（正しい）
    <h3 id="f1"> → id="overview"f1 を検出overview を検出

    後者の1操作で両方が反応することが、2つの検査を持つ理由をそのまま示している。

    結論

    プレースホルダが4本とも同数（24）であることが、使い方コメントとDOMを共有できている傍証になる。
    プレースホルダ検査の合格条件は、テンプレート本体と成果物で逆になる。 テンプレートは雛形なのでプレースホルダが「ある」ことが正しく、成果物では「0件」が正しい。この読み替えを使い方コメントへ明記した（書かないと、テンプレート自身を検査して不合格と誤判定される）。

  4. 4

    タグの開閉バランスを検証した △注意 根拠: 実測

    開きタグと閉じタグの数を要素ごとに数えたところ、4本すべてで li が 22対21、details が 2対1 という不一致が出た。

    原因はテンプレートではなく検査側だった

    本文中のHTMLコメントに、地の文として <li> <details> と書かれた箇所が1つずつある（「タイムラインの <li> には入れない」「長い出力は <details> で折りたたむ」）。HTMLコメントの中身はタグとして解釈されないので、実際のDOMは正しく閉じている。

    結論

    コメントを除去してから数え直すと、section aside main div ol ul li details table thead tbody tr のすべてで開閉が一致した。この書き方は現行 reports.template.html から続く既存のスタイルで人間が読むうえで自然なので変えず、直したのは検査コマンドの側である。
    これは f2 と同じ種類の失敗が別の検査で再び出たもので、「HTMLを機械的に検査するときは、コメントと地の文を先に除く」がこのテンプレート群の一般則だと分かった。
