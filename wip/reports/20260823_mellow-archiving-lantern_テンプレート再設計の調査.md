## 実施した内容と結果

### 1. 二重管理の解消方式 → 案B（テンプレートファイルを正とする）

**判断**: `.github/pull_request_template.md` を**唯一の正**とし、`describe` 節は見出し構成を列挙せず
「テンプレートファイルを読んで、その見出し構成に従う」と指示するだけにする。
`.gitlab/merge_request_templates/Default.md` は GitHub 版の複製とし、**先頭のHTMLコメントを除いた
本文が一致していること**をテストで機械的に保証する（正の実体は1つ、プロバイダ向けの複製が1つ、
という関係にする）。

**保証範囲を「見出し行だけ」に留めない。** 現行テストは `^(Closes|## )` で**見出し行しか**
比べておらず、それだけでは各節のHTMLコメント（＝記入ガイド。10節構成の実質的な中身）が
片方だけずれても検出できない。**先頭のHTMLコメントブロックだけを除外した全文差分**を検査する。

**先頭のHTMLコメントはプロバイダ固有で、一致させない。** GitLab版だけが `Default.md` という
予約名の説明（DDR `i0032-01` への参照）を持つ。除外するのはこのブロックだけである。

**根拠**

- **同じ判断の先例がある。** `references/deliverables.md`「計画・レポートのHTMLビュー」は
  「**記述の型（見出し構成）の正はテンプレート側にあり、SKILL.md（フロー定義）は列挙しない**
  （二重管理を避けるため。型を変えたいときは、フロー定義である SKILL.md ではなくテンプレートの
  中身を差し替える）」と、issue #54 で既に同型の判断を下している。**本issueはこの原則を
  PR/MRテンプレートへ広げるだけ**であり、新しい方針を持ち込まない。
- **テンプレート2本は `core` 層である。** `.claude/dist-layers.json` は `.github` / `.gitlab` を
  `core`（配布元所有・常に上書き）とし、note に「issue/PRテンプレート。見出しが `start`・`describe` と
  **機能的に結合**」と書いている。配布先が改変しても再適用時に `.bak` へ退避して上書きされる
  （`.claude/docs/spec/asset-distribution.md` の層の表）。
  - **ただし `core` が保証するのは「再適用を実行した時点で本家の内容へ戻る」ことだけである。**
    再適用と再適用の間に配布先がテンプレートを書き換えれば、案Bの `describe`（ローカルの
    テンプレートを読んで見出しを決める）は書き換え後の内容を読む。**「配布先でも中身は常に
    本家と一致する」とは言えない**（ドリフトは次の再適用まで残る）。
  - それでも案Bを採れるのは、**ドリフトした場合に読まれるのが「配布先自身が書いた見出し」で
    あって、無関係な別物ではない**からである。配布先が意図してテンプレートを変えたなら
    `describe` がそれに従うのはむしろ正しい挙動であり、意図していないなら再適用で戻る。
- **MCP経路でも動く。** `describe` が行うのはローカルファイルの読み込みであり、経路に依存しない。
  どちらのテンプレートを読むかの判定は `get_provider` で足りる。**出典は `Provider.sh` の実装
  である**（`git remote get-url origin` の結果を `provider_from_remote_url` へ渡すだけで、CLIを
  一切呼ばない）。`references/mcp-fallback.md` の対応表に `get_provider` の行は**無い**ため、
  対応表を根拠に挙げない（同表で「MCP不要」に分類されているのは `get_repo_url` 等の別関数で、
  「`git remote get-url origin` の正規化だけで決まるプロバイダ非依存の関数」という説明文は
  そちらのものである）。
- **人間がWeb UIで作るPRでも見出しが得られる**（案Cが失う性質）。

**採らなかった案**

| 案 | 内容 | 却下の理由 |
|---|---|---|
| 案A | `describe` の手順を「テンプレートを読み込む」へ変え、`describe` 節にも雛形を残す | 雛形が残る限り二重管理が解消しない。読み込む手順を足すだけでは「どちらが正か」の曖昧さが残る |
| 案C | `describe` 節を正とし、テンプレート側は参照だけにする | GitHub/GitLabはテンプレートファイルの中身をそのままPR作成画面へ入れるため、**人間が手で作るPRで見出しが1つも得られない**。テンプレートを置く意味が失われる |

**副次的に判明したこと（案の評価に効く）**

- **フローどおりに作られたPR/MRは、テンプレートファイルの中身を一度も経由しない。**
  Draft PR/MRの初期本文は `Github.sh` / `Gitlab.sh` の `new_draft_merge_request` に
  `Closes #%s\n\n(plan作成中。/issue-mr-flow describe で更新する)` としてハードコードされており、
  MCP経路でも `references/mcp-fallback.md` の対応表が同じ文字列を指定している。
- **この初期本文は10節構成へ合わせない。** 初回の `describe`（flow-id 2-5）で全文置換されるため
  実害が無く、合わせると「まだ何も無い状態の10節」が一時的に残るだけで、かえって読みにくい。
  **合わせないという判断そのものを、テンプレートのHTMLコメントへ1行残す**（後から見た人が
  「初期本文が古いテンプレートのままだ」と誤解しないため）。

**既存テストの扱い**

`.claude/scripts/test/test_install_to_project.sh` は現在、`review-loop.md` の `describe` 節から
`^(Closes|## )` の行を `awk` で抜き出し（抽出できた行数が `3` であることも表明）、テンプレート2本と
3者一致を検査している。案Bでは `describe` 節が雛形を失うため、**この抽出は空振りする**。

置き換え方針は次のとおり。

1. 抽出元を `review-loop.md` から**やめる**。
2. 代わりに、**期待値の10節をテスト内へ書き下す**。テンプレート2本の見出しが、この期待値と
   順序込みで一致することを表明する。
3. **テストの期待値は「二重管理」に数えない。** 期待値は正ではなく**検査**であり、これが無いと
   「2本を比べるだけでは足りない（両方が同時にずれると通ってしまう）」という既存テストの
   コメントが守れなくなる。ただし更新が必要な場所であることに変わりはないため、
   **その旨をテスト側のコメントへ明記する。**
4. 抽出行数の固定値 `3` は残さない。「期待値が非空であること」の表明で空振り防止の目的は満たされる。

### 2. issue #111（flow-id 5-4）との役割分担 → 併存させ、自動化の非対称で分ける

**判断**: MR description と最終統括レポートのサマリコメントは**どちらも残す**。役割は次のとおり。

| | MR description（本issue） | サマリコメント（flow-id 5-4 / issue #111） |
|---|---|---|
| 位置づけ | **flow-id 4-10 時点の全体像**（`describe` の最後の実行。それ以降は自動では更新されない） | **flow-id 5-4 時点の1回きりのスナップショット** |
| 更新 | `describe` が6回（2-5/2-10/3-5/3-10/4-5/4-10）**全文置換**する | ブランチにつき**1回だけ**投稿。以後編集しない |
| 自動更新 | **毎回まるごと上書きされる**（`describe` が全置換する） | **自動では上書きされない**（このリポジトリの自動化経路に、投稿済みコメントを編集する手段が無い） |
| 粒度 | 10節。受け入れ条件との突き合わせ・レビューの結果まで含む | 5見出し（何を変えたか／なぜそうしたか／検証結果／spec・DDRへの反映先／残課題） |
| 1行目 | — | `Claude Codeより（最終統括レポート）:` |

**根拠**

- **重複は意図的な冗長である。** 同じ内容を「自動で上書きされる場所」と「自動では上書きされない
  場所」の2つで持つことに価値がある。`describe` が何度回ってもサマリコメントは書き換わらない。
- **根拠は「自動化の非対称」に限る。** 確かめたのは、このリポジトリの自動化経路
  （`Provider.sh` にあるのは `add_mr_comment` / `add_issue_comment` / `set_mr_description` /
  `add_mr_thread_reply` だけで、投稿済みコメントを編集する関数が無い）であって、
  **GitHub/GitLab上でコメントが編集できないという外部APIの性質ではない**。
  - **限界**: 人間はWeb UI・APIからコメントを編集・削除できる。MCP経路も `Provider.sh` を
    通らない。したがって「サマリコメントは絶対に書き換わらない」とは言えず、正しくは
    **「フローの自動処理が繰り返し上書きするのはdescriptionだけである」**。
  - この区別を落とすと、`reports/REVIEW-POINTS.md` の「制約が外部APIの制約なのか、この
    リポジトリの実装の欠陥なのかを取り違えていないか」に抵触する。
- サマリコメントの5見出しは、新しい10節の**部分集合として読める**。次の対応関係を仕様へ記録する。

  | サマリコメントの見出し | descriptionの対応節 |
  |---|---|
  | 何を変えたか | `## 概要` ＋ `## 変更内容` |
  | なぜそうしたか | `## 設計判断・採らなかった案` |
  | 検証結果 | `## 検証` |
  | spec・DDRへの反映先 | `## 反映先・関連` |
  | 残課題 | `## 未解決・限界・確かめられなかったこと` ＋ `## 意図的にやらなかったこと・スコープ外` |

- **flow-id 5-4 の実装（`upload_attachment`・3層フォールバック・見出し構成）は変更しない。**
  本issueで行うのは役割の**定義**だけである（全体作業計画のスコープ外の項目）。

**採らなかった案**

| 案 | 却下の理由 |
|---|---|
| サマリコメントを廃止し description へ一本化する | #111 が「層2（サマリのコメント投稿）は必須」と定めた設計を壊す。descriptionは上書きされうるため、「ファイルが消えても残る」実体が無くなる |
| サマリコメントを description へのリンク1行だけにする | 同上。リンク先が書き換われば記録も変わってしまい、スナップショットにならない |

### 3. `plans/` `worklog/` `reports/` 参照禁止の書き場所

**判断**: 次の2箇所へ書く。**例外は設けない。**

1. **`.claude/rules/docs-workflow.md`**: 既存段落「コード・スクリプト内のコメントから
   `plans/` `worklog/` `reports/` のファイルを参照しない」（64〜69行目）と、
   **その例示であるコードブロック（71〜76行目の「悪い例／良い例」）の後**、つまり
   **76行目の直後**へMR/PR本文についての段落を足す。
2. **テンプレート2本のHTMLコメント**: `## 反映先・関連` 節の記入ガイドとして、同じ禁止と
   「代わりに何を書くか」を書く。

**根拠**

- **挿入位置は「段落の直後」ではなく「コードブロックの後」である。** 該当の段落（64〜69行目）は
  一般則（「恒久的に参照してよいのは、issue番号と `.claude/docs/spec/` `.claude/docs/ddr/`
  `.claude/docs/usecase/` 配下のファイル」）で文としては終わっているが、**その直後に空行を挟んで
  例示のコードブロック（71〜76行目）が続く**。ここへ割り込ませると、コード例が新しい段落
  （MR/PR本文の話）の例示として読める位置へ移り、`.claude/rules/docs-workflow.md` 自身が禁じている
  **係り先の破壊**がまさに起きる。
  - **「見出しの差し込みではなく段落追加だから、その注意の対象にならない」とは言えない。**
    同ルールが守ろうとしているのは「地の文の係り先を変えないこと」であり、割り込むのが見出しか
    段落かは関係しない。
  - 76行目の直後（`**ファイル移動に伴うパス参照の一括置換は…` の直前）へ置けば、既存の
    段落＋コード例のまとまりを崩さず、その一般則の適用範囲を広げる形で読める。
- **「参照しない」だけでは足りない。** 何を書くかまで示す。
  - `reports/` の結論は、`## 検証` `## 設計判断・採らなかった案` へ**転記する**（リンクしない）。
  - spec/DDRへ昇格したものは、そのパスで指す。
  - issue番号・PR番号・レビューコメントのpermalinkは恒久なので、これらで代替する。
- **例外を認めない。** 「レビュー中はまだ存在するので参照が有効に見える」という状況こそが罠で、
  レビュー時に踏めた参照がマージ後に必ず切れる。issue #145 が集計した「64件中52件」が
  まさにこの経路で生まれている。

### 4. 10節構成と `describe` の6回の全文置換

**判断**: 噛み合う。ただし次の3点を規約として決める。

1. **「特になし」と「未実施」を書き分ける。**
   - `特になし` = 検討した結果、書くことが無かった。
   - `未実施` / `このフェーズではまだ確定していない` = まだその段階に達していない。

   issue #145 は「該当が無ければ『特になし』と1行書いて残す」と定めているが、**まだ書けない節に
   『特になし』と書くと、検討済みと誤読される**。両者を区別する語をテンプレートのHTMLコメントで定義する。
2. **各節の「計画段階では何を書くか」をHTMLコメントで定める**（issue #145 の受け入れ条件）。
   たとえば `## 検証` は計画段階では「未実施（フェーズ3で実施予定の検証を列挙）」、
   `## レビューの結果` は「未実施（まだレビューを受けていない）」と書く。
3. **descriptionの最終形は flow-id 4-10 で完成させる。ただし「常に最新」ではない。**
   `describe` の最後の実行は 4-10 であり、`plans/` `worklog/` `reports/` の削除（flow-id 5-5）は
   その**後**である。つまり最後の `describe` の時点では材料がまだ全部そろっている。
   この順序を仕様へ明記しておかないと、「材料が消えた後に書こうとして書けない」という
   読み違いが起きうる。
   - **その代わり、4-10 より後のステップの変更はdescriptionへ載らない。** flow-id 5-3
     （`.gemini/` 変換同期）・5-4（統括レポートの作成・commit・push）・5-5（`plans/` 等の削除）は
     いずれも**成果物を変更する**ステップであり、マージ時点のdescriptionはこれらを含まない。
     影響を受けるのは `## 変更内容` `## 検証` `## レビューの結果` の3節である。
   - **この差は許容し、5-4 の後に `describe` を追加しない。** 理由は2つ。(a) 5-3〜5-5 の変更は
     いずれも**機械的で、レビューの判断材料にならない**（変換生成物の同期・統括レポートの追加・
     作業ファイルの削除）。(b) 5-4 のサマリコメントが**まさにその時点のスナップショット**を
     担っており、二重に持つ必要が無い。**「常に最新」という言い方をやめ、
     「flow-id 4-10 時点の全体像」と書く**ことで、読み手が差の存在に気づけるようにする。

**確認した事実**

- **全文置換で前回の内容が失われる問題は、現行の3節構成にも同じようにある。** `describe` は毎回
  `get_branch_work_files` でブランチ固有の作業ファイルを読み直して本文を作り直す設計で、
  前回のdescriptionを読み込む手順は無い。10節にしても性質は変わらない。
- **`get_branch_work_files` は `plans/` `worklog/` に加えて `reports/` も列挙する**
