### Q3. 本文を許容した場合、実装・呼び出し側は耐えるか

#### (1) `create-commit.sh` は複数行メッセージを受け付けるか — **受け付ける（実装変更不要）**

実装は `--message) message="$2"` で単一の文字列引数として受け取り、`git commit -m "$message"` へ
そのまま渡す。**一時リポジトリで実際にコミットして確認した。**

```bash
bash .claude/scripts/src/create-commit.sh --message "$(printf 'feat: 件名の行\n\n本文の1行目\n本文の2行目')" -- a.txt
git log -1 --format='%s'   # → feat: 件名の行
git log -1 --format='%b'   # → 本文の1行目 / 本文の2行目
git log --oneline -1       # → 9794fb2 feat: 件名の行
```

`git commit -m` は、渡された文字列の1行目を件名、空行以降を本文として扱う。**スクリプトの変更は
1行も要らない。**

#### (2) 複数行メッセージをどの経路で渡すか — **`--message` への埋め込みで問題ない**

計画で挙げた3つの制約を個別に確かめた。

| 制約 | 判定 | 根拠 |
|---|---|---|
| コマンド位置判定（`command-position.md`）が誤発火しないか | **発火しない** | `CommandPosition.sh` を `source` して直接呼び、本文に「git commit」という語を含む複数行メッセージで `command_invokes_git_subcommand ... commit` が非0（対象外）を返すことを確認した |
| 1行8192バイト超で部分一致へ縮退する | **むしろ有利** | `_CP_MAX_LINE_LENGTH` は**1行あたり**の上限である。本文を許すと1行が短くなるため、縮退しにくくなる。上のテストでの最長行は76バイト |
| 長文はファイル経由で渡す既存方針 | **該当しない** | この方針の主たる理由は**jqの引数長上限**（`shell-script-style.md`「JSON操作」）だが、`create-commit.sh` は **jqを1回も呼ばない**（`grep -c jq` → 0）。プロセス引数長の上限（約32KB）は残るが、コミットメッセージがそのサイズに達することは実務上ない |

**結論: `--message-file` の新設は不要。**

### Q4. squash merge時に本文はどう畳まれるか

**実測できる3項目と、実測できない1項目に分かれる。**

| 部分 | 結果 | 根拠の性質 |
|---|---|---|
| `main` の1行ログに何が出るか | **PRタイトル + ` (#PR番号)`**。直近10件すべてがこの形（例: `.claude/state を wip/state へ移す（issue #184） (#190)`） | **実測** |
| 個別コミットの件名がsquash本文へどう並ぶか | `* <件名>` を空行区切りで羅列 → `---------` → `Co-authored-by: Claude <noreply@anthropic.com>` | **実測** |
| gitの `--squash` が本文をどう畳むか | **本文も含めて畳む**。一時リポジトリで本文付きコミットを作り `git merge --squash` したところ、`.git/SQUASH_MSG` に件名・本文の両方が入った | **実測** |
| **GitHubのsquash mergeが本文をどう畳むか** | **未確認** | **机上確認** |

**GitHub側が未確認である理由**: 現行規約が1行のみを強制してきたため、`main` の履歴に**本文を
持つコミットが1件も存在しない**（畳まれた80行のいずれにも本文が無い）。squash本文の生成は
GitHubのサーバ側の挙動で、ローカルの `git log` では再現できない。確かめるには、このリポジトリの
`main` へ本文付きコミットを含むPRをsquash mergeする必要があり、**検証のために正史を書き換える
ことになる**ため実施しなかった。

**この未確認は方針決定のブロッカーにならない。** 理由は次の2点である。

1. **読み手が最初に見る1行はPRタイトルで、これは個別コミットのメッセージ形式と独立している。**
   本文を許しても許さなくても、`--oneline` の見え方は変わらない。
2. **本文が畳まれなかった場合でも、失うものが無い。** 本文は「1行に収まらないときの逃がし先」で
   あり、件名の質を落とす言い訳にしない（後述の規約でそう明記する）。件名だけが畳まれる最悪の
   ケースでも、現状より情報量が減ることはない。

## 確かめられなかったこと

- **GitHubのsquash mergeが、本文を持つコミットの本文をsquash本文へ含めるか**（Q4）。
  理由は上記のとおり、履歴に本文付きコミットが1件も無く、確かめるには `main` の正史を
  検証のために書き換える必要があるため。**方針決定には影響しない**ことを Q4 に示した。
- **git bash（Windows）実機での挙動**。Q3の実測はすべてLinux（Claude Code on the web）で行った。
  `create-commit.sh` の改行の扱いは `git commit -m` へ委ねられており処理系差は考えにくいが、
  **未計測であることは事実として記す**。
- **`main` の全履歴に対する欠落パターンの分布**。母数を直近5件（80行）に固定したため、
  それ以前の傾向は測っていない。issue本文が挙げた issue #110 の実例は母数の外にある。

## 設計への反映（フェーズ3へ渡すもの）

1. **方針は「件名1行は必須・本文は任意で許容」を推す。** Q3で実装変更が不要と確かめられ、
   Q4で本文が畳まれなくても損が無いと言えるため、採用コストがほぼゼロである。一方で
   Q5が示すとおり、**1行に収まらない内容を要求している既存の規約が既にある**
   （`issue-mr-flow/SKILL.md:229`）。この衝突は本文を許容しないと解消しない。
2. **規約の主役は件名（1行目）の内容規約である。** Q2の実測が示すのは「長さが足りない」ことでは
   なく「**長い行でも中身が無い**」ことなので、文字数を緩めるだけでは直らない。
   満たすべき要素を列挙する形にする。
3. **「mainに残らない成果物のみのコミット」（母数の58%）の書き方を規約へ含める。**
   これが履歴の過半を占めている以上、「そういうコミットは短くてよい」と明示的に許すか、
   何を書かせるかを決めないと、規約が守られない側の多数派になる。
4. **PRタイトルが1行ログに出るという事実を規約へ書く**（Q2の新類型・Q4）。読み手が最初に見る
   1行はPRタイトルなので、コミットメッセージの規約とは別に、その事実を明示しておかないと
   「コミットメッセージを直せば `--oneline` が読めるようになる」という誤解が残る。
5. **書き換える3行と、追随を確認する2箇所が確定した**（Q1・Q5）。
   `commit/SKILL.md:146` を差し替える際、**フッター禁止（同31行と重複）を巻き添えにしない**。
6. **検証は「0件」ではなく「書き換え対象3行が消えたこと」で判定する**（Q1）。
   `.gemini/` 側の同一コピーは flow-id 5-3 の変換同期で追随させる。

## 想定と異なった点

- **`create-commit.sh` の実装変更が要るかもしれない、という計画時の見立ては外れた。**
  改行入りメッセージはそのまま通り、hookも発火しない。「本文を許すなら実装に手を入れる必要が
  ある」という前提で方針を選ぶ必要は無かった。
- **1行の長さは制約になっていなかった。** median 85文字・max 143文字で、短く切り詰められて
  情報が落ちているのではなく、長いまま中身が無い行が多い。
- **`main` の1行ログに出るのはPRタイトルだった。** issue本文は畳まれた個別コミットの件名を
  「main へ残るコミットログ」として扱っているが、`--oneline` で見える1行はPRタイトルである。
  issueの問題意識自体は正しい（squash本文は残るため）が、**規約の効き先が1段ずれている**。
- **同じ方向の規約が既にリポジトリ内にあった**（`resolve-conflict/SKILL.md` の「何を・どう」）。
  ゼロから作るのではなく、既存の前例を一般化する形になる。

## 残課題

- **`commit/SKILL.md` の「## 備考」以下（150〜170行）が孤立している。** 開きの無い閉じフェンス
  （152行）で終わり、「レビュアーが知っておくべきこと」「変更内容の列挙ルール」という、
  PR descriptionの雛形に見える断片が残っている。ファイル新規作成時（`e87d2b4`）から
  この形で、読み手はこの節が何のためのものか判断できない。**本issueの主対象ではないが、
  同じファイルの同じ主題（何を書くか）の箇所であるため、フェーズ3で扱うか別issueへ切り出すかを
  判断する。**
