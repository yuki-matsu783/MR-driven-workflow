### Q2. 履歴の欠落パターン

母数は上記のとおり**件名80件**と、**そのうち本文を持つ6件**である。

#### 現行規約は既に守られていない（初版に無かった実測）

```bash

# → 件名エントリ総数=80 本文を持つエントリ=6
```

- **本文許容を支持する側**: 規約が実態と乖離しており、実務では本文が必要になっている。
- **規約の実効性を疑う側**: 規約を追加しても守られない可能性がある

#### issueの4類型に収まらない類型（新発見）

issue本文は「squash merge後に `main` へ残るコミットログ」として、畳まれた個別コミットの件名を
挙げていた。しかし実測すると、**`main` の1行ログ（`git log --oneline`）に出るのはPRタイトル**で
あり、個別コミットの件名は**squash本文の中にしか現れない**（Q4）。

| 見る場所 | そこに出るもの |
|---|---|
| `git log --oneline` / GitHubのコミット一覧 | **PRタイトル** + ` (#PR番号)` |
| `git log --format=%B` / GitHubのコミット詳細 | `* <個別コミットの件名>` の羅列（本文を持つものは本文も） |

**つまり読み手が最初に見る1行は、コミットメッセージではなくPRタイトルである。**
これは issue が挙げた4類型のどれでもなく、規約の設計に直接効く（後述「設計への反映」）。

### Q3. 本文を許容した場合、実装・呼び出し側は耐えるか

#### (1) `create-commit.sh` は複数行メッセージを受け付けるか — **受け付ける（実装変更不要）**

実装は `--message) message="$2"` で単一の文字列引数として受け取り、`git commit -m "$message"` へ
そのまま渡す。**一時リポジトリで実際にコミットして確認した。**

```bash
bash .claude/scripts/src/create-commit.sh --message "$(printf 'feat: 件名の行\n\n本文の1行目\n本文の2行目')" -- a.txt
git log -1 --format='%s'   # → feat: 件名の行
git log -1 --format='%b'   # → 本文の1行目 / 本文の2行目
git log --oneline -1       # → 9794fb2 feat: 件名の行
```

`git commit -m` は、渡された文字列の1行目を件名、空行以降を本文として扱う。**スクリプトの変更は
1行も要らない。**

#### (2) 複数行メッセージをどの経路で渡すか — **`--message` への埋め込みで問題ない**

計画で挙げた3つの制約を個別に確かめた。

| 制約 | 判定 | 根拠 |
|---|---|---|
| コマンド位置判定（`command-position.md`）が誤発火しないか | **発火しない** | `CommandPosition.sh` を `source` して直接呼び、本文に「git commit」という語を含む複数行メッセージで `command_invokes_git_subcommand ... commit` が非0（対象外）を返すことを確認した |
| 1行8192バイト超で部分一致へ縮退する | **むしろ有利** | `_CP_MAX_LINE_LENGTH` は**1行あたり**の上限である。本文を許すと1行が短くなるため、縮退しにくくなる。上のテストでの最長行は76バイト |
| 長文はファイル経由で渡す既存方針 | **該当しない** | この方針の主たる理由は**jqの引数長上限**（`shell-script-style.md`「JSON操作」）だが、`create-commit.sh` は **jqを1回も呼ばない**（`grep -c jq` → 0）。プロセス引数長の上限（約32KB）は残るが、コミットメッセージがそのサイズに達することは実務上ない |

**結論: `--message-file` の新設は不要。**

**実績もある**（Q2）。既にマージ済みの6件は、この経路で本文付きコミットが作られたことを示している。

### Q4. squash merge時に本文はどう畳まれるか — **4項目すべて実測**

| 部分 | 結果 | 根拠 |
|---|---|---|
| `main` の1行ログに何が出るか | **PRタイトル + ` (#PR番号)`**。直近10件すべてがこの形（例: `.claude/state を wip/state へ移す（issue #184） (#190)`） | `git log origin/main -10 --format='%s'` |
| 個別コミットの件名がsquash本文へどう並ぶか | `* <件名>` を空行区切りで羅列 → `---------` → `Co-authored-by: Claude <noreply@anthropic.com>` | `git log origin/main -1 --format='%B'` |
| gitの `--squash` が本文をどう畳むか | **本文も含めて畳む**。一時リポジトリで本文付きコミットを作り `git merge --squash` したところ、`.git/SQUASH_MSG` に件名・本文の両方が入った | 一時リポジトリでの実行 |
| **GitHubのsquash mergeが本文をどう畳むか** | **`* <件名>` の直後に空行を挟んで本文をそのまま置く。フッター（`Refs #NNN`）も落とさない** | `git log origin/main --skip=3 -1 --format='%B'`（PR #175） |

観測できる形（PR #175 のsquash本文から抜粋）:

```
* fix: 6回目の敵対的レビュー9件へ対応（DDRの実測値・検証の空振り・観点の追随漏れ）

フェーズ4〈反映〉の作業実施に対する敵対的レビュー（通算6回目）の指摘9件を、
いずれも実測で数え直したうえで9件とも受け入れて修正した。
（…中略…）
Refs #155

* docs: HANDOFF.mdのフェーズ4完了とレビュー返信を記録
```

> **注**: 初版はこの項目を「実測できない（履歴に本文付きコミットが1件も無く、確かめるには
> `main` の正史を書き換える必要がある）」としていたが、**事実に反していた**。本文を持つ
> エントリは母数の内側に6件あり、正史を書き換えずに読める。
> あわせて、初版が置いていた「本文が畳まれなかった場合でも失うものが無い」という
> 保険付きの論法は**不要になった**ため削除した。

**帰結**: 本文を書けば、その内容は `main` の履歴に**恒久的に残る**。
`wip/reports/` のように flow-id 5-5 で消えることはない。

### Q5. 規約を変えると壊れる／古くなる箇所はあるか

#### 処理 — **0件**

```bash
grep -rn "log --grep\|log --format='%s'\|log --format=%s\|%B" .claude/scripts/src .claude/hooks --include='*.sh'
```

ヒット0件。コミットメッセージを検索・パースしている処理は存在しない。
`check-base-sync.sh` は `git rev-list --left-right --count` を使うが、**数えるだけでメッセージを
読まない**。**規約を変えても壊れるスクリプトは無い。**

#### 記述 — **2箇所**

| ファイル:行 | 内容 | 追随の要否 |
|---|---|---|
| `.claude/skills/resolve-conflict/SKILL.md:373,376-378,420` | マージコミットの雛形と「何を・どう解消したかを書く」規約 | **要確認**。新しい規約と矛盾しないが、**本issueの規約が上位になるため、参照関係を整理する余地がある** |
| `.claude/skills/issue-mr-flow/SKILL.md:229` | 「確認した結果（何件見つかり、どう対処したか）を、**コミットメッセージへ必ず残す**」 | **要確認**。**1行に収まらない内容を要求している**ため、本文許容の方針と噛み合う |

**`issue-mr-flow/SKILL.md:229` は、現行の「1行のみ」規約と実質的に衝突していた。**
「何件見つかり、どう対処したか」を1行へ押し込むと、まさにissue #185 が問題にしている
「列挙で中身が削れる」形になる。**Q2で見つかった本文6件は、この衝突を実務側が本文で
解決していた証拠**でもある。

- **`main` の全履歴に対する欠落パターンの分布**。母数を直近5件（件名80件）に固定したため、
  それ以前の傾向は測っていない。issue本文が挙げた issue #110 の実例は母数の外にある
  （下記「設計への反映」7を参照）。
- **本文を持つ6件が、本文まで読めば「どう変えたか」を満たしているかの精査**。
  最長19行の1件は変更点を10項目列挙しており満たしていると判断したが、**残り5件は
  本文の中身を1件ずつ読んで判定していない**（分類は件名だけで行った）。

## 設計への反映（フェーズ3へ渡すもの）

1. **方針は「件名1行は必須・本文は任意で許容」を推す。** Q3で実装変更が不要と確かめられ、
   Q4で**本文がsquash後も恒久的に残る**と実測できたため、採用の利点が明確である。さらに
   Q2が示すとおり、**実務側は既に本文を書いており（6件）、現行規約のほうが実態から乖離
   している**。Q5の衝突（`issue-mr-flow/SKILL.md:229`）も本文を許容しないと解消しない。
2. **規約の主役は件名（1行目）の内容規約である。** Q2の実測が示すのは「長さが足りない」ことでは
   なく「**長い行でも中身が無い**」ことなので、文字数を緩めるだけでは直らない。
   満たすべき要素を列挙する形にする。
3. **「mainに残らない成果物のみのコミット」（母数の58%）と「事務的作業記録」（15%）の書き方を
   規約へ含める。** これらが履歴の過半を占めている以上、何を書かせるかを決めないと、
   規約が守られない側の多数派になる。
4. **PRタイトルが1行ログに出るという事実を規約へ書く**（Q2の新類型・Q4）。読み手が最初に見る
   1行はPRタイトルなので、コミットメッセージの規約とは別に、その事実を明示しておかないと
   「コミットメッセージを直せば `--oneline` が読めるようになる」という誤解が残る。
5. **書き換える3行と、追随を確認する2箇所が確定した**（Q1・Q5）。
   `commit/SKILL.md:146` を差し替える際、**フッター禁止（同31行と重複）を巻き添えにしない**。
   なお、そのフッター禁止は**現に6回破られている**（Q2）ため、規約を書くだけでは足りない
   可能性がある点も、DDRへ記録する価値がある。
6. **検証は「0件」ではなく「書き換え対象3行が消えたこと」で判定する**（Q1）。
   `.gemini/` 側の同一コピーは flow-id 5-3 の変換同期で追随させる。
7. **受け入れ条件4（issue本文の実例の書き直し例）の素材は、Q2の母数の外にある。**
   issue #185 の本文が挙げた9行はissue #110 のPR由来で、直近5件の窓に入らない。
   **フェーズ3ではissue本文から直接9行を引き写し、統計の母数とは別枠であることを明示する**
   （母数を広げて統計を取り直すのではない）。

## 想定と異なった点

- **「`main` に本文付きコミットは1件も無い」という初版の前提が誤りだった。** 母数の内側に6件あり、
  しかも本レポートが「良い例」として引用した行が、その最長（19行）の本文を持つコミットだった。
  **自分が根拠として貼った出力の中に、自分の結論の反例が混ざっていた**
  （`wip/reports/REVIEW-POINTS.md` が名指しで警告している失敗の型に、そのまま当てはまった）。
- **`create-commit.sh` の実装変更が要るかもしれない、という計画時の見立ては外れた。**
  改行入りメッセージはそのまま通り、hookも発火しない。
- **1行の長さは制約になっていなかった。** median 45.5文字・max 103文字で、短く切り詰められて
  情報が落ちているのではなく、長いまま中身が無い行が多い。
- **`main` の1行ログに出るのはPRタイトルだった。** issue本文は畳まれた個別コミットの件名を
  「main へ残るコミットログ」として扱っているが、`--oneline` で見える1行はPRタイトルである。
  issueの問題意識自体は正しい（squash本文は残るため）が、**規約の効き先が1段ずれている**。
- **同じ方向の規約が既にリポジトリ内にあった**（`resolve-conflict/SKILL.md` の「何を・どう」）。
  ゼロから作るのではなく、既存の前例を一般化する形になる。
