### 問い5 — 除外規則で**過剰除去が1件発生した**（修正後の再測まで実施）

確定済みの除外規則（正規化後の完全一致＋スラッシュコマンド正規表現）を母集団7件へ当てた。

| 辞書 | 辞書で除外 | スラッシュコマンドで除外 | 残る |
|---|---|---|---|
| **修正前**（`ok`/`OK` を含む） | **1** | 0 | 6 |
| **修正後**（`ok`/`OK` を外した） | **0** | 0 | **7** |

**落としたのは辞書語 `ok` で、1件。** これは flow-id 1-5 の合意（全体作業計画の4論点すべてへの
承認）そのもので、**このタスクで最も重要な意思決定の1つ**である。

**全体作業計画で確定済みの方針「過剰除去が1件でもあれば、その語を辞書から外す」に従い、
`ok` と `OK` を辞書から外した。停止条件が求める「外した後の測り直し」も実施し、除外0件・
残7件を確認した**（下記 問い6 の 1,239B は、**この修正後の母集団7件**を通した値である）。

**同じ理屈が辞書の他の語にも及ぶ。** このワークフローでは、レビュー合意・着手承認・方針同意が
`はい` `了解` `お願いします` のような短い肯定語で表明される。落としたい「意味の無い相槌」と、
落としてはいけない「短い承認」を**文字列だけで区別する手段が無い**というのが実データの
示すところである。

**この点を flow-id 2-8 のレビューで人間の判断へ上げ、「辞書はオッケー」との回答を得た。**
すなわち**辞書方式を継続する**（辞書を空にする案・別方式へ置き換える案は採らない）。
確定した内容は次のとおり。

| 項目 | 確定内容 |
|---|---|
| 方式 | **正規化後の完全一致による辞書除外を継続する**（全体作業計画の規則1のまま） |
| `ok` / `OK` | **辞書から外す**（本調査で過剰除去を実測したため） |
| `はい` `了解` `お願いします` 等 | **辞書に残す**。実データでは1件も過剰除去していない |
| 過剰除去が再発したときの扱い | 全体作業計画の確定方針どおり、**その語を辞書から外す** |
| **辞書の育て方** | **固定の完成品として設計せず、実際のユーザー入力を見ながら継続的に育てる**（下記） |

**残る既知のリスクは「実測されていない過剰除去」である。** `はい` `了解` `お願いします` が
承認として使われた回は、この断面（真の発言7件）には現れなかっただけで、原理的には起こりうる。
**辞書は完全一致なので、外す操作はいつでも1語単位で行え、取り返しがつく**——このことが、
リスクを承知で辞書を継続する判断を支えている。

#### 辞書は「育てる」もの（flow-id 2-8 の追加判断）

**flow-id 2-8 のレビューで、さらに「辞書は毎回のユーザの入力を見ながら育てて行きたい」との
方針が示された。** これは上の「辞書方式を継続する」を一段具体化するもので、
**辞書を設計時に完成させる固定リストとして扱わない**ことを意味する。

本調査の実データは、この方針を支持している。

| 実測 | 何を示すか |
|---|---|
| 辞書12語のうち、実際に何かを落としたのは **`ok` の1語だけ**（しかもそれは過剰除去だった） | **残る11語は、この断面では一度も働いていない**。机上で並べた語が実運用に当たる保証は無い |
| 真の発言は **7件**。相槌として落とすべきものは **0件** | **落とすべきノイズは `origin.kind` の1条件で構造的に消えた**。辞書が担う残余はごく小さい |

**したがって初期辞書は、机上の網羅ではなく「実際に観測した相槌」から始めるのが理にかなう。**
ただし**初期辞書をどこから始めるか（現行12語から `ok`/`OK` を引いた10語で始めるか、
観測実績のある語だけの小さな集合から始めるか）は、本調査が決める範囲を超える**。

**flow-id 3-1 が決めること**（本調査からの申し送り）:

| # | 決めること | なぜ必要か |
|---|---|---|
| 1 | **初期辞書の中身** | 「育てる」の出発点。網羅から始めるか、観測実績から始めるか |
| 2 | **辞書の置き場所**（スクリプト内の定数か、編集しやすい外部ファイルか） | 育てるには**人間が1語単位で足し引きできる**必要がある |
| 3 | **除外実績の可視化** | 「毎回の入力を見ながら」を成り立たせるには、**何がどの語で落ちたかが見える**必要がある。見えなければ過剰除去に気づけず、育てる材料も得られない |
| 4 | **育てる操作の記録先** | 語を足し引きした理由が残らないと、同じ語が足されたり外されたりを繰り返す |

**3が最も重要である。** 本調査で過剰除去に気づけたのは、**除外前後の件数を突き合わせて
落ちた1件の中身を確認したから**であって、通常の運用では hook は黙って落とす。
**「黙って落とす」ままでは、辞書は育たない。**

**除去漏れは0件**（残った7件はいずれも意味のある発言だった）。

**スラッシュコマンドは1件も当たらなかった。** `/compact` は `<command-name>` 形式で記録され、
`origin` を持たないため**母集団に到達する前に落ちている**（問い12）。正規表現を安全網として
残すか外すかはフェーズ3の判断とする（**1事例のみを根拠に「不要」と断じない**）。

### 問い8 — ロケール非依存に文字単位で切れるのは `jq`（と `perl -CSDA`）

日本語10文字（`あいうえお漢字テスト`）の先頭5文字を切り出し、`LANG`/`LC_ALL` を**空にした環境**と
`LC_ALL=C.UTF-8` の両方で比較した。期待値は `あいうえお`。

| 手段 | `LANG` 空 | `LC_ALL=C.UTF-8` | 判定 |
|---|---|---|---|
| **`jq` の `.[0:5]`** | **正しい** | **正しい** | **両方で正しい → 採用** |
| `awk` の `substr`（mawk 1.3.4） | 壊れる（バイト単位） | 壊れる（バイト単位） | 不可 |
| `${s:0:5}` | 壊れる（バイト単位） | 正しい | **ロケール依存 → 不可** |
| `perl -CSDA` | 正しい | 正しい | 可（ただし外部プロセスが増える） |

- **`${var:0:N}` がロケール依存で落ちることを再現した**（`.claude/rules/shell-script-style.md`
  「日本語を含む文字列の先頭を `${var:0:N}` で切り出して比較しない」の実測どおり）。
- `awk` は同ルールの記述どおり **mawk では `substr()` がバイト単位**。gawk では文字単位になる
  ため、**環境によって結果が変わる手段は採らない**。
- `perl` は当初 `-CSD` で試して壊れたが、これは**呼び方の誤り**（`@ARGV` のデコードには `-CA` が
  要る）。`-CSDA` なら両条件で正しい。**perl 自体の欠陥ではない**ため、そう記録する。
- **切り出しは既に jq の中で行うため、`jq` の `.[0:N]` を使えば外部プロセスは増えない。**

### 問い7 — git bash 実機でのパス表記は**未確認**

本調査はリモート実行環境（Linux）で行ったため、**Windows / git bash で `transcript_path` が
どの表記（Windows形式 `C:\...` / MSYS形式 `/c/...`）で渡るかは確認できていない。**
**「確認できた」ことにしない。**

**この環境では POSIX 絶対パス（`/root/...`）で渡った**（問い1）。これは Linux 実行環境の
観測であり、git bash での表記を示すものではない。

**ただし、回避手段が同値であることは確認した。** `jq` へパス名を引数で渡す形と、
標準入力へ繋ぐ形の出力が**バイト単位で一致**する（md5 が一致）。

```bash
jq -R -n -r -f filter.jq "$path"   # パス名を渡す（MSYS のパス変換・native jq の制約を受ける）
jq -R -n -r -f filter.jq < "$path" # 標準入力へ繋ぐ（パス名を渡さないので影響を受けない）
```

`.claude/rules/shell-script-style.md` は「`jq ... < <(...)` のように標準入力へ繋ぐのは、
パス名を渡していないので問題なく動く」としている。**フェーズ3では標準入力へ繋ぐ形を採る**
ことで、パス表記の不確実性を実装から切り離せる（リダイレクトは fork を伴わないので
問い11 のコストも増えない）。
