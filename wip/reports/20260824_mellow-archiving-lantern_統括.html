何を変えたか

MR/PR descriptionを「レビュー時だけの説明」から「後から見返せるアーカイブ」へ作り替えた。 振る舞い・ルールの単位では次の4つである。

  1. テンプレートが10節構成になった。 Closes 行 ＋ 概要／変更内容／設計判断・採らなかった案／検証／レビューの結果／意図的にやらなかったこと・スコープ外／未解決・限界・確かめられなかったこと／受け入れ条件との対応／反映先・関連／備考。全10節が「何を書くか」と「計画段階では何を書くか」の記入ガイドをHTMLコメントで持つ。
  2. 見出し構成の正がテンプレートファイルへ移った。 describe は .github/pull_request_template.md（GitLabは複製）を読んで見出しを決める。references/review-loop.md の describe 節からは見出しの記述そのものが消え、二重管理が構造的に成立しなくなった。配布先でテンプレートを編集すれば describe の出力もそのまま変わる。
  3. MR/PR本文から wip/plans/ wip/worklogs/ wip/reports/ を参照しなくなった。 これらは flow-id 5-5 で削除されるため、レビュー中は踏める参照がマージ後に必ず切れる。ただし「参照」と「アンカー」を線引きし、レビュー対象の位置を指すアンカーは対象外とした。判定基準はマージ後に読み手が困るかである。
  4. GitLab版が機械的に保証されるようになった。 先頭コメントを除いた全文差分が空であることをテストが検査し、生成も awk で行う（手で写さない）。

なぜそうしたか

採用したのは案B（テンプレートファイルを正とし、describe が読む）である。人間の承認を得ている。

案判断理由
案A: describe 節を正とし、テンプレートを生成物にする却下テンプレートはGitHub/GitLabが直接読むファイル。生成物にすると、人間がPR作成画面で見る本文が「生成し忘れ」で古くなる
案B: テンプレートを正とし、describe が読む採用テンプレートは元々プラットフォームが読む実体なので、正にするのが自然。describe 節から見出しが消え、二重管理が構造的に消える
案C: 両方に書き、テストで一致を検査する却下二重管理そのものは残る。検査は「ずれたら気づく」だけで「ずれない」保証ではない

#111（統括レポートのサマリコメント）とdescriptionは併存させる。 判断軸は上書きの非対称で、descriptionは describe で全文置換されるため常に最新の1断面しか持てず、サマリコメントは投稿時点の断面として固定される。descriptionの最終形は flow-id 4-10 であり「常に最新」ではない（describe はフェーズ5に1つも無い）。5-4 の後に describe を足す案は却下した。

この2件は1つのDDRにまとめず分けた。 片方だけが後から supersede されうる独立した判断であり、1件にすると status: superseded を片方だけに付けられないため。

配布層は core のまま変えなかった。 seed へ変えると上流のテンプレート改善が配布先へ二度と届かない。代わりに配布元と配布先で扱いが違うことを先頭コメントへ明記した。

.claude/VERSION は 0.4.0 据え置き（人間の判断）

AIは 0.5.0（MINOR）を提案し非対話例外に基づきいったん適用したが、「0.4.0で良い」との回答を得て戻した。実害は承知のうえで、配布先は中身の違う .claude/ を同じ版として受け取る。過去3回（#54・#26・#165）と同じ結論だが、提案 → 適用 → 確認 → 否認 → 復帰という例外規定どおりの経路をたどった初めての回である。
