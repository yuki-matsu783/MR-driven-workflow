実施した内容と結果

1. 発動条件を残置テキストの側から書いた ◎良

一般化前は「既存ドキュメントへ新しい見出しを差し込むときは、挿入位置の直前の節が『その節全体にかかる地の文』で終わっていないかを必ず確認する」だった。これは操作の名前（見出しの差し込み）を発動条件にしているため、issue #109 の「節の分割」も PR #139 の「後ろが壊れた」も拾えない。

書き換え後の発動条件は次のとおりで、見出しの差し込み・節の分割・並べ替え・箇条書きへの項の追加を例示したうえで、操作の名前で射程を判断しないと念押ししている。

既存の記述を残したまま、その周囲を編集したときは、残した記述の係り先が
変わっていないかを必ず確認する（事故の実例: issue #64・#109・PR #139・#155。
一般化は issue #142）。
結論 「構造変更全般へ広げる」では足りない。「構造変更か？」という判定を書き手に残すためで、残置テキストの側から書くと判定対象が「自分が残した文がどこにかかっているか」という具体へ変わる。

2. 一般化と同時に上限を付けた ◎良

発動条件だけを広げると、あらゆる編集が対象になり「常に確認せよ」と同義になって読み飛ばされる。そこで係り先が変わりうる文の5類型（節・項の全体にかかる補足／結論行／箇条書きを締める一文／見出しを持たない段落／指示語や省略で前を受ける文）を挙げ、次のように締めた。

そういう文が1つも無いと確かめられたときだけ、確認を省いてよい。
省けるかどうかは前後を読んで初めて決まるので、操作の種類
（「末尾へ足すだけだから」等）を理由に省かない。
結論 上限は「省いてよい条件」の側から書いた。省略の根拠として操作の種類を使わせないことが要点で、これが無いと一般化した発動条件が骨抜きになる。
確かめられなかったこと（詳細） 5類型で十分かは、構成した陰性ケース1件（確認不要と判定できること）でしか確かめていない。実際に事故が減るかは今後の運用でしか分からない。

3. 反映先は2箇所（規約とレビュー観点） △注意

フェーズ2の調査で、collect-review-points.sh が集めるのは REVIEW-POINTS.md / REVIEW-POINTS.local.md だけであり、.claude/rules/ はレビュー観点としては敵対的レビューへ渡らないことを確認した（alwaysApply: true の規約はサブエージェントのプロジェクト指示としては入るが、レビュー観点表としては渡らない）。

そこでルート REVIEW-POINTS.md「ドキュメントの構造」の先頭項目を2行→11行にし、Aと同じ発動条件・同じ上限・同じ優先順位の対処を、B単体で判断できる形で書いた（実例の固有名は持たせず、規約側を参照させる）。

$ grep -cF -e '計画の2階層構造' -e 'DDRのnote' -e 'レビュー完了合図の確認' REVIEW-POINTS.md
0
結論 二重管理を承知で選んだ。「Bから A を参照させるだけ」にすると、敵対的レビューはBに書かれた条件だけを見るため、Aを開かなければ発動条件が分からない。
確かめられなかったこと（詳細） 二重に持つ範囲は条文3段落全体で、実例だけがA側にしかない。文言が同一ではないため、一致検査は機械的に行えない。この点は DDR i0142-01 に明記した。

4. 事故4件の当て直しと、既存記述の非破壊 ◎良

同型の事故4件（issue #64・#109・PR #139・#155）を、書き換え後の実文言へ当て直し、条文のどの箇所で拾えるかを明示した。4件とも検出できる。陰性ケース1件（残置側に依存文が無い編集）では「確認不要」と判定でき、過剰一般化にはなっていない。

既存2実例（計6行）と spec の ### issue #64 エントリは、1バイトも変えていない。

$ git diff "$base" -- .claude/ REVIEW-POINTS.md | grep '^-' | grep -cF -e '末尾に節全体へかかる地の文' … 
0
$ grep -c -F -x -f /tmp/protected6.txt .claude/rules/docs-workflow.md
6
結論 削除検査 0 と完全一致 6/6 の両方で確認した。片方だけでは「行が消えていないこと」と「行が書き換わっていないこと」を区別できない。

5. 書き換えの初版が、このルール自身の欠陥を作っていた △注意

新しい2件（#109・PR #139）を既存2件の前へ足したところ、既存2件が持っていた「次の2件は…同じ作業で見つかった」という帰属が、直前の番号付き項目に依存していたため指す先を失った。フェーズ3の2回目の敵対的レビューが検出した。

条文が第一選択とする「係り先が変わらない位置を選ぶ」は、この件では後ろだった。それでも前を選んだのは、新しい2件が一般化そのものの根拠だからである。位置で解けないので、条文の第二選択どおり残した記述の側へ係り先を明示した。

次の2件は issue #64 の同じ作業で見つかったものである（issue #142 で上の2件を
前へ足した際、この2件が番号を持たない項になって「同じ作業で」の指す先が消えた
ため、地の文で明示している）。
結論 ルールを書く作業そのものが、そのルールの適用対象だった。この経緯は DDR i0142-01 の「決定の適用中に踏んだこと」節に残した。
