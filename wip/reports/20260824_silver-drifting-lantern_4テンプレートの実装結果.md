## 実施した内容と結果

### f1. 4テンプレートを共通パーツから組み立てた ◎良

**「共通DOM＋4通りの `<style>`」を、コピーではなく組み立てで実現した。**
scratchpad に次のパーツを置き、`build` 関数で連結している。

| パーツ | 内容 | 共有 |
|---|---|---|
| `head-common.txt` | 使い方コメント（124行） | **4本で共通** |
| `body.html` | DOM本体（216行） | **4本で共通** |
| `style-common.part` | スタイルの骨格（143行。CSS変数を参照するだけ） | **4本で共通** |
| `style-<design>.part` | CSS変数の定義＋そのデザイン固有の上書き（18〜43行） | デザインごと |

組み立ての順序が要点で、**`<style>` の中は「共通の骨格 → デザイン固有」の順**にしている。
逆にすると、同じ詳細度の規則で共通側が勝ってしまい、デザイン固有の上書きが効かない。

**CSS変数は共通骨格より後ろで定義されていても問題ない**（カスタムプロパティはスタイルシート全体を
読んでから解決されるため）。

**ただし「組み立てたから同一である」とは言えなかった。** 冒頭コメントの中にデザイン固有の説明を
書いていたため、共有パーツから組んでいても4本のうちその部分だけが異なっていた（f2）。
**組み立ては同一性を作りやすくするが、保証はしない。検証が要る。**

### f2. DOM共通性を「バイト単位」で検証した ◎良

計画の中心的な主張なので、**主張したまま検証しないことはしない**。

**最初に書いた検証は、タグ名の並びしか比べていなかった。** `grep -oE '</?[a-z][a-z0-9]*'` は
属性もテキストも見ないため、「タグ構成は同じだが中身が違う」状態を素通りする
（敵対的レビュー2回目の指摘）。**`<style>` を除いた残り全体をバイト単位で比較する形へ改めた。**

```bash
cd .claude/skills/issue-mr-flow/assets
tmp=$(mktemp -d)
for F in reports-clean reports-neobrutal reports-mono reports-paper; do
  sed '/^<style>$/,/^<\/style>$/d' "$F.template.html" > "$tmp/$F.nostyle"
  n=$(wc -l < "$tmp/$F.nostyle")
  [ "$n" -lt 100 ] && { echo "FAIL $F: 抽出が $n 行"; exit 1; }   # 空振りガード
done
for v in reports-neobrutal reports-mono reports-paper; do
  diff "$tmp/reports-clean.nostyle" "$tmp/$v.nostyle"             # 3組すべて0行が合格
done
```

**改めた結果、実際に差分が出た。** 冒頭コメントの中にデザイン固有の説明文を置いていたため、
4本のうちその8〜9行だけが異なっていた。タグ名の比較では**この差が一切見えていなかった**。

**修正**: デザイン固有の説明を冒頭コメントから **`<style>` ブロック先頭のCSSコメント**へ移した。
冒頭コメントには「デザインの説明は `<style>` 冒頭にある」という4本共通の1行だけを残した。

| 比較 | 差分行数 |
|---|---|
| clean vs neobrutal | **0** |
| clean vs mono | **0** |
| clean vs paper | **0** |

`<style>` を除いた部分は4本とも **359行 / 22346バイト** で完全に一致する
（テンプレート全体は clean 529行 / neobrutal 543行 / mono 558行 / paper 547行。差は `<style>` だけ）。

**最初に書いた検証コマンドには、もう1つ誤りがあった。** `sed '/^<style>/,/^<\/style>/d'` は
`<style>` ブロックしか落とさないため、使い方コメントの地の文にある `<section>` `<li>` `<code>` が
タグとして数えられていた（289タグ。本文282＋コメント由来7）。バイト比較へ移行したことで
この問題も同時に解消した（コメントも含めて比較対象になり、かつ4本で一致するため）。

### f3. 5種の検査を4本へ流した ◎良

| 検査 | clean | neobrutal | mono | paper |
|---|---|---|---|---|
| 1. プレースホルダ（雛形なので>0が期待） | 24 | 24 | 24 | 24 |
| 2. リンク破断（0行が合格） | 0 | 0 | 0 | 0 |
| 3. 重複ID（出力なしが合格） | なし | なし | なし | なし |
| 4. 外部依存 src/href | 0 | 0 | 0 | 0 |
| 5. 外部依存 url()/@import | 0 | 0 | 0 | 0 |

**プレースホルダが4本とも同数（24）**であることが、使い方コメントとDOMを共有できている傍証になる。

**「出力なし＝合格」の検査は、負のコントロールを取って初めて意味を持つ。**
cleanのコピーを意図的に壊し、検査が反応することを確かめた。

| 壊し方 | リンク破断 | 重複ID |
|---|---|---|
| `href="#f1"` → `#f99` | **`f99` を検出** | 反応せず（正しい） |
| `<h3 id="f1">` → `id="overview"` | **`f1` を検出** | **`overview` を検出** |

後者の1操作で**両方が反応する**ことが、2つの検査を持つ理由をそのまま示している。
あわせて空振りガード（拾えた件数）も出した: **href=12 / id=8**。0でないので検査は働いている。


**プレースホルダ検査の合格条件は、テンプレート本体と成果物で逆になる。** テンプレートは雛形なので
プレースホルダが「ある」ことが正しく、成果物では「0件」が正しい。この読み替えを使い方コメントの
「使い方」5へ明記した（書かないと、テンプレート自身を検査して不合格と誤判定される）。

### f4. タグの開閉バランスを検証した △注意

開きタグと閉じタグの数を要素ごとに数えたところ、**4本すべてで `li` が 22対21、`details` が 2対1**
という不一致が出た。

**原因はテンプレートではなく検査側だった。** 本文中のHTMLコメントに、地の文として
`<li>` `<details>` と書かれた箇所が1つずつある。

```
タイムラインの前に置くが、タイムラインの <li> には入れない（…）
長い出力は <details> で折りたたむ
```

HTMLコメントの中身はタグとして解釈されないので、**実際のDOMは正しく閉じている**。
コメントを除去してから数え直すと、`section` `aside` `main` `div` `ol` `ul` `li` `details`
`table` `thead` `tbody` `tr` のすべてで開閉が一致した。

この書き方（コメント内でタグ名を山括弧付きで書く）は**現行 `reports.template.html` から続く
既存のスタイル**であり、人間が読むうえで自然なので変えていない。**直したのは検査コマンドの側**である。

**これは f2 と同じ種類の失敗**（コメントの地の文をタグとして数える）が、別の検査で再び出たものである。
外部依存検査についても同じ性質の注意を使い方コメントへ書いてあり、**「HTMLを機械的に検査するときは、
コメントと地の文を先に除く」というのがこのテンプレート群を扱ううえでの一般則**だと分かった。

### f5. 新テンプレートでこのレポート自身を作った ◎良

**このレポートのHTMLビューは、`reports-clean.template.html` から作っている。**
テンプレートを作っただけで使わずに終えると、雛形として実用に耐えるかが分からないため。

**使ってみて見つかった不足を1件、テンプレートへ反映した。**
サイドバーの目次はネストした `<ol class="toc-sub">` で章を並べるが、当初の使い方コメントには
「章が増えたらここも増やす」ことが書かれていなかった。目次と本文の対応はリンク破断検査に
かかるので致命傷にはならないが、**検査に頼る前に書き手が気づけるほうがよい**ため、
プレースホルダのコメントへ明記した。
