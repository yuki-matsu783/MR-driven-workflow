### 検証1・2の予測が外れた理由

**どちらも「新設した規約の本文自体が、検索語にヒットする」ことを計算に入れていなかった。**

| 検証 | 増えたヒット | 中身 |
|---|---|---|
| 1 | `commit/SKILL.md` に **5件**（220 / 222 / 224 / 225 / 236行） | 決定1-b の「フッター」の表と、PRタイトル注記の行 |
| 2 | `commit/SKILL.md` に **1件**（210行） | **新規約に沿った複数行メッセージの書き方の例**（`--message "$(cat <<'MSG' …`） |

**判定の根拠は件数ではなく、書き換え対象3行の消失で行った。**

```bash
grep -c '1行のみ' .claude/skills/commit/SKILL.md            # → 0（旧145行）
grep -c '本文・フッター' .claude/skills/commit/SKILL.md      # → 0（旧146行）
grep -c '1行のみ' .claude/docs/spec/create-commit.md         # → 0（旧46行）
```

**教訓**: 「規約を書く」タスクでは、**規約の本文が検証の検索語に必ず引っかかる**。件数の増減を
合格条件にすると、規約を書けば書くほど不合格に近づく。計画時にこれを織り込めなかった。
**件数は「どこが増えたか」を見る材料であって、合否そのものにはできない。**

### 自己適用の結果（検証11）

**このフェーズのコミットメッセージを新規約で書いた。**

```
ai-asset: commit/SKILL.mdへ内容規約を新設し、件名の「どう」を6語で判定する基準とフッターの可否を定める
```

| 要素 | 満たしているか |
|---|---|
| **何を** | `commit/SKILL.md`（と、その中の内容規約） |
| **どう** | 節を新設し、6語の判定基準とフッターの可否を定めた |
| **なぜ** | **件名では省略した。** 「内容規約を新設する」理由は issue #185 そのものであり、対象と手段から辿れる |

**書きにくさは感じなかった。** ただし**件名が長くなる**（この例で103文字）ため、
「どう」を2つ以上並べる場合は本文へ回したほうが読みやすい場面がありそうである。
規約側では「判断に迷ったときの既定」で**迷ったら本文へ書く**としており、この対処で足りる。
