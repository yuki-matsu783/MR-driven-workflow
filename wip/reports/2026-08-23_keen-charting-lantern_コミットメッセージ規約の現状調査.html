Q3. 本文を許容した場合、実装・呼び出し側は耐えるか

確かめられなかったこと

  • GitHubのsquash mergeが本文をsquash本文へ含めるか（Q4）。履歴に本文付きコミットが1件も無く、確かめるには main の正史を検証のために書き換える必要があるため。方針決定には影響しないことを Q4 に示した。
  • git bash（Windows）実機での挙動。 Q3の実測はすべてLinuxで行った。create-commit.sh の改行の扱いは git commit -m へ委ねられており処理系差は考えにくいが、未計測であることは事実として記す。
  • main の全履歴に対する欠落パターンの分布。 母数を直近5件（80行）に固定したため、それ以前の傾向は測っていない。issue本文が挙げた issue #110 の実例は母数の外にある。

設計への反映（フェーズ3へ渡すもの）

  1. 方針は「件名1行は必須・本文は任意で許容」を推す。 Q3で実装変更が不要と確かめられ、Q4で本文が畳まれなくても損が無いと言えるため、採用コストがほぼゼロ。一方 Q5 が示すとおり、1行に収まらない内容を要求している既存の規約が既にある（issue-mr-flow/SKILL.md:229）。この衝突は本文を許容しないと解消しない。
  2. 規約の主役は件名（1行目）の内容規約である。 Q2が示すのは「長さが足りない」ことではなく「長い行でも中身が無い」ことなので、文字数を緩めるだけでは直らない。満たすべき要素を列挙する形にする。
  3. 「mainに残らない成果物のみのコミット」（母数の58%）の書き方を規約へ含める。 これが履歴の過半を占めている以上、何を書かせるかを決めないと規約が守られない側の多数派になる。
  4. PRタイトルが1行ログに出るという事実を規約へ書く（Q2の新類型・Q4）。書かないと「コミットメッセージを直せば --oneline が読めるようになる」という誤解が残る。
  5. 書き換える3行と、追随を確認する2箇所が確定した（Q1・Q5）。commit/SKILL.md:146 を差し替える際、フッター禁止（同31行と重複）を巻き添えにしない。
  6. 検証は「0件」ではなく「書き換え対象3行が消えたこと」で判定する（Q1）。.gemini/ 側の同一コピーは flow-id 5-3 の変換同期で追随させる。

想定と異なった点

  • create-commit.sh の実装変更が要るかもしれない、という計画時の見立ては外れた。 改行入りメッセージはそのまま通り、hookも発火しない。
  • 1行の長さは制約になっていなかった。 median 85文字・max 143文字。短く切り詰められて情報が落ちているのではなく、長いまま中身が無い行が多い。
  • main の1行ログに出るのはPRタイトルだった。 issue本文は畳まれた個別コミットの件名を「main へ残るコミットログ」として扱っている。問題意識自体は正しい（squash本文は残るため）が、規約の効き先が1段ずれている。
