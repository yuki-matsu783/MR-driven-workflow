| **軸1**（実行時に読む／実行する経路） | **0件**（hook `command` 6本すべてが `.claude/hooks/`） | **0件**（資産が書くパス97件すべてが `.claude/scripts/`） | **0件**（`settings.json` に読み込ませるキーが無い） |

ものだけを外す候補とする」であり、軸2の「切れても許容できる理由がある」という逃げ道を使うには
**人間の判断が要る**（計画で明示的にそう定めた）。

#### 軸2が「0件でない」ことの意味は、3つで異なる

- **hooks/ と scripts/ の1件ずつは、どちらも `.gemini/docs/usecase/対応工数を把握する.md` が
  唯一のリンク元である。** つまり `.gemini/docs/` を残す限り必ず切れ、`.gemini/docs/` も外すなら
  リンク元ごと消えて0件になる。
- **docs/ の18件は、残す側（`.gemini/rules/` `.gemini/skills/`）に壊れたリンクとして残り続ける。**
  外す対象の内部で完結するリンク（docs→docs 282件）とは性質が違う。

```
.gemini/docs/usecase/対応工数を把握する.md:37: [post-push-usage-report.sh](../../hooks/post-push-usage-report.sh)
.gemini/docs/usecase/対応工数を把握する.md:39: [show-push-log.sh](../../scripts/src/show-push-log.sh)
```

### 結論4: 3ディレクトリは独立に決められない

issue #172 は3ディレクトリを並列に問うており、全体作業計画も「1つずつ独立に結論を出す」と
書いた。**軸1・軸3・軸4は独立に評価できるが、軸2は独立ではない。**

| 決め方 | hooks/ の軸2 | scripts/ の軸2 | docs/ の軸2 |
|---|---|---|---|
| 3つとも残す | — | — | — |
| hooks/ scripts/ だけ外す | 1 | 1 | — |
| 3つとも外す | 0 | 0 | 18 |

**hooks/ と scripts/ の軸2は、docs/ の採否に依存して 1 にも 0 にもなる。** 「独立に結論を出す」と
いう方針は、軸2に関しては最初から成立していなかった。これは調査で数えたときには
「hooks 1・scripts 1・docs 18」という並びに見えていて、**依存関係としては読み取っていなかった**。

### 結論5: 案2（hooks/ scripts/ だけ外す）を却下した理由

2つある。**どちらか一方でも成り立てば却下に足りる。**

1. **残る `.gemini/docs/` から2件の壊れたリンクが出る**（上記）。「外す対象の中で完結するから
   実害が無い」という説明が使えない（案3の18件も同じく完結しない側だが、そちらは別途18件として
   数えている）。`.gemini/` を見る読み手には壊れたリンクとして見える。
2. **軸1の根拠が `.gemini/rules/` にも当たる**（調査 Q3-b）。「そのパスを実行時に読む経路が無い」
   という根拠は、`.gemini/rules/` `.gemini/skills/` にも同じ強さで当たる。にもかかわらず
   3ディレクトリだけを外すなら、**なぜ rules/ skills/ は外さないのか**を説明できなければならない。
   説明は見つからなかった（`.gemini/rules/` を残す理由として提示できるのは「人間が `.gemini/` を
   眺めたときに読める」ことだけで、それは `.gemini/docs/` にも等しく当てはまる）。

### 結論6: 案3（3つとも外す）を却下した理由

軸2は0件にならず18件で、これを許容するかどうかの判断になる。**許容してよいと言い切れる根拠が
無い**と判断した。

- 18件が「誰も読まないファイルの中の壊れたリンク」だと言うには、`.gemini/rules/`
  `.gemini/skills/` が読まれないことが要る。それは**未観測の推論**である（調査 Q3-b・結論9）。
- 仮にその推論が正しいなら、**`.gemini/rules/` `.gemini/skills/` も同時に外すのが筋**であり、
  それは issue #172 のスコープ外である。「18件の壊れたリンクを抱えた `.gemini/rules/` を残す」と
  いう中間状態は、どちらの前提から見ても正当化できない。（**この2点はフェーズ3・1回目時点の

- 加えて次の結論7がある。

### 結論7: 生成物に含まれないファイルがあると、配布先の再適用が片肺になる（実測）

**「無言で壊れる」ではない。** 引用範囲を手前へ広げると、この継続は**意図的なトレードオフとして
記録されている**ことが分かる。

```
$ sed -n '909,923p' .claude/skills/apply-mr-workflow-to-project/scripts/install-to-project.sh
  # **失敗しても中断しない（警告のみ）。** ここに到達した時点で core / seed / merge の配置は
  # 済んでおり、`.gemini/` が無いこと以外は完了している。中途半端な状態で止めるほうが害が大きい。
  # とくに配布先が自前の `.gemini/` を持っていた場合、生成側の削除ファイル検出が働いて
  # **1バイトも書かずに中断する**ので、何も壊さずに警告だけが残る。
  ...
  if [ -f "${DEST_DIR}/.claude/scripts/src/sync-gemini-assets.sh" ]; then
    ( cd "$DEST_DIR" && bash .claude/scripts/src/sync-gemini-assets.sh ) || {
      printf '警告: .gemini/ の生成に失敗しました。配布先で次を実行してください:\n' >&2
      printf '  bash .claude/scripts/src/sync-gemini-assets.sh\n' >&2; }
```

**警告は2系統出る。**

1. installer が `警告: .gemini/ の生成に失敗しました…` を標準エラーへ出す。
2. その前段で sync 自身が `エラー: .gemini/ に、生成物へ含まれないファイルが N 件あります` ＋
   **全件の一覧** ＋ `消してよければ --force を付けて再実行してください（この実行では1バイトも
   書き込んでいません）` を標準エラーへ出す。

それでも次の2点は実際の弱点として残る。

1. **installer の終了コードが0のままである。** `.gemini/` が更新されていないのに、インストールは
   成功として終わる。標準エラーを読まない自動実行（CI等）では検出できない。
2. **案内される復旧コマンドに `--force` が無い。** `bash .claude/scripts/src/sync-gemini-assets.sh`
   をそのまま実行しても、同じ理由で再び失敗する（`--force` を案内しているのは sync 自身の
   エラーメッセージのほうで、installer の案内ではない）。

**この失敗が起きる条件は「除外を実装したとき」ではない。** 条件は
**生成物に含まれないファイルが配布先の `.gemini/` に1件でもあること**で、除外の実装は
そのうちの一例にすぎない。`sync-gemini-assets.sh` のヘッダが、現行で起きる別の経路を名指ししている。

```
$ sed -n '9,10p' .claude/scripts/src/sync-gemini-assets.sh
# 再生成は .gemini/ の丸ごと置き換えなので、そのままでは手で置いたファイルが黙って消える
# （配布先が自前の .gemini/commands/*.toml や settings.json を持っている場合が該当する）。
```

つまり**自前の `.gemini/commands/*.toml` を持つ配布先では、案1のままでも今日この状態が起きうる**。
「案1を採ったので実害が無い」とは言えない（下記「設計への反映」6）。

除外を実装する場合に限れば、これは「機械的に直せる追随箇所」ではなく**配布先ごとに1回だけ必要な
移行手順**になる。移行方針として (a) spec へ手順を書いて手動実行に委ねる
(b) `install-to-project.sh` 側で残骸を先に消す (c) 何もしない、の3択を計画に置いたが、
**案1を採るため今回はいずれも不要**になった。

### 結論8: 現在のコピー対象に「集合」は無い（全件列挙である）

**当初このレポートは「リンク運用時代の TARGETS が引き継がれ、issue #70 で再検討されていない」と
書いていた。これは誤りだったので訂正する。** 実装を読むと、ディレクトリ単位の対象集合は存在しない。

```
$ grep -n 'ls-files' .claude/scripts/src/sync-gemini-assets.sh
  git -c core.quotepath=false ls-files --cached --others --exclude-standard -z -- .claude
$ sed -n '101,103p' .claude/scripts/src/sync-gemini-assets.sh
readonly COPY_EXCLUDED_PREFIXES=(
  '.claude/settings.json'
)
$ printf 'claude=%s gemini=%s\n' "$(git ls-files .claude | wc -l)" "$(git ls-files .gemini | wc -l)"
claude=215 gemini=215
```

`.claude/` 配下の追跡ファイル**全件**を列挙し、変換生成する2つ（`agents/*.md`・`settings.json`）
だけを `is_copy_excluded` が除く。仕様も `.claude/docs/spec/sync-gemini-assets.md:96-97` に同じ
ことを書いている。実際 `.gemini/` には旧 TARGETS（`docs hooks rules scripts skills`）に含まれない
`REVIEW-POINTS.md` `VERSION` `dist-layers.json` `agents/` `settings.local.json.example` が生成されている。

**「issue #70 で再検討されていない」も誤りである。** 根拠として引こうとした当のDDRが、
TARGETS の構成メンバーを明示的に問い直している。

```
$ sed -n '29,31p' .claude/docs/ddr/i0070-01-*.md
2. **`agents/` がそもそもリンク対象に入っていなかった。** `setup-gemini-links.sh` の `TARGETS`
   は `(docs hooks rules scripts skills)` で、`agents` を含まない。つまりサブエージェント定義は
   Gemini 経路から**一度も見えていなかった**。
```

issue #70 は TARGETS の欠落を是正した結果として、**列挙方式ごと全件へ置き換えている**。
集合が据え置かれたのではない。

**それでも、この経緯から言えることが1つ残る。** リンク運用時代は複製が生じないので対象を
広く取るコストがほぼゼロだったが、issue #70 でコピーへ変えた時点でそのコストは生じるように
なった。にもかかわらず、**「`.claude/` 配下を全部コピーしてよいか」という問いは立てられていない**
（`i0070-01` が問い直したのは `agents/` の欠落であって、全件列挙の是非ではない）。

**issue #172 はその問いに触れる初めての機会である。** ただし本issueの問い方
（「3ディレクトリを外すか」）は**切り方が合っていない**——正しい問いは
「`.gemini/` に何を置くべきか」であり、それには Gemini CLI の読み込み経路の観測が要る
（下記「設計への反映」2）。

### 採否の判断そのもの

**3つとも残す（案1）。** 決め手は次の3点で、**いずれも3ディレクトリに共通して効く**。

1. **外しても配布物は1バイトも減らない**（`dist-layers.json` で `.gemini` は `layer: exclude`）。
   得られるのはこのリポジトリと配布先で生成される `.gemini/` のサイズだけで、
   **失うもの（壊れたリンク・配布先の移行・未観測の推論への依存）と釣り合わない。**
2. **部分的に外すと、完全なコピーでも不在でもない中間状態になる。** `.gemini/` の価値は
   「`.claude/` と同じものが一式そろっている」ことにあり、大半を落として壊れたリンクを残すのは、

なので、標準エラーを読まない経路では `--check` を回すまで気づけない（結論7）。**非対称なので

### 再検討の条件

**この判断は「いま外す根拠が無い」であって、「永久に外さない」ではない。** 次のいずれかが
起きたら、`.gemini/` に何を置くかを問い直す。

## 確かめられなかったこと

- **Gemini CLI 実機の挙動は一切観測していない**（`command -v gemini` が空）。軸1の「0件」も
  結論5-2の「rules にも当たる」も、生成物と設定から導いた推論である。**この判断は未観測のまま
  行った。**
- **（フェーズ3・1回目時点の記述）`.gemini/rules/` `.gemini/skills/` `.gemini/agents/` を
  外すべきかは判断していない（本issueのスコープ外）。** 結論5-2で使ったのは「同じ根拠が
  当たる」という整合性の指摘までで、それらを外すべきだとは言っていなかった。
  **この限定はスコープ拡大により変わった**: `.gemini/rules/` は「論点2・論点3の判断」節で
