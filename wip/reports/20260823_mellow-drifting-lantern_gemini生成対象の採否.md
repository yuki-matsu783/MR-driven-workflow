## 実施した内容と結果

### 判定基準の4軸を3ディレクトリへ独立に当てた結果

軸の定義と合成規則は個別作業計画が正。ここでは適用結果だけを書く。

| | `.gemini/hooks/` | `.gemini/scripts/` | `.gemini/docs/` |
|---|---|---|---|
| **軸1**（実行時に読む／実行する経路） | **0件**（hook `command` 6本すべてが `.claude/hooks/`） | **0件**（資産が書くパス97件すべてが `.claude/scripts/`） | **0件**（`settings.json` に読み込ませるキーが無い） |
| **軸2**（残るファイルから切れる相対リンク） | **1件** | **1件** | **18件**（`rules/` 17・`skills/` 1） |
| **軸3**（外すコスト） | 実装＋テスト＋ドキュメント2箇所＋**配布先移行** | 左に加えて**死んだ設定2ファイル3行** | 実装＋テスト＋ドキュメント2箇所＋**配布先移行** |
| **軸4**（利得） | 14ファイル・217,308 B | 47ファイル・813,984 B | 115ファイル・1,456,431 B |
| **合成規則の判定** | 軸1は満たすが**軸2が0件でない** | 同左 | 同左 |

**3つとも軸1（0件）は満たし、3つとも軸2で落ちる。** 合成規則は「軸1が0件で、かつ軸2を満たす
ものだけを外す候補とする」であり、軸2の「切れても許容できる理由がある」という逃げ道を使うには
**人間の判断が要る**（計画で明示的にそう定めた）。

#### 軸2が「0件でない」ことの意味は、3つで異なる

- **hooks/ と scripts/ の1件ずつは、どちらも `.gemini/docs/usecase/対応工数を把握する.md` が
  唯一のリンク元である。** つまり `.gemini/docs/` を残す限り必ず切れ、`.gemini/docs/` も外すなら
  リンク元ごと消えて0件になる。
- **docs/ の18件は、残す側（`.gemini/rules/` `.gemini/skills/`）に壊れたリンクとして残り続ける。**
  外す対象の内部で完結するリンク（docs→docs 282件）とは性質が違う。

```
.gemini/docs/usecase/対応工数を把握する.md:37: [post-push-usage-report.sh](../../hooks/post-push-usage-report.sh)
.gemini/docs/usecase/対応工数を把握する.md:39: [show-push-log.sh](../../scripts/src/show-push-log.sh)
```

### 結論4: 3ディレクトリは独立に決められない

issue #172 は3ディレクトリを並列に問うており、全体作業計画も「1つずつ独立に結論を出す」と
書いた。**軸1・軸3・軸4は独立に評価できるが、軸2は独立ではない。**

| 決め方 | hooks/ の軸2 | scripts/ の軸2 | docs/ の軸2 |
|---|---|---|---|
| 3つとも残す | — | — | — |
| hooks/ scripts/ だけ外す | 1 | 1 | — |
| 3つとも外す | 0 | 0 | 18 |

**hooks/ と scripts/ の軸2は、docs/ の採否に依存して 1 にも 0 にもなる。** 「独立に結論を出す」と
いう方針は、軸2に関しては最初から成立していなかった。これは調査で数えたときには
「hooks 1・scripts 1・docs 18」という並びに見えていて、**依存関係としては読み取っていなかった**。

### 結論5: 案2（hooks/ scripts/ だけ外す）を却下した理由

2つある。**どちらか一方でも成り立てば却下に足りる。**

1. **残る `.gemini/docs/` から2件の壊れたリンクが出る**（上記）。「外す対象の中で完結するから
   実害が無い」という説明が使えない唯一のケースで、`.gemini/` を見る読み手には壊れたリンクとして
   見える。
2. **軸1の根拠が `.gemini/rules/` にも当たる**（調査 Q3-b）。「そのパスを実行時に読む経路が無い」
   という根拠は、`.gemini/rules/` `.gemini/skills/` にも同じ強さで当たる。にもかかわらず
   3ディレクトリだけを外すなら、**なぜ rules/ skills/ は外さないのか**を説明できなければならない。
   説明は見つからなかった（`.gemini/rules/` を残す理由として提示できるのは「人間が `.gemini/` を
   眺めたときに読める」ことだけで、それは `.gemini/docs/` にも等しく当てはまる）。

### 結論6: 案3（3つとも外す）を却下した理由

軸2は0件にならず18件で、これを許容するかどうかの判断になる。**許容してよいと言い切れる根拠が
無い**と判断した。

- 18件が「誰も読まないファイルの中の壊れたリンク」だと言うには、`.gemini/rules/`
  `.gemini/skills/` が読まれないことが要る。それは**未観測の推論**である（調査 Q3-b・結論9）。
- 仮にその推論が正しいなら、**`.gemini/rules/` `.gemini/skills/` も同時に外すのが筋**であり、
  それは issue #172 のスコープ外である。「18件の壊れたリンクを抱えた `.gemini/rules/` を残す」と
  いう中間状態は、どちらの前提から見ても正当化できない。
- 加えて次の結論7がある。

### 結論7: 除外は既存の配布先で無言の移行失敗を起こす（実測）

```
$ sed -n '920,923p' .claude/skills/apply-mr-workflow-to-project/scripts/install-to-project.sh
  if [ -f "${DEST_DIR}/.claude/scripts/src/sync-gemini-assets.sh" ]; then
    ( cd "$DEST_DIR" && bash .claude/scripts/src/sync-gemini-assets.sh ) || {
      printf '警告: .gemini/ の生成に失敗しました。配布先で次を実行してください:\n' >&2
      printf '  bash .claude/scripts/src/sync-gemini-assets.sh\n' >&2; }
```

`sync-gemini-assets.sh` の write モードは、**生成物に含まれないファイルが1件でもあれば `--force`
が無い限り1バイトも書かずに中断する**（スクリプト冒頭のコメントと write 分岐で確認）。除外を
実装した版を既存の配布先へ再適用すると、配布先に残っている3ディレクトリがこの検出に掛かって
sync が失敗する。ところが手順7は `|| { 警告 }` で**続行する**ため、次のことが同時に起きる。

1. 配布先には**古い3ディレクトリが残ったまま**になる。
2. インストール自体は**成功したように見える**。
3. 以後その配布先で `--check` が落ち続ける（手動で `--force` を実行するまで回復しない）。
4. **案内される復旧コマンドにも `--force` が無い**ため、配布先の人がそのまま実行しても同じ理由で
   失敗する。

これは「機械的に直せる追随箇所」ではなく、**配布先ごとに1回だけ必要な移行手順**である。
移行方針として (a) spec へ手順を書いて手動実行に委ねる (b) `install-to-project.sh` 側で残骸を
先に消す (c) 何もしない、の3択を計画に置いたが、**案1を採るため今回はいずれも不要**になった。

### 結論8: 現在の集合は「リンク運用時代の TARGETS」の引き継ぎである

```
$ sed -n '15,16p' .claude/docs/ddr/i0070-01-*.md
`.gemini/` は `settings.json` 以外（`docs/` `hooks/` `rules/` `scripts/` `skills/`）を
`.claude/` 配下へのローカルリンクとして持ち、`setup-gemini-links.sh` が各開発者のマシン上で
```

DDR `i0000-13` のタイトルは「`.gemini/`配下のリンク（docs/hooks/rules/scripts/skills）は…」で、
この5つが**リンク**として選ばれた理由は「Gemini CLIとClaude Code間でルール・スキル・スクリプトの
二重管理を避ける」ことだった。**リンクである限り複製は生じない**ので、対象を広く取るコストは
ほぼゼロだった。

issue #70（DDR `i0070-01`）が方式をリンクからコピーへ変えたとき、**この集合そのものは
再検討されていない**。結果として、複製が生じない前提で選ばれた集合が、複製が生じる方式へ
そのまま持ち越されている。

**issue #172 はこの点を正面から問う初めての機会である。** ただし本issueの問い方
（「3ディレクトリを外すか」）は、この経緯から見ると**切り方が合っていない**——正しい問いは
「`.gemini/` に何を置くべきか」であり、それには Gemini CLI の読み込み経路の観測が要る
（下記「設計への反映」2）。

### 採否の判断そのもの

**3つとも残す（案1）。** 決め手は次の3点で、**いずれも3ディレクトリに共通して効く**。

1. **外しても配布物は1バイトも減らない**（`dist-layers.json` で `.gemini` は `layer: exclude`）。
   得られるのはこのリポジトリと配布先で生成される `.gemini/` のサイズだけで、
   **失うもの（壊れたリンク・配布先の移行・未観測の推論への依存）と釣り合わない。**
2. **部分的に外すと、完全なコピーでも不在でもない中間状態になる。** `.gemini/` の価値は
   「`.claude/` と同じものが一式そろっている」ことにあり、82%を落として壊れたリンクを残すのは、
   残す・全部消すのどちらよりも悪い。
3. **外す根拠は未観測の推論であり、しかも対象を選べない。** 同じ根拠が `.gemini/rules/`
   `.gemini/skills/` にも当たる以上、3ディレクトリだけを外す線引きに根拠が無い。

**この判断は取り消しやすい。** 残す側の失敗は「複製が残る」で、気づいた時点でいつでも外せる。
外す側の失敗は「配布先で無言に壊れる」で、`--check` を回すまで気づけない。**非対称なので
取り消しやすい側へ倒した。**

## 確かめられなかったこと

- **Gemini CLI 実機の挙動は一切観測していない**（`command -v gemini` が空）。軸1の「0件」も
  結論5-2の「rules にも当たる」も、生成物と設定から導いた推論である。**この判断は未観測のまま
  行った。**
- **`.gemini/rules/` `.gemini/skills/` `.gemini/agents/` を外すべきかは判断していない**
  （本issueのスコープ外）。結論5-2で使ったのは「同じ根拠が当たる」という整合性の指摘までで、
  それらを外すべきだとは言っていない。
- **複製が実際にどれだけの害を出しているかは測っていない。** 案1の難点として挙げた
  「grep の二重計上」は、フェーズ2の調査で実際に踏んだ1件だけが根拠である
  （他の作業でどれくらい起きているかは調べていない）。
- **配布先での再適用は実行していない。** 結論7は `install-to-project.sh` と
  `sync-gemini-assets.sh` を読んで導いたもので、実際に古い `.gemini/` を持つ配布先へ
  再適用して観測したわけではない（案1を採るため、この検証は不要になった）。
- **git bash（Windows）実機での確認はしていない。** `--check` の所要時間・テストの結果は
  Linux 1環境のものである。
