実施した内容と結果

Q1. zip相当の可用性と代替戦略 ◎良

実測: zip（3.0）・unzip（6.00）・python3（3.11.15）・jar が存在。python-pptx は不在（方針どおり新規インストールせず標準ライブラリで検証）。LibreOffice 24.2.7.2 は存在するがフィルタ欠落で .txt すら読めず使用不能。

優先経路判断
1zip -X -r採用（実生成し検証合格）
2python3 標準ライブラリ zipfile採用（実生成し検証合格。エントリ集合・先頭・/ 区切りが経路1と一致）
—PowerShell Compress-Archive却下（検証できない手段を自動フォールバックに入れない）
—jar cfM却下（git bashでのJDK存在を前提にできず、経路1・2への利点が無い）

検出ロジック: command -v zip → 無ければ command -v python3 → どちらも無ければ明示エラーで停止（無言で壊れた .pptx を出さない）。OPCにはODFのmimetype相当の制約が無く、Deflate圧縮・/ 区切り・[Content_Types].xml 先頭配置で両経路とも合格。

Q2. 構成案JSONスキーマの依存範囲 △注意

PR #194 はフェーズ3に進行し、表紙のtype名が title → cover へ改名された（当方も追従）。スキーマファイル本体は未コミット。依存内容（トップレベル構造・enum 8種・型別フィールド）は正文mdへ転記済み。型別フィールドは暫定で、スキーマ確定後の突合手順と分岐（追従修正／記録のみ／#194クローズ時は当方を暫定の正としてspecへ明記）を定義した。実施タイミングはDraft解除前に必ず1回。

Q3. 最小OOXML構造 ◎良

13パーツの最小構成を実生成し、5検査すべて合格: unzip -t／zipfile.testzip()／全XMLのwell-formed／Content_Typesと実体の突合／rels整合（Target実在・r:id解決）。スライド枚数可変時の連動書き換えは [Content_Types].xml・presentation.xml（sldIdLst）・presentation.xml.rels・docProps/app.xml（Slides）の4箇所＋スライド毎rels。

Q4. 雛形の形態 — 展開ディレクトリを採用 △注意

展開ディレクトリ（assets/ 配下にXMLをそのまま置き、生成時にzip）を採用。差分レビュー可能・バイナリ管理の配慮が不要。バイナリ .pptx 案は却下（差分レビュー不能で、利点が「PowerPoint製の保証」しか無い）。

issue本文との差分（要承認） 「雛形をPowerPointで作る」はこの環境では満たせない。手組みのOOXML雛形＋機械検証＋人間の実機確認で代替し、生成スクリプトは「雛形ディレクトリを引数に取り ppt/slides/ 配下と連動4箇所だけを触る」形に固定することで、後からPowerPoint製一式へ差し替え可能にする。

Q5. 8種typeの写像 ◎良

6型必須はテキストボックス（p:sp）とネイティブ表（a:tbl）で表現（cover/section/bullets/two-column/table/summary）。代替2型は diagram→ノード箇条書き＋「A → B（ラベル）」エッジ列挙、comparison→表（列=候補、行=利点/欠点/採否）。speakerNotes は notesSlide として出力する方針（notesMaster同梱。フェーズ3で作業量を見て確定）。スキル名は pptx-slides、出力先既定は入力 <ベース名>.slides.json と同じディレクトリの <ベース名>.pptx。

Q6. 検証の切り分け ◎良

機械検証7種（zip整合性・well-formed・Content_Types突合・rels整合・a:t存在・table系スライドのa:tbl存在・入力JSON全テキスト値⊆a:t集合）を単体テストへ組み込む。人間の実機確認3種（PowerPointで警告なく開く／テキスト・表の編集／Windows git bashでの生成実行）はPRレビューへ依頼する。受け入れ条件7のHTML版との直接比較は #194 未マージのため不能で、「同じJSONに対する忠実性を双方が独立に検査する」分担とする（限界として明記）。
