実施した内容と結果

Q1. zip相当の可用性と代替戦略 ◎良

実測: zip（3.0）・unzip（6.00）・python3（3.11.15）・jar が存在。python-pptx は不在（方針どおり新規インストールせず標準ライブラリで検証）。LibreOffice 24.2.7.2 は存在するがフィルタ欠落で .txt すら読めず使用不能。

優先経路判断
1zip -X -D -r（-D でディレクトリエントリを作らない）採用（2枚構成で実生成し検証8種合格）
2python3 標準ライブラリ zipfile採用（全エントリ15件・順序の先頭・/ 区切りが経路1と完全一致することを突合済み）
—PowerShell Compress-Archive却下（検証できない手段を自動フォールバックに入れない）
—jar cfM却下（生成用途。git bashでのJDK存在を前提にできない。読み出し jar tf は独立実装の検証としてQ3で使用）

検出は「存在」ではなく「能力」で行う: command -v zip があり実際にzip生成→自己検証が通れば経路1。python側は python3 → python → py -3 の候補順に import zipfile の成否で試す（Windowsでは python3 という名前が無い構成・実行できないStoreスタブがある構成の両方がありうるため）。どちらも無ければ明示エラーで停止し、生成後は必ず自己検証を行い、失敗したら出力ファイルを削除して非0で終了する（無言で壊れた .pptx を出さない）。

OOXMLのzip制約は事実と理解を分けて記録: Deflate圧縮・/ 区切り・[Content_Types].xml 先頭配置・ディレクトリエントリ無しで両経路とも検証8種合格（事実）。「OPCにはODFのmimetype相当の制約が無い」は外部Web不使用のため仕様原文での裏取りをしていない未確認の理解で、先頭配置・-D は「PowerPoint自身の出力と同じ形へ寄せる」保険であり必須性は主張しない。

PR #194 はフェーズ3に進行し、表紙のtype名が title → cover へ改名された（当方も追従）。スキーマファイル本体は未コミット。依存内容（トップレベル構造・enum 8種・型別フィールド）は正文mdへ転記済み。title は全型必須（上流準拠。cover も例外にしない）。必須キー表には上流定義か当方の独自定義かの出どころを併記した。型別フィールドは暫定で、スキーマ確定後の突合手順と分岐（type名・必須キー・必須性の緩和/強化に差分→追従修正／差分なし・任意キー追加のみ→記録のみ／#194クローズ→当方を暫定の正としてspecへ明記しユーザーへ報告）を定義した。実施タイミングはDraft解除前に必ず1回＋#194のpush検知時に随時。

Q3. 最小OOXML構造 ◎良

15パーツ（2枚構成）を実生成し、検証8種すべて合格: zip生成（rc=0）／unzip -t／zipfile.testzip()／全XMLのwell-formed／Content_Typesと実体の突合／rels整合（Target実在・r:id解決）／全 .rels 内のrId重複0件／python経路との全エントリ完全一致＋jar tf（第3の独立zip実装）での読み出し。この15パーツで合格したことを測ったのであり、どれか1つを外すと壊れるか（必要性）と PowerPoint が受理するか（十分性）は測っていない（後者は人間の実機確認へ）。

rIdの採番規則（初版に無かった結論） 初版の雛形（1枚構成）は rId1=slideMaster / rId2=slide1 / rId3=theme で、スライド2枚目が theme と衝突する構造だった（敵対的レビューの指摘で判明）。結論: ppt/_rels/presentation.xml.rels は生成スクリプトが丸ごと所有し、固定rels= rId1=slideMaster・rId2=theme を予約、スライドは rId3 から枚数分の連番とする（sldId の id は256から連番）。

スライド枚数可変時の連動書き換えは5箇所: [Content_Types].xml のスライド毎Override・presentation.xml（sldIdLst）・presentation.xml.rels（ファイル全体を生成）・docProps/app.xml（Slides）・スライド毎rels。構造を決める4ファイルの現物は正文mdに貼付（残る11ファイルはフェーズ3で assets/pptx-template/ としてコミット）。

Q4. 雛形の形態 — 展開ディレクトリを採用 △注意

展開ディレクトリ（assets/pptx-template/ にXMLをそのまま置き、生成時にzip）を採用。差分レビュー可能・バイナリ管理の配慮が不要。バイナリ .pptx 案は却下（差分レビュー不能で、利点が「PowerPoint製の保証」しか無い）。

issue本文との差分（要承認） 「雛形をPowerPointで作る」はこの環境では満たせず、手組みのOOXML（Q3で機械検証済み）から始める。PowerPoint製雛形への差し替えは無加工では成立しない（rId採番の違い・既存slide1とsldIdLstエントリ・多数のslideLayout・presProps等の追加パーツの4点で衝突）。差し替えの前処理条件を固定する: (1) ppt/slides/ 配下と presentation.xml.rels を削除してから置く、(2) sldIdLst を空にしておく、(3) スライドの参照レイアウトは slideLayout1.xml に固定。この前処理でも追加パーツが壊れず残るかは未検証で、差し替えは「設計上の可能性」であって検証済みの機能ではない（フェーズ3のスコープ外）。

Q5. 8種typeの写像 △注意

type名は Q2 の転記どおり（表紙=cover）。6型必須はテキストボックス（p:sp）とネイティブ表（a:tbl）で表現（cover/section/bullets/two-column/table/summary）。代替2型は diagram→ノード箇条書き＋「A → B（ラベル）」エッジ列挙＋caption、comparison→表（列=候補、行=利点/欠点/採否）。箇条書き・表のテキストはすべて <a:t> として出力される（＝編集可能・画像化されない）。

speakerNotes の連動コスト（初版の見積りは過小・採否は◆） notesSlide の連動は「各1箇所」ではない。少なくとも (a) Content_Types へ notesMaster 1件＋notesSlideごとに1件のOverride、(b) presentation.xml へ notesMasterIdLst＋rels へ notesMaster 1件、(c) notesSlideごとのrels（対応スライドとnotesMasterへの参照）、(d) notesMaster自身のrels。つまりスライド枚数に比例する連動が2種類増える。notesMaster入り最小構成は実生成しておらず、この列挙自体の実測rootは無い。落とす場合はSKILL.mdへ「speakerNotesは出力されない」と明記する。

スキル名は pptx-slides（html-slides と対になる命名。却下: pptx-export・json-to-pptx）。出力先既定は入力 <ベース名>.slides.json と同じディレクトリの <ベース名>.pptx。

Q6. 検証の切り分け ◎良

機械検証はQ3の8種＋2種の計10種を単体テストへ組み込む: 9. table/comparison スライドに <a:tbl> が存在（受け入れ条件5の構造的証明）、10. 受け入れ条件7の突合 — 入力JSONの葉テキスト値ごとに、生成 .pptx の全 <a:t> 連結文字列への部分一致で存在すること（完全一致の集合包含にしない理由: 写像がテキストを合成するため。対象外リスト: meta.issue（docProps行き）、speakerNotesを落とした場合は speakerNotes も。検査方向はJSON→pptxの包含のみ）。

人間の実機確認は4種: (1) PowerPointで警告なく開く、(2) テキスト・表が選択・編集できる、(3) Windows git bash 上で生成スクリプトが動く — とくに zip 無し構成のpythonフォールバック・python3 という名前が無い構成・Storeスタブがある構成の3ケース、(4) どちらの経路で生成した .pptx かの記録。HTML版との直接比較は #194 未マージのため不能で、「同じJSONに対する忠実性を双方が独立に検査する」分担とする（HTML側の忠実性は #194 側の機械検査に依存することを限界として明記）。
