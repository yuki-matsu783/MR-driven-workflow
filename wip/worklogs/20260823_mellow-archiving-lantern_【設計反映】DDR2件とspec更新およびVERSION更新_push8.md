# worklog: 【設計反映】DDR2件とspec更新およびVERSION更新

対象: issue #145「MR/PRテンプレートの記載内容を、後から見返せるアーカイブとして再設計する」（2026-08-23）。
全体作業計画: `wip/plans/mellow-archiving-lantern.md`
個別作業計画: `wip/plans/【設計反映】DDR2件とspec更新およびVERSION更新.md`
push回数: 8

## 試したこと

- flow-id 4-1 で作った個別反映計画（md・html）に対し、敵対的レビュー（フェーズ4・1回目、カウンタ **1/3**）を実施した。
- findings 13件を1次振り分け表（confidence × severity）に通したところ、投稿候補12件・報告のみ1件になった。
  `select-adversarial-findings.sh` の結果は `posted=12 reported=0`（1次振り分けで報告のみへ落ちた1件は
  スクリプトへ渡していないため、スクリプト側の `reported` は0）。
- 投稿は**FILE単位**で行った。計画mdをレビュー前に全面的に書き直していたため、findingsが指す行番号が
  すでに意味を持たなくなっていたためである（行単位で投稿すると無関係な行に紐づく）。
- 12件すべてへ返信した（未返信スレッド 0）。

## うまくいったこと

- **13件すべてを計画へ反映した**（投稿した12件＋報告のみ1件）。作業項目 9→13件、完了条件 9→13件になり、
  1対1で対応する形へ揃った。追加した4件は次のとおり。

  | 作業項目 | 内容 |
  |---|---|
  | 10 | AIアセット反映の洗い出し（既知の候補3件を明記） |
  | 11 | `test_install_to_project.sh` のヘッダコメントを6種類の列挙へ書き直す |
  | 12 | DDR識別子の参照を `grep` で全件列挙して目視で突き合わせる |
  | 13 | md/htmlの4点チェック（見出し数・注意書き個数・`class` の妥当性・節構成の一致） |

- **完了条件へ「着手前」列を設けた**。着手時点での実測値（`class="warn"` が2件、「3種類」が1件、
  「例外は設けない」が6件）を残すことで、着手前から期待値と一致している＝検査として無意味な条件に
  気づけるようにした。これは「検証が変更前から成功する」という、フェーズ3で実際に踏んだ失敗
  （worklog push5）と同じ型である。
- **VERSIONの目標値の誤りを、着手前列を書く過程で発見した**。計画は 0.3.0 → 0.4.0 としていたが、
  main の PR #191 が既に 0.4.0 へ上げていた。**0.4.0 → 0.5.0** へ訂正した。
- **この計画のHTML自体が壊れていたことを、指摘を受けて発見した**。`class="warn"` は
  `plans.template.html` に存在しないクラスで（正しくは `class="box warn"`）、注意書きが地の文と
  区別が付かない状態だった。加えて土台にしたテンプレートが main のマージ前のもので古かったため、
  新しいテンプレートから生成し直した。`grep -c 'class="warn"'` = 0 を確認済み。
- **`check-doc-references.sh` の検出範囲の限界を明文化できた**。同スクリプトが拾うのは
  `.claude/docs/ddr/i0145-01-….md` のような絶対パス形式だけで、`DDR i0145-01` のような
  識別子だけの省略記法は対象外である。今回の参照はすべて後者なので、スクリプトを流しても
  「参照切れゼロ」としか出ない。作業項目12の目視突き合わせはこれを埋めるためのもの。
  併せて、この検査が**作業順に依存する**こと（DDR本体を作る前に参照側を確定させると必ず
  参照切れになる）も計画へ表として残した。

## ダメだったこと

- **「フェーズ4ではコードの変更は原則として行わない」という位置づけの書き方が誤りだった**
  （findings の factual-error 指摘。判断を撤回した）。`test_install_to_project.sh` のヘッダコメントは
  今回の変更で実際に古くなっており（「3種類」と書いてあるが検査は6種類、`(b2)` の説明が無い）、
  直す先はフェーズ4しかない。「原則として行わない」という曖昧な表現をやめ、**触ってよい範囲の表**
  （挙動を変えるコード＝触らない／今回の変更で古くなった記述＝触る／無関係な既存の欠陥＝報告のみ）
  へ書き直した。
- **調査レポートの「例外は設けない」の修正範囲を1箇所と見積もっていたが、実際は6箇所だった**
  （md 3箇所・html 3箇所）。1箇所だけ直すと、同じレポート内で「例外は設けない」と
  「アンカーは対象外」が併存する、より悪い状態になる。作業項目8のスコープを6箇所すべてへ広げ、
  完了条件11で `grep -c` が0であることを確認する形にした。
- **md と html の同期を、またしても落としかけた**（今回で3回目の系統）。前2回の反省として
  「mdを編集したらその場で4点検証を流す」と決めていたにもかかわらず、今回は
  「土台テンプレートが古い」「存在しないクラス名」という別の形で表面化した。
  4点検証の項目に**`class="box …"` の妥当性**を加え（作業項目13）、検証スクリプトの置き場と
  実行コマンドを計画へ明記した。
