## 観点表へ入れる検査コマンドを、書いた直後に2回壊した

**#9（必須節が丸ごと落ちたことの検出）の検査コマンドが、3版目でようやく動いた。**

### 1版目: ブラケット式へ多バイト文字を入れた

```bash
grep -o -- '<!-- \[必須\][^。]*' "$T" | sed 's/<!-- \[必須\] //'
```

実データへ当てた出力。

```
重<壊れたバイト列>

確
実施
設計
```

`.claude/rules/shell-script-style.md` が**既に警告している罠**である。

> POSIX/`LANG`未設定のロケールでは、POSIX ERE のブラケット式（`[...]`）へ多バイト文字を
> 直接含めると、`grep -E`・bashの `[[ =~ ]]` のいずれも該当行がマッチしないだけでなく、
> パターン全体が一致しなくなることがある。

**issue #171 が `.gitignore` のDDR参照検出で踏み、DDR `i0171-01` に記録した罠を、
その罠を扱う観点表を書いている作業で踏んだ。**

### 2版目: `sed` で回避したが、節名が一致しなかった

```bash
grep -o -- '<!-- \[必須\].*' "$T" | sed 's/<!-- \[必須\] //; s/。.*//'
```

多バイトの問題は消えた（`s///` の置換文字列に多バイトを置くのはブラケット式と違って安全）が、
**テンプレートのコメントは節名ではなく説明文だった。**

```
207:<!-- [必須] この計画で何をするか（目的）。削除しない -->
209-  <h2>この計画で何をするか</h2>
```

`（目的）` が付くため、成果物の `<h2>` と突き合わせると必ず差分が出る。

### 3版目: `[必須]` コメント直後の `<h2>` を取る

```bash
awk '/<!-- \[必須\]/{f=1; next} f && match($0, /<h2>[^<]*<\/h2>/) \
     {print substr($0, RSTART+4, RLENGTH-9); f=0}' "$T" | sort
```

正規表現がASCIIだけで構成され、節名は `<h2>` から直接取る。`sort` して突き合わせ、
**合格条件は「`<` の行が1つも出ないこと」**（`>` は成果物にだけある任意節・目次なので出てよい）。

### 教訓

**3版とも、実データへ当てたから分かった。** 観点表に「こう検査する」と書くだけで実行して
いなければ、どの版でも「書いてある」状態にはなり、**配布先で初めて壊れる**。

これは今回 #3 として `.claude/rules/` へ入れた「計画に書いた検査コマンドは文字列として
そのまま流す」と同根である——**検査は書いた時点では正しさが分からない。**
