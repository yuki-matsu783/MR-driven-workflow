# push8: 敵対的レビュー4回目（フェーズ3・作業実施）への対応

対象: `.claude/skills/commit/SKILL.md`（6件）と作業結果レポート（3件）。実施回数 2/3。

## 何が起きたか

**規約が、同じ節に載っている自分の模範例4件を不合格にしていた**（blocker）。

「6語（修正／更新／反映／追加／作成／記録）で終わる件名は不合格」という**一律の基準**を書いた
ところ、次の4件がすべて掛かった。

- 良い例 `docs: HANDOFFのflow-id 3-6完了とpush回数6を記録`
- 「成果物の変更を伴わないコミット」表の「求める形」3件

機械的に従えば模範例が全滅し、模範例を真似れば規約違反になる。**どちらへ倒しても矛盾する**ため、
規約を読むAIエージェントは判断できない。

## 教訓1: 「機械的に判定できる基準」を作ろうとして、判定と合否を同一視した

**6語で終わるかどうかは、機械的に測れる。** しかし測れることと、それが合否であることは別である。
「HANDOFFを更新」と「HANDOFFのflow-id 3-6完了とpush回数6を記録」は**どちらも6語で終わる**が、
前者は対象名しか伝えず、後者は変更後の状態を伝える。**6語は候補を絞る網であって、判定そのものでは
なかった。**

対処は判定を2段階に分けること。

| 段 | 何をするか | 誰が実行できるか |
|---|---|---|
| 1段目 | 6語で終わる件名を**候補として拾う** | `grep` で機械的に |
| 2段目 | 「その6語と直前の助詞を取り除いたとき、残るのは変更対象の名前だけか」 | 人間・AIが1問に答える |

**機械で全部決めようとしない。** 機械が担うのは「見るべき件名を減らすこと」で、良し悪しの判断は
1問に落とし込んで人間・AIへ渡すほうが、規約として壊れにくい。

## 教訓2: 地の文が主張することを、直下のコマンドで確かめていなかった

節には「語尾は『〜する』『〜した』『体言止め』のいずれも対象」と書いたのに、直下の判定コマンドは
`(する|)$` で、**「〜した」を1件も拾わない**。

```bash
printf 'docs: HANDOFFを更新した' | grep -cE -- '(修正|更新|反映|追加|作成|記録)(する|)$'   # → 0
```

**地の文とコマンドを同じ節へ並べたら、コマンドを実際に走らせて地の文の主張を確かめる。**
書いた本人には両者が同じものに見えるため、レビューまで気づかない。

なお、修正後に母数80件を数え直したところ**51件（64%）のまま変わらなかった**（母数に「〜した」で
終わる件名が0件だったため）。**数値が変わらないことも実測して確かめる**——「広げたのだから増える
はず」と推測で書くと、今度は数値のほうが嘘になる。

## 教訓3: 禁止を書くときは、リポジトリの既存資産に当ててから書く

「モデル名・モデルIDを含む記述は**リポジトリへ入る成果物すべて**で絶対に付けない」と書いたが、
grepすると既存資産3箇所に当たった。

| 箇所 | 何のためにモデル名を持つか |
|---|---|
| `.claude/rules/shell-script-style.md` | 桁区切りの誤適用例（`claude-3-5-sonnet-20241022`） |
| `.claude/scripts/test/test_usage_tracking.sh:402` | テストの期待値 |
| `.claude/hooks/post-push-usage-report.sh:88` | 対応工数レポートの「使用モデル」行の出力 |

いずれも「どのAIが書いたか」を示すものではない。**禁止は対象で書かず、目的で書く。**
「モデル名を書くな」ではなく「どのAIが書いたかを示す目的でモデル名を書くな」とすれば、
技術的な引用や機能の出力は自然に外れる。

## 教訓4: 新しい許容を足したら、既存の禁止が矛盾していないか探す

新設節が `Refs #NNN` フッターを許容したことで、31行の「`Co-Authored-By: Claude` **などのフッター**は
絶対に付けない」が矛盾した（「などのフッター」がフッター全般とも読める）。

**足した側だけを見ていると気づかない。** 同じファイル内で、その概念（今回は「フッター」）に触れて
いる箇所を全部拾ってから書き終える。

## 教訓5: 「作れたか」を検証項目にすると空振りする

検証10は「規約だけを読んで9行を書き直せるか」で、**書き直せた事実だけを見て合格にしていた**。
本来確かめるべきは「書き直した結果が規約を満たすか」である。

規約改訂後に9件を1段目へ通したところ、掛かったのは1件だけで、それも2段目を通った。
**成果物を作る検証は、作った成果物を検証基準へ通し直すところまでを1項目にする。**

## 手順上のメモ

- レビューコメントのIDは `pull_request_read method=get_review_comments` の返り値に `databaseId` が
  無く、`html_url` の `#discussion_r<数字>` から取り出す必要があった。
  レスポンスが65KBを超えて直接読めないため、ツール結果のファイルをpythonで解析している。
- スレッドは `total_count == 1`（返信ゼロ）で絞ると、今回の対象9件が正確に取れた。
