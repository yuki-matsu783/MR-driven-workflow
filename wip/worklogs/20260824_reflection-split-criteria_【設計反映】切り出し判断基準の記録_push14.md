# worklog: 20260824 切り出し判断基準の記録 push14

対応: 敵対的レビュー（フェーズ4・2/3回目）の14件。

## 指摘の型は1つだった

14件のうち、内容の誤りは実質**3つの型**に収まった。

| 型 | 件数 | 例 |
|---|---|---|
| **同じ数字が場所ごとに違う** | 5 | DDR「No 8件／8回止まる」・spec「5件が8回止まる」・レポート「7ファイル」・「却下案5件」で6件列挙 |
| **検査が実データで壊れている／空振り** | 3 | 必須節検査の偽陽性・反11 の合格条件・母数の表の2行目 |
| **新設した基準を、自分で通していない** | 1 | 手順3の穴（#12） |

残り5件は上のいずれかの派生（写経の実例取り違え・spec の却下案の抜け等）である。

## 必須節検査が偽陽性を出していた

前回（push12）に3版かけて書いた検査は、**まだ壊れていた。**

```bash
# 前回の版: sort して diff。合格条件は「< の行が出ないこと」
diff <(awk ... "$T" | sort) <(grep -o -- '<h2>[^<]*</h2>' <ファイル> | sed ... | sort)
```

**完全一致を要求するため、`<h2>変更対象（6箇所）</h2>` のように節名へ補足を足した見出しが
「落ちた」と判定される。** 実測すると、このブランチの計画HTML 4本のうち**2本**が偽陽性だった。

```
== 【AIアセット作成】…html   <   変更対象     ← 実際には「変更対象（6箇所）」が在る
== 【調査】…html             <   変更対象 / <   方針 / <   検証
```

`grep -qF` の部分一致へ変えると、偽陽性2本は消え、**1本だけが残った**。

```
【調査】反映対象の切り出し判断基準.html   落ちている必須節: 変更対象 方針
```

**これは真陽性である。** そのファイルの `<h2>` は 目次／前提（合意状況）／この計画で何をするか／
**調べる問い（6問）**／**調べ方**／やらないこと（スコープ外）／検証 で、`変更対象` と `方針` は
名前ごと置き換わっている。調査計画には変更対象も実装方針も無いので、**置き換えのほうが正しい**。

そこで、`wip/plans/REVIEW-POINTS.md` へ**名前を挙げた読み替え**として書いた（`変更対象`→`調べる問い`、
`方針`→`調べ方`、この2つだけ）。「ヒットするが問題ない」を許す形にはしない——それは
`wip/reports/REVIEW-POINTS.md` が自ら禁じている。

**意図的に壊したときに検出されることも確かめた**（`<h2>検証</h2>` → `<h2>けんしょう</h2>` で検出）。

## 同じ22行を2つの観点表へ写経していた

`wip/plans/` と `wip/reports/` の観点表へ、**テンプレートのパス1行だけを変えた同じ22行**を
置いていた。結果として、

- plans側が **reports固有の節名**（確かめられなかったこと／設計への反映）を実例に挙げ、
- reports側が **plansテンプレートのコメント**（`[必須] この計画で何をするか（目的）`）を引く

という、両方向の取り違えが同時に入っていた。**正が無いので、どちらを直せばよいかも決まらない。**

`wip/reports/` 側を正（コマンド本体＋理由）にし、`wip/plans/` 側は**テンプレートのパスと
計画側だけの読み替え**を持って正を参照する形にした。これで写経が消え、取り違えも同時に消えた。

## 手順3の穴を、主判定へ通した

DDR「調査の限界」に「`references/planning.md` 手順3 段階2 が `REVIEW-POINTS.md` 群を探索範囲に
含めていない。**このMRでは直していない**」と書いていた。理由は「判定に使っている手順を同じMRで
書き換えると、どちらの版で判定したのかが読めなくなる」だった。

**これは出口の説明であって、判定を飛ばしてよい理由ではない**（指摘のとおり）。#12 として
主判定へ通した。

| 主判定 | この反映を見送ってマージした場合、`main` は今回の変更と矛盾・不整合な状態になるか |
|---|---|
| 答え | **Yes** |

**このMRの判定は、既に直した側の探索範囲でやり直してある**（push10 の痕跡確認のやり直し）。
つまり手順の記述だけが古い。直さないと、**`main` に「記録された判定を再現できない手順」が残る**。
Yes なので出口の選択は無く、このMRでやる。

当初の懸念（どちらの版で判定したか読めなくなる）は、**判定を直した側でやり直した以上、
成り立たない**。むしろ直さないほうが読めなくなる。

## 数字が3通りに分かれた原因

DDR・spec・レポート・`HANDOFF.md` で、同じ「止まる回数」が 8回／8回／5回 の3通りになっていた。

原因は単純で、**8 は手順3をやり直す前の断面の値**、5 はやり直した後の値である。
どちらも間違いではなく、**どの断面の値かを書き添えていなかった**ことが誤りだった。

対処は2つ。

1. DDR・spec の該当箇所へ**断面を明記**し、断面が動いても変わらない構造
   （「OR では No の件数がそのまま停止回数になる」）で書き直した。
2. `references/planning.md`「判定の記録」の等式へ、**手順3で対象外になった件数を引く項**を足した。
   母数が「洗い出し10件」なのか「反映対象7件」なのかが等式から読めるようになる。

**2 は #12 と同じく、新設した基準そのものの改善である。**
