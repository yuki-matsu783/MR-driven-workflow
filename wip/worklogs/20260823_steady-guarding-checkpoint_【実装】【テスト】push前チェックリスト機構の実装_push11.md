# worklog: 【実装】【テスト】push前チェックリスト機構の実装（flow-id 3-9）

対象: issue #17「hookを使って、push時にしてほしいことを実現する」フェーズ3（2026-08-23〜24）。
全体作業計画: `wip/plans/steady-guarding-checkpoint.md`
個別作業計画: `wip/plans/【実装】【テスト】push前チェックリスト機構の実装.md`
作業結果（正文）: `wip/reports/20260823_steady-guarding-checkpoint_push前チェックリスト機構の実装.md`
push回数: 11

## 試したこと

- flow-id 3-8 で投稿した敵対的レビュー2回目の指摘7スレッド（8件）を1件ずつ実ツリーで再現し、
  **指摘が正しいことを確かめてから**直した。「レビュアーがそう言っているから直す」を避けるため。
- 縮退時フォールバックのブロッカーは、実際に `rc` を測って確認した。前置フィルタを
  そのままブロック判定へ使っていたため、`push-checklist.sh check`・`path`・
  `cat docs/push-notes.md` のいずれもが `exit 2` になり、**ブロックを解く操作そのものが
  止まって回復不能**になることを再現した。
- 対処として `command_hints_at_git_push_degraded`（`git` を見た後に `push` が来た場合だけ真）を
  新設し、16ケースの単体テストを足した。書き換え後に同じ3コマンドを測り直して全て通過を確認した。

## うまくいったこと

- **「過剰検知は害が無い」が成り立つ範囲を、はっきり線引きできた。** 前置フィルタ（足切り）は
  超集合であるべきで過剰検知が許されるが、**ブロック判定は1度でも誤ると作業が止まる**ため
  同じ理屈を持ち込めない。PostToolUse 側（生成・冪等）とPreToolUse 側（ブロック・非冪等）で
  縮退時の挙動をあえて非対称にし、その理由をコードのコメントへ残した。
- `stale`（チェックリストのコミット忘れ）が `exit 1`（非ブロック）だった件を `exit 2` へ直した。
  **この機構が防ぐために存在する失敗そのものが、唯一ブロックされない経路になっていた。**
- スラッグ一致が後方一致だったため `claude/hook-impl-17` のチェックリストがブランチ
  `hook-impl-17` にも一致していた件を、`<日付>_<スラッグ>` の厳密一致へ直した。
- 縮退経路を1度も踏んでいなかったテストへ、層1b（純粋関数16ケース）と層4（libを外した
  ディレクトリへhookを複製して実際に起動する）を追加した。

## ダメだったこと

- **レポートへ書いた「1,699アサーション」が、数えずに書いた値だった。** 指摘を受けて実測したところ
  レビュー時点で1,598、修正後で1,631だった。md 2箇所・html 3箇所・HANDOFF 1箇所の計6箇所を訂正した。
  数値は**書く瞬間に測る**しかない、という教訓を繰り返し踏んでいる。
- チェックリスト項目の4番目に `wip/plans/ wip/reports/` を直書きしていた。`.mrworkflow.json` で
  変えられる値なので、配布先で嘘になる。`{plansDir}` / `{reportsDir}` のプレースホルダへ直し、
  「テンプレート文字列に `wip/` が現れないこと」をテストで固定した。
- `mcp__github__pull_request_read` の `get_review_comments` が `page` を無視し、1ページ目を
  2回返してきた。カーソルを1件デコードして形式（`cursor:v2:` + msgpack風のタイムスタンプとID）を
  掴み、日付を未来側へ寄せた合成カーソルを `after` へ渡して7スレッドへ直接飛んだ。
