# worklog: 【設計】【実装】【テスト】ユーザー発言抽出・再注入の実装（push9）

## 試したこと

- ユーザーから「辞書は毎回のユーザの入力を見ながら育てて行きたい」との追加方針を受け取り、
  まず調査結果レポート（`wip/reports/…_transcript実測の調査結果.md`/`.html`）と全体作業計画へ
  この方針を反映した（flow-id 2-8 の判断として、辞書は継続し「育てる」運用にする旨・
  flow-id 3-1 で決める4点H-1〜H-4を明記）。
- flow-id 2-9として、指摘10スレッドへ返信した（対応内容の要約を各スレッドへ投稿）。
- flow-id 3-1として、個別作業計画を1ファイルへ【設計】【実装】【テスト】を併記して作成した。
  種別を分けなかったのは、フェーズ2の実測で数値・ロジックが確定済みで、残る設計判断が
  小さく実装方針と一体で判断できるため（`references/planning.md`「種別を複数併記する場合」）。

## うまくいったこと

- **残課題H（辞書を育てる実装4点）を、既存の仕組みの組み合わせで解けた。** 新しいインフラを
  作らず、(1) 辞書はプレーンテキストファイルへ切り出す（H-2）、(2) 除外実績は「辞書語＋件数」の
  形だけを可視化する（H-3）、(3) 育てた記録は辞書ファイル自体のgit履歴に委ねる（H-4）、
  という3つの決定がすべて既存の規約・仕組み（`.gitattributes`のLF保証・`wip/state/`の
  gitignore・`commit`スキルのメッセージ規約）へそのまま乗った。**新設したのは辞書テキスト
  ファイル1つと、累積カウントJSON1つだけ。**
- **秘密情報の扱いが、問い5自身の記録方針（「どの辞書語が何件落としたか」）をそのまま
  実装方針へ昇格させる形で決まった。** 除外された発言の本文を一切保存しない設計にしたことで、
  `.claude/rules/shell-script-style.md`「秘密情報の扱い」の「そもそも値を出さない形にできないか」
  を満たしつつ、「見ながら育てる」の実効性（辞書語ごとの傾向が見える）も両立できた。
- **E（単一transcript前提）の判断が、既存機能の再確認から自然に出た。** `build_work_context`が
  既に`HANDOFF.md`「次にやること」を毎セッション注入していることに気づき、過去transcript走査を
  実装せずこれで代替する、という最小変更の結論に至った。問い10aの実測（この環境では過去
  transcriptが0本）が、複雑な実装を避ける後押しになった。

## ダメだったこと

- **変更対象テーブルの列数を最初に間違えた。** ヘッダを「対象｜内容」の2列にしたまま、行を
  「区分｜対象｜内容」の3列で書いてしまい、markdownテーブルが崩れていた。作成直後に目視で
  気づき修正したが、**Writeツールで新規作成した直後こそヘッダと行の列数を数える**ことを
  怠らないようにする（今回はレビューへ出す前に自分で気づけたが、次は機械的に
  `grep -c '|' `で列数を数える確認を先に入れる）。
- **HTMLのtitle行のプレースホルダコメントを削除し忘れた。** テンプレートの使い方コメントが
  「`<title>`直前のコメントも削除する」と明記しているのに、`sed`でtitleタグの中身だけ書き換えて
  直前行のHTMLコメントを残していた。検証コマンド（`grep -c 'ここに書く'`）を実行して初めて
  気づいた。**このテンプレートの`<title>`はコメント＋タグの2行構成である**ことを次回から
  意識する。
