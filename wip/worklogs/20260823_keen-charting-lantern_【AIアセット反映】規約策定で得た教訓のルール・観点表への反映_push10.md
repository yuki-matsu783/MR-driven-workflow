# push10: 敵対的レビュー5回目（フェーズ4の計画）への対応

9件中8件を投稿・対応。**計画を2つへ分割**し、`【AIアセット反映】` 側の手順1〜4を実施した。

## 教訓1: 種別を併記した瞬間に、片方の評価軸が消えた

`references/planning.md` は「**`【設計反映】` `【AIアセット反映】` `【実装反映】` は、基本的に
併記せず分ける**」と、この3種別だけ一般の併記基準を**上書きする**規定を持つ。理由は
「評価軸が混ざりやすい」こと。

**初版はまさにそのとおりに壊れた。** 併記した計画の「やること」9件は全部が `【設計反映】` 側の
評価軸（正史へ何を書くか）で、`【AIアセット反映】` 側の評価軸（副産物の4類型分類・痕跡確認・
反映先の形態）が**1件も現れていなかった**。しかも併記の理由には、上書き**される側**の一般節を
引いていた。

- **規定に「基本的に〜する」と書かれているものを、一般則の判断基準で上書きしない。**
  一般節を読んで納得した時点で、その上に個別規定が乗っていないかを探す。
- 個別規定は**一般節のすぐ後ろ**にあった。読み飛ばしたのではなく、**一般節で答えが出たので
  読み進めなかった**。「答えが出た」は読むのをやめてよい合図ではない。

## 教訓2: 「着手前に読み直す」と書いた時点で、計画は判断を持っていない

決定Bは「判断根拠は `distribution-assets.md` の更新規則に従う（**着手前に読み直して確認する**）」と
書きながら、値だけ先に `0.4.0` と決め、検証の合格条件も `0.4.0` 固定にしていた。
**読み直した結果が別の結論になった瞬間、計画の検証が自分で不合格になる。**

実際に読んでみると、計画に無かった要件が2つ出てきた。

- 非対話例外は**条件付き**で、(1) specのchangelogと `HANDOFF.md`「判断を迷った内容」の**両方**へ
  記録し、(2) 否認されたら戻す、が義務。
- 同 spec には issue #170 で**書き込み自体がブロックされた記録**があり、本セッションは同じ実行環境。

**「着手前に読む」は、計画のレビューを受ける前に読むという意味ではない。** 計画に書く判断の
根拠なら、計画を書く時点で読む。

## 教訓3: 検証コマンドの基準値を、書く前に測った

`【AIアセット反映】` 側の検証は、**計画へ書く前に変更前のツリーで6件すべて実行**した。

| 検証 | 変更前の値 | 判定 |
|---|---|---|
| A5（当初 `ハング`） | **1** | **使えない**。`shell-script-style.md:771` の別文脈（`source` 時のstdin待ち）に当たる |
| 他5件 | 0 | 使える |

**1件が実際に空振りしていた。** `クォートし忘れ`（変更前0件）へ差し替えた。
これはルート `REVIEW-POINTS.md`「計画に書いた検証コマンドは、着手前に変更前のツリーで実行して、
期待どおり失敗することを確かめる」の実行例である。**規約に書いてあることを実際にやると、
6件に1件の割合で当たりが出る。**

## 教訓4: (a) と (c) の境界は「ファイルがあるか」ではない

B1「判定と合否を同一視した」を当初 (a)（該当アセットが無かった）と疑ったが、
**「AIアセットへ規約を書くときの観点」というアセット（`.claude/REVIEW-POINTS.md`
「スキル・ルール・エージェント定義」）は存在し、その罠が書かれていないだけ**なので (c) が正しい。

`references/planning.md` が「**該当するアセットはファイル単位ではなく記述単位で見る**」と
書いているのはこの逆向きの注意（ファイル単位で見ると (a) が原理的に発生しなくなる）だが、
**記述単位で見た結果を「アセットが無い」と読み違える方向にも同じ罠がある。**
「その罠を扱った記述が無い」＝(c) であって、(a) ではない。

## 教訓5: 導線 (d) の証拠が、レビュー指摘そのものに現れることがある

B3「禁止を書くとき、既存資産に当ててから書かなかった」は、ルート `REVIEW-POINTS.md` に
「**集約する前に、同じ判定を述べている行を全部数えたか**」という観点として**既にあった**。
そして敵対的レビュー4回目は、**まさにその観点を引いて**この誤りを指摘していた。

- **観点はあったのに、書く側は辿り着けなかった。** これが (d) の定義そのものである。
- **レビュー指摘が引いた観点表の項番は、(d) の直接の証拠になる。** 指摘が「観点表: 〇〇」と
  書いていたら、その観点は存在していて、書く側が届かなかったということ。

## 手順上のメモ

- `pull_request_read method=get_review_comments` は**返信済みスレッドも全件返す**ため、
  スレッド数が増えると結果が80KBを超えてツールが直接読めなくなる。
  `total_count == 1`（返信ゼロ）で絞れば対象だけ取れるが、**絞り込みはツール側に無い**ので
  結果をファイルへ落としてpythonで解析する必要がある。
- `perPage` / `page` は効かない（カーソルベース）。`page=4` を渡しても1ページ目が返った。
