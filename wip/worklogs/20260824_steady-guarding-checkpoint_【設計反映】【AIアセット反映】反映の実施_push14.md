## うまくいったこと

- **spec骨組みのプレースホルダを件数で検証する形（検証4・5）が、そのまま埋め忘れの防止に

  実際に書いてみると「影響範囲」「設定項目」「未決定事項・懸念点」の3節に加え、**冒頭の

  **却下案として書くだけでなく「当初こう実装していた」と書くほうが、なぜその判断が要るかが
  伝わる**（判断の非対称——回復可能かどうか——が、実際に踏んだ話として書ける）。

## ダメだったこと

### 1. 同じ罠を、同じissue内で2度踏んだ

検証2（参照切れ0件）が実施の途中で失敗した。

```
参照切れ数=1
HANDOFF.md:201:.claude/docs/ddr/i0017-01-<タイトル>.md
```

1度目は計画ファイルで、敵対的レビューに指摘されて直した。2度目は**その修正を説明するために
`HANDOFF.md` へ書いた行**である。

- **「絶対パス形式で書かない」という対処自体を説明する文章が、また絶対パス形式になる。**
  再帰的な形をしているので、注意していても踏む。
- 対処として、`HANDOFF.md` の該当行に「**この注記自身も同じ形で書くと同じ検出に当たる**ため、
  絶対パス形式を避けて書いている」と明記した。次に読む人が同じ書き換えをしないため。
- **教訓: 検出器に引っかかった記述を「直しました」と説明するとき、説明文が同じ検出器に
  引っかからないかを確かめる。**

### 2. 計画の検証の期待値を、実施の途中で2件変えた

**これが今回いちばん危うい操作だった。** 期待値を後から変えるのは、実装に合わせて goalpost を
動かすのと外形上は区別が付かない。

| 検証 | 当初 | 変更後 |
|---|---|---|
| 4 | bullet 数が前後で同じ（23 → 23） | 23 → 25（+2） |
| 5 | 入れ子込みで 39 → 40（+1） | トップレベル 39 → 40（+1） |

- **どちらも「計画時点の期待が、測ろうとしている性質を正しく表していなかった」ケースだと
  判断した。** 検証4は (d) の意味を「bullet を1件も増やさない」と狭く取りすぎていた。
  (d) が禁じているのは「既にある記述の隣へ**同じことを**書き足す」ことであって、別の確認項目を
  足すことではない。
- **ただし、この区別は当事者が主張しているだけである。** そのままにすると、次に同じ状況で
  「今回も性質が違ったので変えました」と言い続けられてしまう。
  - 対処1: 計画側へ**変更の事実と理由を書き込んだ**（消して書き直すのではなく、変えたことが
    分かる形で残す）。
  - 対処2: レポートの「重点レビュー依頼」の**判断してほしい**へ挙げた。
- **教訓: 検証の期待値を変えたら、変えたこと自体をレビュー対象にする。** 静かに直すと、
  検証が「実施後に辻褄を合わせるもの」に退化する。

### 3. 検証6の基準値が固定値ではなかった

計画に「23本・1,630・失敗0」と書いたが、実測は 1,631 だった。原因は
`test_install_to_project.sh` の dirty ガードが**作業ツリーがクリーンだとスキップされる**こと。

- **最初は「自分の変更でアサーションが1件増えた」と疑った。** テストファイルを一切変更して
  いないので変なのだが、そう考えた。
- **切り分けは `git stash` で行った。** 変更前後で全23本の内訳を取り、`diff` した。
  1行だけ違い、`test_install_to_project.sh` が 99 と 100 だった。
- ここで**もう一段間違えかけた**。「stash したら減ったのだから、自分の変更が原因だ」と読める。
  実際は逆で、**stash したこと自体（作業ツリーがクリーンになったこと）が原因**だった。
  出力の `note:` 行を読んで確定した。

  ```
  note: 本家がクリーンなため B-6（dirty ガード）はスキップしました（1件）
  ```

- **教訓: 「変更前後で比較する」ための操作（`git stash`）が、測定対象そのものを変えることが
  ある。** 比較のための操作に副作用が無いかを疑う。
- この知見は項目4の3つ目の候補（数値が測定時の環境の状態に依存しないか）として
  `wip/reports/REVIEW-POINTS.md` へ反映した。

### 4. 検証7の期待「項目4・5の書き換え分のみ」が曖昧だった

削除行が10行出た。全件を突き合わせたところ**すべて置き換えに伴う行**で問題は無かったが、
期待の書き方が悪かった。

- パスの指定（`.claude/rules/ .claude/skills/ …`）が**両方の計画の変更対象を含んでいる**ため、
  「項目4・5の分のみ」にはなりようがなかった。
- **この種の検証は「0であること」を期待にすると、正当な置き換えまで弾く。** 正しくは
  「**全件が説明できること**」である。レポートへは内訳の表を載せた。
