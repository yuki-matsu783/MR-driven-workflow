  2. `install-to-project.sh` の手順7が `--force` 無しで sync を呼び、**失敗しても警告のみで続行する**
     ため、既存の配布先では「古い3ディレクトリが残ったままインストール成功に見える」。
  後者は追随箇所の1つではなく**軸3（外すコスト）の評価そのものを変える**ため、事実の表へ I として
  追加し、移行方針（3択）をこの計画の決定対象に含めた。
- **`【実装】` の扱いを (2)（別ファイル＋3-2〜3-5 の合意）へ倒した。** 同じファイルへ節を追記する
  当初案では、実装方針に合意を取る地点がフローの中に1つも無かった。(1)（いま併記する）を採らな
  かったのは、案1なら実装0行・案2と案3では対象が違うため、いま併記しても「何に合意したのか」が
  定まらないから。
- HTMLは追記ではなく**body を丸ごと書き直した**（節構成が変わったため）。同期検査は
  placeholders 0 / 外部参照 0 / h2・h3 一致 / 全表のセル数一致。

## MRへ投稿しなかった「報告のみ」3件（いずれも minor / medium）

**内容は妥当だったので、投稿分と同じpushで修正した。**

1. **軸1の「経路」の定義が無く、事実Eと衝突する。** 軸1の問いを字義どおり「そのパスを指すもの」と
   読むと、`.gemini/docs/usecase/対応工数を把握する.md` からの相対リンク1件ずつ（事実E）が該当し、
   hooks/scripts も0件ではなくなって結論が反転する。
   → 軸1の問いを「**実行時に読む／実行する**経路（hook `command`・スクリプト呼び出し・設定キー）。
   **相対リンクは軸2で数え、軸1では数えない**」と書き切り、そう限る理由（事実A・Bが数えたのが
   それだから）も添えた。
2. **4軸をどう合成して採否を決めるかの規則が無い。** 加えて軸2の「切れても許容できる理由がある」と
   軸4の「利得が軸1〜3のコストを上回る」は、書き手が1行添えれば常に満たせる。軸4の言い回しも、
   軸1（読まれるか）はコストではないのでずれていた。
   → 「**軸1が0件で、かつ軸2を満たすものだけを『外す候補』とし、軸3・軸4で最終判断する**」という
   合成規則を1文で置いた。軸2の許容は**人間が判断し、理由と件数をレポートの「実施した内容と結果」へ
   書く**と指定。軸4の条件は「軸2・軸3のコスト」へ修正。
3. **「外す」ときの追随箇所2件が、計画のどのフェーズにも置かれていない。**
   (a) `check-doc-references.sh:9,14` の `CHECK_DOC_REFERENCES_EXCLUDED_DIRS` の
   `".gemini/scripts/test/"` — スコープ外の節が同じファイル名を別の論点（DDR `i0171-01` の検出範囲）で
   挙げているため、読み手には「このファイルは丸ごと対象外」と読めてしまっていた。
   (b) `test_install_to_project.sh:231` のコメント（`.gemini/{docs,…}` を例に挙げている。
   **アサーションは落ちないのでテストでは検出できない**）。
   → (a) はスコープ外の節に「**ただし同スクリプトの除外定義は別の話で、`scripts/` を外す場合の
   追随対象に含める**」と明記し、進め方6へも項目を追加。(b) は新設した「フェーズ4へ送る反映対象
   （候補）」節へ入れた。
