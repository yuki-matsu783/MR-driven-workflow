## うまくいったこと

- **`/compact` を人間に打ってもらう設計が機能した。** 問い9（compact前後の同一性）は
  AI側から起こせないため、flow-id 2-2 のレビュー依頼で明示的に依頼していた。実際に打って
  もらえたので、「未確認」への落とし所を使わずに済んだ。
  - **結果は肯定**（inode 不変・同一ファイルへ追記・compact前の発言も残存）。
  - 副産物として **`compactMetadata` が機械可読** であることが分かった
    （`trigger` / `preTokens` / `postTokens` / `cumulativeDroppedTokens` / `preservedSegment`）。
- **母集団の確定が、ヒューリスティックなしで済んだ。** `origin.kind == "human"` の1条件で
  22件 → 7件へ落ち、`human` 以外は0件だった。**当初「封筒プレフィックス（`<task-notification>`
  等）で除外する」案を検討していたが、不要だった**（構造で落ちるものを文字列で判定しかけた）。
- **問い13を、コードポイント単位の差分まで詰めて断定できた。** `last-prompt` と原文が
  「同じ長さ・同じ先頭・同じ末尾」なのに一致しない、という状態から、47文字目が
  U+0020 と U+000A の違いだと特定した。もう1組は約200字での切り詰めだった。
  **「たぶん同じ」で済ませずに済んだ。**
- **`main` 取り込みを敵対的レビューの前に置けた。** `wip/plans/REVIEW-POINTS.md` と
  `wip/reports/REVIEW-POINTS.md` が**両方**更新されており、push5 のときと同じ形だった。
  前回はダメだったこととして記録した項目が、今回は先回りできた。

## ダメだったこと

- **計画に書いたレポートのファイル名が、実際と食い違った。** 計画は
  `20260823_..._transcript調査結果.md` を前提に検証コマンドを書いていたが、日付が変わり
  実際は `20260824_..._transcript実測の調査結果.md` になった。検証コマンドが
  `test -f` の段で落ちるため、**計画md・html の6箇所を実際の名前へ置換**した。
  - **教訓**: 計画に書く成果物パスは**予測**である。日付を含む名前は日をまたぐと必ずずれる。
    検証コマンドが `test -f` で始まっていたおかげで気づけた（パスを固定値で書いておく価値は
    ここにある）。
- **問い8の初回測定で `perl` を不当に「壊れる」と判定しかけた。** `perl -CSD` で日本語が
  文字化けしたので不可と書きかけたが、原因は**呼び方の誤り**（`@ARGV` のデコードには `-CA` が
  要る）だった。`-CSDA` で測り直すと両ロケールで正しく動いた。
  - **教訓**: 「この手段は使えない」と結論する前に、**自分の呼び方が正しいか**を疑う。
    レポートには「perl 自体の欠陥ではない」と明記した。
- **性能の結論を「Linux で50ms、余裕十分」で終えかけた。** しきい値200msに対し1/4なので
  合格に見えるが、git bash では **jq の起動だけで138ms** を消費する。見積もり直すと
  **約194ms** で、しきい値の97%だった。
  - 計画に書いた「測定環境の断り」の節が効いた。**節を先に書いておかなければ、
    絶対値だけを見て合格と書いていた。**
- **除外辞書が、このリポジトリの運用と噛み合っていないことが分かった。** 過剰除去1件の
  中身が `ok`（flow-id 1-5 の合意そのもの）だった。方針どおり `ok`/`OK` を辞書から外すが、
  同じ理屈は `はい`・`了解`・`お願いします` にも及ぶ。**短い承認と意味の無い相槌を
  文字列だけで区別する手段が無い**というのが実データの示すところで、辞書という approach 自体を
  flow-id 3-1 で問い直す必要がある。
