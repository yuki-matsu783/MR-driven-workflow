# worklog: 個別反映計画の作成（flow-id 4-1）

## 試したこと

- `references/planning.md`「AIアセット反映の対象の洗い出し」の手順1〜3をそのまま実行した。
  起点は worklog 4本・reports 2本・MRのレビュースレッド43本。
- 手順3（痕跡の確認）を、候補ごとに `grep` と `doc-search` の**両方**で行った。片方だけで
  打ち切ると (d)「あったのに辿り着けなかった」を手順自身が生む、と手順書が明記しているため。
- **`【実装反映】` を立てるかどうかを検討し、立てないことにした。** 持ち越していた指摘は
  `--tags` / `--delete` の一律ブロック1件だけで、これを「一律ブロックのまま仕様へ明記する」と
  決めた結果、実装変更が消えて `【設計反映】` に吸収されたため。

## うまくいったこと

- **(a) が0件だと確定できた。** 5件すべてが (c) 追記か (d) 導線改善で、新規ファイルは1つも
  作らない形になった。手順書が「ファイル単位ではなく記述単位で見る」と言っている意味が、
  実際にやってみて分かった——「近いファイル」は必ず見つかるが、「その罠を扱った記述」は
  項目1・4の2件しか無かった。
- **項目1（`read -a` がタブ区切りに使えない）が既に記録済みだったことに、洗い出しで初めて
  気づいた。** `.claude/docs/spec/generate-ddr-list.md` と DDR `i0135-01` に同じ罠がある。
  実装中はこれに辿り着けず自力で debug していたので、(c) ではなく (d) が正しい。
- `--tags` / `--delete` の判断は、**誤りの向きの非対称**で決められた。逃げ道の実装（案B）が
  誤ると「通してはいけないpushを通す」＝ガードが黙って効かなくなるのに対し、一律ブロック（案A）の
  誤りは「通すべきpushを止める」だけで、その場で見えるうえ必ず解ける。

## ダメだったこと

- **`【AIアセット反映】` の計画を「4件」という題で書き始め、表には5件並べていた。** 書いている
  途中で候補を1件統合しようとして、やめた判断のほうを本文へ反映し忘れた。題名・description・
  H1・地の文の4箇所が食い違ったまま完成しており、自分で読み返して気づいた。
  - **数の食い違いは、書き終えてから数え直すしかない。** 直前に「訂正値も測り直す」という
    知見を反映対象へ挙げたばかりで、その場で同じ型の誤りをしていた。
- 同じ計画の起点の件数を「MRのレビューコメント26件」と書いたが、これも数えずに書いた値だった。
  `HANDOFF.md` の投稿件数（10 + 12 + 14 + 7）を実際に足して43本へ直した。
