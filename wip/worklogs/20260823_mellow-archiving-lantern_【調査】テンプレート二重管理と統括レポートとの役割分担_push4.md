### 3. HTMLビューを本文ごと作り直した

指摘7・8はHTML側の食い違いだが、md側の修正が広範（新設1節・§1/§3/§4/§6の書き換え・表の追加）だったため、
**部分修正ではなく本文を全面的に書き直した**（`plans/REVIEW-POINTS.md` の観点。追加だけでは同期にならない）。

検証は前回と同じ4点で行い、すべて通った。

- md の `#`〜`###` と HTML の `<h1>`〜`<h3>` が、バッククォート／タグを除去して**完全一致**（`目次` を除く）
- 各表の `<td>`/`<th>` 数が全行で揃っている（表10件 / 不揃い0件）
- プレースホルダ 0件 / 外部参照 0件
- CR混入なし（バイト数比較）

### 報告のみの3件（投稿しない）

1次振り分け表で「報告のみ」に落ちたもの。内容はここへ残す。

- **[minor / 確度: medium]** サマリ表の「根拠の性質」列が、問1だけ「実装の確認＋既存の先例」と2つ書いており
  他の行と粒度が揃っていない。→ 情報量が増える方向のずれなので**採らない**。
- **[nit / 確度: high]** 「案B」という呼称が、このレポートと計画の中でしか通用しない。spec/DDRへ
  転記するときに「案B」だけが残ると読めなくなる。→ **フェーズ4のDDR執筆時に、案の内容を展開して書く**という
  形で受ける（このレポート内では案A/B/Cの内容を表で示しているため今回は修正しない）。
- **[nit / 確度: low]** 「確かめられなかったこと」の4件目（本文の長さ）は、確かめられなかったのではなく
  **まだ確かめていない**もの。→ フェーズ3の実測で解消される見込みなので、節の分割はしない。

## うまくいったこと

- **敵対的レビューが、自分で書いた事実誤認を3件（#2 `reportsDir`・#6 `get_provider` の出典・
  #4 正の向き）掘り出した。** いずれも「実物を読み直したら確かに違った」もので、レビュー時に
  再検証したところ**3件とも指摘が正しかった**。独立したコンテキストで動く効果がそのまま出ている。
- **#2 は指摘そのものより、指摘が暴いた「関数の出力と手順文言の既存のずれ」のほうが価値が高かった。**
  10節の `## 検証` `## 設計判断・採らなかった案` は `reports/` の結論を転記する節なので、
  手順1が `reports/` を読まないままだと材料が手に入らない。フェーズ3の作業項目（3-b）が1つ増えた。
- **#9（10節の中身が書かれていない）は、寿命の違いに気づかせる指摘だった。** 「10節構成」という語を
  何十回使っても、その実体が `plans/`（flow-id 5-5 で削除）にしか無ければ、spec/DDRへ転記する
  段階で参照先を失う。恒久参照先を issue 本文と明示するのは、まさに本issueが解こうとしている問題そのもの。

## ダメだったこと

- **前回のレビューで直したはずの「md/html 同期」を、今回また落としていた**（#7・#8）。
  前回はplansのHTMLでフェーズ3節が丸ごと抜けており、今回はreportsのHTMLでメタ情報と用語がずれた。
  **md を書き換えたら HTML も同じ回で書き換える**という手順が身についていない。
  - 対策: 今回から**md を編集したら、その場で見出し・表・メタの4点検証を流す**ことにした
    （検証コマンド自体は前回作ってあったのに、走らせていなかったのが実態）。
- **#5（貼った出力がコマンドで再現できない）は、レビューでなければ気づけなかった類ではない。**
  「除外は括弧書きで説明した」で済ませており、貼り直す手間を惜しんだだけだった。
  根拠として貼る出力は、**貼ったコマンドをそのまま実行して得たもの**にする。
