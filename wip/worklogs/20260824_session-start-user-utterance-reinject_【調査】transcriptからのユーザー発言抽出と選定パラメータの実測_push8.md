## うまくいったこと

- **「不合格として人間へ上げる」という停止条件が、意図どおり機能した。**
  計画は「しきい値を後から緩めない」と定めており、AIは約208msを不合格と結論して案A/B/Cを添えた。
  **人間が値そのものを改めた**結果、合格になった。
  - **AIが自分で緩めるのと、人間が値を改めるのは別の経路である。** 計画側の停止条件へ
    この区別を明記した（前者だけを禁じる規則だと読めるようにした）。
  - **改定は「+4.6MB」の誤り訂正の後**に起きた。順序が逆なら「誤った値を根拠に緩めた」に
    なっていた。レポートにこの順序を明記した。
- **辞書の判断が、実データの形と噛み合った。** 「育てる」という方針は、
  **辞書12語のうち実際に働いたのが `ok` の1語だけ**（しかも過剰除去）という実測と一致する。
  机上で並べた11語はこの断面で一度も働かなかった。
- **「育てる」から、設計上の要求が1つ導けた。** 育てるには**何がどの語で落ちたかが見える**必要が
  あり、hookが黙って落とすままでは辞書は育たない。**残課題H の4点のうち可視化を要と位置づけた。**
  - 本調査で過剰除去に気づけたのは、**除外前後の件数を突き合わせたから**である。
    通常の運用にはその突き合わせが無い。

## ダメだったこと

- **返信ゼロのスレッドが10件残ったまま、2-6〜2-9 の進捗列を `[x]` にしていた。**
  `update-handoff-progress.sh` は `- 未返信スレッド:` が0でなければループ範囲への `mark-done` を
  拒否する。**その値を更新しないまま進捗列だけを書き換えていた**ため、機構が働かなかった。
  - issue #70 が塞いだはずの「返信ゼロのスレッドが未対応と区別が付かないまま残る」状態を、
    **別の入口から再現していた**。
  - 今回は `set-header --unreplied 0` を**実物の再取得で確認してから**書いた
    （全30スレッドを1ページで走査し `hasNextPage: false`、返信ゼロ0件）。
  - **教訓**: ヘッダの値は `mark-done` を通すための入力ではなく「確認した結果」である。
    先に進捗列へ手を伸ばした時点で、順序が逆になっている。
- **レポートの `.md` と `.html` で、同じ変更を2回書く形が続いている。** 今回も6ファイルへ
  同じ判断を手で反映した。md を正文としてHTMLを生成する仕組みが無いため、
  **同期は毎回の注意に依存している**（push7 で踏んだ乖離と同根）。
  - 今回は md を先に確定させ、HTML はその内容へ合わせる順序を守った。
  - 検査は機械的に行える（見出しの網羅・プレースホルダ・外部参照・重複id・未解決アンカー）ので、
    **少なくとも「壊れていないこと」は毎回確認する**運用にしている。
