# worklog: 【AIアセット作成】残置テキストの係り先ルールを一般化する

対象: `.claude/rules/docs-workflow.md` の「見出しの差し込み時に係り先を確認する」ルールの一般化（2026-08-23）。
全体作業計画: `plans/brisk-weaving-lantern.md`
個別作業計画: `plans/【AIアセット作成】残置テキストの係り先ルールを一般化する.md`
push回数: 4

## 試したこと

- 書き換えは `sed -n` で前後を切り出し、置き換え後の文をヒアドキュメントで書いた別ファイルと
  連結する方式で行った（`.claude/rules/shell-script-style.md`「差し込むファイルは、先頭に空行を
  置かず、末尾に空行をちょうど1つ持たせる」に従う）。連結後、差し込み位置の前後を目視した。
- 実例の追加位置は**既存2件の前**。計画 A-3 の決定どおりで、実装時に迷う余地は無かった。
- 既存6行の残存は**2通り**で確かめた。(1) 削除検査（`git diff | grep '^-' | grep -cF`）が `0`、
  (2) 書き換え前の109〜114行をパターンファイルにした `grep -n -F -x -f` が **6件一致**。
  前者は「その語を含む削除行が無いか」、後者は「その行がバイト単位でそのまま在るか」を見る。
- 事故4件の当て直しは、**書き換え後の実文言の該当段落を明示する**形で表にした
  （「段落1が『箇条書きへの項の追加』を例示」のように、条文のどこが効くかまで書く）。
- 陰性ケースは構成した1件。実在の事故ではないことをレポートへ明記した。

## うまくいったこと

- **存在検査（`grep -c`）を削除検査と分けた設計が効いた。** 「逃げ道が残っていること」は
  削除検査では原理的に見られない（同じ語句がAの書き換えで消える側にもあるため、削除検査に
  入れるとAの正常な書き換えで必ず1が出る）。分けたうえで、
  `grep -cF '前と後ろの両方' REVIEW-POINTS.md` が**着手前 `0` → 書き換え後 `1`** になることを
  確認できた。**空振りしない検証を、着手前に「必ず落ちる」形で用意できた**のはこれが初めて。
- **A-4 の既定（新しい見出しを立てない）で、実際に何も壊さずに収まった。** 4段落＋実例4件を
  見出し無しの地の文として書いたため、直後の `HANDOFF.md` の段落の直前の見出しは
  書き換え前と同じ `# ドキュメント運用`（10行）のままである。

## ダメだったこと

- **A-4 の確認コマンドを、最初は `sed -n '100,130p'` の固定行番号で書いていた**（敵対的レビューの
  指摘で気づいた）。実例が2件増えて対象段落が下へ動くため、増分次第で窓の外へ出る。
  「見えなかった＝問題なし」と誤読されうる形だった。パターン走査へ変えたが、**素朴な
  `awk '/^#/'` はフェンス内の `# 設計: issue #15 → …` というbashコメントを見出しと誤認**し、
  `直前の見出し: 75: # 設計: issue #15 → …` を返した。フェンスの開閉を追う実装にして解決した。
- **その awk をmdの計画へ書くとき、`/^```/` がmarkdownのフェンスを閉じてしまった。**
  行頭からのインデントが2文字だったため、フェンス終端として解釈される位置だった。
  `/^[`][`][`]/` という文字クラスへ書き換えて、3連バッククォートが並ばない形にした。
