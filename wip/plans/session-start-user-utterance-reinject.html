この計画で何をするか

.claude/hooks/session-start.sh に、ユーザーが自分の言葉で打った入力の抜粋を additionalContext へ足す項目を1つ追加する。抽出元は hook が stdin で受け取る JSON の transcript_path（JSONL）である。

compact の要約は「何を残すか」を指定できないため、依頼・制約・除外条件が言い換えや圧縮で歪む・落ちる。 生の文字列を少量だけ持ち込むことで、要約の精度に依存せず「何を頼まれたか」を保つ。 issue #57（DDR i0057-01）が入れた「compact後の現在地の再注入」の延長にあたる。

前提（合意状況）

  • issue #151 本文が、実 transcript に対する事前確認（人間の入力は type=="user" かつ .message.content が文字列の行／hook の注入は type:"attachment" で混ざらない／ transcript は追記専用）を済ませている。まだ人間のレビュー合意は得ていない（flow-id 1-5 が未了）。
  • 起票時の初期案「頭100文字 × 最大20件」に対し、本セッションでユーザーから方針変更の指示 （「最初の3件のうち意味のありそうなもの＋直近7件のうち意味のありそうなもの、最大合計10件」）があった。 本計画はこれを採用し、下記「方針」で3点を上乗せして提案する。

方針

採用する選定ロジック（ユーザー案＋3点の上乗せ）

ユーザー案「先頭3件＋直近7件、最大合計10件」を採用する。中盤を捨てるのは、セッション中盤が 「ok」「次へ」「それで」といった往復に偏り、同じ枠を使うなら先頭（＝要件定義）と直近（＝現在地）へ 寄せたほうが1件あたりの情報量が高いためである。そのうえで次の3点を上乗せする。

  1. 「先頭」は、現在のブランチに絞ったうえでの先頭とする。 gitBranch が現在のブランチと一致する行だけを母集団にすると、「先頭3件」が このタスクでの最初の依頼を指すようになり、別タスクの発言が枠を食う問題（issue本文の論点2）も 同時に解ける。一致行が0件のときだけ絞りを外す（ブランチ作成前の発言しか無いセッション・ gitBranch 欠落への fail-open）。
  2. 切り出しは「頭M文字」ではなく「頭M文字＋末尾M′文字」にする。 制約・除外条件は末尾に来やすい（「ただし〜はしない」「〜は触らないで」）。頭だけでは、 この機能が守ろうとしているものをまさに落とす（issue本文の論点4）。
  3. 先頭3件は厚く、直近7件は薄く配分する。 初期値は先頭3件＝頭120字＋末尾40字／直近7件＝頭80字＋末尾30字とし、フェーズ2で実データにあてて調整する。

「意味のありそうなもの」（issue本文の論点3）は、次の除外規則として実装する。

  • 文字数がしきい値未満で、かつ既知の相槌パターン（ok / はい / お願い / 続けて / ありがとう 等）に一致するもの。 短いだけでは落とさない（「ダメ、やり直して」のような短くて重要な指示があるため）。
  • 引数の無いスラッシュコマンド単体（/compact /commit 等）。 引数付き（/issue-mr-flow start 151）は残す（何に着手したかの情報を持つため）。
  • <command-name> <local-command-stdout> 等、CLI の展開結果で始まる行。

サイズの扱い（issue本文の論点5）

  • 件数と1件あたりの文字数を固定するため、この項目のバイト数は設計上有界である。 さらに節全体のバイト上限（初期値 4000 バイト）を置き、超えたら直近側の古いものから落とす。
  • CONTEXT_SIZE_WARN_BYTES の対象には含めない。 このしきい値は 「HANDOFF.md や計画が整理されないまま膨らみ続けている」ことを検知して人間に整理を促すためのもので、 整理のしようが無く有界な項目を分母へ入れると、誤った警告が常時鳴る。実装上は main で append_size_warning を適用した後にこの節を連結する。
既存の記述を置き換える場合 本計画に「既存の記述の置き換え」は含まない。 session-start.sh への変更は build_work_context と並ぶ新しい項目の追加であり、既存の注入項目（ブランチ／issue／PR／ 未解決コメント件数／HANDOFF.md「次にやること」／SKILL.md 再読み込み指示）はいずれも文言・条件を変えない。 唯一の例外が main における append_size_warning の適用順で、これは 置換ではなく連結位置の変更のため、フェーズ3の個別作業計画で置換前・置換後の形を示す。

実装上の制約（規約からの持ち込み）

  • transcript は数MBになりうるため、内容を --argjson/--arg で jq へ渡さない。 ファイルパスを渡して jq -R -n ＋ inputs で jq 側に読ませる。
  • jq 呼び出しは1回に集約する（行ごとに jq を起動しない）。
  • 複数行の値をコマンド置換で受けるため、tr -d '\r' を挟む。
  • 抽出・整形の中核は副作用の無い純粋関数として切り出し、source して直接呼べるようにする。

フェーズ2〈調査〉

実施する。 数値（件数・文字数・除外規則）は実データにあてないと決められないため。

  1. hook が受け取る stdin JSON に transcript_path は含まれるか。実体はどこにあり、行数・バイト数はどの程度か。
  2. 実 transcript に対し、issue 本文の抽出条件で何件取れるか。tool_result・hook 注入・サブエージェント由来が混ざらないことを実データで確認できるか。
  3. gitBranch はどの行にも入っているか。ブランチ絞りをかけたときの残存件数は。
  4. 抽出できた発言の文字数分布はどうか。頭120字＋末尾40字で何割が全文に収まるか。
  5. 相槌・スラッシュコマンドは実際に何割を占めるか。除外規則の初期値で過剰除去・除去漏れは起きないか。
  6. 先頭3＋直近7を上記の配分で切り出したときの実測バイト数は。4000 バイトの上限に収まるか。既存の注入量（実測 1.2KB）と合算しても運用上問題ないか。
  7. jq -R -n ＋ inputs 方式で、実 transcript のサイズでも所要時間が許容範囲か。

何が分かれば次へ進めるか: 上記 1〜6 が数値で埋まり、件数・文字数・除外規則の初期値が確定すること。

やらないこと（スコープ外）

この計画では決めない・触らない
  • PreCompact hook 経路での実装 — DDR i0057-01 で却下済み（additionalContext を持たない）
  • 起動要因（startup/resume/clear/compact）ごとの分岐 — 「取れた分だけ出す」設計で自然に解決する（issue本文の論点6）
  • ユーザー発言の全文保存・外部ファイルへの退避 — 本 issue の目的は「少量・有界な再注入」。別 issue の領域
  • AI（assistant）側の発言の再注入 — issue 本文が対象を「ユーザーの生の入力」に限っている
  • transcript の書き換え・削除 — transcript は追記専用の外部資産であり、本機構は読み取りのみ

比較検討した案

案利点採否と理由
先頭3件＋直近7件（最大10件）／ブランチ絞り／頭＋末尾要件定義と現在地の両端を押さえつつ、枠あたりの情報量が高い採用 ユーザー指示を基礎に、ブランチ絞り・頭＋末尾・配分の3点を上乗せ
直近20件を均等に頭100文字（issue 本文の初期案）実装が単純却下 中盤の往復（「ok」「次」）が枠を食い、1件あたりの情報量が低い
直近10件のみ実装が最も単純却下 長いセッションでは最初の依頼（最も歪んでほしくないもの）が落ちる
全発言から文字数の多い順に上位N件情報量の多い発言を拾える却下 貼り付けたログ・エラー出力が上位を占め、依頼が押し出される
頭のみM文字で切る実装が単純却下 末尾に書かれがちな制約・除外条件を落とす（issue本文の論点4）
ブランチ絞りをかけない実装が単純／取りこぼしが無い却下 セッションがブランチをまたぐと、別タスクの発言が「先頭3件」を占める
ブランチ絞りを常に強制する混入がゼロになる却下 一致0件のときに何も出せない。0件時のみ絞りを外すフォールバックを採る
この項目も CONTEXT_SIZE_WARN_BYTES の分母へ入れる注入量の総量を1つの値で見られる却下 有界かつ整理不能な項目のため、「整理せよ」という誤った警告が常時鳴る
しきい値を引き上げる（8000→12000 等）警告が鳴らなくなる却下 本来検知したい「HANDOFF.md の肥大化」の感度を下げる
