この計画で何をするか

.claude/hooks/session-start.sh に、ユーザーが自分の言葉で打った入力の抜粋を additionalContext へ足す項目を1つ追加する。抽出元は hook が stdin で受け取る JSON の transcript_path（JSONL）である。

compact の要約は「何を残すか」を指定できないため、依頼・制約・除外条件が言い換えや圧縮で歪む・落ちる。 生の文字列を少量だけ持ち込むことで、要約の精度に依存せず「何を頼まれたか」を保つ。 issue #57（DDR i0057-01）が入れた「compact後の現在地の再注入」の延長にあたる。

方針

出力位置と、出す／出さない経路

新しい節は build_context の中（build_work_context 経由）で組み立てる。main 側では連結しない。 これにより、ブランチ名（ブランチ絞りに必要）を build_context のローカル変数からそのまま使え、既存のフォールバック方針にも自然に従う。

build_context の経路既存の挙動ユーザー発言節
正常（作業ブランチ上、CLI経路・MCP経路とも）全項目を注入出す
exit 2（main ブランチ上・ブランチ未チェックアウト）何も注入しない出さない（既存方針を変えない）
失敗（非ゼロ終了）(issue/MR情報の取得に失敗しました) のみ出さない

3つ目について: build_context の失敗は Provider.sh の読み込み失敗など環境が壊れていることを示すため、 そこで出力の形を増やすと原因の切り分けが難しくなる。フェーズ2の問い1の結果次第でフェーズ3で再検討する（現時点では出さない側に倒す）。

採用する選定ロジック（ユーザー案＋3点の上乗せ）

ユーザー案「先頭3件＋直近7件、最大合計10件」を採用する。中盤を捨てるのは、セッション中盤が 「ok」「次へ」「それで」といった往復に偏り、同じ枠を使うなら先頭（＝要件定義）と直近（＝現在地）へ 寄せたほうが1件あたりの情報量が高いためである。そのうえで次の3点を上乗せする。

  1. 「先頭」は、現在のブランチに絞ったうえでの先頭とする（絞れる環境でのみ）。 gitBranch が現在のブランチと一致する行だけを母集団にする。この絞りは必須ではなく、材料があるときだけ効く任意の絞り込みとして実装する（下記「ブランチ絞りは絞れる環境でのみ効かせる」）。 この上乗せが解くのは「1つのtranscriptが複数ブランチをまたぐ」方向だけである（逆方向は下記「単一transcript前提の限界」）。
  2. 切り出しは「頭M文字」ではなく「頭M文字＋末尾M′文字」にする。 制約・除外条件は末尾に来やすい（issue本文の論点4）。 全長が M+M′ 以下なら全文をそのまま出す（これを書かないと、短い発言で頭と末尾が重なり同じ部分を2回出す）。 切り出しは文字単位で行う（バイト単位で切るとマルチバイト文字が壊れる。手段はフェーズ2の問い8で確定）。
  3. 先頭3件は厚く、直近7件は薄く配分する。 初期値は先頭3件＝頭120字＋末尾40字／直近7件＝頭80字＋末尾30字。フェーズ2で実データにあてて調整する。

ブランチ絞りは絞れる環境でのみ効かせる（Gemini CLI では不可能）

Gemini CLI では原理的に絞れない Gemini CLI のセッションログには gitBranch に相当するフィールドが無い。 これは本issueで新たに分かったことではなく、issue #97 のフェーズ2調査で確認され DDR i0097-04 へ記録されている事実である（「メッセージ単位でブランチも作業ディレクトリも記録されない」。 唯一近い1行目メタデータの directories はセッション単位のプロジェクトディレクトリであり、 同じワークツリーでブランチを切り替える通常の運用では常に同じ値になるため代用にならない、と却下理由まで書かれている）。

したがってブランチ絞りは必須の前処理にせず、材料があるときだけ効く任意の絞り込みにする。

抽出した行の状態母集団
gitBranch を持つ行があり、現在のブランチと一致するものが1件以上ある一致する行だけに絞る
gitBranch を持つ行があるが、一致するものが0件絞らず全体（ブランチ作成前の発言しか無いセッション）
gitBranch を持つ行が1件も無い絞らず全体（Gemini CLI 形式のログ・フィールド欠落）

切り替えの判定は「経路（Claude Code か Gemini CLI か）」ではなく「行が gitBranch を持つか」で行う。 理由は2つ。

  1. SessionStart には経路を判定する手段が無い。 既存のhookが使うエンジン判定 （tool_name が run_shell_command なら Gemini、Bash/PowerShell なら Claude）は PreToolUse/PostToolUse 専用で、SessionStart のペイロードには tool_name が無い。
  2. フィールドの有無で切り替えれば、将来 Gemini CLI 側がブランチ情報を持ったときに自動で追随する。 経路名で分岐すると、そのときコードを直しに戻る必要がある。

この分岐は「絞れないと壊れる」ものではない。 絞りは1件あたりの情報密度を上げる最適化であって、 絞れなくても「先頭3件＋直近7件」は成立する（先頭が別タスクの発言になりうる、という質の低下に留まる）。

除外規則を先に適用して母集団を作り、そこから採る。 母集団を時系列順に並べて N 件とすると:

先頭枠 = 先頭から min(3, N) 件
直近枠 = 先頭枠で採った分を除いた残りの、末尾から min(7, N - min(3, N)) 件
出力   = 先頭枠 ＋ 直近枠（重複なし。最大10件）
N先頭枠直近枠出力
00件0件節ごと出さない（見出しも出さない）
11件0件1件

33件0件3件
53件2件5件
103件7件10件

「意味のありそうなもの」（＝除外規則）

適用順は「除外してから採る」。 ユーザー指示の文言は「最初の3件のうち意味のありそうなもの」だが、 それを「先に3件採ってから除外する」と読むと、セッション冒頭が /compact や「よろしく」だった回に先頭枠が0件になり、 この機能の主目的（最初の依頼を保つ）が空振りする。枠を空振りさせない側に倒す。

#除外するもの初期値・判定方法
1相槌正規化後の完全一致（正規化＝前後の空白・句読点・感嘆符・記号を落とす）。辞書は ok OK はい／うん／お願い／お願いします／よろしく／続けて／続けてください／ありがとう／ありがとうございます／了解 等。文字数のしきい値は設けない（完全一致で判定する以上、長さ条件は何も足さない。「ダメ、やり直して」のような短くて重要な指示を落とさないためでもある）
2引数の無いスラッシュコマンド単体^/[A-Za-z][A-Za-z0-9:_-]*$（前後の空白除去後）。引数付きは残す
3CLIの展開結果<command-name> <local-command-stdout> <command-message> 等のタグで始まる行

辞書の中身と、それで実データが何割落ちるかはフェーズ2の問い5で確定させる。 過剰除去が1件でも見つかったら辞書から外す。

サイズの扱い（issue本文の論点5）

  • 理論最大は 3×(120+40) + 7×(80+30) = 1250文字 ≒ 約3,750バイト、見出し・記号・改行を足して約3,900バイト。
  • 節全体のバイト上限は 6000バイト（USER_UTTERANCE_MAX_BYTES）。理論最大の約1.5倍に置くのは、 上限を「実質発動しない安全網」に留めるため。理論最大に近い値（例: 4000）だと4バイト文字が混ざるだけで常時発動し、 「有界」という説明と実挙動が食い違う。
  • 超えた場合は、直近枠の古い側から1件ずつ落とす。先頭枠の3件は落とさない。 それでも収まらなければ節ごと出さない。
  • CONTEXT_SIZE_WARN_BYTES の判定からは、この節のバイト数を差し引く。 あのしきい値は「HANDOFF.md や計画が整理されないまま膨らみ続けている」ことを検知して人間に整理を促すためのもので、 整理のしようが無く有界な項目を分母へ入れると誤った警告が常時鳴る。 ただし警告文には「全体Nバイト（うち再注入分Mバイトを除外して判定）」と両方の数値を出す（差し引くこと自体は隠さない）。

単一transcript前提の限界（フェーズ2で詰める）

この上乗せで解けない方向 抽出元は transcript_path 1ファイルである。したがって1つのタスクが複数セッション（＝複数transcript）にまたがる場合、 「先頭3件」はそのtranscriptの冒頭でしかなく、要件定義の発言はどのtranscriptからも読まれない。 本リポジトリのようにissueが数日にわたる運用では、これが常態になりうる。この限界は「直近10件のみ」案を却下した理由と同じ形をしている。 フェーズ2の問い9・10で実測し、崩れる場合の扱いをフェーズ3の個別作業計画で決める。

抽出条件は issue 本文の4条件では足りない（実データでの補正）

issue #151 本文は抽出条件を「type=="user" かつ content が文字列／userType=="external"／isSidechain==false」としているが、 本ブランチの実 transcript を見ると、この4条件を満たす行に機械由来のものが混ざる。

  • type=="user" かつ .message.content が文字列の行のうち、origin.kind が "task-notification"（サブエージェントの完了通知など、ハーネスが差し込む機械生成のユーザーターン）のものがあった。 userType は "external"、isSidechain は false なので4条件では落とせない。
  • これは受け入れ条件「hookの注入テキスト・サブエージェント由来の行が混入しない」に直接効く。

したがって抽出条件へ .origin.kind == "human" を加える（origin を持たない行の扱いはフェーズ2の問い12で決める）。あわせて次の2点もフェーズ2で確認する。

  • .message.content が配列でも、text ブロックだけの人間発言がありうる（実データで1件）。文字列限定にすると取りこぼす可能性がある。
  • type=="last-prompt" という行がユーザーの生発言をそのまま保持しているが、gitBranch を持たないためブランチ絞りの母集団には使えない（代替として使えるかはフェーズ2の問い13）。
gitBranch 絞りは完全なフィルタではない issue #37 で、同一セッションが複数回・複数ブランチにわたって resume されると、transcript 上に 同じ行が異なる gitBranch ラベル付きで複数回出現することが実データで確認されている（DDR i0000-04）。 uuid による重複除去を入れる（同じ発言が2回枠を食うのを防ぐ）。

テストの移植性

  • .claude/ は dist-layers.json で core（配布元所有・そのまま配布）であり、 test_session_start.sh は他プロジェクトでも実行される。
  • 単体テストは合成フィクスチャのみで完結させる。 実行マシンのtranscriptに依存すると、配布先・他の開発者の環境でファイル不在により必ず落ちる。
  • 実 transcript での確認は検証節の手動確認として行い、結果を wip/reports/ へ記録する。

実データを扱うときの記録方針（秘密情報）

  • 実 transcript に現れるのはユーザーが打った生の文字列であり、貼り付けたトークン・パス・第三者の情報を含みうる。
  • レポート・worklog へ発言の本文を貼らない。 残すのは件数・文字数分布・バイト数といった統計値と、 自分が本セッションで打った発言に限った抜粋だけにする。

実装上の制約（規約からの持ち込み）

  • transcript は数MBになりうるため、内容を --argjson/--arg で jq へ渡さない。 ファイルパスを渡して jq -R -n ＋ inputs で jq 側に読ませる。
  • jq 呼び出しは1回に集約する（行ごとに jq を起動しない）。
  • 複数行の値をコマンド置換で受けるため、tr -d '\r' を挟む（Windowsネイティブjqは最終行以外の行末へCRを付ける）。
  • 実行環境が git bash（MSYS）である前提を落とさない。 「Windowsネイティブjqへプロセス置換のパスを渡せない」 「MSYS_NO_PATHCONV=1 を効かせたシェルではMSYS形式パスをjqが開けない」という実機で踏んだ罠があり、 jq へファイルパスを引数で渡す本設計はこの直撃コースにある。 候補の対策は「パス名を渡さず jq -R -n 'inputs' < "$path" の形で標準入力へ繋ぐ」。実際の表記はフェーズ2の問い7で確認する。
  • 抽出・整形の中核は副作用の無い純粋関数として切り出し、source して直接呼べるようにする。

#逸脱根拠と、崩れたときの戻し方
1全体作業計画を planツールで作らなかったリモート実行環境でハーネスが既に Plan モードを抜けており、再入は承認待ちでセッションを止める。ファイル名が 【 で始まらない＝全体作業計画、という判別規則には従っている
2flow-id 1-5（人間の合意）を待たずに先へ進めている衝突先: AGENTS.md「計画がユーザーに承認されるまでファイルの書き換え・コマンド実行を行ってはいけない」。根拠: ユーザー指示が「PR作って進めて。各フェーズでの計画時に一度敵対的レビュー、作業実施毎に一度ずつ敵対的レビューを自動で行い、指摘に対する修正を行いながら進めること」であり、レビューはPR上で受ける前提が示されている。戻し方: 不同意ならフェーズ2以降の成果物を破棄し本計画から作り直す（手戻りは wip/plans/ wip/reports/ に限られる）
3ブランチ名がリポジトリの命名規則に従っていないハーネスが designated branch を指定しているため、branchPrefixTemplate（feature-{issue}-{slug}）には従わない。結果として get_issue_number_from_branch がissue番号を抽出できず、SessionStart hook の注入も「issue: 特定できず」になる（本issueが扱う機能の動作確認に影響しうる点として記録）
