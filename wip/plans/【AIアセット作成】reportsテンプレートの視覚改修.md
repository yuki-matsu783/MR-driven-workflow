## 方針

調査結果の結論を転記した次の設計で実装する。

### 節の並び順（節名は全維持）

ヘッダ帯（結論件数チップ追加）→ 目次 → **重点レビュー依頼（新設・必須）** →
サマリ（結論の一覧）（色分け結論カードへ改修・必須）→ **確かめられなかったこと（前半へ移動・必須。
一覧は全項目を保持し、詳細は各章のcalloutへ）** → 実施条件（測った対象・環境）（任意）→
実施した内容と結果（必須。
章ID・性質チップ・未確認詳細callout）→ 設計への反映（必須）→ 想定と異なった点（任意）→
残課題（任意）→ フッタ。

### 新設: 重点レビュー依頼（`id="review-focus"`）

3段階の枠を色付きカードで用意し、各項目から該当章（`#f1` 等）へリンクする。

| 段階 | 意味 | 視覚（線色＋地色＋ラベル） |
|---|---|---|
| 特に見てほしい | 判断に困っている | `border: 2px solid var(--accent)`＋`background: var(--accent-soft)`・「◆特に見てほしい」 |
| 承認が欲しい | 方針は決めたので確認してほしい | `border: 1px solid var(--accent)`＋`background: var(--panel)`・「◇承認が欲しい」 |
| 細かいレビューは不要 | ほぼ確実 | `border: 1px solid var(--line)`＋`background: var(--panel)`・文字 `var(--muted)`・「・細かいレビューは不要」 |

（**色相（青/黄/赤）は結論の性質専用に予約し、レビューの重みには使わない**。重みは
アクセント系1色相の中の濃度・枠の太さ＋記号（◆◇・）で表す。こうすることで、流し読みで
「重点依頼の赤」を「問題の赤」と読み違える混線を避ける。第3段階は専用トークンを新設せず
既存の `--panel`／`--line`／`--muted` で組む——`--muted` は文字色にのみ使い、背景には使わない。）

### サマリ（結論の一覧）の改修

- 表を廃止し、**結論カードのリスト**にする。1件＝「性質チップ（◎良／△注意／✕問題）＋
  短い結論（1行）＋**根拠の性質**（実測／推測 等。現行の表の4列目の情報を落とさず引き継ぐ）＋
  該当章へのアンカーリンク」の4要素。
- 性質の色: 良＝青 `--good`（新設）／注意＝黄 `--warn`／問題＝赤 `--stop`。
- ヘッダ帯に件数チップ（例: ◎3 △2 ✕1）を置く。
- 記述量の目安をコメントで指示（結論は1行。詳細は章に書く）。

### 色トークン・チップ

- `:root` へ `--good: #1d4ed8; --good-soft: #e7edfd;`、ダーク側へ
  `--good: #8ab4f8; --good-soft: #17233a;` を追加。
- `.tag.ok/.tag.warn/.tag.stop`（既存・本体未使用）は削除し、結論性質チップ
  `.chip.good/.chip.warn/.chip.stop` へ置き換える（緑チップと青「良」チップの語彙併存を防ぐ）。
  置き換えの前後は次のとおり（現行144〜147行の4行を丸ごと削除し、`.chip` 系4行を追加する。
  形状の宣言は現行 `.tag` と同一）。

  ```css
  /* 削除（現行144〜147行） */
  .tag { display: inline-block; border-radius: 999px; padding: 1px 9px; font-size: 12px; font-weight: 600; }
  .tag.ok { background: var(--ok-soft); color: var(--ok); }
  .tag.warn { background: var(--warn-soft); color: var(--warn); }
  .tag.stop { background: var(--stop-soft); color: var(--stop); }

  /* 追加 */
  .chip { display: inline-block; border-radius: 999px; padding: 1px 9px; font-size: 12px; font-weight: 600; }
  .chip.good { background: var(--good-soft); color: var(--good); }
  .chip.warn { background: var(--warn-soft); color: var(--warn); }
  .chip.stop { background: var(--stop-soft); color: var(--stop); }
  ```
- `--ok`（緑）と `.box.ok` は「決めたこと・手順の成功」専用として存続。役割の違いを
  コメントに明記する（結論の性質には使わない）。

### 確かめられなかったこと（前半移動）

- サマリ直後に置き、**1行1件の一覧**（各行に関連章へのリンク）。節名・警告色（`--warn`）は維持。
- 詳細は各章内の専用callout `.box.warn.unverified-detail`（ラベル「確かめられなかったこと（詳細）」）
  で語る。一覧側を空にしない・詳細だけを前半に書かない、という分担をコメントで指示。

### 実施した内容と結果

- 各h3章に `id="f1"` `id="f2"` …の連番IDを振る（結論カード・未確認一覧・重点レビュー依頼の
  3箇所から参照される）。
- 章見出しの隣に性質チップを置き、サマリの色と対応させる。

### アンカーの位置ずれ対策・検査

- `section[id], h3[id] { scroll-margin-top: 16px; }` を追加。
- テンプレート冒頭コメントへ**リンク破断検査**を追記する（下記「検証」のcommコマンド。
  出力0行が合格）。
- `#` を `&#35;` と書くエスケープの適用範囲を限定して明記する:
  **対象はコメント中で具体的なIDを引用する見本アンカー（例: `href="&#35;f1"`）のみ**。
  検査コマンド自身の正規表現（`href="#[A-Za-z0-9_-]+"`）はエスケープしない——正規表現の
  `#` の直後は文字クラス `[` であり ID列にマッチしないため検査を汚染せず、エスケープすると
  逆にコマンドをコピーして実行できなくなる。

### テンプレートコメント（次の書き手への伝承）

冒頭コメントを更新する: (1) 節の並び順とその理由（未確認事項が前半にある理由＝結論の
確からしさを先に把握させる） (2) 色・記号の使い分け（性質3色＋緑boxの役割分担） (3) 重点
レビュー依頼の3段階の書き方 (4) リンク破断検査 (5) 既存の「フェーズごとの読み替え」を更新
（統括5-4: 重点レビュー依頼は「マージ判断で最後に見てほしい点」、未確認一覧は残存分のみ。
反映4-6: 設計への反映は「次のissueへ回したもの」——従来どおり） (6) プレースホルダ検査・
自己完結性・md/html併存の既存指示は維持。

## 検証

```bash
f=.claude/skills/issue-mr-flow/assets/reports.template.html

# 1. 自己完結性（いずれも0件が合格）
grep -nE "(src|href)=['\"]?(https?:)?//" "$f"
grep -nE "(url\(|@import[[:space:]]+)['\"]?(https?:)?//" "$f"

# 2. リンク破断（テンプレートの見本アンカー自身が整合していること。出力0行が合格）
comm -23 <(grep -oE 'href="#[A-Za-z0-9_-]+"' "$f" | sed 's/^href="#//;s/"$//' | sort -u) \
         <(grep -oE 'id="[A-Za-z0-9_-]+"'   "$f" | sed 's/^id="//;s/"$//'   | sort -u)

# 2b. 検査自体が壊れていないことの確認（存在しないIDへの参照を1件仕込んだ一時コピーで、
#     同じコマンドが「zzz-broken」1行を出力すること。異常が無ければ何も出ない検証の空振り対策）
tmp="$(mktemp)"
sed 's|</body>|<a href="#zzz-broken">x</a></body>|' "$f" > "$tmp"
comm -23 <(grep -oE 'href="#[A-Za-z0-9_-]+"' "$tmp" | sed 's/^href="#//;s/"$//' | sort -u) \
         <(grep -oE 'id="[A-Za-z0-9_-]+"'   "$tmp" | sed 's/^id="//;s/"$//'   | sort -u)
rm -f "$tmp"

# 3. プレースホルダ検査手順が維持されていること（テンプレート自身には残っているのが正。0でないこと）
grep -c '<!-- ここに書く' "$f"

# 4. 受け入れ条件の構造確認（それぞれ1件以上ヒットすること）
grep -c 'id="review-focus"' "$f"
grep -c -- '--good' "$f"
grep -c 'scroll-margin-top' "$f"

# 5. コメントの伝承内容が実在すること（左のコマンドが右の件数以上を返すこと）
grep -c '重点レビュー依頼' "$f"   # 2以上（本文の節と冒頭コメントの双方に現れる）
grep -c 'リンク破断' "$f"          # 1以上（冒頭コメントの検査手順）
grep -c '結論の性質' "$f"          # 1以上（色・記号の使い分けの説明）

# 6. 節順（h2の実測と期待値の機械比較。差分なしが合格）
diff <(grep -oE '<h2>[^<]*</h2>' "$f" | sed 's/<[^>]*>//g') - <<'EOF'
目次
重点レビュー依頼
サマリ（結論の一覧）
確かめられなかったこと
実施条件（測った対象・環境）
実施した内容と結果
設計への反映
想定と異なった点
残課題
EOF
```

- 空振りの排除: 検証4の3語（`id="review-focus"`・`--good`・`scroll-margin-top`）と検証5の3語
  （重点レビュー依頼・リンク破断・結論の性質）は、いずれも**現テンプレートでは0件**であることを
  実測済み（2026-08-23。改修後に規定件数以上へ変わることが変更の検出になる）。検証3は
  現テンプレートで18件（残っているのがテンプレートとして正。誤って全て埋めた場合に0となり
  検出できる）。検証2は「出力なし＝合格」の形のため、検証2bで**意図的な破断を検出できること**を
  併せて確かめる。
- 検証6が成り立つよう、**h2はプレーンテキストのまま保つ**（チップ・アンカーはh2の中に入れず、
  h3側と帯・カード側に置く）。
- 実ブラウザ確認は行えない環境のため、HTML構文の機械確認（タグ対応）と上記grepで代替し、
  その旨をレポートの「確かめられなかったこと」へ残す。
