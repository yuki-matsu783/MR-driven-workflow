# 全体作業計画 — compact後もユーザーの直近発言をSessionStart hookで再注入する（issue #151）

- issue: [#151](https://github.com/yuki-matsu783/MR-driven-workflow/issues/151)
- PR: [#197](https://github.com/yuki-matsu783/MR-driven-workflow/pull/197)
- ブランチ: `claude/user-recent-utterance-reinject-9ygbxd`

## この計画で何をするか

`.claude/hooks/session-start.sh` に、**ユーザーが自分の言葉で打った入力の抜粋**を
`additionalContext` へ足す項目を1つ追加する。抽出元は hook が stdin で受け取る JSON の
`transcript_path`（JSONL）である。

compact の要約は「何を残すか」を指定できないため、依頼・制約・除外条件が言い換えや圧縮で歪む・
落ちる。**生の文字列を少量だけ持ち込む**ことで、要約の精度に依存せず「何を頼まれたか」を保つ。
issue #57（DDR i0057-01）が入れた「compact後の現在地の再注入」の延長にあたる。

## 方針

### 出力位置と、出す／出さない経路

新しい節は **`build_context` の中**（`build_work_context` 経由）で組み立てる。`main` 側では
連結しない。これにより、ブランチ名（方針1のブランチ絞りに必要）を `build_context` の
ローカル変数からそのまま使え、既存のフォールバック方針にも自然に従う。

| `build_context` の経路 | 既存の挙動 | ユーザー発言節 |
|---|---|---|
| 正常（作業ブランチ上、CLI経路・MCP経路とも） | 全項目を注入 | **出す** |
| `exit 2`（`main` ブランチ上・ブランチ未チェックアウト） | 何も注入しない | **出さない**（既存方針を変えない） |
| 失敗（非ゼロ終了） | `(issue/MR情報の取得に失敗しました)` のみ | **出さない** |

3つ目について: 「取れた分だけ出す」という本機能の設計思想からは、失敗経路でも発言だけは
出したくなる。しかし `build_context` の失敗は `Provider.sh` の読み込み失敗など**環境が壊れて
いる**ことを示すため、そこで出力の形を増やすと原因の切り分けが難しくなる。**フェーズ2の
問い1が「`transcript_path` はどの経路でも取れる」ことを確認できた場合に限り、フェーズ3で
再検討する**（現時点では出さない側に倒す）。

### 採用する選定ロジック（ユーザー案＋3点の上乗せ）

ユーザー案「**先頭3件＋直近7件、最大合計10件**」を採用する。中盤を捨てるのは、
セッション中盤が「ok」「次へ」「それで」といった往復に偏り、同じ枠を使うなら
**先頭（＝要件定義）と直近（＝現在地）**に寄せたほうが1件あたりの情報量が高いためである。
そのうえで次の3点を上乗せする。

1. **「先頭」は、現在のブランチに絞ったうえでの先頭とする。**
   セッションはブランチをまたいで継続しうるため、`gitBranch` が現在のブランチと一致する行だけを
   母集団にする。こうすると「先頭3件」が**このtranscript上でこのタスクへ入った最初の依頼**を
   指すようになり、別タスクの発言が枠を食う問題（issue本文の論点2）も同時に解ける。
   **一致行が0件のときだけ絞りを外す**（ブランチ作成前の発言しか無いセッション・`gitBranch`
   欠落への fail-open）。
   **この上乗せが解くのは「1つのtranscriptが複数ブランチをまたぐ」方向だけである**
   （逆方向は下記「単一transcript前提の限界」）。

2. **切り出しは「頭M文字」ではなく「頭M文字＋末尾M′文字」にする。**
   issue本文の論点4が指摘するとおり、制約・除外条件は末尾に来やすい
   （「ただし〜はしない」「〜は触らないで」）。頭だけでは、この機能が守ろうとしているものを
   まさに落とす。
   **全長が M+M′ 以下なら全文をそのまま出す。** 超える場合のみ `頭M文字 … 末尾M′文字` に
   連結する（これを書かないと、短い発言で頭と末尾が重なり同じ部分を2回出す）。
   **切り出しは文字単位で行う**（バイト単位で切るとマルチバイト文字が壊れる）。ロケール非依存に
   文字数で切る手段はフェーズ2の問い8で確定させる。

3. **先頭3件は厚く、直近7件は薄く配分する。**
   先頭は要件定義なので長い文が来やすく、直近は現在地の確認なので短くて足りる。
   初期値は**先頭3件＝頭120字＋末尾40字／直近7件＝頭80字＋末尾30字**とし、
   フェーズ2で実データにあてて調整する。

#### 採り方（母集団が少ないときの重複を防ぐ）

**除外規則を先に適用して母集団を作り、そこから採る。** 母集団を時系列順に並べて N 件とすると、

```
先頭枠 = 先頭から min(3, N) 件
直近枠 = 先頭枠で採った分を除いた残りの、末尾から min(7, N - min(3, N)) 件
出力   = 先頭枠 ＋ 直近枠（重複なし。最大10件）
```

| N | 先頭枠 | 直近枠 | 出力 |
|---|---|---|---|
| 0 | 0件 | 0件 | **節ごと出さない**（見出しも出さない） |
| 1 | 1件 | 0件 | 1件 |
| 2 | 2件 | 0件 | 2件 |
| 3 | 3件 | 0件 | 3件 |
| 5 | 3件 | 2件 | 5件 |
| 10 | 3件 | 7件 | 10件 |
| 30 | 3件 | 7件 | 10件（中盤20件は落とす） |

この表の各行を**単体テストのケースとして必ず持つ**。

#### 「意味のありそうなもの」（＝除外規則）

**適用順は「除外してから採る」**（上式のとおり）。ユーザー指示の文言は「最初の3件**のうち**
意味のありそうなもの」だが、それを「先に3件採ってから除外する」と読むと、セッション冒頭が
`/compact` や「よろしく」だった回に先頭枠が0件になり、この機能の主目的（最初の依頼を保つ）が
空振りする。**枠を空振りさせない側に倒す。**

除外するのは次の3つ。

| # | 除外するもの | 初期値・判定方法 |
|---|---|---|
| 1 | 相槌 | **正規化後の完全一致**。正規化は「前後の空白・句読点・感嘆符・記号を落とす」まで。辞書は `ok` `OK` `はい` `うん` `お願い` `お願いします` `よろしく` `続けて` `続けてください` `ありがとう` `ありがとうございます` `了解` 等。**文字数のしきい値は設けない**（完全一致で判定する以上、長さ条件は何も足さない。「ダメ、やり直して」のような短くて重要な指示を落とさないためでもある） |
| 2 | 引数の無いスラッシュコマンド単体 | `^/[A-Za-z][A-Za-z0-9:_-]*$`（前後の空白除去後）。**引数付き（`/issue-mr-flow start 151`）は残す**（何に着手したかの情報を持つため） |
| 3 | CLIの展開結果 | `<command-name>` `<local-command-stdout>` `<command-message>` 等のタグで**始まる**行 |

**辞書の中身と、それで実データが何割落ちるかはフェーズ2の問い5で確定させる。** 初期値は
上表のとおりで、過剰除去（本物の指示が落ちる）が1件でも見つかったら辞書から外す。

### サイズの扱い（issue本文の論点5）

- 件数と1件あたりの文字数を固定するため、**この項目のバイト数は設計上有界**である。
  上記配分での理論最大は `3×(120+40) + 7×(80+30) = 1250文字`。UTF-8の日本語は1文字3バイトなので
  **約3,750バイト**、見出し・箇条書き記号・区切り・改行を足して**約3,900バイト**になる。
- 節全体のバイト上限は **6000バイト**（`USER_UTTERANCE_MAX_BYTES`、環境変数で上書き可）。
  理論最大の約1.5倍に置くのは、**上限を「実質発動しない安全網」に留めるため**である。
  理論最大に近い値（例: 4000）だと、4バイト文字（絵文字）が混ざるだけで上限が常時発動し、
  「件数と文字数を固定したので有界」という説明と実挙動（毎回件数が変わる）が食い違う。
- **超えた場合は、直近枠の古い側から1件ずつ落とす。先頭枠の3件は落とさない**（要件定義が
  最も歪んでほしくないもののため）。それでも収まらなければ節ごと出さない。
- **`CONTEXT_SIZE_WARN_BYTES` の判定からは、この節のバイト数を差し引く。** このしきい値は
  「HANDOFF.md や計画が整理されないまま膨らみ続けている」ことを検知して**人間に整理を促す**
  ためのものであり、整理のしようが無く、かつ有界な項目を分母へ入れると、誤った警告が常時鳴る。
  **ただし警告文には「全体Nバイト（うち再注入分Mバイトを除外して判定）」と両方の数値を出す**
  （差し引くこと自体は隠さない。隠すと警告メッセージが実際の注入量と食い違う）。

### 単一transcript前提の限界（フェーズ2で詰める）

本機能の抽出元は hook が受け取る `transcript_path` **1ファイル**である。したがって
**1つのタスクが複数セッション（＝複数transcript）にまたがる場合、「先頭3件」は
そのtranscriptの冒頭でしかなく、要件定義の発言はどのtranscriptからも読まれない。**
本リポジトリのようにissueが数日にわたる運用では、これが常態になりうる。

この限界は、本計画が「直近10件のみ」案を却下した理由（最初の依頼が落ちる）と同じ形をしている。
**フェーズ2の問い9・10でこの前提を実測し、崩れる場合の扱い（先頭枠を諦める／同一ブランチの
過去transcriptも対象にする／`HANDOFF.md` 側で代替する）をフェーズ3の個別作業計画で決める。**

### テストの移植性

`.claude/` は `dist-layers.json` で `core`（配布元所有・そのまま配布）であり、
`test_session_start.sh` は**他プロジェクトでも実行される**。既存のこのテストは `mktemp -d`
配下のフィクスチャだけで完結しており、外部の実ファイルに依存していない。

- **単体テストは合成フィクスチャのみで完結させる。** 実行マシンのtranscriptに依存する
  アサーションを入れると、配布先・他の開発者の環境でファイル不在により必ず落ちる。
- **実 transcript での確認は、単体テストではなく検証節の手動確認として行い**、結果を
  `wip/reports/` へ記録する。`.claude/rules/shell-script-style.md`「テスト」が求める
  「合成フィクスチャのテストだけで完了としない」は、単体テストへ実データ依存を入れよという
  意味ではない。

### 実データを扱うときの記録方針（秘密情報）

フェーズ2・検証では実 transcript を扱う。そこに現れるのは**ユーザーが打った生の文字列**で
あり、貼り付けたトークン・パス・第三者の情報を含みうる。

- **レポート・worklog へ発言の本文を貼らない。** 残すのは件数・文字数分布・バイト数といった
  統計値と、**自分が本セッションで打った発言に限った**抜粋だけにする。
- `.claude/rules/shell-script-style.md`「秘密情報の扱い」の「そもそも値を出さない形にできないかを
  先に考える」に従う。

### 実装上の制約（規約からの持ち込み）

- **transcript は数MBになりうるため、内容を `--argjson`/`--arg` でjqへ渡さない。**
  ファイルパスを渡して `jq -R -n` ＋ `inputs` でjq側に読ませる
  （`.claude/rules/shell-script-style.md`「JSON操作」）。
- **jq呼び出しは1回に集約する**（行ごとにjqを起動しない。同「外部プロセス起動のコスト」）。
- 複数行の値をコマンド置換で受けるため、**`tr -d '\r'` を挟む**（同「文字コード」。
  Windowsネイティブjqは最終行以外の行末へCRを付ける）。
- **実行環境が git bash（MSYS）である前提を落とさない。** 同ルールは
  「Windowsネイティブjqへプロセス置換のパスを渡せない」「`MSYS_NO_PATHCONV=1` を効かせた
  シェルではMSYS形式パスをjqが開けない」という実機で踏んだ罠を挙げており、
  **`jq` へファイルパスを引数で渡す本設計はこの直撃コースにある**。
  対策の候補は「パス名を渡さず `jq -R -n 'inputs' < "$path"` の形で標準入力へ繋ぐ」だが、
  実際にどの表記で `transcript_path` が渡るかはフェーズ2の問い7で確認する。
- 抽出・整形の中核は**副作用の無い純粋関数**として切り出し、`source` して直接呼べるようにする
  （`.claude/rules/shell-script-style.md`「テスト」）。

## フェーズ2〈調査〉

**実施する。** 数値（件数・文字数・除外規則）は実データにあてないと決められないため。

問いの形で列挙する。

1. hook が受け取る stdin JSON に `transcript_path` は含まれるか。含まれるとき、その実体は
   どこにあり、行数・バイト数はどの程度か。
   **含まれなかった場合の分岐**: `CLAUDE_PROJECT_DIR` 等から辿れるか調べ、辿れなければ
   本issueは実装不能として、その事実を `wip/reports/` へ記録したうえで**issueへ差し戻す**
   （代替経路を無理に作らない。`PreCompact` は DDR i0057-01 で却下済み）。
2. 実 transcript に対し、issue本文の抽出条件（`type=="user"`／content が文字列／
   `userType=="external"`／`isSidechain==false`）で何件取れるか。tool_result・hook注入・
   サブエージェント由来が混ざらないことを実データで確認できるか。
3. `gitBranch` はどの行にも入っているか。ブランチ絞りをかけたときの残存件数は。
4. 抽出できた発言の**文字数分布**はどうか。頭120字＋末尾40字で何割が全文に収まるか
   （＝「全長 ≤ M+M′」の分岐へ落ちる割合）。
5. 相槌・スラッシュコマンドは実際に何割を占めるか。上記の除外規則の初期値（辞書・正規表現）で
   過剰除去・除去漏れは起きないか。**過剰除去が1件でもあれば辞書から外す。**
6. 先頭3＋直近7を上記の配分で切り出したときの**実測バイト数**はいくつか。
   **既存の注入量はこの環境で測り直す**（後述の注記のとおり、1.2KB は issue #57 時点の値で
   その後の追加分を含まない）。合算値が `CONTEXT_SIZE_WARN_BYTES`（8000）に対してどうか。
7. **git bash 実機で `transcript_path` がどの表記（Windows形式／MSYS形式）で渡るか。**
   この調査はリモート実行環境（Linux）で行うため実機確認できない見込みで、その場合は
   **「未確認」と明記して残す**（確認できたことにしない）。jq へパス名を渡さない形
   （標準入力へ繋ぐ）で回避できるかを机上で確認する。
8. マルチバイト文字を**文字単位で**切り出す手段のうち、ロケール設定に依存しないものはどれか
   （`${var:0:N}` はロケール次第でバイト単位になる実績がある）。

## 補足: このタスクにおけるフロー定義からの逸脱

**`wip/plans/` はタスク単位で削除されるため、この節の内容は flow-id 4-6（設計反映）で
DDR `i0151-01` へ書き戻す。** `HANDOFF.md` も flow-id 5-5 でリセットされるため、逸脱の記録を
そちらだけに置かない。

### 1. 全体作業計画を planツールで作らなかった

`references/planning.md` は全体作業計画を **planツール（Planモード）** で作ることを求めるが、
本セッションはリモート実行環境（Claude Code on the web）であり、ハーネスが既に Plan モードを
抜けた状態で開始している。Planモードへの再入はユーザーの承認待ちでセッションを止めるため、
本ファイルは Write で直接作成した（ファイル名が `【` で始まらない＝全体作業計画である、という
判別規則には従っている）。

### 2. flow-id 1-5（人間の合意）を待たずに先へ進めている

- **何と衝突するか**: `AGENTS.md` の「計画がユーザーに承認（Approve）されるまで、ファイルの
  書き換えやコマンドの実行を行ってはいけない」。
- **根拠**: ユーザーからの指示が「PR作って進めて。各フェーズでの計画時に一度敵対的レビュー、
  作業実施毎に一度ずつ敵対的レビューを自動で行い、指摘に対する修正を行いながら進めること」で
  あり、**レビューはPR上で受ける前提**が示されている。加えて本セッションは人間のレビュー往復を
  待てない環境である。
- **崩れたときの戻し方**: ユーザーが本計画へ不同意を示した場合、フェーズ2以降の成果物を破棄し、
  本計画から作り直す（実装コードへ着手するのはフェーズ3以降なので、この時点までの手戻りは
  `wip/plans/` `wip/reports/` に限られる）。
- **合意状態の記述は、本計画md・同名HTML・`HANDOFF.md` の3箇所で揃える。**

### 3. ブランチ名がリポジトリの命名規則に従っていない

ハーネスが designated branch として `claude/user-recent-utterance-reinject-9ygbxd` を指定して
いるため、`.mrworkflow.json` の `branchPrefixTemplate`（`feature-{issue}-{slug}`）には従って
いない。ハーネス側の指示を優先する。**この結果、`get_issue_number_from_branch` がissue番号を
抽出できず、SessionStart hook の注入も「issue: 特定できず」になる**（本issueが扱う機能の
動作確認に影響しうる点として記録する）。

### 4. フェーズ1の敵対的レビューは回数カウンタの対象外

`adversarial-review-count.sh` は phase 2/3/4 のみを受け付ける。本計画（flow-id 1-4）に対する
敵対的レビューはフェーズ1のため、カウンタへ記録されない。**実施は1回のみとし、その事実を
本節へ記録することで代替する。**
