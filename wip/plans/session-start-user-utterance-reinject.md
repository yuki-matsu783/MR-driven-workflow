# 全体作業計画 — compact後もユーザーの直近発言をSessionStart hookで再注入する（issue #151）

- issue: [#151](https://github.com/yuki-matsu783/MR-driven-workflow/issues/151)
- PR: [#197](https://github.com/yuki-matsu783/MR-driven-workflow/pull/197)
- ブランチ: `claude/user-recent-utterance-reinject-9ygbxd`

## この計画で何をするか

`.claude/hooks/session-start.sh` に、**ユーザーが自分の言葉で打った入力の抜粋**を
`additionalContext` へ足す項目を1つ追加する。抽出元は hook が stdin で受け取る JSON の
`transcript_path`（JSONL）である。

compact の要約は「何を残すか」を指定できないため、依頼・制約・除外条件が言い換えや圧縮で歪む・
落ちる。**生の文字列を少量だけ持ち込む**ことで、要約の精度に依存せず「何を頼まれたか」を保つ。
issue #57（DDR i0057-01）が入れた「compact後の現在地の再注入」の延長にあたる。

## 前提（合意状況）

- issue #151 本文が、実 transcript に対する事前確認（人間の入力は `type=="user"` かつ
  `.message.content` が文字列の行／hook の注入は `type:"attachment"` で混ざらない／transcript は
  追記専用）を済ませている。本計画はそれを出発点とし、**数値の妥当性（何件・何文字）だけを
  フェーズ2で実データにあてて決める**。
- 起票時の初期案は「頭100文字 × 最大20件」だったが、**ユーザーから
  「最初の3件のうち意味のありそうなもの＋直近7件のうち意味のありそうなもの、最大合計10件」
  という方針変更の指示があった**（本セッション）。本計画はこれを採用したうえで、下記
  「方針」に3点の上乗せを提案する。

## 方針

### 採用する選定ロジック（ユーザー案＋3点の上乗せ）

ユーザー案「**先頭3件＋直近7件、最大合計10件**」を採用する。中盤を捨てるのは、
セッション中盤が「ok」「次へ」「それで」といった往復に偏り、同じ枠を使うなら
**先頭（＝要件定義）と直近（＝現在地）**に寄せたほうが1件あたりの情報量が高いためである。
そのうえで次の3点を上乗せする。

1. **「先頭」は、現在のブランチに絞ったうえでの先頭とする。**
   セッションはブランチをまたいで継続しうるため、`gitBranch` が現在のブランチと一致する行だけを
   母集団にする。こうすると「先頭3件」が**このタスクでの最初の依頼**を指すようになり、
   別タスクの発言が枠を食う問題（issue本文の論点2）も同時に解ける。
   **一致行が0件のときだけ絞りを外す**（ブランチ作成前の発言しか無いセッション・`gitBranch`
   欠落への fail-open）。

2. **切り出しは「頭M文字」ではなく「頭M文字＋末尾M′文字」にする。**
   issue本文の論点4が指摘するとおり、制約・除外条件は末尾に来やすい
   （「ただし〜はしない」「〜は触らないで」）。頭だけでは、この機能が守ろうとしているものを
   まさに落とす。`頭 … 末尾` の形で連結する。

3. **先頭3件は厚く、直近7件は薄く配分する。**
   先頭は要件定義なので長い文が来やすく、直近は現在地の確認なので短くて足りる。
   初期値は**先頭3件＝頭120字＋末尾40字／直近7件＝頭80字＋末尾30字**とし、
   フェーズ2で実データにあてて調整する。

「意味のありそうなもの」（issue本文の論点3）は、次の**除外規則**として実装する。

- 文字数がしきい値未満で、かつ既知の相槌パターン（`ok` `はい` `お願い` `続けて` `ありがとう` 等）に
  一致するもの。**短いだけでは落とさない**（「ダメ、やり直して」のような短くて重要な指示があるため）。
- 引数の無いスラッシュコマンド単体（`/compact` `/commit` 等）。**引数付き
  （`/issue-mr-flow start 151`）は残す**（何に着手したかの情報を持つため）。
- `<command-name>` `<local-command-stdout>` 等、CLIの展開結果で始まる行。

### サイズの扱い（issue本文の論点5）

- 件数と1件あたりの文字数を固定するため、**この項目のバイト数は設計上有界**である。
  さらに節全体のバイト上限（初期値4000バイト）を置き、超えたら**直近側の古いものから落とす**。
- **`CONTEXT_SIZE_WARN_BYTES` の対象には含めない。** このしきい値は「HANDOFF.md や計画が
  整理されないまま膨らみ続けている」ことを検知して**人間に整理を促す**ためのものであり、
  整理のしようが無く、かつ有界な項目を分母へ入れると、誤った警告が常時鳴るようになる。
  実装上は `main` で `append_size_warning` を適用した**後**にこの節を連結する。

### 実装上の制約（規約からの持ち込み）

- **transcript は数MBになりうるため、内容を `--argjson`/`--arg` でjqへ渡さない。**
  ファイルパスを渡して `jq -R -n` ＋ `inputs` でjq側に読ませる
  （`.claude/rules/shell-script-style.md`「JSON操作」）。
- **jq呼び出しは1回に集約する**（行ごとにjqを起動しない。同「外部プロセス起動のコスト」）。
- 複数行の値をコマンド置換で受けるため、**`tr -d '\r'` を挟む**（同「文字コード」）。
- 抽出・整形の中核は**副作用の無い純粋関数**として切り出し、`source` して直接呼べるようにする
  （`.claude/rules/shell-script-style.md`「テスト」）。

## フェーズ2〈調査〉

**実施する。** 数値（件数・文字数・除外規則）は実データにあてないと決められないため。

問いの形で列挙する。

1. hook が受け取る stdin JSON に `transcript_path` は含まれるか。含まれるとき、その実体は
   どこにあり、行数・バイト数はどの程度か。
2. 実 transcript に対し、issue本文の抽出条件（`type=="user"`／content が文字列／
   `userType=="external"`／`isSidechain==false`）で何件取れるか。tool_result・hook注入・
   サブエージェント由来が混ざらないことを実データで確認できるか。
3. `gitBranch` はどの行にも入っているか。ブランチ絞りをかけたときの残存件数は。
4. 抽出できた発言の**文字数分布**はどうか。頭120字＋末尾40字で何割が全文に収まるか。
5. 相槌・スラッシュコマンドは実際に何割を占めるか。除外規則の初期値で過剰除去・除去漏れは
   起きないか。
6. 先頭3＋直近7を上記の配分で切り出したときの**実測バイト数**はいくつか。4000バイトの
   上限に収まるか。既存の注入量（実測1.2KB）と合算しても運用上問題ないか。
7. `jq -R -n` ＋ `inputs` 方式で、実 transcript のサイズでも所要時間が許容範囲か。

**何が分かれば次へ進めるか**: 上記1〜6が数値で埋まり、件数・文字数・除外規則の初期値が
確定すること。

## 比較検討した案

| 案 | 採否 | 理由 |
|---|---|---|
| 直近20件を均等に頭100文字（issue本文の初期案） | 却下 | 中盤の往復（「ok」「次」）が枠を食い、1件あたりの情報量が低い。ユーザー案のほうが密度が高い |
| 直近10件のみ | 却下 | 長いセッションでは**最初の依頼**（最も歪んでほしくないもの）が落ちる |
| 全発言から文字数の多い順に上位N件 | 却下 | 貼り付けたログ・エラー出力が上位を占め、依頼が押し出される |
| 頭のみM文字で切る | 却下 | 末尾に書かれがちな制約・除外条件を落とす（issue本文の論点4） |
| ブランチ絞りをかけない | 却下 | セッションがブランチをまたぐと、別タスクの発言が「先頭3件」を占める |
| ブランチ絞りを常に強制する | 却下 | 一致0件のときに何も出せなくなる。0件時のみ絞りを外すフォールバックを採る |
| この項目も `CONTEXT_SIZE_WARN_BYTES` の分母へ入れる | 却下 | 有界かつ整理不能な項目のため、「整理せよ」という誤った警告が常時鳴る |
| しきい値を引き上げる（8000→12000等） | 却下 | 本来検知したい「HANDOFF.md の肥大化」の感度を下げてしまう |

## 補足: 全体作業計画の作り方についての逸脱

`references/planning.md` は全体作業計画を **planツール（Planモード）** で作ることを求めるが、
本セッションはリモート実行環境（Claude Code on the web）であり、ハーネスが既に Plan モードを
抜けた状態で開始している。Planモードへの再入はユーザーの承認待ちでセッションを止めるため、
本ファイルは Write で直接作成した（ファイル名は `【` で始まらない＝全体作業計画である、という
判別規則には従っている）。
