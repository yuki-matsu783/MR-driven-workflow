問1. テンプレートファイルと describe 節の二重管理をどう解消するか

現状、旧3節構成（Closes #N / ## Plan / ## 実装状況）を具体的に列挙している箇所は5つある。テンプレート側のコメントは「SKILL.md（現 review-loop.md）が正」と書いているが、正を指すだけの箇所と、構成そのものを持つ箇所が混在している。

#箇所現在の役割
1.github/pull_request_template.md雛形の実体（GitHub）
2.gitlab/merge_request_templates/Default.md雛形の実体（GitLab）
3references/review-loop.md の describe 節雛形の実体。テンプレート側が「正」と名指ししている
4.claude/docs/spec/distribution-assets.md「PR/MRテンプレート」節見出し構成を仕様として列挙し「見出しを増やさない」と規定
5index.md（Repository Map）の該当行見出しを括弧書きで列挙

.gemini/ 配下の同名ファイルは数えない（.claude/ からの変換生成物であり、sync-gemini-assets.sh が再生成する）。.claude/rules/directory-structure.md はテンプレートの存在に触れるだけで見出しを列挙していないため、10節化の影響を受けない（この判定も調査結果へ書き残す）。

フローどおりに作られたPR/MRは、テンプレートを一度も経由しない Draft PR/MRの初期本文は Github.sh / Gitlab.sh（およびMCP経路では references/mcp-fallback.md の対応表）にハードコードされており、テンプレートが効くのは人間がWeb UIでPRを作る場合だけである。これは案の評価軸（案Cの副作用の重さ）に直結し、「10節構成をこの初期本文にも反映するのか、describe まで暫定のままでよいのか」という決めごとを生む。

調べること:

  • 案A（describe がテンプレートファイルを読み込む）が成立するか。
    • (a) MCP経路でも動くか。GitHub/GitLabのどちらのファイルを読むかの判定が必要になる。get_provider で判定できるか
    • (b) 配布先で、テンプレート2本が .claude/dist-layers.json のどの層に属するか
    • (c) 配布先がテンプレートを改変していた場合に何が起きるか
    • (d) テンプレートのHTMLコメントを、生成するdescriptionへそのまま持ち込んでよいか
  • 案B（テンプレートを正とし、describe 節は見出し名だけを列挙して雛形を持たない）
  • 案C（describe 節を正とし、テンプレート側から重複を削って参照だけにする）。この場合、人間が手で作るPRで見出しが得られなくなる副作用の大きさを見積もる
  • どの案を採っても、上表の4・5（distribution-assets.md / index.md）は「正を指すだけ」へ書き換えるのか、列挙を残すのかを1件ずつ決める。
  • Draft PR/MRの初期本文を、10節構成へ合わせるかどうかを決める。 合わせない場合は「合わせない理由」を書く（describe が最初に走った時点で全文置換されるため、実害が無いと判断できるかどうか）。
  • 既存テスト .claude/scripts/test/test_install_to_project.sh が、採る案の下でも成立するかを確認する。 同テストは review-loop.md の describe 節から ^(Closes|## ) の行を awk で抜き出し、テンプレート2本と3者一致を表明している。describe 節が雛形を持たなくなる案（案B）を採ると、この抽出が空振りする。抽出元をどこにするかまで含めて案の一部として決める。
判定基準 「見出し構成を1箇所直せば、テンプレート・describe の両方が追随するか」と「人間が手でPRを作るときにも見出しが得られるか」を両立できるか。

issue #111 は PR #144 でマージ済みで、flow-id 5-4 が稼働している。廃止ではなく棲み分けを定義する。
