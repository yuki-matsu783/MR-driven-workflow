# 【調査】テンプレート参照箇所と視覚設計の判断材料（issue #186 / フェーズ2）

## 前提（合意状況）

- 上位の計画: `plans/vivid-report-canvas.md`（flow-id 1-5 で合意）。
  ただし本セッションは非対話（Claude Code on the web）のため、**計画内容そのものへの人間の
  レビューは経ておらず、進行の包括指示（「PR作って進めて」「敵対的レビューを自動で行い
  修正しながら進めること」）を承認とみなしている**（HANDOFF.md と同じ記録）。
- 目的: フェーズ3で作る新テンプレートの「節順・色トークン・コメント方針・アンカー設計」が
  一意に決まる状態にする。

## この計画で何をするか

次の4つの問いに答える。

### Q1. テンプレートの節構成・運用に言及するドキュメントはどこにあるか

- 対象は下記「変更対象（調査で読む範囲）」のとおり。
- 方法: `doc-search`（frontmatterインデックス）で `reports.template` `HTMLビュー` を検索し、
  本文中の固有文字列は `grep` で補完する（検索語は下記「検証」のコマンドに固定する。
  インデックス検索が主・全文検索が従のルールに従い、両方の結果を突き合わせる）。
- 判定: 列挙した各箇所を「節構成が変わると矛盾するか（＝フェーズ3で直す対象か）」で仕分けし、
  **全件を「直す／直さない（理由付き）」の表としてreports側に残す**。
- `.gemini/` 配下は**列挙はするが直す対象ではない**（`.claude/` からの変換生成物であり
  直接編集禁止。flow-id 5-3 の `sync-gemini-assets.sh` 再生成で追随する側。
  `.claude/rules/directory-structure.md`）。この扱いを調査結果にも明記し、フェーズ3の
  実装者が `.gemini/` を手編集しないようにする。

### Q2. 現テンプレートの構造のうち、何を残し何を変えるか

- 対象: `reports.template.html` の必須／任意節・スタイルトークン・「フェーズごとの読み替え」
  コメント・プレースホルダ検査手順。
- 判定: issue #186 の期待する動作（色分けサマリ・重点レビュー依頼・未確認事項の前半移動）と
  突き合わせ、節ごとに「維持／移動／改修／新設」を決める。
- **受け入れ条件のうち現テンプレートで既に部分的に満たされている項目**（例: サマリ節の
  「各行から本文の該当節へリンクする」コメント指示）を洗い出し、新設指示と二重化しない形を
  決める。
- **章IDの命名規則とアンカー設計**: 既存の節ID（`#summary` 等）との整合、結論→章リンクに使う
  章ID・見出しIDの命名規則、アンカー移動時の位置ずれ対策（`scroll-margin-top` 等）の要否。

### Q3. 色の設計をどうするか

- 論点1: issueは「良かった＝青系統」を指定するが、既存テンプレートは `--ok`（緑系）を
  「決めたこと・結論」に使っている。青は現在アクセント色（リンク・見出し）でもある。
  衝突しない色トークン設計を決める。
- 論点2: ダークモードでの可読性（既存の `prefers-color-scheme` 対応を維持したまま色を増やす）。
- 論点3: 色だけに依存しない表現（記号・ラベル併用）。色覚多様性への配慮として、
  青／黄／赤を色のみで区別させない。

### Q4. 「フェーズごとの読み替え」を新構成へどう引き継ぐか

- 「確かめられなかったこと」を前半へ移した場合の、統括レポート（5-4）での扱い。
- 「設計への反映」節の位置と、反映結果レポート（4-6）での読み替え。
- 新設する「重点レビュー依頼」は全フェーズ共通で意味が通るか（通らないフェーズがあるなら
  読み替えコメントを用意する）。

## 変更対象（調査で読む範囲）

このフェーズでは**ファイルを変更しない**（読むだけ）。読む範囲は次のとおり。

| 範囲 | 読み方 |
|---|---|
| `.claude/` 配下のrules・skills（references・assets含む）・docs（spec/ddr/usecase）・hooks | 下記「検証」の検索コマンドでヒットした箇所を精読 |
| 各 `REVIEW-POINTS.md`（ルート・`.claude/`・`plans/`・`reports/`） | 全文（テンプレート・HTMLへの観点を持つため） |
| ルート直下のガイド類（`index.md` `AGENTS.md` 等） | 検索コマンドでヒットした場合のみ |
| `.gemini/` 配下 | 検索コマンドで**件数のみ**列挙（生成物のため精読しない） |
| `reports.template.html` 本体 | 全文（Q2の対象） |

## 方針

1. まず検索（下記コマンド）で参照元を機械的に列挙し、目視の精読はヒット箇所に限定する
   （探索の打ち切り条件: 検索コマンド2系統の全ヒットを仕分けし終えた時点）。
2. 各ヒットを「現在の状態の記述」か「point-in-time記録（DDR本文・specの過去changelog）」かで
   仕分ける。後者はフェーズ3で**書き換えない**（`.claude/rules/docs-workflow.md`）。
3. Q2〜Q4は、Q1で確定した「直す対象」との整合が取れる形で結論を出す。

## やらないこと（スコープ外）

- テンプレートの実改修（フェーズ3へ送る）。
- `plans.template.html` / `canvas-report` の調査（全体作業計画のスコープ外）。
- `.gemini/` 配下の精読・修正（生成物。flow-id 5-3 の再生成で追随）。

## 検証（この調査が完了したと言える条件）

次のコマンドを実行し、**全ヒットが調査結果の仕分け表（直す／直さない＋理由）に載っている**こと。

```bash
# 参照元の列挙（パス言及）。.gemini/ は件数のみ扱う
grep -rln --include='*.md' --include='*.sh' --include='*.html' -e 'reports\.template\.html' \
  .claude/ .gemini/ *.md

# 節名への言及（構成が変わると矛盾しうる箇所）
grep -rn --include='*.md' --include='*.sh' \
  -e 'サマリ（結論の一覧）' -e '確かめられなかったこと' -e '設計への反映' \
  -e '想定と異なった点' -e '実施条件（測った対象・環境）' \
  .claude/ *.md reports/REVIEW-POINTS.md

# frontmatterインデックス側（grepの取りこぼし確認）
bash .claude/scripts/src/search-frontmatter.sh --text 'reports.template' --format count
bash .claude/scripts/src/search-frontmatter.sh --text 'HTMLビュー' --format count
```

- **空振りの排除**: 上記の節名検索は、調査開始時点で `planning.md` `issue-mr-workflow.md`
  `reports/REVIEW-POINTS.md` の3ファイルに必ずヒットすることを実測済み（2026-08-23。
  ヒット0件で「矛盾なし」と結論する形にはならない）。仕分け表の行数が
  検索ヒット件数と一致することを、レポート内で件数付きで示す。
- Q2〜Q4の各判定が、フェーズ3の個別作業計画へそのまま書き写せる粒度で結論になっていること
  （節順・色トークン・コメント方針・アンカー設計の4点が確定している）。
- 結果は `reports/<YYYYMMDD>_vivid-report-canvas_調査結果.md`（＋同名.html）へ記録する
  （日付は実施日。ファイル名は既存慣行のハイフン無し `YYYYMMDD` 形式。
  この計画ファイルには結果を書かない）。
