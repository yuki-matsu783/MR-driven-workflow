## 実データを扱ううえでの制約

**記録方針の正は全体作業計画の該当節である。** 本計画で緩めない。原則は次のとおり。

- **`wip/reports/` ・worklog へ発言の本文を貼らない。** 残してよいのは件数・文字数分布・
  バイト数といった**統計値**と、**自分（AI）が本セッションで打った発言に限った**抜粋だけ。
  「必要なら引用してよい」という読み替えをしない（本文が要ると感じたら、**値と件数で表現できる
  形へ問いを言い換える**）。
- **問い5（過剰除去の確認）が最も踏みやすい。** 「除外された発言を全件目視する」のは
  **手元での確認**であり、レポートへ残すのは『**どの辞書語が何件落としたか**』という
  **語と件数だけ**にする。過剰除去が出た場合も、記録するのは「その語」と「件数」であって
  発言本文ではない。
- 秘密情報（トークン等）が本文に含まれていた場合、**値そのものを置換する**
  （`.claude/rules/shell-script-style.md`「秘密情報の扱い」）。接頭辞決め打ちのマスクに頼らない。
- 一時ファイル（退避した生JSON・抽出結果）は**scratchpad へ置き、リポジトリへコミットしない**。

```bash
REPORT='wip/reports/20260824_session-start-user-utterance-reinject_transcript実測の調査結果.md'

# 1. 成果物が md / html の両方そろっているか
test -f "$REPORT" && test -f "${REPORT%.md}.html" && echo 'OK: 成果物2件'

# 2. 14項目の見出しが「過不足なく」あるか。
#    見出しの個数を数えるだけでは、中身が空でも通ってしまう。実際に現れた番号を
#    列挙して期待値と突き合わせ、差分が無いことを見る。
diff <(grep -oE '^### 問い[0-9]+[ab]?' "$REPORT" | sed 's/^### 問い//' | sort -u) \
     <(printf '%s\n' 1 10a 10b 11 12 13 2 3 4 5 6 7 8 9 | sort -u) \
  && echo 'OK: 問いの番号が過不足なく一致'

# 3. 各見出しの直下に結論の実体があるか（空の見出しを弾く）。
#    「見出しでない非空行が1行以上あるか」だけを見る。結論の"形"を正規表現で判定しない
#    （後続の見出し行自身が数字を含むため、形での判定は空の見出しを取りこぼす。実測済み）。
#    0 が返れば合格。1件以上なら、その見出し名が標準エラーへ出る。
awk '
  /^###[ 　]/ { if (h != "" && n == 0) print h; h=$0; n=0; next }
  /^#/        { if (h != "" && n == 0) print h; h=""; n=0; next }
  NF          { if (h != "") n++ }
  END         { if (h != "" && n == 0) print h }
' "$REPORT" | tee /dev/stderr | wc -l

# 4. 「やらないこと」を破っていないか。
#    origin/main は fetch してから、分岐点を実行時に求める（SHAは書き写さない）。
#    対象は1ファイルではなくディレクトリ単位で見る（テスト・他のhookへの混入も拾うため）。
git fetch origin main
base="$(git merge-base origin/main HEAD)"
git diff --name-only "$base" -- .claude/
```

**合格条件**

| # | 何を確かめるか | 合格 |
|---|---|---|
| 1 | 成果物が md / html の2件そろっている | `OK: 成果物2件` が出る |
| 2 | 14項目が**過不足なく**ある | `diff` が差分を出さず `OK: 問いの番号が過不足なく一致` が出る（**多い場合も少ない場合も落ちる**） |
| 3 | 各問いに**結論の実体**がある | 標準出力が `0`（結論の無い見出しが0件。1件でもあれば、その見出し名が標準エラーへ出る） |
| 4 | 実装へ手を入れていない | `git diff` の出力が**空**（`.claude/` 配下に1件も変更が無い） |

**検証2・3は、合成フィクスチャで「本当に落ちること」を確認済みである**（`REVIEW-POINTS.md`
「異常があるときに本当に検出できるか」）。flow-id 2-1 の時点で次を実測した。

| フィクスチャ | 検証2 | 検証3 |
|---|---|---|
| 14項目そろい・各見出しに結論あり | OK | 0件 |
| 見出しを1つ落とす | **NG（検出）** | 0件 |
| 空の見出しを1つ足す | NG（番号が増えたため） | **1件（検出）** |

**この確認の過程で、検証3の初版が空振りだった。** 「見出しの直下の非空行が『数値／断定／未確認』の
形をしているか」を正規表現で見る書き方にしていたところ、**後続の見出し行自身が数字を含む**ため
空の見出しを取りこぼした（0件と出た）。形の判定をやめ、「見出しでない非空行が1行以上あるか」
だけを見る形へ直してある。

## 停止条件・差し戻し条件

| 条件 | 対応 |
|---|---|
| **問い1が否**（`transcript_path` が取れず、`CLAUDE_PROJECT_DIR` からも辿れない） | 以降の問いを解かず**即座に停止**する。記録するのは「**この実行環境（Claude Code on the web / Linux）では取得できなかった**」という**事実**であって、「実装不能」ではない（下記）。**代替経路を無理に作らない**（`PreCompact` は DDR `i0057-01` で却下済み）。そのうえで**人間の判断を仰ぐ**ため issue #151 へ差し戻す |
| **問い11がしきい値超過**（追加コスト 200ms 超） | フェーズ3へ進む前に実装方式（jqの呼び方・走査量）を見直す案を出す。しきい値を後から緩めない |
| **問い5で過剰除去が発生** | 該当語を辞書から外して測り直す。「まれだから許容」としない |
| **調査中に規模が本issueに収まらないと判明** | `.claude/skills/issue-mr-flow/references/planning.md`「issueが大きすぎる場合の分割提案」に従い、未着手範囲の別issue化を提案する |

**「この環境で取れなかった」を「実装不能」と書かない。** `transcript_path` の有無・表記は
ハーネスの実装に依存し、本調査は問い7で認めるとおり**リモート実行環境（Linux）でしか行えない**。
実運用環境（Windows / git bash 上の Claude Code）で取れるかどうかは、ここでは分からない。
`.claude/rules/shell-script-style.md`「テスト」が言う『**測れないから現状維持**』と
『**測ったうえで現状維持**』の区別と同じで、両者を混ぜると**実機なら動く機能を「実装不能」として
葬る**ことになる。

差し戻すときのレポートには、次の3つを必ず書く。

1. **確認できた環境**と、そこで取れなかったという事実
2. **確認できていない環境**（Windows / git bash 上の Claude Code、および Gemini CLI）
3. 結論は「実装不能」ではなく「**実機での確認が済むまで判断保留（未確認）**」であること
