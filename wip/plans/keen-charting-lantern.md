# 全体作業計画 — 1行コミットログを後から辿れる形にする（issue #185）

## この計画で何をするか

squash merge後に `main` へ残る1行のコミットログだけで「何を・どう変えたか」を追えるように、
**コミットメッセージの内容についての規約**を `commit` スキルへ追記する。あわせて、
「1行のみを維持するか本文を許容するか」の方針をDDRとして記録し、`create-commit.md` の
記述と矛盾しない状態にする。

- 変えるのは**規約（AIアセット）**であり、`create-commit.sh` の実装は原則触らない。
  実装変更が要ると判明した場合は、フェーズ3の作業計画で改めて範囲を確定する。
- issue本文の「実例」に挙がった各行が新しい規約でどう書かれるかを、書き直し例として示す。

## 背景（issueの要約）

- `commit` スキルはメッセージを `<prefix>: <日本語説明>` の**1行のみ**と定め、本文・フッターを
  付けない（`.claude/skills/commit/SKILL.md`「Step 4」、`.claude/docs/spec/create-commit.md`）。
- `wip/plans/` `wip/worklogs/` `wip/reports/` は flow-id 5-5 で削除され、squash merge により
  `main` に残らない。main上で作業の内訳を辿れるのは `.claude/docs/spec/` `.claude/docs/ddr/` と
  コミットログだけであり、**1行の情報量がそのまま履歴の情報量になる**。
- 現状の1行は「どのファイル・どのドキュメントを触ったか」に寄りやすく、**どう変えたか**が
  残らない。

## 変更対象（領域の粒度）

| 領域 | 想定する変更 |
|---|---|
| `.claude/skills/commit/SKILL.md` | コミットメッセージの内容規約（満たすべき要素・良い例・悪い例・成果物の変更を伴わないコミットの書き方）を追記 |
| `.claude/docs/ddr/` | 「1行のみ／本文許容」の方針決定をDDRとして新設（`i0185-01`）。`generate-ddr-list.sh` で一覧を再生成 |
| `.claude/docs/spec/create-commit.md` | メッセージ形式の記述を、決めた方針と矛盾しない状態にする |
| `.claude/rules/git-workflow.md`（見込み） | 「コミット運用」節から新しい規約への入口が要るかをフェーズ4で判定 |
| `.gemini/` | flow-id 5-3 の変換同期で追随（手では編集しない） |

ファイル単位・行単位の確定は、フェーズ2の調査結果を受けてフェーズ3の個別作業計画で行う。

## フェーズ2〈調査〉

**実施する。** 規約を書く前に、次を明らかにする。

1. 現行の規約が「1行のみ」をどこで・何回述べているか（`commit` スキル、`create-commit.md`、
   `git-workflow.md`、その他のルール・spec）。書き換え漏れが残る箇所の洗い出し。
2. squash merge後に `main` へ残る実際のコミットログ（直近N件）が、どのような欠落パターンを
   持つか。issue本文の4類型（対象しか分からない／どう直したか分からない／事務的作業記録／
   mainに残らない対象）以外の類型があるか。
3. `create-commit.sh` が複数行メッセージを受け付けられるか（`--message` の扱い、`git commit -m`
   への渡し方）。本文を許容する方針を採った場合に実装変更が要るかどうかの判定材料。
4. squash merge時にGitHubが本文をどう畳むか（PRのコミット一覧が本文ごとsquashコミット本文へ
   入る挙動）。本文を許容した場合に `main` の1行目に何が残るか。
5. 他のAIアセット（`issue-mr-flow` の各flow-id、`cleanup-task.sh` 等）が、コミットメッセージの
   文言を前提にしていないか（例: 特定の文字列でコミットを検索する処理の有無）。

**何が分かれば次へ進めるか**: 「1行のみを維持するか」の判断材料が揃い、書き換えが必要な
ドキュメントの一覧が確定すること。

## フェーズ3〈作業〉

1. 方針を決める（1行のみ維持／本文許容／条件付き許容）。
2. `commit` スキルへ内容規約を追記する。**AIエージェントが機械的に従える形**にする
   （満たすべき要素の列挙・良い例・悪い例・判断に迷ったときの既定）。
3. 成果物の変更を伴わないコミット（HANDOFF更新・空コミット・片付け）の書き方を規約へ含める。
4. issue本文の「実例」9行の書き直し例を示す。
5. `create-commit.md` のメッセージ形式の記述を方針と揃える。

## フェーズ4〈反映〉

**反映対象は flow-id 4-1 で洗い出す。** 現時点の見込みは次のとおり（確定ではない）。

- DDR新設（方針決定の経緯・却下案）と `.claude/docs/README.md` のDDR一覧の再生成。
- `.claude/docs/spec/create-commit.md` の「影響範囲」へ本issueのエントリを追記。
- `.claude/rules/git-workflow.md`「コミット運用」からの入口の要否。
- `.claude/docs/usecase/` の記述・リンクが古くならないかの確認。

## やらないこと（スコープ外）

| 項目 | 判断の根拠 |
|---|---|
| 過去のコミットメッセージの書き換え | 履歴の改変であり、issueの目的（今後の履歴を読めるようにする）を超える |
| `create-commit.sh` の実装変更（方針上不要な場合） | 規約の追記で受け入れ条件を満たせる見込み。必要と判明したらフェーズ3で範囲を確定する |
| prefix一覧（`feat`/`fix`/…）そのものの見直し | issueが問題にしているのは prefix の後ろの説明部分である |
| issue本文が「主対象ではない」と断っている英語コミットの経路調査 | issue本文が記録として残すに留めている |

## 検証

- issue #185 の受け入れ条件5件それぞれについて、対応する記述が成果物のどこにあるかを示せる。
- `grep` で「1行のみ」の記述が残る箇所をすべて洗い、方針と矛盾する記述が0件である。
- DDRを追加した後に `bash .claude/scripts/src/generate-ddr-list.sh` を実行し、差分が
  同じコミットに含まれている。
- `bash .claude/scripts/src/check-doc-references.sh` で参照切れが無い。

## issueの受け入れ条件との対応

| 受け入れ条件 | 対応するフェーズ |
|---|---|
| `commit/SKILL.md` に内容規約（満たすべき要素・良い例・悪い例）が追記されている | フェーズ3 |
| 「1行のみ」か「本文許容」かの方針が決まりDDRに記録されている | フェーズ3（方針決定）・フェーズ4（DDR） |
| `create-commit.md` の記述が方針と矛盾しない | フェーズ3・フェーズ4 |
| issue本文の実例の書き直し例が示されている | フェーズ3 |
| 成果物の変更を伴わないコミットの書き方が規約に含まれている | フェーズ3 |

## この計画の位置づけ・非対話セッションでの読み替え

本セッションは Claude Code on the web のリモート実行環境（非対話）で、人間のレビュー往復
（flow-id 1-5・2-3/2-8・3-3/3-8・4-3/4-8）を待てない。ユーザーからの指示により、
**各フェーズの計画時に1回、作業実施ごとに1回、`adversarial-review` スキルによる敵対的レビューを
自動実行し、その指摘への対応をもってレビュー往復の代替とする**。

- 全体作業計画はplanツール（Planモード）ではなくWrite/Editで作成した（Planモードの承認を
  待てないため）。この逸脱は最終統括レポート（flow-id 5-4）にも記す。
- 人間のレビュー担当ステップの進捗記号は `[]` のまま残す
  （`.claude/rules/docs-workflow.md` の非対話セッションの扱いに従う）。
