# 個別作業計画 — コミットメッセージ内容規約の策定とcommitスキルへの追記

対応する全体作業計画: `wip/plans/keen-charting-lantern.md`（flow-id 1-4）
前提となる調査結果: `wip/reports/2026-08-23_keen-charting-lantern_コミットメッセージ規約の現状調査.md`（flow-id 2-6）

**この計画には「これから何をするか」だけを書く。** 実施結果は
`wip/reports/2026-08-23_keen-charting-lantern_コミットメッセージ内容規約の策定.md` へ書く。

## 種別を併記した理由

`【設計】`（方針の確定）と`【AIアセット作成】`（`commit/SKILL.md` の改訂）を1ファイルにした。
**方針の中身がそのまま規約の文面になるため、分けても記述が重複するだけで合意の単位が変わらない**
（`references/planning.md`「種別を複数併記する場合／分ける場合」の併記側の基準）。
方針そのものは調査（Q3・Q4）で実測が揃っており、フェーズ3で新たに検討するのは
「その方針を、AIエージェントが機械的に従える文面へどう落とすか」だけである。

## 目的

issue #185 の受け入れ条件のうち、フェーズ3が担うのは次の4件（条件2のDDR本体はフェーズ4）。

| 受け入れ条件 | フェーズ3での担当 |
|---|---|
| 1. 1行で「何を・どう変えたか」が分かる内容規約を定める | 規約の文面を作る |
| 2. 「1行のみ」を維持するか本文を許容するかを決める | **方針を確定する**（DDRへの記録はフェーズ4） |
| 3. `commit/SKILL.md` へAIが機械的に従える形で書く | 追記の実施 |
| 4. issue本文の実例9行の書き直し例を示す | 9行すべての書き直し例を作る |

## 決めること（設計）

### 決定1: 件名1行は必須・本文は任意で許容する

調査で実測が4点揃っているため、この方針を採る。**この計画のレビューで覆る余地は残す**が、
覆す場合は下記の実測のどれを否定するかを示す必要がある。

| 根拠 | 実測の出所 |
|---|---|
| 実装変更が不要（`create-commit.sh` は改行入りメッセージをそのまま通す） | 調査Q3 |
| 本文はsquash後も `main` へ恒久的に残る | 調査Q4 |
| 実務側は既に本文を書いており、現行規約のほうが実態から乖離している（本文6件・フッター6件） | 調査Q2 |
| `issue-mr-flow/SKILL.md:229`（確認結果を必ずコミットメッセージへ残す）が1行縛りと衝突 | 調査Q5 |

**本文を「任意」にするか「特定の場面では必須」にするかは、この計画で決める。**
現時点の案は「原則任意。ただし**件名だけでは要素を満たせない場合は本文へ書く**」で、
「必ず本文を書け」とはしない（守られない規約を増やさないため）。

### 決定2: 件名が満たすべき要素

issue #185 が問題視しているのは「対象＋動詞で終わる」形なので、**動詞の先を要求する**形にする。
現時点の案は次の3要素だが、**要素の粒度と個数はこの計画のレビューで確定させる**。

| 要素 | 内容 | 省略してよい場合 |
|---|---|---|
| **何を** | 変更した対象（ファイル・機能・概念） | 省略不可 |
| **どう** | どう変えたか（変更後の状態・採った手段） | 省略不可 |
| **なぜ** | 変更の理由 | 対象と手段から自明なら省略可。本文へ回してもよい |

**「どう」の判定基準を文面へ入れる。** 「修正した」「更新した」「反映した」で終わる行は、
どう変えたかを述べていないため不合格とする（調査で母数の64%がこの形）。

### 決定3: 成果物の変更を伴わないコミットの書き方

調査で `main` に残らない成果物のみのコミットが58%、事務的作業記録が15%あった。
**この多数派の書き方を決めないと、規約は守られない側が多数になる。** 次の3類型を扱う。

| 類型 | 現状の書かれ方 | 規約で求める形（案） |
|---|---|---|
| `HANDOFF.md` の進捗更新のみ | `docs: HANDOFFを更新` | **どのflow-idが何になったか**を書く |
| `wip/plans/` `wip/worklogs/` `wip/reports/` のみの変更 | `docs: 計画を修正` | **何を変えたか**（どの節・どの判断が変わったか）を書く |
| Draft PR作成のための空コミット | `chore: 空コミット（baseとの差分が無いため）` | 現状の形で足りる。**例外として明記する** |

### 決定4: PRタイトルが1行ログに出る事実を規約へ書くか

調査Q4で、`git log --oneline` に出るのは**PRタイトル**であり、個別コミットの件名は
squash本文の中にしか現れないと実測できた。**この事実を `commit/SKILL.md` へ書くかどうかを決める。**

- 書く場合: 「コミットメッセージを直せば `--oneline` が読めるようになる」という誤解を防げる。
- 書かない場合: `commit` スキルの守備範囲（コミットの作り方）から外れる。

現時点の案は「**注記として1段落だけ書く**」。PRタイトルの規約そのものは本issueのスコープ外とし、
必要なら別issueへ切り出す。

## 作ること（成果物）

### 1. `.claude/skills/commit/SKILL.md` への追記

**置き換え前**（144〜146行）:

```
**コミットメッセージ形式：**
- `<prefix>: <日本語説明>` の **1行のみ**
- 本文・フッター・Co-Authored-By など一切付けない
```

**置き換え後**: 決定1〜4を反映した節へ差し替える。

**この2行は役割を2つ兼ねている。** 差し替えで巻き添えにしないこと。

| 役割 | 扱い |
|---|---|
| (1) メッセージの形式（1行のみ・本文なし） | **方針決定の対象**。決定1で置き換える |
| (2) Claudeフッター・Co-Authored-By の禁止 | **方針に関わらず維持する**。同ファイル31行に同趣旨の絶対ルールがあるが、**それは146行を消してよい理由にならない** |

追記する節の構成（案）:

1. 件名（1行目）の形式と、満たすべき要素
2. 良い例・悪い例（悪い例には**なぜ悪いか**を必ず添える）
3. 本文（2行目以降）を書く場合の形式と、書くべき場面
4. 成果物の変更を伴わないコミットの書き方（決定3の3類型）
5. PRタイトルについての注記（決定4）

### 2. issue本文の実例9行の書き直し例

**素材は統計の母数の外にある。** issue #185 の本文が挙げた9行はissue #110 のPR由来で、
調査で固定した母数（直近5件・80件）には含まれない。**issue本文から直接9行を引き写し、
統計とは別枠であることを明示する**（母数を広げて統計を取り直さない）。

書き直し例は `wip/reports/…内容規約の策定.md` へ表として置く。**規約が実際に適用できることの
検証を兼ねる**ため、9行すべてを対象にし、1行も飛ばさない。

- 9行のうち1行（`Fix formatting and clarify task types in workflow doc`）は**英語・prefix無し**
  である。規約は日本語・prefix必須なので、書き直し例では両方を直す。
  **英語コミットが生まれた経路の調査はスコープ外**（全体作業計画）。

## 判断を仰ぐこと

**`commit/SKILL.md` の「## 備考」以下（150〜170行）が孤立している。** 開きの無い閉じフェンスで
終わり、PR descriptionの雛形に見える断片（「レビュアーが知っておくべきこと」「変更内容の列挙
ルール」）が残っている。ファイル新規作成時（`e87d2b4`）からこの形である。

- **同じファイルの同じ主題（何を書くか）**の箇所であり、今回追記する節のすぐ下に来る。
- ただし**本issueの受け入れ条件のどれにも該当しない**。
- 現時点の案は「**触らず、別issueとして切り出す**」。無言で削除はしない（何のための断片か
  判断できない以上、消してよいと断定できないため）。

## 検証

**「0件」を合格条件にしない**（調査Q1で、無関係なヒットが15件常駐すると分かっているため）。

| 検証項目 | 方法 | 合格条件 |
|---|---|---|
| 書き換え対象3行のうち2行が消えたか | `grep -n '1行のみ\|本文・フッター' .claude/skills/commit/SKILL.md` | `145` `146` に相当する記述が無い |
| フッター禁止が残っているか | `grep -n 'Co-Authored-By' .claude/skills/commit/SKILL.md` | 31行の絶対ルールが残っている |
| 追記した節がAIエージェントに機械的に従えるか | 規約の文面だけを読んで、issue本文の9行を書き直せるか | 9行すべてに書き直し例が作れる |
| 悪い例に理由が添えられているか | 目視 | 悪い例の全件に「なぜ悪いか」がある |
| 規約が自分自身に適用できるか | このフェーズのコミットメッセージを新規約で書く | 件名が決定2の3要素を満たす |

**最後の項目は自己適用の検証である。** 規約を作った当人が最初の適用者になるため、
書けない・書きにくいと感じたらそれは規約側の欠陥として扱う。

## 進め方

1. 上記の決定1〜4を確定させる（この計画のレビュー）。

4. 検証表の5項目を実施する。
5. 敵対的レビュー（作業実施に対して）→ 指摘へ対応・返信。
