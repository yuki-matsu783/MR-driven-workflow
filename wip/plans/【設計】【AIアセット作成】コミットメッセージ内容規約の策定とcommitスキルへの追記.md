## 種別を併記した理由

`【設計】`（方針の確定）と`【AIアセット作成】`（`commit/SKILL.md` の改訂）を1ファイルにした。
**方針の中身がそのまま規約の文面になるため、分けても記述が重複するだけで合意の単位が変わらない**
（`references/planning.md`「種別を複数併記する場合／分ける場合」の**併記側の基準**）。
方針そのものは調査（Q3・Q4）で実測が揃っており、フェーズ3で新たに検討するのは
「その方針を、AIエージェントが機械的に従える文面へどう落とすか」だけである。

## 決めること（設計）

### 決定1: 件名1行は必須・本文は任意で許容する

調査で実測が4点揃っているため、この方針を採る。**この計画のレビューで覆る余地は残す**が、
覆す場合は下記の実測のどれを否定するかを示す必要がある。

| 根拠 | 実測の出所 |
|---|---|
| 実装変更が不要（`create-commit.sh` は改行入りメッセージをそのまま通す） | 調査Q3 |
| 本文はsquash後も `main` へ恒久的に残る | 調査Q4 |
| 実務側は既に本文を書いており、現行規約のほうが実態から乖離している（本文6件・フッター6件） | 調査Q2 |
| `issue-mr-flow/SKILL.md:229`（確認結果を必ずコミットメッセージへ残す）が1行縛りと衝突 | 調査Q5 |

> **1行目の根拠には限界がある。** 調査の「確かめられなかったこと」が明記しているとおり、
> Q3の実測は**すべてLinux（Claude Code on the web）で行っており、git bash（Windows）実機では
> 未計測**である。本リポジトリの標準実行環境はgit bash（`.claude/rules/shell-script-style.md`
> 「前提」）なので、この未計測は残る。**改行の扱いは `git commit -m` へ委ねられており処理系差は
> 考えにくいが、断定はしない。** 実機確認はフェーズ4のDDRへ「未計測である事実」として
> 引き継ぐ（実機を持つ環境で確認できたら、そのとき記録を更新する）。

**本文を「任意」にするか「特定の場面では必須」にするかは、この計画で決める。**
現時点の案は「原則任意。ただし**件名だけでは要素を満たせない場合は本文へ書く**」で、
「必ず本文を書け」とはしない（守られない規約を増やさないため）。

#### 決定1-b: 本文以外のフッター（`Refs #NNN` 等）を許容するか

**置き換え対象の146行は役割を3つ兼ねている**（初版は2つと数えていた）。

| 役割 | 扱い |
|---|---|
| (1) 本文の禁止 | **決定1で置き換える** |
| (2) **フッター全般の禁止**（`Refs #NNN` 等） | **決定1-b で決める。初版はこの役割を見落としていた** |
| (3) `Co-Authored-By` の禁止 | **方針に関わらず維持する**（下記） |

- **(3) の維持先である31行は、(2) を代替しない。** 31行が禁じているのは
  「`Co-Authored-By: Claude` **など**のフッター」であり、`Refs #NNN` を禁じているとも
  許しているとも読める。146行を消すだけでは、(2) の可否が誰にも決められない状態になる。
- **調査Q2で `Refs #NNN` フッターが6件マージ済みと実測されている。** 「禁止のまま」と
  「許容へ変える」で実務の扱いが正反対になるため、**どちらかを明文で決める**。
- 現時点の案は「**`Refs #NNN` のような追跡用フッターは許容する。ただしAIの生成物であることを
  示すフッター（`Co-Authored-By: Claude` 等）は引き続き絶対禁止**」。前者は人間が書いても
  同じ形になる情報で、後者とは性質が違う。

### 決定2: 件名が満たすべき要素

issue #185 が問題視しているのは「対象＋動詞で終わる」形なので、**動詞の先を要求する**形にする。
**要素の粒度と個数はこの計画のレビューで確定させる。**

| 要素 | 内容 | 省略してよい場合 |
|---|---|---|
| **何を** | 変更した対象（ファイル・機能・概念） | 省略不可 |
| **どう** | どう変えたか（変更後の状態・採った手段） | 省略不可 |
| **なぜ** | 変更の理由 | 対象と手段から自明なら省略可。本文へ回してもよい |

**「どう」の判定基準は、調査の実測と同じ形で書く。** 調査Q2 (a) の51件（64%）は次のコマンドで
数えたものなので、規約の不合格基準もこれに揃える。

```bash
grep -cE '(を|の)?(修正|更新|反映|追加|作成|記録)(する|)$'
```

- 対象の語は **6語**（`修正` `更新` `反映` `追加` `作成` `記録`）。初版は3語しか挙げていなかった。
- 語尾は **「〜する」「〜した」「体言止め（〜更新）」のいずれも対象**とする。上の正規表現が
  拾うのは非過去形（`〜を更新` / `〜を更新する`）だけで、初版が書いていた「〜更新**した**」は
  **1件も一致しない**。実測の多数派である「docs: HANDOFFを更新」型を規約が取り逃がさないよう、
  語尾を明示的に列挙する。
- **64%という数値を引用するときは「この6語で終わる形」と正確に添える。**

### 決定3: 成果物の変更を伴わないコミットの書き方（受け入れ条件5）

調査で `main` に残らない成果物のみのコミットが58%、事務的作業記録が15%あった。
**この多数派の書き方を決めないと、規約は守られない側が多数になる。** 次の3類型を扱う。

| 類型 | 現状の書かれ方 | 規約で求める形（案） |
|---|---|---|
| `HANDOFF.md` の進捗更新のみ | `docs: HANDOFFを更新` | **どのflow-idが何になったか**を書く |
| `wip/plans/` `wip/worklogs/` `wip/reports/` のみの変更 | `docs: 計画を修正` | **何を変えたか**（どの節・どの判断が変わったか）を書く |
| Draft PR作成のための空コミット | `chore: 空コミット（baseとの差分が無いため）` | 現状の形で足りる。**例外として明記する** |

### 決定4: PRタイトルが1行ログに出る事実を規約へ書くか

調査Q4で、`git log --oneline` に出るのは**PRタイトル**であり、個別コミットの件名は
squash本文の中にしか現れないと実測できた。**この事実を `commit/SKILL.md` へ書くかどうかを決める。**

- 書く場合: 「コミットメッセージを直せば `--oneline` が読めるようになる」という誤解を防げる。
- 書かない場合: `commit` スキルの守備範囲（コミットの作り方）から外れる。

現時点の案は「**注記として1段落だけ書く**」。PRタイトルの規約そのものは本issueのスコープ外とし、
必要なら別issueへ切り出す。

### 決定5: `create-commit.md:46` をフェーズ3で直す

**全体作業計画のフェーズ3 項目5がこれを担当と定めており、調査Q1は `create-commit.md:46` を
書き換え対象3行の1つと確定させている。** 初版はこれを理由なくフェーズ4へ送っていたが、
**フェーズ3で直す**。

- **理由**: フェーズ3のcommit時点で `commit/SKILL.md` が「本文を許容」・`create-commit.md:46` が
  「1行のみ」という**同一リポジトリ内で矛盾した状態**を作らないため。
- **やり方**: 全体作業計画「メッセージ形式の『正』は1箇所に置く」に従い、`create-commit.md` から
  具体形式を落とし、**`commit/SKILL.md` への参照だけを残す**（両方に具体形式を書かない）。
- **フェーズ4へ残るのは、`create-commit.md` の「影響範囲」への本issueのエントリ追記**である
  （こちらは`【設計反映】`の担当。仕様本文の修正とは別物）。

### 決定6: 追記する節をどこへ置くか

**`commit/SKILL.md` 144〜146行は「### Step 4: コミット実行」の中にあり、直後の148行
「複数コミットの場合は順番に Step 3-4 を繰り返す。途中で失敗したら**そこで停止**して状況を報告」は
Step 4全体にかかる地の文である。**

この位置へ見出し付きの規約節を差し込むと、148行が新しい節の続きに読め、**複数コミット時の
手順指示という役割が失われる**（ルート `REVIEW-POINTS.md`「新しい見出しの挿入位置が、直前の節の
『節全体にかかる地の文』の係り先を壊していないか」）。

**採る形**: 144〜146行の位置には**規約への短い参照**だけを残し、**規約の本体は148行の後・
`## 備考` の前へ独立した `##` 節として置く**。こうすると148行の係り先はStep 4のまま変わらない。

```
### Step 4: コミット実行
  …
  （144〜146行の位置）→ 「メッセージの書き方は下記『コミットメッセージの内容規約』に従う」の1行
  148行: 複数コミットの場合は順番に Step 3-4 を繰り返す…   ← 係り先は Step 4 のまま
## コミットメッセージの内容規約     ← 新設（決定1〜4）
## 備考                              ← 既存（下記「判断を仰ぐこと」）
```

## 検証

**「0件」を合格条件にしない。** 変更前のツリーでも無関係なヒットが常駐するため、
**変更前の実測件数を基準値として、差分で判定する**。基準値は次のとおり（2026-08-23 実測）。

```bash
# (a) 規約の地の文（検索語はQ1の4語）
grep -rn '1行のみ\|本文・フッター\|フッター' --include='*.md' .claude AGENTS.md CLAUDE.md GEMINI.md | wc -l
# → 19（うち書き換え対象3・維持1・無関係15）
grep -rn '1行のみ\|本文・フッター\|フッター' --include='*.md' .claude .gemini AGENTS.md CLAUDE.md GEMINI.md | wc -l
# → 38（.gemini/ が .claude/ の完全な鏡なのでちょうど2倍）

# (b) 旧規約に沿った例示・雛形（(a) では1件も拾えない）
grep -rn --include='*.md' --include='*.sh' -e '--message "' .claude | wc -l
# → 14
grep -rn --include='*.md' --include='*.sh' -e '--message "' .claude .gemini | wc -l
# → 28
```

| 11 | 規約が自分自身に適用できるか | このフェーズのコミットメッセージを新規約で書く | 件名が「何を」「どう」を満たし、**「なぜ」は件名か本文のいずれかにあるか、自明として省略した理由を説明できる** |

**項目11は自己適用の検証である。** 規約を作った当人が最初の適用者になるため、
書けない・書きにくいと感じたらそれは規約側の欠陥として扱う。
**合格条件で「3要素すべて」を求めないのは、決定2が「なぜ」を省略可としているためである**
（3要素を機械的に求めると、規約上は合格の件名が検証で不合格になる）。
