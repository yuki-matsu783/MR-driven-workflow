段取りD: 実装手段の確認

#問い調べ方判定基準
8マルチバイト文字を文字単位で切り出す、ロケール非依存の手段はどれか候補（jq の .[0:N]／awk の substr／${var:0:N}）を、LANG を空にした環境と C.UTF-8 の両方で日本語文字列へ当てる両方の環境で同じ結果になる手段だけを採る。Windowsネイティブjq・MSYSは未確認と明記する（下記）
11jq -R -n ＋ inputs は実 transcript のサイズで許容範囲か段取りAで測った実サイズのファイルへ、確定した抽出フィルタを当てて空関数をベースラインに時間を測る。測定はLinux追加コスト 200ms 以内（先に置いたしきい値）。Linuxでの合否は暫定とし、git bash実機の見積もりを併記する（下記）
7git bash 実機で transcript_path はどの表記で渡るか本調査はリモート実行環境（Linux）で行うため実機確認できない見込み確認できなければ「未確認」と明記する（確認できたことにしない）。jq へパス名を渡さず標準入力へ繋ぐ形で回避できるかを机上で確認する
段取りDの測定環境（問い8・11に共通する制約） 本調査はリモート実行環境（Linux）でしか行えない。問い7だけでなく、問い8・11も同じ制約を受ける。これを断らずに数値を出すと、実運用環境で成り立たない結論が「実測済み」として固定される。
問いLinuxで測ると何がずれるかどう扱うか
11（性能）git bash（MSYS）の外部プロセス起動は約95ms/回、jq -nc '1' 1回が実測138msで、Linuxとは桁が違う（.claude/rules/shell-script-style.md「外部プロセス起動のコスト」は『Linuxで得た閾値をそのままgit bashへ持ち込まないこと』と明記している）。Linuxで150msと出て「200ms以内・合格」としても、git bashではjq起動だけで大半を消費して超過しうるLinuxの実測値と、git bash実機の見積もり（jq起動回数 × 138ms ＋ 走査時間）を併記する。合否は暫定とし、フェーズ3で実機再測を要する旨をレポートへ書く
8（ロケール依存の文字切り出し）検証するのは LANG 空／C.UTF-8 の2条件だが、Windowsネイティブjq・MSYSでは再現していない。.claude/rules/shell-script-style.md は、Windows版jqが strptime/mktime を持たない等、同じjqでも実装差があることを実例で記録している「Linux上の2条件で同結果だった」までを結論とし、Windowsネイティブjq・MSYSでの挙動は「未確認」と明記する
この断りを、しきい値を緩める口実に使わない。200ms を超えた場合は、下記「停止条件」のとおりフェーズ3へ進む前に実装方式を見直す（暫定なのは「合格」の側だけで、「不合格」は不合格である）。

問い11の計測は .claude/rules/shell-script-style.md「起動回数がゼロであることを計測で確かめるとき」の手順に従う（空関数をベースラインに取る／試行回数を十分に取る／同一セッション内で連続して測る）。絶対値だけを見て「速い・遅い」と判断しない。

実データを扱ううえでの制約

記録方針の正は全体作業計画。本計画で緩めない
  • wip/reports/・worklog へ発言の本文を貼らない。残してよいのは件数・文字数分布・バイト数といった統計値と、自分（AI）が本セッションで打った発言に限った抜粋だけ。「必要なら引用してよい」という読み替えをしない（本文が要ると感じたら、値と件数で表現できる形へ問いを言い換える）。
  • 問い5（過剰除去の確認）が最も踏みやすい。「除外された発言を全件目視する」のは手元での確認であり、レポートへ残すのは『どの辞書語が何件落としたか』という語と件数だけにする。過剰除去が出た場合も、記録するのは「その語」と「件数」であって発言本文ではない。
  • 秘密情報（トークン等）が本文に含まれていた場合、値そのものを置換する（.claude/rules/shell-script-style.md「秘密情報の扱い」）。接頭辞決め打ちのマスクに頼らない。
  • 一時ファイル（退避した生JSON・抽出結果）はscratchpad へ置き、リポジトリへコミットしない。

検証

実行できるコマンドで確かめる（wip/plans/REVIEW-POINTS.md「検証手順」）。flow-id 2-6 の実施後に、リポジトリルートで次を流す。

REPORT='wip/reports/20260824_session-start-user-utterance-reinject_transcript実測の調査結果.md'

# 1. 成果物が md / html の両方そろっているか
test -f "$REPORT" && test -f "${REPORT%.md}.html" && echo 'OK: 成果物2件'

# 2. 13の問いの見出しが「過不足なく」あるか。
#    見出しの個数を数えるだけでは、中身が空でも通ってしまう。実際に現れた番号を
#    列挙して期待値と突き合わせ、差分が無いことを見る。
diff <(grep -oE '^### 問い[0-9]+[ab]?' "$REPORT" | sed 's/^### 問い//' | sort -u) \
     <(printf '%s\n' 1 10a 10b 11 12 13 2 3 4 5 6 7 8 9 | sort -u) \
  && echo 'OK: 問いの番号が過不足なく一致'

# 3. 各見出しの直下に結論の実体があるか（空の見出しを弾く）。
#    「見出しでない非空行が1行以上あるか」だけを見る。結論の"形"を正規表現で判定しない
#    （後続の見出し行自身が数字を含むため、形での判定は空の見出しを取りこぼす。実測済み）。
#    0 が返れば合格。1件以上なら、その見出し名が標準エラーへ出る。
awk '
  /^###[ 　]/ { if (h != "" && n == 0) print h; h=$0; n=0; next }
  /^#/        { if (h != "" && n == 0) print h; h=""; n=0; next }
  NF          { if (h != "") n++ }
  END         { if (h != "" && n == 0) print h }
' "$REPORT" | tee /dev/stderr | wc -l

# 4. 「やらないこと」を破っていないか。
#    origin/main は fetch してから、分岐点を実行時に求める（SHAは書き写さない）。
#    対象は1ファイルではなくディレクトリ単位で見る（テスト・他のhookへの混入も拾うため）。
git fetch origin main
base="$(git merge-base origin/main HEAD)"
git diff --name-only "$base" -- .claude/
