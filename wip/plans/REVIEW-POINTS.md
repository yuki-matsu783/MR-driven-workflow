# レビュー観点（plans配下）

## 2階層構造

- **全体作業計画がこのブランチに1つだけ**か（`wip/plans/` 配下で `【` で始まらないファイル）。
  セッションごとに増えていないか。
- 個別計画（`wip/plans/【*.md`）を**planツールで作っていない**か（Write/Editで作る）。
- 全体作業計画のファイル名が、ハーネスの提示した自動命名のままか。

## 種別

- 種別が `【調査】【設計】【実装】【テスト】【AIアセット作成】【設計反映】【AIアセット反映】【実装反映】`
  の8種から選ばれているか。
- 併記／分割の判断が「**人間の合意を1回で取るか、フェーズごとに分けて取るか**」で説明できるか。
  迷う粒度なら分ける。
- `【設計反映】` `【AIアセット反映】` `【実装反映】` を併記していないか（対象・評価軸が異なる
  ため原則分ける）。
- `【AIアセット作成】`と`【AIアセット反映】`の使い分けが、成果物（そのissueの主たる目的）か
  副産物（作業中に気づいた改善）かで説明できるか。
- `【実装反映】`が、フェーズ3のレビュー往復ループ（3-6〜3-9）で解消できる不具合まで
  取り込んでいないか（フェーズ3で解消できるものはフェーズ3で対応する）。

## 内容

- issueの**受け入れ条件すべて**に、計画上の対応箇所があるか（漏れているものはないか）。
- **調査結果・作業結果を計画ファイルへ書いていないか**（結果は `wip/reports/` 配下へ分ける。issue #87）。
- **依拠する調査・レポートの結論を計画へ引くとき、結論の文言をそのまま引用しているか。変える
  場合は変更点と理由が明示されているか**（issue #168 の html-slides スキルで実際に踏んだ:
  調査で確定した型名enum・スキーマ構造を計画へ書き写す段階で独自に変えてしまい、レビューで
  初めて発覚した。転記時の無言の改変は、前段の合意を静かに無効化する）。
- 「この計画で決めないこと（スコープ外）」が書かれているか。後段のフェーズへ送った判断が
  どこで決まるのか追えるか。
- 前提として確定した事項に、**いつ・どこで合意したか**（flow-id）が添えられているか。
- **「既存のN行をこう置き換える」形の修正指示に、置き換え前後の形が両方書かれているか。**
  「どこを何に変えるか」だけだと、**置き換え対象の行が兼ねていた役割の巻き添え**を計画の段階で
  検出できない。実例（issue #127）: 置き換え対象の行が別の変数の `local` 宣言を兼ねており、
  指示どおり実装すると未定義変数参照になる状態だった。
- **同一計画内の別の作業が、ある作業の前提を崩していないか。** 実例（issue #127）: ある作業で
  「外部プロセスを起動しないテスト」と書いた一方、別の作業の変更でその経路が
  `git remote get-url origin` を起動するようになっていた。作業を独立に読むと、どちらも正しく見える。

## issue分割のトリガー

- 「期待する動作」「受け入れ条件」が**同型の成果物の並列列挙**（画面・API・CLIサブコマンド・
  バッチ・テーブル・外部連携先が「AとBとCを作る」と並ぶ形）になっていないか。
- 該当する場合、「各項目が単独でマージされてもシステムが壊れないか」で判定したか。
- 分割しないと判断したなら、その**理由が全体作業計画と `HANDOFF.md` に残って**いるか。
- 分割の判断をAIが独断で行っていないか（提案までがAIの役割）。

## 【AIアセット反映】の計画（issue #155）

**この節は「何を見るか」だけを持つ。** 4類型の定義・証拠を要求する範囲・打ち切りの段階・2軸の
対応表は、`.claude/skills/issue-mr-flow/references/planning.md`「AIアセット反映の対象の洗い出し」が正である
（ここへ再掲すると、類型や形態を増やしたときに片方だけが古くなる）。

- **起点が「今回の作業の副産物」になっているか。** そのissueの主たる成果物としてのアセット作成が
  紛れ込んでいないか（それは `【AIアセット作成】`（フェーズ3）で扱う）。
- **各項目が4類型 (a)〜(d) のどれに当たるか書かれているか。** 「どれにも当たらない」と判断した
  項目について、そう判断した理由が書かれているか。
- **(a) と分類した項目に、再現性の証拠が添えられているか。** (b)(c)(d) に対して再現性の証拠を
  求めていないか（**再現性**を要求するのは (a) だけである）。
- **(a) と (c) の両方について、痕跡を探したか。** (c)（アセットはあったが罠が書かれていなかった）と
  判定するには「その罠を扱った記述が本当に無いこと」の確認が要るため、痕跡の確認は (a) 限定では
  ない。探さずに (c) と決めていないか。
- **痕跡の確認をどの段階で打ち切ったかが書かれているか。** `doc-search` の `matched=0` だけを
  根拠にしていないか（frontmatterのキーしか見ないため、本文の記述を拾えない）。
- **痕跡が見つかった項目を (a)/(c) のままにしていないか。** 見つかったなら (d)（あったのに辿り着け
  なかった）であり、新規作成・追記ではなく導線の改善になる。
- **反映先の形態が2軸（いつ効いてほしいか × 守らせ方の強さ）で選ばれているか。** 「とりあえず
  `rules` へ書く」になっていないか（常時読込はセッションごとにコンテキストを消費する）。
- **削除・統合が検討されているか。** 追記だけで済ませていないか。
- **削除・統合を含む場合、`.claude/VERSION` の扱いに触れているか**
  （`.claude/docs/spec/distribution-assets.md`。上流の削除は配布先へ伝播しない）。
- **`【設計反映】` `【実装反映】` と併記していないか**（上記「種別」の観点）。
- **反映先が `.claude/scripts/` `.claude/hooks/` の項目について、種別の判定が
  `references/planning.md`「AIアセット反映の対象の洗い出し」の規定どおりか。**

## 検証手順

- 計画に「検証」節があり、**実際に実行できるコマンド**が書かれているか。
- 実機確認が必要なもの（外部API・別プロバイダ）を、机上確認で済ませる計画になっていないか。
- **空振り**（変更前から通ってしまう検証）を排除したか。観点の正はルート `REVIEW-POINTS.md`
  「検証コマンドが、異常があるときに本当に検出できるか」である。

## HTML版（issue #54）

計画にも同名の `.html`（人間レビュー用ビュー）を置く。土台は
`.claude/skills/issue-mr-flow/assets/plans.template.html`。

- **自己完結**しているか（外部依存・ローカル参照が1つも無い）。検査は「実際に外部を読みに行く
  記述」に限り、`grep -nE "(src|href)=['\"]?(https?:)?//" <ファイル>` と
  `grep -nE "(url\(|@import[[:space:]]+)['\"]?(https?:)?//" <ファイル>` がいずれも **0件**である
  こと（`https://` を含む行を数える検査にすると、`<code>` の中でURLを引用しただけの計画を
  誤検知する。狭めすぎるとシングルクォート・プロトコル相対・`@import` が素通りする。
  **拾えないもの**（相対パスのローカル参照・`<code>` 内でHTML属性ごと引用した箇所）の扱いを
  含め、判定の根拠は `wip/reports/REVIEW-POINTS.md` の同名の観点が正）。
- **テンプレートの埋め忘れが無いか。** `grep -c '<!-- ここに書く' <ファイル>` が 0 であること
  （`<!--` まで含めて数える。**地の文で「ここに書く」という語に触れる成果物**——テンプレート自身を
  説明する計画・レポート——を誤検知しないため）。使わなかった `[任意]` の `section` は、
  プレースホルダを残さず**節ごと削除**する。
- **ページ内アンカー（`href="#…"`）を張るHTMLは、リンク破断・重複IDの検査を実行したか。**
  計画HTMLも目次（`nav.toc`）からアンカーを張るため、レポート側と同じ罠（存在しないIDへの
  参照・コピーによるIDの振り直し忘れ）が起こる。**検査コマンド・合格条件・一般則の正は
  `.claude/skills/issue-mr-flow/references/deliverables.md`「検査手順の正はこの節にある」**
  （ID抽出をタグ内に限定する理由を含む。ここには再掲しない。issue #186, #203）。
- **`<style>` が1つだけか**（検査6）。**コメントを除去してから**数えた `<style` と `</style>` が
  **どちらも 1** でなければ不合格（`perl -0pe 's/<!--.*?-->//gs'` を先に通す。行頭に固定すると
  インデントされた重複を取りこぼし、固定を外すと地の文の言及を誤検出するため）。2つあると2つ目はCSSのテキストとして扱われ、続く
  `:root { … }` ブロックごと破棄される。**ダーク環境では正常に見え、ライト環境でだけ配色が
  初期値へ落ちる**ため、レビュアーの環境によっては気づけない（issue #203 で実際に踏んだ。
  リンク破断・重複ID・外部依存の検査はどれもこれを捕まえない）。
- markdown版とHTML版の**内容が同期**しているか（片方だけ更新されていないか）。
  **同期を「追記」だけで済ませていないか。既存記述の更新まで含める。** 判定の目安は
  「**md側の差分が『追加のみ』でないなら、HTML側も『追加のみ』では同期していない**」
  （`wip/plans/` だけをレビュー対象にすると `wip/reports/REVIEW-POINTS.md` は収集されないため、
  目安はここにも書く。実例・詳細はあちらの同名の観点）。
- **必須節が丸ごと落ちていないか。** 上の埋め忘れ検査（`<!-- ここに書く`）は**プレースホルダが
  残っている**ことしか見ないため、`<section>` ごと削除された節は0を返して合格する（issue #176
  で実際に踏んだ。計画側の必須節は「この計画で何をするか／変更対象／方針／やらないこと（スコープ外）
  ／検証」の5つで、このいずれかが節ごと消えていても埋め忘れ検査は通る）。
  テンプレートの `[必須]` コメントと突き合わせる。

  **検査コマンドの正は `wip/reports/REVIEW-POINTS.md` の同名の観点**（完全一致で突き合わせては
  いけない理由・部分一致にしたことで代わりに取りこぼす形を含む。**ここには再掲しない**——
  以前は同じ22行を両側へ写経しており、実例だけが取り違えられたまま残った。issue #176）。
  計画側は次の2点だけが違う。

  - テンプレートは `.claude/skills/issue-mr-flow/assets/plans.template.html`。
  - **`【調査】` の個別計画に限り、`変更対象`→`調べる問い`、`方針`→`調べ方` と読み替える**
    （調査計画には変更対象も実装方針も無いため、この2節は名前ごと置き換わる）。**読み替えて
    なお落ちていれば欠落である。** 読み替えの対象はこの2つだけで、他の必須節には適用しない。

  **md 側と HTML 側を突き合わせるだけでは足りない**（下の「節の見出しが一致しているか」）。
  両方から同じ節が落ちていれば一致してしまうため、**テンプレートを基準に見る**。
- **md側とHTML側で、節の見出しが一致しているか。** mdの `##`/`###` と HTML の
  `<h2>`/`<h3>` を一覧にして突き合わせる（片方だけに節がある状態は同期漏れである）。
  **突き合わせる前にバッククォートと `<code>` の差を正規化する**（md側はバッククォートを除去し、
  HTML側はタグを除去する）。挟まないと、内容が同一でも必ず差分が出る。
- **markdownの表のセルに、パイプ・バッククォートを含むコマンドを書いていないか。**
  セル内のパイプは**列区切り**と解釈されて列がずれ（HTML側で `<td>` の数が行ごとに合わなくなる）、
  エスケープすると今度はバックスラッシュが落ちて別のコマンドとして表示される。**説明をセルに置き、
  コマンドは表の直後のコードブロックで示す。** 検査は、各表の `<td>`/`<th>` の数が全行で
  揃っていることで行う（issue #155 で2回踏んだ）。
- ファイル名が対応する `.md` と**同じベース名**になっているか。全体作業計画のHTMLも
  ハーネスが提示した自動命名に従い、**AIが別名を付け直していないか**。
