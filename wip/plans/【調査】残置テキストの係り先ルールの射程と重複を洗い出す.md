# 【調査】残置テキストの係り先ルールの射程と重複を洗い出す

issue #142 / PR #188 / flow-id 2-1。

## 前提（合意状況）

- 上位の計画: `plans/brisk-weaving-lantern.md`（flow-id 1-4 で作成。flow-id 1-5 の人間合意は
  非対話的セッションのため `[-]`。ユーザーの指示をもって着手の合意とみなす）。
- 同型の事故が4件あること（issue #64 / #109 / PR #139 / issue #155）は、issue #142 の本文と
  そこへ付いた通知コメント2件から**確定済み**である。この4件を再発掘する調査は行わない。
- **「壊れた位置」の軸は、新しく書いた部分から見て前か後ろかで揃える**（上位計画の背景表と同じ軸。
  「分割点の直後」のような別の基準を混ぜると、同じ事例が前とも後ろとも言える）。

## この計画で何をするか

フェーズ3でルール文言を書き換えるにあたり、**書き換え先・書き換え方を一意に決めるために足りない
情報**を集める。調査の問いは全体作業計画の5問を引き継ぐ。

**4件の判定表（拾えるか／壊れた位置）の正は、この計画ではなく調査結果 `reports/…md` に置く。**
上位計画の背景表は着手時点の見立てであり、調査結果と食い違った場合は調査結果が正である。

## 調査項目

### Q1. 現行ルールの射程と、一般化後に既存記述と矛盾しないか

- `.claude/rules/docs-workflow.md` の該当段落（104〜114行目付近）を全文で確認し、
  **どの文が「見出しの挿入」に依存しているか**を1文ずつ切り分ける。
- 既存の実例2件（`計画の2階層構造` の位置／ファイルごとに結論が変わる話）が、一般化後の文言の
  下でも**そのまま実例として成立するか**を確かめる。
- **確認方法**: 該当段落の前後を読み、下記の暫定案を当てはめて矛盾する語を探す。

### Q2. 同趣旨のルールが他ファイルに重複していないか

- ルート `REVIEW-POINTS.md`「ドキュメントの構造」に、同型の観点
  （「新しい見出しの挿入位置が、直前の節の『節全体にかかる地の文』の係り先を壊していないか」）が
  ある。**正を1箇所に決めるのか、規約（`rules`）と観点表（`REVIEW-POINTS.md`）で役割を分けるのか**を
  決める材料を集める。
- **同じ判定を述べている行を、目に付いた2箇所で打ち切らずに全部数える**（ルート
  `REVIEW-POINTS.md`「集約する前に、同じ判定を述べている行を全部数えたか」）。
- **`.gemini/` を数えない。** `.gemini/` は `.claude/` の変換生成物であり（`sync-gemini-assets.sh`
  が生成する写し）、「重複した記述」ではない。除外しないと件数がちょうど2倍になり、重複箇所を
  過大に見積もる。**`.gemini/` は直接編集しない**（`.claude/rules/directory-structure.md`）。
- **確認方法**: `doc-search` でドキュメントを絞り込んだうえで、本文の語（「係り先」「地の文」
  「見出し」）を横断検索して数える。件数を調査結果へ書く。

### Q3. ルール本文へ載せる実例は何件か

- 4件それぞれについて「**現行ルールで拾えるか／拾えないか**」と「**壊れたテキストが、新しく書いた
  部分から見て前か後ろか**」を表にする。
- issue #142 のコメントが「#109（分割で**前**が壊れる）と PR #139（挿入で**後ろ**が壊れる）は
  方向が逆で、2つ並べると観点が立体的になる」と述べている。**全件載せるか、方向の異なる2件へ
  絞るか**を、読み手の負担と網羅性の両面から判断する。
- **確認方法**: 4件を表に起こし、それぞれが「**下記の暫定案**だけを読んで検出できるか」を机上で
  突き合わせる。1件でも検出できないものが残れば、その形は暫定案では拾えていない。

#### 判定に使う暫定案（この計画では確定しない）

Q3・Q1 の机上判定には、上位計画「フェーズ3〈作業〉」が挙げる5項目を**暫定案**として当てる。
**この調査で確定させるのは「暫定案で4件を検出できるか」という判定結果だけ**であり、
最終的な文言は flow-id 3-1 の個別作業計画で決める（下記「やらないこと」）。

### Q4. 係り先・見出し挿入のルールを扱ったDDRがあるか（DDRの要否の材料）

- **識別子（`i0064-*`）ではなく内容で判定する。** issue #64 由来のDDRは実在するが
  （`i0064-01-issueの分割は並列列挙構造を主トリガーにAIが提案し人間が決定する.md`）、
  中身は「issue分割の判断」であり係り先ルールとは無関係である。**接頭辞の件数だけを見ると
  「追記で足りる」という誤った結論へ流れる。**
- ヒットしたファイルの `title` / `description` まで見て、**今回の拡張の追記先になりうるか**を
  1件ずつ判定する。DDRは本文を変更しない運用のため、「追記」は実質的に新規DDRの作成か
  frontmatter の `note` の追加のいずれかになる。
- 「操作の列挙ではなく観点で書く」という判断が、**却下案を伴う意思決定**なのかを確かめる
  （伴わないなら規約への記述だけで足り、DDRは不要という結論もありうる）。
- **確認方法**: `doc-search` スキルで `type: ddr` を絞り込み、「見出し」「係り先」「構造」で検索する。
  0件だった場合は本文の横断検索へフォールバックし、**ヒットしたファイル名を調査結果へ列挙する**。

### Q5. ルールを実際に守らせる場所はどこか

- 4件とも**自己確認では見つからず敵対的レビューが検出**している。この事実から、
  **規約（`rules`）に書くだけで守られるのか**を検討する。
- 候補は3つ。(a) `.claude/rules/docs-workflow.md` のみ、(b) ＋ルート `REVIEW-POINTS.md` の観点、
  (c) ＋`.claude/agents/adversarial-reviewer.md`。**(c) はスコープ外**と全体作業計画で決めているが、
  「(a)(b) で足りる」と判断できる根拠までは集める。
- **確認方法**: 敵対的レビューが観点表をどう使うか（`adversarial-review` スキル手順2-b、
  `collect-review-points.sh`）を読み、`rules` 配下が敵対的レビューへ渡るかを確かめる。
  **渡らないなら、規約だけに書いても敵対的レビューは見ない**ことになる。

## やらないこと（スコープ外）

- **4件以外の事例の発掘。** 4件で射程の議論には十分であり、発掘に上限が無い
  （判断は本計画で確定し、以後蒸し返さない）。
- **過去ドキュメントの遡及点検**（判断は別issueへ送る。全体作業計画のスコープ外を引き継ぐ）。
- **文言の確定。** 上記「判定に使う暫定案」での机上判定は行うが、**実際に書く文言の確定は
  flow-id 3-1 の個別作業計画で決める**。暫定案の字句を推敲したり、代替案を比較したりしない。

## 検証

**調査が終わったと言える条件は、次の3つがすべて満たされていることである。**

- Q1〜Q5 のすべてに、**根拠（ファイルパスと行、またはコマンドの出力）を添えた答え**が
  `reports/` の調査結果へ書かれている。
- Q2・Q4 について、**件数を数えた結果**（0件も含む）と、**ヒットしたファイル名**が書かれている。
  「見つからなかった」だけで終えない。
- Q3 の表が4件すべてを含み、各件について「暫定案で検出できるか」の判定がある。

下記は**上記3条件を満たすための材料を得る手段**であって、それ自体は合格条件ではない
（着手前の現ツリーでもそのまま成功するため、実行できたことは何も保証しない）。

```bash
# Q2: 同趣旨の記述を横断で数える（.gemini/ は変換生成物なので除外する）
grep -rn '係り先' --include='*.md' . | grep -v '^\./\(plans\|reports\|worklog\|\.gemini\)/' | wc -l
grep -rn '地の文' --include='*.md' . | grep -v '^\./\(plans\|reports\|worklog\|\.gemini\)/' | wc -l

# Q4: 係り先・見出し挿入を扱ったDDRを内容で探す（ファイル名を調査結果へ列挙する）
bash .claude/scripts/src/search-frontmatter.sh --type ddr --text '見出し'
grep -rln '係り先\|地の文' .claude/docs/ddr/ || true
```
