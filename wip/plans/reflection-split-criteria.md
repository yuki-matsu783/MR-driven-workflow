# 全体作業計画 — 反映対象の「このMRで対応するか別issueへ切り出すか」の判断基準（issue #176）

## この計画で何をするか

フェーズ4〈反映〉で洗い出した反映対象について、「このMRで対応するか、別issueへ切り出すか」を
判断する基準を、`issue-mr-flow` スキルのドキュメント一式へ定義する。あわせて判断の経緯・却下案を
DDRへ記録し、関連specへ反映する。

## 背景（issueの現状認識）

- 別issueへの切り出しに触れているのは `【実装反映】` 定義（`references/planning.md`）の1文だけで、
  参照先「issueが大きすぎる場合の分割提案」（issue #64）は**着手前のissue粒度**を判定する基準
  （主トリガーが並列列挙構造）である。フェーズ4で拾う反映対象は列挙構造を持たないことが多く、
  この基準ではほぼ判定できない。
- issue #155（PR #175）が「AIアセット反映の対象の洗い出し」節を新設し、**反映対象を4類型
  （a）〜（d）へ分類する手順**まで定めた。本issueは、その分類結果に対して
  「このMRでやるか、別issueへ送るか」を決める部分を担う（両者は重ならず接続する）。

## 変更対象（領域の粒度）

| 領域 | 変更の種類 | 概要 |
|---|---|---|
| `.claude/skills/issue-mr-flow/references/planning.md` | 変更（新節の追加＋既存1文の差し替え） | 切り出し判断の節を新設し、`【実装反映】` 定義の参照先を新節へ向け直す |
| `.claude/skills/issue-mr-flow/SKILL.md` | 変更 | flow-id 4-1／4-6 の行から新節を指す（フロー定義側の入口） |
| `.claude/docs/ddr/` | 新規 | `i0176-01-…`（判断基準の設計判断と却下案）。`generate-ddr-list.sh` で一覧を再生成 |
| `.claude/docs/spec/issue-mr-workflow.md` | 変更 | 仕様側への反映 |
| `.gemini/` | 生成物の再生成 | flow-id 5-3 で `sync-gemini-assets.sh` を流す |

## 方針

- 基準の**正は1箇所**に置く（issue本文の受け入れ条件が求める「二重管理をしない」）。
  issue #160 で SKILL.md の詳細節は `references/` 配下へ切り出されているため、基準の本体は
  `references/planning.md` へ置き、SKILL.md（フロー定義）からは参照だけを張る。
  **この読み替えの妥当性はフェーズ2で確認する**（受け入れ条件の文言は「SKILL.md に節がある」）。
- 既存の「issueが大きすぎる場合の分割提案」（issue #64）とは**判定タイミングと入力が違う**ため、
  節を統合せず並置し、相互に「どちらを使うか」を1行で示す。
- AIは提案までとし、決定は人間が `AskUserQuestion` で行う（issue #64 と同じ扱い）。

## フェーズ2〈調査〉

次の問いに答える。**実施する。**

1. 受け入れ条件の「SKILL.md に節がある」を、issue #160 の分割後の構造でどう満たすのが正しいか
   （SKILL.md 本体へ書く／`references/planning.md` へ書いて SKILL.md から指す）。
2. 差し替え対象の「既存の1文」は具体的にどこか。差し替えたとき、`【実装反映】` 定義の他の記述と
   矛盾しないか。
3. issue #155 の4類型（a）〜（d）と、切り出し判断の主判定はどう接続するか。類型ごとに
   判断が変わるのか、類型に依らず同じ一問で足りるのか。
4. 過去のDDRに残る「別issueの規模と判断して見送った」個別事例（i0000-02・i0023-01・i0014-01 等）は、
   検討中の基準で同じ結論になるか（基準の妥当性検証）。
5. 「切り出さない条件（誤爆防止）」の固定費は何ステップか。既存記述（issue #64 の「5フェーズ43
   ステップ」）と数字が揃っているか。
6. 切り出した／切り出さなかった判断の**記録先**は、既存のどのファイル・節か。

## フェーズ3〈作業〉

`【AIアセット作成】` として、`references/planning.md` への新節追加と、SKILL.md・
`【実装反映】` 定義からの参照張り替えを行う。調査結果を受けて着手する。

## フェーズ4〈反映〉

反映対象は flow-id 4-1 で洗い出す。現時点の見込みは次のとおり（確定した反映内容ではない）。

- **設計反映**: DDR `i0176-01`（主判定を一問へ集約した理由・却下案）と、
  `.claude/docs/spec/issue-mr-workflow.md` への反映。DDR追加後は
  `bash .claude/scripts/src/generate-ddr-list.sh` を実行して一覧を再生成する。
- **AIアセット反映**: 作業の副産物として気づいた不備があれば、flow-id 4-1 の洗い出し手順
  （`references/planning.md`「AIアセット反映の対象の洗い出し」手順1〜2）に従って分類する。

## やらないこと（スコープ外）

- **既存の「issueが大きすぎる場合の分割提案」（issue #64）節の書き換え**。判定タイミングが違う
  別の基準であり、統合すると issue #64 の決定を上書きすることになる。相互参照の1行追加までに留める。
- **フェーズ2・3で見つかった反映対象を、この基準に従って実際に別issueへ切り出すこと**。
  今回のissueの成果物は基準そのものであり、基準の適用は次タスク以降。
  ただし flow-id 4-1 で自分自身に適用してみることは、基準の妥当性検証として行う。
- **`.claude/scripts/` へのスクリプト追加**（判断は人間が行うため、機械化しない）。

## 検証

- issueの受け入れ条件3つがすべて満たされていること。
- `bash .claude/scripts/src/check-doc-references.sh` で参照切れがないこと。
- `bash .claude/scripts/src/generate-ddr-list.sh` の差分が同じコミットに含まれていること。
- `bash .claude/scripts/src/sync-gemini-assets.sh --check` が通ること（flow-id 5-3）。

## 進め方の前提（このセッション固有）

- 非対話セッションのため、人間のレビュー往復（2-3/2-8/3-3/3-8/4-3/4-8）は成立しない。
  代わりに**各フェーズの計画時と作業実施時に1回ずつ敵対的レビューを自動起動**し、指摘へ対応する
  （ユーザーからの明示指示）。実施回数は `adversarial-review-count.sh` が各フェーズ最大3回で強制する。
- ブランチ名はハーネス指定の `claude/reflection-plan-criteria-tnhfvs` を使う
  （`.mrworkflow.json` の `feature-<issue番号>-<slug>` 規則とは異なる）。
