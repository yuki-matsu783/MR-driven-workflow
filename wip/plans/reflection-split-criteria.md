# 全体作業計画 — 反映対象の「このMRで対応するか別issueへ切り出すか」の判断基準（issue #176）

## この計画で何をするか

フェーズ4〈反映〉で洗い出した反映対象について、「このMRで対応するか、別issueへ切り出すか」を
判断する基準を、`issue-mr-flow` スキルのドキュメント一式へ定義する。あわせて判断の経緯・却下案を
DDRへ記録し、関連specへ反映する。

## 背景（issueの現状認識）

**「別issueへの切り出し」に触れている記述は、`.claude/skills/` `.claude/rules/` 配下に
実測10行ある**（`grep -rn -- '別issue' .claude/skills .claude/rules`。`.gemini/` は生成物なので
除く）。うち**issue #64 の「issueが大きすぎる場合の分割提案」を切り出しの基準として指しているのは
次の3箇所**で、残る7行は「起票と着手を同じセッションでやらない」（`issue-create/SKILL.md:82,123`・
`start-resume.md:27`）・記録やテンプレートの例示（`phase5-close.md:290`・`review-loop.md:82,190`・
`plans.template.html:271`）であり、基準を指してはいない。

| # | 場所 | 何を判定しているか | 本issueの対象か |
|---|---|---|---|
| 1 | `references/planning.md:93`（`【実装反映】` 定義の末尾） | **フェーズ4の反映対象**を切り出すか | **対象**（差し替える） |
| 2 | `SKILL.md:76`（flow-id 2-6） | フェーズ2で規模が判明したときに**issueの未着手範囲**を切り出すか | 対象外（issue粒度の話であり #64 のままでよい） |

- **issue本文は「触れているのは1文のみ」と書いているが、これは1の意味では正しく、
  「切り出し」全般では正しくない。** 2・3は**別の判定**（issueそのものの粒度）なので、
  新節へ寄せずに #64 側へ残す。ただし読み手がどちらを使うか迷わないよう、**新節と #64 節に

  『着手前か後か』ではなく『何を割るか』（issueそのものか、フェーズ4の反映対象か）である。**
- issue #155（PR #175）が「AIアセット反映の対象の洗い出し」節を新設し、**反映対象を4類型
  （a）〜（d）へ分類する手順**まで定めた。本issueは、その分類結果に対して
  「このMRでやるか、別issueへ送るか」を決める部分を担う（両者は重ならず接続する）。

## 方針

- 基準の**正は1箇所**に置く（issue本文の受け入れ条件が求める「二重管理をしない」）。
  issue #160（DDR `i0160-01`）は SKILL.md 本体に残すものを「全体フロー表・PR/MR担当・
  詳細ルールへのポインタ・前提・旧節名の対応表」と定め、詳細は `references/` 配下へ移している。
  同型の既存節（「issueが大きすぎる場合の分割提案」）も `references/planning.md` にある。
  **したがって基準の本体は `references/planning.md` へ置き、SKILL.md からは参照だけを張る。**
  受け入れ条件の文言「SKILL.md に節がある」は issue #160 以前の構造を前提としたものと読み替える
  （**この読み替えの妥当性はフェーズ2の問い1で裏取りする。** 裏取りの結果しだいで SKILL.md 本体へ
  置く形もありうる）。
- 既存の #64 節とは**判定の対象が違う**（issueそのもの／フェーズ4の反映対象）ため、節を統合せず
  並置し、相互に「どちらを使うか」を1行で示す。
- AIは提案までとし、決定は人間が `AskUserQuestion` で行う（#64 と同じ扱い）。

### 既存の記述を置き換える箇所（置換前・置換後）

**置換前**（`references/planning.md` の `【実装反映】` 定義の末尾1文）:

> 対応が1issueに収まらない規模になった場合は、下記「issueが大きすぎる場合の分割提案」の基準に
> 従い別issueへの切り出しを検討する。

**この1文は2つの役割を兼ねている。**

| 役割 | 内容 | 置換後の扱い |
|---|---|---|
| (i) 行為の指示 | 「規模が1issueに収まらないなら切り出しを検討する」 | **新節へ引き継ぐ。ただしトリガー条件を言い直す**（下記） |
| (ii) 参照先の提示 | 「基準は #64 節にある」 | 新節への参照へ差し替える |

**(ii) の差し替えだけでは足りない。** (i) のトリガーは「規模」だが、新節の主判定は
`main` の整合性を先に問う予定であり、規模は二次的な条件（切り出さない条件）へ移る。
**規模をトリガーのまま残すと、規模が大きいという理由だけで必須の反映が先送りされる。**
置換後の文面はフェーズ3で確定させるが、この役割の分解自体はここで固定する。

## フェーズ2〈調査〉

次の問いに答える。**実施する。**

1. 受け入れ条件の「SKILL.md に節がある」を、issue #160 の分割後の構造でどう満たすのが正しいか
   （SKILL.md 本体へ書く／`references/planning.md` へ書いて SKILL.md から指す）。
2. 差し替え対象の1文（上記「置換前」）を差し替えたとき、`【実装反映】` 定義の他の記述と
   矛盾しないか。`【AIアセット反映】` 側から新節を指す必要はあるか。
3. issue #155 の4類型（a）〜（d）と、切り出し判断はどう接続するか。類型ごとに判断が変わるのか、
   類型に依らず同じ一問で足りるのか。
4. 過去のDDRに残る「規模を理由に見送った」事例に、フェーズ3で検討する主判定の候補を当てると
   同じ結論になるか（基準の妥当性検証）。**母数の取り方は個別調査計画で決める**
   （issue本文は `i0000-02`・`i0023-01`・`i0014-01` を挙げているが、**`i0014-01` は
   「別issueの規模」を理由とした見送りではない**——本文に「別issue」「見送」「規模」のいずれも
   現れず、最も近い記述は「本issueのスコープ外とし、ドキュメントでの明記に留める」という
   スコープ限定である。「等」で曖昧にせず、機械的に洗い出した集合を母数にする）。
5. 新節で固定費（フローのステップ数）を**再掲するのか、既存記述への参照で済ませるのか**。
   実数は43で `references/planning.md:224` と一致しており調べる必要は無いが、同じ数字は
   `SKILL.md:44`・`.claude/rules/docs-workflow.md:24`・`.claude/docs/usecase/` にも複製され、
   過去に 40→43 と繰り下がっている（`i0064-01:25`・`i0092-01:52` は当時の値のまま。
   point-in-time の記録なので書き換えない）。**複製をもう1つ増やすかどうかを決める。**
6. 切り出した／切り出さなかった判断の**記録先**は、既存のどのファイル・節か。

## フェーズ4〈反映〉

反映対象は flow-id 4-1 で洗い出す。現時点の見込みは次のとおり（確定した反映内容ではない）。

- **設計反映**: DDR `i0176-01` と、`.claude/docs/spec/issue-mr-workflow.md` への反映。
  DDRの主題（何を決めた記録にするか）はフェーズ2・3の結論が出てから決める。DDR追加後は
  `bash .claude/scripts/src/generate-ddr-list.sh` を実行して一覧を再生成する。
- **AIアセット反映**: 作業の副産物として気づいた不備があれば、flow-id 4-1 の洗い出し手順
  （`references/planning.md`「AIアセット反映の対象の洗い出し」手順1〜2）に従って分類する。

## やらないこと（スコープ外）

- **既存の #64 節の判定基準そのものの書き換え**。判定の対象が違う別の基準であり、統合すると
  issue #64 の決定を上書きすることになる。**相互参照の1行追加までに留める。**
- **`SKILL.md:76`（flow-id 2-6）の切り出し記述の変更**。これはissue粒度の判定であり #64 の担当
  （上記「背景」の表の2）。
- **フェーズ2・3で見つかった反映対象を、この基準に従って実際に別issueへ切り出すこと**。
  今回のissueの成果物は基準そのものであり、基準の適用は次タスク以降。
  - **ただし flow-id 4-1 で自分自身へ適用してみることは、基準の妥当性検証として行う。**
    その結果が「切り出す」側へ倒れた場合は、**妥当性検証の材料として `wip/reports/` の反映結果へ
    記録するに留め、実際の切り出しは `AskUserQuestion` で人間へ諮る**（AIの独断では起票しない。
    #64 の「決定は人間が行う」と同じ）。人間の応答を得られない非対話セッションでは、
    **起票せず、記録と最終応答での明示に留める。**
- **`.claude/scripts/` へのスクリプト追加**（判断は人間が行うため、機械化しない）。

## 検証

**受け入れ条件ごとに、変更前は0件・変更後は1件以上になる検査を置く。** 数える語は、見出し・目次に
既出の構造語（「切り出し」「判断基準」）を避け、新節に固有の語を選ぶ。

```bash
# 受け入れ条件1: 切り出し判断の節がある（新節に固有の語を含むファイル数を数える）
grep -rl -- '見送ってマージ' .claude/skills/issue-mr-flow/ | wc -l

# 受け入れ条件2: 【実装反映】定義からの参照が新節を指している
#   変更前は「issueが大きすぎる場合の分割提案」を指す1行がヒットする
sed -n '/\*\*`【実装反映】`\*\*/,/^### /p' .claude/skills/issue-mr-flow/references/planning.md \
  | grep -c -- 'issueが大きすぎる場合の分割提案'

# 受け入れ条件3: DDRとspecへの反映
ls .claude/docs/ddr/i0176-*.md
grep -c -- 'issue #176' .claude/docs/spec/issue-mr-workflow.md

# 常時の健全性（この変更で壊していないこと）
bash .claude/scripts/src/check-doc-references.sh
bash .claude/scripts/src/generate-ddr-list.sh
bash .claude/scripts/src/sync-gemini-assets.sh --check
```

**着手前に、変更前のツリーで上の3本を実行して期待どおりの値（1本目=0、2本目=1、3本目=ls失敗かつ
grep=0）になることを確かめる。** 確かめた結果は個別作業計画（flow-id 3-1）へ記録する。

合格条件: 変更後に 1本目が1件以上、2本目が0、3本目の `ls` が成功しかつ `grep` が1件以上。
常時の健全性3本がいずれも変更前と同じ結果（参照切れ0件・DDR一覧の差分なし・`.gemini/` 同期済み）。

## 進め方の前提（このセッション固有）

- 非対話セッションのため、人間のレビュー往復（2-3/2-8/3-3/3-8/4-3/4-8）は成立しない。
  代わりに**各フェーズの計画時と作業実施時に1回ずつ敵対的レビューを自動起動**し、指摘へ対応する
  （ユーザーからの明示指示）。実施回数は `adversarial-review-count.sh` が各フェーズ最大3回で強制する。
- **ブランチ名はハーネス指定の `claude/reflection-plan-criteria-tnhfvs` を使う**
  （`.mrworkflow.json` の `feature-<issue番号>-<slug>` 規則からの逸脱）。
- **planツール（Planモード）を使えない実行環境のため、この全体作業計画は Write で作成し、
  ファイル名は内容から付けた**（`wip/plans/REVIEW-POINTS.md` が求める「ハーネスの提示した
  自動命名のまま」からの逸脱）。worklog・reports のファイル名もこの名前に揃えてある。
