調べること（問い）

Q1. 現行の規約はどこで・どう述べられているか

2種類ある。両方を洗わないと全件リストにならない。

種類探し方
(a) 規約の地の文grep -rn '1行のみ\|本文・フッター\|フッター' --include='*.md' .claude AGENTS.md CLAUDE.md GEMINI.md
(b) 旧規約に沿った例示・雛形grep -rn -- '--message "' --include='*.md' --include='*.sh' .claude（(a) の検索語では1件も拾えない。実例: .claude/skills/resolve-conflict/SKILL.md のマージコミットの雛形）

対象は .claude/ 配下すべて・AGENTS.md・CLAUDE.md・GEMINI.md・.gemini/（変換生成物なので直接の書き換え対象ではないが、同期漏れの検出に使う）。本文中の言い回しを探す問いなので、frontmatterインデックス検索ではなく grep を使う（AGENTS.md の使い分け）。

出力: ファイル・行番号と、「規約として述べている」「他所を参照しているだけ」「例示・雛形」の区別。

Q2. 実際のコミットログの欠落パターン

母数を固定する: git log origin/main -5 --format='%B' が出す直近5件のsquashコミットと、その本文に畳まれた ^* 行（80行。数え直しの起点にする）。さらに main の1行ログは git log origin/main -10 --format='%s' の10件を見る。

issue本文の4類型（(a) 対象しか分からない／(b) どう直したか分からない／(c) 事務的作業記録／(d) mainに残らない対象）で分類し、4類型に収まらない例があるかを確認する。1行が長すぎる例・列挙で中身が削れている例の実数も数える。

出力: 類型ごとの件数（母数80に対する数として書く）と代表例。件数は分類に使ったコマンドとともに示し、自分で数え直す。

Q3. 本文を許容した場合、実装・呼び出し側は耐えられるか

2つに分けて調べる。前者だけを確かめても「実装変更が要らない」とは言えない。

  1. create-commit.sh が複数行メッセージを受け付けるか: --message) message="$2" と git commit -m "$message" を読み、一時リポジトリで実際に改行入りメッセージをコミットして確認する。
  2. 複数行メッセージをどの経路で渡すか: create-commit.sh は --message-file 相当の入口を持たない。--message へ埋め込むとBashツールへ渡すコマンド文字列に改行ごと載るため、次の既知の制約に触れる。
    • .claude/docs/spec/command-position.md のコマンド位置判定が、クォート内の改行をどう正規化するか。
    • 1行8192バイト超で判定が部分一致へ縮退する（.claude/rules/git-workflow.md「コミット運用」）。
    • 長文はコマンド文字列へ直接埋め込まずファイル経由で渡すという既存方針（Provider.sh の set_mr_description がファイルパスを取る設計）。

出力: 実装変更（--message-file の新設等）が要るか／要らないか。要らないと結論する場合は、上の3つの制約それぞれについて理由を示す。

Q4. squash merge時に本文はどう畳まれるか

実測できる部分と実測できない部分に分かれる 区別して答える。
部分手段根拠の性質
main の1行ログに何が出るかgit log origin/main --format='%s' を読む実測（既存の履歴）
個別コミットの件名がsquash本文へどう並ぶか同上（%B を読む）実測（既存の履歴）
gitの --squash が本文をどう畳むか一時リポジトリで本文付きコミットを作り git merge --squash → .git/SQUASH_MSG を読む実測
GitHubのsquash mergeが本文をどう畳むか実測できない——現行規約が1行のみを強制してきたため、main の履歴に本文を持つコミットが1件も無い。squash本文の生成はGitHubのサーバ側の挙動で、ローカルの git log では再現できない机上確認（実測できないことを明記する）

出力: 本文を許容した場合に main の1行目・本文へ何が残るか。GitHub側の畳み方が未確認でも判断が止まらないこと（＝方針がこの答えに依存していないこと）を確認する。

Q5. 規約を変えると壊れる／古くなる箇所はあるか

対象を2つに分ける。

  • 処理: .claude/scripts/ .claude/hooks/ で、コミットメッセージを検索・パースしている箇所（git log --grep、prefixでの分岐等）。
  • 記述: .claude/skills/ .claude/rules/ .claude/docs/ で、コミットメッセージの例示・雛形・書き方の指示を持つ箇所（Q1の(b)と重なる。resolve-conflict スキルの「何を」「どう」解消したかを書く規約、issue-mr-flow/SKILL.md の「確認した結果をコミットメッセージへ必ず残す」等）。

出力: 壊れる処理の有無と、追随が要る記述の一覧。

手順

  1. Q1: 上表の2つの grep を実行し、表にする。
  2. Q2: git log origin/main -5 --format='%B' | grep '^* ' を母数（80行）として分類・計数する。
  3. Q3: create-commit.sh を読んだうえで、一時リポジトリで複数行メッセージを実際にコミットし、さらに渡し方を上記3制約に照らして判断する。
  4. Q4: 既存のsquashコミット本文を読み、git merge --squash を一時リポジトリで実行する。GitHub側の畳み方は机上確認に留め、その旨をレポートへ書く。
  5. Q5: 処理と記述の2系統をそれぞれ grep -rn で洗う（処理側の検索パターンは 'git log\|--grep\|%s\|%B'）。
  6. 結果を wip/reports/ のmd・htmlへ記録し、wip/worklogs/ に試行錯誤を残す。
