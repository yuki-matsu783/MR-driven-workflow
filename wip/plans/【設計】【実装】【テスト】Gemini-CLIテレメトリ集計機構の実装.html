フェーズ2報告からの更新点（重要）

重要: .gemini/settings.jsonは手編集対象ではなくなった

フェーズ2報告5〜7節は「.gemini/settings.jsonを手で編集する」前提だったが、defaultブランチ追従で取り込んだPR #157（issue #70）により.gemini/は.claude/からの変換生成物になっている。手編集してもsync-gemini-assets.shの次回実行で失われる。

生成ロジック（convert_settings() / SETTINGS_JQ_FILTER）には、Claude Code側に存在しない設定（telemetry）を注入する仕組みが元々無いため、本計画で新設する。既存のSETTINGS_IGNORED_KEYSのenvキーには「Claude Code側OTelリスナー（.claude/hooks/otel/listener.pl）へGemini由来のテレメトリを流すと壊れるため変換しない」という既存判断があるが、本計画の注入（target: "local"固定・outfileへ直接書き込み、リスナーを経由しない）はこの判断と衝突しない。理由は3点: (1) Claude Code側のenvブロックは一切参照しない、(2) telemetry.targetは"local"固定でOTLPネットワーク受信を経由しない、(3) SETTINGS_IGNORED_KEYSは「変換しないキー」の記録であり「新規キーを固定値で追加すること」を妨げない。

この計画で何をするか

フェーズ2報告の8方針を、設定層（.gemini/settings.json生成へのtelemetry注入）・集計層（UsageTracking.shへのバイトオフセットカーソル集計関数群）・レポート層（post-push-usage-report.shへの別セクション追加）の3層で実装し、単体テストを追加する。あわせて配布先.gitignoreへの/usage/追記漏れを是正する。

方針

1. .gemini/settings.jsonへのtelemetry注入

sync-gemini-assets.shのSETTINGS_JQ_FILTERの出力へ、次の値を固定で追加する。enabledはfalse固定で注入する（下記の理由）。

{
  "telemetry": {
    "enabled": false,
    "target": "local",
    "outfile": "usage/gemini-otel.log",
    "logPrompts": false
  }
}
enabled: false固定とし、本計画の範囲では有効化しない

フェーズ2報告7.節の結論は「保留」（配布先gitignore是正・tool_call機微情報確認の2条件が揃うまでON化しない）であり、実機確認前に既定ONへ倒すのはこの結論と矛盾する。

利用者による手動有効化は前提にしない。.gemini/settings.jsonは生成物であり、手編集しても次にsync-gemini-assets.shが走った時点（flow-id 5-3が毎タスクで通る）で無言でfalseへ戻り、さらに--checkが「生成物と一致しない」として失敗するようになる。したがって「利用者が手でtrueにする」運用は成立しない。

有効化の手段（GEMINI_TELEMETRY_ENABLED環境変数を使うか、.claude/settings.json側に有効化フラグを持たせて変換するか等）は本計画では決定せず未決定事項へ回す。有効化手段が無いままでも、enabled: false固定の配線自体（target/outfile/logPromptsの用意）は次のissueの土台として意味を持つため、本計画のスコープとして進める。

受け入れ条件1（telemetry設定によりファイルが生成・追記される）は、本計画の実装だけでは有効化できないため確認できない。人間の実機確認ではtelemetry.enabledを検証用に一時的にtrueへ書き換えてもらう手順が必要になる（後述「人間への実機確認依頼」）。

outfileは相対パスusage/gemini-otel.logとする。相対パスの解決基準（cwd基準かプロジェクトルート基準か）は未確認のまま採用する。解決基準がcwd基準だった場合、サブディレクトリでGemini CLIを起動すると<subdir>/usage/gemini-otel.logが作られ、配布先.gitignoreへ足す/usage/（先頭スラッシュ＝リポジトリルート限定）の対象外になり、プロンプト・tool_call由来の機微情報を含みうるファイルがgit statusに現れる可能性がある。この解決基準は人間への実機確認依頼に含める（依頼項目6）。確認できるまでは受け入れ条件6を「本リポジトリでは対応済み・配布先での解決基準は未確認」として扱う。

SETTINGS_IGNORED_KEYSのenvキーに付与されている既存コメント（「Gemini CLI経路では対応工数のOTel計測が行われない」旨）は、本変更によりその帰結が変わる。コメントを「envブロックの変換は行わないが、telemetryブロックは固定値で注入する（issue #105）」の趣旨へ更新する（同じファイルの中に相反する説明を残さないため）。

2. バイトオフセットカーソル集計

フェーズ2報告4.節の設計をそのまま実装する。新規関数（案）:

  • _usage_read_otel_cursor / _usage_write_otel_cursor: usage/state/gemini-otel/cursor.jsonの読み書き（サブディレクトリを切る。直下に置くとusage/state/<branch>.jsonのブランチ別状態ファイル名と、同名のブランチが存在した場合に完全一致し内容を壊し合う可能性があるため）。空・不正JSONへの自己回復は既存の_usage_read_gemini_totalsと同じパターン
  • _usage_otel_fold: outfileの新規バイトから、完全にパースできた末尾までを処理する。
    • エントリ境界の検出方法: シリアライズ形式（safeJsonStringify(data, 2) + '\n'、インデント2のpretty-print JSON＋末尾改行1つ）を前提に、行頭（列0）が}で始まる行の直後を1エントリの終端とみなしてバイト単位で切り出す。この方式は出力形式に依存する実装依存の判定であり、Gemini CLI側の出力形式が変わると壊れるリスクをspec側に明記する（フェーズ4）
    • metricsを除外する（10秒間隔で周期exportされるため）
    • 同一イベントの2重emit（toLogRecord/toSemanticLogRecord）には、semantic conventions形式のみを採用しレガシー形式は集計対象から除外する方式を既定として採用する
  • 境界をまたぐ二重計上への対処: 2エントリが別々の読み取り窓に分かれるケースでも、semantic conventions形式のみを採用したことで原理的に二重計上は発生しない（判別方法の実データでの裏取りは未決定事項）
  • 初回集計（カーソル0）での全量計上: outfileはローテーション無しの無制限追記のため、有効化してから初めてレポートが走るまでに複数日分のデータが溜まっている可能性がある。初回もカーソル0から通常どおり全量を計上する（末尾へ合わせて0件扱いにする特別扱いはしない）
  • ファイル縮小検知: DDR i0097-01のneedsResetと同じ考え方でカーソルを0へリセット
  • _sync_usage_state_otel: 上記を統合。既存のsync_usage_state（Claude Code経路・Gemini経路）とは完全に独立し、既存関数のシグネチャ・返り値は変更しない

3. post-push-usage-report.shへの統合

_sync_usage_state_otelの呼び出しはengineによる分岐ではなく、outfileが存在するかどうかで判定する（既存呼び出しとは別）。既存の設計判断（「トークンテーブルの列構成はengineではなくデータで決める」issue #97）と整合させるため。engine分岐だと、Gemini CLIでの作業後にClaude Code側の操作でpushが起きた場合にテレメトリ分の新規バイトが読まれず、未処理バイトが次にengine=geminiでpushした回へずれて計上されてしまう。

build_usage_report_bodyへ新しい引数（テレメトリ集計結果）を追加する際は、既存の呼び出し（現在5引数）を壊さないよう新引数は"${6:-}"のように既定値付きで受ける（既存テストが5引数のまま直接呼んでおり、単純に受けるとset -uで失敗するため）。結果があれば「### Gemini CLI公式テレメトリ（参考値）」セクションを追加し、既存のtokensByModelへは合算しない。

4. 配布gitignore是正

install-to-project.shのignore_rules配列は実ファイル確認の結果3要素（/.claude/usage-state/ /.claude/session-logs/ /.claude/settings.local.json）である。先頭2つは旧パス名だが、3つ目は旧パスではなく issue #70 で意図的に配っている現行の行。この3要素の末尾へ/usage/を追加する（既存の3行は削除しない）。test_install_to_project.shに、配布先.gitignoreへ/usage/が1行入ることを実際に確認するケースを1件追加する。

5. テストフィクスチャ

フェーズ2報告の方針（safeJsonStringify(data, 2) + '\n'形式）に沿ったヒアドキュメントを追加する。以下の7項目を含める: 正常系（2重emitのうちsemantic形式のみ計上）、境界またぎ2重emit（読み取り窓をまたいでも二重計上しない）、metrics混在（除外）、カーソル継続、初回集計（既存データありでも全量計上）、ファイル縮小、状態ファイル破損、途中書き込み、レポート本文（既存セクション不変・5引数呼び出し無改修）。
