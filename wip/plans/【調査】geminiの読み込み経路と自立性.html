調べること

Q7: Gemini CLI の読み込み経路（ドキュメントの精読）

  • skills/ の探索規則・優先順位・SKILL.md の形式要件（必須 frontmatter キー）
  • agents/ の探索規則・ファイル形式の要件
  • .agents/skills/ エイリアス: 探索されるか／.gemini/skills/ との優先順位／Claude Code 側も同じパスを見るか（見ないなら第3の道は成立しないので、ここは要確認）
  • context.fileName で AGENTS.md を読ませられるか（GEMINI.md を介さない経路の有無）
  • 答え方: 該当ドキュメントのパスと引用を添える。「たぶんそう」は書かない。

Q8: 現在の .gemini/skills/ .gemini/agents/ はそのまま使えるか

  • 9つの SKILL.md の frontmatter が、Agent Skills 標準の必須キーを満たすか（件数で）
  • agents/*.md 2本が Gemini CLI の localAgentSchema を満たすか
  • 満たさない場合、sync-gemini-assets.sh の変換で埋まるか、追加の変換が要るか

Q9: 自立させる場合に必要な変更の全量

374件の内訳を書き換えてよいもの／いけないものへ分類する。分類の軸は次の4つ。

#分類扱い
1実行パス（bash .claude/scripts/…・source …）書き換え対象
2ドキュメント参照（.claude/docs/spec/… へのリンク）書き換え対象（リンク先が .gemini/ にも複製されている場合に限る）
3事実の記述（git ls-files -- .claude・.claude/VERSION・生成の仕組みの説明）書き換えると嘘になる
4編集先の指示（「編集は常に .claude/ 側へ行い」）書き換えると有害
  • 各分類の件数を出す。 分類が機械的に判定できるか（できないなら自立化の実装コストは「374件の一括置換」では済まない）も答える。
  • hooks の実体・scripts の実体・rules の import 元をどうする必要があるか。
  • DDR本文・過去changelog の一括置換は .claude/rules/docs-workflow.md が禁止している。 .gemini/docs/ddr/ が対象に含まれるかを確認する（含まれるなら自立化と既存ルールが衝突する）。

Q10: 依存を明示する場合に必要な変更

  • 「Gemini CLI 利用時も .claude/ は必須」をどこへ書くか（spec・README・.gemini/ 側の案内ファイル）。候補と、それぞれが読まれる経路を出す。
  • 読まれない複製（rules/ docs/ hooks/ scripts/）をやめると何が壊れるか。Q3・Q4 の実測値をそのまま使う（再測定しない）。
  • .gemini/ に残るのが settings.json skills/ agents/ だけになった場合のファイル数・バイト数（1回目の実測から算出）。

Q11: 配布への影響

  • install-to-project.sh 手順7・dist-layers.json は2つの方向それぞれでどう変わるか。
  • 配布先が片方のCLIしか使わない場合の手順が成立するか。
    • Claude Code のみ: .gemini/ を生成しない選択肢はあるか
    • Gemini CLI のみ: .claude/ を消せるか（自立化しない限り消せないはず。確認する）
