論点1は決着した（自立化の要件は取り下げ）

ユーザー判断（2026-08-23）

AGENTS.mdで.claudeのパスを指定している時点で、.gemini配下の資産だけで動かすのは現実的じゃないことに気が付いた。その要件については取り下げでお願いしたい

根拠は構造的である。 AGENTS.md はリポジトリルートにあり、dist-layers.json で layer: seed——どのCLIを使う配布先へも常に配られる。その中身が @./.claude/rules/agent-common.md を import しているため、.gemini/ 配下だけを残しても共通ルールが読めない。.gemini/ の中を何件書き換えても、この依存はルート側に残る。

したがって論点1は「.claude/ への依存を明示する」で確定とし、この計画から次を落とす。

落とすもの理由
Q9（自立させる場合に必要な変更の全量）自立化しないので不要。392件の分類も行わない
「論点1の判定基準」節決着したので判定が要らない
.claude/… → .gemini/… のパス書き換え（ユーザーの以前の提案）自立化のための変更だったため、あわせて取り下げ

残る論点は2つ。

  1. 読まれない4ディレクトリ（rules/ docs/ hooks/ scripts/）の扱い（＝元の issue #172 の問いに rules/ を足したもの）
  2. .agents/skills/ エイリアスを使うか——自立化とは独立した論点として残る。Claude Code 側も同じパスを見るなら、.claude/skills/ と .gemini/skills/ の二重管理をやめられる。ただし優先度は下がる（Q7で成立するかだけ確かめる）。

事実Eの数え方（数字を引用するときの前提）

# (a) パス文字を伴う参照だけを数える（366 / 8）
grep -rho '\.claude/[^ )`"'"'"']*' .gemini/skills/ | wc -l
grep -rho '\.claude/[^ )`"'"'"']*' .gemini/agents/ | wc -l
# (b) `.claude/` の全出現を数える（384 / 8）
grep -rho '\.claude/' .gemini/skills/ | wc -l
grep -rho '\.claude/' .gemini/agents/ | wc -l
  • 単位は出現数（行数でもファイル数でもない）。対象は .gemini/skills/ .gemini/agents/ 配下の全ファイル（skills は md 24ファイルのうち .md 299・.template 43・.sh 32・.html 10）。
  • 差の18件は「.claude/ 配下」のようにパス文字を伴わない言及である。自立化を取り下げたため、この件数はもう「書き換える対象の規模」ではない。 依存の大きさを示す参考値として残す（引用するときは (a)(b) のどちらかを明示する）。
  • 「374件」という数字を使わない。 これは (a) の 366+8 の合計だが、偶然にも「skills 単独・HTML除外」の値（299+43+32=374）と一致するため、どちらの意味か読み手が取り違える（実際に敵対的レビューで取り違えが起きた）。

Q10: 依存の明示と、読まれない複製の扱い（この調査の主軸）

  • 「Gemini CLI 利用時も .claude/ は必須」をどこへ書くか（spec・README・.gemini/ 側の案内ファイル）。候補と、それぞれが読まれる経路を出す。
  • 読まれない複製4つ（rules/ docs/ hooks/ scripts/）を外した場合に切れるリンクを実測し直す。 1回目の Q4 は3つを外した場合の値なので使えない。
    • 採否レポートの軸2の18件は内訳が rules/ 17・skills/ 1 である。rules/ も外せばその17件はリンク元ごと消えるので「壊れたリンク」ではなくなり、残るのは skills/ の1件だけになるはずである。この見立てが正しいかを実測で確かめる（18件をそのまま持ち込むと17件過大に見積もる）。
    • 残る1件は読まれる .gemini/skills/ の中にあるため、1回目とは性質が違う。
  • .gemini/rules/ とトップレベルファイルのファイル数・バイト数を新たに実測する。 1回目の Q6 は hooks/（14/217,308）・scripts/（47/813,984）・docs/（115/1,456,431）・3つの合計（176/2,487,723）・.gemini/ 全体（215/3,159,948）の5行しか持たず、rules/ とトップレベルの内訳が無いので「1回目の実測から算出」はできない（215−176＝39ファイルに rules/・skills/・agents/・トップレベルが混ざっている）。
  • そのうえで、.gemini/ に残るのが settings.json skills/ agents/ だけになった場合のファイル数・バイト数を出す。

Q11: 配布への影響

  • install-to-project.sh 手順7・dist-layers.json は、論点2の結論（複製を外す／残す）に応じてどう変わるか。
  • 配布先が片方のCLIしか使わない場合の手順が成立するか。
    • Claude Code のみ: .gemini/ を生成しない選択肢はあるか
    • Gemini CLI のみ: .claude/ は消せない（論点1の決着により確定）。この事実を配布時にどう伝えるか（install-to-project.sh の出力・README等）
  • ルート直下のファイルの帰属（CLAUDE.md GEMINI.md AGENTS.md .mrworkflow.json REVIEW-POINTS.md 等）はどうなるか。dist-layers.json では CLAUDE.md・GEMINI.md が core、AGENTS.md が seed で、どのCLIを使う配布先へも常に配られる。事実Bの依存の連鎖も起点2つ（GEMINI.md・AGENTS.md）はルートにあり、「.claude/ 単体／.gemini/ 単体」という言い方はルート直下を含んでいない。この帰属を決めないと、受け入れ条件の「両方向について記録されている」を満たせない。
  • 「両方向」の記述が受け入れ条件を満たす形になっているか。 .claude/ 単体は動き、.gemini/ 単体は動かない——この非対称を、ルート直下のファイルまで含めて言い切れるか。

検証項目確かめ方

判断が混入していない下記の語で検査する

「判断をしていない」の検査は、探す語を先に列挙する（異常が無ければ何も出ない形の検査は、語が実データに現れない限り常に成功してしまうため）。

grep -nE '採用する|採る|を選ぶ|が妥当|結論として|決めた|すべきである' "$R"
  • ヒットが0でも「判断していない」とは結論しない。意図的に「案Aを採用する」という1行を混ぜて、この検査が実際に検出することを確かめてから、その行を消す。
  • 検出できないなら、語の列挙が実データに合っていない（列挙を足す）。
