# 【調査】デザイン4案のテンプレート化方針（issue #203 / flow-id 2-1）

## 前提（合意状況）

- 上位の計画: `wip/plans/silver-drifting-lantern.md`（全体作業計画。flow-id 1-4 で作成）
- この調査計画は、全体作業計画の「フェーズ2〈調査〉」節に挙げた5項目を、**答えを出せる問いの形**へ
  分解したものである。

## この調査で何を決めるか

フェーズ3（実装）の個別作業計画を書けるようにする。具体的には、**次の7つが決まれば調査は完了**とする。

1. Tailwindのクラスを、素のCSSのどの単位へ畳むか（変換の方針）
2. 4案を「1つの構造 ＋ 4つのスタイル」で表せるか、それとも4本を独立させるか
3. 現行 `reports.template.html` を置き換えるのか併存させるのか、**既定はどれか、4案をどう使い分けるか、
   ファイル名は何にするか**
4. 現行の3種の検査コマンドが、新しい構造でもそのまま使えるか
5. `wip/design-samples/` をどう後始末するか
6. **issue #186 の色と記号の意味論が、4案それぞれの配色で成立するか**
7. **ライト単一テーマの案（10・13）にダークモードを足すか否か**

（6・7は敵対的レビュー1回目の指摘で追加した。当初の5項目には、意味論の維持とダーク対応という
issue本文が明示している要件を確かめる問いが無かった。）

## 調べること（問いと、答えの出し方）

### Q1. Tailwindのクラスは、どの単位のCSSへ畳めばよいか

- **やること**: 4案が使っているTailwindクラスを機械的に抽出し、頻度順に並べる。そのうえで
  「意味を持つ単位」（チップ・タイムラインのドット・カード・サイドバー等）へ分類する。
- **答えの形**: クラス名 → セマンティッククラス（`.chip.good` 等）の対応表。
- **判断基準**: 現行テンプレートは CSS変数（`--accent` 等）＋セマンティッククラスで書かれており、
  HTMLを読んだときに**構造と意味だけが見える**状態を保っている。変換後もこれを崩さないこと。
  ユーティリティクラスがHTMLに残る形（`class="mt-5 grid grid-cols-3 gap-3"`）は採らない。

### Q2. 4案はDOMを共有できるか

- **やること**: 4案のHTMLから**タグ構造だけ**を抽出して（class属性を落として）差分を取る。
- **答えの形**: 「完全一致」か「差分あり（どこが違うか）」。
- **なぜ効くか**: 全体作業計画では目視で「DOM同一」と見立てているが、目視は当てにならない。
  機械的な突き合わせで確かめる。**一致するなら**、プレースホルダ・使い方コメントを1回書けば
  4案へ同じものを配れる（記述の二重管理を避けられる）。
- **判断基準（差分があった場合の分岐）**: 差分の「量」ではなく**種類**で線を引く。
  「量に応じて」とだけ書くと、結果を見ても方針が一意に決まらない。

  | 差分の種類 | 判断 |
  |---|---|
  | 装飾目的のタグ置換（`strong`↔`mark`、`p`↔`span`）・レイアウト用ラッパー `div` の増減 | **共有DOMへ寄せる**（CSSで表現できるため） |
  | 節（`section`）の有無・`id` の増減・要素の並び順の違い | **4本独立**（構造そのものが違う） |

### Q3. 現行テンプレートの9節は、新構成のどこへ行くか

- **やること**: 現行 `reports.template.html` の節（目次／重点レビュー依頼／サマリ／確かめられなかった
  こと／実施条件／実施した内容と結果／設計への反映／想定と異なった点／残課題）を一方に置き、
  **サンプル06側は `section` と `id` を機械的に列挙してから**突き合わせる。
  **06の節構成をあらかじめ列挙しない**（列挙すると、それ自体がQ3の結論の先取りになるうえ、
  実際の構造と食い違ったときに「対応先が無い節」を誤って作り出す。現行の必須節が別の節へ
  *吸収されている* 場合と、*どこにも無い* 場合を取り違えないため）。
  **あわせて、作業結果レポート版のサンプル16でも同じ吸収先が成立するかを確認する**
  （下の「やらないこと」が16を例外として残しているのは、この確認のためである）。
- **答えの形**: 対応表（現行の節 → 新構成での置き場、必須／任意の別）。
  **対応先が無い節があれば、それをどう扱うか**（新構成へ節を足す／落とす）まで決める。
- **判断基準**: 現行の必須節を落とさない。落とすなら、なぜ落としてよいかを言えること。

### Q4. 3種の検査コマンドは新構造でも成立するか

- **やること**: **4案すべて**に対して、現行テンプレートが定めるリンク破断検査・重複ID検査を
  **実際に流す**。プレースホルダ検査は、テンプレート化した後でないと流せないため、
  「新構成でプレースホルダをどこへ置くか」の見通しだけを立てる。
  **あわせて、受け入れ条件(2)「外部依存ゼロ」の検査**（`wip/reports/REVIEW-POINTS.md` が定める2本）
  を調査項目に加える。3種の検査だけでは、変換漏れ（残った `<script src>`・`@import url(//…)`・
  Webフォント指定）がどの検査にも当たらない。
- **答えの形**: 各コマンドの実行結果と、修正が要るなら修正後のコマンド。
- **空振りにしないこと**: これらは「異常が無ければ何も出ない」形の検査である。
  **正常なファイルで0件だったことは、検査が働いた証拠にならない。** 次の2つを併せて行う。
  1. `href` と `id` の**件数**を出し、0件でないことを確認する（対象を取れていないだけ、を除く）。
  2. サンプルのコピーへ**意図的な異常**（存在しないIDへの `href`／`id` の重複）を作り、
     検査が実際に検出するところまで確かめる。外部依存検査は、**変換前のサンプル**（Tailwind CDN
     を持つ）へ流して非0件になることで、当たっていることを示す。
- **注意**: 新構成はサイドバー目次からも本文IDを参照するため、**参照の数が現行より増える**。
  検査コマンドは正規表現でID定義側をタグ内に限定しているが、それが新構成でも守られるかを見る。

### Q5. `wip/design-samples/` をどう後始末するか

- **やること**: 別ブランチ `claude/report-template-design-0bpul1` の状態と、そのブランチに
  対応するPRの有無を確認する。
- **答えの形**: 「このPRで取り込む」「別ブランチ側で処理する」「何もしない」のいずれかと、その理由。
- **判断基準**: issue #203 の受け入れ条件(5)が「後始末を決めて**実施している**」ことを求めている。
  3択のそれぞれについて、**このPRで何をコミットすれば「実施した」と言えるか**まで答えの形に含める
  （「分かれ目」で止めると、マージ時点で条件を満たしたのか判定できない）。

  | 決め方 | このPRで「実施した」と言うために必要なもの |
  |---|---|
  | このPRで取り込む | `wip/design-samples/` を取り込むコミット（ただし flow-id 5-5 で削除される点を織り込む） |
  | 別ブランチ側で処理する | 処理内容を決め、**このPRの調査結果へ記録**する。ブランチ削除など取り消しの難しい操作は**ユーザーの明示指示を待つ**旨も明記する |
  | 何もしない | 「何もしない」と判断した**根拠**を調査結果へ記録する（判断したことが外形から分かる形にする） |

### Q6. 現行テンプレートの扱い・既定・選択基準・ファイル名をどう決めるか

**敵対的レビュー1回目の指摘で追加した。** 当初の計画は「決めること」の3番（置き換え／併存・既定）を
掲げていながら、それに答える問いを持っていなかった。Q3は節の対応表を作るだけで、置き換えの結論も
既定の選定も含まない。

- **やること**: 現行テンプレートと新4案の適性（レイアウトが要求する分量・テーマ数・用途）を比べる。
  既存の使い分け記述（`.claude/skills/canvas-report/SKILL.md`「いつcanvasを選ぶか」）を型として使う。
- **答えの形**: 次の4つをすべて含む。
  1. 置き換えか併存かの結論と理由
  2. **既定テンプレートのファイル名**（1つ）
  3. **4案の使い分けを1行ずつ書いた表**（受け入れ条件(4)「選択基準がドキュメント化されている」）
  4. **作るファイルの数と名前**（受け入れ条件(1)。検証節が要求しているのに、当初どのQも決めていなかった）
- **判断基準**: `deliverables.md` のテンプレート表に何行載るか（＝書き手が選ぶときに見る一覧）で
  検証する。行が増えるだけで選び方が書かれていなければ、受け入れ条件(4)を満たさない。

### Q7. issue #186 の色と記号の意味論は、4案それぞれの配色で成立するか

**敵対的レビュー1回目の指摘で追加した。** issue本文が「意味論を維持する」ことを明示的に求めているのに、
それが4案の配色で成立するかを確かめる問いが無かった。

- **やること**: 4案それぞれについて、次の4系統が視覚的に区別できるかを確かめる。
  `--good`（◎良=青）／`--warn`（△注意=黄）／`--stop`（✕問題=赤）／`--ok`（決めたこと・手順の成功=緑）。
- **答えの形**: 案ごとの可否と、区別できない案についての**代替の置き方**（記号＋文字での表現）。
- **判断基準**: 現行テンプレートは「緑は決めたこと専用。結論の性質には使わない」と定めている。
  この住み分けが崩れる案があれば、**色以外の手段（枠の太さ・ラベル文字）で代替する**。
  色だけに意味を持たせない原則は、代替後も守る。

### Q8. ライト単一テーマの案（10・13）にダークモードを足すか

**敵対的レビュー1回目の指摘で追加した。** 現行テンプレートは `prefers-color-scheme` を持つのに対し、
サンプル10・13はライト単一テーマである。足す／足さないを決めないままフェーズ3へ進むと、
既定テンプレート次第では機能後退（ダークで読めないレポート）になる。

- **やること**: 4案の `dark:` バリアントの有無を数え、10・13が単一テーマである理由
  （サンプル冒頭コメントが述べている設計意図）と照らす。
- **答えの形**: 案ごとに「ダーク対応する／しない」と、しない場合にブラウザの強制ダーク化から
  どう守るか。
- **判断基準**: **既定テンプレートは必ずダーク対応させる**（現行からの機能後退を作らない）。
  既定以外については、そのデザインの意図が単一テーマを要求しているなら維持してよいが、
  **選択基準の表（Q6）へ「ダーク対応の有無」を明示**し、書き手が知って選べるようにする。

## やらないこと（スコープ外）

- 選定外のサンプル（01〜05・07〜09・11・14〜16）の分析。ただし16は「統合構成が作業結果レポートでも
  成立する」ことの根拠としてissue本文が挙げているため、Q3の突き合わせでのみ参照する。
- `plans.template.html` の調査（issue #203 の対象外）

## 検証（この調査が終わったと言える条件）

- Q1〜Q8のすべてに、**根拠を添えた答え**が `wip/reports/` のレポートへ書かれていること。
- Q2・Q4・Q7・Q8は**実際にコマンドを流した結果**が根拠として残っていること（目視・推測で済ませない）。
- **Q4は「異常を検出できること」まで示せていること**（0件だったという結果だけで終わらせない）。
- フェーズ3の個別作業計画に必要な情報（作るファイルの数・名前・各ファイルの中身の方針）が
  出揃っていること。

## 想定している作業手順

```bash
# Q1: Tailwindクラスの抽出（4案ぶん、頻度順）
# sed で class=" と閉じ " を先に剥がす。剥がさないと先頭・末尾のクラスが
# `class="text-xs` `text-sm"` という別トークンになり、同じクラスが分裂して数えられる。
grep -oE 'class="[^"]*"' <サンプル> | sed -E 's/^class="//; s/"$//' \
  | tr ' ' '\n' | grep . | sort | uniq -c | sort -rn

# Q2: タグ構造の突き合わせ（開きタグだけでなく閉じタグも拾う）
# `<[a-z]` だけだと `</div>` を拾わず、得られるのは「開始タグ名の並び」であって
# 入れ子構造ではない。閉じタグを含めて初めて構造の比較になる。
grep -oE '</?[a-z][a-z0-9]*' <サンプルA> > a.txt
# 同様にB〜Dを作り diff で比較

# Q4: 検査が「異常を検出できる」ことの確認（空振り防止）
# 正常なファイルで0件だったことは、検査が働いた証拠にならない。
# 意図的に壊したコピーを作り、検査が実際に検出することまで確かめる。
cp <サンプル> broken.html
sed -i 's|href="#f3"|href="#f99"|' broken.html   # 存在しないIDへのリンク
sed -i 's|id="f2"|id="f1"|' dup.html                     # IDの重複

# 外部依存の検査（受け入れ条件(2)。wip/reports/REVIEW-POINTS.md が定める2本）
grep -nE "(src|href)=['\"]?(https?:)?//" <F>
grep -nE "(url\(|@import[[:space:]]+)['\"]?(https?:)?//" <F>

# Q4: 現行テンプレートの検査コマンドをサンプルへ流す
comm -23 <(grep -oE 'href="#[A-Za-z0-9_-]+"' <F> | sed 's/^href="#//;s/"$//' | sort -u) \
         <(grep -oE '<[a-z][^>]*[[:space:]]id="[A-Za-z0-9_-]+"' <F> | sed 's/.*id="//;s/"$//' | sort -u)
grep -oE '<[a-z][^>]*[[:space:]]id="[A-Za-z0-9_-]+"' <F> | sed 's/.*id="//;s/"$//' | sort | uniq -d
```
