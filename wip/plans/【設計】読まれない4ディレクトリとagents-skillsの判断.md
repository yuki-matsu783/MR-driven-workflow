# 【設計】読まれない4ディレクトリと.agents/skillsの判断

issue #172（スコープ拡大後）／PR #193／フェーズ3〈作業〉の**2回目**。
論点1（自立化するか）は既に決着済み（`.claude/`への依存を明示する。**flow-id 1-4の
スコープ拡大時、2026-08-23、ユーザー判断**。記録: `wip/plans/mellow-drifting-lantern.md`
「スコープ拡大」節）。この計画は残る**論点2・論点3**を判断する手順と判断基準を定める
（**判断の結果そのものは書かない**。結果は `wip/reports/…gemini生成対象の採否.md` へ書く。
issue #87「計画と実施結果の分離」）。

## この計画で決めること

### 論点2: 読まれない4ディレクトリ（rules/ docs/ hooks/ scripts/）の扱い

判断基準は1回目調査が置いた4軸（読まれるか／自己完結／外すコスト／外す利得）と、
フェーズ3・1回目が導いた3つの決め手（配布物は減らない／部分除去は中間状態になる／
外す根拠は未観測の推論）を、2回目調査のQ10実測値で更新して適用する。**`rules/`単独の
軸1〜軸4（とくに軸3＝外すコスト）が1回目時点で埋まっていないため、この計画の実施時に
埋めるか、埋めないなら「未評価」と明記する。**

**判断に使う新事実（2回目調査Q10）**:

- 4ディレクトリを外すと壊れたリンクの**件数**は18件→1件へ減る（`rules/`が自身の軸2の
  17件を道連れに消すため）。ただし残る1件は `.gemini/skills/apply-mr-workflow-to-project/SKILL.md`
  という**Gemini CLIが実際に読むファイルの中**にあり、消える17件（読まれないファイルの中）とは
  性質が違う。件数の増減だけで「弱まった／強まった」を判定しない。
- 1回目・フェーズ3の決め手2（部分的に外すと中間状態になる）は「落ちる割合」（案3で
  81.9%/78.7%）を根拠にしていた。4ディレクトリ版の割合（85.6%/84.7%、Q10-1実測）を
  **同じ尺度で**比較したうえで、決め手2への影響を判定する。

一方、フェーズ3・1回目の決め手1（配布物は1バイトも減らない）と決め手3前半（`rules/`
`docs/` `hooks/` `scripts/` が読まれないという結論そのもの）は、2回目調査でも変わって
いない。**Gemini CLI実機は依然未観測**であり、「読まれない」という結論は「公式ドキュメントに
記載が無い」という消極的根拠のままである。

### 論点3: `.agents/skills/` エイリアス

2回目調査Q7の実測（Claude Code公式ドキュメントに`.agents`の言及が0件）を根拠に、
成立するかどうかを判定する。

## 決めないこと

- Gemini CLI実機での検証（環境が無い。**ユーザーの指示により、この確認はGemini CLIの
  ソースコードを参照できる別環境へ委ねる**）
- 論点2の判断確定後の実装（sync-gemini-assets.shの変更等）は、判断後に着手する

## 進め方

1. 論点2を4軸＋Q10実測で判定し、結論を出す
2. 論点3の不成立を記録する
3. 結果を既存の採否レポートへ追記する形で反映する（新規ファイルは作らず、
   `wip/reports/…採否.md`に論点2・論点3の節を追加。理由: 同一issueの最終判断であり、
   採否の文脈を分離すると読み手が2つのレポートを往復する必要が生じるため）
4. 敵対的レビュー（フェーズ3で残り1回）を、判断結果に対して実施する
5. HANDOFF更新、commit・push

## 検証

**この計画の判断は「現状維持（コード無変更）」になりうる。その場合、変更が無いことを
機械的に確かめる。** 次の2つは変更前から通るため、それだけでは検証にならない
（`sync-gemini-assets.sh --check` の終了コード0、`test_sync_gemini_assets.sh` の
`failures=0`）。判断の記録が実際に増えたことは、以下で確かめる。

```bash
# 「決めないこと」に書いた実装（sync-gemini-assets.shの変更）を、
# この計画の作業では行っていないことを、分岐点との差分で確かめる
BASE_SHA=$(git merge-base origin/main HEAD)
git diff "$BASE_SHA" -- .claude/scripts/src/sync-gemini-assets.sh .claude/dist-layers.json | wc -l
# 期待値: 0（この計画では実装を変更しない）

# 判断結果が採否レポートへ追記されたことを確認する
grep -c '^#### 論点2' "wip/reports/20260823_mellow-drifting-lantern_gemini生成対象の採否.md"
grep -c '^#### 論点3' "wip/reports/20260823_mellow-drifting-lantern_gemini生成対象の採否.md"
# 期待値: いずれも1
```

合格条件: 上記1つ目のコマンドが0行を返す（実装を変更していない）ことと、2つ目・3つ目が
1を返す（判断が採否レポートへ書かれている）こと。あわせて、採否レポート側で次を目視確認する。

- 論点2・論点3のいずれにも、判断と理由（4軸・決め手・Q10実測・実機未観測の制約）が明記されている
- 「今の設計がベスト」という結論の可能性も排除していない
- 実機未観測の制約が明記されている
- **決定した対象**（例: 「4つとも残す」という判断そのもの）と**未確定の対象**
  （例: 「外す根拠の有無」の再検討）が、1文で区別して書かれている
