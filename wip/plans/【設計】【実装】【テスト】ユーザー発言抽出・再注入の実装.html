残る設計判断（flow-id 3-3 で承認を得る）

この4点は承認を得るまで実装へ進まない 以下 H-1〜H-4・E・C・A の提案は、いずれもフェーズ2の実測結果を踏まえた提案であって、まだ人間の承認を得ていない。

H-1. 初期辞書の中身

提案: 現行12語から ok/OK を除いた10語をそのまま初期値にする。

はい / うん / お願い / お願いします / よろしく / 続けて / 続けてください / ありがとう / ありがとうございます / 了解

フェーズ2の実測（真の発言7件）ではこの10語のうち1語も働かなかったが、これは「不要と確認された」ことを意味しない——単にこの断面に登場しなかっただけである。机上の判断で先回りして削ると、後から本当に必要だった語を消したことになりかねない。「育てる」の出発点は観測実績ではなく現行の網羅にし、以後は下記H-3の可視化を見ながら削っていく（削るほうが安全——辞書は完全一致なので、削っても後から戻せる）。

H-2. 辞書の置き場所

提案: プレーンテキストファイル .claude/hooks/session-start-ack-words.txt に切り出す。

  • 1行1語（正規化後の形で書く）。# で始まる行はコメント（削除・追加の理由を書ける）。空行は無視。
  • UTF-8・BOM無し・LF改行で保存し、.gitattributes のdist:begin〜dist:endマーカーの内側へ1行を追加する（.sh規約と同じ理由。マーカーの内側にしないと配布先ではLFが保証されない）。改行がCRLFに化けると、辞書照合はjqの完全一致比較のため一致しなくなる（caseパターンマッチではない）。
理由 辞書をsession-start.sh内のbash配列に直書きすると、1語増減するだけでもスクリプト本体を編集することになり、「育てる」操作のハードルが上がる。独立ファイルなら、Write/Editツール（または人間のエディタ）で1行足し引きするだけで済み、差分も1行になる。
却下した案 JSON形式（語ごとに理由・追加日等のメタデータを持たせる）。今回はメタデータの必要性が実測で確認できておらず（H-4のとおり理由はコミットメッセージに残る）、構造を持たせるコストに見合わない。

H-3. 除外実績の可視化（最重要）

提案: 2段構えにする。

  1. 注入テキストへの当該セッション分の内訳: そのセッションで1件でも除外があれば、ユーザー発言節の末尾へ1行足す。 
    - 相槌等として除外: はい×1, ありがとう×1
    辞書語と件数だけで、除外された発言の本文は出さない。選定結果（selected）が0件になった場合でも、除外が1件以上あればこの行だけは出す（下記「全件除外時の扱い」）。
  2. 累積カウントのローカル状態ファイル: wip/state/session-start-ack-exclusion-counts.json（.gitignoreの/wip/state/で既に除外対象。issue #184で導入済みのディレクトリを流用するため新規の除外パターンは不要）。辞書語をキーに、除外した累積件数と、重複計上を防ぐためのuuid集合を持つ。 
    {
  "counts": {"はい": 3, "ありがとう": 1},
  "countedUuids": ["c1a2...", "9f3e..."]
}
    セッションごとに読み込み、まだcountedUuidsに無いuuidの除外イベントだけを加算して書き戻す。このファイルにも発言の本文は書かない（語と件数、および重複除去用のuuidのみ）。
重複計上対策（フェーズ3敵対的レビュー指摘） SessionStart hookはstartup/resume/clear/compactのたびに発火し、同一セッションで同じtranscriptを何度も読み直す（実測済み）。素朴に「今回加算して書き戻す」だけだと、同じ除外イベントを再発火のたびに数え直してしまう。除外イベントごとに元行のuuidをcountedUuids集合と突き合わせ、未計上のものだけ加算する。集合は短い文字列（uuid）のみでファイルサイズへの影響は軽微で、このファイル自体がローカル状態（gitignore対象）のため肥大化しても実害は無い。
状態ファイルの破損・空・並行書き込みへの備え（同上） issue #37と同型の恒久回復不能を避けるため、読み込み前に空文字チェック→jq -e .の順で検証し、いずれかに失敗したら「状態なし」（counts={}・countedUuids=[]）へフォールバックする。書き込みは一時ファイルへ書いてからmvする（原子的な置き換え）。
理由 「毎回のユーザの入力を見ながら育てる」を成り立たせるには、まず何かが落ちたことに気づける必要がある。当該セッションの内訳（1）は即座に気づける経路、累積カウント（2）は「はいが何度も引っかかる」のような傾向に気づける経路で、役割が異なるため両方持つ。
秘密情報の扱い 除外された発言の本文は、注入テキストにも状態ファイルにも一切書かない。「そもそも値を出さない形にできないかを先に考える」に従う。本文が要る判断（「本当にこれは相槌か」）は、人間が該当セッションのtranscriptを自分で開けば足りる——hookが本文を持ち歩く必要は無い。
却下した案 除外した発言の本文をログへ残す。過剰除去の判断がしやすくなる一方、秘密情報を平文でローカルに蓄積することになる。上記の代替で足りると判断した。

全件除外時の扱い（H-3と関連。フェーズ3敵対的レビュー指摘）

除外内訳行は、selectedが0件になった場合でも独立に出す。 現在の「N=0なら節ごと出さない」という既存方針（DDR i0057-01）は保つが、それは「発言そのものが1件も選ばれなかった場合にユーザー発言節の見出し・本文を出さない」という意味であり、除外内訳行はこの判定に含めない。辞書との一致・バイト上限超過などでselectedが全滅してもexcludedCountsが1件以上あれば、除外内訳行だけを（見出しなしで）出す。気づきたい度合いが最大の状況でこそ、この行が唯一の手がかりになる。

H-4. 育てた操作の記録先

提案: 新しい記録先を作らない。辞書ファイル（H-2）自体のgit履歴を記録先にする。

辞書語の追加・削除は、session-start-ack-words.txt の1行編集として行い、commitスキル経由のコミットメッセージへ理由を書く。恒久的な設計判断（辞書という方式そのものの採否等）は従来どおり.claude/docs/ddr/へ書く。

理由 専用の記録先を新設すると、育てる操作のたびに2箇所（辞書ファイルと記録先）を更新することになり、更新漏れが起きる。git履歴は編集のたびに必ず残るため、これ以上のインフラは不要。

E. 単一transcript前提への対処方針

提案: 過去transcriptの走査は実装せず、HANDOFF.md「次にやること」節の既存の注入で代替する。

理由内容
1. 既に半分実装済みbuild_work_contextは既にHANDOFF.md「次にやること」節を毎セッション注入している（既存機能）。継続性は一定量カバーされている
2. コストに見合わない過去transcriptを対象にすると走査コストが本数倍に増える。問い10aでこの実行環境では0本だったため、効果が実測できない
3. フェーズ2の停止条件に沿うローカル（Windows）環境で過去transcriptが残るかは未確認のまま。未確認の前提の上に複雑な実装を積まない

今回やらないことは、.claude/docs/spec/（flow-id 4-6）へ「単一transcript前提の限界」として明記し、恒久的な記録として残す。

C. 母集団が0件になったことに気づける形

提案: 追加の実装は行わない。既存の「N=0なら節ごと出さない」方針のままにする。

理由 「母集団が0件になったこと」への気づきは、上記H-3の可視化（除外件数）と、下記の単体テスト（抽出条件の回帰防止）の2つで別の角度からカバーできる。実行時の自己診断を足すと、「取れた分だけ出す・fail-openを崩さない」という既存設計（DDR i0057-01）に例外を作ることになる。リスクは実装のバグによる回帰であり、それはテストの役割。

抽出パイプライン（1回のjq呼び出しに集約する）

「外部プロセス起動のコスト」規約に従い、抽出・母集団確定・除外規則適用・ブランチ絞り・uuid重複除去・先頭/直近の採り方・切り出し・バイト数計算までをUserUtteranceSelect.jq 1本のjq呼び出しでまとめて行う。

jq -R -n -f "$lib_dir/UserUtteranceSelect.jq" \
  --arg branch "$branch" \
  --rawfile ack_words_raw "$ack_words_path" \
  --argjson head_count "$USER_UTTERANCE_HEAD_COUNT" \
  --argjson tail_count "$USER_UTTERANCE_TAIL_COUNT" \
  ... \
  < "$transcript_path"
  • transcript_pathだけを引数で渡さず標準入力へ繋ぐ（フェーズ2問い7の結論。動的で任意の位置になりうる外部パスのため）。-fのフィルタパスと--rawfileの辞書パスは、いずれもリポジトリ内の固定相対パスであり標準入力へ逃がす対象ではない（既存session-start.shがjqを-f引数で呼んでいる箇所と同じ扱い）。
  • 辞書は--rawfileでテキストごと渡し、jq側で改行分割・各行のtrim（前後空白・CR除去）・コメント行/空行除去を行う。発言側と同じ正規化を辞書語にも適用してから比較する（末尾空白・CRLF・字下げされたコメント行で辞書語が無言で無効化されるのを防ぐ）。
  • 辞書ファイルが存在しない・読めない場合、bash側は--rawfileを使わず空文字列を--argで渡す（存在しないパスを--rawfileへ渡すとjq起動自体が失敗するため）。
  • 出力は1つのJSONオブジェクト（selected / excludedCounts / populationCount）にまとめ、bash側はjq -rで崩す（bash・jq間の受け渡しも1回で済ませる）。
CR除去（フェーズ3敵対的レビュー指摘） Windows native jqはコマンド置換・パイプでも行末へCRを付与する。excludedCountsのキーを複数件ループで取り出す場合、selected[].textのように複数行になりうる値をコマンド置換で受ける場合のいずれも最後の要素・最終行以外にCRが残る。この2箇所は| tr -d '\r'を挟む（単一行・単一要素で完結する取り出しには不要）。

抽出条件（フェーズ2確定分。実装で崩さない）

type=="user" ＋ .message.contentが文字列 ＋ userType=="external" ＋ isSidechain==false ＋ origin.kind=="human"。肯定形を崩さない。

除外規則

  1. 辞書との正規化後の完全一致（前後の空白・句読点・感嘆符・記号の除去）。辞書ファイルが存在しない・空・読めない場合は、この規則を無効化して続行する（辞書0語＝この規則では何も除外しない）。
  2. 引数の無いスラッシュコマンド単体（^/[A-Za-z][A-Za-z0-9:_-]*$）
  3. <command-name> 等のタグで始まる行

除外が発生するたびにexcludedCountsへ辞書語（規則1のみ）をキーとして加算する。

ブランチ絞り・重複除去・採り方・切り出し・サイズ

いずれもフェーズ2確定のロジックをそのまま実装する（個別調査計画・調査結果レポートが正。ここでの再掲はしない）。

  • ブランチ絞り: 行がgitBranchを持ち、かつ現在のブランチと一致するものが1件以上あるときだけ絞る。
  • uuidによる重複除去。
  • 先頭min(3,N)件 ＋ 残りの末尾min(7, N-min(3,N))件（重複なし）。
  • 切り出しはjqの.[0:N]。先頭枠は頭120字＋末尾40字、直近枠は頭80字＋末尾30字。
  • 節全体のバイト上限USER_UTTERANCE_MAX_BYTES（既定6000）。超えた場合は直近枠の古い側から1件ずつ落とす。先頭枠は落とさない。

transcript_pathの受け渡し（フェーズ3敵対的レビュー指摘）

下方向は関数引数でそのまま渡す。 transcript_pathはmainがraw="$(cat)"で読んだstdin JSONの中にしかない。下方向の値渡しはコマンド置換のサブシェル境界に影響されない——issue #43が問題にしているのは「サブシェル内で設定したグローバル変数が呼び出し元へ伝わらない」という上方向の話であり、引数を下へ渡す分には無関係である。

main() {
  raw="$(cat)"
  transcript_path="$(printf '%s' "$raw" | jq -r '.transcript_path // empty')"
  if context_text="$(build_context "$transcript_path")"; then ...
}
build_context() {
  local transcript_path="${1:-}"
  work_context="$(build_work_context "$branch" "$transcript_path")"
}
build_work_context() {
  local branch="${1:-}" transcript_path="${2:-}"
}
build_user_utterance_context() {
  local branch="${1:-}" transcript_path="${2:-}"
}

再注入バイト数の返し方（同上の指摘）

上方向はグローバル変数では伝わらない。 work_context="$(build_work_context ...)" も context_text="$(build_context ...)" もコマンド置換でありサブシェルへforkするため、内側で設定したグローバル変数はmainまで伝わらない。標準出力の中身自体はコマンド置換が何段ネストしてもそのまま親へ伝わるため、build_user_utterance_contextは本文の末尾へセンチネル行を1行追加して返す。

__USER_UTTERANCE_BYTES__:1234

各関数はこの行を含めてlines配列へそのまま積む。mainはcontext_textからこの行をgrepで抜き出して数値を取り出し、本体からは取り除いてからwrite_additional_contextへ渡す。ユーザー発言節を1行も出さない場合、センチネル行も出さない（excluded_bytesは既定の0）。

出力位置

build_work_context内、「HANDOFF.md次にやること」ブロックの直後・SKILL.md再読み込み指示の手前へ挿入する（issue #113の末尾配置を維持）。センチネル行はmainが取り除くため、実際にユーザーへ見える注入内容には現れない。

append_size_warningの変更

現在(text, limit)の2引数。末尾へexcluded_bytesを追加し(text, limit, excluded_bytes)の3引数（第3引数は省略可・既定0）へ変更する（間へ差し込まない）。effective_bytes = context_text_bytes(text) - excluded_bytesで判定し、警告文には「全体Nバイト（うち再注入分Mバイトを除外して判定）」の両方を出す。

既存テストへの影響（フェーズ3敵対的レビュー指摘） 第3引数を末尾へ追加し既定値0にしたことで、test_session_start.shの既存2引数呼び出し6箇所は変更不要になる（excluded_bytes省略時はeffective_bytes = total_bytesとなり従来と完全に同じ判定になる。当初案「第2引数へ差し込む」は既存呼び出しの意味を無言で変えるため採らない）。mainは新しい第3引数を渡すよう変更する。

fail-open

transcript_pathが空・不正・壊れたJSONの場合、UserUtteranceSelect.jqの呼び出しが失敗してもbuild_context全体を失敗させず、他の注入項目は通常どおり出す。

具体的な実装（フェーズ3敵対的レビュー指摘） build_work_context自体はbuild_contextの中でset -e配下にあるため、素朴にuser_utterance_context="$(build_user_utterance_context ...)"と書くと失敗時に既存6項目が丸ごと消える。「bashでのtry/catch相当の書き方」の出力を受け取る形を適用する。 
set +e
user_utterance_context="$(set -e; build_user_utterance_context "$branch" "$transcript_path")"
rc=$?
set -e
[ "$rc" -eq 0 ] || user_utterance_context=""
[ -z "$user_utterance_context" ] || lines+=("$user_utterance_context")

比較検討した案

案利点採否と理由
辞書をJSON形式にし語ごとにメタデータを持たせる（H-2）削除・追加の理由を辞書ファイル自体に残せる却下 必要性が未実証。git履歴（H-4）で理由は残る
除外した発言本文をログへ残す（H-3）過剰除去の判断がしやすい却下 秘密情報の平文蓄積になる。語＋件数で「見ながら育てる」は成り立つ
除外実績の記録専用ファイルを新設する（H-4）育てた理由を専用の場所へ集約できる却下 辞書ファイル自体のgit履歴で足り、更新箇所を増やすと更新漏れの元になる
過去transcriptも対象にする（E）複数セッションにまたがるタスクでも先頭枠が保てる却下 この環境で0本、コストが本数倍。HANDOFF.md側の既存機能が一定量カバーする
先頭枠を諦める（E）実装が単純になる却下 本機能の主目的（最初の依頼を保つ）そのものを手放す。他の2案より損失が大きい
AskUserQuestion回答を今回のスコープに含める（A）人間の意思決定を取りこぼさない却下 抽出条件の再設計に近い規模で、本issueのスコープを超える
母集団0件を実行時に検知して警告する（C）異常への気づきが早くなる却下 fail-open設計（DDR i0057-01）に例外を作る。回帰は単体テストで防ぐべき性質
excluded_bytesをappend_size_warningの第2引数へ差し込む引数の並びが直感的却下 既存呼び出し（test_session_start.shの6箇所）が無言で意味を変える
再注入バイト数を専用の状態ファイル経由でmainへ渡すサブシェル境界を気にしなくてよい却下 1回の実行内で完結する値をファイルI/Oで往復させる必要が無い。センチネル行のほうが単純
