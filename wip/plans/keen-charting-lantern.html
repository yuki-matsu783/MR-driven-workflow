この計画で何をするか

コミットメッセージの内容についての規約を .claude/skills/commit/SKILL.md へ追記する。あわせて「1行のみを維持するか本文を許容するか」の方針をDDRとして記録し、.claude/docs/spec/create-commit.md の記述と矛盾しない状態にする。

なぜ1行の情報量が問題になるか wip/plans/ wip/worklogs/ wip/reports/ は flow-id 5-5 で削除され、squash merge により main に残らない。main上で作業の内訳を辿れるのは .claude/docs/spec/ .claude/docs/ddr/ とコミットログだけであり、1行の情報量がそのまま履歴の情報量になる。

領域の粒度で示す。ファイル単位・行単位の確定は、フェーズ2の調査結果を受けてフェーズ3の個別作業計画で行う。

メッセージ形式の「正」は1箇所に置く

現状の .claude/docs/spec/create-commit.md:46 は「1行のみ（形式はcommitスキル側の規約）」と、正を commit スキルへ委ねる構造になっている。この構造を維持する——形式の正は .claude/skills/commit/SKILL.md 1箇所とし、create-commit.md からは具体形式を落として参照だけを残す。両方へ具体形式を書くと、片方だけが古くなる（受け入れ条件「create-commit.md の記述が方針と矛盾しない」は、書いた直後の一致しか保証しない）。

方針

変えるのは規約（AIアセット）であり、create-commit.sh の実装は原則触らない。実装変更が要ると判明した場合は、フェーズ3の作業計画で改めて範囲を確定する。

規約は「AIエージェントが機械的に従える形」で書く。すなわち、満たすべき要素の列挙・良い例と悪い例の対・判断に迷ったときの既定の3点を備えさせる。抽象的な心構え（「分かりやすく書く」等）だけにしない。

フェーズ2〈調査〉

実施する。規約を書く前に、次を明らかにする（各問いの手段・母数の確定は個別調査計画 wip/plans/【調査】コミットメッセージ規約の現状と本文許容の可否.md が正）。

  1. 現行の規約がどこで・どう述べられているか。地の文（「1行のみ」等）だけでなく、旧規約に沿った例示・雛形（--message "…" の形）も洗う（後者は地の文の検索語では1件も拾えない）。
  2. squash merge後に main へ残る実際のコミットログ（母数を固定して数える）が、どのような欠落パターンを持つか。issue本文の4類型以外の類型があるか。
  3. 本文を許容した場合、実装（create-commit.sh）と呼び出し側（複数行メッセージの渡し方）が耐えられるか。
  4. squash merge時に本文がどう畳まれるか。GitHub側の畳み方は実測できない（履歴に本文付きコミットが1件も無く、生成はサーバ側の挙動のため）ので、実測できる部分と机上確認の部分を区別する。
  5. 規約を変えると壊れる／古くなる箇所はあるか。処理（.claude/scripts/ .claude/hooks/）と記述（.claude/skills/ .claude/rules/ .claude/docs/ の例示・雛形・書き方の指示）の両方を対象にする。

何が分かれば次へ進めるか: 「1行のみを維持するか」の判断材料が揃い、書き換えが必要なドキュメントの一覧が確定すること。

フェーズ3〈作業〉

  1. 方針を決める（1行のみ維持／本文許容／条件付き許容）。
  2. commit スキルへ内容規約を追記する。AIエージェントが機械的に従える形にする（満たすべき要素の列挙・良い例・悪い例・判断に迷ったときの既定）。
  3. 成果物の変更を伴わないコミット（HANDOFF更新・空コミット・片付け）の書き方を規約へ含める。
  4. issue本文の「実例」9行の書き直し例を示す。
  5. create-commit.md のメッセージ形式の記述を方針と揃える。

やらないこと（スコープ外）

この計画では決めない・触らない
  • 過去のコミットメッセージの書き換え — 履歴の改変であり、issueの目的（今後の履歴を読めるようにする）を超える。
  • create-commit.sh の実装変更（方針上不要な場合） — 必要と判明したらフェーズ3の個別作業計画で範囲を確定する。
  • prefix一覧そのものの見直し — issueが問題にしているのは prefix の後ろの説明部分である。
  • 英語コミットが生まれた経路の調査 — issue本文が「主対象ではない」と断り、記録として残すに留めている。

検証

旧規約の記述・例示が残っていないことを、次の2つのgrepで確認する。

# (a) 規約の地の文（検索語はQ1の4語へ揃える）
grep -rn '1行のみ\|本文・フッター\|フッター' --include='*.md' .claude AGENTS.md CLAUDE.md GEMINI.md

# (b) 旧規約に沿った例示・雛形（(a) では1件も拾えない）
grep -rn -- '--message "' --include='*.md' --include='*.sh' .claude

# DDR追加後の一覧再生成（差分は同じコミットへ含める）
bash .claude/scripts/src/generate-ddr-list.sh

# ドキュメント間の参照切れ
bash .claude/scripts/src/check-doc-references.sh
「0件」を合格条件にしない (a) は変更前のツリーでも無関係なヒットが常駐する（.claude/hooks/session-start.sh・.claude/scripts/test/test_check_base_conflicts.sh・.claude/docs/spec/distribution-assets.md（VERSIONはSemVer1行のみ）・.claude/docs/spec/search-frontmatter.md・.claude/docs/ddr/i0033-03… の5件と、生成物の index.jsonl）。変更前の件数を基準値として調査レポートへ記録し、変更後との差分で判定する。

GEMINI.md と .gemini/ を検索範囲に含める。 .gemini/skills/commit/SKILL.md は .claude/ 側と同一内容のコピーであり、flow-id 5-3 の変換同期を忘れると旧規約がここに残る（範囲から外すと同期漏れを検出できない）。

合格条件: issue #185 の受け入れ条件5件それぞれについて、対応する記述が成果物のどこにあるかを示せること。上記コマンドが矛盾・参照切れを報告しないこと。
