この計画で何をするか

コミットメッセージの内容についての規約を .claude/skills/commit/SKILL.md へ追記する。あわせて「1行のみを維持するか本文を許容するか」の方針をDDRとして記録し、.claude/docs/spec/create-commit.md の記述と矛盾しない状態にする。

なぜ1行の情報量が問題になるか wip/plans/ wip/worklogs/ wip/reports/ は flow-id 5-5 で削除され、squash merge により main に残らない。main上で作業の内訳を辿れるのは .claude/docs/spec/ .claude/docs/ddr/ とコミットログだけであり、1行の情報量がそのまま履歴の情報量になる。

変更対象

領域の粒度で示す。ファイル単位・行単位の確定は、フェーズ2の調査結果を受けてフェーズ3の個別作業計画で行う。

方針

変えるのは規約（AIアセット）であり、create-commit.sh の実装は原則触らない。実装変更が要ると判明した場合は、フェーズ3の作業計画で改めて範囲を確定する。

規約は「AIエージェントが機械的に従える形」で書く。すなわち、満たすべき要素の列挙・良い例と悪い例の対・判断に迷ったときの既定の3点を備えさせる。抽象的な心構え（「分かりやすく書く」等）だけにしない。

既存の記述を置き換える箇所 置き換え前: commit/SKILL.md「Step 4」の「<prefix>: <日本語説明> の 1行のみ / 本文・フッターを一切付けない」。
置き換え後: フェーズ3で決める方針に従う。この2行が兼ねている役割は2つある——(1) メッセージの形式（1行か複数行か）、(2) Claudeフッターの禁止。(2) は方針に関わらず維持する（commit スキルの絶対ルール）。

フェーズ2〈調査〉

実施する。規約を書く前に、次の問いへ答える。

  1. 現行の規約が「1行のみ」をどこで・何回述べているか（commit スキル、create-commit.md、git-workflow.md、その他のルール・spec）。書き換え漏れが残る箇所はどこか。
  2. squash merge後に main へ残る実際のコミットログは、どのような欠落パターンを持つか。issue本文の4類型以外の類型はあるか。
  3. create-commit.sh は複数行メッセージを受け付けられるか（--message の扱い、git commit -m への渡し方）。本文を許容する方針を採った場合に実装変更が要るか。
  4. squash merge時にGitHubが本文をどう畳むか。本文を許容した場合、main の1行目に何が残るか。
  5. 他のAIアセット・スクリプトが、コミットメッセージの文言を前提にしていないか（特定文字列でのコミット検索等）。

何が分かれば次へ進めるか: 「1行のみを維持するか」の判断材料が揃い、書き換えが必要なドキュメントの一覧が確定すること。

フェーズ4〈反映〉

反映対象は flow-id 4-1 で洗い出す。現時点の見込みは次のとおりで、確定した反映内容ではない。

  • DDR新設（方針決定の経緯・却下案）と .claude/docs/README.md のDDR一覧の再生成。
  • .claude/docs/spec/create-commit.md の「影響範囲」へ本issueのエントリを追記。
  • .claude/rules/git-workflow.md「コミット運用」からの入口の要否。
  • .claude/docs/usecase/ の記述・リンクが古くならないかの確認。

やらないこと（スコープ外）

この計画では決めない・触らない
  • 過去のコミットメッセージの書き換え — 履歴の改変であり、issueの目的（今後の履歴を読めるようにする）を超える。
  • create-commit.sh の実装変更（方針上不要な場合） — 必要と判明したらフェーズ3の個別作業計画で範囲を確定する。
  • prefix一覧そのものの見直し — issueが問題にしているのは prefix の後ろの説明部分である。
  • 英語コミットが生まれた経路の調査 — issue本文が「主対象ではない」と断り、記録として残すに留めている。
