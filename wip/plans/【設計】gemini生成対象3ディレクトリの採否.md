# 【設計】`.gemini/` の hooks/ scripts/ docs/ の採否を決める

全体作業計画: `wip/plans/mellow-drifting-lantern.md`
調査結果: `wip/reports/20260823_mellow-drifting-lantern_gemini生成対象の参照実態.md`（issue #172 / PR #193）

## この計画で何をするか

3ディレクトリそれぞれについて **「生成対象に含める／外す」を1つずつ決め、決め方（判定基準）と
結論の根拠を `wip/reports/` へ記録する**。**この計画は設計（判断）までで閉じ、実装は含まない。**

**種別を `【設計】` 単独にした理由と、実装をどう扱うか**: このフェーズの成果物は「判断とその
理由」であって、コードではない。**「外す」結論になった場合は、この計画へ節を追記するのではなく、
別ファイル `wip/plans/【実装】gemini生成対象の除外.md`（＋`.html`）を flow-id 3-1 として新規に
作成し、3-2〜3-5 の合意を経てから実装する**。同じファイルへ追記すると、追記した実装方針に
合意を取る地点がフローの中に無くなり（実装が flow-id 3-6 で設計結論と同時に走り、人間が見るのは
3-8 の事後レビューだけになる）、種別を分けた意味が運用上まったく達成されない。対象は配布される
実装スクリプトとその出力176ファイルの削除なので、事後レビューだけで済ませる粒度ではない。
ファイル名と中身が食い違わないという副次的な利点もある（`wip/plans/【*.md` は種別で読まれる）。

## 判定基準（これで決める）

3ディレクトリを**同じ物差しで**測る。物差しをディレクトリごとに変えると、issue本文の見立て
（hooks/scripts は不要・docs は要る）をなぞるだけになる。

| 軸 | 問い | 「外す」へ倒れる条件 |
|---|---|---|
| 1. 読まれるか | そのパスを**実行時に読む／実行する**経路（hook `command`・スクリプト呼び出し・設定キー）があるか。**相対リンクは軸2で数え、軸1では数えない** | 0件 |
| 2. 自己完結が壊れないか | 外したとき、**残るファイルから**切れる相対リンクが出るか | 0件、または切れても許容できる理由がある |
| 3. 外すコスト | 実装・テスト・ドキュメント追随・**配布先の移行**に何が要るか | 追随箇所が特定でき、いずれも機械的に直せる |
| 4. 外す利得 | 何がどれだけ減るか | 利得が軸2・軸3のコストを上回る |

**軸1の「経路」を実行時のものに限るのは、事実A・Bが数えたのがそれだからである。** 相対リンクまで
含めて読むと hooks/scripts も0件ではなくなり（事実E）、軸1の結論が反転する。**同じ物差しで測る
という要点は、目盛りの定義を1つに固定して初めて成立する。**

**4軸の合成規則**: **軸1が0件で、かつ軸2を満たすものだけを「外す候補」とし、軸3・軸4で最終判断
する**（軸1・軸2は必要条件、軸3・軸4は判断材料）。軸2の「切れても許容できる理由がある」を採る
場合、**許容の判断は人間が行い、その理由と切れる件数を flow-id 3-6 のレポートの「実施した内容と
結果」へ書く**（1行の自己申告で条件を満たせないようにする）。

**軸1で「0件」を根拠に外すなら、同じ根拠が当たる `.gemini/rules/` `.gemini/skills/` を外さない
理由も同時に説明できなければならない**（事実D）。説明できないなら、その根拠は3ディレクトリの
採否を決める根拠として使えない。**この整合性チェックを判定基準の一部として明示的に置く**のが、
この計画の要点である。

## この計画で決めること・決めないこと

**決めること**（結論が「外す」の場合に限り必要になるものを含む）:

- 3ディレクトリそれぞれの採否と、その理由。
- **既存の配布先の移行方針**（事実I）。次の3つから選ぶ。
  1. 移行手順を `.claude/docs/spec/sync-gemini-assets.md` へ書き、配布先の手動実行に委ねる
  2. `install-to-project.sh` 側で、除外したディレクトリの残骸だけを sync の前に消す
  3. 何もしない（配布先が `--check` の失敗に気づいた時点で対処する）

**決めないこと（スコープ外）**:

- **`.gemini/rules/` `.gemini/skills/` `.gemini/agents/` の採否**。issue #172 が対象にするのは
  3ディレクトリであり、事実Dはそれらを**外す根拠**としてではなく、**3ディレクトリを外す根拠の
  整合性を検査する材料**として使う。`.gemini/` 全体に何を置くかの再設計は、Gemini CLI 実機で
  読み込み経路を観測できるようになった時点で別issueとして扱う（この線引き自体を結論へ記録する）。
- **`.claude/docs/ddr/i0127-01-….md:132` の切れリンク**（issue #133 の改番で旧ファイル名が残った
  既存の欠陥）。本issueのスコープ外なので、扱いはフェーズ4（flow-id 4-1）で決める。
- **`check-doc-references.sh` の検出範囲そのもの**（絶対パス形式に限る、というDDR `i0171-01` の
  限定）。相対リンクの切れを検出できないことは調査で確認したが、その限定を見直すかは本issueの
  対象外である。**ただし同スクリプトの除外定義（`CHECK_DOC_REFERENCES_EXCLUDED_DIRS` の
  `".gemini/scripts/test/"`）は別の話で、`scripts/` を外す場合の追随対象に含める**（下記「進め方」6）。
- **Gemini CLI 実機での動作確認**（実行環境に CLI が無い。全体作業計画のスコープ外に既出）。

## 進め方（flow-id 3-6 で行うこと）

1. 判定基準の4軸を3ディレクトリへ**それぞれ独立に**当て、表として書き出す。
2. 軸1の整合性チェック（事実D）を通す。通らない案は、その旨を明記して落とす。
3. 合成規則に従って案1〜案3から1つを選び、**選ばなかった案を却下した理由**まで書く
   （フェーズ4でDDRの「却下した案」節へそのまま移せる粒度で書く）。
4. **結論に「未観測のまま判断した」ことを明記する**（事実H）。どの結論を選んでも、根拠は
   実機観測ではなく生成物と設定からの推論である。
5. **再検討の条件を書く**（何が観測できたら、この判断を見直すのか）。
6. 「外す」を選んだ場合は、**この計画をここで閉じ**、別ファイルの `【実装】` 計画（flow-id 3-1）へ
   進む。その計画が持つべき項目は次のとおり（ここでは実装しない）。
   - `is_copy_excluded` の変更。**変更前**は次の3行である。

     ```bash
     for p in "${COPY_EXCLUDED_PREFIXES[@]}"; do
       [ "$rel" = "$p" ] && return 0
     done
     ```

     **変更後の形は「素朴な前方一致」にしてはいけない。** `case "$rel" in "$p"*)` へ変えると、
     既存の唯一の要素 `.claude/settings.json` が**前方一致のパターンへ意味を変え**、将来の
     `.claude/settings.json.bak` のようなファイルまで無言で除外対象になる。ディレクトリ除外に
     必要なのは `"$p"` または `"$p"/*` の一致である。また同関数には既に
     `case "$rel" in .claude/agents/*.md) return 0 ;; esac` の分岐があるので、判定の順序と
     責務を混ぜないこと。除外配列へ足す要素も列挙する。
   - `test_sync_gemini_assets.sh` の T8 へ「除外したディレクトリが出力に無いこと」と
     **「除外していないディレクトリは残ること」の対**を追加する（後者が無いと、判定が全件除外へ
     壊れても気づけない）。
   - **`bash .claude/scripts/src/sync-gemini-assets.sh --force`** で `.gemini/` を再生成する。
     **`--force` が要る。** write モードは「生成物に含まれないファイル」が1件でもあると
     `--force` が無い限り**1バイトも書かずに中断する**ため、除外した176ファイルがまるごとこの
     検出に掛かる。`--force` は issue #70 が置いた歯止めを意図的に外す操作なので、
     「除外したディレクトリの既存ファイルは意図した削除である」という理由を添えて実行する。
   - **削除される176ファイルをコミットに含める**（`.gemini/` は Git 管理下）。
   - `scripts/` を外す場合は、`.claude/scripts/src/check-doc-references.sh:9,14` の
     `CHECK_DOC_REFERENCES_EXCLUDED_DIRS` から `".gemini/scripts/test/"` を除き、
     `.claude/docs/spec/check-doc-references.md:49` の除外表も直す（放置すると**存在しない
     ディレクトリを指す死んだ設定**が無言で残る。検出する仕組みは無い）。
   - 上で選んだ配布先の移行方針を実装する。
7. 結果を `wip/reports/日付_mellow-drifting-lantern_gemini生成対象の採否.md`（＋同名 `.html`）へ
   記録する。**この計画ファイルへ結果を書かない。**

## 検証

**結論が「残す」の場合。**

```bash
bash .claude/scripts/src/sync-gemini-assets.sh --check ; echo "exit=$?"   # → 0
bash .claude/scripts/test/test_sync_gemini_assets.sh | tail -1            # → passed=91 failures=0
```

- 上の2つは**変更前から通る**（調査で実測済み）。したがって**これだけでは検証にならない**。
  「残す」を選んだ場合の検証は、**判定基準の4軸すべてに3ディレクトリ分の答えが書かれていること**
  と、**却下した案2・案3の理由が書かれていること**をレポートで確かめることである。

**結論が「外す」の場合**（実装は別ファイルの `【実装】` 計画で行うが、検証の形はここで決めておく）。
**目視ではなく件数で見る。**

```bash
# 除外した側は0件、残す側は非0件、という対で見る（片側だけでは全件除外の事故を検出できない）
for d in hooks scripts docs;  do printf '%s=%s\n' "$d" "$(find ".gemini/$d" -type f 2>/dev/null | wc -l)"; done
for d in rules skills agents; do printf '%s=%s\n' "$d" "$(find ".gemini/$d" -type f 2>/dev/null | wc -l)"; done
bash .claude/scripts/test/test_sync_gemini_assets.sh | tail -1   # → passed=N failures=0（Nは91より増える）
bash .claude/scripts/src/sync-gemini-assets.sh --check ; echo "exit=$?"   # → 0
bash .claude/scripts/src/check-dist-coverage.sh ; echo "exit=$?"          # → 0
```

- **T8 の追加が空振りしないことを確かめる。** 追加したアサーションが、`is_copy_excluded` を
  完全一致へ戻した状態で**実際に落ちる**ことを一度確認する（落ちなければ、そのテストは
  除外の実装を固定していない）。
- 切れる相対リンクの件数を、調査と同じ手順（リンク解決）で**再測して記録する**。事前の見込みは
  hooks/scripts のみなら2件、3つすべてなら18件。
- **配布先の移行方針を実装した場合は、`test_install_to_project.sh` で「古い3ディレクトリを持つ
  配布先へ再適用したとき、それが残らないこと」を確かめる**（事実I。方針3〈何もしない〉を選んだ
  場合は、その旨を spec へ書いたことをもって代える）。
