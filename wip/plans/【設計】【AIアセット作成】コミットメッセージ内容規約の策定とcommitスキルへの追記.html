決めること（設計）

決定1: 件名1行は必須・本文は任意で許容する

調査で実測が4点揃っているため、この方針を採る。この計画のレビューで覆る余地は残すが、覆す場合は下記の実測のどれを否定するかを示す必要がある。

根拠実測の出所
実装変更が不要（create-commit.sh は改行入りメッセージをそのまま通す）調査Q3
本文はsquash後も main へ恒久的に残る調査Q4
実務側は既に本文を書いており、現行規約のほうが実態から乖離している（本文6件・フッター6件）調査Q2
issue-mr-flow/SKILL.md:229（確認結果を必ずコミットメッセージへ残す）が1行縛りと衝突調査Q5
1行目の根拠には限界がある（Linux実機限定）

調査の「確かめられなかったこと」が明記しているとおり、Q3の実測はすべてLinux（Claude Code on the web）で行っており、git bash（Windows）実機では未計測である。本リポジトリの標準実行環境はgit bash（.claude/rules/shell-script-style.md「前提」）なので、この未計測は残る。改行の扱いは git commit -m へ委ねられており処理系差は考えにくいが、断定はしない。 実機確認はフェーズ4のDDRへ「未計測である事実」として引き継ぐ。

本文を「任意」にするか「特定の場面では必須」にするかは、この計画で決める。 現時点の案は「原則任意。ただし件名だけでは要素を満たせない場合は本文へ書く」で、「必ず本文を書け」とはしない（守られない規約を増やさないため）。

決定1-b: 本文以外のフッター（Refs #NNN 等）を許容するか

置き換え対象の146行は役割を3つ兼ねている（初版は2つと数えていた）。

役割扱い
(1) 本文の禁止決定1で置き換える
(2) フッター全般の禁止（Refs #NNN 等）決定1-b で決める。初版はこの役割を見落としていた
(3) Co-Authored-By の禁止方針に関わらず維持する
  • (3) の維持先である31行は、(2) を代替しない。 31行が禁じているのは「Co-Authored-By: Claude などのフッター」であり、Refs #NNN を禁じているとも許しているとも読める。146行を消すだけでは、(2) の可否が誰にも決められない状態になる。
  • 調査Q2で Refs #NNN フッターが6件マージ済みと実測されている。「禁止のまま」と「許容へ変える」で実務の扱いが正反対になるため、どちらかを明文で決める。
  • 現時点の案は「Refs #NNN のような追跡用フッターは許容する。ただしAIの生成物であることを示すフッター（Co-Authored-By: Claude 等）は引き続き絶対禁止」。前者は人間が書いても同じ形になる情報で、後者とは性質が違う。

決定2: 件名が満たすべき要素

issue #185 が問題視しているのは「対象＋動詞で終わる」形なので、動詞の先を要求する形にする。要素の粒度と個数はこの計画のレビューで確定させる。

要素内容省略してよい場合
何を変更した対象（ファイル・機能・概念）省略不可
どうどう変えたか（変更後の状態・採った手段）省略不可
なぜ変更の理由対象と手段から自明なら省略可。本文へ回してもよい
「どう」の判定基準は、調査の実測と同じ形で書く

調査Q2 (a) の51件（64%）は次のコマンドで数えたものなので、規約の不合格基準もこれに揃える。

grep -cE '(を|の)?(修正|更新|反映|追加|作成|記録)(する|)$'
  • 対象の語は 6語（修正 更新 反映 追加 作成 記録）。初版は3語しか挙げていなかった。
  • 語尾は 「〜する」「〜した」「体言止め（〜更新）」のいずれも対象とする。上の正規表現が拾うのは非過去形（〜を更新 / 〜を更新する）だけで、初版が書いていた「〜更新した」は1件も一致しない。実測の多数派である「docs: HANDOFFを更新」型を規約が取り逃がさないよう、語尾を明示的に列挙する。
  • 64%という数値を引用するときは「この6語で終わる形」と正確に添える。

決定3: 成果物の変更を伴わないコミットの書き方（受け入れ条件5）

調査で main に残らない成果物のみのコミットが 58%、事務的作業記録が 15% あった。この多数派の書き方を決めないと、規約は守られない側が多数になる。

類型現状の書かれ方規約で求める形（案）
HANDOFF.md の進捗更新のみdocs: HANDOFFを更新どのflow-idが何になったかを書く
wip/plans/ wip/worklogs/ wip/reports/ のみの変更docs: 計画を修正何を変えたか（どの節・どの判断が変わったか）を書く
Draft PR作成のための空コミットchore: 空コミット（baseとの差分が無いため）現状の形で足りる。例外として明記する

決定4: PRタイトルが1行ログに出る事実を規約へ書くか

調査Q4で、git log --oneline に出るのはPRタイトルであり、個別コミットの件名はsquash本文の中にしか現れないと実測できた。

  • 書く場合: 「コミットメッセージを直せば --oneline が読めるようになる」という誤解を防げる。
  • 書かない場合: commit スキルの守備範囲（コミットの作り方）から外れる。

現時点の案は「注記として1段落だけ書く」。PRタイトルの規約そのものは本issueのスコープ外とし、必要なら別issueへ切り出す。
