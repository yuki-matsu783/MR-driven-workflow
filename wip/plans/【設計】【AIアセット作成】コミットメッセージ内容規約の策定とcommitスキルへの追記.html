決めること（設計）

決定1: 件名1行は必須・本文は任意で許容する

調査で実測が4点揃っているため、この方針を採る。この計画のレビューで覆る余地は残すが、覆す場合は下記の実測のどれを否定するかを示す必要がある。

根拠実測の出所
実装変更が不要（create-commit.sh は改行入りメッセージをそのまま通す）調査Q3
本文はsquash後も main へ恒久的に残る調査Q4
実務側は既に本文を書いており、現行規約のほうが実態から乖離している（本文6件・フッター6件）調査Q2
issue-mr-flow/SKILL.md:229（確認結果を必ずコミットメッセージへ残す）が1行縛りと衝突調査Q5

現時点の案は「原則任意。ただし件名だけでは要素を満たせない場合は本文へ書く」で、「必ず本文を書け」とはしない（守られない規約を増やさないため）。

決定2: 件名が満たすべき要素

issue #185 が問題視しているのは「対象＋動詞で終わる」形なので、動詞の先を要求する形にする。要素の粒度と個数はこの計画のレビューで確定させる。

要素内容省略してよい場合
何を変更した対象（ファイル・機能・概念）省略不可
どうどう変えたか（変更後の状態・採った手段）省略不可
なぜ変更の理由対象と手段から自明なら省略可。本文へ回してもよい
「どう」の判定基準を文面へ入れる

「修正した」「更新した」「反映した」で終わる行は、どう変えたかを述べていないため不合格とする（調査で母数の 64% がこの形）。

決定3: 成果物の変更を伴わないコミットの書き方

調査で main に残らない成果物のみのコミットが 58%、事務的作業記録が 15% あった。この多数派の書き方を決めないと、規約は守られない側が多数になる。

類型現状の書かれ方規約で求める形（案）
HANDOFF.md の進捗更新のみdocs: HANDOFFを更新どのflow-idが何になったかを書く
wip/plans/ wip/worklogs/ wip/reports/ のみの変更docs: 計画を修正何を変えたか（どの節・どの判断が変わったか）を書く
Draft PR作成のための空コミットchore: 空コミット（baseとの差分が無いため）現状の形で足りる。例外として明記する

決定4: PRタイトルが1行ログに出る事実を規約へ書くか

調査Q4で、git log --oneline に出るのはPRタイトルであり、個別コミットの件名はsquash本文の中にしか現れないと実測できた。

  • 書く場合: 「コミットメッセージを直せば --oneline が読めるようになる」という誤解を防げる。
  • 書かない場合: commit スキルの守備範囲（コミットの作り方）から外れる。

現時点の案は「注記として1段落だけ書く」。PRタイトルの規約そのものは本issueのスコープ外とし、必要なら別issueへ切り出す。

2. issue本文の実例9行の書き直し例

素材は統計の母数の外にある

issue #185 の本文が挙げた9行はissue #110 のPR由来で、調査で固定した母数（直近5件・80件）には含まれない。issue本文から直接9行を引き写し、統計とは別枠であることを明示する（母数を広げて統計を取り直さない）。

書き直し例は wip/reports/…内容規約の策定.md へ表として置く。規約が実際に適用できることの検証を兼ねるため、9行すべてを対象にし、1行も飛ばさない。

9行のうち1行（Fix formatting and clarify task types in workflow doc）は英語・prefix無しである。規約は日本語・prefix必須なので、書き直し例では両方を直す。英語コミットが生まれた経路の調査はスコープ外。
