## 残る設計判断（flow-id 3-3 で承認を得る）

### H-1. 初期辞書の中身

**提案: 現行12語から `ok`/`OK` を除いた10語をそのまま初期値にする。**

```
はい / うん / お願い / お願いします / よろしく / 続けて / 続けてください / ありがとう / ありがとうございます / 了解
```

**理由**: フェーズ2の実測（真の発言7件）ではこの10語のうち1語も働かなかったが、これは
「不要と確認された」ことを意味しない——単に**この断面に登場しなかった**だけである。
机上の判断で先回りして削ると、後から本当に必要だった語を消したことになりかねない。
**「育てる」の出発点は観測実績ではなく現行の網羅にし、以後は下記H-3の可視化を見ながら
削っていく**（削るほうが安全——辞書は完全一致なので、削っても後から戻せる）。

### H-2. 辞書の置き場所

**提案: プレーンテキストファイル `.claude/hooks/session-start-ack-words.txt` に切り出す。**

- 1行1語（正規化後の形で書く）。`#` で始まる行はコメント（削除・追加の理由を書ける）。空行は無視。
- UTF-8・BOM無し・LF改行で保存し、`.gitattributes` へ `.claude/hooks/session-start-ack-words.txt text eol=lf`
  を追加する（`.claude/rules/shell-script-style.md`の`.sh`規約と同じ理由。改行がCRLFに化けると
  `case`パターンマッチが壊れる）。
- **理由**: 辞書を`session-start.sh`内のbash配列に直書きすると、1語増減するだけでもスクリプト
  本体を編集することになり、「育てる」操作のハードルが上がる。独立ファイルなら、
  Write/Editツール（または人間のエディタ）で1行足し引きするだけで済み、差分も1行になる。
- **却下した案**: JSON形式（語ごとに理由・追加日等のメタデータを持たせる）。今回はメタデータの
  必要性が実測で確認できておらず（H-4のとおり理由はコミットメッセージに残る）、構造を持たせる
  コストに見合わない。将来メタデータが要ると分かった時点で移行を検討する。

### H-3. 除外実績の可視化（最重要）

**提案: 2段構えにする。**

1. **注入テキストへの当該セッション分の内訳**: そのセッションで1件でも除外があれば、
   ユーザー発言節の末尾へ1行足す。

   ```
   - 相槌等として除外: ok×1, はい×1
   ```

   辞書語と件数だけで、**除外された発言の本文は出さない**（下記の秘密情報の理由と同じ）。

2. **累積カウントのローカル状態ファイル**: `wip/state/session-start-ack-exclusion-counts.json`
   （`.gitignore`の`/wip/state/`で既に除外対象。issue #184で導入済みのディレクトリを流用するため
   新規の除外パターンは不要）。辞書語をキーに、除外した累積件数を持つ。

   ```json
   {"ok": 3, "はい": 1}
   ```

   セッションごとに読み込み、今回分を加算して書き戻す。**このファイルにも発言の本文は書かない**
   （語と件数のみ。問い5がとった記録方針「どの辞書語が何件落としたか」と同じ形）。

- **理由**: 「毎回のユーザの入力を見ながら育てる」を成り立たせるには、まず**何かが落ちたことに
  気づける**必要がある。当該セッションの内訳（1）は即座に気づける経路、累積カウント（2）は
  「`ok`が何度も引っかかる」のような**傾向**に気づける経路で、役割が異なるため両方持つ。
- **秘密情報の扱い**: 除外された発言の本文は、注入テキストにも状態ファイルにも一切書かない。
  `.claude/rules/shell-script-style.md`「秘密情報の扱い」の「そもそも値を出さない形にできないか
  を先に考える」に従う。本文が要る判断（「本当にこれは相槌か」）は、人間が該当セッションの
  transcriptを自分で開けば足りる——hookが本文を持ち歩く必要は無い。
- **却下した案**: 除外した発言の本文をログへ残す（過剰除去の判断がしやすくなる一方、
  秘密情報を平文でローカルに蓄積することになる。上記の代替で足りると判断）。

### H-4. 育てた操作の記録先

**提案: 新しい記録先を作らない。辞書ファイル（H-2）自体のgit履歴を記録先にする。**

辞書語の追加・削除は、`session-start-ack-words.txt` の1行編集として行い、`commit`スキル経由の
コミットメッセージへ理由を書く（`.claude/skills/commit/SKILL.md`「コミットメッセージの内容規約」
に従い、「何を・どう・なぜ」を満たす）。恒久的な設計判断（辞書という方式そのものの採否等）は
従来どおり`.claude/docs/ddr/`へ書く。

**理由**: 専用の記録先を新設すると、育てる操作のたびに2箇所（辞書ファイルと記録先）を更新する
ことになり、更新漏れが起きる。git履歴は編集のたびに必ず残るため、これ以上のインフラは不要。

### E. 単一transcript前提への対処方針

**提案: 過去transcriptの走査は実装せず、`HANDOFF.md`「次にやること」節の既存の注入で代替する。**

3案（先頭枠を諦める／過去transcriptも対象にする／`HANDOFF.md`側で代替する）のうち、
`HANDOFF.md`側での代替を採る。

- **理由1（既に半分実装済み）**: `build_work_context`は既に`HANDOFF.md`「次にやること」節を
  毎セッション注入している（既存機能）。複数transcriptにまたがるタスクの継続性は、この既存機能が
  一定量カバーしている。本機能が追加するのは「人間の生の言葉」であって、`HANDOFF.md`が持つ
  「AIによる要約」とは性質が違うが、**要約側は既に動いている**。
- **理由2（コストに見合わない）**: 過去transcriptを対象にするには、同一ブランチの過去
  transcriptファイルを列挙し、`uuid`重複除去を複数ファイルへ拡張し、走査コストが本数倍に
  増える。フェーズ2の問い10aで**この実行環境では過去transcriptが0本**だったため、
  実装する効果が実測できない。
- **理由3（フェーズ2の停止条件に沿う）**: 個別調査計画は「この実行環境では取得できなかった、
  という事実であって実装不能ではない」としており、**ローカル（Windows）環境で過去
  transcriptが残るかは未確認のまま**である。未確認の前提の上に複雑な実装を積むのは、
  本計画の「実装上の制約」（規約）が求める手堅さに反する。
- **今回やらないことの記録**: `.claude/docs/spec/`（flow-id 4-6）へ「単一transcript前提の限界」
  として明記し、対象外の判断を恒久的な記録として残す。

### C. 母集団が0件になったことに気づける形

**提案: 追加の実装は行わない。既存の「N=0なら節ごと出さない」方針のままにする。**

- **理由**: 「母集団が0件になったこと」への気づきは、上記H-3の可視化（除外件数）と、
  下記の単体テスト（抽出条件の回帰防止）の**2つで別の角度からカバーできる**。
  除外0件・抽出0件の両方を実行時に区別して警告する仕組みを足すと、「取れた分だけ出す・
  fail-openを崩さない」という既存設計（DDR i0057-01）に例外を作ることになる。
  **リスクは実装のバグによる回帰であり、それは単体テストの役割**——実行時の自己診断ではなく
  テストで防ぐ。

別issueは今は起票しない（必要になった時点で起票する）。

- **理由**: `tool_result`の構造（`Your questions have been answered: "<質問>"="<回答>"`）を
  母集団へどう混ぜるかは、抽出条件の設計をやり直すのに近い規模の変更になりうる。

## 方針

### 抽出パイプライン（1回のjq呼び出しに集約する）

`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」に従い、抽出・母集団確定・
除外規則適用・ブランチ絞り・`uuid`重複除去・先頭/直近の採り方・切り出し・バイト数計算までを
**`UserUtteranceSelect.jq` 1本のjq呼び出しでまとめて行う**。

```bash
jq -R -n -f "$lib_dir/UserUtteranceSelect.jq" \
  --arg branch "$branch" \
  --rawfile ack_words_raw "$ack_words_path" \
  --argjson head_count "$USER_UTTERANCE_HEAD_COUNT" \
  --argjson tail_count "$USER_UTTERANCE_TAIL_COUNT" \
  ... \
  < "$transcript_path"
```

- パス名を引数で渡さず**標準入力へ繋ぐ**（フェーズ2問い7の結論。git bashでのパス表記問題を回避）。
- 辞書は`--rawfile`でテキストごと渡し、jq側で改行分割・コメント行/空行除去を行う
  （`split("\n") | map(select(startswith("#") or length == 0 | not))`）。
- 出力は1つのJSONオブジェクトにまとめる。

  ```json
  {
    "selected": [{"text": "整形済み文字列", "isHead": true}, ...],
    "excludedCounts": {"ok": 1},
    "populationCount": 7
  }
  ```

  bash側はこのJSONを`jq -r`で崩し、注入テキスト・除外内訳行・累積カウント更新用の入力を作る
  （bash・jq間の受け渡しも1回で済ませる）。

### 抽出条件（フェーズ2確定分。実装で崩さない）

`type=="user"` ＋ `.message.content`が文字列 ＋ `userType=="external"` ＋ `isSidechain==false` ＋
`origin.kind=="human"`。**肯定形を崩さない**（`origin.kind != "task-notification"`のような
否定形にしない。`origin`キーを持たない行が混入するため。個別調査計画・問い12）。

### 除外規則

1. 辞書（`session-start-ack-words.txt`）との**正規化後の完全一致**。正規化は前後の空白・
   句読点・感嘆符・記号の除去。
2. 引数の無いスラッシュコマンド単体（`^/[A-Za-z][A-Za-z0-9:_-]*$`）。
3. `<command-name>` 等のタグで始まる行。

除外が発生するたびに`excludedCounts`へ辞書語（規則1のみ）をキーとして加算する。規則2・3は
辞書ではないため`excludedCounts`の対象外（可視化はH-3の対象を辞書語に限定しているため）。

### ブランチ絞り・重複除去・採り方・切り出し・サイズ

いずれもフェーズ2確定のロジックをそのまま実装する（個別調査計画・調査結果レポートが正。
ここでの再掲はしない）。

- ブランチ絞り: 行が`gitBranch`を持ち、かつ現在のブランチと一致するものが1件以上あるときだけ絞る。
- `uuid`による重複除去。
- 先頭`min(3,N)`件 ＋ 残りの末尾`min(7, N-min(3,N))`件（重複なし）。
- 切り出しは`jq`の`.[0:N]`。先頭枠は頭120字＋末尾40字、直近枠は頭80字＋末尾30字
  （全長がその合計以下なら全文）。
- 節全体のバイト上限`USER_UTTERANCE_MAX_BYTES`（既定6000）。超えた場合は直近枠の古い側から
  1件ずつ落とす。先頭枠は落とさない。それでも収まらなければ節ごと出さない。

### 出力位置と`append_size_warning`の変更

`build_work_context`内、「`HANDOFF.md`次にやること」ブロックの直後・SKILL.md再読み込み指示の
**手前**へ挿入する（issue #113の末尾配置を維持）。

`append_size_warning`は現在`(text, limit)`の2引数。**`(text, excluded_bytes, limit)`の3引数へ
変更**し、`effective_bytes = context_text_bytes(text) - excluded_bytes`で判定する。警告文には
「全体Nバイト（うち再注入分Mバイトを除外して判定）」の両方を出す（サイズの扱い節の合意どおり）。
既存呼び出し元（`main`）も新しい引数を渡すよう変更する。

### fail-open

`transcript_path`が空・不正・壊れたJSONの場合、`UserUtteranceSelect.jq`の呼び出しが失敗しても
`build_user_utterance_context`は空文字列を返し（`build_context`全体は失敗させない）、
他の注入項目（ブランチ・issue・PR等）は通常どおり出す。

| 16 | 除外が1件も無いセッション | 除外内訳の行が出ない |
