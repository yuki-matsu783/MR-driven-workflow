## 残る設計判断（flow-id 3-3 で承認を得る）

### H-1. 初期辞書の中身

**提案: 現行12語から `ok`/`OK` を除いた10語をそのまま初期値にする。**

```
はい / うん / お願い / お願いします / よろしく / 続けて / 続けてください / ありがとう / ありがとうございます / 了解
```

**理由**: フェーズ2の実測（真の発言7件）ではこの10語のうち1語も働かなかったが、これは
「不要と確認された」ことを意味しない——単に**この断面に登場しなかった**だけである。
机上の判断で先回りして削ると、後から本当に必要だった語を消したことになりかねない。
**「育てる」の出発点は観測実績ではなく現行の網羅にし、以後は下記H-3の可視化を見ながら
削っていく**（削るほうが安全——辞書は完全一致なので、削っても後から戻せる）。

### H-2. 辞書の置き場所

**提案: プレーンテキストファイル `.claude/hooks/session-start-ack-words.txt` に切り出す。**

- 1行1語（正規化後の形で書く）。`#` で始まる行はコメント（削除・追加の理由を書ける）。空行は無視。
- UTF-8・BOM無し・LF改行で保存し、`.gitattributes` の`dist:begin`〜`dist:end`マーカーの
  **内側**へ `.claude/hooks/session-start-ack-words.txt text eol=lf` を追加する
  （`.claude/rules/shell-script-style.md`の`.sh`規約と同じ理由。マーカーの内側にしないと
  配布先ではLFが保証されない。issue #151フェーズ3敵対的レビュー指摘）。改行がCRLFに化けると、
  辞書照合は`jq`の完全一致比較のため一致しなくなる（`case`パターンマッチではない。
  同レビュー指摘——当初の理由記述が誤っていた）。
- **理由**: 辞書を`session-start.sh`内のbash配列に直書きすると、1語増減するだけでもスクリプト
  本体を編集することになり、「育てる」操作のハードルが上がる。独立ファイルなら、
  Write/Editツール（または人間のエディタ）で1行足し引きするだけで済み、差分も1行になる。
- **却下した案**: JSON形式（語ごとに理由・追加日等のメタデータを持たせる）。今回はメタデータの
  必要性が実測で確認できておらず（H-4のとおり理由はコミットメッセージに残る）、構造を持たせる
  コストに見合わない。将来メタデータが要ると分かった時点で移行を検討する。

### H-3. 除外実績の可視化（最重要）

**提案: 2段構えにする。**

1. **注入テキストへの当該セッション分の内訳**: そのセッションで1件でも除外があれば、
   ユーザー発言節の末尾へ1行足す。

   ```
   - 相槌等として除外: はい×1, ありがとう×1
   ```

   辞書語と件数だけで、**除外された発言の本文は出さない**（下記の秘密情報の理由と同じ）。
   **選定結果（`selected`）が0件になった場合でも、除外が1件以上あればこの行だけは出す**
   （下記「全件除外時の扱い」）。

2. **累積カウントのローカル状態ファイル**: `wip/state/session-start-ack-exclusion-counts.json`
   （`.gitignore`の`/wip/state/`で既に除外対象。issue #184で導入済みのディレクトリを流用するため
   新規の除外パターンは不要）。辞書語をキーに、除外した累積件数と、重複計上を防ぐための
   `uuid`集合を持つ。

   ```json
   {
     "counts": {"はい": 3, "ありがとう": 1},
     "countedUuids": ["c1a2...", "9f3e..."]
   }
   ```

   セッションごとに読み込み、**まだ`countedUuids`に無い`uuid`の除外イベントだけ**を加算して
   書き戻す（下記「重複計上対策」）。**このファイルにも発言の本文は書かない**
   （語と件数、および重複除去用の`uuid`のみ。問い5がとった記録方針「どの辞書語が何件落としたか」
   と同じ形。`uuid`はtranscript上の識別子であり発言本文ではない）。

- **重複計上対策（issue #151フェーズ3敵対的レビュー指摘）**: SessionStart hookはstartup/resume/
  clear/compactのたびに発火し、同一セッションで同じtranscriptを何度も読み直す
  （個別調査計画・調査結果レポートで実測済み）。素朴に「今回加算して書き戻す」だけだと、
  同じ除外イベントを再発火のたびに数え直してしまう。**除外イベントごとに元行の`uuid`を
  キーとして`countedUuids`集合と突き合わせ、未計上のものだけ加算する。** 集合はセッションを
  横断して蓄積されるが、値は短い文字列（`uuid`）のみでファイルサイズへの影響は軽微であり、
  このファイル自体がローカル状態（gitignore対象）のため無制限に肥大化しても実害は無い。
- **状態ファイルの破損・空・並行書き込みへの備え（issue #151フェーズ3敵対的レビュー指摘）**:
  `.claude/rules/shell-script-style.md`「JSON操作」の教訓（issue #37と同型の恒久回復不能）を
  踏まえ、読み込み前に**空文字チェック→`jq -e .`の順で検証**し、いずれかに失敗したら
  「状態なし」（`counts={}`・`countedUuids=[]`）へフォールバックする。書き込みは
  一時ファイルへ書いてから`mv`する（原子的な置き換え。並行書き込みでも壊れたファイルが
  残らない）。
- **理由**: 「毎回のユーザの入力を見ながら育てる」を成り立たせるには、まず**何かが落ちたことに
  気づける**必要がある。当該セッションの内訳（1）は即座に気づける経路、累積カウント（2）は
  「`はい`が何度も引っかかる」のような**傾向**に気づける経路で、役割が異なるため両方持つ。
- **秘密情報の扱い**: 除外された発言の本文は、注入テキストにも状態ファイルにも一切書かない。
  `.claude/rules/shell-script-style.md`「秘密情報の扱い」の「そもそも値を出さない形にできないか
  を先に考える」に従う。本文が要る判断（「本当にこれは相槌か」）は、人間が該当セッションの
  transcriptを自分で開けば足りる——hookが本文を持ち歩く必要は無い。
- **却下した案**: 除外した発言の本文をログへ残す（過剰除去の判断がしやすくなる一方、
  秘密情報を平文でローカルに蓄積することになる。上記の代替で足りると判断）。

### 全件除外時の扱い（H-3と関連。issue #151フェーズ3敵対的レビュー指摘）

**除外内訳行は、`selected`が0件になった場合でも独立に出す。** 現在の「N=0なら節ごと出さない」
という既存方針（DDR i0057-01）は保つが、それは「発言そのものが1件も選ばれなかった場合に
ユーザー発言節の見出し・本文を出さない」という意味であり、**除外内訳行はこの判定に含めない**。
辞書との一致・バイト上限超過などで`selected`が全滅しても`excludedCounts`が1件以上あれば、
除外内訳行だけを（見出しなしで）出す。**気づきたい度合いが最大の状況
（全件が相槌等として落ちた、または全件がバイト上限で切り落とされた）でこそ、この行が
唯一の手がかりになる。**

### H-4. 育てた操作の記録先

**提案: 新しい記録先を作らない。辞書ファイル（H-2）自体のgit履歴を記録先にする。**

辞書語の追加・削除は、`session-start-ack-words.txt` の1行編集として行い、`commit`スキル経由の
コミットメッセージへ理由を書く（`.claude/skills/commit/SKILL.md`「コミットメッセージの内容規約」
に従い、「何を・どう・なぜ」を満たす）。恒久的な設計判断（辞書という方式そのものの採否等）は
従来どおり`.claude/docs/ddr/`へ書く。

**理由**: 専用の記録先を新設すると、育てる操作のたびに2箇所（辞書ファイルと記録先）を更新する
ことになり、更新漏れが起きる。git履歴は編集のたびに必ず残るため、これ以上のインフラは不要。

### E. 単一transcript前提への対処方針

**提案: 過去transcriptの走査は実装せず、`HANDOFF.md`「次にやること」節の既存の注入で代替する。**

3案（先頭枠を諦める／過去transcriptも対象にする／`HANDOFF.md`側で代替する）のうち、
`HANDOFF.md`側での代替を採る。

- **理由1（既に半分実装済み）**: `build_work_context`は既に`HANDOFF.md`「次にやること」節を
  毎セッション注入している（既存機能）。複数transcriptにまたがるタスクの継続性は、この既存機能が
  一定量カバーしている。本機能が追加するのは「人間の生の言葉」であって、`HANDOFF.md`が持つ
  「AIによる要約」とは性質が違うが、**要約側は既に動いている**。
- **理由2（コストに見合わない）**: 過去transcriptを対象にするには、同一ブランチの過去
  transcriptファイルを列挙し、`uuid`重複除去を複数ファイルへ拡張し、走査コストが本数倍に
  増える。フェーズ2の問い10aで**この実行環境では過去transcriptが0本**だったため、
  実装する効果が実測できない。
- **理由3（フェーズ2の停止条件に沿う）**: 個別調査計画は「この実行環境では取得できなかった、
  という事実であって実装不能ではない」としており、**ローカル（Windows）環境で過去
  transcriptが残るかは未確認のまま**である。未確認の前提の上に複雑な実装を積むのは、
  本計画の「実装上の制約」（規約）が求める手堅さに反する。
- **今回やらないことの記録**: `.claude/docs/spec/`（flow-id 4-6）へ「単一transcript前提の限界」
  として明記し、対象外の判断を恒久的な記録として残す。

### C. 母集団が0件になったことに気づける形

**提案: 追加の実装は行わない。既存の「N=0なら節ごと出さない」方針のままにする。**

- **理由**: 「母集団が0件になったこと」への気づきは、上記H-3の可視化（除外件数）と、
  下記の単体テスト（抽出条件の回帰防止）の**2つで別の角度からカバーできる**。
  除外0件・抽出0件の両方を実行時に区別して警告する仕組みを足すと、「取れた分だけ出す・
  fail-openを崩さない」という既存設計（DDR i0057-01）に例外を作ることになる。
  **リスクは実装のバグによる回帰であり、それは単体テストの役割**——実行時の自己診断ではなく
  テストで防ぐ。

### A. `AskUserQuestion` の回答が母集団から漏れる

**提案: 本issueのスコープ外とし、flow-id 4-1で`.claude/docs/spec/`「未決定事項」へ記録する。**
別issueは今は起票しない（必要になった時点で起票する）。

- **理由**: `tool_result`の構造（`Your questions have been answered: "<質問>"="<回答>"`）を
  母集団へどう混ぜるかは、抽出条件の設計をやり直すのに近い規模の変更になりうる。

**この4点（H・E・A・C）は、flow-id 3-3の人間レビューで承認を得るまで実装へ進まない。**

## 方針

### 新しい環境変数の既定値（issue #151フェーズ3敵対的レビュー指摘）

`session-start.sh`冒頭、既存の`CONTEXT_SIZE_WARN_BYTES`（50行目）と同じ位置・同じ形
（`VAR="${VAR:-既定}"`）で次を宣言する（`set -u`配下のため、宣言漏れは未定義変数エラーで
注入全体を落とす）。

```bash
USER_UTTERANCE_HEAD_COUNT="${USER_UTTERANCE_HEAD_COUNT:-3}"
USER_UTTERANCE_TAIL_COUNT="${USER_UTTERANCE_TAIL_COUNT:-7}"
USER_UTTERANCE_MAX_BYTES="${USER_UTTERANCE_MAX_BYTES:-6000}"
```

### 抽出パイプライン（1回のjq呼び出しに集約する）

`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」に従い、抽出・母集団確定・
除外規則適用・ブランチ絞り・`uuid`重複除去・先頭/直近の採り方・切り出し・バイト数計算までを
**`UserUtteranceSelect.jq` 1本のjq呼び出しでまとめて行う**。

```bash
jq -R -n -f "$lib_dir/UserUtteranceSelect.jq" \
  --arg branch "$branch" \
  --rawfile ack_words_raw "$ack_words_path" \
  --argjson head_count "$USER_UTTERANCE_HEAD_COUNT" \
  --argjson tail_count "$USER_UTTERANCE_TAIL_COUNT" \
  ... \
  < "$transcript_path"
```

- **`transcript_path`だけ**を引数で渡さず標準入力へ繋ぐ（フェーズ2問い7の結論。動的で
  任意の位置になりうる外部パスのため、git bashでのパス表記問題を回避する）。**`-f`のフィルタ
  パス（`UserUtteranceSelect.jq`）と`--rawfile`の辞書パス（`session-start-ack-words.txt`）は
  いずれもリポジトリ内の固定相対パスであり、標準入力へ逃がす対象ではない**
  （既存`session-start.sh`が`jq`を`-f`引数で呼んでいる箇所と同じ扱い。問い7が対象にしていたのは
  「実行のたびに変わる外部ファイル」のパス表記問題であり、リポジトリ内の固定パスは対象外。
  issue #151フェーズ3敵対的レビュー指摘——当初の「パス名を引数で渡さない」という書き方は
  この2つのパスと矛盾していた）。
- 辞書は`--rawfile`でテキストごと渡し、jq側で改行分割・**各行のtrim（前後空白・CR除去）**・
  コメント行/空行除去を行う（`split("\n") | map(gsub("\r$";"") | gsub("^\\s+|\\s+$";"")) |
  map(select(startswith("#") or length == 0 | not))`）。**発言側と同じ正規化（前後空白・
  句読点等の除去）を辞書語にも適用してから比較する**（issue #151フェーズ3敵対的レビュー指摘。
  末尾空白・CRLF・字下げされたコメント行で辞書語が無言で無効化されるのを防ぐ）。
- **辞書ファイルが存在しない・読めない場合、bash側は`--rawfile`を使わず空文字列を`--arg`で渡す**
  （呼び出し前に`[ -r "$ack_words_path" ]`で分岐する。存在しないパスを`--rawfile`へ渡すと
  jq起動自体が失敗し、ユーザー発言節全体が出なくなるため。下記「除外規則」参照）。
- 出力は1つのJSONオブジェクトにまとめる。

  ```json
  {
    "selected": [{"text": "整形済み文字列", "isHead": true}, ...],
    "excludedCounts": {"はい": 1},
    "populationCount": 7
  }
  ```

  bash側はこのJSONを`jq -r`で崩し、注入テキスト・除外内訳行・累積カウント更新用の入力を作る
  （bash・jq間の受け渡しも1回で済ませる）。

  **Windows native jqはコマンド置換・パイプでも行末へCRを付与する**
  （`.claude/rules/shell-script-style.md`「文字コード」）。`excludedCounts`のキーを複数件
  ループで取り出す場合、`selected[].text`のように複数行になりうる値をコマンド置換で受ける場合の
  いずれも、**最後の要素・最終行以外にCRが残り**、辞書語との一致判定や注入テキストの内容が
  崩れる。この2箇所（`excludedCounts`のキー列挙、`selected[].text`の取り出し）は
  `| tr -d '\r'`を挟む（単一行・単一要素で完結する取り出し——`populationCount`等——には不要。
  同ルール「複数行になりうる値」の判定基準に従う。issue #151フェーズ3敵対的レビュー指摘）。

### 抽出条件（フェーズ2確定分。実装で崩さない）

`type=="user"` ＋ `.message.content`が文字列 ＋ `userType=="external"` ＋ `isSidechain==false` ＋
`origin.kind=="human"`。**肯定形を崩さない**（`origin.kind != "task-notification"`のような
否定形にしない。`origin`キーを持たない行が混入するため。個別調査計画・問い12）。

### 除外規則

1. 辞書（`session-start-ack-words.txt`）との**正規化後の完全一致**。正規化は前後の空白・
   句読点・感嘆符・記号の除去。**辞書ファイルが存在しない・空・読めない場合は、この規則を
   無効化して続行する**（辞書0語＝この規則では何も除外しない、という扱い。上記「辞書ファイルが
   存在しない・読めない場合」参照。issue #151フェーズ3敵対的レビュー指摘）。
2. 引数の無いスラッシュコマンド単体（`^/[A-Za-z][A-Za-z0-9:_-]*$`）。
3. `<command-name>` 等のタグで始まる行。

除外が発生するたびに`excludedCounts`へ辞書語（規則1のみ）をキーとして加算する。規則2・3は
辞書ではないため`excludedCounts`の対象外（可視化はH-3の対象を辞書語に限定しているため）。

### ブランチ絞り・重複除去・採り方・切り出し・サイズ

いずれもフェーズ2確定のロジックをそのまま実装する（個別調査計画・調査結果レポートが正。
ここでの再掲はしない）。

- ブランチ絞り: 行が`gitBranch`を持ち、かつ現在のブランチと一致するものが1件以上あるときだけ絞る。
- `uuid`による重複除去。
- 先頭`min(3,N)`件 ＋ 残りの末尾`min(7, N-min(3,N))`件（重複なし）。
- 切り出しは`jq`の`.[0:N]`。先頭枠は頭120字＋末尾40字、直近枠は頭80字＋末尾30字
  （全長がその合計以下なら全文）。
- 節全体のバイト上限`USER_UTTERANCE_MAX_BYTES`（既定6000）。超えた場合は直近枠の古い側から
  1件ずつ落とす。先頭枠は落とさない。それでも収まらなければ節ごと出さない。

### transcript_pathの受け渡し（issue #151フェーズ3敵対的レビュー指摘）

**下方向は関数引数でそのまま渡す。** `transcript_path`は`main`が`raw="$(cat)"`で読んだ
stdin JSONの中にしかない（`raw`直下の`transcript_path`キー）。**下方向の値渡しはコマンド置換の
サブシェル境界に影響されない**——issue #43や`.claude/rules/shell-script-style.md`「戻り値が
複数ある関数」節が問題にしているのは「サブシェル内で設定したグローバル変数が呼び出し元へ
伝わらない」という**上方向**の話であり、引数を下へ渡す分には無関係である。

```bash
main() {
  ...
  raw="$(cat)"
  local transcript_path
  transcript_path="$(printf '%s' "$raw" | jq -r '.transcript_path // empty')"
  ...
  if context_text="$(build_context "$transcript_path")"; then
    ...
}
build_context() {
  local transcript_path="${1:-}"
  ...
  work_context="$(build_work_context "$branch" "$transcript_path")"
  ...
}
build_work_context() {
  local branch="${1:-}"
  local transcript_path="${2:-}"
  ...
}
build_user_utterance_context() {
  local branch="${1:-}"
  local transcript_path="${2:-}"
  ...
}
```

### 再注入バイト数の返し方（同上の指摘）

**上方向はグローバル変数では伝わらない。** `work_context="$(build_work_context ...)"` も
`context_text="$(build_context "$transcript_path")"` もコマンド置換であり、呼ぶたびに
サブシェルへforkする。ネストの内側で`REPLY`相当のグローバル変数を設定しても、外側の
`main`までは伝わらない。**一方、標準出力の中身自体はコマンド置換が何段ネストしてもそのまま
親へ伝わる。** そこで、`build_user_utterance_context`はユーザー発言節の本文の**末尾へ
センチネル行を1行追加**して返す。

```
__USER_UTTERANCE_BYTES__:1234
```

`build_work_context`・`build_context`はこの行を含めて`lines`配列へそのまま積む（他の行と
同様に扱うだけで、特別な中継処理は不要）。`main`は`context_text`を受け取った後、この行を
`grep`で抜き出して数値を取り出し、`context_text`本体からは取り除いてから
`write_additional_context`へ渡す。

```bash
local excluded_bytes=0
local sentinel
sentinel="$(printf '%s\n' "$context_text" | grep -o '__USER_UTTERANCE_BYTES__:[0-9]*' | tail -1)"
if [ -n "$sentinel" ]; then
  excluded_bytes="${sentinel#__USER_UTTERANCE_BYTES__:}"
  context_text="$(printf '%s\n' "$context_text" | grep -v '^__USER_UTTERANCE_BYTES__:')"
fi
write_additional_context "$(append_size_warning "$context_text" "$CONTEXT_SIZE_WARN_BYTES" "$excluded_bytes")"
```

ユーザー発言節（除外内訳行のみの場合を含む）を1行も出さない場合、`build_user_utterance_context`は
空文字列を返し、センチネル行も出さない（`excluded_bytes`は既定の0のまま）。

### 出力位置

`build_work_context`内、「`HANDOFF.md`次にやること」ブロックの直後・SKILL.md再読み込み指示の
**手前**へ挿入する（issue #113の末尾配置を維持）。センチネル行は`main`が取り除くため、
実際にユーザーへ見える注入内容には現れない。

### `append_size_warning`の変更

現在`(text, limit)`の2引数。**末尾へ`excluded_bytes`を追加し`(text, limit, excluded_bytes)`の
3引数（第3引数は省略可・既定0）へ変更**する（間へ差し込まない。理由は下記）。

```bash
append_size_warning() {
  local text="$1"
  local limit="${2:-$CONTEXT_SIZE_WARN_BYTES}"
  local excluded_bytes="${3:-0}"
  local total_bytes effective_bytes
  total_bytes=$(context_text_bytes "$text")
  effective_bytes=$((total_bytes - excluded_bytes))
  # 判定は effective_bytes で行う（既存は total_bytes で判定していた箇所を差し替える）
  ...
}
```

`effective_bytes = context_text_bytes(text) - excluded_bytes`で判定し、警告文には
「全体Nバイト（うち再注入分Mバイトを除外して判定）」の両方を出す（サイズの扱い節の合意どおり）。

**第3引数を末尾へ追加し既定値0にしたことで、`test_session_start.sh`の既存2引数呼び出し6箇所は
変更不要になる**（`excluded_bytes`省略時は`effective_bytes = total_bytes`となり、従来と
完全に同じ判定になる。issue #151フェーズ3敵対的レビュー指摘——当初案の「第2引数へ差し込む」は
既存呼び出しの意味を無言で変えるため採らない）。`main`は上記のとおり新しい第3引数を渡すよう
変更する。

### fail-open

`transcript_path`が空・不正・壊れたJSONの場合、`UserUtteranceSelect.jq`の呼び出しが失敗しても
`build_context`全体を失敗させず、他の注入項目（ブランチ・issue・PR等）は通常どおり出す。

**具体的には`.claude/rules/shell-script-style.md`「bashでのtry/catch相当の書き方」の
出力を受け取る形を、`build_work_context`が`build_user_utterance_context`を呼ぶ箇所へ適用する**
（`build_work_context`自体は`build_context`の中で`set -e`配下にあるため、素朴に
`user_utterance_context="$(build_user_utterance_context ...)"`と書くと、失敗時に
`build_work_context`ごと終了し既存6項目が丸ごと消える。issue #151フェーズ3敵対的レビュー指摘）。

```bash
local user_utterance_context rc
set +e
user_utterance_context="$(set -e; build_user_utterance_context "$branch" "$transcript_path")"
rc=$?
set -e
[ "$rc" -eq 0 ] || user_utterance_context=""
[ -z "$user_utterance_context" ] || lines+=("$user_utterance_context")
```

この形にすることで、`UserUtteranceSelect.jq`の構文エラー・`transcript_path`の不整合等で
ユーザー発言節の生成が失敗しても、`build_work_context`・`build_context`は正常終了し、
既存の注入項目（ブランチ理由・issue・PR・HANDOFF次にやること・SKILL再読み込み指示）は
影響を受けない。この性質はテスト計画#22で確認する。
