この計画で何をするか

post-push-compact-prompt.sh がpushのたびに送るレビュー依頼メッセージの「defaultブランチとの差分」リンクを、レビューコメントを直接付けられるビューへ変える。現在のリンク先はPR/MRに紐づかない汎用のCompareページ（/compare/base...head）で、開いた先でインラインコメントを付けられない。

あわせて、gh/glab CLIが無くMCPツールしか使えない実行環境（Claude Code on the web）でも同じ体験になる道が無いかを調査で決める。hookはシェルプロセスでありMCPツールを呼べないため、「hookがMCPを叩く」形は成立しない。

方針

  1. get_mr_diff_url 系は純粋関数のまま保つ。 MR/PR URLを引数で受け取り、渡されなければ現行のCompareページを返す。関数の中でCLI・APIを呼ばない。
  2. MR/PR URLの解決は呼び出し元（hook）の責務とする。 CLI経路は現行どおり get_mr_for_branch。MCP経路での解決方法はフェーズ2で決める。
  3. 後退させない。 MR/PR URLを解決できなければ現行のCompareページのまま送る。
既存の設計に前例がある get_diff_anchor_base_url（issue #127）が既に同じ形を採っている——mr_url が空ならCompareへ縮退し、GitLabでは <mrUrl>/diffs を返す。新しい設計を持ち込むのではなく、この既存の形へ揃える。
ユーザーからの追加要望（MCP経路でも成立させる） issueの受け入れ条件は「MCP経路ではCompareのままでよい（後退しないこと）」だが、ユーザーから「MCPツールのみの環境でもやりようはあると思うので検討してほしい」という追加要望がある。hookがローカルで参照できる情報からMR/PR URLを導けないかをフェーズ2で評価する（候補は下の「比較検討した案」）。単一案に決め打ちせず、安いものから順に試すチェーンも選択肢に含める。

フェーズ2〈調査〉

実施する。 方針2（MCP経路でのMR/PR URL解決）が未決であり、これを決めないと実装に入れない。次の問いに答える。

  • git ls-remote でPR番号を解決できるか。この実行環境で実測したときのコスト（所要時間）・refの伝播遅延・fork元PRでの挙動はどうか。
  • GitHub /pull/<n>/files・GitLab /-/merge_requests/<n>/diffs というURL形式は妥当か（推測ではなく裏取りできるか）。
  • get_mr_diff_since_url（前回push〜今回pushの差分）もDiffviewへ寄せられるか。GitHubの /files に範囲指定の口はあるか。
  • 差分アンカー（get_diff_anchor_base_url）と土台URLが二重に決まらないか。整合は取れるか。
  • 影響を受ける既存テスト・spec記述はどれか。

案利点懸念
A. git ls-remote で refs/pull/<n>/head（GitLabは refs/merge-requests/<n>/head）を引き、HEADのSHAと突き合わせるエージェントの協力が要らず自動で効くpushのたびに1往復のネットワークI/O。refの伝播遅延。fork元PRの扱い
B. AIエージェントがMCPで得たPR番号を wip/state/ へ保存し、hookが読むネットワークI/Oが不要で速い。既存の wip/state/review-links/ と同じ形エージェントが書き忘れると効かない。書く契機の定義が要る
C. HANDOFF.md のヘッダ - PR: #NN（URL ） 行を読む既に運用され維持されている情報を再利用できる表記ゆれに弱い。フォーマットへの依存が増える
