# 【AIアセット作成】残置テキストの係り先ルールを一般化する

issue #142 / PR #188 / flow-id 3-1。

## 前提（合意状況）

- 上位の計画: `plans/brisk-weaving-lantern.md`（flow-id 1-4）。
- **調査結果が確定させたこと**は `reports/20260823_brisk-weaving-lantern_係り先ルールの射程調査.md`
  「設計への反映（フェーズ3で決めること）」の8項目が正である。**本計画はそれを実行手順へ落とすもので、
  結論を蒸し返さない。**
- flow-id 3-3（人間の作業計画レビュー）は非対話的セッションのため成立しない。**本計画に対する
  敵対的レビュー（フェーズ3の1回目）をもって代替する。**
  **出所**: ユーザーが flow-id 1-1 の依頼と同じ発言で明示した（上位計画「進め方の前提（この
  セッション固有）」参照）。**flow-id 1-5 の人間合意は `[-]` で未取得**であり、この代替は
  人間の合意を経た前提ではない。

## この計画で何をするか

書き換え先は**2箇所**。どちらも「残置したテキストの係り先が変わっていないか」という同じ観点を
述べるが、**役割が違うので同じ文言にはしない**。

| # | ファイル | 現在 | 何をするか |
|---|---|---|---|
| A | `.claude/rules/docs-workflow.md` 104〜114行 | 見出しの挿入に限定された規約＋実例2件 | **正**。発動条件を一般化し、実例を4件へ増やす |
| B | ルート `REVIEW-POINTS.md` 47〜48行 | 「新しい見出しの挿入位置が…係り先を壊していないか」 | **敵対的レビューが実際に読む唯一の経路**。単独で「何を疑うか」が伝わる中身にする |

**Bを「Aを見よ」というポインタで済ませない。** `collect-review-points.sh` は `REVIEW-POINTS.md` /
`REVIEW-POINTS.local.md` しか集めず、**`.claude/rules/` は敵対的レビューへ渡らない**（Q5）。
ポインタだけでは、辿る動機そのものが生まれない。

### 用語（「4件」を2つの意味で使わない）

この計画には数の同じ別物が2つある。**混同すると #155 が検証から落ちる**ため、以下の語で呼び分ける。

| 語 | 中身 | 使う場所 |
|---|---|---|
| **事故4件** | issue #64 / issue #109 / PR #139 / **issue #155** | 書き換え後の文言を当て直す対象（検証） |
| **載せる実例4件** | #64（位置）/ #64（ファイルごと）/ #109 / PR #139 | ルール本文の箇条書きへ並べるもの（A-3） |

**#155 は「載せる実例」には入らないが、「当て直す事故」には必ず入る。** #155 こそが
「操作の分類で書くと取りこぼす」という A-1 の根拠だからである。

## A: `.claude/rules/docs-workflow.md` の書き換え

### A-1. 発動条件（トリガー）

- **操作の分類で書かない。**「見出しの差し込み」も「構造変更全般」も操作の分類であり、
  issue #155（同じ深さの項を1つ足しただけ）が含まれるかどうかが読み手に委ねられる。
- **残置テキストの側から書く。**「既存の記述を残したまま、その周囲を編集したとき」という形にする。
- **上限の無い条件にしない。** そのままでは末尾への純粋な追記を除くほぼ全ての編集に当たり、
  常時発動＝実質的に無視される規約になる。**残置側に「直前・直後の内容に依存して意味が決まる文」**
  （節・項の全体にかかる補足、結論行、箇条書きを締める一文）**があるとき**へ絞る。
- **発動しない場合を明示する。** そういう文を持たない記述の周りを編集した場合（独立した段落を
  末尾へ1つ足す等）は確認不要、と書く。

### A-2. 確認の観点

- 「**残置した地の文・箇条書きが、変更前と同じものに係っているか**」を見る。
- **編集した位置の前と後ろの両方を見る。** 現行の「直前の節が…」は、PR #139（新設した見出しの
  後ろにあった段落群が配下に入った形）を**射程内の操作なのに検出できなかった**。

### A-2b. 対処（係り先が変わっていたらどうするか）

現行104〜107行は (i) 発動条件・(ii) 壊れ方・(iii) **対処**の3要素を持つ。(iii) を落とすと、
**正であるAから対処が消え、観点表であるBにだけ残る**という逆転が起きる。一般化した発動条件に
対応する形で書き直す。

- **係り先が変わらない位置を選ぶ**（見出しを差し込むなら節の末尾＝次の見出しの直前へ回す。
  これは一般則の特殊例として置く）。
- 位置で解けないなら、**残置側へ係り先を明示する**（専用の見出しを与える／「この節では」
  「上記2件は」のように何にかかるかを文の中へ書く）。PR #139 は前者で解いた。

### A-3. 実例（載せる実例4件）

**既存2件を1行も消さない**（受け入れ条件）。109〜114行の6行はそのまま残し、2件を足す。

| 実例 | 何を示すか | 扱い |
|---|---|---|
| issue #109 | **分割前は正しかった行が、分割によって誤りになる** | 追加 |
| PR #139 | 新設した見出しの**後ろ**が巻き込まれる | 追加 |
| `計画の2階層構造` の位置（issue #64） | 挿入位置の**前**が壊れる | **既存のまま残す** |
| ファイルごとに結論が変わる（issue #64） | 同じ節名でも判定が変わる | **既存のまま残す** |

**挿入位置は「既存2件の前」で確定する（flow-id 3-6 の裁量に落とさない）。** 理由は、この操作自体が
issue #155 と同型（既存の箇条書きへ項を足す）だからである。既存2件目（112〜114行）は
「『別のファイルで同じ位置へ入れられたから安全』とは判断せず、**ファイルごとに確認する**。」で
終わっており、**この一文は箇条書き全体を締める指示としても読める**。後ろへ足すと締めの一文が
新しい2件より前に来て係り先が変わる。前へ足せば、締めの一文は末尾のまま動かない。

- issue #155 は**載せる実例には並べない**（5件並べると、ルール本文より事例集のほうが長くなる）。
  代わりに A-1 の根拠として**1行だけ**触れる（「同じ深さの項を1つ足しただけでも起きた」）。

### A-4. 書き換えるときに自分が踏んではいけない罠

**この書き換えは、前後の両方向で自分が同じ事故を起こしうる。** 片方向しか点検しないと、
「前後どちらも見る」を書いている当の作業が片方向しか見ていないことになる。

| 方向 | 何が起きうるか | 対処 |
|---|---|---|
| **後ろ** | 直後（現116行）は `HANDOFF.md` の進捗記号を扱う**無関係な段落**である。新しい見出しを立てると、その段落が配下に入る（PR #139 と同型） | **新しい見出しを立てない**（現行と同じく見出しを持たない段落として書く）。**これを既定とする** |
| **前** | 既存2件目の締めの一文「ファイルごとに確認する」の係り先が、項の追加で変わる（#155 と同型） | A-3 のとおり**既存2件の前**へ足す |

**選択肢として「直後の `HANDOFF.md` の段落にも見出しを与える」は採らない。** 116行以降には
「1周が完全に完了した」の条件・進捗記号 `[-]`・非対話的実行環境、と複数の段落が続くため、
新見出しがどこまでを覆うかを決める必要が生じ、**その下端で同じ係り先問題がもう一度発生する**。
issue #142 のスコープに照らして割に合わない。採るなら flow-id 3-6 でその理由を作業結果へ書く。

### A-5. 置き換え後の文案

**104〜107行（3文）を次で置き換える。** 実例の箇条書き（109〜114行）はこの下に、A-3 の順で並べる。

```markdown
**既存の記述を残したまま、その周囲を編集したときは、残した記述の係り先が変わっていないかを必ず
確認する**（issue #64・#109・#142）。見出しの差し込み・節の分割・並べ替え・箇条書きへの項の追加は
いずれもこれに当たる。**操作の名前で射程を判断しない**——「同じ深さの項を1つ足しただけ」でも起きる
（issue #155）。

**確認が要るのは、残した記述の中に「直前・直後の内容に依存して意味が決まる文」があるときである**
（節・項の全体にかかる補足、結論行、箇条書きを締める一文）。そういう文を持たない記述の周りを
編集しただけなら（独立した段落を末尾へ1つ足す等）、この確認は要らない。

**編集した位置の前と後ろの両方を見る。** 前だけを見る手順では、新しい見出しの配下へ既存の段落が
入ってしまう形を検出できない（PR #139）。係り先が変わるなら、**係り先が変わらない位置を選ぶ**
（見出しを差し込むなら、挿入位置を節の末尾＝次の見出しの直前へ回す）。位置で解けないなら、
**残した記述の側へ係り先を明示する**（専用の見出しを与える、「この節では」「上記2件は」のように
何にかかるかを文の中へ書く）。
```

**足す実例2件（既存2件の前へ置く）:**

```markdown
- 実例: `issue-mr-flow/SKILL.md`「レビュー完了合図の確認」節を (1)(2) へ**分割**したところ、
  (1) の直下に残した「残っていなければ、そのまま次のステップに進む」が、分割前は唯一の確認に
  対する結論だったのに、分割後は「(1) を満たしただけで次へ進んでよい」と読めるようになった
  （issue #109）。**分割前は正しかった行が、分割によって誤りになる。**
- 実例: `.claude/rules/markdown-frontmatter.md` へ `## DDRのnote` 節を差し込んだところ、その
  **後ろ**にあった見出しを持たない段落群（`index.jsonl` の説明）が、新設した節の配下に入ったように
  読めるようになった（PR #139）。**壊れたのは挿入位置の後ろで、「直前を見よ」という手順では
  検出できない。** 残った段落群へ専用の見出しを与えて解消した。
```

**この文案は合意の対象である。** flow-id 3-6 で字句を推敲してよいが、**次の4点は変えない**
（変えると検証条件が意味を失う）。

1. 発動条件が操作の分類ではなく残置テキスト側から書かれていること。
2. 発動しない場合が書かれていること。
3. 「前と後ろの両方を見る」が明示されていること。
4. 対処（位置を選ぶ／係り先を明示する）が A 側にあること。

## 検証

**作業が終わったと言える条件は、次の7つがすべて満たされていることである。**

1. **既存2実例（計6行）が1行も消えていない。** 下記「削除検査」が `0` を出す。
2. **事故4件（#64・#109・PR #139・#155）すべてが、書き換え後の実文言の下で「見るべきだった」と

awk '
