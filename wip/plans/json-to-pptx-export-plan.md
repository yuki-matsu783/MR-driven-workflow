## 目的（何を作るか）

構成案JSON（HTMLスライドと同じ入力）から、PowerPointで**テキストボックス・ネイティブ表として
編集可能な** `.pptx` を生成する仕組みを `.claude/` 配下へ追加する。

- 生成方式: **雛形（OOXMLパーツ一式）＋ `ppt/slides/slideN.xml` の生成＋zip再梱包**。
  画像化・クリップボード経由・python-pptx は採らない（却下理由はフェーズ4でDDRへ記録する）。
- スライド型: 8種のうち **表紙／章扉／箇条書き／2カラム／表／まとめ の6型を必須**で表現し、
  図解・比較は代替表現（箇条書き・表への写像）でよい（issue本文）。

## issue分割の判定（flow-id 1-4）

受け入れ条件6の「6型を出力」は同型成果物の並列列挙に形の上で当たるが、**分割は提案しない**。
6型は単一の生成スクリプト内の分岐（type→XML断片の写像）であり、型単位で切り出しても
単独マージで意味を成さない横断的変更のため（`references/planning.md`「issueが大きすぎる場合の
分割提案」の除外基準）。この判定の最終判断は人間に委ねる（PRレビューで異議があれば分割する）。

## フェーズ2〈調査〉

実施する。次の問いに答える（個別調査計画 flow-id 2-1 で確定させる）。

- Q1. **zip相当の可用性**（受け入れ条件1）: この実行環境（Linux）で使える圧縮手段をQ1で実測して
  記録する。ユーザー常用環境（Windows git bash）は実機が無いため、代替手段の優先順位候補と
  検出ロジックを決め、DDRの材料にする。
- Q2. **構成案JSONスキーマの現状**: PR #194 の調査レポートQ5の内容を精読し、.pptx側が依存して
  よい範囲（type enum・必須キー）と、スキーマ未確定部分への防御（jqによる必須キー検査で入力を
  検証し、スキーマファイル本体には依存しない）を決める。
- Q3. **最小のOOXML構造**: 警告なく開く .pptx に必要なパーツ一覧（`[Content_Types].xml`・
  `_rels/`・`presentation.xml`・slideMaster・slideLayout・theme・`docProps`）と、スライド追加時に
  連動して書き換える必要のある箇所（rels・sldIdLst等）を、実際に最小構成を組んで検証する。
- Q4. **雛形の形態**: 展開ディレクトリ（テキストXMLをGit管理し生成時にzip）かバイナリ .pptx かを、
  差分レビュー可能性・PowerPointでの再作成可能性の観点で比較する。issue本文は「雛形を
  PowerPointで作る」ことを想定するが、この環境にPowerPointは無い。雛形を後からPowerPoint製へ
  差し替え可能な構造にすることで両立させる案を検証する。
- Q5. **6型の写像**: 8種のtype → スライドXML表現（テキストボックス `<p:sp>`・表 `<a:tbl>`）の
  対応を決める。
- Q6. **検証手段**: この環境で機械検証できる範囲（zip整合性・XML well-formed・独立実装で開ける
  か）と、人間の実機確認（PowerPointで警告なく開く・編集できる・Windows git bashで生成スクリプト
  が動く）に残す範囲を切り分ける。**受け入れ条件7（HTML版と内容が一致）の確認手段もここで
  定義する**（案: 同一のサンプル構成案JSONを入力に、pptx側の全テキスト（`<a:t>`列）がJSONの
  テキスト項目を過不足なく含むことをスクリプトで突合する。HTML版そのものとの直接比較は
  PR #194 の成果物がマージされるまでできないため、その場合の代替と限界を明記する）。
