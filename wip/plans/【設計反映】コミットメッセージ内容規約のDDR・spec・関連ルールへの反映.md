# 【設計反映】コミットメッセージ内容規約のDDR・spec・関連ルールへの反映

**種別を1つにした理由**（敵対的レビュー5回目の指摘を受けて分割）: 初版は
`【設計反映】【AIアセット反映】` の併記だったが、`references/planning.md` は
「**`【設計反映】` `【AIアセット反映】` `【実装反映】` は、基本的に併記せず分ける**（issue #36, #110）」
と、この3種別についてだけ一般の併記基準を**上書きする**規定を持つ。理由は「評価軸が異なるため、
1回のレビューでまとめて合意を取ろうとすると評価軸が混ざりやすい」ことであり、**初版はまさに
そのとおり `【AIアセット反映】` 側の評価軸（副産物の4類型分類）が丸ごと落ちていた**。
副産物の反映は `wip/plans/【AIアセット反映】規約策定で得た教訓のルール・観点表への反映.md` へ分けた。

**`.claude/rules/` `.claude/skills/` への追記（#3〜#5）がこの計画に残る理由**: これらは
**このissueの主たる成果物（規約）の正の所在を各所へ知らせる参照整理**であり、作業の副産物では
ないため `【AIアセット反映】`（副産物が対象）には当たらない。実装・テストの修正も伴わないため
`【実装反映】` でもない。**正史の一貫性を保つ書き戻し**として `【設計反映】` に含める。

## この計画で何をするか

フェーズ3で `commit/SKILL.md` へ新設した内容規約を、**恒久的に残る場所**（DDR・spec・rules）へ
反映し、参照関係の食い違いを無くす。`wip/plans/` `wip/worklogs/` `wip/reports/` はflow-id 5-5で
削除されるため、それらにしか無い判断は失われる。

## 決めること

### 決定A: DDR `i0185-01` に何を書くか

**1件（枝番01）にまとめる。** 「1行のみを維持するか本文を許容するか」（受け入れ条件2）と
「判定を2段階にした」は、**同じ「規約をどう書くか」という1つの決定の表と裏**であり、分けると
どちらのDDRを読んでも片方が欠ける。

| # | 節 | 内容 |
|---|---|---|
| 1 | 決定 | 件名1行を必須、**本文は任意で許容**。追跡用フッター（`Refs #NNN`）も許容 |
| 2 | 背景 | `main` の1行ログに出るのは**PRタイトル**であり、個別の件名は squash 本文の `* 件名` として残る（実測） |
| 3 | 却下案1 | **1行のみを維持する** — 却下。現行規約は既に破られており、本文6件・`Refs` フッター6件がマージ済み |
| 4 | 却下案2 | **本文を必須にする** — 却下。事務的な作業記録（母数の15%）にまで本文を強いると、書く手間に見合わない |
| 5 | 却下案3 | **6語で終わる件名を一律に不合格とする** — 却下。**規約自身の模範例4件を不合格にする**自己矛盾を起こした。判定と合否を同一視したのが原因 |
| 6 | **懸念・残るリスク** | **同じ実測は二面の材料である。** 「規約が実態と乖離している」（本文許容を支持）と、「**規約を追加しても守られない可能性がある**」（実効性を疑う。フッター禁止は明文の絶対ルールなのに6回すり抜けた）の両方が読める。**今回は規約の追記のみで、機械的な強制は入れていない** |
| 7 | **既存の絶対ルールを2箇所限定した判断** | 31行「`Co-Authored-By` **などのフッター**」→「AIの生成物であることを示すフッター」／モデル名行「**成果物すべて**」→「どのAIが書いたかを示す目的で」。**限定しなければ既存資産3箇所**（`shell-script-style.md` の実例・`test_usage_tracking.sh` の期待値・対応工数レポートの「使用モデル」行）**と矛盾する** |
| 8 | 未計測 | **git bash（Windows）実機での複数行メッセージは未計測**。Linux実機でのみ確認している |

**#6・#7 は敵対的レビュー5回目の指摘で追加した。** #6 は調査レポート（flow-id 5-5で削除）が
「二面の材料」と明記した片面が消えるため、#7 は**禁止の緩和は後から最も理由を問われる変更**で
あり、結論だけが `main` に残ると元の広い禁止へ戻される余地が生まれるため。

### 決定B: `.claude/VERSION` をどこまで上げるか

**計画を書く時点で `.claude/docs/spec/distribution-assets.md` の更新規則を読んだ**（初版は
「着手前に読み直す」と後回しにしていた。敵対的レビュー5回目の指摘）。読んだ結果は次のとおり。

| 規則 | 本件への当てはめ |
|---|---|
| 増分は**人間が決める**。非対話セッションではAIが目安表に沿って**適用してよい** | 本セッションは非対話（Claude Code on the web）なので例外に当たる |
| ただし **(1) 適用した事実と根拠を、そのissueのspecのchangelogと `HANDOFF.md`「判断を迷った内容」の両方へ残す** | やること #3・#4 として明示的に立てた |
| ただし **(2) レビューで人間が否認したら元の値へ戻す** | 本計画のレビューおよびPRレビューで否認されたら `0.3.0` へ戻す |
| 目安表: `MINOR` = 資産の追加・フローの拡張 | 規約節（140行）の新設は資産の拡張。呼び出し方（`create-commit.sh --message`）は変わらないので MAJOR ではない |

**したがって `0.3.0` → `0.4.0`（MINOR）を適用する。**

**issue #170 の「今後 `.claude/VERSION` を上げる場合は、改めて人間の指示を起点に増分を検討する」との関係**:
これは同 spec の `## 影響範囲` にある**その回の判断の記録**であり、その上にある `## 仕様` の
非対話例外を打ち消すものではないと解釈する（仕様が正、changelogはその回の記録）。ただし
**この解釈自体を #3 の changelog へ明記**し、人間が否認できる形にする。

**フォールバック**: issue #170 では `.claude/VERSION` への書き込みが**実行環境の権限クラシファイアに
よりブロック**されて適用できなかった。本セッションも同じ実行環境である。ブロックされた場合は
**据え置き、その事実と理由を #3 の changelog へ書く**（適用できなかったことを黙って落とさない）。

## やらないこと

- **過去コミットの書き換え**（上位計画のスコープ外）。
- **`commit/SKILL.md` の `## 備考` 以下の孤立ブロックの修正。** 本issueの受け入れ条件のどれにも
  該当しないため、**別issueへの切り出しを提案する**方針を維持する（無言で削除しない）。
- **prefix一覧の見直し**（スコープ外）。
- **副産物（worklog・レポートの教訓）の反映**。`【AIアセット反映】` の計画が担当する。

## 後続フェーズへの申し送り

**フェーズ3作業結果の残課題が持つ `.gemini/` 同期の期待値（42/30）は、この計画で失効する。**

`.claude/` 側と一致すること」で判定する。**
