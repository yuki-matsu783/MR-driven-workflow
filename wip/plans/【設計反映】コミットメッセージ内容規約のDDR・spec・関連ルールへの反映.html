決定A: DDR i0185-01 に何を書くか

1件（枝番01）にまとめる。「1行のみを維持するか本文を許容するか」と「判定を2段階にした」は、同じ決定の表と裏であり、分けるとどちらのDDRを読んでも片方が欠ける。

#節内容
1決定件名1行を必須、本文は任意で許容。追跡用フッター（Refs #NNN）も許容
2背景main の1行ログに出るのはPRタイトルであり、個別の件名は squash 本文の * 件名 として残る（実測）
3却下案11行のみを維持する — 却下。現行規約は既に破られており、本文6件・Refs フッター6件がマージ済み
4却下案2本文を必須にする — 却下。事務的な作業記録（母数の15%）にまで本文を強いると割に合わない
5却下案36語で終わる件名を一律に不合格とする — 却下。規約自身の模範例4件を不合格にする自己矛盾。判定と合否を同一視したのが原因
6懸念・残るリスク同じ実測は二面の材料である。「規約が実態と乖離している」と「規約を追加しても守られない可能性がある」（フッター禁止は明文の絶対ルールなのに6回すり抜けた）の両方が読める。今回は規約の追記のみで、機械的な強制は入れていない
7既存の絶対ルールを2箇所限定した判断31行「などのフッター」→「AIの生成物であることを示すフッター」／モデル名行「成果物すべて」→「どのAIが書いたかを示す目的で」。限定しなければ既存資産3箇所と矛盾する
8未計測git bash（Windows）実機での複数行メッセージは未計測

#6・#7 は敵対的レビュー5回目の指摘で追加した。 #6 は調査レポート（flow-id 5-5で削除）が「二面の材料」と明記した片面が消えるため、#7 は禁止の緩和は後から最も理由を問われる変更であり、結論だけが main に残ると元の広い禁止へ戻される余地が生まれるため。

決定B: .claude/VERSION をどこまで上げるか

計画を書く時点で distribution-assets.md の更新規則を読んだ（初版は「着手前に読み直す」と後回しにしていた）。

規則本件への当てはめ
増分は人間が決める。非対話セッションではAIが目安表に沿って適用してよい本セッションは非対話（Claude Code on the web）なので例外に当たる
ただし (1) 適用した事実と根拠を、specのchangelogと HANDOFF.md「判断を迷った内容」の両方へ残すやること #3・#4 として明示的に立てた
ただし (2) レビューで人間が否認したら元の値へ戻す否認されたら 0.3.0 へ戻す
目安表: MINOR = 資産の追加・フローの拡張規約節（140行）の新設は資産の拡張。呼び出し方は変わらないので MAJOR ではない

したがって 0.3.0 → 0.4.0（MINOR）を適用する。

issue #170 の「今後は人間の指示を起点に」との関係

これは同 spec の ## 影響範囲 にあるその回の判断の記録であり、その上にある ## 仕様 の非対話例外を打ち消すものではないと解釈する（仕様が正、changelogはその回の記録）。ただしこの解釈自体を #3 の changelog へ明記し、人間が否認できる形にする。

フォールバック

issue #170 では .claude/VERSION への書き込みが実行環境の権限クラシファイアによりブロックされて適用できなかった。本セッションも同じ実行環境である。ブロックされた場合は据え置き、その事実と理由を #3 の changelog へ書く（適用できなかったことを黙って落とさない）。
