## 方針

### 1. 選択基準（受け入れ条件(4)の実体）

**`deliverables.md` の1箇所に置き、他所からはそこを参照させる。** 5本ぶんの説明が複数の
ファイルへ散ると、次に増やしたとき全部が古くなる。

| テンプレート | 向く場面 |
|---|---|
| `reports-clean.template.html` | **既定。迷ったらこれ。** サイドバー常時表示で章数が多くても迷子にならない。ライト／ダーク両対応 |
| `reports-neobrutal.template.html` | 結論を強く押し出したいとき（太い黒枠＋ハードシャドウ）。ライト単一 |
| `reports-mono.template.html` | **色が付いている＝意味がある**を徹底したいとき。印刷・スクリーンショットでの誤読を避けたい場合 |
| `reports-paper.template.html` | **印刷・PDF化して配る**とき（`@media print` を持つ）。ライト単一 |
| `reports.template.html`（現行） | **既存の成果物を更新するとき**。新規作成で選ぶ理由は無い |

**既定を1つ決めるのが要点である。** 5本並べて「好みで選ぶ」と書くと、レポートごとに見た目が
変わり、読み手が毎回レイアウトを学び直すことになる。**選ぶのは、上表の右列に当てはまる
理由があるときだけ**とする。

### 2. 「土台は `reports.template.html`」という記述の直し方

**パスを5つ並べる形にしない。** flow-id 2-6・3-6・4-6・5-4 の4箇所すべてに5本の一覧を書くと、
テンプレートが増減するたび4箇所を直すことになる（今回まさにそれをやっている）。

```
変更前: 土台は `.claude/skills/issue-mr-flow/assets/reports.template.html`
変更後: 土台は `.claude/skills/issue-mr-flow/assets/reports-clean.template.html`（既定）。
        他の3案・現行との使い分けは `references/deliverables.md`「計画・レポートのHTMLビュー」
```

**既定のパスは書く。** 「deliverables.md を見よ」だけにすると、フロー定義だけを読んで作業する
場面で1回余分に開くことになる。**既定＋参照**の形にして、迷ったときだけ開けば済むようにする。

### 3. DDR（`i0203-01`）

| 項目 | 内容 |
|---|---|
| ファイル名 | `.claude/docs/ddr/i0203-01-レポートHTMLビューは共通DOMと4スタイルで持ち現行を残す.md` |
| 決めたこと | 4デザインを**共通DOM＋4通りの `<style>`** で持ち、**現行を残して**既定を `reports-clean` にした |
| 却下案1 | **4本を独立したHTMLとして持つ** — 使い方コメント・検査手順・節構成が4重管理になる |
| 却下案2 | **現行を置き換える（1本に絞る）** — 既存の成果物が現行テンプレートの節構成に依存しており、更新時に節ごと作り直すことになる |
| 却下案3 | **1本のテンプレートにテーマ切り替えを持たせる**（`data-theme` 等） — 未使用のCSSが常に載り、「外部依存ゼロ・自己完結」の利点が薄れる。切り替えUIはレビュー時に触られない |
| あわせて残す | **機械的に検査するときの一般則3つ**（下記） |

**DDRへ「一般則」を残すのは、同じ失敗を2回踏んだためである。**

1. **コメントと地の文を先に除く** — HTMLコメント中の `<li>` `<details>` をタグとして数えて
   MISMATCHが出た（f4）。同じ失敗がDOM比較でも出た（f2）。
2. **「出力なし＝合格」の検査は、負のコントロールを取る** — 検査が壊れていても同じく無出力になる。
3. **構造の同一性は、タグ名ではなくバイト単位で比べる** — タグ名比較は属性もテキストも見ないため、
   実際に成立していなかった主張を「合格」と報告してしまった（敵対的レビュー2回目の指摘2）。

## 検証

### (1) 参照が切れていないか

```bash

```

**DDRを新規追加するので必須。** `.md`/`.sh`/`.gitignore` 内の絶対パス参照が対象。

### (2) DDR一覧が生成物として最新か

```bash

```

**手書きで行を足さない**（一覧は生成物。issue #135）。

### (3) 「触らない」と決めたものが本当に触られていないか

**これが今回いちばん壊しやすい。** 過去issueのchangelogを書き換えると、当時の記録が失われる。

```bash
# 分岐点は実行時に求める（文書へ書き写した固定SHAは、main取り込み後に誤検出へ変わる）
git fetch origin main
base=$(git merge-base origin/main HEAD)
# 触らないと決めた行が、この作業で変更されていないこと
git diff "$base" -- .claude/docs/spec/issue-mr-workflow.md | grep -nE '^[-+].*(3132|3216|3275|3651)' || echo '該当なし'
git diff "$base" --stat -- .claude/docs/ddr/   # 新規1本以外の変更が無いこと
```

**より確実なのは、変更後の該当行を直接読むこと。** 上のgrepは行番号が動くと当たらない
（**行番号で検査するのは信用できない**）ので、**変更前の文字列そのもの**で確かめる。

```bash
# 過去changelogの記述が原文のまま残っていること（4件とも1件ずつヒットするのが合格）
grep -c -e 'reports.template.html' .claude/docs/spec/issue-mr-workflow.md
git show "$base:.claude/docs/spec/issue-mr-workflow.md" | grep -c -e 'reports.template.html'
```

### (4) usecase文書への影響

```bash
grep -rln -e 'HTMLビュー' -e 'reports' .claude/docs/usecase/
```

ヒットしたファイルを開き、**記述・リンクが古くならないか**を確認する（issue #170）。
