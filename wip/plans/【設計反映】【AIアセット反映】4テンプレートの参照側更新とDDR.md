## この計画で何をするか

**「置いてあるだけ」の4本を、フロー定義から選んで使える状態にする。** 具体的には
(a) 選択基準の文書化（受け入れ条件(4)）、(b) 参照側の記述更新、(c) 判断のDDR化、
(d) 作業の副産物として得た検査の一般則のアセット化、の4つ。

### 種別を併記する理由

`references/planning.md` は `【設計反映】` `【AIアセット反映】` を**基本的に併記せず分ける**と
定めている。**今回あえて併記するのは、両者の入力が同一の作業結果1本で、合意を1回で取れば
足りるためである**（分けると同じ作業結果を2つの計画から参照し、レビューも2往復になる）。

**併記する以上、`【AIアセット反映】` 側の手順1〜2は省略しない**（下記「AIアセット反映の洗い出し」）。

## 方針

### 1. 選択基準（受け入れ条件(4)の実体）

**`deliverables.md` の1箇所に置き、他所からはそこを参照させる。** 5本ぶんの説明が複数の
ファイルへ散ると、次に増やしたとき全部が古くなる。

**全行に同じ軸を揃える**（テーマ／印刷／向く内容）。軸が抜けた行があると、その行と他の行の
どちらを選ぶかが決まらない。

| テンプレート | テーマ | `@media print` | 向く場面 |
|---|---|---|---|
| `reports-clean` | ライト／ダーク | 無し | **既定。迷ったらこれ。** サイドバー常時表示で章数が多くても迷子にならない |
| `reports-neobrutal` | **ライト単一** | 無し | 結論を強く押し出したいとき（太い黒枠＋ハードシャドウ） |
| `reports-mono` | ライト／ダーク | 無し | **色が付いている＝意味がある**を徹底したいとき。白黒での閲覧・スクリーンショットでの色の誤読を避けたい場合 |
| `reports-paper` | **ライト単一** | **有り** | **印刷・PDF化して配る**とき |
| `reports.template.html`（現行） | ライト／ダーク | 無し | **移行期のみ。** このブランチ以前に作られ、まだ片付いていないレポートを更新する場合に限る |

- **既定を1つ決めるのが要点である。** 5本並べて「好みで選ぶ」と書くと、レポートごとに見た目が
  変わり、読み手が毎回レイアウトを学び直すことになる。**選ぶのは、右列に当てはまる理由が
  あるときだけ**とする。
- **競合したら `paper` を優先する。** 「白黒で読む」は `mono` と `paper` の両方に当てはまるが、
  実際に印刷するなら `@media print` を持つのは `paper` だけである（実測: 4本中 `paper` のみ）。
- **現行を選ぶ場面は、移行が終われば消える。** `wip/reports/` の成果物は flow-id 5-5 で削除され
  mainに残らないため、「既存の成果物を更新する」に該当するのは同一ブランチ内だけである。
  **いつ現行を廃止するかはDDRの未確認事項へ入れる**（`install-to-project.sh` は上流で消えた
  ファイルを配布先から削除しないため、廃止時に配布先へ旧テンプレートが残る）。

### 2. 「土台は `reports.template.html`」という記述の直し方

**パスを5つ並べる形にしない。** flow-id 2-6・3-6・4-6・5-4 の4箇所すべてに5本の一覧を書くと、
テンプレートが増減するたび4箇所を直すことになる（今回まさにそれをやっている）。

```
変更前: 土台は `.claude/skills/issue-mr-flow/assets/reports.template.html`
変更後: 土台は `.claude/skills/issue-mr-flow/assets/reports-clean.template.html`（既定）。
        他の3案・現行との使い分けは `references/deliverables.md`「計画・レポートのHTMLビュー」
```

**既定のパスは書く。**「`deliverables.md` を見よ」だけにすると、フロー定義だけを読んで作業する
場面で1回余分に開くことになる。**既定＋参照**の形にして、迷ったときだけ開けば済むようにする。

**Eの348行だけは、この形にしない。** あの表は「テンプレート → どのflow-idの成果物か」の対応表
なので、4本を足すと**同じ対象を持つ5行**が並び、区別する情報を持たない一覧がもう1つできる
（方針1が避けようとしている二重管理そのもの）。**reports系を1行へ畳み、直後にある
「何の正か → どこ」の表へ「どれを選ぶか → `deliverables.md`」の行を足す。**

### 3. 検査手順の「正」をどこに置くか（新規の論点）

**フェーズ3で、検査手順の実体が1つから5つに増えた。** 新4本は使い方コメントごとバイト単位で
同一なので、プレースホルダ検査・リンク破断検査・重複ID検査の説明が**4本すべてに複製されている**。
一方、「検査コマンドの正は `reports.template.html` 冒頭コメント」と名指しする箇所が3つある。

| 名指ししている場所 | 扱い |
|---|---|
| `plans.template.html` 20行 | **J** で向け直す |
| `wip/plans/REVIEW-POINTS.md` 108行 | **K** で向け直す |
| DDR `i0186-02` 25行 | **触らない**（DDR本文は変更しない）。向け先の変更は spec の changelog（E）へ記録する |

**ルート `REVIEW-POINTS.md` は「正は1箇所に決め、他はそこを指すリンクだけにする」を観点として
持つ。** 5コピーはこれに反する。**正を `deliverables.md`（A）へ移す。**

- テンプレート側のコメントは**使い方の説明**として残す（読む場所にあることに価値がある）。
- **`deliverables.md` を「検査手順の正」と決め、テンプレートのコメントには「正は
  `deliverables.md`」と1行だけ書く。**
- **4本のバイト一致という不変条件と両立する。** 同じ1行を4本へ同じように書くだけなので、
  一致は保たれる。

### 4. 検査を5種から6種へ増やす（AIアセット反映 (c)）

**この計画のHTMLビュー自身が、`<style>` の二重出力という壊れ方をした**（敵対的レビュー3回目で
検出）。既存の5種は**どれも捕まえなかった**——アンカー・ID・外部依存しか見ないためである。

```bash
# 6. 構造の妥当性（1でなければ不合格）
grep -c '^<style>' "$f"; grep -c '^</style>' "$f"
```

**この壊れ方は、ライト環境でだけ表示が崩れる。** `<style>` の直後にもう1つ `<style>` があると、
2つ目はCSSのテキストとして扱われ、続く `:root { … }` ブロックごと破棄される。ダーク環境では
メディアクエリ内で `:root` を再定義しているため正常に見え、**確認する環境によって結果が変わる**。

反映先は J（`plans.template.html`）・K（`wip/plans/REVIEW-POINTS.md`）と、
**新4本＋現行テンプレートの冒頭コメント**である。

判断する**と定めている。フェーズ3で配布対象アセットを**4本追加**したので、判断が必要である。

### (3) 「触らない」と決めたものが本当に触られていないか

**これが今回いちばん壊しやすい。** 過去issueのchangelogを書き換えると、当時の記録が失われる。

**当初この計画は、次の2つを検証手順として書いていた。どちらも機能しない**（敵対的レビュー3回目）。

| 書いていたもの | なぜ機能しないか |
|---|---|
| `git diff … \| grep -nE '^[-+].*(3132\|3216\|3275\|3651)'` | diff本文に**文字列「3132」が現れる行**を探しており、行番号を見ていない。**何をしても「該当なし」を返す空振り**である |
| `grep -c -e 'reports.template.html' <spec>` の件数突き合わせ | 実測は**6**（348・758・3132・3216・3275・3651行）で、計画が書いた「4件」と合わない。しかも**更新対象の348・758行を母数に含む**ため、増減が「触らない側が無傷か」を示さない |

**正しくは、触らないと決めた4行の原文そのものを固定文字列で1件ずつ確かめる。**

```bash
cd /home/user/MR-driven-workflow
git fetch origin main
base=$(git merge-base origin/main HEAD)   # 分岐点は実行時に求める（固定SHAを書き写さない）

# 触らないと決めた4行の原文を、分岐点の版から取り出しておく
git show "$base:.claude/docs/spec/issue-mr-workflow.md" \
  | sed -n '3132p;3216p;3275p;3651p' > /tmp/frozen.txt
# 4行とも、現在のファイルに1件ずつ残っていること
while IFS= read -r line; do
  printf '%s -> %s\n' "$(grep -c -F -e "$line" .claude/docs/spec/issue-mr-workflow.md)" "${line:0:40}"
done < /tmp/frozen.txt
```

- **合格条件は「4行すべてが 1」である。** 0 なら書き換えてしまっている。
- **`grep -F` で固定文字列として渡す**（原文には正規表現のメタ文字が含まれうる）。
- **`-e` を使う**（原文がハイフンで始まる場合に `grep: unknown option` で落ちるため。
  `.claude/rules/shell-script-style.md`）。

**負のコントロールを取る。** 「4行とも1」は、検査が壊れていても同じく出る。

```bash
cp .claude/docs/spec/issue-mr-workflow.md /tmp/broken.md
sed -i '3132s/.*/意図的に壊した行/' /tmp/broken.md
# 上のループを /tmp/broken.md に対して流し、1行目だけが 0 になることを確かめる
```

**DDRについても同じく確かめる。**

```bash
git diff "$base" --stat -- .claude/docs/ddr/   # 新規1本以外の変更が無いこと
```

### (5) 4テンプレート自身が回帰していないこと

参照側と冒頭コメントを直す計画なので、**バイト一致が保たれているか**を必ず確かめる
（方針3・4で4本の冒頭コメントへ同じ1行を足すため、書き漏らすと一致が壊れる）。

```bash
cd .claude/skills/issue-mr-flow/assets
tmp=$(mktemp -d)
for F in reports-clean reports-neobrutal reports-mono reports-paper; do
  sed '/^<style>$/,/^<\/style>$/d' "$F.template.html" > "$tmp/$F.nostyle"
  n=$(wc -l < "$tmp/$F.nostyle")
  [ "$n" -lt 100 ] && { echo "FAIL $F: 抽出が $n 行"; exit 1; }   # 空振りガード
done
md5sum "$tmp"/*.nostyle | awk '{print $1}' | sort -u | wc -l   # 1 なら4本一致
```

**ハッシュの種類数が 1 であることを合格条件にする**（行数・バイト数を目で見比べるより確実で、
出力も1行で済む）。

### (6) 6種の検査を全成果物へ流す
