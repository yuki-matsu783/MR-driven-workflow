この計画で何をするか

フェーズ3でルール文言を書き換えるにあたり、書き換え先・書き換え方を一意に決めるために 足りない情報を集める。調査の問いは全体作業計画の5問を引き継ぐ。

4件の判定表の正 この計画ではなく調査結果 reports/…md に置く。 上位計画の背景表は着手時点の 見立てであり、調査結果と食い違った場合は調査結果が正である。

調査項目

Q1. 現行ルールの射程と、一般化後に既存記述と矛盾しないか

  • .claude/rules/docs-workflow.md の該当段落（104〜114行目付近）を全文で確認し、 どの文が「見出しの挿入」に依存しているかを1文ずつ切り分ける
  • 既存の実例2件が、一般化後の文言の下でもそのまま実例として成立するかを確かめる

確認方法: 該当段落の前後を読み、下記の暫定案を当てはめて矛盾する語を探す。

Q2. 同趣旨のルールが他ファイルに重複していないか

  • ルート REVIEW-POINTS.md「ドキュメントの構造」に同型の観点がある。 正を1箇所に決めるのか、規約と観点表で役割を分けるのかを決める材料を集める
  • 同じ判定を述べている行を、目に付いた2箇所で打ち切らずに全部数える
  • .gemini/ を数えない。 .gemini/ は .claude/ の 変換生成物であり「重複した記述」ではない。除外しないと件数がちょうど2倍になり、重複箇所を 過大に見積もる。.gemini/ は直接編集しない

確認方法: doc-search で絞り込んだうえで、本文の語を横断検索して数える。 件数を調査結果へ書く。

Q3. ルール本文へ載せる実例は何件か

  • 4件それぞれについて「現行ルールで拾えるか」と「壊れたテキストが、新しく書いた部分から 見て前か後ろか」を表にする
  • #109（分割で前が壊れる）と PR #139（挿入で後ろが壊れる）は方向が逆。 全件載せるか、方向の異なる2件へ絞るかを、読み手の負担と網羅性の両面から判断する

確認方法: 4件を表に起こし、それぞれが「下記の暫定案だけを読んで検出できるか」を 机上で突き合わせる。1件でも検出できないものが残れば、その形は暫定案では拾えていない。

判定に使う暫定案（この計画では確定しない）

Q3・Q1 の机上判定には、上位計画「フェーズ3〈作業〉」が挙げる5項目を暫定案として当てる。 この調査で確定させるのは「暫定案で4件を検出できるか」という判定結果だけであり、 最終的な文言は flow-id 3-1 の個別作業計画で決める。

Q4. 係り先・見出し挿入のルールを扱ったDDRがあるか（DDRの要否の材料）

  • 識別子（i0064-*）ではなく内容で判定する。 issue #64 由来のDDRは実在するが、 中身は「issue分割の判断」であり係り先ルールとは無関係である。接頭辞の件数だけを見ると 「追記で足りる」という誤った結論へ流れる
  • ヒットしたファイルの title / description まで見て、 今回の拡張の追記先になりうるかを1件ずつ判定する。DDRは本文を変更しない運用のため、 「追記」は実質的に新規DDRの作成か frontmatter の note の追加のいずれかになる
  • 「操作の列挙ではなく観点で書く」という判断が、却下案を伴う意思決定なのかを確かめる

確認方法: doc-search で type: ddr を絞り込み、 「見出し」「係り先」「構造」で検索する。0件なら本文の横断検索へフォールバックし、 ヒットしたファイル名を調査結果へ列挙する。

Q5. ルールを実際に守らせる場所はどこか

  • 4件とも自己確認では見つからず敵対的レビューが検出している。この事実から、 規約に書くだけで守られるのかを検討する
  • 候補は (a) 規約のみ、(b) ＋ルート REVIEW-POINTS.md の観点、 (c) ＋敵対的レビューのサブエージェント定義。(c) はスコープ外だが、 「(a)(b) で足りる」と判断できる根拠までは集める
確認方法 敵対的レビューが観点表をどう使うか（adversarial-review スキル手順2-b、 collect-review-points.sh）を読み、rules 配下が敵対的レビューへ渡るかを 確かめる。渡らないなら、規約だけに書いても敵対的レビューは見ないことになる。

やらないこと（スコープ外）

この計画では決めない・触らない
  • 4件以外の事例の発掘。4件で射程の議論には十分であり、発掘に上限が無い
  • 過去ドキュメントの遡及点検（判断は別issueへ送る）
  • 文言の確定。上記「判定に使う暫定案」での机上判定は行うが、実際に書く文言の確定は flow-id 3-1 の個別作業計画で決める。暫定案の字句を推敲したり、代替案を比較したりしない

検証

調査が終わったと言える条件は、次の3つがすべて満たされていることである。

  • Q1〜Q5 のすべてに、根拠（ファイルパスと行、またはコマンドの出力）を添えた答えが reports/ の調査結果へ書かれている
  • Q2・Q4 について、件数を数えた結果（0件も含む）と、ヒットしたファイル名が 書かれている。「見つからなかった」だけで終えない
  • Q3 の表が4件すべてを含み、各件について「暫定案で検出できるか」の判定がある

下記は上記3条件を満たすための材料を得る手段であって、それ自体は合格条件ではない （着手前の現ツリーでもそのまま成功するため、実行できたことは何も保証しない）。
