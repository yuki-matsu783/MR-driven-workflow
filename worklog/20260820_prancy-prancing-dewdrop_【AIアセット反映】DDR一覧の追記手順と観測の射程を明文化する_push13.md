## うまくいったこと

- **反映3の置き場所を `reports/` ではなくルートにした。** 失敗そのものは `reports/` の
  レポートで表面化したが、**同じ失敗はspec本文・DDR・rulesのどの変更でも起きる**。
  既存のルート観点「検証コマンドが、異常があるときに本当に検出できるか」と対になる内容で、
  同じ節に並べると差が読み取れる（**既存はパターンの話、追加は基準の話**）。
- **`collect-review-points.sh` で拾えることまで確認した**（検証3）。観点表は収集されて初めて
  効くので、書いただけでは反映になっていない。ルート・`reports/` の両方から拾えた。
- **検証4で、追加した観点そのものを実践した。** 基準をブランチ分岐点 `ad18795` に固定し、
  対象を1ファイルに絞らず3ファイルまとめて見た。結果は `34 insertions(+), 1 deletion(-)` で、
  削除1行は意図した運用表の書き換えだった。

  ```bash
  git diff ad18795 -- .claude/rules/docs-workflow.md reports/REVIEW-POINTS.md REVIEW-POINTS.md \
    | grep '^-' | grep -v '^---'
  ```

## ダメだったこと

- **`docs-workflow.md` へ `##` 見出しを新設しようとして、やめた。** 表のセルに
  「下記「DDR一覧への追記」」と書いてから本文を見たところ、**このファイルは `# ドキュメント運用`
  以外に見出しを持たない地の文構成**だと分かった。1つだけ `##` を入れると構造が浮くため、
  既存と同じ「太字で始まる段落」の形に揃え、表からの参照も「下記」に留めた。
  **参照の書き方を先に決めてから本文の構造を見る順序が逆だった。**
- 差し込みで**空行が2つ連続した**（`{ sed -n '1,73p'; echo; cat frag; sed -n '74,$p'; }` の
  `echo` と、フラグメント末尾の空行が重なった）。
  `.claude/rules/docs-workflow.md`「差し込んだら前後3行を目視」で気づいて詰めた。

## 決まったこと

- **反映1の反映先は `issue-mr-flow/SKILL.md` ではなく `docs-workflow.md`。** changelogに
  「DDR一覧へ00NN を追加」が繰り返し現れており、**慣習は確立していて明文化だけが無い**状態
  だった。不足しているのは手順の新設ではないので、flow-idは増やさない。
- **反映2へ「件数の内訳」を計画外で足した**（AIの判断）。射程の逸脱には「主語がずれる」以外に
  「件数が水増しされる」形もあると、フェーズ4の敵対的レビューで実際に踏んで分かったため。
  既存観点の粒度を細かくする範囲で反映先も計画どおりのため、承認は取らずに報告のみとした。
- **反映3は計画外の追加なので、チャットで承認を得てから実施した**（記録:
  PR #132 の #issuecomment-5361040462）。反映先が計画に無いファイル（ルート観点表）へ広がる
  変更であり、AIの判断の範囲を超えると考えたため。
