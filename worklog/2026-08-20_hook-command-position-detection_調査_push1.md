# worklog: 【調査】hook検知の誤検知類型と判定方式

対象: hookのコマンド文字列検知をコマンド位置ベースへ置き換えるための調査（2026-08-20）。
全体作業計画: `plans/hook-command-position-detection.md`
個別作業計画: `plans/【調査】hook検知の誤検知類型と判定方式.md`
push回数: 1

## 試したこと

- issue #53 の本文と3件のコメントをMCP経路で取得した（`gh` CLIがこの実行環境に無いため）。
  - issue #94 からの申し送り: 位置ベースにするならCRの扱いを再判定すること。
  - issue #47 の実測: この環境（Claude Code on the web / Linux）では push検知hookは
    「地の文だけ」では発火しなかった。コミット側は `if` を経由しないため必ず発火する。
  - issue #133: 本文が参照する DDR 0012 は `i0000-09` へ改番済み。
- 4hookの検知箇所を `grep -n 'tool_input.command'` で洗い出した。

## うまくいったこと

- **20ケースの表を先に作り、hookへ直接JSONを流して変更前の実測を取った。** 誤検知6件・検知漏れ1件と
  いう内訳が数字で出たので、以降の判断（どの案を採るか）が「たぶん」ではなく表の突き合わせになった。
- **「新方式で新たに素通りしうる構造」を実装前に列挙した。** `bash -c` / `eval` / `$( )` / `xargs` /
  `find -exec` の5類型で、これを洗い出していなければ全部素通りしていた（変更前は5件ともブロック
  されていたので、純粋な機能後退になるところだった）。
- **性能の見込み違いを実装前に潰せた。** `${s:i:1}` の遅さはマルチバイトロケールのせいだと思って
  いたが、`LC_ALL=C` にしても変わらなかった。行配列＋チャンク読み飛ばしへ切り替えて線形にした。
- **CRの検証にスタブjqが使えた**（`.claude/rules/shell-script-style.md`「テスト」の手法）。
  Windows実機なしで「CRがあっても結果が変わらない」を20ケースで確認できた。

## ダメだったこと

- **調査中に2回、自分でブロックを踏んだ。** デバッグ用スクリプトのコメントと、修正パッチの説明
  コメントに該当語が入っていただけ。issue本文の主張がそのまま再現した。回避策は「本文をファイルへ
  書いてから実行する」で、これは既存ルールどおり。
- ブラケット式をダブルクォートの中へ直接書いたところ、`\\` と `\'` の解釈がシェルとパターン照合で
  二重にかかり、**バックスラッシュが文字集合から落ちた**。`$'...'` で組み立てた変数を
  クォートせずに展開する形へ変えて解決した。
- ヒアストリング `<<<` を1文字ずつ返していたため、残った `<<"` を次の走査がヒアドキュメントの
  開始と誤認した。3文字まとめて消費する形へ直した。
- `bash` を無条件のフォールバック対象に入れたところ、受け入れ条件のケース
  （`bash create-commit.sh --message "…"`）が落ちた。コード指定オプションと併用時のみに絞った。
