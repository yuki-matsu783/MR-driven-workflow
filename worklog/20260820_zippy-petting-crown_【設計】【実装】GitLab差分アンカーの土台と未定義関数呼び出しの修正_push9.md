# worklog: 【設計】【実装】GitLab差分アンカーの土台と未定義関数呼び出しの修正

対象: フェーズ2で検出した不具合2件の修正方針の決定と、個別作業計画の作成（2026-08-20）。
全体作業計画: `plans/zippy-petting-crown.md`
個別作業計画: `plans/【設計】【実装】GitLab差分アンカーの土台と未定義関数呼び出しの修正.md`
push回数: 9

## 試したこと

- **案Bの実現可能性の見極め**（`?diff_id=&start_sha=` で範囲を保ったままアンカーを効かせられるか）。
  1. `/merge_requests/1/versions` → `id` と `head_commit_sha` が取れることを確認（11/10/9/5）。
  2. `/-/merge_requests/1/diffs?start_sha=<head>` は200。`diffs_stream` も200で34ファイル。
  3. しかし **`diffs_stream` は `start_sha` も `diff_id` も無視していた**（パラメータ有無・
     でたらめなSHAの3通りで、いずれもバイト数が315838で完全一致）。
  4. 実際にページが使う描画経路を `data-endpoint-batch` 属性から特定し直し、
     **`diffs_batch.json` が本線**だと分かった（素の `/diffs` も同じ経路）。
  5. `diffs_batch.json` に対して同じ比較をやり直した。
- 絞り込み結果の妥当性検証として、返ってきた `file_hash` と `sha1sum` を突き合わせた。
- 異常系として、**MRバージョンのheadでないSHA**（mainのbase commit・でたらめなSHA）を
  `start_sha` に渡したときの挙動を確認した。
- 不具合2の直し方を決めるため、`Gitlab.sh` から `Provider.sh` の共有関数を呼ぶ先例があるかを
  調べた（`grep` で `to_slug` / `url_encode_path_to_reply` / `get_provider` 等の実呼び出しを判別）。

## うまくいったこと

- **`diffs_batch.json` では `start_sha` 単独で絞り込みが効く**ことを確認できた
  （パラメータ無し30件 → `start_sha` 付き1件）。**`diff_id` は不要**で、案Bでも
  `/versions` への追加API呼び出しは要らないと分かった。
- **絞り込み後のファイル集合が `build_file_links_text` の `diff_range` と一致する**設計であることと、
  `file_hash` が `sha1(パス)` そのものであることを実測で確認した
  （`docs/mmm-大きい差分.md` → `79ca8e71bf25b4152f332b840fc896571d810b36` が両者一致）。
- **案Bの弱点を先に見つけられた。** バージョンheadでない `start_sha` を渡すと、
  **HTTP 200のままファイル数0**になる（エラーにならない）。`prev_sha` は hookがローカルHEADから
  記録する値で、**pushを伴わない誤検知でも上書きされる**（issue #23で3回発生）。
  案Bはこの既知の問題を「無言で空の差分ページ」という形で表面化させる。
- 以上から**案A（`<mrUrl>/diffs#<sha1>`）を推奨**として計画に落とせた。案Aは唯一
  目視確認済みで、失うのは「アンカーの土台が今回pushの範囲に絞られる」ことだけである
  （範囲そのものは、メッセージが別に持つ「前回pushとの差分」リンクが引き続き担う）。
- **不具合2の直し方に新しい判断が不要**だと確認できた。`Gitlab.sh:31` が既に `to_slug`
  （`Provider.sh` の共有関数）を呼んでおり、`get_repo_url` を呼ぶ形は先例の範囲内。

## ダメだったこと

- **`diffs_stream` を本線だと思い込んだまま案Bを評価しかけた。** フェーズ2で
  「Compareページの `diffs_stream` から `id=` を取り出す」手法が当たったため、MR差分ページでも
  同じだろうと考えたが、実際は `diffs_batch.json` だった。**同じ結論（バイト数が完全一致）が
  3通りの入力で出た時点で「効いていない」ではなく「見ている場所が違う」を先に疑うべきだった。**
- 最初の異常系テストで、バージョンheadのSHAを手で切り詰めて継ぎ足した無効なSHAを使ってしまい、
  「効いていない」という誤った観測を1回混ぜた。**SHAは必ずAPIの出力から丸ごと取る。**
- `printf 'status=%%{http_code}\n'` と書いてしまい、`curl -w` へ渡す前にPercentが畳まれて
  リテラル出力になった（実害なし。`curl -w` の書式は `printf` の書式と混ぜない）。

# 追記: 敵対的レビュー（フェーズ3・1回目）と計画の改訂

## 試したこと

- 敵対的レビューで10件の指摘。9件をPR #128 へインライン投稿し、1件は報告のみ。
- 机上で確認できる指摘を実物と突き合わせた（hookの292行・末尾の `( main ) || true`、
  `get_repo_url` の実体、`Github.sh` がコメントURLをGraphQLの `comment { url }` から
  受け取っていること）。
- **案Aの機能後退を実機で再現した。** 検証用MRで `docs/mmm-大きい差分.md` を
  「前のpushで追加 → 今回のpushで削除」の状態にし、`diffs_batch.json` を土台別に取得して
  対象ファイルが載るかを比較した。
- `github_get_note_url` の形式が推測かどうかを、本リポジトリのPR #128 の実コメントで確かめた。

## うまくいったこと

- **推奨を案A → 案Bへ変更する根拠が得られた。** 案A（MR全体の差分）は30ファイル中0件、
  案B（`?start_sha=`）は1ファイル中1件。`build_file_links_text` は削除ファイルにも
  アンカーを必ず出すため、案Aでは**存在しない要素を指すアンカー**が生まれる。
  **ファイルの改名も差分上は削除＋追加なので同じ形に該当する**（当初これを見落としていた）。
- 決め方を「どちらが便利か」から「**土台が覆う範囲をファイル一覧の供給元 `diff_range` と
  一致させる**」という原則へ置き換えられた。初回pushは `<mrUrl>/diffs`、2回目以降は
  `?start_sha=<prev_sha>` と、範囲の対応が1対1になる。
- **`github_get_note_url` の形式は推測ではなかった。** 実データが
  `…/pull/128#discussion_r3821657827` で一致。ただし「本番経路に呼び出し元が無い」という
  指摘自体は妥当なので、その理由をコメントに残す方針にした。
- 計測結果を `reports/` の md・html 両方へ移し、計画からは参照リンクだけにした（issue #87）。

## ダメだったこと

- **「失うものが小さい」という案Aの推奨根拠が誤っていた。** 「リンク先のファイルは今回pushで
  変わったものに限られる」ことを、そのまま「土台ページにも存在する」と読み替えていた。
  **一覧に載るかと、土台に存在するかは別の話**であり、範囲が違えば一致しない。
- hookの修正指示を「2行を1行へ置き換える」と書いたが、その2行は `file_links_text` の
  `local` 宣言を兼ねていた。**置き換え前後の形を両方書かずに「置き換える」とだけ書くと、
  こういう巻き添えを計画の段階で検出できない。**
- 「外部プロセスもネットワークも使わない」とテストの性質を書いたが、同じ計画の作業2で
  `get_repo_url`（`git remote get-url origin` を起動する）を経由させる変更を入れていた。
  **同一計画内の別の作業が前提を崩していないかを見ていなかった。**

# 追記: flow-id 3-6（実装）

## 試したこと

- 案Bの実装（`get_diff_anchor_base_url` ディスパッチャ＋GitLab側のバージョンhead検証）、
  不具合2の修正、`get_mr_url` / `get_note_url` のディスパッチャ追加、テスト16ケース追加。
- **GitHub側の出力が変わっていないことを、変更前後の関数を取り出して直接突き合わせた。**
  `git show a13f4aa:<hook>` から旧版を取り出し、`list_changed_files` と
  `build_file_links_text` だけを `sed -n '/^fn() {/,/^}/p'` で抜き出して別プロセスで実行し、
  出力をdiffした。
- ブラウザ目視確認用に、検証用MRへ32ファイルの差分（うち1つは402行）を作ってリモートへ反映した。
- 4本のアンカーURLについて、**対象ファイルが実際にそのページの差分に載っているか**を
  `diffs_batch.json` で確認した。

## うまくいったこと

- **GitHub側の出力が完全一致した**（old/new とも2,526バイト・15行、diff無し）。出力が空でない
  ことも先頭3行で確認しており、比較が空振りしていない。
- 実機で4通りの分岐がすべて設計どおりになった（`since_sha` 空 → `/diffs`、バージョンhead →
  `?start_sha=`、バージョンheadでない → 縮退、`mr_url` 空 → Compareページ）。
- 不具合2の修正後、`get_mr_unresolved_comments` の出力に `url=` が入るようになった。
- **hookを丸ごとsourceせずに済ませる方法が要った。** このhookは末尾が `( main ) || true` と
  `exit 0` で、sourceすると `cat` でstdin待ちになり、最後の `exit 0` で呼び出し元のシェルまで
  落ちる。**関数定義だけを `sed` で抜き出して別プロセスで実行する**形にした。

## ダメだったこと

- **静的検出テストが最初に2件失敗した。** `mcp_tool_hint` が文字列として持つMCPツール名
  （`github__list_pull_requests` のように**アンダースコア2つ**）が `(github|gitlab)_[a-z0-9_]+`
  に一致し、未定義の関数として9件検出された。アンダースコア2つで始まる名前を除外して解決。
  **「関数名らしい文字列」を正規表現で拾う検出は、同じ接頭辞を持つ別種の識別子を巻き込む。**
- **折りたたみ（`collapsed`）を再現できなかった。** 402行のファイルを置いても
  `diffs_batch.json` では32ファイル全件が展開された。フェーズ2では `diffs_stream` で畳まれて
  いたので、**畳む条件はファイル単体の行数ではなくページ全体の規模に依存する**と思われるが、
  特定できていない。目視確認の2本目は「折りたたみ」ではなく「長いファイル」の確認に留まる。
