# worklog: ユーザー判断4件の反映

対象: issue #26 フェーズ3（2026-08-23）。push回数: 11。3-6〜3-9 の**2周目**。
結果の正文: `reports/20260822_ai-asset-manifest-distribution_manifest方式の実装結果.md`

## 試したこと

- 判断が下りた4件のうち、実装を伴う3件（内部終了コード検査・`seed` 雛形2件・削除の一覧提示）を
  反映した。1件（回帰テストの形はこのままでOK）は判断の追認なので変更なし。
- `add-round 3-6` が拒否された（1周目の進捗列が `[]` のまま）。規約どおり
  `set-header --loop` で2周目にした。**`add-round` は「前回の往復が完了している」ことを
  前提にするので、1周目を `set-header` で開始した場合は2周目も `set-header` になる。**

## うまくいったこと

- **`run_or_fail <説明> <コマド...>` という小さなラッパー1つで、`cp`/`mkdir` の検査が
  9箇所そろった。** 各所に `|| { printf ...; return 1; }` を書くより短く、失敗時の文言も
  「何をしようとして失敗したか」で揃う。関数呼び出しなのでforkは増えない。
  - 併せて `dirname "$dst_path"` を `${dst_path%/*}` へ置き換えられた（forkが減る）。
- **`build_plan` が0件で成功していた穴が、この作業で見つかった。** `read_entries_records` は
  プロセス置換の中で走るので、jqが失敗しても `while` が0回まわるだけで、以降は
  「core を 0 件配置しました」と成功で終わる。**指摘されていなかったが、同じ「失敗が成功として
  報告される」類型なので併せて塞いだ**（テスト D-3）。
- **雛形の二重管理を、テストで機械的に縛った。** `HANDOFF.md.template` は `cleanup-task.sh` の
  `HANDOFF_TEMPLATE` と同一である必要があるので、`test_cleanup_task.sh` で本文とバイト数の
  両方を突き合わせる。片方だけ直すと落ちる。

## ダメだったこと

- **フィクスチャが追跡ファイルだけを写していたため、新規作成した雛形が入らなかった。**
  `seed の配布元がありません` で落ちた。`git ls-files -z --cached --others --exclude-standard`
  へ変え、**作業ツリーの現在の状態**を写すようにした。
  - 教訓: 「クリーンな本家」のフィクスチャは、**コミット済みの内容**ではなく
    **これから検証したい内容**を写す必要がある。前者だと、新しいファイルを足した回だけ
    落ちる（しかも原因がフィクスチャ側にあると気づきにくい）。
- **「本家から削除された」状態を作るのに `rm -f` を使い、別のエラーで落ちた。**
  作業ツリーから消しても `git ls-files` はindexを返すので、配布計画には残ったまま
  `cp` が `No such file or directory` になる。`git rm` でindexからも消す必要があった。
  - これは規約の「`git ls-files` の列挙結果を、ワーキングツリーに実体があるものとして扱わない」
    （issue #117）と同根。**今回は `run_or_fail` を入れた直後だったので、
    `エラー: 配置（...）に失敗しました（cp）` と出て一発で分かった**（入れる前なら
    `cp` の生のメッセージだけが流れて終わっていた）。
- **`assert_eq` で片側だけ生の変数を渡して必ず失敗した。** コマンド置換は末尾の改行を落とすので、
  `"$HANDOFF_TEMPLATE"` と `"$(cat file)"` は末尾改行の分だけ食い違う。両辺を同じ `$(...)` に
  通し、末尾改行の有無はバイト数で別途見る形にした（規約「末尾の改行を含む期待値の検証に
  `$(...)` を使わない」の裏返し）。
- 節Dの1件目で `dest_new` を使い回して落ちた。**その配布先は受け入れ条件3の確認で
  `HANDOFF.md` を編集済み**だった。使い回す前に、その配布先が既にどう汚されているかを見ること。
