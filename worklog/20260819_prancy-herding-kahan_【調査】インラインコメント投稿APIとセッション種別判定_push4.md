  読み手が意味を取れない状態だった。根拠を再確認した。

  - `.claude/scripts/src/vcs/Gitlab.sh:131-132`: `[unresolved threadId=...] user: body` のみで、
    `position`（`new_path` / `new_line`）を一切参照していない。
  - つまり**GitLab APIの制約ではなく、このリポジトリの実装の欠落**である。

## うまくいったこと

- スレッド1の指摘を受け、調査1の「設計への反映」を書き換えた。**ファイル全体にかかる指摘を
  レビュー本文（サマリ）へ集約する方針をやめ、「そのファイルのdiff上で最初に現れる有効行」へ
  インラインで付ける方針へ変更**した。レビュー時に、どのファイルへの指摘かが一目で分かる。
  - 新規追加ファイルはhunkが `@@ -0,0 +1,N @@` になるため、この行は**そのまま1行目に一致する**。
    指摘の趣旨（1行目に書けばよい）は、新規ファイルではそのまま満たされる。
  - ただし既存ファイルの部分変更では1行目がdiffに含まれないことがある（push2の実機確認で
    `HANDOFF.md` の有効行は14〜107であり、`line=5` は422で失敗した）。そのため実装は
    「1行目に固定」ではなく**有効行集合の最小値**とする。既にフェーズ3の作業項目としてある
    「有効行を算出する純粋関数」から自然に導ける。
  - サマリへ回すのは「そのファイルがdiffに全く現れない場合」（`patch` が省略された場合を含む）
    だけに絞った。
- スレッド2の指摘を受け、HTMLの該当セルに「**どのファイルの何行目への指摘なのかが出力されない**」
  「GitLab APIの制約ではなく `gitlab_format_discussion_notes` が `position` を出力していないため」
  という説明を補った。
- HTMLの「設計への反映」カード3も、md側の方針変更と同じ内容へ差し替えた（md・HTMLの同期）。
