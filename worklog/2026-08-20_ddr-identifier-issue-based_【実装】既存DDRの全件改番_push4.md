# worklog: 【実装】既存DDRの全件改番

対象: issue #133 の追加対応（2026-08-20）。
全体作業計画: `plans/ddr-identifier-issue-based.md`
個別作業計画: `plans/【実装】既存DDRの全件改番.md`
push回数: 4

## 試したこと

- **DDR本文からissue番号を機械的に抽出する。** 最初にやったが誤りだった。旧 `0016` は本文中で
  別のissueへ言及しているだけの番号を拾い、旧 `0014` は移植元プロジェクトの #48 を名乗っていた。
- **git履歴から「そのDDRを追加したコミット」を辿る。** 使えなかった。shallow clone であり、
  かつ移植分は単一の一括コミット `3f30159` としてまとめて入っているため、DDRごとの由来が無い。
- **本リポジトリのissue 78件を全件取得し、DDRのタイトル・本文と突き合わせる。** これが正解。
  「本文が名乗る番号のissue」が実際に同じ話をしているかを1件ずつ確認し、根拠つきの一覧として
  ユーザーへ提示して承認を得た。
- 改番は `git mv` → frontmatterの `title` → 本文冒頭の見出し → 全ファイルの参照、の順で
  機械的に処理した。`title` はクォート付き（`title: "0018. …"`）の書き方が混ざっていたため、
  `title: `・`title: "`・`title: '`・`\n# ` の4パターンを個別に扱った。

## うまくいったこと

- **検証を「リンクが実ファイルへ解決するか」に置いた。** 置換漏れは目視では見つからないが、
  この検証なら必ず落ちる。実際にこれで2種類の漏れ（リンクのラベルだけ旧番号のまま／hookの
  コメント内のDDRパス）を検出できた。
- **`i00` をリポジトリ全体の通し番号にした。** `i00` は特定のissueを指さないので「同一issue内で
  01から」という原則が働かない。全体通しにすることで枝番の意味が一意に決まる。
- 改番の前後で単体テスト全12件を実行し、`failures=0` を維持できていることを確認した。

## ダメだったこと

- **一括置換が `test_check_base_conflicts.sh` のフィクスチャを壊した。** このテストは
  `0027-gh_glab-CLI不在時…` と `0027-プロバイダ判定…` という2パスで **PR #52 の実際の衝突を
  再現している**。片方だけが新識別子へ変わった結果「重複しない2ファイル」になり、
  **テストは緑のまま意図だけが失われた**。`git checkout --` で差し戻し、以降このファイルを
  置換対象から丸ごと除外した。
  - 教訓: リネーム作業では、**テストのフィクスチャを本物のファイル名と同じ扱いにしない**。
    緑であることが無事の証拠にならない壊し方がある。
- **`test_extract_frontmatter.sh` が1件失敗した。** フィクスチャの入力側
  （`superseded_by: "0019"`）だけが置換され、期待値が `"0019"` のまま残っていた。
  入力と期待値が別々の行にある比較テストは、一括置換で片側だけが動く典型。
- **対応issueの件数を一度誤って報告した**（3件 → 13件）。本文のissue記載をそのまま信じたため。
  「移植元プロジェクトの番号が混ざっている」という前提に気づくまで、誤りに気づけなかった。
- **ハードコードした件数が陳腐化した。** 「既存55件」と各所へ書いていたが、`main` の取り込みで
  `0060` が増えて56件になった。件数は `.claude/docs/README.md` の一覧を正とし、
  他のドキュメントへは書かない方針へ変えた。
