# worklog: 【設計】【実装】【テスト】manifest方式の配布機構

対象: issue #26 の配布方式作り直し（2026-08-22）。
全体作業計画: `plans/ai-asset-manifest-distribution.md`
個別作業計画: `plans/【設計】【実装】【テスト】manifest方式の配布機構.md`、
`plans/【AIアセット作成】配布ドキュメントとAGENTS分割.md`
push回数: 7

## 試したこと

- 計画ファイルの分け方をユーザーへ確認し、**`【設計】【実装】【テスト】` と
  `【AIアセット作成】` の2ファイル**に分ける指示を受けた（flow-id 3-1）。
- 層分け定義ファイルの形式を、調査3で採用した「案A（定義ファイル1枚）」から具体化した。
  検討したのは次の3点。
  1. **形式をJSONにするかTSV等の行形式にするか。** コメントを持てない代わりに `note` フィールドを
     置けること、manifestが既にJSONで jq 前提であること、将来の収穫スキルが機械的に読めることから
     JSONを採った。読み出しは jq 1回でTSVへ落とし、以降はbashで扱う（fork回数を定数に抑える）。
  2. **パスの一致判定をどうするか。** globの意味論をbashで再実装せず、
     `git ls-files -z -- "$path"` にgit pathspecとして評価させる形にした。
  3. **例外の表し方。** 「`plans` は `local`、ただし `plans/REVIEW-POINTS.md` は `core`」のような
     例外を、`.gitignore` / `.gitattributes` と同じ **後に書いたエントリが勝つ**規約で表す。
- 網羅性チェックの分母を、調査結果の「168」から**追跡ファイル全件**へ変えられることに気づいた
  （`plans` `worklog` `reports` を `local` エントリとして定義へ載せるため、除外条件を
  スクリプト側に持たせずに済む）。
- インストーラの処理順序を書き出す過程で、**受け入れ条件4が1パスでは満たせない**ことが分かった。
  「上書きの**前に**警告と一覧を出す」ためには、走査パス → 提示 → 配置パス の2パスが要る。

## うまくいったこと

- **`seed` に `source` フィールドを持たせる案で、2つの問題が同時に解けた。**
  - `REVIEW-POINTS.local.md` の空雛形を本家の4ディレクトリへ実ファイルとして置かずに済む
    （本家に意味の無い空ファイルが4つ増えるのを避けられる）。
  - `AGENTS.md` を配るときに本家固有の3行を落とせる。調査6で「雛形化が必要」と書いたが、
    **本家の `AGENTS.md` 自身を汎用文へ書き換えるわけにはいかない**（本家には本家の説明が要る）。
    配布元を別ファイルにできる仕組みが要ることに、計画を書いていて気づいた。
- **2パス構成にすると、既存欠陥#4（`HAS_WARNED` が `safe_copy_dir` の外へ伝わらない）が
  副次的に消える。** 警告をサブシェル内の変数ではなく、走査パスで作った配列として持てるため。
  「作り直しで消える」と調査で切り分けた根拠が、処理順序のレベルで裏づけられた。
- **2つの計画が同じファイルを触る箇所を洗い出せた。** `.gitignore` は
  「マーカー化（対の計画）」と「`/build/` の削除（この計画）」の両方の対象になるため、
  実際の編集を対の計画へ寄せ、`【AIアセット作成】` 側は判断の記録だけを持つ形にした。
  `plans/REVIEW-POINTS.md` の「同一計画内の別の作業が、ある作業の前提を崩していないか」という
  観点を、**計画をまたいで**適用した形になる。

## ダメだったこと

- **`local` エントリのパスの意味が2種類あることに、最初の設計では気づいていなかった。**
  追跡ファイル（`plans/`）と、追跡されていない生成物（`usage/`）では突き合わせ先が違う
  （前者は `git ls-files`、後者は `.gitignore` のパターン行）。同じ `path` キーで両方を
  表そうとすると「どちらの意味か」がエントリを見ても分からなくなるため、
  `gitignorePattern` を別キーとして分けた。
- **`REVIEW-POINTS.local.md` の波及先を、対の計画へ機械的に割り振れなかった。**
  スクリプト（`cleanup-task.sh` / `collect-review-points.sh`）はこちら、ルール
  （`markdown-frontmatter.md` 等）はAIアセット側、spec（`adversarial-review.md`）はフェーズ4、と
  3つに分かれる。1つの決定が3つの層へ波及するので、**どれか1つでも落とすと運用が食い違う**。
  それぞれの計画の「自己点検」節へ相互参照を書いて対処した。
