# worklog: 【AIアセット反映】forkゼロの検証はベースライン差で測る

対象: issue #55 のフェーズ4（AIアセット反映）（2026-08-19）。
全体作業計画: `plans/mutable-beaming-leaf.md`
個別反映計画: `plans/【AIアセット反映】forkゼロの検証はベースライン差で測る.md`
push回数: 3

## 試したこと

### 反映すべき知見の切り出し

フェーズ3で実際に陥りかけた誤りが元になっている。`split_remote_url` は外部コマンド・
コマンド置換・パイプを一切含まずforkゼロのはずなのに、20回ループの計測が **177ms**（約9ms/回）と
出たため「見落としたforkがある」と実装を疑う方向へ進みかけた。実際は `$(seq 20)` と `date` 自体の
fork・試行回数の少なさによるノイズで、空関数を基準にした200回計測では **0.065ms/回** だった。

`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」節を読み直したところ、
**「起動を減らせ」とは書いてあるが「減らせたことの確かめ方」は書いていない**ことを確認した。
プロジェクト固有ではなくgit bashでプロセス起動コストを扱う限り再発する話なので、
削除されるworklogではなくルールへ残す対象と判断した。

### 他の候補の棚卸し（反映しないと判断したもの）

| 候補 | 判断 |
|---|---|
| `REPLY` へ返す関数はパイプでなくヒアストリングで呼ぶ | 同節に**既に記載あり**。今回は従っただけ |
| 値が2つなら `REPLY_HOST`/`REPLY_PATH` と分ける | 既存記述の自然な拡張で、独立した知見ではない |
| 合成テストで終わらせず実データのbefore/after diffを取る | 「テスト」節に**既に記載あり**。今回は従って助かった側 |
| 性能比較は同一セッション内で旧実装を再現して測る | ベースラインを揃えるという同じ話なので、上の1項目に含める |

**反映は1件のみ**とした。既存ルールに書いてあることを再掲すると、節が長くなるだけで参照される
確率がむしろ下がるため。

### 反映の実施（flow-id 4-6・2周目）

`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」節の**末尾**（キャッシュの項目の後ろ）
へ、既存の書式に合わせて1項目追加した。計画どおり**1件のみ**で、他の節・他ファイルは変更していない。

書いた要点は計画の3点に加えて1点増やし、計4点にした。

1. ゼロであることを測るときは空関数をベースラインに取り、その差で見る（+実例: 177msの誤読）
2. 試行回数を十分に取る（20回では判別できず200回で差が見えた）＋200回計測の表
3. 同条件での外部コマンド1回の実測値を併記し「1/500」の形で結論を出す
4. **旧実装との性能比較も同一セッション内で連続して測る**（計画段階では「1に含める」と
   していたが、書いてみると独立した失敗例（285ms/回との比較をしかけた件）を持つため、
   サブ項目として分けたほうが読み手に伝わると判断した）

### コード例を実際に動かして検証した

ルールに載せるコード例が動かないと意味がないため、ドキュメントから機械的に切り出して実行した。

```bash
sed -n '/^  # 計測の骨子/,/^  bench 200 split_remote_url/p' .claude/rules/shell-script-style.md \
  | sed 's/^  //' > bench.sh
bash -n bench.sh && source bench.sh
```

1回目の実行で**問題が見つかった**。`provider_from_remote_url` を測ると `github` が200行流れる。
計測対象が標準出力へ書く関数の場合、例のままでは画面が埋まって使い物にならない。
**ループ本体へ `>/dev/null` を追加**し、あわせて「リダイレクトはforkを伴わないので計測に影響しない」
という補足コメントを入れた。修正後に再実行して確認した。

| 計測対象（200回） | 所要 | 空関数との差 |
|---|---|---|
| 空関数 `noop` | 49ms | — |
| `split_remote_url` | 85ms | +36ms（0.18ms/回） |
| `provider_from_remote_url` | 95ms | +46ms（0.23ms/回） |
| `parse_repo_slug`（`jq` 1回/呼び出し） | **15046ms** | +14997ms（**75ms/回**） |

この対比が、そのままルールの主張の裏付けになっている。**forkを1回でも含む関数は空関数の300倍以上に
なり、含まない関数は数十msの差に収まる。** 差の桁がはっきり違うため、ベースラインさえ取れば
判定を誤る余地はない。

## うまくいったこと

- 「ルールに書いていないこと」を、印象ではなく**該当節を読み直して**確認できた。
- 候補を4件棚卸ししたうち3件が既存ルールでカバー済みと分かり、追記を1件に絞れた。
- **ルールに載せるコード例をドキュメントから切り出して実際に実行した。** これをやらなければ、
  出力が200行流れる使いにくい例をそのまま残すところだった。手順を書くルールほど、
  書いた手順自体を1回通してみる価値が高い。
- 検証のために測った `parse_repo_slug` の75ms/回が、期せずして「forkあり/なしの桁の違い」を
  示す良い対照例になり、ルールの説得力を補強できた。

## ダメだったこと

- **コード例の初版で、標準出力へ書く関数を測るケースを考慮していなかった。** 実行して初めて
  気づいた。ドキュメントに載せるコードは、代表的な使い方を1つ通すだけでは不十分で、
  「対象が何を出力するか」のバリエーションまで考える必要がある。
