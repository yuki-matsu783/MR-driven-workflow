### HANDOFF.mdの進捗表の組み立て

## うまくいったこと

- **進捗表の機械生成**。`SKILL.md` の `| <flow-id> | ステップ | 担当 |` 行を抽出し、
  進捗列を先頭へ足す形で41行ちょうどを得られた。`update-handoff-progress.sh mark-done` が
  期待どおり動くことも確認できた（正規表現 `^(\|[[:space:]]*)(\[[^\|]*\])...` に合致する）。
- **hook誤検知の再現**。HANDOFF.mdの地の文へ `permissions.deny` のパターン文字列をそのまま
  書いてBashツールへ渡したところ、`block-direct-git-commit.sh` が exit 2 でブロックした。
  issue #47 が扱う論点の実例をこのセッション内で得られたので、ルール本文の根拠に使える。
  対処はWriteツールで一時ファイルへ書き出し、Bash側は連結だけを行う形にした。

## ダメだったこと

- **`awk` の文字クラスでマルチバイト文字を切ろうとして壊した**。ステップ列を短くするために
  `sub(/[（。].*$/, "", step)` と書いたところ、`（` `。` がバイト単位で扱われ、日本語の途中で
  切れて `**Plan` `調査�` のような壊れた文字列になった。bashのパラメータ展開
  （`${step%%（*}`）へ置き換えて解決した。UTF-8は自己同期的なので、**文字クラスではなく
  「その文字列全体」で一致させる**形なら安全である。
  - 既存ルール（`.claude/rules/shell-script-style.md`）には「日本語を含む文字列の先頭を
    `${var:0:N}` で切り出して比較しない」という近い注意はあるが、**awkの文字クラス**については
    書かれていない。フェーズ4のAIアセット反映の候補。
- **`set -euo pipefail` を宣言しないアドホックなコマンドで、HANDOFF.mdの進捗表を消した**。
  `last=$(grep -n '^| \[.\] | 5-5 |' ...)` の正規表現 `\[.\]` が `[]`（記号1文字を挟まない形）に
  マッチせず `last` が空になり、`sed -n "1,p"` が失敗。ところが `set -e` が無いため後続の
  `mv -f HANDOFF.md.new HANDOFF.md` がそのまま実行され、tailだけのファイルで上書きされた。
  scratchpadに断片を残していたため再構築できた。
  - 教訓は2つ。(1) **進捗記号 `[]` は「0文字」なので `\[.\]` ではマッチしない**（`\[[^]]*\]` を
    使う）。(2) **ファイルを上書きするアドホックなコマンドでも `set -euo pipefail` を宣言する**。
    フェーズ4のAIアセット反映の候補。

## 前方一致の裏取り（調査2の先行実施）

**issue #47 の前提と食い違う既存記録を見つけた。** `.claude/docs/spec/issue-mr-workflow.md` の
「制約」節と `.claude/docs/ddr/0022-...md` の「副次的な確認事項」に、issue #23 対応時の実機観測
3回をもとに「`if` フィールドは**前方一致ではなく部分一致**として動作する」と明記されている。
issue #47 は逆に「先頭がコメント行だと前方一致が外れる」と述べている。

そこで、このリモート実行環境で `if: "Bash(git push*)"` の発火条件を実測した。

| # | コマンドの構成 | 発火 |
|---|---|---|
| 1 | 1行目 `set -euo pipefail` / 2行目 `git push -u origin <branch> ...` | した |
| 2 | 1行目 `set -euo pipefail` / 2行目 コメント / 3行目 `echo '...git push...'` | **しない** |
| 3 | **1行目 コメント** / 2行目 `git push --dry-run origin <branch>` | **した** |

- #3 が本命。**1行目にコメントを置いても発火した**。少なくともこの環境では、
  issue #47 が言う「先頭がコメント行だと前方一致が外れる」は**再現しない**。
- #2 から、単純な部分一致でもないと分かる（`echo` の引数に該当語があっても発火しない）。
- #1〜#3 を最も素直に説明するのは「**コマンドを部分コマンドへ分解し、各部分コマンドに対して
  前方一致で照合する**」というモデルである。コメント行・無関係な行はマッチを妨げない。
- ただし DDR 0022 の観測（heredocの地の文で発火）はこのモデルでは説明できない。
  **Claude Codeのバージョン・プラットフォーム（Windows git bash 対 リモート実行環境）で
  挙動が違う可能性が高い**。片方の環境の観測だけを根拠に断定してはいけない。

**`permissions.deny` 側は安全に実測できない。** `deny` に載っているのはコミット操作のパターン
だけで、同じ文字列は PreToolUse hook（`block-direct-git-commit.sh`）にも引っかかる。hookが先に
exit 2 で止めるため、`deny` がマッチしたかどうかを切り分けられない。`allow` を試すには
`settings.json` の変更が要り、リポジトリの設定を実験のために書き換えることになるので行わない。

> **この判断は後に覆った**（下記「flow-id 2-6」節）。既存の `deny` パターンを対象にするから
> 切り分けられないのであって、**無害なパターンを別に置けば実測できる**。敵対的レビューの指摘で
> 気づいた。「危険だからできない」と早々に結論づけて、代替手段を探していなかった。

**flow-id 1-6 で観測した「地の文でのブロック」は、`if` の話ではない。** あれは
`block-direct-git-commit.sh` が発火したもので、このhookのmatcherは `Bash|PowerShell`
（ツール名のみ）であり、スクリプト内部の正規表現がコマンド文字列**全体**を見ている。
`if` フィールドの照合とは別の仕組みである。
**この2つを混同すると、ルール本文の根拠を取り違える。**

### 訂正（敵対的レビュー1回目の指摘を受けて）

**上の実測を `permissions.allow` / `deny` の根拠として使ってはいけない。** 敵対的レビューの指摘
（PR #132 のインラインコメント、個別調査計画75行目）が正しい。

- 測ったのは `hooks[].if` の照合であって、`permissions` の照合ではない。書式が
  `Bash(...)` で同じでも、同じ実装を通っている保証はどこにも無い。
- リポジトリの既存記録（`.claude/rules/git-workflow.md`「push検知hookの誤検知」）は、この `if` を
  **部分一致**として観測している。先頭一致で照合していないものの発火実績から、
  前方一致が外れるかどうかは導けない。
- したがって「1行目にコメントを置いても発火した」は、**issue #47 の前提を否定する証拠にはならない**。
  否定できるのは「`if` の照合に関する既存記述が、この環境では成り立たない」ことだけである。

**当初この worklog に書いた「issue #47 が言う前提はこの環境では再現しない」という表現は、
射程を広げすぎていた。** 実測が示す範囲は `if` に限られる。`permissions` については
`.claude/settings.local.json` へ無害なパターンを一時的に置く実測（個別調査計画
「安全に実機確認する方法」）で、flow-id 2-6 に確かめ直す。

### 気づき

- **`block-direct-git-commit.sh` だけが `if` を持たない。** `.claude/settings.json` を読み直して

## 敵対的レビュー2回目を受けた訂正（重要）

指摘10件のうち最も重いものが、**flow-id 2-6 の結論そのものを突き崩した**。

### `deny` の実測から `permissions` 全体へ一般化していた

`deny` と `allow` は非対称な意味論を持つ。

| | 意味論 |
|---|---|
| `deny` | **いずれか**の部分コマンドが一致したら拒否（ANY） |
| `allow` | **すべて**の部分コマンドが一致して初めて自動承認（ALL） |

この非対称のもとでは、**先頭のコメント行が「無視される」のか「どの許可規則にも一致しない
部分コマンドとして数えられる」のかを、`deny` の実験では原理的に区別できない**（後者でも
`deny` の結果は変わらない）。

**issue #47 の付帯制約が挙げる帰結は2つあり、私が反証したのは片方だけだった。**

| issueの帰結 | 対応する設定 | 実測 |
|---|---|---|
| `deny` をすり抜ける | `permissions.deny` | 反証された |
| 許可済みのはずの操作で承認プロンプトが出る | `permissions.allow` | **未確認。反証していない** |

**それにもかかわらず、レポートの結論表と会話への報告の両方で「`permissions` の前方一致は
外れない」「issueの前提はこの環境では成り立たない」と書いていた。** これは実測の射程を
超えた一般化である。レポートを訂正し、`allow` 側を「未確認」として独立の行に分けた。

**同じ誤りを2回繰り返している。** 1回目は `hooks[].if` の観測を `permissions` の根拠にしかけた
（レビュー1回目の指摘）。2回目は `deny` の観測を `allow` を含む `permissions` 全体へ広げた。
どちらも「書式が同じだから同じ挙動だろう」という推測を、実測の顔をして書いてしまう形である。
**測った対象の名前をそのまま結論の主語にする**（`deny` を測ったなら結論の主語は `deny`）と
決めておくのが対策になる。フェーズ4のAIアセット反映の候補。

### `allow` 側の実測は見送った

観測するには権限モードをプロンプトが出る形へ変える必要があり、そうすると以降のあらゆるコマンドが
承認待ちになって**セッションが止まる**（承認する人間が不在なら、実験用設定を削除するコマンドすら
実行できず復旧できない）。実験のために作業不能になるリスクは取らない。レポートには
「見送った理由」として明記した。

**実験時の権限モードを記録していなかった**のも指摘のとおり。`allow` 由来の挙動は権限モード依存
なので、追試するならまず記録する。

### heredocの構成で追試した

指摘#2（issue #23 の記録は「heredocの地の文」なのに `echo` の引数で試して食い違いと断定した）を
受けて、コマンド置換＋heredocの形で測り直した。**結果は発火せず。** 同じ構成で確かめたので、
食い違いは実証されたことになる。`if` の参考表へケース4として追加した。

### その他の反映

- 結論要約#3（hook誤検知）が本文と食い違っていた（要約は無条件「起きる」、本文は
  「コミット側は必ず／push側は起きなかった」）。要約を条件付きへ直した。

  「1環境・1セッション・既存ファイルのみ」を本文へ書き、`markdown-frontmatter.md` の書き換え
  提案は新規ファイルでの実測が取れるまで保留と明記した。
- 受け入れ条件2（`description` の1行制約）の扱いがレポートのどこにも無かった。「設計への反映」へ
