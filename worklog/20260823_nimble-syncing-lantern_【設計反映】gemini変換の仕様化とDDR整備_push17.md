# worklog: 【設計反映】gemini変換の仕様化とDDR整備

対象: issue #70 のフェーズ4〈反映〉2本目（2026-08-23）。
全体作業計画: `plans/nimble-syncing-lantern.md`
個別反映計画: `plans/【設計反映】gemini変換の仕様化とDDR整備.md`
push回数: 17

## 試したこと

- **`setup-gemini-links` の残存参照を `grep -rn` で探したところ、出力が2.7MBになった。**
  `usage/session-logs/` 配下のセッションログ（自分自身の会話ログ）と `index.jsonl` が全件
  ヒットしていた。`git grep` に切り替え、pathspecの除外（`':!plans'` 等）で絞ったところ
  1件になった。**`.gitignore` 対象を自動で外してくれるぶん、追跡ファイルの棚卸しには
  `git grep` のほうが向いている。**
- `flow-id 5-4` の残存を数えたら36件あった。**「0件を期待する検索」ではないことに、数えてから
  気づいた**。今回 5-4 は「統括レポート」という有効な番号として存在し続けるためである。
  件数だけでは判断できないので、全件を `awk` で所属見出しまで遡って分類した。
- `.claude/docs/spec/distribution-assets.md` の該当行を計画は「L159」と指していたが、main を
  取り込んだ後で行番号がずれていた。**行番号ではなく本文で探す**ようにした。
- 単体テストの重複（`--path 生成物` が2箇所）を直したあと、**意図的に除外を壊して落ちる件数を
  確かめた**。`.gemini` 側だけが落ち `build` 側が落ちないことを見て、独立したと判断した。

## うまくいったこと

- **DDR本文の不変を、分岐点からの `git diff` の削除行で機械的に確認できた**（4件、すべて
  `note:`）。「本文を変えていない」を目視で保証しようとすると見落とすので、この確認は毎回やる。
- **`issue-mr-workflow.md` の issue #57 の未決定事項を、削除ではなく「決定済み事項」へ移した。**
  計画は「削除」と書いていたが、同ファイルに `## 決定済み事項（旧・未決定事項）` という受け皿が
  既にあった。**削除すると「なぜ揃えていなかったのか」が読めなくなる**ので、移動を選んだ。
  移した文には、解消した理由（Gemini の source に `compact` が無い／matcher が完全一致）を
  足してある。
- **写像規則の正を `sync-gemini-assets.md` 1箇所へ寄せた。** `issue-mr-workflow.md` 側には
  リンクだけを残し、`PreToolUse`→`BeforeTool` のような対応表を重複して書かなかった。
  フェーズ3の敵対的レビューが「スクリプト側のコメントだけが更新されていて、正が2つある」と
  指摘したのと同じ形を、こちらで作らないため。
- **棚卸しの落とし穴を `docs-workflow.md` へ残した**（`plans/` `reports/` をディレクトリ単位で
  除外すると、寿命が永続の `REVIEW-POINTS.md` だけがすり抜ける）。今回の繰り下げ漏れ1件が
  まさにこれで、**除外はディレクトリ単位ではなくファイル単位で判断する**と書いた。

## ダメだったこと

- **`grep -rn` を素で流して2.7MBの出力を作った**（上記）。`usage/` が `.gitignore` 対象である
  ことを失念していた。以後、追跡ファイルの棚卸しは `git grep` から始める。
- **計画が指していた行番号がすべてずれていた**（main の取り込み後なので当然だが、計画を書いた
  時点の番号をそのまま信じかけた）。行番号は「だいたいこのあたり」以上の意味を持たない。
