# worklog: 【設計】【実装】【テスト】DDR一覧生成スクリプト

対象: `.claude/docs/README.md` のDDR一覧を生成スクリプト化する（2026-08-20）。
全体作業計画: `plans/ddr-list-generation.md`
個別作業計画: `plans/【設計】【実装】【テスト】DDR一覧生成スクリプト.md`
push回数: 1（敵対的レビュー対応で push2 へ続く）

## 試したこと

- 着手前にDDR一覧の実体を確認した。DDRファイルは55件、README上の一覧も55行で一致。
  DDRを列挙している箇所はリポジトリ内でここだけだった。
- **一覧行を正規表現で走査し、末尾に `（…）` を持つ行を機械的に洗い出した。** その結果、
  issueが「唯一の注記」としていた0009（`status: superseded`）のほかに、frontmatterから
  導けない散文の注記が0022・0048の2件あることが分かった。issueの前提が実物と食い違っていた
  ので、`note` キーの新設で受け止める方針にした。
- frontmatterの抽出方式を検討した。`index.jsonl` を読む案もあったが、生成物であり最新とは
  限らないうえ、Git管理外なのでclone直後は存在しない。DDRファイルを直接読む方式にした。
- 抽出は**awk 1回**で全ファイルを処理する形にした（`.claude/rules/shell-script-style.md`
  「外部プロセス起動のコスト」。1ファイル1回だとファイル数に比例して遅くなる）。
  awkの `FNR==1` で前ファイル分を emit する形にして、`nextfile` を使わずに
  「1ファイル必ず1レコード」を保証した。
- 生成結果と変更前のREADME区間を `diff` で突き合わせた（等価性の検証）。

## うまくいったこと

- **等価性の検証を「実装直後・READMEを書き換える前」に置いたのが効いた。** 差分が2種類出て、
  どちらも本物の不具合だった。先にREADMEを書き換えていたら比較対象を失っていた。
- 生成先をREADME内のマーカー区間にしたことで、READMEの他の節（由来の注記・欠番の説明・
  spec一覧）を手書きのまま残せた。
- DDR 0060 を追加した直後に再実行したら、一覧が55件→56件へ自動で増えた。手書き更新が
  不要になったことを実地で確認できた。

## ダメだったこと

- **awk→bashの受け渡しをタブ区切りにしたのが誤りだった。** bashの `read` はタブを
  IFS空白文字として扱い、連続する区切りを1つへ畳む。`status` と `superseded_by` が両方空の
  DDR（＝大多数）で `note` が `status` の位置へずれ込み、
  「`── **`status: <注記の全文>`**`」という壊れた行になった。
  - 切り分けは `printf 'A\t\t\tD\n' | { IFS=$'\t' read -r a b c d; ... }` を直接叩いて確認した。
  - US（0x1f）区切りへ変更して解決。awkの文字列リテラルは移植性のため `\037`（8進）で書いた
    （`\x1f` はgawk拡張で、POSIX awkでは解釈されない）。
  - **教訓**: 「区切り文字にタブ」は反射的に選びがちだが、bashの `read` で受けるなら空フィールドが
    消える。値が空になりうるフィールドを持つなら、IFS空白文字以外を使う。
- **ファイル名に空白を含む場合の `<>` 囲みが、意図せず等価性を壊した**……と最初は思ったが、
  調べると逆で、**囲まない従来の書き方のほうが壊れていた**。0009のファイル名は
  「git checkout復元」の空白を含み、CommonMarkではリンクとして解釈されない。
  `commonmark` モジュールで両方の書き方をレンダリングして確認した（従来は `<p>[t](…)</p>` の
  まま、`<>` 付きは `<a href="…%20…">` になる）。生成側で直す方向にした。
  - **教訓**: 「既存と一致しない」を即座に自分の実装のバグと決めつけない。既存側が壊れている
    可能性を、仕様（CommonMark）と実測で切り分ける。

## 敵対的レビューでの追加（push2以降）

- `adversarial-review` スキルで専任サブエージェントへレビューさせ、14件の指摘を得た。
- **指摘を鵜呑みにせず、高確度のものは全て一時リポジトリで再現を取ってから直した。**
  擬似DDR（末尾空白・BOM・ブロックスカラー・0バイト・不正JSON）を置いて `--print` の出力を
  目で確認する、という手順が有効だった。結果、**高確度の指摘はすべて実際に再現した**。
- 最も効いた指摘は「frontmatterの読み取りが**エラーにならず注記だけ黙って消える**」系の4件。
  出力は一見正しくテストも通るため、自分では気づけなかった。
- 次に効いたのは「**新しい手順が、同じファイルの既存の禁止事項と矛盾している**」という指摘。
  `resolve-conflict` の絶対ルールは `--ours` を禁じているのに、自分が足した類型Bの手順が
  `--ours` を使っていた。**節を足すときは、そのファイルの禁止事項が古くなっていないかを見る**。
- 検証手順の順序（生成物の作り直し → 単体テスト）も指摘で気づいた。逆順だと、DDRを改番した
  直後に**必ず**テストが1件落ちる。自分で書いた自己検証テストが原因なのに、その相互作用を
  見落としていた。
