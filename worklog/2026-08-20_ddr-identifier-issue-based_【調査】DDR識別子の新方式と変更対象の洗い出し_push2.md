# worklog: 【調査】DDR識別子の新方式と変更対象の洗い出し

対象: DDRの識別子を連番からissue番号ベースへ変更する（2026-08-20）。
全体作業計画: `plans/ddr-identifier-issue-based.md`
個別作業計画: `plans/【調査】DDR識別子の新方式と変更対象の洗い出し.md`
push回数: 2

## 試したこと

- `ls .claude/docs/ddr/*.md | wc -l` で現行DDRの実件数を数えた → **55件**。issue本文は
  「既存の連番DDR 58件」「現行DDR 54件」と2つの数を挙げていたが、どちらとも一致しない。
  番号は 0003〜0059 の連続で、欠番は 0001 / 0002 / 0008 / 0015 の4つ（移植時に持ち込まなかった
  もの。`.claude/docs/README.md` の注記どおり）。57 − 2（0008・0015）= 55 で計算が合う。
- `ls .claude/docs/ddr/ | grep -oE '^[0-9]{4}' | sort | uniq -d` → 出力なし。現時点で重複は無い。
- 番号参照の量を数えた。`(^|[^0-9])[0-9]{4}-[^0-9]` にマッチする行はリポジトリ全体で **262行**
  （うち `.claude/docs/ddr/` の外が251行）。出現回数で数えると919回。
  内訳の上位は `.claude/docs/spec/issue-mr-workflow.md`（130回）、`.claude/docs/README.md`（111回）。
  issue本文の「107箇所」とは数え方が違うが、**桁として「数百箇所」であることは変わらない**。
- 4桁形式を前提にしているスクリプトを探した。`.claude/scripts/` `.claude/hooks/` 配下の `.sh` で
  `[0-9]{4}` を使っているのは次の2箇所のみ。
  - `check-base-conflicts.sh` の `ddr_number_to_reply`（`^([0-9]{4})-`）… **今回の対象**
  - `search-frontmatter.sh:134` の `^[0-9]{4}-[0-9]{2}-[0-9]{2}$` … **日付（`--since` の引数）判定**
    であり、DDRとは無関係。触らない。
- `duplicateDdrNumbers` / `hasDuplicateDdrNumber` の利用側を全数列挙した
  （`resolve-conflict/SKILL.md` 4箇所、`check-base-conflicts.md` 3箇所、スクリプト本体3箇所、
  単体テスト多数）。

## うまくいったこと

- **`i<issue番号>-<枝番2桁>-<タイトル>.md` を採用した。** 先頭が数字でないため
  `^[0-9]{4}-` に絶対マッチせず、新旧を正規表現1本で判別できる。
- **枝番を1件しか作らない場合も必須にした。** 後から2件目を足すときに1件目の改番が要らない
  （＝DDR本文不変の原則を破らずに済む）。「1件なら省略、2件目から付ける」案は、まさに
  今回無くそうとしている「後から番号を振り直す」作業を再導入してしまうため却下した。
- **issue番号のゼロ埋めをしない**と決めた。`#133` とファイル名 `i0133-01-...` の数字が一致し、
  「何桁に揃えるのか」という新たな転記ミスの余地を作らない。
- 検知ロジックは**削らずに残す**と決めた。新方式では衝突しないが、既存の連番DDRが両ブランチで
  同時に触られる可能性はゼロではなく、また同一issueを別ブランチで追加作業した場合に枝番が
  ぶつかりうるため、検知そのものは残す価値がある。

## ダメだったこと

- ゼロ埋め無しの副作用として、**ディレクトリの並び順が番号順にならない**
  （`i0099-01` が `i0133-01` より後ろに来る）。これは受け入れる。DDRはもともと番号順に通読する
  ものではなく、`doc-search`（frontmatterインデックス）と `.claude/docs/README.md` の一覧から
  引くため。README側は**issue番号の数値順**に並べることで補う。
- JSON出力のキー名（`duplicateDdrNumbers` / `hasDuplicateDdrNumber`）を
  `...Identifiers` へ改名する案は却下した。これらは複数のスキル・specから参照される公開
  インターフェースであり、改名は「参照の追従漏れ」というこのissueが無くそうとしているリスクを
  自ら作り出す。**内部の純粋関数名だけを改名し、JSONキーは据え置く**。
