# worklog: 【調査】配布経路と追加資産の設計判断

対象: issue #33 配布テンプレート資産の整備（2026-08-20）。
全体作業計画: `plans/配布テンプレート資産の整備.md`
個別調査計画: `plans/【調査】配布経路と追加資産の設計判断.md`
push回数: 2

## 試したこと

- `gh` CLIの有無を確認した（SessionStart hookの報告どおり不在）。issue取得はMCP
  （`mcp__github__issue_read`）で行った。
- `sync-assets.sh` / `install-to-project.sh` を通読し、コピー対象と配置方法を洗い出した。
- issue #26 本文を取得し、層分け（core/seed/merge/local）と `sync-assets.sh` 廃止予定を確認した。

- 使い捨ての空リポジトリ（`git init` した一時ディレクトリ）へ `install-to-project.sh` を実際に
  適用し、配布先が元から持つ `.gitattributes` / `VERSION` / `.gitignore` がどう扱われるかを観測した。

## うまくいったこと

- 実機観測により、`.gitattributes` とルートの `VERSION` が**配布経路にまったく載っていない**ことを
  確認できた（読解だけでは「列挙漏れ」なのか「意図的な除外」なのか判断がつかなかった）。
- 配布先が `VERSION` に `1.2.3` を持っている状態を作ったことで、「ルートへVERSIONを置く案」が
  配布先のアプリの版を壊すことを、仮定ではなく実物で示せた。
- `.claude/VERSION` へ置くと `sync-assets.sh`（`.claude/*` のループ）と `install-to-project.sh`
  （`safe_copy_dir` の `find -type f`）の両方に**スクリプト変更なし**で載ることが分かった。

## ダメだったこと

- 当初は「`.gitattributes` も他のルートファイルと同じく `safe_copy_file` で配ればよい」と考えていたが、
  配布先に自前の `.gitattributes`（`*.png binary` 等）を置いて試した時点で不採用になった。`.bak` 退避が
  あっても、バイナリのテキスト化のように**気づかないまま履歴へ残る破損**を招くため。`.gitignore` と
  同じ行追記へ切り替えた。
- 調査の副産物として、配布先へ `index.jsonl`（10件以上）と `.claude/state/` が混入すること、
  追記される `.gitignore` の行が実際の状態ディレクトリ（`/usage/`・`/.claude/state/`）と食い違って
  いることが見つかった。どちらも issue #26 の受け入れ条件が既に扱っているため、本issueでは直さず
  記録に留めた（二重対応を避けるため）。
