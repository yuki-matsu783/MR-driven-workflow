# worklog: 【調査】【実装】Windows版jqのCR付与によるテスト失敗の修正

対象: issue #94（2026-08-20）。
全体作業計画: なし（Planモードを経由しない非対話セッションのため個別計画のみ）
個別作業計画: `plans/【調査】【実装】Windows版jqのCR付与によるテスト失敗の修正.md`
push回数: 1

## 試したこと

- **スタブ`jq`による再現（1回目・失敗）**: 「Windowsネイティブjqは各行末にCRを付ける」を
  そのまま再現するスタブ（`sed 's/$/\r/'`）を作りPATHの先頭へ置いたところ、12本中6本が
  大量に失敗した（`test_vcs_provider.sh` で37件など）。issueの報告値（1件だけ失敗）と合わない。
- **モデルの見直し**: issueコメントの実測値（3行の値でCRが2個＝行数−1）を読み直し、
  「コマンド置換は末尾の `\r\n` をまとめて落とす」という**MSYS bash側の性質**を合成しないと
  実機の値にならないと気づいた。Linux bashは末尾の `\r` を残すため、素朴なスタブでは
  厳しすぎる（実機では起きない失敗を出す）方向にずれる。
- **スタブ2回目（成功）**: 最終行**以外**へCRを付ける（`sed '$!s/$/\r/'`）に変えたところ、
  `test_post_issue_create_notice.sh` が `passed=13 failures=1` となり、失敗するアサーション名まで
  issue本文と一致した。
- **横断確認**: `tr -d '\r'` の無い `jq -r` を全件列挙し、取り出す値が複数行になりうるかで
  絞り込んだ。あわせて `jq -c` / 素の `jq` をコマンド置換で受けている箇所も確認した
  （いずれも1行出力のため対象外）。
- **スタブ残差の切り分け**: 修正後もスタブjqで5件が失敗し続けたため、実際の不具合かどうかを
  1件ずつ確認した（下記「ダメだったこと」）。

## うまくいったこと

- スタブjqによる再現が、原因の理解が正しいことの確認になった。`passed=13 failures=1` という
  報告値をそのまま再現できたため、修正後に `failures=0` になったことをWindows実機なしでも
  根拠を持って言える。
- 横断確認を「複数行になりうるか」で絞り込んだことで、95箇所のうち修正対象が2件に定まった。
  機械的に全件へ `tr` を足すと、毎ツール呼び出しで発火するhookにも不要なforkが入っていた。
- `Github.sh` の `github_get_mr_unresolved_comments` に除去が無く、GitLab側の対応関数
  （`gitlab_format_discussion_notes`）には入っている非対称を見つけられた。テストが無い箇所
  （`gh` CLI依存）なので、テストを流すだけでは見つからなかった。

## ダメだったこと

- 素朴なスタブ（全行にCR）を「Windowsの再現」として使いかけた。そのまま進めていたら、
  実機では壊れていない単一行の `jq -r` を含む95箇所を機械的に直すことになっていた。
  **再現スタブは、報告されている失敗件数まで一致することを確認してから使うべき**だった。
- 修正後もスタブjqで5件失敗し続けた件は、いずれもスタブ側の限界だった。
  - `test_vcs_provider.sh` の4件: `jq -r ... | head -1` / `| sed -n '3p'` と後段が挟まる形。
    実jqは最終行にもCRを付けるので後段を通してもコマンド置換が落とせるが、スタブは最終行に
    CRを付けないためずれる。issueコメントの実機実測（`passed=131 failures=0`）とも整合する。
  - `test_extract_frontmatter.sh` の1件: テストが `PATH="$fake_bin"` とPATH自体を差し替える
    ケース。スタブが内部で呼ぶ `sed` もPATHから消えて空を返していた。
  - 一時「実は他にも壊れている」と読みかけたので、**スタブの限界を規約へ書き残した**。

## 次の一歩

- 特になし（完了）。Windows実機での最終確認（`failures=0`）だけは実機を持つ担当者に委ねる。
