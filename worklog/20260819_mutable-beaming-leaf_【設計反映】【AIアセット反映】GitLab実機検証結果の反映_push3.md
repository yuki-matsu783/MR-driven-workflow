### 設計反映（flow-id 4-6・1周目）

レビューで3点の判断を得た（DDR 0026は作成する／`MSYS_NO_PATHCONV`は追記する／
`docs-workflow.md`の矛盾は別issue）。判断はチャットで交わされたためMR上に記録が残らず、
**MRコメントとして明示的に投稿した**（この運用自体をフローへ組み込む件は issue #50 として起票）。
`docs-workflow.md`の矛盾は issue #51 として起票済み。

反映内容は次のとおり。

- **spec「Draft PR作成失敗時の自動リトライ」節**: 「`gh pr create` / `glab mr create` が失敗する
  既知の制約があった」という**両プロバイダを並べた記述を訂正**し、GitHub固有であることと、
  GitLab CE 18.5.4での実測を表で示した。DDR 0026へのリンクを追加。
- **spec「提供関数」表**: `add_mr_comment` のGitLab実装欄を `glab mr note --message` →
  `glab api`（notes追加）へ。`get_mr_unresolved_comments` の説明にシステムノート除外を追記。
  表の直後に「上表は`Provider.sh`経由の共通インターフェースであり内部ヘルパーは含まない」旨の
  段落を足し、`gitlab_format_discussion_notes` の位置づけ（単体テストのための切り出し）を書いた。
- **spec「issue作成（AIエージェント代行）」節**: `gitlab_new_issue` の未検証注記を実態へ更新。
- **spec「決定済み事項」**: GitLabのシステムノートの扱いを新規項目として追加。
  `resolvable`/`resolved` とは別軸の除外条件であること、GitHub側は不要であることを明記。
- **spec「未決定事項・懸念点」**: 「GitLab側の動作未検証」を**部分解消**として書き換え。
  残る未検証範囲を3点（ディスパッチャ経由／バージョン・エディション／プロジェクト構成）に整理した。
  同様に `gitlab_new_issue` の項目も解消として更新。
- **spec「影響範囲」**: issue #48分の新規エントリを末尾に追加。
- **DDR 0026 新規作成**、`.claude/docs/README.md` のDDR一覧へ追記。

#### 「触ってよい節／触ってはいけない節」の切り分けが実際に効いた

`git diff` の削除行（`-`）だけを抜き出して確認したところ、削除は
「提供関数」表2行・リトライ節本文・issue #25節・未決定事項2項目に限られ、
**「影響範囲」の過去エントリからは1行も削除されていない**ことを機械的に確認できた。

特に L968 の `- \`dev-tools/src/vcs/Gitlab.sh\`（\`gitlab_new_issue\`を追加。未検証）` は、
「未検証」という語だけを見て一括置換していれば確実に壊していた行である
（issue #24で実際に起きかけた事故と同じ形）。**検証手順として「削除行だけを見る」を
先に決めておいたのが有効だった。**

#### DDR 0005 の扱い

`git status` に `0005-...md` が現れないことを確認した。0026は0005を置き換えるものではなく、
適用範囲をプロバイダ単位で限定する追記的な決定という位置づけのため、
`superseded_by` は付けていない。

## うまくいったこと

- 反映計画を書く前にspecを実際に読み、**触ってよい節（現在の状態）と触ってはいけない節
  （過去のchangelog）を先に切り分けられた**。issue #24で歴史を破壊しかけた前例があるため、
  この切り分けを計画段階で明文化し、検証手順も「`git diff` の削除行だけを見る」と決めておいた。
  結果として過去エントリを1行も壊さずに済んだ。
- 「GitLab側の動作未検証」を**削除ではなく部分解消として書き換えた**。全13関数を通したとはいえ
  ディスパッチャ経由・他バージョン・サブグループ構成は未検証であり、まとめて消していれば
  「GitLabは完全に検証済み」という誤った印象を残していた。
- チャットで交わされたレビュー判断をMRコメントとして残した。記録が消える構造上の問題に
  気づけたため issue #50 として起票できた。

## ダメだったこと

- レビュー判断をMRへ残す運用が抜けていた（issue #50 で対応予定）。SKILL.mdの `comments` 手順は
  「MRにコメントすることを促す」としか書いておらず、AI側が記録する責務になっていなかった。
