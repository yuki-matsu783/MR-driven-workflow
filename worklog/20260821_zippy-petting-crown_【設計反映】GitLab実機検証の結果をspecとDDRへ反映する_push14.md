# worklog: 【設計反映】敵対的レビュー（フェーズ4・2回目）への対応

対象: issue #127 の設計反映に対する敵対的レビューと修正（2026-08-21）。
全体作業計画: `plans/zippy-petting-crown.md`
個別作業計画: `plans/【設計反映】GitLab実機検証の結果をspecとDDRへ反映する.md`
push回数: 14

## 試したこと

- 設計反映のdiffを対象に敵対的レビューを実施（フェーズ4・2回目／最大3回）。12件の指摘。
- 確度×重大度の振り分けで7件をMRへ投稿（`{"posted":7,"summarized":0}`）。
- **投稿の可否とは別に、12件すべてを実ファイルと突き合わせて真偽を確かめた。**
  - `Provider.sh` から `gitlab_*` を参照しているかをループで機械的に数え、
    **ディスパッチャを持つのは20関数・持たないのは7関数**であることを確定した。
  - `gitlab_summary_post_kind` / `gitlab_add_mr_inline_comments` の実装を読み、
    **`summarized=0` でも `gitlab_add_mr_comment` が必ず1件投稿する**ことを確認した。
  - PAT取り出しの書き換えは、実際の `glab auth status --show-token` の出力へ当てて
    （トークン値は出力せず長さと先頭3文字だけを確認して）動作を検証した。

## うまくいったこと

- **11件を修正できた**（残る1件は「数値の断面が違う」というもので、何を数えた値かの併記で解決）。
- **最も重い3件が同じ原因に収束した**: 「全27関数を `Provider.sh` 経由」「残る未検証は
  バージョン・エディションの1点だけ」「検証状況の正が2つ」は、いずれも**同じ主張を
  4ファイルへ複製した**ことに起因していた。正を `issue-mr-workflow.md`「未決定事項・懸念点」の
  1箇所に決め、`Gitlab.sh` ヘッダ・`shell-scripts.md`・新規specは参照だけにした。
- **新規specへ `## 背景・目的` と `## 未決定事項・懸念点` を足せた。** 未解決事項（折りたたみの
  再現条件）が「落とし穴」節の中に埋もれていたのを、他specと同じ場所へ移した。

## ダメだったこと

- **今回の設計反映そのものが「ヘッダの記述が実態と合わなくなった」ことの訂正だったのに、
  訂正の過程で同じ構造（複数ファイルへの複製）を新たに作っていた。** 「実態に合わせて直す」
  だけでは足りず、**次に実態が動いたときに1箇所を直せば済む形にする**ところまでが訂正である。
- **数を「丸めて」書いた。** 27関数のうち20だけがディスパッチャを持つと知っていたのに
  （同じcommitの別の場所にそう書いている）、要約では「全27関数を `Provider.sh` 経由」と
  書いた。要約の側で情報を落とすと、詳細と食い違う。
- **`glab auth status --show-token` の出力を確認する際、マスク用の `sed` パターンが実際の
  出力行（`Token found in operating system keyring: <値>`）に合っておらず、トークンが
  そのまま出力に現れた。** ローカル検証用GitLabのトークンだが、**マスクは「そのパターンが
  実データに当たるか」を確かめてから使う**（当たらないマスクは無いのと同じで、しかも
  マスクしたつもりになる分たちが悪い）。
