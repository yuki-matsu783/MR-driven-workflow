  確定する**と計画に書いておいたのが効いた（SKILL.md と同じ位置に機械的に合わせていたら、
  今度は逆に不要な位置変更をするところだった）。
- **節の見出しは同名にしない**。SKILL.md 側は `### issueが大きすぎる場合の分割提案（issue #64）`、
  spec の `## 影響範囲` 側は `### issue #64（issueが大きすぎる場合の分割提案ルールの追加）` とした。
  spec内で `grep 'issue #64'` したときに、仕様節とchangelogエントリを見分けられる。

  作業4の1行（39行→40行）のみで、DDR本文・spec `## 影響範囲` の過去エントリが1行も
  変わっていないことを機械的に確認できた。目視だと1400行超のファイルでは確認しきれない。

## ダメだったこと

- **`{ sed -n '1,Np'; cat 追加分; sed -n 'N+1,$p'; }` で本文を差し込む際、空行が二重になった／
  逆に足りなくなった**。追加分のファイルが先頭に空行を持っていたため、分割点の直前の空行と
  重なって2行連続の空行になり、末尾には空行が無いまま次の `## 設定項目` に接した。
  **差し込むファイル側は「先頭に空行を置かず、末尾に空行を1つ置く」形に揃える**のが分かりやすい
  （今回は事後に `sed -i` で調整した）。
- **`python - <<'EOF'` によるテキスト置換が使えなかった**。この環境の `python` はPython 2で、
  非ASCII文字を含むスクリプトを標準入力から渡すと `SyntaxError: Non-ASCII character ... but no
  encoding declared` になる。日本語を含む置換は `sed -i` で足りる範囲に収めるのが確実。

## 判断したこと

- **spec の新節には判断基準の詳細を書かず、「正は SKILL.md 側」と明記した**。issueの分割基準は
  AIエージェントが実行時に読む運用ルールであり、specは「そういう位置づけの機能がある」ことと
  意思決定へのリンクを持てばよい。同じ基準を2箇所へ書くと片方だけ更新されて食い違う
  （`issue-create` 側を参照のみに留めたのと同じ理由）。
- **`## 影響範囲` のエントリに、SKILL.md の挿入位置を変更した経緯を含めた**。「なぜ
  `計画の2階層構造` の隣ではないのか」は、後から読むと不自然に見える箇所であり、
  記録が無いと次の改訂で「揃えるべき」と判断して壊されうる。
