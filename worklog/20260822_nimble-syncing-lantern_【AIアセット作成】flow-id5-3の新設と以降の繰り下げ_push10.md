# worklog: flow-id 5-3 の新設と以降の繰り下げ（push10）

対象: issue #70 / PR #157 / flow-id 3-6

## 危うかった箇所（機械置換だけなら壊していた）

計画は「降順に置換する」としか書いておらず、**それだけでは足りなかった**。実際に踏みかけた
のは次の5類型で、いずれも「降順かどうか」とは無関係である。

### 1. 生成物を直接編集しかけた（`.claude/docs/README.md`）

初回の dry-run で README.md に**7件**の置換が出た。中身を見ると4件は DDR一覧の行で、これは
`generate-ddr-list.sh` が **DDRの `note` frontmatter から生成する**ものだった。直接書き換えても
次の生成で消える。**`note` 側を直し、生成し直す**のが正しい。

- 手書きなのは spec一覧の1行だけで、そちらは直接編集でよい。**同じファイルの中に、生成される
  部分と手書きの部分が同居している。**

### 2. 「当時の番号」と「現在の番号」が同じ行に同居する（4件）

```
（**issue名の `5-1` は当時の番号**。片付けは issue #112 の並べ替えで 5-3 になり、issue #111 の
統括レポート追加でさらに繰り下がって現在**flow-id 5-4** である。…）
```

この行は `5-3`（当時）と `5-4`（現在）を両方含む。**行単位の保護／非保護では表現できない。**
自動置換から外し、現在の番号だけを手で直した。

### 3. 置換対象の範囲外にある片割れ（節見出し）

`### なぜ 5-2 と 5-4 の間なのか` は、`5-4` だけが置換されて
`### なぜ 5-2 と 5-5 の間なのか` になった。**`5-2` は繰り下げ対象ではないので機械置換では
直らないが、意味としては「5-3 と 5-5 の間」に変わっている。** 数え上げ系の検証
（`flow-id 5-N` の件数）でも引っかからない。

### 4. 数字を含まない表現（`42ステップ`）

`5-[3-7]` にマッチしないため、grepベースの棚卸しから丸ごと漏れる。6箇所あった。
**「flow-idの繰り下げ」という語感に引きずられると、総ステップ数の存在を忘れる。**

### 5. `## 影響範囲` の外にある point-in-time の記録

`.claude/docs/spec/issue-mr-workflow.md` は L1754 以降が changelog なので節単位で保護できる、
と考えたが、**`## 仕様` 節の中にも4行あった**（L637・643・652・674）。「新設当時は 5-3」
「旧5-3→5-4、旧5-4→5-5 へ繰り下げ」のような記述である。節で切るだけでは足りない。

## 検出に効いた手立て

**削除行と追加行を `5-N` で伏せ字にして突き合わせ、対応の付かない削除行だけを列挙する。**

```python
norm = lambda l: re.sub(r'5-[1-7]', '5-N', l)
orphan = Counter(deleted_lines_normalized) - Counter(added_lines_normalized)
```

繰り下げただけの行は削除・追加が相殺されて消えるので、**残るのは「繰り下げ以外の変更」だけ**に
なる。19件出て、すべて意図した手修正であることを確認できた。逆に、意図せず内容を落としていれば
ここに現れる。

- `git diff | grep '^-'` を目で追う方法では、125件の削除行を全部読むことになり実質不可能だった。
- **この検証は「削除がゼロであること」ではなく「削除が説明できること」を見ている。** 繰り下げは
  必ず削除行を生むので、ゼロを条件にはできない。

## 1パス置換にした理由

計画は「降順に置換する（`5-6`→`5-7` → `5-5`→`5-6` → …）」としていたが、
**`re.sub` のコールバックで `+1` する1パスに変えた。**

```python
re.sub(r'(?<![0-9-])5-([3-6])(?![0-9])', lambda m: '5-' + str(int(m.group(1)) + 1), line)
```

降順でも結果は同じだが、**順序を1回でも間違えると静かに多重繰り下がる**。1パスなら、
順序という守るべき前提そのものが無くなる。

## やらなくてよかったこと

計画の手順5（`cleanup-task.sh` の `HANDOFF.md` 雛形へ新設行を足す）は**不要だった**。
雛形は進捗表を持たず `（進捗表は次タスク着手時に記入する）` の1行だけだった。
`update-handoff-progress.sh` の `LOOP_RANGES` もフェーズ5の範囲を持たない。

**計画を書いた時点では中身を確認していなかった**ということで、確認したうえで「不要」と
結論づけた事実自体は記録に残す（次に同じ繰り下げをする人が、また同じ確認をしなくて済むように）。
