## 試したこと

- 矛盾の全量把握: `grep -rn "PR作成\|pr create\|pr merge\|明示的に指示\|人間が実施"` でリポジトリ全体を
  走査した。方針と衝突する記述は次の3箇所だけだった。
  - `.claude/rules/git-workflow.md:102`（「PR作成・レビュー依頼・マージは人間が実施する」）
  - `.claude/skills/issue-mr-flow/SKILL.md`「PRがflow-id 5-1実施前にマージされてしまった場合の
    対処」手順4（「PR作成・マージの実行は…明示的な指示を受けてから行う」）
  - flow-id 1-3 / 5-4 の担当欄（明示指示の要否が書かれていないため、読み手が
    `git-workflow.md` 側の原則を当てはめてしまう）
  `index.md` / `README.md` / `DEVELOPERS.md` / `apply-mr-workflow-to-project` には担当の記述が無く、
  修正対象外だった。
- 線引きの基準を「担当者の役割分担」ではなく「**その操作が取り消せるか**」に置いた。
  作成・description更新・レビュー返信・Draft解除はいずれもクローズ／書き直し／Draftへの差し戻しで
  取り消せて `main` を変えないのに対し、マージだけが `main` の正史を書き換える。
- ハーネス側の指示との優先順位: 「リポジトリ方針を優先（フロー定義への準拠を明示的な依頼とみなす）」と
  「ハーネス側を優先」の2案を比較し、後者を採った。前者は衝突の解釈をAIに都度委ねる形になり、
  issue #41 が問題にした非再現性が戻るため。
- 挿入位置の確認: `.claude/rules/docs-workflow.md`「既存ドキュメントへ新しい見出しを差し込むときは、
  挿入位置の直前の節が『その節全体にかかる地の文』で終わっていないか」に従い、SKILL.md の
  `## サブコマンド` 直前（直前はissue分割の箇条書きの末尾）と、spec の `### 計画の2階層構造` 直前
  （直前はサブコマンド6種を述べる段落）をそれぞれ確認したうえで差し込んだ。

## うまくいったこと

- **再現性の要点を「必ずPRを作る」ではなく「毎回同じ判断になる」と捉え直したこと**が、ハーネス衝突の
  設計を決めた。ハーネス側を優先しても、そこから先の振る舞い（ブランチ作成まで → `AskUserQuestion` で
  1回だけ確認 → 応答を待てないならPRを作らずその事実を明示）を決め打ちにすれば、issue #41 の
  受け入れ条件「環境に関わらず同じ判断に到達する」は満たせる。
- 確認の対象をPRの**新規作成のみ**に限定できた。ハーネスが制限しているのはPR作成であって既存PRの
  更新ではないため、flow-id 5-3（Draft解除）・`describe`・`reply` はこの確認を挟まずに済む。
  フロー後半で人間待ちが増えない。
- flow-id 5-2（コンフリクト検知・解消）の担当は変更不要だと確認できた。作業ブランチ上の操作で
  `main` を変えないため、新しい線引きと最初から整合していた。この「変えなかった理由」もspecの
  changelogへ明記した。
- SKILL.md の `start` 手順に項目を1つ挿入した際、既存の `c.` が `d.` へ繰り下がったため、
  `grep -rn "手順c\|手順 c"` で参照が壊れていないことを確認した（該当0件）。
