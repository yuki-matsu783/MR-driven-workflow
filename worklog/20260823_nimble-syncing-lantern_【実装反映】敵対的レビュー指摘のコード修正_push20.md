# worklog: 【実装反映】敵対的レビュー指摘のコード修正

## 試したこと

- 計画の5件のうち、**5件目（`read -d ''` の実機計測）は main が先に片付けていた。**
  PR #162（issue #159）が `.claude/rules/shell-script-style.md` へ「1バイトずつ read(2) する」
  という注意そのものを入れており、こちらで書くはずだった内容と重複していた。**残っていたのは
  「ではどう測るのか」だけ**だったので、そこだけを同じ節へ足した。
- 修正ごとに**意図的に壊して落ちる件数を測った**（検出力の確認）。4件すべてで、直した箇所を
  壊すとテストが落ちることを確かめてから次へ進んだ。
- `.gitignore` の `/.claude/settings.local.json` は**既に存在した**（main の PR #158 が
  OTel 対応で入れていた）。計画は「追加する」と書いていたが、実際に要ったのは
  **配布先の `.gitignore` へ配ること**（`install-to-project.sh`）だった。

## うまくいったこと

- **CR対応を入口と出口の両方で入れた。** 当初は出口（`convert_settings` の `tr -d '\r'`）だけを
  考えていたが、入口（`mapfile` が CRLF の `agents/*.md` を誤診する）も同じ根の問題だった。
  spec へ表で並べて書いたことで、片方だけ直すと不完全だと分かる形になった。
- **`build_into` の失敗条件を「コピー対象0件」から「列挙0件」へ狭めた。** `agents/*.md` と
  `settings.json` は変換で作るので、その2つしか無い `.claude/` でも生成物としては成立する。
  0件のときは原因を3つに切り分けてメッセージへ出すようにした。
  - **`main` が先に `git rev-parse --show-toplevel` へ `cd` していることに、書いてから気づいた。**
    もとのメッセージ（「リポジトリルートで実行していますか」）は、その時点で既に成り立たない
    案内だった。原因の切り分けを書こうとして初めて、既存メッセージの誤りが見えた。
- **スタブ `jq`（`sed '$!s/$/\r/'`）で、Linux 上でも Windows native jq の CR 付与を再現できた。**
  「直った」と言い切る根拠がこれで持てる。スタブ自身が実際に CR を付けることも同じテストで
  表明してある（付けないスタブなら検査は無条件に通ってしまう）。

## ダメだったこと

- **自分が追加した前置フィルタが超集合になっていなかった。** `.claude/rules/shell-script-style.md`
  の「push系2本は判定本体がコマンド位置ベースなのでバックスラッシュ除去は要らない」という
  注記を**書いた直後に、その場で反例を作って確かめたら偽だった**。
  - `git pu\sh` は精密判定では push と読まれるが、生JSONには `pu\\sh` としか現れないので
    `*push*` が一致しない。`git pu\<改行>sh` に至っては、バックスラッシュ1文字だけの除去でも
    `punsh` になって取りこぼす。
  - **issue #159 が `commit` 側で塞いだのとまったく同じ穴を、`push` 側に開けたまま出していた。**
    しかも T11 のテストは「超集合であること」を主張していたのに、ケース一覧にバックスラッシュが
    無かったため通っていた。**主張しているのにケースが無いテストは、通っていても根拠にならない。**
  - 教訓を「語ごとに考えないこと」として同じ節へ残した。判定対象が `commit` か `push` かは
    関係が無く、**精密判定が正規化するなら前置フィルタも同じ正規化をする**、が正しい形である。
- **注記を書くという行為自体が検証になった。** 「〜なので要らない」と書こうとして根拠を
  示そうとしたら、反例が出た。断定を書く前に必ず実際に動かすこと。
- テストが `prefilter_passes` を**写経していた**のも同根の弱さだった。実装を `source` して
  呼ぶ形へ変え、2本の実装が同一であることも別途表明した。
