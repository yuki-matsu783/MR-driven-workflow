## 試したこと

- **NULバイトの有無を3系統で確認した**（issueの事象1）。
  1. `file .claude/docs/spec/*.md` → 全て `Unicode text, UTF-8 text`（`data` 判定は無し）
  2. `git ls-files -z` で全追跡ファイルを走査し `wc -c` と `tr -d` の結果を比較 → 差分ゼロ
  3. `python3` で `bytes.count` によるNULの数え上げ → 0
- リンク切れの網羅調査を、目視ではなくPythonスクリプト（markdownのリンク記法を正規表現で抽出し
  `os.path.exists` で判定）で行った。
- `.gitignore` 1行目の由来を `git log --follow` で遡り、最初の「輸入」コミット時点から
  存在することを確認した。

## うまくいったこと

- **リンク切れは機械的走査で5件見つかった**（issue記載は2件）。追加の2件は
  `.claude/docs/ddr/0019-...md:79` の `0002-...` 参照と `index.md:37` の `./plans/`。
  受け入れ条件が「リポジトリ内の**全**markdownの相対リンクが解決する」であるため、
  5件すべてを対象に含めた。修正後の再走査で0件になった。
- **事象4は「文書側を`Default.md`へ統一」を採用した。** `Default.md` はGitLabの予約名で、
  新規issueの説明欄へ**自動適用**される。`task.md` へ改名するとテンプレート選択が手動操作に
  なり、「issueテンプレート標準化」という当初目的が損なわれる。実体を正とし文書9箇所を直した
  （issue記載は8箇所。specのツリー図中の裸の `task.md` 1行が加わる）。詳細はDDR 0035。
- **DDR 0019 の本文は「追記のみ」の範囲に収めた。** リンク記法だけを外し、表示テキスト
  （`DDR 0014相当のissue #43`）はそのまま残したうえで `（移植元のDDR 0002。本テンプレートには
  未同梱）` を追記した。決定内容の記録は一切書き換えていない。
- `index.md` の `./plans/` `./build/` は、実体を作るのではなくリンク記法を外した。
  前者はflow-id 5-1で削除される寿命、後者は `.gitignore` の `/build/` 対象で、いずれも
  Git管理下に実体を持てない。「なぜリンクにしていないか」を各行へ併記した。

## ダメだったこと

- **`od -c` の出力を誤読しかけた。** `sed -n '94p' ... | od -c` の結果に `0` が現れたのを
  NULバイトだと判断しかけたが、`od -c` はNULをバックスラッシュ付きの表記で示し、
  **印字可能文字はそのまま出す**。この `0` は本文「要素0個なら」の**数字のゼロ**だった。
  Pythonでのバイト数え上げまで行って初めて確定できた。NULの有無は `od` の目視ではなく
  `tr -d` の前後でバイト数を比較して判定する。
- **`git ls-files` の出力をそのままループへ渡して失敗した。** 非ASCIIパスが
  `"\343\203\254..."` の形にクォートされ、`wc -c < "$f"` が `No such file or directory` に
  なった。`git ls-files -z` ＋ `while IFS= read -r -d ''` で受ける必要がある
  （`.claude/rules/shell-script-style.md`「コマンド置換とNULバイト」の良い例2と同じ形）。
- 事象1は**既にissue #69（PR #78）で解消済み**だった。specの `## 影響範囲` に
  「本ドキュメント内に紛れ込んでいた生のNULバイト1個を、意図どおりのエスケープ表記へ直した」
  という記録が残っていた。着手前に対象ファイルのchangelogを読めば、走査の前に分かった。
