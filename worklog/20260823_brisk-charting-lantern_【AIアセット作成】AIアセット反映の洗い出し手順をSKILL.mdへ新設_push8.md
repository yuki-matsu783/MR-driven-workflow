## 試したこと

- 計画の順序どおり6ステップで実施した（除外規定 → 新節 → 4-1/4-6行 → 表と地の文（同時）→
  観点表 → 検証）。
- **置換はすべて python の `str.replace` で行い、事前に `count == 1` をアサートした。**
  `sed` だと複数箇所へ誤爆しても気づけないため。5箇所すべてで1件だった。
- 検証は計画の表（V1〜V7）と、新節の範囲を絞った5本を実行した。**12本すべて期待値どおり。**

## うまくいったこと

- **`count == 1` のアサートが「照合文字列が一意である」ことの実行時の確認になった。** 計画段階で
  `grep -c` を実測しているが、実際に置換する時点でもう一度確かめられる形になっている。
- **「下記」が本当に下記であることを実測で確かめられた。** 参照元5箇所（82・87・131・134・
  167行目）はすべて新節（341行目）より前にある。挿入位置を計画で決めておいたので、確認は
  `grep -n` 1回で済んだ。
- **範囲を絞った検証（`sec()`）が期待どおり働いた。** 変更前は節が存在しないので `sec` の出力が
  空になり5本とも0、変更後はそれぞれ1〜3件。**ファイル全体で数えていたら `.claude/agents/`（2件）と
  `REVIEW-POINTS`（4件）は変更前から通っていた。**

## ダメだったこと

- **レポートの表へ、python の文字列連結（`'` + "\`" + `'`）がそのまま残った。** markdownの
  コードスパンの中にバッククォートを入れようとしてヒアドキュメント側で細工した結果、
  レンダリングされない文字列になっていた。**表のセル内でバッククォートを含むコマンドを見せようと
  すると、たいてい破綻する。** セルには「除外規定の照合文字列」のように説明を書き、コマンド自体は
  コードブロックで別に示す形へ直した。

## 計画から変えた点

- **4類型の表を3列→4列にした**（「反映の向き」を追加）。分類がそのまま次の行動（新規作成／訂正／
  追記／導線の改善）に繋がるため。受け入れ条件（4類型と証拠要求範囲が表で示されている）は列が
  増えても満たす。

## 学び（次回以降に効くもの）

- **置換の一意性は、計画時の `grep -c` と実施時の `count == 1` アサートの2回確かめる。**
  計画から実施までの間にファイルが変わる（今回は自分自身の前段の置換で変わる）ため、
  計画時の実測だけでは足りない。実際、除外規定を先に書き換えた後で4-1行を置換している。
- **markdownの表のセルに、バッククォートを含むコマンドを書かない。** コードスパンの入れ子は
  素直に書けない。説明をセルに置き、コマンドはコードブロックへ出す。
